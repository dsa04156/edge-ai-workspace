# 디바이스 매니저 v1

> 2026-09-30 · ② Device Manager의 첫 로컬 구현. Profile 연결·상태 조회 범위다.
> 워크플로우·스케줄링·서비스 실행·VD 생성은 다음 단계다. 운영 배포 상태는 docs/현재-구현-상태.md를 따른다.

## 화면에서 하는 일

로컬 주소: `http://192.168.0.56:8768/#device-manager`.

**기존 NEXUS 대시보드의 왼쪽 메뉴 → 디바이스 관리**에서 연다. 운영 현황·디바이스 관리 중
장비 사양을 관리하는 별도 페이지다. 네비게이션은 기존 것을 유지하며 iframe·새 브라우저 탭을 사용하지 않는다.
운영 현황 등을 다녀와도 선택 장비와 작성 중 사양 입력이 유지된다.
장비 읽기 원본과 로컬 Profile/연결 DB는 그대로 사용한다.

1. **연산 장비 → 장비 선택**으로 현재 자원 상태·장비 사양·실행 서비스를 조회한다. 선택만으로
   편집 폼을 열거나 Profile을 생성하지 않는다.
2. 사양 표는 **자동 관측(Kubernetes 보고값)**과 **수동 등록(저장한 Profile)**을 나란히 보여준다.
   관측 조회 시각과 사양 등록 시각을 구분한다. 등록 시각을 하드웨어 확인 시각으로 취급하지 않는다.
   보고 CPU/RAM은 제조사 총용량과 다를 수 있고, GPU/runtime·물리 여부는 추정하지 않는다.
3. **사양 편집**을 누르면 기존 등록값을 우선 불러온다. 미등록 장비는 보고값으로 초안을 채운다.
   이름은 architecture별 `compute-arm64` 등의 초안 이름, 버전은 해당 이름의 미사용 다음 버전으로
   제안한다. 장비 모델을 추정한 이름이 아니며 **고급: 프로파일 이름·버전**에서 변경할 수 있다.
4. **사양 저장**은 새 버전 저장·선택 Node UID 연결을 한 transaction으로 처리하고 조회 화면으로
   돌아간다. 다른 장비 연결은 유지한다. 자동 조회로 수동 사양을 덮어쓰지 않는다.
   **취소**는 해당 장비의 미저장 초안만 버린다.
5. **고급: 프로파일 연결 관리**에서 기존 Profile 연결·해제·새 Profile 추가를 수행한다.
   상단 **공용 프로파일**에서는 독립 Profile 추가·새 버전 작성·미사용 버전 삭제가
   가능하다. 참조 중인 버전은 삭제할 수 없다. 장비 원본 등록·삭제는 포함하지 않는다.
6. **센서·입력**은 기존 EdgeX Device/Profile·연결·데이터 수신 상태를 읽는다. 센서 Profile 변경은
   기존 EdgeX 절차를 따른다. 연산 장비용 Profile로 복제하거나 수정하지 않는다.

장비 전환 후에는 조회 화면으로 돌아가고 **편집 계속**으로 해당 장비의 초안을 다시 연다.
새로고침 버튼은 초안을 유지한다. 페이지 자체를 새로고침하면 미저장 초안은 사라지고
저장된 Profile/연결만 다시 읽는다.

## 소유권과 저장 범위

| 정보 | 원본·권위 | 이 기능의 동작 |
|---|---|---|
| 노드 이름·UID·architecture·준비 | Kubernetes/KubeEdge | 읽기 전용 조회. 별도 장비 원장을 만들지 않음 |
| 센서 Device/Profile·연결·Event | EdgeX | 기존 typed reader/대시보드 projection 재사용 |
| 예약량과 가용량 | Kubernetes allocatable·Pod requests | 실제 CPU/RAM 사용량과 구분 |
| 실제 사용률 | Prometheus | 원래 observedAt 유지. 오래된/미래/미수집 값은 판단 보류 |
| 실행 서비스 | 공통 RuntimeService 관측 원장 | active·준비·정리 위치 구분. 시스템 Pod를 AI 서비스로 세지 않음 |
| 정적 DeviceProfile 정의·버전 | 로컬 Profile metadata 저장소 | 사용자 선언값. 실행·성능 검증 근거가 아님 |
| 장비와 Profile 연결 | 로컬 Profile metadata 저장소 | 실제 Node UID + Profile 이름/버전 참조만 저장 |

저장 파일은 `DATA_DIR/device-profile-bindings.sqlite3`다. 노드·센서의 상태/telemetry/워크로드
목록을 별도 원장으로 저장하지 않는다. 철회한 logical-device registry와 다른 경로이며
`/logical-devices`, 기존 VD 생성·제어 API를 호출하지 않는다.

- Profile 내용은 동일 name/version에서 고정한다. 같은 내용의 재등록은 중복 생성하지 않는다.
- 참조 버전이 없거나 알려진 architecture가 다른 경우 연결을 거절한다.
- 연결 저장 직전에 노드의 이름과 UID를 다시 읽는다. 같은 이름의 교체 장비로 자동 이전하지 않는다.
- `expectedRevision`이 현재 연결 revision과 달라지면 409로 거절한다. 연결 해제 후에도 revision을
  유지해 오래된 요청이 새 연결을 덮어쓰지 않게 한다.
- 원본 삭제·조회 실패 시 남은 연결을 별도 표시한다. 원본이 없어도 로컬 참조 해제는 가능하다.
- 참조 중인 버전 삭제는 거절한다. 새 버전 등록만으로 기존 장비의 참조를 바꾸지 않는다.
- 네 source의 실패를 따로 표시한다. runtime 원본 실패는 서비스 0개가 아니며 상태 확인 불가다.

## API와 로컬 실행

| 경로 | 기능 |
|---|---|
| `GET /api/v1/device-manager` | 원본별 장비·상태·서비스, Profile 버전·연결 목록 |
| `POST /api/v1/device-manager/profiles` | DeviceProfile 명세 검증 후 불변 버전 저장 |
| `DELETE /api/v1/device-manager/profiles/{name}/{version}` | 미참조 버전만 삭제 |
| `PUT /api/v1/device-manager/nodes/{name}/profile-document` | document/nodeUid/expectedRevision으로 버전 저장·연결 원자 처리 |
| `PUT /api/v1/device-manager/nodes/{name}/profile` | nodeUid/expectedRevision/profileRef로 연결·해제 |

쓰기 기본값은 비활성이다. 로컬 미리보기에서만 `DEVICE_MANAGER_ENABLED=true`를 지정한다.
쓰기 요청은 같은 origin의 JSON과 `X-Device-Manager: 1`을 요구한다.
배포된 원본의 Kubernetes/EdgeX/RuntimeService를 수정하는 API는 추가하지 않았다.

저장소 루트에서 실행한다.

```bash
rtk proxy bash edge-orch/state-aggregator/scripts/run-device-manager-preview.sh
```

스크립트는 `app.device_manager_preview:create_app --factory`를 `0.0.0.0:8768`에 실행한다.
이 앱은 기존 NEXUS `index.html`·정적 파일과 Device Manager router를 제공한다.
기존 대시보드의 `/state/*`, `/api/*` GET은 지정 운영 origin으로 중계하며 응답 오류도 보존한다.
운영 변경 요청은 중계하지 않는다. 로컬 Profile/연결 쓰기만 기존 관리 router로 처리한다.
`app.main`을 import하거나 수집/실행 제어 loop를 시작하지 않는다.
데이터는 기본적으로 `~/.local/state/edgeai-device-manager-preview`에 보관하며 `DATA_DIR`로 바꿀 수 있다.
`DEVICE_MANAGER_READ_BASE_URL`은 운영 aggregator의 `/api/resources`, `/state/devices`,
`/state/runtime-services`를 장비 관리 원본으로 읽고 기존 대시보드 GET도 중계하는 로컬 preview 설정이다. 브라우저 입력으로 URL을 받거나
광역 탐색/fallback을 하지 않는다. 독립 앱은 이 원본 URL 설정을 요구하며 비어 있으면 시작하지 않는다.
Node UID는 로컬 Kubernetes client로 직접 읽는다. 이 mode 차이는 응답 `readMode`에 표시한다.

## 검증과 다음 단계

- 테스트: 불변 버전·영속성·참조 삭제 차단·revision 충돌·UID 교체·architecture 불일치·부분 원본 실패·
  쓰기 차단·서비스 실행/준비/정리·stale 상태를 확인한다.
- 브라우저: 별도 fixture DB에서 등록→연결→새로고침 후 유지→해제→새 버전→삭제를 확인한다.
  실제 8768 미리보기에는 시험 Profile을 등록하지 않는다.
- 미구현: 새 노드 join, 센서 쓰기·등록 변경, Profile 자동 사양 검증, 감사 로그/사용자 인증·권한 체계,
  전체 lifecycle 관리, Workflow·자동 배치·VD 동적 생성. 실제 운영 배포는 별도 단계다.

현재 체크포인트와 배포 상태는 [현재 구현 상태](../docs/현재-구현-상태.md)를 따른다.
