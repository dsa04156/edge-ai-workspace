# 저장소 구조

## 물리 장비의 가상 디바이스 표현 (2026-09-08 승인)

사용자의 명시적인 구현 요청에 따라 물리 source별 읽기 전용 가상 디바이스 표현을 추가한다. `physical-vd:<인코딩된 source ID>`라는 대시보드 논리 ID를 두고 원본 장비, EdgeX 등록 기능, 기존 관측 트윈과 이용 서비스를 연결한다. 이 용어는 장비 수준의 조회 표현에 한정하며 EdgeX inventory·상태 권위나 기능별 관측 트윈의 계약을 변경하지 않는다. simulator·센서 제어·실행 컨테이너가 아니다. 원본 없는 항목에는 가상 ID를 만들지 않는다.

NEXUS의 **가상 디바이스** 탭과 `/#physical-virtual-devices`에서 선택·상세·원본 이동을 제공한다. `source-view.js`의 논리 모델과 기존 GET API를 재사용하며 별도 inventory 저장·등록·쓰기 API는 추가하지 않는다. 상세 계약과 검증 기준은 [물리 장비의 가상 디바이스](물리-가상-디바이스.md)를 따른다.


## 2026-09-08 통합 운영 대시보드 확장

이번 승인 범위는 기존 NEXUS의 서비스 중심 운영 projection, 데이터 비교,
추천·실행 이력 연결과 서버 설계 버전·시험 원장 저장이다. EdgeX 물리 권위와
Kubernetes/KubeEdge node/workload 권위를 유지한다. 설계 저장은 Configured이며
범용 배포·오프로딩을 실행하지 않는다. 현재 실제 가능/부분 구현/미구현과
API·검증·운영 책임은 [통합 운영 대시보드 고도화](통합-운영-대시보드-고도화.md)를 따른다.
로컬 수정 및 검증 상태이며 운영 image 반영은 별도다. 아래 과거 날짜의 운영 기록은
그 시각의 근거로만 읽는다.


## 2026-09-08 가상 디바이스 운영 사이클

사용자 승인 구현 범위는 `virtual-device-test/vd-demo-001` 한 개의 시작·시험 추론·정지와 영속 작업 이력이다. `state-aggregator/app/virtual_device_control.py`가 기존 운영 토큰, 고정 계약과 SQLite 요청 원장을 사용하고 `static/virtual-device-controls.js`가 NEXUS 내부 가상 디바이스 화면에 연결된다. ## 배포 소유권

격리 Llama 버튼 시연의 선택 배포 진입점은
`qualification/llama-offloading/demo-k8s/`다. `gpu_session.py`는 승인된 RTX 5080
임시 사용 및 영속 보상 기록을 소유한다. 전용 SA는 exact-name worker scale과
exact-name 센서 Argo Application patch만 수행하며, 기존 `state-aggregator` 권한은
넓히지 않는다. 센서 Application의 원래 설정은 보존하고 자기 소유 override만 제거한다.
운영 EdgeX root나 legacy placement engine을 이 실험에 연결하지 않는다.

| 대상 | Argo CD Application | 기준 ref |
|---|---|---|
| 중앙 EdgeX·Device Service | `edgex-telemetry` | Application에 선언된 Git ref의 `edgex/k8s` |
| 대시보드 | `edge-orch-state-aggregator` | Application에 선언된 Git ref |
| 문서 사이트 | `docs-html` | Application에 선언된 Git ref + immutable image digest |

`state-aggregator` Deployment Controller가 생성하는 AI workload는 `edge-ai-workloads`
namespace에만 존재한다. 이 동적 workload의 소유자는 Controller이며 Argo CD가 개별
Deployment manifest를 소유하지 않는다. Controller의 권한은 신규 create와 상태 read로
제한하고 기존 Deployment update·patch·delete, migration과 offloading은 지원하지 않는다.
Controller 자체, 전용 namespace와 RBAC는 계속 `edge-orch-state-aggregator` Application이
GitOps로 소유한다.

Runtime Recommendation Engine은 Git Service Catalog에 선언된 workload만 읽고,
Deployment/StatefulSet·Pod·Node·서비스 지표를 결합한다. 최신 상태, dwell/cooldown과 판단
이력은 `state-aggregator` PVC의 SQLite가 소유한다. 추천 결과는 Placement Engine 입력일
뿐 Controller 실행 요청으로 연결되지 않으며 자동 배포·traffic 전환·삭제를 수행하지 않는다.
같은 모듈의 Runtime Execution Plan은 최신 추천을 결정적인 단계 목록으로 projection하며,
별도 실행 상태를 저장하거나 Deployment Controller·Kubernetes·traffic plane을 호출하지
않는다. 대상 workload와 node, 선행조건, 실패조건, 조건부 rollback은 계획 설명에만 존재한다.

`sensor-anomaly-demo/app/inference_executor.py`는 local/remote/fallback 추론 실행 계약과 요청별
latency·authoritative-result metadata를 소유한다. `remote_inference.py`는 Git/Secret으로 승인된
Server1 endpoint 호출, 응답 identity/model/freshness 검증과 runtime mode 전환을 담당하고,
`inference_api.py`는 같은 model adapter를 재사용하는 idempotent Server1 `/infer` endpoint를
제공한다. raw telemetry와 결과 저장은 계속 각각 EdgeX와 ACTIVE edge worker가 소유한다.
`state-aggregator`의 Service Catalog offloading contract는 remote workload/API/architecture/
accelerator/network threshold를 고정하고 기존 `placement.py`의 Filter/Score를 재사용한다.
이는 legacy `placement_engine/`을 운영 경로로 되살리는 것이 아니다.
이 partial offloading 경로는 2026-08-28 현재 checkout의 로컬 검증 대상이며 Argo CD가 동기화한
`07fc3b1` 배포 기준선에는 포함되지 않는다.

Execution Controller는 별도 승인 API에서만 plan을 소비한다.
`app/config/candidate_workload_templates.json`이 source 복제 대신 사용할 서비스별 승인 candidate
계약과 state policy를 소유한다. Controller는 source Deployment·Service·PVC/StorageClass와 target
Node를 읽기 전용 preflight한 뒤 전용 namespace에 신규 Deployment만 생성하고 Ready를 관측한다.
`app/config/candidate_validation_contracts.json`은 Ready 이후 Pod-IP read-only health/input/model/
inference/freshness/latency 검증과 dwell을 소유한다. planId별 실행 record와 단계 상태,
candidate/PVC 식별자, validation check와 감사 event는 같은 PVC의 별도 SQLite 파일이 소유한다.
`app/config/traffic_routing_contracts.json`은 Service/namespace/port/source와 post-switch·rollback
정책을 고정한다. Runtime Controller는 Service selector를 patch하지 않고 자신이 소유한 단일
EndpointSlice만 resourceVersion compare-and-swap으로 갱신하며, switch 전후 snapshot과 서비스별
lock을 SQLite에 보존한다. 현재 EdgeMesh의 EndpointSlice 소비가 입증되지 않아
`sensor-anomaly-demo` 계약은 blocked이고 실클러스터 traffic mutation은 수행하지 않는다.
`terminate_current`, source/candidate 삭제와 promotion은 지원하지 않는다.

대시보드의 `static/runtime-operations.js`와 `static/runtime-operations.css`는 서비스 운영
read model의 화면 소유 경로다. Runtime Recommendation에 포함된 Placement 후보를 그대로
표시하고 화면 갱신 때 `/api/placements/select`를 호출하지 않는다. `dashboard.js`의 노드
상세는 이 모듈이 읽은 `/api/resources` snapshot을 사용해 Prometheus usage와 Kubernetes
scheduling capacity를 분리한다. 화면에는 Execution Controller 승인·실행 동작을 연결하지 않는다.

live 리소스를 직접 수정해 Git과 충돌시키지 않는다. image를 바꾸면 tag가 아니라 registry에서
확인한 immutable digest와 실제 Pod `imageID`까지 검증한다.

## 2026-09-08 Nano ↔ 실제 AGX 서비스 연속성 기준 구현

사용자의 기준 수립 계획 구현 승인 범위다. `qualification/llama-offloading/nano-agx-k8s/`를
별도 운영자 소유 시험 경로로 사용한다. Nano의 기존 Llama runtime에 전용 측정 API를
연결하고 실제 AGX `etri-dev0005-jetagx`에 고정 모델 runtime을 배치한다. 기존 RTX 역할
대체 시연, 센서 서비스와 운영 EdgeX root는 변경하지 않는다. AGX는 기존
`nvidia.com/gpu.shared` 1개를 요청하며 privileged·hostPath·노드 설정 변경을 추가하지 않는다.

목표는 cache-only AGX 준비 → 신규 요청 전체 전환 → Nano 복귀 → 진행 요청 drain →
모델 메모리 해제다. Pod/GPU 공유 슬롯 반환과 모델 메모리 해제는 다르다. 이번에는
관리 Pod와 공유 슬롯을 유지한다. Service는 고정 selector를 사용하고 EndpointSlice나
운영 Service를 동적으로 수정하지 않는다. 실제 요청을 보내는 시험 client의 정책이
대상을 선택하며 범용 외부 서비스용 gateway·전체 노드 장애 복구는 후속이다.

기준선 3회·AGX activation 10회로 정책을 동결한 뒤 동일 부하의 Nano-only/왕복
10쌍을 시험한다. GPU runtime·Service 통신·측정값이 미확보면 실패/미측정으로 둔다.
절차와 현재 증거는 [Nano–AGX 서비스 연속성 기준](../qualification/llama-offloading/continuity-runbook.md)을 따른다.

9월 8일 후속 검증에서 AGX 저장공간을 정리하고 공식 Ollama ARM64 원본의 불필요한
backend만 제외한 고정 이미지를 적용했다. 실제 GPU 기준선과 cache-only 활성화 10회를
완료했고 AGX의 4.8 req/s 수용도 3회 확인했다. 이전 v1 저부하 p95 기반 예측식의 15%
이득 조건은 불합격이어서 정책 생성·자동 왕복 10회는 수행하지 않았다. 운영 기능 완료로
승격하지 않으며, 자세한 측정값과 최종 상태는 위 실행 절차의 최종 판정을 따른다.

## 2026-09-10 장비 독립 공통 실행 제어기 승인 범위

사용자 지시에 따라 Nano·Orin·Spark를 예시로 한 고정 순서를 플랫폼 정책으로 사용하지 않는다.

전용 `platform-runtime` namespace의 workload·요청 gateway·실행 이력은 이 제어기가 소유한다.

대상 준비 후 요청 전환, 기존 요청 drain 후 자원 반환, 저부하 복귀와 제어기 재시작 복구다.

배포·중단한다. 구현·시험·라이브 배포 상태와 지원 실행 방식은
[공통 서비스 Kubernetes 오케스트레이션](공통-서비스-Kubernetes-오케스트레이션.md)에서 구분한다.

2026-09-10 후속 구현은 공통 실행 계약에 기존 runtime 연결을 추가한다. 명시적으로 연결한 Pod·Service·이미지·모델을 읽기 전용으로 검증하고, 기존 실행 제어기가 중단된 독점 제어 계약에서 모델 활성화·해제 API를 호출한다. GPU 예약·Pod는 유지하며 모델 메모리만 반환한다. 새 Pod 생성 모드와 같은 제어 루프를 사용하되 자원 반환 의미와 검증 결과를 구분한다. 세부 기준은 [공통 서비스 Kubernetes 오케스트레이션](공통-서비스-Kubernetes-오케스트레이션.md)을 따른다.

2026-09-10 NEXUS 연결 범위는 **서비스 → 클러스터 실행**(`/#runtime-services`)의 읽기 전용 관측이다. `state-aggregator/app/common_runtime.py`가 공통 제어기의 고정 `/services`를 조회해 현재 실행체·준비 대상·반환 중 실행체·전환 이유·모델 메모리 관측을 전달한다. 마지막 해제 기록과 GPU 예약 유지 여부를 구분하며 15초 이상 오래된 관측은 현재 정상으로 표시하지 않는다. NEXUS 운영자는 관측·진단을 담당하고 계약 등록·배치 정책 변경은 `platform-runtime` Kubernetes 운영자가 담당한다. 서비스 설계 dry-run의 실행 권한을 확장하지 않는다. API 실패·stale·모바일 overflow 검사를 적용한다.

2026-09-10 추가 승인 구현은 공통 RuntimeService의 선택적 지연시간 정책이다. gateway 대기·worker 응답 시간을 같은 서비스 UID/실행 revision별로 측정하고 p95 표본 수·window·실패 여부를 확인한다. 지연 초과 지속 시 검증값이 있는 후보로 전환하고, 복귀는 낮은 부하·회복 지연·후보 검증을 함께 요구한다. 제어기 재시작 뒤에는 새 표본이 쌓여야 판단한다. 측정·모델 qualification·운영 적용 책임은 platform-runtime 운영자에게 있으며 지연 SLO 보장·HA 달성으로 설명하지 않는다.

2026-09-10 공통 데모 실행 승인 범위는 RuntimeService의 명시적 demo 계약에 한정한다. NEXUS 클러스터 실행에서 토큰 입력 없이 고정 입력 단일 요청·제한된 부하/회복 시험·시험 중단과 영속 결과 조회를 제공한다. 공통 Operator는 시험 요청만 gateway에 전달하며 Kubernetes 배치 정책은 기존 제어기가 판단한다. 서비스별 한 시험, 전체 동시 시험 상한·요청 수·시간·재실행 대기·동일 실행 ID 재조회·재시작 시 Interrupted 검증을 적용한다. aggregator는 동일 출처의 제한된 demo API만 연결하며 서비스 설계 dry-run 및 EdgeX/노드 write 권한을 확장하지 않는다. demo 허용과 고정 입력의 검증·등록은 platform-runtime 운영자가 담당한다.


## 2026-09-11 AI 추론 지표·승인 기반 증강

실행 증거를 구분하며 실제 증강 승인은 사용자 클릭으로 수행한다. 상세는
