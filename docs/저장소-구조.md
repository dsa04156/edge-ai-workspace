# 저장소 구조

## 목적

이 문서는 레포 안의 디렉터리와 주요 파일을 현재 PoC 범위 기준으로 분류한다.
새 작업을 시작할 때 어떤 경로를 현재 구현 경로로 볼지, 어떤 경로를 보조/참조/보관 대상으로 볼지 판단하기 위한 기준 문서다.

현재 범위 판단은 `docs/프로젝트-범위.md`를 우선한다.

## 분류 기준

| 분류 | 의미 |
|---|---|
| Current | 현재 서비스 데모, 디바이스-서비스 연결 구조, 통합 운영 가시화에 직접 연결되는 경로 |
| Current-supporting | 설치, 배포, 운영, ingress, registry 등 현재 범위를 지원하는 경로 |
| Legacy / Reference | 현재 연구 방향에서 진행하지 않는 과거 physical-device mapper/KubeEdge Device plane, workflow/offloading/agent-planning 실험 또는 참조 구현 |
| Archive | 과거 통합 기록, 연구 초안, 논문/실험 자료. 현재 판단 기준이 아님 |
| 외부/참조 | KubeEdge API, MapperFramework 등 외부 코드 또는 참고용 코드 |
| Cleanup Review | 운영 중 생성된 데이터, 캐시, runner 산출물 등 레포 관리 대상인지 검토가 필요한 경로 |

| `edge-orch/state-aggregator/app/static/service-designer-model.js`, `service-designer-viewport.js`, `service-designer.js` | 서비스 설계 구현 | model은 allowlist 서비스 preset, EdgeX 입력 가능 수, `sensor-anomaly-demo` 3축 예시, 타입 매핑, DAG·배치 validation과 dry-run 계획을 담당한다. EdgeX Core Metadata의 Device/Device Profile은 KubeEdge `Device`/`DeviceModel` CRD와 다른 객체다. Discovery SQLite도 승인 전 후보와 등록 진행을 위한 control-plane 저장소일 뿐 물리 Device inventory가 아니다. 기존 telemetry Agent/SQLite outbox/HTTPS 수직 슬라이스와 aggregate `sensehat-001` bootstrap은 퇴역했다. 현재 root render에는 Jetson Arduino Serial과 Raspberry Pi Sense HAT I2C Device Service가 있고 고정 MQTT 입력 workload나 broker는 없다. MQTT 자기등록 subscriber는 없지만 웹에서 허용 broker 설정을 선언하면 Controller가 검증된 공식 `device-mqtt`를 필요할 때 배포하는 개발 경로가 있다. broker/publisher fixture는 별도 development overlay다. Modbus는 자동 discovery 없이 Git에 등록한 개발 simulator Unit 1·2 endpoint용 공식 Device Service 등록·Event 경로를 과거 검증했지만 Controller Runtime은 현재 퇴역 상태다. OPC-UA·ONVIF discovery는 미구현이고 RTSP는 별도 media 경로다.

## 새 작업 판단 절차

새 파일을 만들거나 기존 파일을 수정하기 전에 다음을 확인한다.

1. `docs/프로젝트-범위.md`의 현재 PoC 범위에 들어가는가?
2. 서비스 데모, 디바이스-서비스 연결 구조, 통합 운영 가시화에 직접 기여하는가?
3. 중앙 EdgeX Metadata inventory/schema와 Core Data/PostgreSQL authority, 정식 Device Service의 endpoint 소유권과 protocol별 검증 gate를 지키는가?
4. workflow/offloading/agent-planning 계열을 다시 현재 경로로 끌어오는 작업은 아닌가?
5. 현재 범위가 아니라면 archive/reference/정리 검토 대상으로 표시할 수 있는가?
