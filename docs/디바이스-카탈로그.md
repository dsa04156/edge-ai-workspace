# 디바이스 Binding 및 Profile Catalog

## 목적

발견 API가 임의의 container image, parser, Profile, host path를 선택하지 못하게 한다.
새 장비 지원은 Git review를 거친 Catalog와 배포 변경으로만 추가한다.

현재 파일:

```text
edgex/adapter-controller/config/
  device_bindings.json
  runtime_templates.json
  discovery_plans.json
  profiles/
    arduino-multisensor-v1.json
    edgeai-modbus-temperature-v1.json
    etri-sensehat-gyroscope.json
```

`runtime_templates.json`은 Device Service Runtime의 배치 template이고,
`device_bindings.json`은 stable hardware identity와 Runtime/Profile을 연결한다. 두 파일의
역할을 섞지 않는다.

## Runtime network egress

Controller가 만든 Runtime은 기본적으로 DNS와 중앙 EdgeX Keeper/Metadata/MessageBus에만
접근한다. TCP 기반 물리 endpoint가 추가로 필요하면 `runtime_templates.json`의 검토된
template에만 목적지를 선언한다.

```json
{
  "networkEgress": [
    {
      "namespace": "edgex-edge",
      "podSelector": {
        "app.kubernetes.io/name": "edge-modbus-simulator"
      },
      "ports": [1502]
    }
  ]
}
```

selector 목적지는 `namespace`와 `podSelector`를 함께 사용한다. 실제 외부 PLC는
`cidr`와 허용 TCP port를 사용하며 selector 방식과 섞지 않는다. `/0`, 빈 selector,
중복·범위 밖 port는 Catalog 로딩에서 거부한다. candidate API의 Host 값이 NetworkPolicy를
직접 확장하지 않으며, endpoint와 egress는 둘 다 Git Catalog 변경을 거쳐야 한다.

## Device Binding schema

```json
{
  "version": 1,
  "imageAllowlist": [
    "registry.example/device-serial@sha256:<64 hex>"
  ],
  "parserAllowlist": [
    "arduino-multisensor-v1"
  ],
  "profileAllowlist": [
    "arduino-multisensor-v1"
  ],
  "bindings": [
    {
      "bindingId": "jetson-arduino-multisensor-v1",
      "protocol": "serial",
      "match": {
        "nodeId": "etri-dev0001-jetorn",
        "vendorId": "2341",
        "productId": "0043",
        "hardwareId": "75035303230351E0D171"
      },
      "runtimeHardwareBindingId": "jetson-arduino-serial-001",
      "connection": {
        "Port": "/dev/arduino-001",
        "BaudRate": 115200,
        "DeviceID": "arduino-001",
        "ResourceName": "*"
      },
      "adapter": {
        "runtimeAdapterId": "serial-jetson",
        "serviceName": "device-serial-jetson",
        "image": "registry.example/device-serial@sha256:<64 hex>",
        "parser": "arduino-multisensor-v1"
      },
      "profile": {
        "name": "arduino-multisensor-v1",
        "file": "profiles/arduino-multisensor-v1.json"
      },
      "security": {
        "approvalRequired": true
      },
      "registrationMode": "create-or-reuse",
      "deviceNamePrefix": "arduino"
    }
  ]
}
```

## 검증 규칙

- image는 tag가 아니라 `@sha256:<digest>` 형식이어야 한다.
- binding image, parser, Profile name은 각각 상위 allowlist에 있어야 한다.
- Profile file은 Catalog 디렉터리 안의 JSON이어야 하며 path traversal을 허용하지 않는다.
- Profile file의 `name`은 binding의 Profile name과 같아야 한다.
- binding ID는 중복될 수 없다.
- match에는 hardware ID, VID/PID, model, endpoint 또는 required capability 중 stable
  조건이 하나 이상 있어야 한다.
- `match.properties`는 수동 선언된 endpoint의 mode, host, port, unit ID처럼 Git에서
  승인한 exact property 조합만 매칭한다.
- `edgeXProtocol`은 공통 후보 protocol과 EdgeX Device protocol key가 다를 때 사용한다.
  예를 들어 후보 `modbus`는 Device 등록 시 `modbus-tcp` 또는 `modbus-rtu`가 된다.
- `connectionPropertyMap`은 후보 property를 EdgeX protocol property로 명시적으로
  옮긴다. 요청 값으로 임의 key를 추가하지 않는다.
- `autoEvents`는 Git Catalog가 승인한 source와 interval만 Device에 추가한다.
- `registrationMode` 기본값은 `create-or-reuse`다. `reuse-existing`은
  `existingDeviceName`과 검증할 `existingDeviceTags`를 모두 요구하고, 기존 Profile과
  Device의 service/profile/protocol/tag subset이 일치할 때만 통과한다.
- 여러 binding이 동시에 exact match되면 `ambiguous`로 차단한다.
- active Manifest probe가 실패했거나 Manifest의 recommended Profile이 binding과 다르면
  알려진 USB serial이라도 exact match하지 않는다.
- invalid binding 하나는 격리해 API `errors`에 표시하고, 나머지 유효 binding은 계속
  사용할 수 있다. Catalog 문서 전체가 깨졌으면 빈 Catalog로 기동해 모든 신규 등록을
  fail-closed한다.

Catalog는 Controller 시작 시 읽는다. 현재 hot reload API는 없으므로 Git 변경 배포 후
Controller rollout으로 반영한다.

## Profile 원칙

신규 Arduino/ESP32 멀티센서 장비는 물리 보드 하나를 EdgeX Device 하나로 만든다.
센서 값은 여러 `DeviceResource`로 표현한다.

```text
Device: arduino-<stable-id>
Profile: arduino-multisensor-v1
Resources:
  temperature_raw
  light_raw
  magnetic_raw
  acceleration_x_raw
  acceleration_y_raw
  acceleration_z_raw
```

Profile에는 `edge-adapter-controller` label을 넣어 Catalog 관리 Profile임을 표시한다.
Device에는 `controllerCandidateId`, `hardwareId`, `nodeName`, `catalogBindingId` tag를
넣는다.

카메라는 원본 RTSP frame을 Profile resource나 Core Data Event로 만들지 않는다. camera
상태, endpoint metadata, AI 결과만 별도 Profile resource 후보로 정의한다.

## 새 Serial 장비 추가 절차

1. 대상 노드에서 `/dev/serial/by-id/*`, VID/PID와 USB serial을 확인한다.
2. firmware가 지원하면 WHOAMI Manifest의 model/resource schema를 PTY 또는 실장비로
   검증한다.
3. parser가 기존 `device-serial`로 처리 가능한지 확인한다. 새 framing이면 parser 코드와
   단위 테스트를 먼저 추가한다.
4. 한 물리 보드의 resource를 정의한 Profile JSON을 `config/profiles/`에 추가한다.
5. `runtime_templates.json`에 exact host CharDevice와 container path binding을 추가한다.
6. `device_bindings.json`에 stable match, Runtime binding, connection, parser, Profile과
   immutable image를 추가한다.
7. `discovery_plans.json` 또는 Plan API에서 필요한 VID/PID만 허용한다. Active Manifest
   probe는 기존 Device Service와 포트 경쟁이 없는 검증 창에만 켠다.
8. Catalog, scanner, Device Service, Kustomize 테스트를 실행한다.
9. 배포 후 후보가 `PENDING_APPROVAL`인지 확인한다.
10. 운영자와 외부 인증 승인 뒤 `EVENT_CONFIRMED`까지 확인한다.

새 장비를 연결할 때마다 DB schema를 수정하지 않는다. Candidate, Event/Reading,
Profile/Device는 generic 모델로 저장되고 장비별 schema는 Profile/Catalog가 관리한다.

2026-07-28 dev0003에서 발견된 CH340 `1a86:7523`은
`/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0`까지 passive 확인했다. 이 장비에는
별도 exact binding `raspi5-mpu6050-serial-v1`을 사용한다. binding은 node, VID/PID,
stable by-id hardware ID를 함께 매칭하고, 검증 template의 exact CharDevice를
`/dev/mpu6050-001`로 마운트한다. 연결 계약은 `Port`, `BaudRate`, `DeviceID`,
`Parser=mpu6050-imu-v1`, `ResourceName=*`이며 Profile은
`config/profiles/mpu6050-imu-v1.json`이다.

이 Catalog 등록은 장비 신뢰와 telemetry 완료를 뜻하지 않는다. USB serial number가 없는
CH340의 stable identity 한계를 운영자가 검토하고, 보드 firmware가 예제의 6축 JSON-line을
출력하며 승인 뒤 첫 Event까지 확인해야 한다. 기존 Jetson binding의 parser나 mount를
재사용해 완료로 판정하지 않는다.

## I2C 장비 추가 절차

1. bus와 address를 Plan allowlist에 넣는다.
2. 상태를 바꾸지 않는 identity register, expected chip ID, model, Profile과 capability를
   `identificationRules`에 선언한다. 여러 chip이 한 물리 보드를 구성하면
   `identities` 배열로 모두 선언해 하나의 composite fingerprint를 만든다.
3. `MockI2CBusAdapter` 테스트로 허용 address만 읽는지 검증한다.
4. 해당 Profile, Device Service image/parser와 Device Binding을 Catalog에 추가한다.
5. 실장비 read와 첫 EdgeX Event를 검증하기 전에는 완료로 표시하지 않는다.

버스 `/dev/i2c-N` 존재만으로 Device Binding을 만들지 않는다.

현재 Sense HAT v1 binding은 dev0003 bus 1의 네 chip ID
`1c3d-5cbd-5fbc-6a68`을 exact match한다. 이미 Argo CD가 관리하는
`device-sensehat-raspi`와 기능별 Device 6개가 있으므로 `registrationMode:
reuse-existing`, 대표 Device `imu-sensehat-gyroscope-01`을 사용한다. 승인 Saga는 기존
Profile/Device 계약을 readback하고 승인 이후 첫 Event만 확인하며 해당 리소스의 소유권을
취하거나 중복 Device를 만들지 않는다.

## Modbus 장비 추가 절차

현재 구현된 범위는 공식 EdgeX `device-modbus:4.0.2`와 개발 simulator를 연결하는
`template-verified` 경로다. simulator는 Unit 1과 Unit 2를 제공하고 각 Unit은 서로 다른
exact hardware binding으로 등록된다. 자동 network scan과 실제 PLC 지원은 아직 없다.

1. 개발 fixture를 기본 운영 render와 분리해 배포한다.
2. 대시보드에서 node `etri-dev0001-jetorn`, protocol `modbus`, mode `tcp`,
   host `edge-modbus-simulator.edgex-edge.svc.cluster.local`, port `1502`, unit ID `1`
   또는 `2`로 후보를 선언한다.
3. exact `match.properties`가 일치한 후보만 `PENDING_APPROVAL`로 이동한다.
4. 승인 후 Controller가 digest 고정 공식 Device Service Runtime을 배포한다.
5. Runtime이 Core Metadata에 나타난 뒤 read-only temperature Profile과 Device를 등록한다.
6. 1초 AutoEvent가 Core Data에 도착한 뒤에만 `EVENT_CONFIRMED`로 완료한다.

Unit 2는 두 번째 가상 온도 센서 등록과 중복 격리를 검증하기 위한 fixture다. 2026-07-28
Unit 2 후보 승인부터 Controller-owned Runtime, Metadata Device, 첫 Event와 dashboard
`available`까지 확인했다. Unit 번호만 바꾼 임의 후보는 Catalog exact match를 통과하지
못한다.

실제 PLC를 추가할 때는 simulator binding을 수정하지 않고 별도 binding/Profile을 만든다.
장비 문서의 register table, starting address, raw type, scale, byte/word swap을 검토하고
endpoint/CIDR egress도 Git allowlist에 추가한다. 실제 Event와 재연결을 확인하기 전에는
`hardware-verified`로 승격하지 않는다.

## MQTT 장비 추가 절차

현재는 자기등록 payload parser만 있고 broker subscriber와 MQTT Device Service가 없다.
다음 작업을 완료하기 전에는 binding을 운영 승격하지 않는다.

1. Secret 기반 broker TLS/auth 설정
2. retained `edge/discovery/{nodeId}/{deviceId}` subscriber
3. topic node/device 일치와 schema 검증
4. discovery topic과 telemetry topic 분리
5. MQTT Device Service parser와 Profile
6. 중복 자기등록 idempotency, disconnect와 first Event 검증

## CI의 image digest 정렬

`.github/workflows/docker-build-push.yml`은 Device Service image를 먼저 build/push한다.
그 다음 CI 작업공간의 `runtime_templates.json`과 `device_bindings.json`을 새 digest로
해석하고 Controller image를 build한다. 따라서 배포되는 Controller Catalog와 실제
Device Service Deployment가 같은 immutable digest를 사용한다.

Git의 digest는 마지막 검증 기준선으로 남고, Argo CD image override와 Controller image
내부 Catalog는 한 CI 실행에서 생성된 digest로 함께 배포된다. Saga는 실제 Deployment
image readback이 Catalog digest와 다르면 `RUNTIME_IMAGE_NOT_VERIFIED`로 중단한다.
