# 2026-07-15 젯슨·센스햇 운영 검증 기록

> 상태: 중앙 MessageBus 분리 배치 이전의 운영 검증 기록. 현재 운영 절차가 아니다.

## 목적과 운영 경계

이 문서는 현재 운영 중인 EdgeX MQTT canary를 조회하고 장애 범위를 좁히는 절차다. 물리 디바이스 inventory, 관리 상태, telemetry의 권위는 EdgeX이며, KubeEdge는 edge node에 workload를 배치하고 실행 상태를 관찰하는 역할만 맡는다.

현재 검증된 MQTT 물리 경로는 두 개다.

```text
arduino-001
sensehat-001
```

Serial, Modbus, OPC-UA, RTSP는 목표 protocol이지만 아직 완성된 운영 경로가 아니다. 각 protocol은 Device Service, profile, 실장비 연결, Core Data Event/Reading 증거를 별도로 확보해야 한다.

운영 배포 계약은 다음과 같다.

| 항목 | 현재 값 |
|---|---|
| Argo CD Application | `edgex-telemetry` |
| Kustomize entrypoint | `edgex/k8s` |
| namespace | `telemetry` |
| target nodes | Core/UNO: `etri-dev0001-jetorn`, Sense HAT Device MQTT: `etri-dev0003-raspi5` |
| EdgeX release/image | EdgeX `4.0.2`, ARM64 |
| Core Metadata | `edgex-core-metadata:59881` |
| Core Data | `edgex-core-data:59880` |
| internal MessageBus | ClusterIP `edgex-messagebus:1883` |
| southbound MQTT | Jetson `127.0.0.1:1883`, Raspberry Pi 5 `192.168.0.6:1883` |
| persistence | PostgreSQL StatefulSet와 retained PVC |
| state-aggregator | namespace `default`의 `state-aggregator:8000` |

Docker Compose는 현재 운영 배포 경로가 아니다. Git 반영 후에는 `edgex/k8s`를 소스로 삼는 Argo CD Application이 유일한 소유자다. 2026-07-14 live workload와 ingestion은 수동 Kustomize 적용으로 검증됐지만, `edgex-telemetry` Application의 live 등록은 repository 변경 반영 전이므로 별도 완료 조건이다. 일반 점검은 조회 전용이며 apply, delete, restart, scale, patch 명령을 포함하지 않는다.

## 현재 데이터 경로

```text
Arduino UNO
  -> Jetson serial collector
  -> Jetson local Mosquitto 127.0.0.1:1883
  -> hostNetwork edgex-device-mqtt
  -> ClusterIP edgex-messagebus:1883
  -> edgex-core-data:59880
  -> PostgreSQL PVC
  -> state-aggregator

Sense HAT
  -> existing Sense HAT publisher
  -> Raspberry Pi 5 local Mosquitto 192.168.0.6:1883
  -> edgex-device-mqtt-sensehat
  -> ClusterIP edgex-messagebus:1883
  -> edgex-core-data:59880
  -> PostgreSQL PVC
  -> state-aggregator
```

`edgex-device-mqtt`만 `hostNetwork`를 사용해 Jetson의 southbound Mosquitto에 접속한다. `edgex-device-mqtt-sensehat`는 host network를 사용하지 않고 Raspberry Pi 5 node endpoint에 접속한다. 두 instance는 내부 MessageBus에서 고유 client ID를 사용한다. `edgex-messagebus`는 EdgeX 내부 통신용 ClusterIP이며 southbound broker나 외부 접속 주소가 아니다.

입력 topic은 다음과 같다.

```text
etri/etri-dev0001-jetorn/arduino-001/{temperature,light,magnetic,acceleration}
etri/etri-dev0003-raspi5/sensehat-001/{temperature,humidity,pressure,compass,orientation,gyroscope}
```

Device MQTT instance는 각 node prefix를 구독하고 `{device-name}/{source}` suffix를 해당 Device와 Device Command에 매핑한다.

## 6. Kubernetes MQTT smoke

Core Service는 ClusterIP이며 KubeEdge edge Pod에 대한 workstation `port-forward`는 지원되지 않을 수 있다. cluster 내부의 기존 Python workload에서 read-only smoke를 실행한다.

```bash
POD=$(kubectl -n default get pod -l app=state-aggregator \
  -o jsonpath='{.items[0].metadata.name}')
kubectl cp edgex/scripts/smoke_test.py \
  "default/${POD}:/tmp/edgex-smoke.py"
kubectl exec -n default "${POD}" -- python /tmp/edgex-smoke.py \
  --metadata-url http://edgex-core-metadata.telemetry.svc.cluster.local:59881 \
  --data-url http://edgex-core-data.telemetry.svc.cluster.local:59880 \
  --timeout 15 \
  --freshness-seconds 120
kubectl exec -n default "${POD}" -- rm /tmp/edgex-smoke.py
```

성공 출력은 정확히 다음과 같다.

```text
PASS: device=arduino-001 sources=temperature,light,magnetic,acceleration
```

이 smoke는 Core Metadata의 Profile/Device와 Core Data의 최근 Event를 GET으로만 조회한다. `temperature`, `light`, `magnetic`, `acceleration` source가 모두 fresh하고 profile에 정의된 typed Reading을 포함해야 성공한다.

2026-07-14 live 실행에서 다음 경로와 성공 출력을 확인했다.

```text
Jetson serial collector
  -> Jetson local Mosquitto
  -> device-mqtt
  -> internal MessageBus
  -> Core Data/PostgreSQL

PASS: device=arduino-001 sources=temperature,light,magnetic,acceleration
```

이 증거는 현재 MQTT compatibility ingestion과 read-only GET 경로에만 해당한다. direct UART Device Service, Serial/Modbus/OPC-UA/RTSP 완료 증거나 새 state-aggregator image가 live 배포됐다는 증거가 아니다.

### 새 state-aggregator image 배포 증거

2026-07-14 ingestion smoke와 dashboard image cutover를 혼동하지 않는다. 새 image 배포를 주장하려면 다음 live 값을 릴리스 대상 digest와 대조하고 rollout 상태가 완료됐음을 별도로 기록한다.

```bash
kubectl -n argocd get application.argoproj.io edge-orch-state-aggregator \
  -o jsonpath='{.status.sync.status}{"\t"}{.status.health.status}{"\t"}{.spec.source.path}{"\t"}{.spec.destination.namespace}{"\n"}'
kubectl -n default get deployment state-aggregator \
  -o jsonpath='{.metadata.generation}{"\t"}{.status.observedGeneration}{"\t"}{.status.updatedReplicas}{"\t"}{.status.availableReplicas}{"\n"}'
kubectl -n default get pod -l app=state-aggregator \
```

`Synced`/`Healthy`, generation 일치, updated/available replica 충족, 기대한 immutable `IMAGE_ID`가 모두 있어야 새 image의 live deployment 증거다. 이어서 `/state/devices`와 `/state/dashboard`가 EdgeX 필드를 반환해야 dashboard cutover 증거가 완성된다.

## 8. 로그 기반 failure isolation

로그 조회는 상태를 변경하지 않는다. 먼저 최근 로그를 좁혀 확인한다.

```bash
kubectl -n telemetry logs deployment/edgex-device-mqtt \
  --since=10m --tail=200
kubectl -n telemetry logs deployment/edgex-messagebus \
  --since=10m --tail=200
kubectl -n telemetry logs deployment/edgex-core-data \
  --since=10m --tail=200
kubectl -n telemetry logs deployment/edgex-core-metadata \
  --since=10m --tail=200
kubectl -n telemetry logs statefulset/edgex-postgres \
  --since=10m --tail=200
kubectl -n default logs deployment/state-aggregator \
  --since=10m --tail=200
```

재시작이 있었다면 직전 container 로그도 확인한다.

```bash
kubectl -n telemetry logs deployment/edgex-device-mqtt \
  --previous --tail=200
kubectl -n telemetry logs deployment/edgex-core-data \
  --previous --tail=200
kubectl -n default logs deployment/state-aggregator \
  --previous --tail=200
```

### A. Argo가 OutOfSync 또는 Degraded

1. Application YAML의 `status.conditions`와 `operationState`를 본다.
2. source가 `edgex/k8s`, destination이 `telemetry`인지 확인한다.
3. 누락 object, health probe 실패, image pull 실패를 Pod 상태와 events로 좁힌다.

```bash
kubectl -n telemetry get events \
  --sort-by=.metadata.creationTimestamp
```

### B. EdgeX Pod가 Pending 또는 Ready가 아님

1. Jetson Ready와 Pod `NODE`를 확인한다.
2. Pod 상세에서 scheduling, image pull, probe, volume mount 이유를 확인한다.
3. PostgreSQL PVC가 Bound인지 확인한다.

```bash
kubectl -n telemetry get pod \
  -l app.kubernetes.io/part-of=edgex-telemetry -o wide
kubectl -n telemetry describe pod \
  -l app.kubernetes.io/part-of=edgex-telemetry
kubectl -n telemetry get pvc data-edgex-postgres-0 -o wide
```

### C. Metadata/Data Service proxy가 실패

1. Service port와 Endpoint 존재 여부를 확인한다.
2. 해당 Core Pod의 Ready와 로그를 확인한다.
3. Core dependency인 Keeper/PostgreSQL 상태를 확인한다.

```bash
kubectl -n telemetry get service,endpoints \
  edgex-core-metadata edgex-core-data edgex-core-keeper edgex-postgres
kubectl -n telemetry get pod \
  -l app.kubernetes.io/part-of=edgex-telemetry -o wide
```

### D. Metadata는 정상이지만 최신 Event가 없음

1. Jetson serial collector가 네 UNO topic을 local `127.0.0.1:1883`에 계속 발행하는지 확인한다.
2. `edgex-device-mqtt`가 Ready이고 `etri/etri-dev0001-jetorn/#` subscription 및 Event publish 오류가 없는지 본다.
3. `edgex-messagebus` Endpoint와 로그를 확인한다.
4. Core Data와 PostgreSQL 로그를 확인한다.
5. smoke를 실행해 네 source의 최근 Event/Reading을 GET으로 확인한다.

Jetson local Mosquitto와 serial collector는 host 서비스이며 Argo CD가 소유하지 않는다. Kubernetes 객체가 모두 정상인데 Device MQTT 로그에 `127.0.0.1:1883` 연결 실패가 있으면 Jetson host broker와 collector를 별도 host 운영 절차로 점검한다.

### E. Core Data는 정상이지만 dashboard가 비었거나 stale

1. state-aggregator Service/Endpoint와 Pod Ready를 확인한다.
2. `EDGEX_CORE_METADATA_URL`과 `EDGEX_CORE_DATA_URL`이 `.telemetry.svc.cluster.local` FQDN인지 확인한다.
3. state-aggregator 로그에서 Core timeout/HTTP 오류를 확인한다.
4. Core service-proxy 응답과 `/state/devices` 응답을 같은 시점에 비교한다.
5. 새 image를 기대했다면 live `IMAGE_ID`를 릴리스 digest와 비교한다.

다른 inventory/state/telemetry source로 fallback하지 않는다. EdgeX 조회 실패는 dashboard에서 오류 또는 미관측 상태로 드러내고 EdgeX 연결을 복구한다.

## 9. cutover exclusion 확인

```bash
kubectl -n default get pod -l app=mqttvirtual-mapper -o wide
```

Pod가 보이면 현재 경로와 병행 운영하지 말고 배포 소유자와 잔존 workload를 식별한다. 이 확인은 삭제 명령을 수행하지 않는다.

## 10. Dashboard와 Workflow Builder 경계

Dashboard에서는 다음을 확인한다.

1. EdgeX 등록 device 수와 canary 이름
2. Device Profile과 Device Service 연결
3. `adminState`, `operatingState`, connection state
4. 최신 Event 시각, reading 값, freshness
5. node/workload 진단과 service relation
6. issue/reason을 통한 우선 점검 대상

Workflow Builder는 브라우저 상태 안에서만 service stage 구성, device/resource bind/release dry-run, validation, execution plan preview를 보여주는 읽기 전용 설계 표면이다. 다음 동작은 수행하지 않는다.

- Kubernetes apply/delete/restart/scale/patch
- EdgeX metadata 또는 관리 상태 변경
- MQTT/actuator command publish
- workload 생성, 이동, runtime migration, offloading
- 자동 placement나 agent-assisted execution

Dry-run plan이 바뀌어도 live cluster와 EdgeX 권위 상태는 바뀌지 않는다. 이를 동적 orchestration이 운영 완료된 증거로 설명하지 않는다.
