# 시스템 구축 목표

이 문서는 EdgeX 기반 물리 디바이스와 KubeEdge 기반 edge node/workload를 결합한 엣지 AI PoC에서 흔들리지 않아야 할 시스템 구축 목표를 정의한다.
기존 문서와 구현은 이 목표를 기준으로 Active, Ops, Archive로 나눈다.

## 한 문장 목표

EdgeX를 물리 디바이스 inventory, state, telemetry의 단일 권위로 사용하고, KubeEdge는 node/workload 관리에 한정하여 실제 서비스 데모와 디바이스 상태를 dashboard와 read-only 운영 보조 요약에서 통합 가시화한다.

## 짧은 표현

EdgeX 물리 디바이스와 edge AI 서비스 데모를 운영 관점에서 보이게 만드는 시스템.

## 시스템 이름 후보

- EdgeX 물리 디바이스 기반 edge AI 서비스 운영 가시화 플랫폼
- 실공장 PoC형 edge AI 운영 가시화 시스템
- 혼합 디바이스 서비스 데모 운영 가시화 PoC

## 현재 시스템이 반드시 보여줘야 하는 것

1. 어떤 edge node와 server node 및 workload가 존재하는가.
2. EdgeX Core Metadata에 어떤 Device Profile, Device, Device Service가 등록되어 있는가.
3. 물리 I2C/Serial/Modbus/OPC-UA endpoint가 protocol별 EdgeX Device Service에 연결되고, MQTT-only 장비만 명시적 broker를 사용하는가.
4. telemetry가 EdgeX Event/Reading으로 Core Data/DB에 저장되고 AI services, state-aggregator, dashboard로 전달되는가.
5. API의 `profile_name`, `device_service_name`, `protocol_names`, `admin_state`, `operating_state`, `connection_state`, `device_service_available`이 inventory와 연결 상태를 일관되게 보여주는가.
6. `latest_event_timestamp`, `latest_readings`, `telemetry_freshness`가 Core Data event의 최신성과 값을 보여주는가.
7. `admin_state=LOCKED` 또는 `operating_state=DOWN`이면 `unavailable`, Device Service가 연결되고 최신 event가 fresh이면 `available`, 그 밖의 불완전하거나 오래된 상태는 `degraded`로 설명되는가.
8. device가 어떤 service demo group과 AI/storage consumer에 연결되어 있는가.
9. 운영자는 문제가 생겼을 때 physical endpoint, Device Service, 중앙 MessageBus, Core Data, consumer, state-aggregator, dashboard 중 어디부터 봐야 하는가.
10. KubeEdge node/workload 정보가 물리 device availability의 권위나 gate가 아니라 선택적 진단 및 배치 정보로만 표시되는가.
11. 이 데모 상태가 옥동 시나리오의 생산성 향상 효과와 어떻게 연결되는가.
12. Kagenti 같은 운영 보조 agent가 read-only 방식으로 상태를 요약할 수 있는가.

## 현재 범위에 포함하는 것

- EdgeX Core Metadata 기반 물리 디바이스 inventory
- I2C/Serial/Modbus/OPC-UA별 EdgeX Device Service 경계
- Device Service, Core Data/DB 기반 telemetry와 최신 Event/Reading
- MQTT-only 장비 또는 local pub/sub 요구에 한정한 optional broker 경계
- Workflow Pod가 직접 구독하는 RTSP media 경로와 상태/결과 metadata 경계
- AI services/storage/state-aggregator/dashboard 소비 경로
- EdgeX 기반 state-aggregator API와 dashboard 운영 가시화
- KubeEdge 기반 edge node/workload 관리
- device-service binding
- 서비스 데모 시나리오
- 운영 runbook
- 옥동 시나리오 생산성 KPI 설명
- read-only 운영 보조 요약 API
- 중앙 EdgeX와 EdgeX dashboard 계약. 2026-07-21 Jetson Arduino Serial과 Raspberry Pi Sense HAT 직접 I2C Device Service 정상 경로 live 검증
- Arduino와 Sense HAT 물리 source를 기능별 가상 Device 6개씩, 총 12개로 분리한 두 수직 슬라이스와 이후 protocol별 독립 검증
- Modbus/OPC-UA/RTSP, 다른 I2C 장비·주소와 Serial/I2C 물리 분리·복구는 각각 독립 실행 증거가 확보되기 전까지 미검증

## 현재 범위에서 제외하는 것

다음 항목은 현재 시스템 구축 목표가 아니다.
필요하면 archive에서 과거 연구 맥락으로만 확인한다.

- 완전 자율형 workflow orchestration
- 동적 offloading 최적화
- agent-assisted planning 기반 자동 실행
- LLM/agent가 Kubernetes나 EdgeX metadata/state/command를 직접 제어하는 구조
- MapperFramework, `mqttvirtual`, KubeEdge Device/DeviceStatus 또는 mapper direct-write를 물리 inventory/state/telemetry의 현재·병행·fallback 경로로 사용하는 구조
- selective replanning 논문 방향을 현재 구현 목표로 보는 것
- 과거 cost model 중심 runtime 최적화를 현재 PoC의 핵심 목표로 보는 것

## 운영 보조 agent의 위치

Kagenti 또는 유사 agent는 제어 주체가 아니라 운영 보조 계층으로 제한한다.

허용하는 역할:

- state-aggregator API 조회
- dashboard 상태 요약
- docs/runbook 기반 troubleshooting 안내
- service demo group과 KPI 의미 설명
- Kubernetes 리소스 read-only 진단 일부

허용하지 않는 역할:

- `kubectl apply/delete/rollout restart` 실행
- EdgeX Core Metadata 또는 device state 수정
- Device Service 재배포
- EdgeX command 또는 actuator command 직접 실행
- 운영자 승인 없는 자동 복구

## 문서 정리 기준

문서가 현재 목표를 직접 설명하면 Active 문서로 둔다.
운영 중 점검과 장애 대응에 필요하면 Ops 문서로 둔다.
과거 연구, 논문 초안, legacy orchestration, selective replanning 자료는 Archive로 둔다.
중복이 있거나 현재 목표와 연결이 약한 문서는 정리 후보로 표시한다.

판단 질문:

1. 이 문서가 현재 서비스 데모 운영 가시화에 직접 필요한가?
2. 운영자가 dashboard를 해석하거나 데모를 점검하는 데 필요한가?
3. EdgeX device-service 연결 구조나 Core Data telemetry/availability 정책을 설명하는가?
4. 생산성 KPI 또는 실공장 PoC 설명에 필요한가?
5. 아니라면 과거 연구 맥락으로 archive에 남길 가치가 있는가?

## 앞으로의 구현 우선순위

1. 서비스 데모 시나리오를 명확하게 유지한다.
2. EdgeX device-service binding을 backend API와 dashboard에서 일관되게 보여준다.
3. dashboard availability를 EdgeX `admin_state`, `operating_state`, `connection_state`, `device_service_available`, Core Data latest event freshness로 설명한다.
4. Device Service 저장소 산출물과 실제 endpoint/live Event 증거를 구분하고, 검증 fixture를 아키텍처 완료 기준과 분리한다.
5. 현재 Serial/Sense HAT I2C 정상 경로의 증거를 유지하고 Modbus/OPC-UA/RTSP와 다른 I2C 장비는 각 protocol의 Device Service와 실장비 event를 독립 검증한 뒤 지원 범위로 승격한다.
6. dashboard가 운영자 질문에 바로 답하도록 정보를 배치한다.
7. 운영 runbook과 troubleshooting 문서를 실제 점검 흐름 중심으로 유지한다.
8. read-only 운영 보조 요약은 dashboard를 보조하는 계층으로만 둔다.
9. 과거 workflow/offloading/replanning 자료는 현재 구축 목표와 분리한다.
