# 시스템 구축 목표

## 한 문장 목표

PLC·MES·센서 데이터를 EdgeX 기반 물리 디바이스 경로로 수집하고, 엣지 AI 서비스의 실행·저장·알림·장애 상태를 대시보드에서 운영 가능한 형태로 보여주는 실공장 PoC를 구축한다.

2026년도 2차년도 일정·역할·산출물은 [ETRI 실행계획](2차년도-ETRI-실행계획.md)을 기준으로 한다.

## 책임 경계

| 계층 | 권위 | 책임 |
|---|---|---|
| 물리 디바이스 | 실제 PLC·센서·카메라 | 현장 데이터와 연결 상태 제공 |
| Protocol Adapter | 노드 로컬 수집기 | Serial/I2C/Modbus/OPC-UA/MQTT 입력을 canonical Event로 변환 |
| edge telemetry agent | 엣지 노드 | SQLite WAL outbox, 재시도, HTTPS/mTLS 업로드 |
| EdgeX Core Metadata | 중앙 | Device/Profile/Device Service inventory와 관리 상태 |
| EdgeX Core Data/PostgreSQL | 중앙 | Event/Reading 영구 저장과 이력 조회 |
| state-aggregator | 중앙 소비 API | EdgeX·Prometheus·Kubernetes 정보를 운영 read model로 정규화 |
| KubeEdge/Kubernetes | 노드·워크로드 관리 | 배치, 재시작, 리소스·노드 진단. 물리 Device의 권위가 아님 |
| AI 서비스 | 서비스 컨테이너 | 전처리·추론·결과 생성 |
| dashboard | 운영 화면 | 상태·freshness·서비스 연결·KPI·알림 가시화 |

## 현재 구축 목표

```text
물리 장비
  → Protocol Adapter
  → canonical EdgeX Event
  → edge-telemetry-agent / SQLite outbox
  → HTTPS/mTLS ingest gateway
  → EdgeX Core Data / PostgreSQL
  → AI 서비스·state-aggregator·dashboard
```

중앙 MessageBus는 Core 서비스 내부의 EdgeX 런타임 경로다. MQTT를 모든 센서 전송에 강제하지 않는다. MQTT-only 장비가 실제로 확인될 때만 별도 broker/adapter wave로 추가한다.

## 현재 범위

- 중앙 EdgeX Core Keeper, Metadata, Data, Command, MessageBus, PostgreSQL
- `edgex/k8s` root Kustomize 배포와 `edgex/telemetry-plane` 구현
- 엣지 SQLite outbox와 HTTPS persisted-ACK 계약
- EdgeX Device/Profile 기반 inventory·schema·상태 조회
- Core Data Event/Reading 기반 최신성·이력 조회
- `state-aggregator` API와 dashboard
- 센서·MES 품질 판별, 펌프·모터 이상감지 서비스의 플랫폼 연결
- KubeEdge node/workload 운영 진단
- read-only workflow source/binding preview

## 현재 완료로 표현하면 안 되는 범위

- 모든 프로토콜의 실장비 연결 완료
- discovery 후보가 자동으로 신뢰·등록되는 기능
- 운영자 승인 없는 EdgeX Device 생성
- dynamic workflow 실행, runtime migration, 자동 offloading
- LLM/agent의 Kubernetes·EdgeX 변경
- RTSP 원본 영상을 EdgeX에 저장하는 구조
- `mappers/` 또는 KubeEdge DeviceStatus를 EdgeX의 fallback authority로 사용하는 구조

## 운영자가 확인해야 할 결과

1. 어떤 Device/Profile/Device Service가 중앙 Metadata에 등록됐는가?
2. 최신 Core Data Event와 `telemetry_freshness`가 fresh인가?
3. 엣지 outbox에 대기 데이터가 있는가?
4. 품질·이상감지 서비스가 어떤 source와 window를 사용하는가?
5. 결과가 저장되고 알림으로 연결됐는가?
6. 노드·워크로드 문제와 물리 Device 문제를 구분할 수 있는가?
