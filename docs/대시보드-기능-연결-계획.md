# NEXUS 대시보드 기존 기능 연결

2026-09-07. 과제 전체 구조에 기존 운영 기능을 연결한다. 목표 시스템, 실제 관측, 문서 기반 구현 근거를 구분한다.

## 진입점과 작업 공간

- `/`, `/dashboard`: NEXUS. 기본값은 실제 관측이다.
- `/classic`: 기존 대시보드. NEXUS 내부 작업 화면은 `/classic?workspace=1#...`을 같은 출처의 iframe으로 연다.
- 내부 작업 화면은 기존 모듈과 권한·API 계약을 재사용한다. 상위 갱신은 열린 iframe을 다시 만들지 않아 편집 중인 초안과 관리 상태를 유지한다.
- `#management`, `#designer`, `#virtual-devices`, `#nodes`, `#operations` 기존 링크는 대응 작업 공간을 연다.
- 로컬 읽기 전용 검토 서버는 `scripts/serve-nexus-preview.py`, `0.0.0.0:8769`다. 기존 조회 API를 proxy하고 POST 등 쓰기는 제공하지 않는다. 운영에서는 원래 API의 권한 검증이 적용된다.

## 연결한 기능

| 새 메뉴 | 연결 내용 | 기존 근거 |
|---|---|---|
| 플랫폼 개요 | 물리 source → 등록 Device → 트윈 → 서비스 | `/state/devices`, `/state/device-twins`, `/state/services` |
| 디바이스·트윈 | 검색·최신 Reading·원 시각, 가상 실행체, 장비 관리 | 기존 virtual-devices와 device-management 모듈 |
| 서비스·워크플로우 | 입력·모델·단계 정의·저장 결과, 운영 상세와 서비스 설계 | service-demo, service-designer, runtime-operations |
| 자원·배치 | 가용 자원과 실측 사용률, 추천 근거, 노드·워크로드, 계획·이력 | `/api/resources`, `/api/runtime-recommendations`, 기존 nodes·operations 화면 |
| 데이터·복구 | 최신 Event와 기간별 Reading, 서비스 실행·롤백 기록 진입 | 기존 Core Data telemetry와 runtime-operations |
| 실증·성능 | 운영 증거 종류와 과제 목표 8종의 측정 경계 | 연구개발계획서. 공식 실측 결과 API는 없음 |

가상 실행체는 정의·Pod·모델·요청 관측을 표시한다. 실행 Pod가 없는 상태도 그대로 표시하며 화면 검증을 위해 시험 Pod를 시작하지 않는다. 장비 관리는 후보 검토·등록 Saga·첫 Event·소유 런타임의 기존 절차를 재사용한다. 서비스 설계는 브라우저 초안·source binding·validation·execution plan dry-run이며 실제 배포나 실행을 하지 않는다.

## 데이터 표시 계약

- 30초 GET 갱신, 중복 요청 합치기, 20초 timeout, 원천별 실패 격리. 숨겨진 상위 탭의 주기 조회는 멈춘다.
- API 수신 시각과 원 관측 시각을 구분한다. 90초 넘은 수신 snapshot은 현재 정상으로 표시하지 않는다. 센서 freshness 정책 변경은 아니다.
- 실패 시 이전 데이터를 보존하면서 현재 상태는 확인 불가로 표시한다. 실패·미관측은 0이나 정상으로 대체하지 않는다.
- 물리 source 미지정 Device는 별도 유지하며 물리 source·등록 Device·트윈의 분모를 합치지 않는다.
- 서비스 입력 상태는 서비스 API의 판단을 유지한다. Git 단계 정의와 과거 저장 결과는 현재 실행 성공을 뜻하지 않는다.
- Kubernetes 가용·예약 자원과 Prometheus 실측 사용률을 구분한다. 측정 시각과 관측 오류를 함께 확인한다.
- 외부 값은 HTML escape하며 Event UUID와 ISO 시각을 사용한다.

## 연결 범위 밖에 남은 측정

프로토콜별 장애 감지→전송 재개 시간, 저장·재전송 성공률과 과제 공식 성능지표는 실시간 측정 API에 연결되지 않았다. 최신 Event만으로 이 지표를 추정하지 않는다. 옥동 서비스 2종의 현장 적용과 범용 분산 실행을 완료 기능으로 표시하지 않는다. 해당 구현은 별도 범위·계약·실증 근거가 필요하다.

## 검증과 배포 기준

- JS 데이터·기존 모듈 전체 189개 통과. Python 전체 330개(진입점·정적 asset 그래프 포함), 저장소 UI 회귀 31개 통과.
- 실제 API 연결: 디바이스, 트윈, 서비스 결과, 노드 자원·추천. 값은 검증 시점에 따라 달라진다.
- 가상 실행체·설계·관리·노드·운영·telemetry 여섯 내부 화면, 편집 화면의 상위 갱신 보존, 모바일 가로 넘침과 JavaScript 오류를 브라우저에서 확인한다.
- 설계 편집·입력 검증은 읽기 흐름으로 확인한다. 실제 등록·배포·복구 mutation을 UI 검증용으로 실행하지 않는다.
- 원천 API 503 실패 격리와 복구, 검색·상세·모드 전환도 검증한다.
- 배포는 `k8s/deployment.yaml`의 immutable image digest와 Argo CD `edge-orch-state-aggregator`를 따른다. 공식 주소의 새 UI·API, 동일 Git revision의 Synced/Healthy와 목표 digest의 Ready Pod를 확인한다.
