# 1세부 개발범위와 우선순위

> 기준일: 2026-09-30. 사용자가 확정한 전체 개발 순서다.
> 개발 방향과 인수 기준이며, 각 단계의 구현·실장비 검증·운영 배포 완료를 뜻하지 않는다.

## 목표와 책임 경계

1세부의 핵심은 **어느 디바이스에서 실행할지 판단 → 부족하면 Edge AI Server에 자원 요청 →
할당·준비 결과를 받아 서비스 실행/재배치**하는 것이다.
서버 내부 GPU/NPU의 선택·분할·공유 스케줄러 자체 구현은 선행조건으로 두지 않는다.
서버 내부 자원 관리는 세부2 등 연계 대상의 책임으로 두고 요청·응답 API를 합의한다.

쉽게 말하면 장비의 능력표와 작업의 요구사항표를 먼저 만들고, 이를 비교해 실행할 곳을 고른다.
로컬 장비가 부족하면 서버에 필요한 자원을 요청하고 준비된 실행환경으로 작업을 연결한다.

## 확정한 전체 개발 순서

| 순서 | 단계 | 산출물과 확인 기준 |
|---|---|---|
| ① | Device / Service Profile 정의 | 정적 Capability·서비스 요구량·runtime/model 호환성 정의, 동적 RuntimeState와 분리 |
| ② | Device Manager | 물리/가상 디바이스 등록·상태·자원·연결 여부·실행 서비스 관리; 이 단계에서는 배치 판단을 하지 않음 |
| ③ | Workflow 실행 구조 | Task의 의존성·입출력·실행 상태와 Service Profile 전달 구조 정의 |
| ④ | Device Scheduler | Profile과 최신 상태를 비교해 Filter → Score → Placement 판단; 선택·탈락·검증 필요 사유 제공 |
| ⑤ | Offloading Controller | 로컬 부족 판단을 받아 서버 요청·준비·전환·복귀·반환의 수명주기 조율 |
| ⑥ | Edge AI Server 연계 API | 자원 요청·수락/거절·준비·상태 조회·취소·반환 계약 및 실제 상호운용 검증 |
| ⑦ | Virtual Device | 서버 실행환경과 등록 객체 연결, 물리/가상 공통 배치 후보 표현 |
| ⑧ | Multi-Device Orchestration | Workflow Task별 여러 디바이스 배치·데이터 전달·의존성·부분 실패 처리 |
| ⑨ | 대규모 Workload 실행 | 100 → 1,000 단계적 확장; 등록·관리·동시 실행 규모와 처리율·지연·오류를 분리 검증 |
| ⑩ | 복구 / 고가용성 / 운영 | 재시작·통신 단절·장애복구·고가용성·운영 절차의 통합 검증 |

앞서 정리한 **Profile → Manager → Scheduler → Offloading API**는 초기 핵심 기능의 요약이다.
위 10단계를 대체하거나 ③ Workflow 실행 구조와 ⑤ Offloading Controller를 생략하는 순서가 아니다.
③의 초기 작업은 Task/Profile 전달 계약부터 시작할 수 있으며 전체 도구 UI 완성과 구분한다.
실패 처리·멱등성·복구의 기본 계약은 각 단계에서 정의하고 ⑩에서 통합·고가용성 검증을 확대한다.

## 단계별로 지킬 경계

- 컴퓨팅 배치용 Device Profile은 센서 resource·command를 정의하는 EdgeX DeviceProfile과 구분한다.
  정적 Capacity·Capability만 담고 예약 여유·현재 사용량·관측 시각은 RuntimeState로 분리한다.
  미수집·미검증 값을 0이나 정상으로 채우지 않는다.
- Service Profile은 CPU·메모리·가속기 최소/최대 요구량, runtime/model, 지연 목표와 측정 범위,
  offloading 허용 여부를 담는다. 장비에 GPU/NPU가 있다는 사실과 모델 실행·성능 검증은 별개다.
- Device Manager는 기존 원본을 연결한다. 물리 inventory/state/telemetry/command는 EdgeX,
  노드·워크로드는 Kubernetes/KubeEdge, 실제 사용량은 Prometheus의 관측을 따른다.
- Scheduler는 실행 위치를 판단하고 Controller는 실행을 조율한다. 기존 Runtime Operator와
  gateway의 준비 확인·요청 전환·drain·복귀 경로를 재사용할 수 있는지 먼저 확인한다.
- 서버 API의 요청 수락과 실행 준비 완료를 구분한다. 같은 서비스·요청·할당의 준비를 확인한 뒤
  경로를 전환하고 진행 요청 정리 후 반환한다. 서버 내부 GPU 0/NPU 1 선택은 연계 대상에 맡긴다.
- VD 등록만으로 자원을 선점하지 않는다. 등록 객체·실제 할당·실행체를 구분하며 서버와 그 위의
  VD 자원을 중복 합산하지 않는다. 에뮬레이션 완료는 별도 명세와 시험으로 확인한다.
- 100/1,000은 단계적 규모 목표다. 등록·관측·제어·실행·공식 평가를 구분하고 상시 Pod 수로 바꾸지 않는다.
- Namespace 분리는 기능 책임이 정리된 뒤 검토하고, Istio는 실제 통신 요구가 생길 때 선택한다.

## 기존 설계와 현재 구현의 관계

이 순서가 전체 개발 우선순위다. [서버측 가상 디바이스 통합 설계](서버측-가상-디바이스-통합-설계.md)의
M0~M6는 ⑦ 단계 안의 세부 설계로 참고하며, VD를 전체 개발의 첫 단계로 앞당기지 않는다.
서버 자원 제공 API와 기존 Operator의 실행 책임을 정렬한 뒤 구체화한다.
9월 28일 철회한 VD·수동 Workflow 프로토타입을 이 문서 갱신으로 재개하지 않는다.

현재 `서비스 설계` 화면은 dry-run이다. ③과 ⑧은 후속 구현 대상이며 legacy Workflow 코드를
현재 기능으로 승격하지 않는다. 실제 구현·검증 근거는 [현재 구현 상태](현재-구현-상태.md),
범위는 [프로젝트 범위](프로젝트-범위.md), 경로와 소유권은 [저장소 구조](저장소-구조.md)를 따른다.
현장 옥동 AI 2종의 입력·출력·모델 계약 확정 과제는 계속 유지한다.

## 기존 저장소에서 Profile부터 확장 — 2026-09-30 확정

새 저장소를 만들지 않고 현재 저장소 안의 **`profile-spec/`**를 독립 개발 영역으로 사용한다.
기존 EdgeX 수집·노드 관측·Runtime Operator·대시보드를 기반으로 확장한다.
지금 확정한 것은 개발 위치와 접근 방식이며, 해당 디렉터리와 Schema 코드를 생성한 상태는 아니다.

첫 개발 묶음은 다음 순서로 진행한다.

1. 기존 RuntimeService·ServiceDescriptor·노드 관측과 새 개념의 **필드 대응표** 작성
2. **DeviceProfile·ServiceProfile·VirtualDeviceProfile·RuntimeState** 네 가지 Schema 초안 작성
3. 정상·누락·불일치 예제와 단위·참조·버전·값 검증
4. 기존 정보를 새 규격으로 변환하는 **읽기 전용 연결부** 작성
5. 실제 배치를 바꾸지 않고 후보·제외 이유를 비교한 뒤 기존 배치 로직과 연결 범위 결정

`profile-spec/`의 초기 산출물은 Schema·예제·검증 코드·필드 대응표다. YAML 예제와 JSON Schema의
검증 규칙을 따로 중복 관리하지 않는다. 초기 정적 정의는 버전 있는 파일로 관리하고 Profile Manager
REST API·Registry DB는 계약과 기존 원본의 소유권을 정리한 후 개발한다.
Profile Registry가 EdgeX·Kubernetes의 디바이스 원본을 복제한 별도 관리 원장이 되지 않도록 한다.

### Schema에 반영할 원칙과 미해결 항목

| 항목 | 적용 방향 |
|---|---|
| Capability 매칭 | ServiceProfile에 장비명 `compatibleDevices`를 직접 나열하지 않고 자원·architecture·backend·runtime 조건으로 후보 탐색 |
| 실행·성능 근거 | 기존 `verifiedNodes`와 qualification은 검증 근거로 유지; Capability 일치만으로 자동 배치 자격을 주지 않음 |
| 정적 정의와 상태 | DeviceProfile은 기본 능력, RuntimeState는 현재 관측·예약 여유·수집 시각·실패 사유; 상태는 정적 Profile Registry의 수정 대상이 아님 |
| Profile과 인스턴스 | 같은 Profile을 여러 Device가 참조; 참조 버전과 실제 instance ID를 구분 |
| 서비스 실행 형태 | 기존 variants의 이미지·모델 artifact·architecture·backend 조합을 연결; GPU/NPU 종류만으로 호환성을 단정하지 않음 |
| 요구량 | minimum·recommended·maximum을 구분; Kubernetes requests/limits나 관측 min/max를 실측 요구량으로 자동 치환하지 않음 |
| 메모리와 자원 | 실제 사용량과 예약 가능량을 구분하고 공유 메모리·서버/VD의 동일 자원을 중복 합산하지 않음 |
| VirtualDeviceProfile | Schema 초안은 함께 정의하되 동적 생성·삭제·서버 할당 연결은 ⑦에서 구현; Profile·VD 인스턴스·서비스 연결·실제 할당 관계를 먼저 정리 |

VD의 물리 기능/인터페이스 표현과 dynamic binding 제안이 기존 RuntimeService 서버 슬롯의 고유
연결 규칙에 미치는 영향은 아직 상세 계약 확정 전이다. 기존 규칙을 조용히 바꾸거나
`binding.mode: dynamic` 선언만으로 동적 연결·에뮬레이션을 지원한다고 설명하지 않는다.
사용자가 제시한 장비 사양·자원 수치·이미지·API 예시는 명세 초안이며 실제 검증값으로 등록하지 않는다.

첫 인수 기준은 **기존 노드·서비스 정보를 새 Schema로 표현하고 후보·제외 이유를 설명할 수 있음**이다.
여러 기관이 독립적으로 명세를 배포·버전 관리해야 할 때 별도 Profile 명세 저장소 분리를 검토한다.

## 진행 기록과 다음 작업

**현재 단계는 ①의 방향·구조 정리 완료, Schema 코드 구현 전**이다.
다음 작업은 기존 필드 대응표와 네 가지 v1 Schema 초안·예제·검증이다.
진행 중·완료·보류, 검증 근거, 커밋/배포 여부와 다음 작업은
[현재 구현 상태](현재-구현-상태.md)의 최신 체크포인트에 계속 기록한다.
이 문서는 확정한 방향·순서·인수 기준을 관리하며 일일 진행 기록은 중복하지 않는다.
