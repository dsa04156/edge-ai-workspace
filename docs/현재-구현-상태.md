## live 상태 스냅샷

2026-08-28 조회 시 전체 6개 node 중 5개가 Ready다. 중앙 EdgeX workload, Serial Device
Service, Adapter Controller, source `sensor-anomaly-demo`, Server1 endpoint와
`state-aggregator`는 Ready다.

`etri-dev0003-raspi5`는 2026-08-27 06:32 UTC부터 `NodeStatusUnknown`이며
`node.kubernetes.io/unreachable` taint가 적용됐다. 이 노드에 고정된 Sense HAT Pod는
schedule되지 않아 `device-sensehat-raspi`가 `0/1`이고, 이 때문에 `edgex-telemetry`가
`Progressing`이다. 확인된 직접 증거는 “kubelet이 node status를 게시하지 않음”까지이며,
전원·네트워크·EdgeCore 중 하위 원인은 별도 현장 진단이 필요하다.

source `sensor-anomaly-demo`는 `sensor-anomaly-demo-execution` Lease holder로 ACTIVE다.
입력은 fresh, 모델은 ready, Runtime Recommendation은 `NORMAL/read_only`이며 현재 요청은
edge-local에서 처리된다. `edge-ai-workloads`에 과거 격리 검증 candidate가 남아 있지만
source 소유권이나 production traffic을 대체하지 않는다.

## Runtime 실행 검증 경계

2026-08-26 격리 실클러스터 시험에서 다음을 확인했다.

- 승인된 immutable candidate Deployment 생성과 Pod Ready
- SHADOW 상태의 health·input·model·memory-only inference validation
- Kubernetes Lease의 source→candidate handoff와 candidate ACTIVE 처리
- candidate 장애 후 source로 Lease rollback과 inference 재개
- selectorless Service와 controller 소유 core `Endpoints`를 이용한
  Jetson source→Raspberry Pi candidate→Jetson source HTTP 전환

그러나 현재 production Service는 Argo CD 소유 selector를 유지하고 Runtime Controller의
계약은 EndpointSlice 기반이다. EdgeMesh의 EndpointSlice 소비가 입증되지 않아
`sensor-anomaly-demo` traffic 단계는 `routing_mode_unsupported`로 차단된다. 승인 실행 이력
2건도 각각 routing 미지원과 candidate 장애 검증으로 최종 `FAILED`이며, 이는 실패를 숨기지
않는 fail-closed 증거이지 운영 migration/offloading 완료 근거가 아니다.

## 로컬 검증 중인 미배포 구현

Serial Device Service에는 established stream의 오류 감지부터 첫 유효 sample이 EdgeX SDK
async channel에 전달될 때까지를 재는 계측과 400ms 개발 gate가 추가됐다. 초기 open 실패는
표본에서 제외하고 포트 open만으로 완료 처리하지 않는다. 25·50·100·200ms fast-retry와
`SerialRecoveryTargetMisses` metric을 포함하지만, 새 image 배포와 30회 실장비 장애 주입을
아직 수행하지 않았으므로 400ms 달성 상태는 `미측정`이다. 공식 250ms 목표와 전체 node/Pod
failover는 별도다. 상세 기준은 [가상화 노드 오류 복구시간](가상화-노드-오류-복구시간.md)을
따른다.

현재 checkout에는 ACTIVE Jetson이 수집·전처리·저장을 유지하고 Server1에 inference만 요청하는
부분 offloading 구현이 있다. stable request ID, 응답 identity/model/freshness 검증, 중복 결과
차단, source 측 network preflight와 LOCAL_FALLBACK을 포함한다. 2026-08-28 현재 파일 기준
검증 결과는 다음과 같다.

- `sensor-anomaly-demo`: 118 tests passed
- `state-aggregator`: 317 Python tests passed
- dashboard: 167 JavaScript tests passed
- `state-aggregator/k8s`: Kustomize render 성공

이 변경은 아직 커밋·Argo 배포되지 않았으며, `baseline-1.0.0` Server1 후보의 기존 GPU 성능
자격도 계속 `rejected`다. 따라서 실제 운영 요청은 자동으로 REMOTE로 바뀌지 않는다.

## 서비스 데모 의미

[`sensor-anomaly-demo`](펌프-모터-이상감지-서비스.md)의 입력 계약은
`okdong.pump-motor.telemetry/v1`이다. 현재 Arduino raw 입력은 플랫폼 연결 기준선이며 옥동
설비 단위가 아니다.

- 가속도 X/Y/Z는 같은 `origin`으로 frame을 구성한다.
- 온도는 허용 시간차 안의 가장 가까운 sample만 결합한다.
- 진동 20개, 온도 10개 window와 30개 warm-up을 사용한다.
- 현재 backend는 학습된 고장 분류기가 아닌 `online-baseline`이다.
- 결과와 alert transition은 서비스 소유 SQLite에 idempotent하게 저장한다.
- 화면의 `anomaly`는 현재 통계 기준선 판정이며 실제 설비 고장을 입증하지 않는다.

실제 설비 고장 분류 정확도와 생산성 개선 효과는 옥동 현장 데이터로 별도 검증해야 한다.
