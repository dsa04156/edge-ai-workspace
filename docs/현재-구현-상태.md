## 미사용 워크로드 운영 정리 — 2026-09-17

사용자 요청으로 Kubeflow·Kueue·AI Scientist·MLflow와 후속 과학 AI 스택·과거 실험의
실행·접속 리소스를 운영 클러스터에서 제거했다. 데이터 삭제와 구분한 정리다.

  Deployment 16개·Service 13개·Ingress 4개·CronJob 1개 제거 뒤 대상 Pod 0개를 확인했다.
  정리 전 Pod 19개 중 Running은 16개였으며, 종료된 잔여 Pod도 소유자 삭제로 정리됐다.
- PVC 5개(선언 용량 합계 67Gi)는 같은 UID·Bound 상태로 보존했다. Namespace,
  ConfigMap, Secret과 소스·과거 검증 기록도 유지했다. 67Gi는 실제 디스크 확보량이 아니다.

비교 기준은 [2026년도 2차년도 옥동 PoC 추진계획(안)](단계별-추진계획.md)의

함께 참고한다. 이 표는 해당 PoC의 개발 진행 비교이며 협약 전체 정량지표의 공식 달성 판정은 아니다.
계획서에 누적된 과거 구현 설명보다 최신 승인 범위와 날짜별 검증 근거를 우선한다.

### 지금 작업이 연차 목표에 기여하는 지점

현재의 **서비스 선택·실행 맵·부하·오프로딩 개발은 서비스 실행 기반, 엣지·서버 분산,
통합 운영 화면을 준비하는 작업**이다. 모델과 장비를 넓혀도 같은 방식으로 운영할 수 있게
만드는 중이며, 옥동 AI 2종의 모델·데이터와 생산성 효과까지 대신 검증한 것은 아니다.

연차 목표를 위해 다음을 병행해야 한다.

1. **현장 입력 확정:** 옥동의 접근 권한·PLC/MES 항목·생산 건 식별자·label을 확정하고,
   ETRI 수집 인터페이스에서 원본 값과 중앙 저장 값을 대조한다.
2. **실제 모델 연결:** KPST의 생산품질 판별, 경북대학교의 펌프·모터 모델을 서비스별 계약으로
   인수한다. ETRI는 컨테이너 실행·데이터·결과·운영 경로를 연결하고 KPST와 워크플로우를 연동한다.
3. **운영·복구 검증:** 현재 범용 AI 운영 개발을 이어가면서 영속 저장·재전송을 구현하고,
   TTA와 단위·통합 시험의 측정 구간·입력 조건·합격 기준을 맞춘다.

정량 비교는 숫자가 같은 이름을 가졌는지보다 **무엇을 어디까지 측정했는지**를 먼저 확인한다.
Serial 30회 시험의 최대 309.848ms는 오류 감지부터 유효 sample의 SDK 전달까지인
**2차년도 내부 400ms 개발 기준** 통과 근거다. 과제 최종 250ms, 노드 전체 복구,
장애 중 데이터 유실 0건을 입증한 값은 아니다. 생산품질·이상감지의 정확도와 생산성 개선은
현장 정답 데이터·비교 기간·분모와 합격 기준을 확정한 뒤 별도로 평가한다. 임의 완료율은 쓰지 않는다.

이 비교표는 의미 있는 개발 단계가 끝날 때 관련 행의 **현재 구현·남은 작업·근거**를 갱신한다.
연차 목표 자체와 기관 역할은 승인된 계획이 바뀔 때만 수정한다.

## Serial recovery 배포·실측 상태

Serial Device Service에는 established stream의 오류 감지부터 첫 유효 sample이 EdgeX SDK
async channel에 전달될 때까지를 재는 계측과 400ms 개발 gate가 추가됐다. 초기 open 실패는
표본에서 제외하고 포트 open만으로 완료 처리하지 않는다. 25·50·100·200ms fast-retry,
`SerialRecoveryTargetMisses` metric과 port ready·first byte 구간 계측을 포함한 immutable
image가 Jetson에 배포됐다.

개선 전 2026-09-01 실제 Arduino의 `cdc_acm` 인터페이스를 50ms 단절·복원한 canary에서
`detected=1`, `completed=1`, `durationMs=2215.224661`, `attempts=4`, `targetMisses=1`을
관측했다. 같은 Device Service Pod는 restart 0으로 Ready를 유지했고 stable Serial path와 첫
후속 Core Data Event도 복원됐다. 자동 복구는 성공했지만 400ms gate는 실패했으며 첫 초과로
30회 `max ≤ 400ms` 합격이 불가능해 나머지 29회는 조기 중단했다. 공식 250ms 목표와 전체
node/Pod failover는 별도다. 상세 증거와 후속 계측 항목은
[가상화 노드 오류 복구시간](가상화-노드-오류-복구시간.md)을 따른다.

후속 원인 진단은 같은 50ms 단절을 6건으로 제한해 수행했다. 1건은 158.629ms로 통과했지만
5건은 1,817.702~1,843.971ms로 실패해 process-local counter가 `detected=6`, `completed=6`,
`targetMisses=5`가 됐다. 실패 5건의 감지→port ready는 61.218~84.425ms, port ready→첫 byte는
1,750.519~1,754.341ms, 첫 byte→유효 frame은 4.170~8.704ms였다. 같은 Pod는 Ready·restart 0을
유지했고 Core Data Event도 계속 증가했다. 이 6건은 원인 진단이며 당시에는 30회
qualification 통과 증거가 아니었다.

원본 sketch·pin·JSON 계약과 application rollback을 확보한 뒤 Linux termios의 `HUPCL`만
해제하고 Arduino sample cycle을 1,000ms에서 100ms로 줄였다. physical auto-reset 회로,
bootloader, fuse와 EEPROM은 변경하지 않았다. revision `d9adba1b`, immutable image
`edgex-device-serial@sha256:fe0377db16757fde48f70029088c72e6c21ac86ba7c3d7d11b51d3b5af55dcfe`
를 배포했다.

같은 50ms 단절·복원의 사전 canary는 104.169ms였고 이어서 실행한 정식 30회는 30/30회
통과했다. min 90.469ms, p50 108.062ms, p95 231.078ms, max 232.432ms, mean 127.539ms이며
최종 process counter는 `detected=31`, `completed=31`, `targetMisses=0`이었다. 동일 Pod가
Ready·restart 0을 유지했고 Core Data temperature Event도 p50 118.623ms cadence로 계속
증가했다. 이 결과는 2차년도 400ms 내부 개발 gate 통과 근거이며 과제 최종 250ms나 전체
node/Pod failover 합격 근거는 아니다.

2026-09-02에는 정상 전송을 1,000ms로 복원하고 재연결 뒤 첫 byte가 없을 때만 25ms 간격으로
최대 네 번 `READ_NOW`를 보내는 저빈도 방식으로 교체했다. USB 재열거로 `ttyACM` 번호가
바뀌어도 Pod가 따라가도록 승인된 udev identity rule이 `/run/edgeai/devices/arduino-001`을
현재 major/minor로 교체하고, Device Service에는 이 좁은 디렉터리만 read-only mount한다.
전체 `/dev`·`/sys` mount는 추가하지 않았다.

최종 canary는 199.839ms였고 별도 정식 30회는 30/30회 통과했다. min 181.833ms, p50
196.619ms, p95 304.244ms, max 309.848ms, mean 214.674ms이며 canary 포함 최종 counter는
`detected=31`, `completed=31`, `targetMisses=0`이다. 같은 Pod는 Ready·restart 0을 유지했고
Local Data 정상 sample 11개 간격은 998.627~1,003.651ms였다. 당시 Core Data Event query가
사전부터 503이어서 그 30회의 회차별 중앙 Event 묶음은 확보하지 못했다.

2026-09-02에 약 1,200만 Event를 전체 최신순으로 훑던 디바이스 조회를 device-first index
조회로 바꾸고, Event row를 읽는 DB 연결을 반납한 뒤 Reading을 조회하도록 Core Data 4.0.2를
패치했다. 수정 뒤 stale Sense HAT latest Event는 22.719ms에 HTTP 200, 같은 요청 8개 동시는
8/8회 109.084~202.137ms에 성공했다. 신규 Event는 시험 직후 10초에 60건이 적재됐고 latest
age는 0.123초였다. 추가 50ms Serial 단절 canary도 205.724ms에 복구됐으며 첫 후속
temperature Event가 4.130ms 뒤 중앙 DB에 저장되고 Event ID API에서 HTTP 200으로 조회됐다.
따라서 중앙 저장 E2E canary는 통과했지만 과거 30회 전체에 중앙 readback을 소급 적용하지
않는다.

- 온도는 허용 시간차 안의 가장 가까운 sample만 결합한다.
- 진동 20개, 온도 10개 window와 30개 warm-up을 사용한다.
- 현재 backend는 학습된 고장 분류기가 아닌 `online-baseline`이다.
- 결과와 alert transition은 서비스 소유 SQLite에 idempotent하게 저장한다.
- 화면의 `anomaly`는 현재 통계 기준선 판정이며 실제 설비 고장을 입증하지 않는다.

실제 설비 고장 분류 정확도와 생산성 개선 효과는 옥동 현장 데이터로 별도 검증해야 한다.
