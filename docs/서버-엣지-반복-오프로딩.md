# 서버·엣지 반복 오프로딩

2026-09-10 변경: 전용 웹 데모의 **왕복 데모 시작·신규 요청 중지**는 토큰 입력 없이
사용한다. `/api/demo/start`, `/api/demo/stop`에 적용하며, 별도 직접 추론·개별 요청 조회
API의 인증은 유지한다. 아래 9월 9일 인증 시험 기록은 변경 전 이력이다.

현재 사용자 지정 데모는 **Nano → AGX Orin → DGX Spark → AGX Orin → Nano**다.
Nano와 AGX는 모두 엣지이고 Spark가 서버다. 물리 역할과 실행 순서를 별도 설정으로
관리하며, 정상 승격·복귀는 인접 단계만 이동한다. 중앙 컨트롤러가 판단·전환을 담당한다.
아래 초기 구현 기록의 AGX 서버 역할은 이 후속 지시로 대체됐다.

2026-09-09 사용자 승인 범위는 기존 Runtime Recommendation → Execution Plan →
Execution Controller에 모델 실행 경로를 추가하는 것이다. 모델 준비·실제 추론 확인·
신규 요청 전환·복귀·drain·메모리 해제를 실행한다. Pod, GPU 공유 슬롯, EdgeX 수집기,
Kubernetes Service selector는 유지한다. 서비스 설계 화면은 계속 dry-run이다.

## 판단과 실행 계약

- Git 설정은 노드별 edge/server 역할, 고정 요청 계약, 후보별 측정 근거와
  `execution_order`를 지정한다. 현재 순서는 Nano·AGX·Spark이고 역할은 edge·edge·server다.
- 후보는 모델 digest·실제 node identity·관리 상태·자원 상태·관측 freshness와
  검증된 수용량을 통과해야 한다. 선언되지 않은 주소를 검색하거나 자동 등록하지 않는다.
- Kubernetes Ready·Memory/Disk/PIDPressure·실제 runtime Pod 배치와 고정 image를
  확인한다. 이미 상주하는 Pod의 GPU 예약을 사용하므로 추가 GPU 슬롯을 요청하지 않는다.
- 부하가 지속될 때 현재 실행 노드의 바로 다음 단계만 평가한다. 준비 중 현재 노드가 계속 처리하는 비용과 측정된
  네트워크 포함 처리시간을 비교한다. 예측은 미래 부하가 유지된다는 가정이다.
- 준비와 probe 전에는 현재 노드가 신규 요청도 처리한다. 접수된 요청은 지정된 노드에서
  완료하며 전송 결과가 불명확한 요청은 자동 재전송하지 않는다.
- 낮은 전체 유입률이 직전 단계 용량의 60% 이하로 30초 유지되고 실제 추론을 확인한 뒤 한 단계 복귀한다. 떠난 상위 노드의 접수·진행·worker
  queue가 모두 비고 유휴 시간이 지난 뒤 모델만 해제한다.
- 실제 CACHED·model_loaded=false·VRAM=0을 확인한 뒤 다음 주기를 허용한다.
- SQLite FULL WAL에 요청 원장과 상태 전이를 저장한다. 재시작 시 미완료 요청은
  interrupted/unknown으로 보존하고 서버 잔여 작업을 확인·정리한 뒤 재개한다.

## 검증 및 운영 책임

초기 계약은 기존 Llama 3.2 1B 시험의 고정 prompt·8토큰이다. 다른 서비스에는 별도
계약·측정이 필요하다. 운영자는 단일 컨트롤러, 영속 원장, 검토된 설정과 실행 token을
관리한다. 실행 API는 X-Execution-Token을 사용하며 기본 운영 배포에서는 비활성이다.
자동시험은 후보 선택, 준비 중 엣지 처리, 반복 왕복, drain, 실패·stale·중복·재시작을
확인한다. 실장비 증거는 별도 기록하며 계획을 검증 완료로 설명하지 않는다.
엣지 전체 정전/네트워크 단절, 중앙 고가용성, 실행 중 KV cache 이동은 제외한다.

## 코드와 API

| 역할 | 구현 |
|---|---|
| 역할·고정 요청·측정 근거 | `app/model_offload_contract.py`, `app/config/model_offload_llama.json` |
| 엣지/서버 판단 및 후보 선택 | `runtime_recommendation.recommend_model_offload` |
| 모델 단위 실행 계획 | `runtime_execution_plan.build_model_offload_execution_plan` |
| 반복 실행·영속 원장·worker 통신 | `app/model_offload_controller.py` |
| edge→edge→server 순차 전환·복귀 | `app/model_offload_ordered.py` |
| 격리 데모 실행 진입점 | `app/model_offload_demo.py` |
| API와 기존 app 수명주기 연결 | `app/model_offload_api.py`, `app/main.py` |
| 자동시험 | `tests/test_model_offload.py`, `tests/test_model_offload_ordered.py` |

위 경로는 `edge-orch/state-aggregator/` 기준이다. 기존 sensor-anomaly의 워크로드
증강·교체 controller 및 API는 그대로다. 모델 단위 실행은 전용 executor로 연결한다.
과거 `edge-orch/placement_engine/`·workflow 코드를 운영 경로로 복원하지 않는다.

API prefix는 `/api/runtime-model-offloading`이다.

- `GET /`: 현재 상태, 선택 노드, 후보별 제외 이유, 관측·queue·inflight
- `GET /execution-plan`: 모델 단위 실행 단계
- `GET /history`: 영속 상태 전이 기록
- `POST /generate`: `request_id`, 검증된 `prompt`, `max_tokens=8`로 요청
- `GET /requests/{request_id}`: 재접속 후 결과 또는 unknown/interrupted 확인

요청 생성과 개별 결과 조회는 `X-Execution-Token`이 필요하다. 같은 ID로 다시 요청하면
기존 결과를 반환하거나 진행 중 요청을 기다린다. unknown은 재실행하지 않는다.
응답은 최종 JSON이며 정상 여부는 `status=ok`를 확인한다. worker의 첫 streaming token을
받은 시점은 `gateway_ttft_ms`에 기록한다. 이는 gateway 접수 이후 내부 측정으로,
외부 HTTP client의 첫 응답 byte나 과거 CLI의 scheduled-arrival TTFT와 같지 않다.

## 실행과 중지

현재 격리 데모 배포는 아래의 [순차 데모 실행 절차](../qualification/llama-offloading/nano-orin-spark-controller-k8s/README.md)를 따른다.
기존 플랫폼에 통합 배포할 때는 state-aggregator image build 경로가 새 app 파일과 JSON을
함께 포함한다. 새 이미지를 검증한 환경에서 다음 설정으로 시작한다.

```text
MODEL_OFFLOAD_ENABLED=true
MODEL_OFFLOAD_CONTRACT_PATH=/app/app/config/model_offload_llama.json
DATA_DIR=/app/data
EXECUTION_MANAGEMENT_TOKEN=<운영 Secret에서 주입>
```

기본 Kustomize에는 enable 설정을 넣지 않았다. 기존 Pod의 환경변수만 바꾸어도
새 코드가 생기지는 않으므로 새 이미지 배포가 선행되어야 한다. 기존 실행 token·
node/pod 읽기 RBAC를 재사용하며 Kubernetes 쓰기 권한을 추가하지 않는다.
Service DNS로 계약에 등록한 모든 worker에 접근 가능한 클러스터 내부에서 실행한다.

컨트롤러는 1개 replica·Recreate와 영속 DATA_DIR을 사용한다. 파일 잠금으로 같은 원장의
중복 소유를 막는다. 운영자는 다른 CLI/프록시가 같은 worker의 모델을 제어하지 않도록
해야 한다. 별도 원장을 쓰는 중복 컨트롤러나 다른 클라이언트를 분산 잠금으로 차단하는
기능은 없다. 원장 보존과 디스크 용량 관리도 운영 책임이다.

중지 전 신규 요청을 멈추고 `LOCAL`, 서버 `CACHED`, VRAM 0을 확인한다. 서버 상태가
불명확하면 엣지의 신규 처리는 가능하지만, 해제를 확인할 때까지 다음 서버 주기는
보류한다. 강제 종료 시 이미 전송한 요청은 unknown으로 남기며 성공처럼 복구하지 않는다.

## 초기 2단계 구현의 검증 기록

역할 기반 후보 선택·stale/모델/자원/실제 배치 제외, 준비 중 엣지 처리, 수동 시계의
3회 왕복, 실제 background loop의 연속 2회 왕복, 중복·client 취소·불명확한 원격 응답,
drain·해제 readback·재시작 원장 복구를 자동시험한다. 합성 worker 시험이며 실장비
처리율이나 무중단 SLO의 증거로 사용하지 않는다.

실장비 사전 점검에서 AGX `etri-dev0005-jetagx`는 NotReady, 기존 Llama Pod는
Terminating, 대체 Pod는 unreachable taint로 Pending이었다. SSH도 No route to host였다.
따라서 새 컨트롤러의 실제 Nano↔AGX 반복시험과 운영 배포는 수행하지 않았다.
기존 9월 8일 10쌍의 CLI 합격은 이전 실행 경로의 증거로 유지한다.

최종 자동시험은 state-aggregator Python 402개(새 오프로딩 31개 포함), JavaScript
228개, 문서 집중 검사 21개가 통과했다. 기본 Kustomize render와 `git diff --check`도
통과했다. 저장소 전체 검사는 115개 통과·1개 기존 실패다. 실패 항목은 sensor-anomaly
Argo CD의 targetRevision을 main으로 기대하는 테스트와 기존 HEAD의
agent/edgex-central-docs 설정 불일치이며 이번 작업에서 변경하지 않았다.

[검증 결과·코드 해시](assets/model-offload-20260909/verification.json),
[실장비 사전 점검](assets/model-offload-20260909/live-preflight.json)을 함께 보관한다.
로컬 HTML 생성 완료이며 새 코드와 문서를 live 배포한 것으로 설명하지 않는다.

## 후속: 실제 Nano·AGX·Spark 3단계 데모

사용자 수정에 따라 Nano와 AGX를 모두 엣지로 두고 실제 DGX Spark를 마지막 서버 단계로
연결했다. Spark 노드는 `etri-ser0003-cg0ms0`이며 RTX 대체 서버가 아니다.
`execution_order`와 물리 `role`을 분리했고, 정상 전환은 인접 단계만 평가한다.
현재 노드 용량의 85%·5초 압력, 준비 비용 포함 예측 이득 15%, 60초 cooldown을 유지한다.
복귀는 직전 단계 용량의 60%·30초 저부하를 기준으로 한 단계씩 수행한다.

| 구간 | 역할 | 상승 검토 유입률 | 하강 검토 유입률 |
|---|---|---|---|
| Nano → AGX | edge → edge | 3.4 req/s 이상 5초 | AGX → Nano: 2.4 req/s 이하 30초 |
| AGX → Spark | edge → server | 4.08 req/s 이상 5초 | Spark → AGX: 2.88 req/s 이하 30초 |

큐 기반 예상 TTFT도 상승 조건이다. 상승 조건만으로 즉시 전환하지 않으며 실제 모델
준비·추론, 후보 자격, 현재 유입률 수용 가능성과 cooldown을 함께 확인한다.
높은 단계에서는 아래 단계 모델을 복귀용으로 유지한다. 내려온 뒤에는 떠난 단계의
queue/inflight가 비고 30초 유휴가 지난 다음 모델을 해제한다. Pod·GPU 예약은 유지한다.

Spark는 `nvidia-spark` RuntimeClass를 지정해 NVIDIA GB10·CUDA(compute capability 12.1) 장치로
인식됨을 확인했다. 최초 RuntimeClass 누락 시도는 CPU fallback으로 거절하고 별도 보존했다.
Ollama의 GB10 지원은 [공식 지원 목록](https://docs.ollama.com/gpu)과 대조했으며,
이번 완료 판단은 실제 runtime 로그·모델 GPU 메모리·응답 node identity로 수행한다.

고정 8토큰의 Spark 실측은 busy 30건×3회, cache activation+probe 10회,
6 req/s·30초 부하×3회다. 540개 부하 요청의 회차별 p95 첫 토큰 지연은 약 20.6~21.1ms,
캐시 준비+실제 추론은 약 2.7~3.1초였다. 6 req/s는 검증된 하한이며 포화점의 최댓값이 아니다.
기존 v2 전체 자격시험을 재수행했다고 설명하지 않는다.
[실측 profile·원본 해시](assets/ordered-offload-20260909/spark-profile.json)를 함께 보관한다.

새 격리 controller는 `llama-continuity-test`의 `ordered-offload-controller`다.
기존 플랫폼 app image와 해시가 붙은 코드 ConfigMap을 사용하며, 운영 대시보드의
기본 MODEL_OFFLOAD_ENABLED는 변경하지 않는다. API port는 18113이다.
배포·보안 경계와 재현 명령은
[순차 데모 실행 절차](../qualification/llama-offloading/nano-orin-spark-controller-k8s/README.md)를 따른다.

### 실제 왕복 시험과 장애 기록

2026-09-09 첫 실행은 Nano → AGX → Spark → AGX까지 정상 전환했고, 마지막 Nano
복귀 전 AGX heartbeat가 끊겨 신규 요청을 Nano로 긴급 전환했다. AGX가 다시 Ready로
관측된 뒤 잔류 모델을 해제했다. 정상 왕복 횟수는 0이며 **불합격**으로 보존한다.
1,622건 중 1,616건이 정상 완료했고, HTTP 오류 1건·처리 여부 불명 1건·전송 전 실패
4건이 발생했다. 노드 연결 단절의 근본 원인은 이 시험만으로 확정하지 않았다.

[첫 실행 결과와 상태 전이](assets/ordered-offload-20260909/run-01.json)를 보관한다.
이 결과는 정상 부하 전환과 노드 단절 시 무손실 처리가 서로 다른 검증 항목임을 보여준다.
현재 이미 전송한 불명확한 요청은 자동 재실행하지 않고, 전송 전 실패도 성공으로
바꾸지 않는다. 따라서 노드 단절까지 포함한 무중단·무손실을 보장한다고 표현하지 않는다.

같은 임계값·부하의 두 번째 실행은 **Nano → AGX → 실제 Spark → AGX → Nano**를
정상 완료했다. 고정 요청 1,622건 모두 성공했고, 중복 ID·실패·unknown은 0건이다.
실제 응답은 Nano 312건·AGX 692건·Spark 618건이다. 최종 정상 왕복 횟수는 1이며,
Nano ACTIVE를 유지한 채 AGX·Spark 각각 CACHED, model_loaded=false, 모델 VRAM 0,
active_requests=0, queue_length=0을 확인했다. Pod와 GPU 예약은 유지했다.

[두 번째 실행 결과·실제 응답 노드·해제 확인](assets/ordered-offload-20260909/run-02.json)을
근거로 **고정 8토큰 정상 부하 왕복 데모 1회 합격**으로 판정한다. 첫 실패 기록을
제외해 장애 연속성까지 합격했다고 일반화하지 않는다. 상세 요청과 압축 관측 원본은
`qualification/llama-offloading/results/2026-09-09-ordered-demo/`에 보관한다.

추가 자동시험에서 인접 단계 복귀 probe와 admission 장애 전환이 겹치면 중단된 왕복을
정상 횟수로 셀 수 있는 경합을 재현했다. DRAINING 진입 시 즉시 복구 상태로 표시하고
정상 왕복 자격을 지우도록 수정했다. 관련 40개·전체 state-aggregator Python 411개
검사를 통과했다. [검증·코드 해시](assets/ordered-offload-20260909/verification.json)를 보관한다.
실장비 두 실행의 코드 ConfigMap은 `ordered-offload-code-ckf9t7th8c`이고, 경합 수정은

## 실장비 데모 화면

후속 요청으로 [Nano·Orin·Spark 데모](http://offload-demo.192.168.0.56.sslip.io/)를 추가했다.
시작 버튼은 고정 5구간 부하를 서버에서 실행하며, 실제 전환은 기존 순차 controller가
결정한다. 별도 시뮬레이션 이동이나 임의 노드 전환 버튼은 없다. 화면은 현재 요청 처리
노드, 실제 응답 수·텍스트, 실패·불명확, 모델 메모리와 이동 이력을 표시한다.

`app/model_offload_demo_run.py`가 단일 실행·토큰 인증·고정 요청·32개 이하의 동시
부하 작업을 관리한다. `app/static/ordered-demo/`는 별도 화면이며 운영 대시보드와
서비스 설계 dry-run을 변경하지 않는다. 정지 시 부하만 멈추고 접수 요청 마무리,
Nano 복귀·상위 모델 해제를 확인한다. 컨트롤러 재시작은 interrupted로 남기며
브라우저 재접속은 기존 실행 상태를 조회한다. 토큰은 브라우저에 영속 저장하지 않는다.

시작 전 세 노드 자격·관측, Nano 준비, 이전 요청과 잔류 모델 정리를 확인한다.
UI 실행 중 중복 시작과 다른 `/generate` 요청은 409로 거절한다. 직접 worker를
조작하는 외부 CLI까지 분산 잠금으로 통제하는 것은 아니다. 운영 토큰 조회·실행 절차는
[데모 실행 절차](../qualification/llama-offloading/nano-orin-spark-controller-k8s/README.md)를 따른다.

### 웹 실행기 검증 중 발견한 저장 지연

첫 UI 전체 실행은 585건 중 565건 정상·관측 유효성에 따른 거절 20건으로 중지했다.
관측을 추가 기록한 다음 실행은 767건 중 683건 정상, 전송 전 실패 33건·접수 거절
49건·부하 생성기 동시 작업 제한 2건으로 중지했다. 두 실행 모두 왕복 불합격이다.
두 번째 관측에서는 세 노드의 실제 관리 응답·모델 identity가 유지된 상태에서 관측
나이가 동시에 4~5초 이상으로 증가했다. 컨트롤러 cgroup CPU throttling은 0,
I/O pressure full avg60은 13.42%로 확인했다. 노드 자체 장애로 단정하지 않는다.

UI 요약이 요청 SQLite FULL WAL에 요청마다 동기 commit을 추가하던 구현을 제거했다.
기존 요청 원장의 내구성은 유지하고, UI 요약은 별도 JSON 파일에 단일 비동기 writer로
합쳐 저장한다. 실행 header를 저장한 뒤 부하를 시작하고 최종 결과도 저장한다.
느린 요약 파일 쓰기와 동시에 heartbeat가 계속 진행하는 자동시험을 추가했다.
실제 성능 개선 여부는 수정 후 왕복 결과와 구분해 기록한다.

UI 요약의 비동기 저장만 적용한 전체 실행도 1,622건 중 1,578건 정상, 거절 42건·전송 전
실패 2건으로 불합격이었다. 이어서 요청 FULL WAL의 자동 checkpoint를 고정 UI 실행
동안만 중지하고, 종료 시 별도 연결·비동기 PASSIVE checkpoint를 수행한 뒤 기존 설정을
복원하도록 변경했다. 각 commit의 FULL 내구성은 완화하지 않았다.

**최종 웹 실행은 1,622/1,622건 정상, 실패·unknown 0건으로 합격했다.** 실제 순서는
Nano → AGX → Spark → AGX → Nano이며 응답 수는 Nano 319건,
AGX 678건, Spark 625건이다.
Nano ACTIVE를 유지하면서 AGX·Spark의 CACHED·모델 메모리 0·queue/inflight 0을 확인했다.
종료 checkpoint는 busy=0, WAL 8,384페이지 전부 반영으로 완료했다.

[최종 웹 실행 결과](assets/ordered-offload-20260909/ui-final-run.json),
[자동검사·화면 확인·실패 시도와 수정 이력](assets/ordered-offload-20260909/ui-verification.json)을
보관한다. 수정 전 실패를 삭제하지 않았으며, 최종 1회 합격을 장기간·노드 단절까지
보장한 것으로 일반화하지 않는다. 최종 관련 검사 44개 통과이며, 직전 전체 Python
검사는 415개 통과했다. 전체 검사에서 발견한 기존 합성 타이밍 시험은 이미 지난
REMOTE 상태를 뒤늦게 기다리던 문제를 원장으로 확인해, 전환 관측 시 부하를 멈추도록
수정했다. 실행기 임계값은 변경하지 않았다.

PC·모바일 화면, 재접속, 잘못된 토큰 거절, 연결 단절 표시·버튼 비활성, 실제 시작·중지
API를 확인했다. 짧은 중지 시험은 접수된 29건을 모두 마무리했다. 9월 9일 당시 실행·중지는 운영
토큰을 요구했으며, 9월 10일부터 고정 데모 시작·중지는 토큰 없이 사용한다. 문서 HTML 생성과 이 데모 웹 배포는
별도다.

## 2026-09-10: 고정 웹 데모 토큰 입력 제거

사용자 요청으로 고정 왕복 데모의 시작·중지 API와 화면에서 실행 토큰 입력을 제거했다.
실제 배포 후 브라우저에서 토큰 없이 시작하고 Nano 단계에서 중지했다. 접수된 **24/24건**을
정상 완료했으며 실패 0, `status=stopped`, `active=false`, `can_start=true`를 확인했다.

별도 직접 추론 API에 토큰 없이 요청하면 HTTP 403을 반환하는 기존 경계도 확인했다.
