# 처음부터 배우는 Edge AI 시스템

이 문서는 컴퓨터와 AI를 처음 보는 사람도 현재 시스템을 처음부터 끝까지 이해할 수 있도록
아주 쉬운 말로 설명한다. 어려운 이름이 나오면 바로 뜻을 붙인다.

## 1. 이 시스템은 무엇을 하나요?

한 문장으로 말하면 다음과 같다.

> 기계에 붙은 센서의 숫자를 받아서, AI가 이상한 변화가 있는지 보고, 사람이 화면에서
> 확인하게 해 주는 시스템이다.

어린이집에 비유하면 이렇다.

| 실제 시스템 | 쉬운 비유 |
|---|---|
| 센서 | 교실의 온도계와 흔들림 측정기 |
| EdgeX | 선생님에게 숫자를 전달하는 반장 |
| AI 서비스 | 숫자를 보고 “평소와 다른가?” 생각하는 선생님 |
| Device1 | 교실 안의 작은 컴퓨터 |
| Server GPU | 어려운 계산을 도와주는 큰 컴퓨터 |
| 대시보드 | 모든 상황을 한눈에 보는 상황판 |
| 자원 증강 | 작은 컴퓨터가 바쁠 때 큰 컴퓨터의 도움을 준비하는 것 |

## 2. 무엇이 어디에 있나요?

### 센서

센서는 실제 세상의 값을 숫자로 바꾼다.

- 가속도 X: 좌우 방향으로 얼마나 흔들렸는지 나타낸다.
- 가속도 Y: 앞뒤 방향으로 얼마나 흔들렸는지 나타낸다.
- 가속도 Z: 위아래 방향으로 얼마나 흔들렸는지 나타낸다.
- 온도: 얼마나 뜨겁거나 차가운지 나타낸다.

현재 데모는 Arduino 센서의 X/Y/Z/온도를 사용한다. 이것은 시스템 연결을 확인하는
테스트베드다. 옥동 공장의 실제 펌프 고장을 학습한 완성 모델이라는 뜻은 아니다.

### Device1

Device1은 센서 가까이에 있는 작은 컴퓨터다. 현재 이름은
`etri-dev0001-jetorn`이고 Jetson 장비다.

Device1은 센서 값을 읽고, 값을 정리하고, 기본 AI 계산을 하고, 결과를 저장하고, 자기
CPU와 메모리가 얼마나 바쁜지 알려 준다.

### Server GPU

Server GPU는 Device1보다 큰 서버다. 현재 여유 GPU가 확인된 실제 노드는
`etri-ser0002-cgnmsb`다. API의 `server1` 이름은 기존 호환을 위해 유지한다.

Server GPU의 AI 추론 Pod는 HAMi를 통해 GPU 일부를 배정받는다. GPU backend 이름은
`cuda-online-baseline`, 모델 버전은 `cuda-baseline-1.0.0`이다. CUDA는 NVIDIA GPU에서
계산을 실행하는 기술 이름이다.

Server GPU는 다음 세 가지가 모두 맞아야 “준비됨”이 된다.

1. HAMi가 GPU를 실제로 배정한다.
2. 프로그램이 CUDA 장치를 연다.
3. GPU에서 시험 계산을 실행하고 올바른 답을 받는다.

GPU 이름만 붙이고 CPU로 계산하는 구조가 아니다. CUDA 시험 계산이 실패하면 모델은
준비되지 않은 것으로 처리한다. 다만 이 GPU 모델도 현재 통계 기준선의 GPU 실행 버전이다.
옥동 현장 데이터로 학습한 최종 고장 분류 모델은 아직 아니다.

### EdgeX

EdgeX는 “어떤 센서가 있고, 그 센서가 무슨 값을 보냈는지”를 관리한다.

- Core Metadata: 센서의 이름과 설명을 보관한다.
- Device Profile: 센서가 어떤 종류의 값을 보내는지 정한다.
- Device Service: 실제 센서와 이야기한다.
- Core Data: 센서가 보낸 최신 값과 이력을 보관한다.

물리 센서에 관한 정답은 EdgeX가 가진다. 대시보드가 센서를 마음대로 새로 만들거나 값을
고치지 않는다.

### Kubernetes와 KubeEdge

Kubernetes와 KubeEdge는 프로그램을 컴퓨터에 올리고 살아 있는지 확인한다.

- Node: 프로그램을 실행하는 컴퓨터다.
- Pod: 실행 중인 프로그램 한 묶음이다.
- Service: 다른 프로그램이 Pod를 찾아가는 고정 입구다.
- Ready: 지금 요청을 받을 준비가 됐다는 뜻이다.

Kubernetes는 센서 값의 주인이 아니다. 컴퓨터와 프로그램의 실행 상태를 관리한다.

### HAMi

HAMi는 여러 프로그램이 GPU를 나누어 쓸 수 있게 도와주는 GPU 스케줄러다.

현재 Server GPU AI Pod는 다음처럼 GPU를 요청한다.

| 요청 | 뜻 |
|---|---|
| `nvidia.com/gpu: 1` | GPU 장치 하나를 사용할 수 있게 해 달라 |
| `nvidia.com/gpucores: 20` | GPU 연산 자원의 20%를 사용하겠다 |
| `nvidia.com/gpumem: 1024` | GPU 메모리 1,024MiB를 사용하겠다 |

이 숫자는 Pod가 요청하는 몫이다. 실제 GPU 사용률은 Prometheus와 GPU exporter가 따로
관측한다.

### Prometheus

Prometheus는 컴퓨터의 계기판 숫자를 모은다. CPU, 메모리, GPU, 처리 시간, 기다리는 작업
수, 1초에 처리한 작업 수를 모은다. 값이 없거나 너무 오래됐으면 0으로 거짓 표시하지 않고
“관측 불가”로 표시한다.

### state-aggregator와 대시보드

`state-aggregator`는 여러 곳의 정보를 읽어 한 화면에 모은다.

```text
EdgeX의 센서 상태 ─┐
Kubernetes의 Pod 상태 ├─→ state-aggregator ─→ 대시보드
Prometheus의 자원 값 ┤
AI 서비스의 결과 ───┘
```

대시보드는 읽고 보여주는 역할이다. 현재 화면에서 자동으로 센서를 제어하거나 Pod를
증설하지 않는다.

## 3. 센서 값 한 건은 어떻게 움직이나요?

```text
센서 수집 → 전처리 → 특징 추출 → AI 추론 → 결과 저장 → 대시보드
                                      ├→ Device1 CPU
                                      └→ Server GPU 후보
```

### 1단계: 센서 수집

Device Service가 Arduino에서 X/Y/Z/온도를 읽는다. 각 값에는 측정 시각인 `origin`이 붙는다.

### 2단계: 전처리

프로그램이 같은 시각의 X/Y/Z를 한 묶음으로 맞춘다. 온도는 그 시각에서 2초 안에 있는 가장
가까운 값을 고른다. 필수 값이 하나라도 없거나 너무 오래됐으면 계산을 멈추고 이유를 남긴다.

### 3단계: 특징 추출

원래 숫자를 바로 판단하지 않고 이해하기 쉬운 특징으로 바꾼다.

- RMS: 흔들림의 전체 크기
- peak: 가장 큰 흔들림
- kurtosis: 갑자기 튀는 충격의 모양
- temperature mean: 최근 평균 온도
- temperature stddev: 온도가 얼마나 들쭉날쭉한지
- temperature delta: 처음과 마지막 온도의 차이

### 4단계: AI 추론

처음 30개 값으로 “평소 모습”을 준비한다. 그 뒤 새 값이 평소와 얼마나 다른지 점수를 낸다.
진동 점수 70%와 온도 점수 30%를 합친다.

기본 경로는 Device1 CPU다. Server GPU 후보는 같은 설명 가능한 기준선 계산의 점수 계산 부분을
CUDA GPU에서 실행한다.

### 5단계: 결과 저장

결과에는 측정 시각, 특징, 점수, 정상/이상 상태, 모델 버전, 실제 처리 위치가 들어간다.
서비스가 소유한 SQLite 저장소에 기록한다.

### 6단계: 대시보드 표시

대시보드는 현재 실행 중인 단계를 밝게 표시하고 다음 정보를 함께 보여준다.

- 센서가 신선한지
- 모델이 준비됐는지
- Device1과 Server GPU가 몇 건씩 처리했는지
- CPU, GPU, latency, backlog, throughput
- 설비 이상 알림
- 자원 증강 상태와 이유

## 4. “설비 이상”과 “컴퓨터가 바쁨”은 왜 다른가요?

두 상황은 완전히 다르다.

```text
센서 특징 변화 → 이상 점수 증가 → 설비 이상 알림

CPU·메모리·GPU가 바쁨
또는 처리 시간이 길어짐
또는 기다리는 작업이 쌓임
→ 자원 증강 판단
```

그래서 이상 점수는 자원 증강 판단에 사용하지 않는다.

## 5. 자원 증강은 언제 권고하나요?

자원 증강은 “Server GPU의 도움을 받을 준비를 하자”는 뜻이다. 현재는 `observed-only`라서
화면에 권고만 표시하고 자동 전환하지 않는다.

다음 문을 모두 통과해야 한다.

1. 센서가 연결돼 있고 값이 최신이다.
2. X/Y/Z/온도가 모두 있고 모양이 맞다.
3. Device1 모델이 준비됐다.
4. 자원과 서비스 지표가 최신이다.
5. CPU·메모리·GPU 중 하나의 압박이 5분 이어졌다.
6. 처리 지연, backlog, throughput 저하 중 하나가 3분 이어졌다.
7. Server GPU Pod와 endpoint가 Ready다.
8. Server GPU CUDA 모델이 Ready다.
9. Server GPU 노드에 배정 가능한 GPU 몫이 남아 있다.

모두 통과하면 `RECOMMENDED`, 즉 “증강 권고”가 된다.

## 6. 상태 이름은 무슨 뜻인가요?

```text
NORMAL → OBSERVING → RECOMMENDED → AUGMENTED → COOLDOWN → NORMAL
                    필요한 근거가 없으면 BLOCKED
```

| 상태 | 아주 쉬운 뜻 |
|---|---|
| `NORMAL` | 지금은 컴퓨터가 잘 처리하고 있다 |
| `OBSERVING` | 바쁜 것 같아서 시간을 재고 있다 |
| `RECOMMENDED` | 충분히 오래 바빴으니 GPU 도움을 권한다 |
| `AUGMENTED` | 운영자 승인으로 Server1 경로가 실제 사용 중이다 |
| `COOLDOWN` | 바로 또 바꾸지 않고 안정될 때까지 기다린다 |
| `BLOCKED` | 안전하게 판단할 정보나 준비가 부족하다 |

`BLOCKED`는 전체 서비스를 껐다는 뜻이 아니다. 증강 판단을 믿을 수 없어서 증강 경로만
막았다는 뜻이다. 화면의 첫 번째 실패 이유를 보면 무엇을 먼저 고칠지 알 수 있다.

## 7. 대시보드는 어디서 보고 무엇을 보나요?

브라우저에서 다음 주소를 연다.

```text
http://aggregator.192.168.0.56.sslip.io
```

1. 서비스 목록에서 `펌프·모터 진동·온도 이상감지`를 찾는다.
2. 센서 freshness가 `fresh`인지 본다.
3. DAG에서 밝게 표시된 현재 단계를 본다.
4. AI 추론 상자의 Device1과 Server GPU 분기를 본다.
5. Device1/Server GPU 처리 비율을 본다.
6. CPU, GPU, latency, backlog, throughput을 본다.
7. 자원 증강 카드의 상태와 실패한 gate를 본다.
8. 오른쪽 타임라인에서 이상 알림과 증강 이벤트의 시간을 본다.

| 화면 값 | 쉬운 해석 |
|---|---|
| freshness `fresh` | 새 센서 값이 계속 들어오고 있다 |
| freshness `stale` | 마지막 센서 값이 너무 오래됐다 |
| latency | 값 한 건을 처리하는 데 걸린 시간 |
| backlog | 아직 처리하지 못하고 기다리는 일의 수 |
| throughput | 1초에 처리한 일의 수 |
| CPU/Memory/GPU | 컴퓨터 자원을 얼마나 사용 중인지 |
| `N/A` 또는 관측 불가 | 값이 없으므로 정상이라고 단정할 수 없다 |

## 8. 문제가 생기면 무엇부터 확인하나요?

항상 왼쪽에서 오른쪽 순서로 확인한다.

```text
센서 → EdgeX → Device1 서비스 → Prometheus → Server GPU → 대시보드
```

1. 센서의 최신 값이 EdgeX에 있는지 본다.
2. Device Service와 AI Pod가 Ready인지 본다.
3. AI 모델이 warm-up을 끝내고 Ready인지 본다.
4. Prometheus 지표의 시각이 최신인지 본다.
5. Server GPU Pod에 HAMi GPU 할당 표시가 있는지 본다.
6. Server GPU 준비 API에 `accelerator: cuda`와 GPU 이름이 나오는지 본다.
7. 대시보드의 `BLOCKED` reason과 실패 gate를 본다.

더 자세한 명령은 [현재 데모 운영 절차](ops/현재-데모-운영-절차.md)를 따른다.

## 9. 지금 되는 것과 아직 안 되는 것

### 지금 되는 것

- 실제 센서 값을 EdgeX로 수집한다.
- 센서 freshness를 판단한다.
- Device1에서 기준선 이상감지를 실행한다.
- 결과와 알림을 저장한다.
- Server GPU에 HAMi GPU 추론 후보를 준비한다.
- 자원 증강 조건과 차단 이유를 화면에 보여준다.
- DAG와 운영 지표를 대시보드에서 본다.

### 아직 자동으로 하지 않는 것

- AI가 마음대로 Kubernetes Pod를 늘리지 않는다.
- 운영자 승인 없이 Server GPU로 요청을 보내지 않는다.
- 센서나 액추에이터에 쓰기 명령을 보내지 않는다.
- 옥동 현장 고장 종류를 완성된 정확도로 분류하지 않는다.
- 모든 장비를 자동 발견하고 등록하지 않는다.

## 10. 딱 세 문장만 기억하기

1. EdgeX는 센서의 이름과 값을 책임진다.
2. Kubernetes·KubeEdge·HAMi는 프로그램과 GPU 실행을 책임진다.
3. 대시보드는 모든 근거를 모아 보여주지만, 현재 자원 증강은 먼저 권고만 한다.
