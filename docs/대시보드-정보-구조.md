# 대시보드 정보 구조

## 물리 장비의 가상 디바이스 표현 (2026-09-08 승인)

사용자의 명시적인 구현 요청에 따라 물리 source별 읽기 전용 가상 디바이스 표현을 추가한다. `physical-vd:<인코딩된 source ID>`라는 대시보드 논리 ID를 두고 원본 장비, EdgeX 등록 기능, 기존 관측 트윈과 이용 서비스를 연결한다. 이 용어는 장비 수준의 조회 표현에 한정하며 EdgeX inventory·상태 권위나 기능별 관측 트윈의 계약을 변경하지 않는다. simulator·센서 제어·실행 컨테이너가 아니다. 원본 없는 항목에는 가상 ID를 만들지 않는다.

NEXUS의 **가상 디바이스** 탭과 `/#physical-virtual-devices`에서 선택·상세·원본 이동을 제공한다. `source-view.js`의 논리 모델과 기존 GET API를 재사용하며 별도 inventory 저장·등록·쓰기 API는 추가하지 않는다. 상세 계약과 검증 기준은 [물리 장비의 가상 디바이스](물리-가상-디바이스.md)를 따른다.


## 2026-09-08 통합 운영 대시보드 확장

이번 승인 범위는 기존 NEXUS의 서비스 중심 운영 projection, 데이터 비교,
추천·실행 이력 연결과 서버 설계 버전·시험 원장 저장이다. EdgeX 물리 권위와
Kubernetes/KubeEdge node/workload 권위를 유지한다. 설계 저장은 Configured이며
범용 배포·오프로딩을 실행하지 않는다. 현재 실제 가능/부분 구현/미구현과
API·검증·운영 책임은 [통합 운영 대시보드 고도화](통합-운영-대시보드-고도화.md)를 따른다.
로컬 수정 및 검증 상태이며 운영 image 반영은 별도다. 아래 과거 날짜의 운영 기록은
그 시각의 근거로만 읽는다.


## 2026-09-08 물리 장비 중심 탐색

사용자 확인에 따라 NEXUS 실제 관측의 `디바이스·트윈`은 **물리 장비 선택 → 등록 기능·관측 트윈 → 이용 서비스 → 별도 실행 기능 시험** 순서로 탐색한다.

- 물리 장비는 EdgeX read model의 `physical_device_id`로만 묶는다. 이름이나 실행 노드가 같아도 임의로 병합하지 않으며 미지정 항목은 별도 표시한다.
- 장비의 기능은 EdgeX 등록 Device 단위로 펼친다. `physical_device_id`와 Device 이름이 모두 일치하는 관측 트윈만 연결한다. 최근 Reading이 Profile의 전체 기능 목록이라고 설명하지 않는다.
- 기능 검색은 해당 장비를 찾되 같은 장비의 다른 기능을 숨기거나 기능·서비스 수를 줄이지 않는다. 기능별 서비스 연결은 N:M이며 장비별 서비스 요약은 service ID로 중복을 제거한다.
- 등록 상태, Reading 수신 시각·단위, 트윈 상태, 서비스 입력 상태는 각 원천의 관측을 유지한다. 조회 실패·보존 응답·일치 트윈 부재는 현재 정상이나 연결 없음으로 단정하지 않는다.
- 계산 장치인 Jetson·서버의 노드 상태는 자원·배치에서 확인한다. 수집 실행 노드를 물리 센서나 센서의 가상 복제본으로 합치지 않는다.
- `vd-demo-001`은 하단의 독립 실행 기능 시험으로 연결한다. 선택 장비나 서비스에 실제로 바인딩된 증거가 없으므로 이미 증강 중이라고 표시하지 않는다.
- 센서의 소프트웨어 표현은 현재 계약명인 EdgeX 등록 Device와 관측 트윈을 사용한다. 새 simulator, 원하는 상태 제어, 센서 데이터 생성 또는 증강 실행 API를 추가하지 않는다.

구현: `app/static/nexus/source-view.js`·`source-view.css`와 기존 `live-ui.js`의 탐색 연결. 기존 GET API를 재사용한다.

## 메뉴와 운영 흐름

| 메뉴 | 먼저 답하는 질문 | 주요 화면 |
|---|---|---|
| 운영 개요 | 무엇을 먼저 확인하고 어떤 서비스와 연결되는가? | 점검 요약, 관측 근거, source→트윈→서비스, 관측 경로 |
| 디바이스·서비스 연결 | 이 입력을 어떤 서비스들이 사용하는가? | 관측 트윈 검색·연결/상태 필터, 전체 EdgeX 등록 목록 |
| AI 서비스 | 입력·실행·결과가 각각 어떤 상태인가? | Git 서비스 목록, 기존 Runtime 조회·운영 화면, 접힌 데모 상세 |
| 노드·자원 | 실행 환경과 자원 관측에 문제가 있는가? | 서버·현장 노드, 노드 목록, 워크로드 연결, 기술 지표 |
| 장비 연결·관리 | 등록 장비와 승인 전 후보는 무엇인가? | 기존 등록 마법사·검증·관리 흐름 |
| 서비스 설계 | 입력과 stage 구성이 유효한가? | 기존 브라우저 내부 dry-run |

별도 `가상 디바이스 시험` 메뉴는 기존 독립 시험 화면으로 보존한다. 물리 inventory나
EdgeX 관측 트윈과 합치지 않는다. 기존 `#inventory`, `#device-twins` 링크는 연결 화면으로,
`#services`는 AI 서비스 화면으로 이동한다.

## 화면 목표

대시보드는 “장비가 몇 개인가”만 보여주는 화면이 아니다. 기본 운영 화면은 디바이스 입력,
AI 서비스, 노드 자원, 결과·알림을 권위 원본과 함께 추적하는 read-only 화면이다. 별도 장비
관리 화면은 승인된 Catalog와 기능 플래그 안에서 EdgeX 등록 Saga를 수행하므로 같은
read-only 범주로 설명하지 않는다.

현재 화면의 데이터 authority는 다음과 같다.

| 화면 영역 | API | 원본 |
|---|---|---|
| 센서 디바이스 | `/state/devices` | EdgeX Core Metadata + Core Data |
| 센서 이력 | `/state/devices/{id}/telemetry` | EdgeX Core Data |
| 관측 트윈·서비스 연결 | `/state/device-twins` | EdgeX Device + 최신 Event + 서비스 바인딩 |
| AI 서비스 목록 | `/state/services` | Git 서비스 계약 + 서비스 관측 |
| 노드 상태 | `/state/nodes` | Prometheus/node-exporter·Kubernetes 진단 |
| 서비스 workflow | `/state/workflows` | 수신된 workflow event의 read model |
| 서비스 자원 | `/state/service-resource-profiles` | Kubernetes/Prometheus 관측 |
| 전체 화면 | `/state/dashboard` | 위 응답의 합성 |

## 첫 화면 배치

### 1. 상단 요약

- 우선 점검 디바이스: backend 상태, 연결 상태와 Event freshness를 사용하며 새 임계값을 만들지 않는다.
- 영향 확인 서비스: 점검 대상 Device에 바인딩된 고유 service ID 수다. 실행 실패 수가 아니다.
- 물리 source: 명시적 `physical_device_id`를 중복 제거한다. source 미지정 등록은 별도 수로 안내한다.
- 현장 엣지 노드: 정상 관측 수 / 전체 수. 물리 입력의 통신 성공을 뜻하지 않는다.

API 실패·부분 오류·아직 응답 없음은 `—`로 표시한다. source 미지정 등으로 점검 Device가
트윈 projection에 없으면 서비스 연결 없음으로 추정하지 않고 영향 수를 미확인으로 둔다.

KPI의 상세 의미는 [대시보드 판단 정책](대시보드-판단-정책.md)에서 정의한다.

### 2. 센서 디바이스 목록

첫 화면은 우선 점검 항목과 다음 근거 보기를 먼저 배치한다. 옆에는 관측 출처와 실행 환경을
분리한다. 이어서 source별 대표 관측 트윈을 우선하여 최대 4개의 연결 행을 보여 준다.
전체 연결 화면에서는 N:M 바인딩을 모두 표시하며 다음 항목을 확인한다.

- 센서 디바이스 이름
- Protocol
- 연결 상태
- 최신 Event 시각
- telemetry freshness
- 연결된 AI 서비스

`근거`는 기존 디바이스 상세와 Core Data 이력을 연다. 서비스 링크는 AI 서비스 목록 및 해당
Runtime 선택으로 이동한다. source identity가 없는 등록도 전체 EdgeX 등록 목록에서 확인한다.
키보드로 상세에 진입하고 Escape로 닫으면 갱신 후에도 해당 항목으로 focus를 복귀한다.

### 3. 서비스 목록

실제 서비스 목록은 Git 계약과 서비스 API에서 가져온다. 고정 센서 데모와 옥동 후속 서비스
준비 상태는 구분하며, 대표 목표 서비스의 입력·출력은 다음과 같다.

| 서비스 | 입력 | 결과 |
|---|---|---|
| 생산품질 판별 | MES 생산 건 + 센서 window | 계약 단계: 양품/불량/unknown, confidence |
| 펌프·모터 이상감지 | 진동 3축 + 온도 | 테스트베드 기준선: anomaly score, severity, reason code |

서비스 카드에는 source binding, 모델 버전, 입력 freshness, 실행 노드, 마지막 성공/실패, 결과 저장 상태를 표시한다.

### 4. 노드·자원 진단

노드 상태는 물리 디바이스 상태와 분리한다. CPU/memory/GPU, pod 자원과 resource profile은 배치·용량 진단이다. Kubernetes Ready가 디바이스 연결 성공을 의미하지 않는다.

## 상세 화면의 공통 구조

```text
식별
  → EdgeX Device / Profile / Device Service / Protocol
입력
  → latest Event / readings / timestamp / freshness
서비스
  → binding / input window / model version / execution node
결과
  → classification 또는 anomaly / confidence / severity / alert
운영
  → last error / retry / next safe check / 관련 runbook
```

## 서비스 설계 화면에서 하지 않는 동작

- Kubernetes apply/delete/restart
- workflow 실제 실행
- Runtime candidate·Lease·traffic mutation 또는 partial offloading 실행
- actuator command(현재 범위에서 제외)

현재 workflow builder는 stage 구성·resource bind/release·validation·execution plan preview만 브라우저 상태에서 수행한다.

## 장비 관리 화면의 쓰기 경계

장비 관리 화면은 `/management` BFF와 Adapter Controller를 통해 검증된 Profile/Device 등록,
Controller 소유 Runtime과 discovery candidate Saga를 수행할 수 있다. 임의 image·hostPath·raw
manifest·command는 받지 않으며 Argo CD 소유 Runtime은 변경하지 않는다. `Idempotency-Key`와
내부 HMAC은 중복 방지와 서비스 간 무결성 수단이지 사용자 인증이 아니다. 신뢰 가능한
사용자 인증·인가를 Ingress 앞에 추가하기 전에는 테스트베드 관리 기능으로만 본다.

## API 오류 표시

EdgeX 관측 실패는 빈 목록으로 숨기지 않는다.

```json
{
  "devices": [],
  "device_observation_error": "EdgeX device observation unavailable: EdgeXBackendError"
}
```

자원 관측 실패도 센서 디바이스 장애와 분리한다. 운영자는 “장비 없음”과 “관측 backend 장애”를 구분해야 한다.

전체 요청 실패 시 이전 성공 데이터는 참고용으로 남기고 이전 관측 시각과 오류를 표시한다.
서비스 바인딩 관측이 실패하면 `미연결`로 표시하지 않는다. 관측 트윈은 운영 개요·연결 화면에서
5초 주기로 갱신하며 중복 요청은 같은 promise를 기다린다. 수동 새로고침은 트윈 응답도 기다린다.
새 화면은 기존 API를 조합하며 등록·제어·실행 API나 권한을 추가하지 않는다.

## 저장·검색 용어

물리 telemetry 최신성은 Core Data Event `origin`을 사용한다. optional InfluxDB resource-profile recording을 physical telemetry 저장소로 설명하지 않는다. InfluxDB latest 설명이 필요한 경우 `_start/_stop`은 Flux query window, `_time`은 실제 sample timestamp, 최신성은 device-level latest sample 기준이며 property별 freshness를 보장하지 않는다고 표시한다.
