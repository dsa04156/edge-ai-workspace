# 대시보드 정보 구조

## 목적

이 문서는 엣지 AI 서버, 현장 엣지 노드, 논리 자원과 EdgeX 센서 endpoint를 구분하는
운영 dashboard 정보 구조를 정의한다. 센서 디바이스는 EdgeX를 유일한 상태 권위로
사용하고, Dashboard는 Core Metadata의 등록·연결 상태와 Core Data event freshness를
함께 보여 주어 운영자가 점검 대상을 빠르게 좁히도록 돕는다.

```text
physical device -> EdgeX Device Service -> Core Data -> AI services / storage / dashboard
```

2026-07-30 live Core Metadata에는 Jetson의 기존 resource별 Device 6개, 승인 Saga로
추가된 Arduino aggregate Device 1개, Sense HAT Device 6개로 총 13개 EdgeX Device가
있다. `디바이스` 화면의 `센서 디바이스` 분류는 이 13개 identity를 한 행씩 표시하고,
`장비 관리` 화면만
`physicalDeviceId`와 승인 hardware binding을 사용해 `arduino-001`, `sensehat-001`
두 물리 장비 카드로 묶는다. 관리 카드 상세에서는 개별 Device 이름과 수정·삭제 동작을
확인할 수 있다. 별도 Discovery Agent의 onboarding 후보는 이 inventory에 합치지 않는다.
아래 payload는 Arduino 온도 Device의 API schema 예시이며 실제 판정은 live API 시각과
값을 다시 조회한다.

## 정보 구조 원칙

1. 센서 디바이스 inventory는 EdgeX Core Metadata `Device`만 사용한다.
2. 연결 상태는 Device Service, `adminState`, `operatingState`, `connection_state`로 설명한다.
3. 데이터 최신성은 EdgeX Core Data의 최신 event timestamp로 판단한다.
4. `latest_readings`는 최신 event에 포함된 reading이며, 저장 이력 그래프와 구분한다.
5. 저장 이력 그래프는 `state-aggregator` → EdgeX Core Data API → PostgreSQL 경로를 사용하고 dashboard가 DB에 직접 연결하지 않는다.
6. Kubernetes node와 workload 상태는 `엣지 AI 서버`와 `물리 디바이스` 분류의
   관측 근거다. 센서 디바이스 availability의 선행조건이나 권위는 아니다.
7. Service binding은 orchestration이 아니라 EdgeX device data가 AI 서비스, 저장소, dashboard consumer로 전달되는 관계다.
8. `디바이스 관리`는 노드를 먼저 선택해 등록 물리 연결·Runtime·protocol package·EdgeX Device를 같은 운영 범위로 좁힌다. `node_type=edge_*` 노드와 Runtime·Device·등록 binding이 실제로 참조하는 노드만 관리 카드에 표시하고, 관계없는 중앙 `cloud_server` 노드는 제외한다. 이 노드 필터는 탐색·배치 범위이며 EdgeX 상태 판정을 덮어쓰지 않는다.
9. 기본 `등록 현황`의 `연결 대기` 영역은 onboarding 후보를 다룬다. USB Serial stable identity와 allowlist I2C chip identity는 노드별 Discovery Plan에 따라 읽는다. MQTT 자기등록 subscriber와 Modbus/OPC-UA/ONVIF network scan은 구현하지 않았다. MQTT broker 연결은 자동 후보가 아니라 `장비 연결`의 검증된 network package에서 운영자가 선언한다. 후보 목록을 Core Metadata inventory에 합치지 않는다.
10. 후보 `presence`, 명시적 `state`, `authState`, Catalog `packageState`를 서로 분리한다. `pending`·`accepted`·`ignored` decision은 기존 Dashboard BFF 하위 호환 표현이다.
11. `binding-required`·`verification-required`로 차단된 후보에는 `연결 설정` 액션을
    표시한다. 이 액션은 node와 protocol 문맥을 등록 화면으로 넘기고 차단 사유를
    보여 줄 뿐, exact Git binding이 없는 장비를 승인하거나 임의 Runtime으로 배포하지 않는다.
12. 후보 승인은 exact Catalog match와 presence를 재검증한 뒤 외부 인증, 검증 Runtime, Metadata readback과 첫 Event를 순서대로 실행한다. 첫 Event 확인 전에는 등록 완료로 표시하지 않는다.
13. 노드 현황은 연결 등록, 실제 장비 관측, Device Service 통신과 Core Data 최신성을 네 상태로 분리한다. Git binding이나 발견 후보만으로 물리 장비가 통신 중이라고 추정하지 않는다.
14. 관리 화면은 노드 선택을 공통 범위로 유지한다. 기본 등록 현황에는 `등록 장비`, `디바이스 프로필`, `연결 대기`, `수집 서비스`를 순서대로 표시하고, `장비 연결`과 `기존 디바이스 수정`만 별도 화면으로 전환한다. 등록 입력은 4단계 중 현재 단계만 표시한다. 1단계에서는 protocol package, 노드, 등록 연결과 protocol별 Runtime/Device 설정을 입력한다. Runtime mode는 `auto`로 고정해 기존 service 재사용 또는 검증 template 배포를 서버가 결정한다.
15. protocol package는 `재사용 가능`, `설치 가능`, `연결 등록 필요`, `검증 필요`를 구분한다. 검증된 template과 exact 또는 제한된 network binding이 없으면 설치할 수 없고 raw path 직접 입력이나 미검증 Adapter 활성화로 이어지지 않는다. MQTT 개발 package는 broker scheme/host/CIDR/port, topic과 QoS를 서버에서 다시 검증한다.
16. Device Profile은 대시보드 BFF에서 목록 조회, mutation 없는 검증, idempotent 생성을
    제공한다. 웹에서 생성한 Profile은 등록 현황에 즉시 표시하고, 전체 Profile은 장비
    연결 단계의 선택 목록에 넣는다. 웹 생성 Profile은 읽기 전용 DeviceResource만 허용하며 command, parser,
    Device Service image와 hardware binding을 함께 만들지 않는다. 후보 capability는
    편집 초안일 뿐 value type·units의 자동 추론 근거가 아니다. 검증 protocol package가
    bundled Profile을 제공하면 연결할 때 자동으로 생성/readback하고 기존 동일 Profile은
    재사용한다.
17. 대시보드 전체에 `간편 보기`와 `전체 보기`를 따로 두지 않는다. `운영 현황`에는
    `엣지 AI 서버`, `물리 디바이스`, `가상 디바이스`, `센서 디바이스`의 수와 상태,
    현재 서버·물리 디바이스 자원 관측과 조치 항목을 먼저 표시한다. 두 패널은
    `/state/dashboard`의 node snapshot을 `node_type`으로 분리해 평균 CPU·메모리,
    GPU 관측 대수, pressure 주의 대수와 노드별 현재 meter를 만든다. 누락 metric은
    `N/A`로 표시하고 과거 시계열을 추정하지 않는다.
    고정 서비스 데모는 접힌 보조 영역으로 둔다.
    플랫폼 기술 지표와 서비스 연결 구조는 필요할 때만 펼친다.
18. `디바이스` 메뉴는 네 분류 모두 반복 카드가 아니라 이름·상태·최신 관측 또는
    Event·상세보기의 목록을 사용한다. 분류 탭으로 하나씩 숨기지 않고 네 목록을 같은
    화면에 연속 표시하며 공통 노드 필터를 적용한다. 센서 Profile, Device Service, protocol, 상태
    근거와 저장 이력, 노드 자원 관측값과 가상 자원 상태는 선택 행의 상세 패널에서
    확인한다.
19. 375px, 768px, 1024px viewport에서 문서 전체의 가로 overflow와 잘린 텍스트가 없어야
    한다. 표·캔버스처럼 내부 스크롤이 필요한 요소만 자체 scroll container를 사용한다.
20. 화면 분류의 권위는 다음과 같다.
    - `엣지 AI 서버`: `/state/nodes`에서 `node_type=cloud_server|server`
    - `물리 디바이스`: `/state/nodes`의 나머지 Jetson·Raspberry Pi 엣지 노드
    - `가상 디바이스`: `/state/virtual-resources`의 자원증강형 논리 자원
    - `센서 디바이스`: `/state/devices`의 EdgeX Core Metadata Device
21. `서비스 설계` 상단은 `/state/services`의 현재 운영 서비스와 실제 관측 상태를
    읽기 전용 목록으로 표시한다. 각 항목은 `입력 → 전처리 → AI 분석 → 결과` 4단계,
    실행 위치, 물리 소스 → Device Service 수집 경로와 입력·모델 상태를 먼저 보여 준다.
    단계명은 versioned 계약에서만 만들고 계약이 없는 서비스의 구조는 추정하지 않는다.
    지원 서비스의 `설계 편집`을 선택하면 versioned
    `design_contract`를 브라우저 편집 초안으로 복사하고 기존 일반 초안은 보존한다.
    서비스별 초안은 단계·연결·설정·이름 수정, 저장과 검증을 지원하며 주기적 상태 갱신으로
    덮어쓰지 않는다. 계약이 없는 서비스의 구조를 추정하지 않는다. 왼쪽의 `설계 블록`은 `/state/devices`와
    `/state/device-profiles`의 실제 EdgeX Device/DeviceResource를 입력으로 사용한다.
    EdgeX 입력 2종, 전처리 6종, 추론 3종, 점수 결합 1종과 결과 1종의 13개 블록을
    보여 주며 실제 입력 가능 수와
    `설계용` 계약을 구분한다. 브라우저 localStorage 초안, 단계·포트,
    타입·DAG·node 배치 validation과 dry-run 계획만 제공한다. `입력·설계 검증`은 모든
    센서 입력의 최근 5분 중앙 이력을 Device별 한 번 읽어 입력별 최신값, window 필요 표본
    충족, 수집 간격과 실제 이력 시각 정렬을 표시하고 실패하면 계획을 차단한다. 이는 로컬
    cache나 Runtime 실행 확인이 아니다. 운영 상태 판정,
    Kubernetes/EdgeX mutation과 실제 workload 실행에는 참여하지 않는다.

Telemetry freshness 시계는 EdgeX Core Data latest Event의 nanosecond `origin` sample 시각이다. API 조회 시각이나 Kubernetes 상태로 대체하지 않는다.

## 주요 API

| API | 역할 |
|---|---|
| `GET /state/dashboard` | device, node diagnostics, summary, KPI를 포함한 dashboard 전체 상태 |
| `GET /state/devices` | EdgeX 기반 센서 디바이스 상태 목록 |
| `GET /state/device-profiles` | 서비스 설계용 Device Profile/DeviceResource 읽기 전용 계약. resource protocol `attributes` 제외 |
| `GET /state/services` | 현재 운영 배포 대상으로 관리하는 서비스 목록과 상태·입력·모델·배치 노드 관측, 지원 서비스의 versioned 설계 계약. 현재 `sensor-anomaly-demo` 1개 |
| `GET /state/devices/{device_id}/telemetry?window=-30m&limit=1000` | 해당 EdgeX device의 Core Data Event/Reading history. `window`은 음수 duration, `limit`은 최대 1,000 Event |
| `GET /state/nodes` | 엣지 AI 서버와 물리 디바이스의 Kubernetes/KubeEdge 관측 |
| `GET /state/virtual-resources` | 자원증강형 가상 디바이스의 읽기 전용 상태 |
| `GET /state/summary` | 운영 상태 요약 |
| `GET /metrics` | Prometheus scrape metric |
| `GET /management/adapters` | Adapter Catalog, Device Service 상태와 전역 `mutationEnabled` 조회 |
| `GET /management/profiles` | Core Metadata의 Device Profile 이름·설명·제조사·모델·label·resource 수 조회 |
| `POST /management/profiles/validate` | 읽기 전용 DeviceResource 계약, 이름 충돌과 기존 동일 Profile 재사용 가능 여부를 mutation 없이 검증 |
| `POST /management/profiles` | 검증한 Profile을 `Idempotency-Key`로 Core Metadata에 생성하고 readback. 동일 계약은 재사용 |
| `GET /management/discovery` | 발견 node 상태와 후보 목록 조회. `q`, `node`, `protocol`, `decision`, `presence`, `includeIgnored`, `limit` 필터 지원 |
| `POST /management/discovery/manual` | idempotency key로 네트워크·수동 endpoint 후보 선언 |
| `PATCH /management/discovery/{candidateId}` | 하위 호환 BFF. `accepted`는 승인 또는 FAILED retry, `ignored`는 거절, `pending`은 허용된 초기 상태 복귀 요청 |
| `DELETE /management/discovery/{candidateId}` | 수동 후보 soft delete 또는 자동 후보 tombstone 처리. 등록 완료 후보 삭제는 차단 |
| `GET /management/adapter-runtimes` | 외부·Controller runtime owner, phase, target node, EdgeX service와 consumer 조회 |
| `POST /management/adapter-runtimes/plan` | exact node/hardware binding 기준 `REUSE`·`DEPLOY`·`BLOCKED` plan |
| `POST /management/adapter-runtimes/{name}/restart` | Controller 소유 runtime만 idempotent 재시작 |
| `DELETE /management/adapter-runtimes/{name}` | consumer 0과 exact-name 확인 뒤 Controller 소유 runtime 퇴역 |
| `POST /management/connections/validate` | runtime과 EdgeX Profile/Device 변경을 하나의 mutation-free plan으로 검증 |
| `POST /management/connections` | 승인 runtime과 EdgeX onboarding saga 실행 |
| `GET /management/connections/operations/{requestId}` | runtime, Metadata, first Event와 보상 상태 조회 |
| `POST /management/devices/validate` | Profile/Device/binding 충돌을 mutation 없이 dry-run |
| `POST /management/devices` | 활성화된 관리 경로에서 Profile/Device 생성과 readback |
| `PATCH /management/devices/{name}` | 활성화된 관리 경로에서 allowlist field만 수정 |
| `GET /management/operations/{requestId}` | Metadata 적용과 first Event 검증 상태 조회 |

## `/state/devices` 계약

각 항목은 다음 필드를 사용한다.

| API field | EdgeX 의미 |
|---|---|
| `name` | Core Metadata device 이름 |
| `source` | 물리 상태 권위. 현재 값은 `edgex` |
| `profile_name` | Core Metadata `profileName` |
| `device_service_name` | Core Metadata `serviceName` |
| `protocol_names` | Core Metadata `protocols`의 protocol 이름 목록 |
| `admin_state` | Core Metadata `adminState` |
| `operating_state` | Core Metadata `operatingState` |
| `connection_state` | `connected`, `disconnected`, `unknown`으로 정규화한 연결 상태 |
| `device_service_available` | Device Service 경로가 사용 가능한지 나타내는 값 |
| `latest_event_timestamp` | 최신 Core Data event/reading의 시각 |
| `latest_readings` | 최신 event의 reading 목록 |
| `telemetry_freshness` | `fresh`, `stale`, `no_events` |
| `node_name` | EdgeX tags/properties에서 얻은 선택적 배치 진단값 |

대표 응답 항목:

```json
{
  "name": "virtual-temperature-001",
  "source": "edgex",
  "profile_name": "etri-arduino-temperature",
  "device_service_name": "device-serial-jetson",
  "protocol_names": ["serial"],
  "admin_state": "UNLOCKED",
  "operating_state": "UP",
  "connection_state": "connected",
  "device_service_available": true,
  "latest_event_timestamp": "2026-07-21T08:00:33Z",
  "latest_readings": [
    {
      "device_name": "virtual-temperature-001",
      "source_name": "temperature",
      "resource_name": "temperature",
      "value_type": "Int32",
      "value": 283,
      "timestamp": "2026-07-21T08:00:33Z",
      "event_id": "event-id",
      "units": "raw"
    }
  ],
  "telemetry_freshness": "fresh",
  "node_name": "etri-dev0001-jetorn"
}
```

`source_name`은 Core Data event의 `sourceName`, `resource_name`은 reading의 `resourceName`이다. 예시의 식별자와 값은 계약 설명용이며 live 배포 증거가 아니다.

## Dashboard 영역

| 영역 | 표시 내용 |
|---|---|
| 운영 현황 | 전체 상태, 엣지 AI 서버·물리 디바이스·가상 디바이스·센서 디바이스 수와 가용 상태, Prometheus/Kubernetes 기반 현재 서버·물리 디바이스 자원 meter와 조치 항목. 고정 서비스 데모는 접힌 보조 영역이며 model version과 최근 발생·복귀 알림 이력을 함께 표시 |
| 디바이스 인벤토리 | 네 분류를 탭 전환 없이 한 화면의 연속 영역으로 모두 표시하며 이름, Available/Degraded/Unavailable/Unknown, 최신 관측 또는 Event 경과 시간, 상세보기를 동일한 목록 구조로 제공. 공통 노드 필터 제공 |
| 센서 상세정보 | source, profile, Device Service, protocol, admin/operating/connection 상태와 최신 reading |
| 서버·물리 디바이스 상세정보 | 분류, 호스트, CPU·메모리·GPU 사용률, pressure와 최신 관측 시각 |
| 가상 디바이스 상세정보 | 리소스 ID, 배치 노드, 유형, desired/observed/free/allocated 인스턴스, capability와 상태 근거 |
| Latest Event | Event timestamp, freshness, source/resource별 최신 reading |
| Stored History | 선택 Device의 5분·30분·1시간·24시간 Core Data history, 반환 Reading 수, 실제 첫/마지막 timestamp와 최신 1,000 Event 제한 |
| AI Result / Alert | `/state/service-demo/results`, `/state/service-demo/alerts`로 조회한 application-owned 파생 결과와 이상 발생·정상 복귀 이력. EdgeX 원시 Event 이력과 구분 |
| Device-Service Relation | EdgeX Device → Device Service → AI/storage/dashboard consumer |
| 디바이스 관리 | 공통 노드 선택 뒤 `등록 장비`를 물리 source별 카드로 먼저 표시하고 카드 안에서 개별 EdgeX Device를 펼친다. 그 뒤 `디바이스 프로필`, 연결 대기 후보와 수집 서비스를 이어서 표시한다. 보이는 신규 등록 동작은 `장비 연결` 하나이며 과거 직접 후보 등록 UI는 숨긴다. 후보의 근거·failure·binding은 `후보 상세정보`를 열어 확인하고 검색·필터·승인/무시를 수행한다. `프로필 생성` 결과는 등록 현황에 즉시 표시되고 package bundled Profile과 전체 기존 Profile은 장비 연결 3단계에서 선택한다. 장비 연결은 protocol package/노드/연결 설정 → 디바이스 정보 → 프로필 → `검증하고 연결` 순서로 진행하며 마지막 버튼이 Runtime 준비, EdgeX 등록과 first Event를 이어서 처리 |
| 서비스 설계 | 상단의 현재 실행 서비스를 입력→전처리→AI 분석→결과 4단계 흐름과 실행·수집 정보로 요약하는 읽기 전용 목록, 선택한 `sensor-anomaly-demo-v1` 원본에서 만든 10단계 편집 초안, 실제 EdgeX 센서 디바이스/DeviceResource 선택과 최근 5분 Core Data Reading 미리보기, 모든 입력의 최신값·관측/필요 표본·수집 간격·실제 이력 시각 정렬을 함께 판정하는 사전 점검, 검색 가능한 13종 설계 블록과 입력 가능 수, 전처리·추론·점수 결합·결과 preset 단계 추가·이동·삭제, 포트 연결, 속성 inspector, 타입·순환·freshness·배치 validation과 차단 사유가 보이는 dry-run 실행 계획. 일반 초안과 서비스별 초안은 브라우저에 분리 저장하며 `기존 초안으로 돌아가기`와 `원본으로 초기화`를 제공한다. 배포·실행 버튼 없음 |
| Issue / Focus | locked, service down, disconnected, stale/no event 원인 |
| Node Diagnostics | 선택적 workload placement와 자원 상태. 물리 상태 판정에는 사용하지 않음 |

## 상태 판단

| 상태 | 판단 의미 | 운영자 행동 |
|---|---|---|
| `available` | `admin_state`가 허용 상태이고 `operating_state=UP`이며 최신 Core Data event가 fresh | 정상 관찰 |
| `degraded` | Device Service는 UP이지만 event가 stale/no_events이거나 상태가 불명확 | Device Service와 event 발행 경로 점검 |
| `unavailable` | `admin_state=LOCKED` 또는 `operating_state=DOWN` | Core Metadata 정책과 Device Service 연결 점검 |

`EDGEX_EVENT_FRESH_SECONDS`가 freshness 기준을 설정한다. `latest_event_timestamp`가 기준 시간 안이면 `fresh`, 벗어나면 `stale`, event가 없으면 `no_events`다.

## KPI 구조

| KPI | 의미 |
|---|---|
| `registered_device_count` | Core Metadata 등록 device 수 |
| `available_device_count` | EdgeX 상태와 Core Data freshness 기준 available 수 |
| `degraded_device_count` | 점검이 필요한 degraded 수 |
| `unavailable_device_count` | locked/down 상태 수 |
| `edgex_connected_device_count` | 연결 상태가 connected인 수 |
| `edgex_connection_ratio` | connected / registered |
| `device_service_available_count` | Device Service available 수 |
| `device_service_availability_ratio` | Device Service available / registered |
| `core_data_event_device_count` | Core Data event가 관측된 device 수 |
| `fresh_core_data_event_device_count` | 최신 event가 fresh인 device 수 |
| `stale_core_data_event_device_count` | 최신 event가 stale인 device 수 |
| `core_data_freshness_ratio` | fresh Core Data event device / registered |
| `operator_focus_count` | degraded + unavailable device 수 |

Node KPI는 `엣지 AI 서버`와 `물리 디바이스` 분류에 별도 표시하며 센서 디바이스 KPI의
분모나 availability gate로 사용하지 않는다.

## 운영자 해석 순서

1. `source=edgex`와 `registered_device_count`로 관리 범위를 확인한다.
2. profile, Device Service, protocol이 의도한 바인딩인지 본다.
3. admin/operating/connection 상태를 확인한다.
4. `latest_event_timestamp`와 `telemetry_freshness`를 본다.
5. `latest_readings`의 source/resource/value를 확인한다.
6. Device를 선택해 저장 이력의 요청 범위, 반환 Reading 수, 실제 구간과 resource별 series를 확인한다.
7. 새 장비를 다룰 때 `디바이스 관리`에서 대상 KubeEdge 노드를 먼저 선택한다. 기본 등록 현황의 `연결 대기`에서 node report online/stale, 후보의 presence·상태·인증·Catalog match를 확인한다. USB Serial은 stable identity와 선택적 Manifest로, I2C는 Plan의 bus/address 및 read-only chip ID 규칙으로 후보를 식별한다. 네트워크 protocol은 기본 비활성화하며 임의 CIDR scan을 하지 않는다. 후보는 운영자 승인과 외부 인증, Runtime/Profile/Device 검증, 첫 Event 확인을 모두 통과해야 등록 완료가 된다.
8. 등록 현황의 물리 장비 카드를 선택해 등록 연결과 실제 장비 상태의 네 증거, Runtime,
   protocol package와 개별 EdgeX Device를 펼쳐 확인한다. `장비 연결` 1단계는
   protocol/Device Service를 먼저 고르고, 그 결과에 종속된 등록 hardware binding과
   protocol별 Runtime/Device 설정을 입력한다. target node와 binding의
   `Port`/`Bus`/`DeviceID` 값은 직접 입력하지 않는다. `auto` plan이 기존 runtime을
   재사용하는지, 검증된 빈 binding에 새 runtime을 배포하는지, 또는 차단 이유가 무엇인지
   마지막 단계에서 확인한다. `검증하고 연결`이 통합 validation을 먼저 수행하고 유효할
   때만 요청별 idempotency key로
   연결하고 runtime, Metadata readback과 first Event 상태를 구분해 본다. 기존 Device는
   펼친 개별 Device 행의 수정 동작으로 들어가 allowlist 필드만 변경한다.
9. AI 서비스, 저장소, dashboard consumer의 영향 범위를 확인한다.
10. 필요한 경우에만 Kubernetes node placement를 진단 정보로 본다.

`디바이스 관리`는 browser 관리자 token과 `Authorization` header를 사용하지 않는다.
외부/Argo runtime의 restart/retire 버튼은 비활성화하고,
Controller 소유 runtime만 관리한다. 브라우저는 raw manifest, image, hostPath 또는 Kubernetes
credential을 전달하지 않는다. Profile/Device 강제 삭제, command publish, actuator control,
EdgeMesh와 KubeEdge Device CRD 변경은 제공하지 않는다. 과거 AI Pipeline/Workflow
Builder와 전용 샘플 미리보기 API는 제거했다. 현재 메뉴는 `운영 현황`, `디바이스`,
`장비 관리`, `서비스 설계` 네 화면이다. `서비스 설계`는 EdgeX read-only 계약의
browser-local validation·dry-run이고 실제 edge consumer는 같은 노드의 Device Service
Local Data API를 직접 사용한다.
미검증 Adapter는 protocol 선택 목록과 접힌 현황 영역에서 상태를 확인할 수 있지만
비활성화된다. MQTT는 개발용 검증 package 범위에서만 활성화되고 운영 TLS/auth broker나
임의 payload를 지원한다고 표시하지 않는다. idempotency key와 기존 Device의 protocol properties JSON은 고급 영역을 열었을
때만 표시한다. 이 progressive disclosure는 표시 밀도를 줄이기 위한 UI 규칙이며 API 검증과
권한 경계를 완화하지 않는다.
현재 BFF 자체에는 운영자 인증·인가가 없으며 `Idempotency-Key`와 내부 HMAC도 사용자
인증 수단이 아니다. 따라서 이 mutation 경로는 접근이 제한된 개발 테스트베드에서만
사용하고, 운영 노출 전 Ingress 앞의 별도 인증·인가 계층을 추가한다.
웹 Profile 생성도 같은 경계를 따른다. 서버가 `edge-ai-web-managed` label을 추가하고
Core Metadata readback을 확인하지만, 이 label은 검증된 parser/image/binding의 대체
증거가 아니다.
발견 후보의 비밀번호·token·URL userinfo는 서버에서 거부한다. 발견 목록과 상태 이력은
Adapter Controller의 SQLite Registry에 영속 저장하는 onboarding staging 자료이며 Core
Metadata Device 수, availability와 physical-device KPI 분모에 넣지 않는다. 기존
`edgex-device-discovery-registry` ConfigMap이 있으면 최초 기동 때 한 번만 migration
입력으로 읽고 이후 권위 저장소로 사용하지 않는다.
Adapter가 `installed`여도 현재 endpoint/resource route를 다른 Device가 소유하면 새 등록은
`protocol_binding_exists`다. `edgeAiOnboarding*`, `nodeName`, `physicalDeviceId`는 system tag로
보고 사용자 PATCH에서 변경하지 않는다. 새 connection으로 생성한 Device의
`hardwareBindingId`도 system tag이며 같은 규칙을 적용한다.

## 현재 cutover 범위

기존 loopback Agent/SQLite/HTTPS edge 경로와 aggregate `sensehat-001` bootstrap은 퇴역했다. 두 Device Service의 10분·10,000 sample 메모리 cache는 로컬 Workflow 입력용이며 재시작하면 사라진다. dashboard는 이 로컬 cache나 과거 Core Data record로 현재 연결을 보정하지 않고, 계속 Core Metadata와 최신 Core Data Event `origin`으로 상태와 freshness를 판단한다. Serial 6개와 I2C 6개 가상 Device의 Metadata, 계약된 Reading Event와 freshness를 각각 확인하고 실제 케이블/보드 분리·복구 검증은 별도 PASS 항목으로 남긴다.
