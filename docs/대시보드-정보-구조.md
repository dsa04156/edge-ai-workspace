# 대시보드 정보 구조

## 화면 목표

대시보드는 “장비가 몇 개인가”만 보여주는 화면이 아니다. 기본 운영 화면은 디바이스 입력,
AI 서비스, 노드 자원, 결과·알림을 권위 원본과 함께 추적하는 read-only 화면이다. 별도 장비
관리 화면은 승인된 Catalog와 기능 플래그 안에서 EdgeX 등록 Saga를 수행하므로 같은
read-only 범주로 설명하지 않는다.

현재 화면의 데이터 authority는 다음과 같다.

| 화면 영역 | API | 원본 |
|---|---|---|
| 센서 디바이스 | `/state/devices` | EdgeX Core Metadata + Core Data |
| 센서 이력 | `/state/devices/{id}/telemetry` | EdgeX Core Data |
| 노드 상태 | `/state/nodes` | Prometheus/node-exporter·Kubernetes 진단 |
| 서비스 workflow | `/state/workflows` | 수신된 workflow event의 read model |
| 서비스 자원 | `/state/service-resource-profiles` | Kubernetes/Prometheus 관측 |
| 전체 화면 | `/state/dashboard` | 위 응답의 합성 |

## 첫 화면 배치

### 1. 상단 요약

- 등록 Device 수
- available/degraded/unavailable 수
- Core Data fresh event 비율
- Device Service availability 비율
- 우선 점검 대상 수
- 노드 online 비율

KPI의 상세 의미는 [대시보드 판단 정책](대시보드-판단-정책.md)에서 정의한다.

### 2. 센서 디바이스 목록

목록에는 다음만 먼저 표시한다.

- 센서 디바이스 이름
- Protocol
- 연결 상태
- 최신 Event 시각
- telemetry freshness
- 연결된 AI 서비스

카드를 과도하게 쌓지 않고, 클릭 시 Profile, Device Service, resource, latest reading, 입력 window, 서비스 결과, 장애 원인을 상세로 보여준다.

### 3. 서비스 목록

현재 2차년도 대표 서비스는 두 그룹으로 표시한다.

| 서비스 | 입력 | 결과 |
|---|---|---|
| 생산품질 판별 | MES 생산 건 + 센서 window | 계약 단계: 양품/불량/unknown, confidence |
| 펌프·모터 이상감지 | 진동 3축 + 온도 | 테스트베드 기준선: anomaly score, severity, reason code |

서비스 카드에는 source binding, 모델 버전, 입력 freshness, 실행 노드, 마지막 성공/실패, 결과 저장 상태를 표시한다.

### 4. 노드·자원 진단

노드 상태는 물리 디바이스 상태와 분리한다. CPU/memory/GPU, pod 자원과 resource profile은 배치·용량 진단이다. Kubernetes Ready가 디바이스 연결 성공을 의미하지 않는다.

## 상세 화면의 공통 구조

```text
식별
  → EdgeX Device / Profile / Device Service / Protocol
입력
  → latest Event / readings / timestamp / freshness
서비스
  → binding / input window / model version / execution node
결과
  → classification 또는 anomaly / confidence / severity / alert
운영
  → last error / retry / next safe check / 관련 runbook
```

## 서비스 설계 화면에서 하지 않는 동작

- Kubernetes apply/delete/restart
- workflow 실제 실행
- Runtime candidate·Lease·traffic mutation 또는 partial offloading 실행
- actuator command(현재 범위에서 제외)

현재 workflow builder는 stage 구성·resource bind/release·validation·execution plan preview만 브라우저 상태에서 수행한다.

## 장비 관리 화면의 쓰기 경계

장비 관리 화면은 `/management` BFF와 Adapter Controller를 통해 검증된 Profile/Device 등록,
Controller 소유 Runtime과 discovery candidate Saga를 수행할 수 있다. 임의 image·hostPath·raw
manifest·command는 받지 않으며 Argo CD 소유 Runtime은 변경하지 않는다. `Idempotency-Key`와
내부 HMAC은 중복 방지와 서비스 간 무결성 수단이지 사용자 인증이 아니다. 신뢰 가능한
사용자 인증·인가를 Ingress 앞에 추가하기 전에는 테스트베드 관리 기능으로만 본다.

## API 오류 표시

EdgeX 관측 실패는 빈 목록으로 숨기지 않는다.

```json
{
  "devices": [],
  "device_observation_error": "EdgeX device observation unavailable: EdgeXBackendError"
}
```

자원 관측 실패도 센서 디바이스 장애와 분리한다. 운영자는 “장비 없음”과 “관측 backend 장애”를 구분해야 한다.

## 저장·검색 용어

물리 telemetry 최신성은 Core Data Event `origin`을 사용한다. optional InfluxDB resource-profile recording을 physical telemetry 저장소로 설명하지 않는다. InfluxDB latest 설명이 필요한 경우 `_start/_stop`은 Flux query window, `_time`은 실제 sample timestamp, 최신성은 device-level latest sample 기준이며 property별 freshness를 보장하지 않는다고 표시한다.
