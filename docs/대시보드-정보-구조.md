# 대시보드 정보 구조

## 목적

이 문서는 EdgeX를 물리 디바이스의 유일한 상태 권위로 사용하는 운영 dashboard 정보 구조를 정의한다. Dashboard는 Core Metadata의 등록·연결 상태와 Core Data event freshness를 함께 보여 주어 운영자가 점검 대상을 빠르게 좁히도록 돕는다.

```text
physical device -> EdgeX Device Service -> Core Data -> AI services / storage / dashboard
```

2026-07-24 현재 `device-serial-jetson`과 `device-sensehat-raspi`가 physical `arduino-001`, `sensehat-001`을 각각 한 번 읽고 기능별 6개씩, 총 12개 가상 Device inventory/telemetry로 분리한다. 별도 Discovery Agent가 onboarding 후보를 수집하지만 후보를 이 inventory에 합치지 않는다. 아래 payload는 Arduino 온도 Device의 API schema 예시이며 실제 판정은 live API 시각과 값을 다시 조회한다.

## 정보 구조 원칙

1. 물리 디바이스 inventory는 EdgeX Core Metadata `Device`만 사용한다.
2. 연결 상태는 Device Service, `adminState`, `operatingState`, `connection_state`로 설명한다.
3. 데이터 최신성은 EdgeX Core Data의 최신 event timestamp로 판단한다.
4. `latest_readings`는 최신 event에 포함된 reading이며, 저장 이력 그래프와 구분한다.
5. 저장 이력 그래프는 `state-aggregator` → EdgeX Core Data API → PostgreSQL 경로를 사용하고 dashboard가 DB에 직접 연결하지 않는다.
6. Kubernetes node와 workload 상태는 선택적 배치 진단 정보다. 물리 디바이스 availability의 선행조건이나 권위가 아니다.
7. Service binding은 orchestration이 아니라 EdgeX device data가 AI 서비스, 저장소, dashboard consumer로 전달되는 관계다.
8. `디바이스 관리`는 노드를 먼저 선택해 등록 물리 연결·Runtime·protocol package·EdgeX Device를 같은 운영 범위로 좁힌다. `node_type=edge_*` 노드와 Runtime·Device·등록 binding이 실제로 참조하는 노드만 관리 카드에 표시하고, 관계없는 중앙 `cloud_server` 노드는 제외한다. 이 노드 필터는 탐색·배치 범위이며 EdgeX 상태 판정을 덮어쓰지 않는다.
9. 기본 `장비 발견` 탭은 onboarding 후보를 다룬다. USB Serial stable identity와 allowlist I2C chip identity는 노드별 Discovery Plan에 따라 읽는다. MQTT는 자기등록 규약만 허용하며 Modbus/OPC-UA/ONVIF network scan은 기본 비활성화다. 이 목록을 Core Metadata inventory에 합치지 않는다.
10. 후보 `presence`, 명시적 `state`, `authState`, Catalog `packageState`를 서로 분리한다. `pending`·`accepted`·`ignored` decision은 기존 Dashboard BFF 하위 호환 표현이다.
11. 후보 승인은 exact Catalog match와 presence를 재검증한 뒤 외부 인증, 검증 Runtime, Metadata readback과 첫 Event를 순서대로 실행한다. 첫 Event 확인 전에는 등록 완료로 표시하지 않는다.
12. 노드 현황은 연결 등록, 실제 장비 관측, Device Service 통신과 Core Data 최신성을 네 상태로 분리한다. Git binding이나 발견 후보만으로 물리 장비가 통신 중이라고 추정하지 않는다.
13. 관리 화면은 노드 선택을 공통 범위로 유지하고 `장비 발견`, `노드 현황`, `새 디바이스 등록`, `기존 디바이스 수정` 작업을 서로 다른 탭으로 분리한다. 등록 입력은 4단계 중 현재 단계만 표시한다. 1단계에서는 protocol/Device Service를 먼저 고르고 등록된 물리 연결과 Device Service 준비 방식을 뒤에서 선택한다.
14. protocol package는 `재사용 가능`, `설치 가능`, `연결 등록 필요`, `검증 필요`를 구분한다. 검증된 template과 exact binding이 없으면 설치할 수 없고 raw path 직접 입력이나 미검증 Adapter 활성화로 이어지지 않는다.

Telemetry freshness 시계는 EdgeX Core Data latest Event의 nanosecond `origin` sample 시각이다. API 조회 시각이나 Kubernetes 상태로 대체하지 않는다.

## 주요 API

| API | 역할 |
|---|---|
| `GET /state/dashboard` | device, node diagnostics, summary, KPI를 포함한 dashboard 전체 상태 |
| `GET /state/devices` | EdgeX 기반 물리 디바이스 상태 목록 |
| `GET /state/devices/{device_id}/telemetry?window=-30m&limit=1000` | 해당 EdgeX device의 Core Data Event/Reading history. `window`은 음수 duration, `limit`은 최대 1,000 Event |
| `GET /state/nodes` | 선택적 Kubernetes 배치·자원 진단 |
| `GET /state/summary` | 운영 상태 요약 |
| `GET /metrics` | Prometheus scrape metric |
| `GET /management/adapters` | Adapter Catalog, Device Service 상태와 전역 `mutationEnabled` 조회 |
| `GET /management/discovery` | 발견 node 상태와 후보 목록 조회. `q`, `node`, `protocol`, `decision`, `presence`, `includeIgnored`, `limit` 필터 지원 |
| `POST /management/discovery/manual` | idempotency key로 네트워크·수동 endpoint 후보 선언 |
| `PATCH /management/discovery/{candidateId}` | 하위 호환 BFF. `accepted`는 승인 또는 FAILED retry, `ignored`는 거절, `pending`은 허용된 초기 상태 복귀 요청 |
| `DELETE /management/discovery/{candidateId}` | 수동 후보 soft delete 또는 자동 후보 tombstone 처리. 등록 완료 후보 삭제는 차단 |
| `GET /management/adapter-runtimes` | 외부·Controller runtime owner, phase, target node, EdgeX service와 consumer 조회 |
| `POST /management/adapter-runtimes/plan` | exact node/hardware binding 기준 `REUSE`·`DEPLOY`·`BLOCKED` plan |
| `POST /management/adapter-runtimes/{name}/restart` | Controller 소유 runtime만 idempotent 재시작 |
| `DELETE /management/adapter-runtimes/{name}` | consumer 0과 exact-name 확인 뒤 Controller 소유 runtime 퇴역 |
| `POST /management/connections/validate` | runtime과 EdgeX Profile/Device 변경을 하나의 mutation-free plan으로 검증 |
| `POST /management/connections` | 승인 runtime과 EdgeX onboarding saga 실행 |
| `GET /management/connections/operations/{requestId}` | runtime, Metadata, first Event와 보상 상태 조회 |
| `POST /management/devices/validate` | Profile/Device/binding 충돌을 mutation 없이 dry-run |
| `POST /management/devices` | 활성화된 관리 경로에서 Profile/Device 생성과 readback |
| `PATCH /management/devices/{name}` | 활성화된 관리 경로에서 allowlist field만 수정 |
| `GET /management/operations/{requestId}` | Metadata 적용과 first Event 검증 상태 조회 |

## `/state/devices` 계약

각 항목은 다음 필드를 사용한다.

| API field | EdgeX 의미 |
|---|---|
| `name` | Core Metadata device 이름 |
| `source` | 물리 상태 권위. 현재 값은 `edgex` |
| `profile_name` | Core Metadata `profileName` |
| `device_service_name` | Core Metadata `serviceName` |
| `protocol_names` | Core Metadata `protocols`의 protocol 이름 목록 |
| `admin_state` | Core Metadata `adminState` |
| `operating_state` | Core Metadata `operatingState` |
| `connection_state` | `connected`, `disconnected`, `unknown`으로 정규화한 연결 상태 |
| `device_service_available` | Device Service 경로가 사용 가능한지 나타내는 값 |
| `latest_event_timestamp` | 최신 Core Data event/reading의 시각 |
| `latest_readings` | 최신 event의 reading 목록 |
| `telemetry_freshness` | `fresh`, `stale`, `no_events` |
| `node_name` | EdgeX tags/properties에서 얻은 선택적 배치 진단값 |

대표 응답 항목:

```json
{
  "name": "virtual-temperature-001",
  "source": "edgex",
  "profile_name": "etri-arduino-temperature",
  "device_service_name": "device-serial-jetson",
  "protocol_names": ["serial"],
  "admin_state": "UNLOCKED",
  "operating_state": "UP",
  "connection_state": "connected",
  "device_service_available": true,
  "latest_event_timestamp": "2026-07-21T08:00:33Z",
  "latest_readings": [
    {
      "device_name": "virtual-temperature-001",
      "source_name": "temperature",
      "resource_name": "temperature",
      "value_type": "Int32",
      "value": 283,
      "timestamp": "2026-07-21T08:00:33Z",
      "event_id": "event-id",
      "units": "raw"
    }
  ],
  "telemetry_freshness": "fresh",
  "node_name": "etri-dev0001-jetorn"
}
```

`source_name`은 Core Data event의 `sourceName`, `resource_name`은 reading의 `resourceName`이다. 예시의 식별자와 값은 계약 설명용이며 live 배포 증거가 아니다.

## Dashboard 영역

| 영역 | 표시 내용 |
|---|---|
| Overview KPI | Core Metadata 등록 수, available 수, Device Service availability, Core Data freshness |
| Device State | source, profile, Device Service, protocol, admin/operating/connection 상태 |
| Latest Event | event timestamp, freshness, source/resource별 최신 reading |
| Stored History | 선택 Device의 5분·30분·1시간·24시간 Core Data history, 반환 Reading 수, 실제 첫/마지막 timestamp와 최신 1,000 Event 제한 |
| Device-Service Relation | EdgeX Device → Device Service → AI/storage/dashboard consumer |
| 디바이스 관리 | 공통 노드 선택 카드와 `장비 발견`·`노드 현황`·`새 디바이스 등록`·`기존 디바이스 수정` 탭. 발견 탭은 후보 검색·필터·수동 endpoint 선언·승인/무시를 제공한다. 현황에는 등록 연결/장비 관측/통신/데이터 증거와 Runtime·protocol package·EdgeX Device를 표시하고, 등록은 protocol/Device Service → 등록된 물리 연결/준비 방식 → 디바이스 정보 → 프로필 → 검증 및 연결 순서로 진행 |
| Issue / Focus | locked, service down, disconnected, stale/no event 원인 |
| Node Diagnostics | 선택적 workload placement와 자원 상태. 물리 상태 판정에는 사용하지 않음 |

## 상태 판단

| 상태 | 판단 의미 | 운영자 행동 |
|---|---|---|
| `available` | `admin_state`가 허용 상태이고 `operating_state=UP`이며 최신 Core Data event가 fresh | 정상 관찰 |
| `degraded` | Device Service는 UP이지만 event가 stale/no_events이거나 상태가 불명확 | Device Service와 event 발행 경로 점검 |
| `unavailable` | `admin_state=LOCKED` 또는 `operating_state=DOWN` | Core Metadata 정책과 Device Service 연결 점검 |

`EDGEX_EVENT_FRESH_SECONDS`가 freshness 기준을 설정한다. `latest_event_timestamp`가 기준 시간 안이면 `fresh`, 벗어나면 `stale`, event가 없으면 `no_events`다.

## KPI 구조

| KPI | 의미 |
|---|---|
| `registered_device_count` | Core Metadata 등록 device 수 |
| `available_device_count` | EdgeX 상태와 Core Data freshness 기준 available 수 |
| `degraded_device_count` | 점검이 필요한 degraded 수 |
| `unavailable_device_count` | locked/down 상태 수 |
| `edgex_connected_device_count` | 연결 상태가 connected인 수 |
| `edgex_connection_ratio` | connected / registered |
| `device_service_available_count` | Device Service available 수 |
| `device_service_availability_ratio` | Device Service available / registered |
| `core_data_event_device_count` | Core Data event가 관측된 device 수 |
| `fresh_core_data_event_device_count` | 최신 event가 fresh인 device 수 |
| `stale_core_data_event_device_count` | 최신 event가 stale인 device 수 |
| `core_data_freshness_ratio` | fresh Core Data event device / registered |
| `operator_focus_count` | degraded + unavailable device 수 |

Node KPI는 인프라 진단용으로 별도 표시하며 물리 디바이스 KPI의 분모나 availability gate로 사용하지 않는다.

## 운영자 해석 순서

1. `source=edgex`와 `registered_device_count`로 관리 범위를 확인한다.
2. profile, Device Service, protocol이 의도한 바인딩인지 본다.
3. admin/operating/connection 상태를 확인한다.
4. `latest_event_timestamp`와 `telemetry_freshness`를 본다.
5. `latest_readings`의 source/resource/value를 확인한다.
6. Device를 선택해 저장 이력의 요청 범위, 반환 Reading 수, 실제 구간과 resource별 series를 확인한다.
7. 새 장비를 다룰 때 `디바이스 관리`에서 대상 KubeEdge 노드를 먼저 선택한다. 기본 `장비 발견` 탭에서 node report online/stale, 후보의 presence·상태·인증·Catalog match를 확인한다. USB Serial은 stable identity와 선택적 Manifest로, I2C는 Plan의 bus/address 및 read-only chip ID 규칙으로 후보를 식별한다. 네트워크 protocol은 기본 비활성화하며 임의 CIDR scan을 하지 않는다. 후보는 운영자 승인과 외부 인증, Runtime/Profile/Device 검증, 첫 Event 확인을 모두 통과해야 등록 완료가 된다.
8. `노드 현황`에서 `등록 연결과 실제 장비 상태`의 네 증거, Runtime, protocol package와 기존 Device를 확인한다. 등록 1단계는 protocol/Device Service를 먼저 고르고, 그 결과에 종속된 등록 hardware binding과 Device Service 준비 방식을 선택한다. target node와 binding의 `Port`/`Bus`/`DeviceID` 값은 직접 입력하지 않는다. `auto` plan이 기존 runtime을 재사용하는지, 검증된 빈 binding에 새 runtime을 배포하는지, 또는 차단 이유가 무엇인지 마지막 단계에서 확인한다. 통합 validation이 유효할 때만 요청별 idempotency key로 연결하고 runtime, Metadata readback과 first Event 상태를 구분해 본다. 기존 Device는 `기존 디바이스 수정` 탭에서 선택한 뒤 allowlist 필드만 변경한다.
9. AI 서비스, 저장소, dashboard consumer의 영향 범위를 확인한다.
10. 필요한 경우에만 Kubernetes node placement를 진단 정보로 본다.

`디바이스 관리`는 browser 관리자 token과 `Authorization` header를 사용하지 않는다.
외부/Argo runtime의 restart/retire 버튼은 비활성화하고,
Controller 소유 runtime만 관리한다. 브라우저는 raw manifest, image, hostPath 또는 Kubernetes
credential을 전달하지 않는다. Profile/Device 강제 삭제, command publish, actuator control,
EdgeMesh와 KubeEdge Device CRD 변경은 제공하지 않는다. 기존 Workflow Builder는 별도 화면과
browser-local state를 사용하며 connection operation과 결합하지 않는다.
미검증 Adapter는 protocol 선택 목록과 접힌 현황 영역에서 상태를 확인할 수 있지만
비활성화된다. idempotency key와 기존 Device의 protocol properties JSON은 고급 영역을 열었을
때만 표시한다. 이 progressive disclosure는 표시 밀도를 줄이기 위한 UI 규칙이며 API 검증과
권한 경계를 완화하지 않는다.
현재 BFF 자체에는 운영자 인증·인가가 없으며 `Idempotency-Key`와 내부 HMAC도 사용자
인증 수단이 아니다. 따라서 이 mutation 경로는 접근이 제한된 개발 테스트베드에서만
사용하고, 운영 노출 전 Ingress 앞의 별도 인증·인가 계층을 추가한다.
발견 후보의 비밀번호·token·URL userinfo는 서버에서 거부한다. 발견 목록과 상태 이력은
Adapter Controller의 SQLite Registry에 영속 저장하는 onboarding staging 자료이며 Core
Metadata Device 수, availability와 physical-device KPI 분모에 넣지 않는다. 기존
`edgex-device-discovery-registry` ConfigMap이 있으면 최초 기동 때 한 번만 migration
입력으로 읽고 이후 권위 저장소로 사용하지 않는다.
Adapter가 `installed`여도 현재 endpoint/resource route를 다른 Device가 소유하면 새 등록은
`protocol_binding_exists`다. `edgeAiOnboarding*`, `nodeName`, `physicalDeviceId`는 system tag로
보고 사용자 PATCH에서 변경하지 않는다. 새 connection으로 생성한 Device의
`hardwareBindingId`도 system tag이며 같은 규칙을 적용한다.

## 현재 cutover 범위

기존 loopback Agent/SQLite/HTTPS edge 경로와 aggregate `sensehat-001` bootstrap은 퇴역했다. 두 Device Service의 10분·10,000 sample 메모리 cache는 로컬 Workflow 입력용이며 재시작하면 사라진다. dashboard는 이 로컬 cache나 과거 Core Data record로 현재 연결을 보정하지 않고, 계속 Core Metadata와 최신 Core Data Event `origin`으로 상태와 freshness를 판단한다. Serial 6개와 I2C 6개 가상 Device의 Metadata, 계약된 Reading Event와 freshness를 각각 확인하고 실제 케이블/보드 분리·복구 검증은 별도 PASS 항목으로 남긴다.
