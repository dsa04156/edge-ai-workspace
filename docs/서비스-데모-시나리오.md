# 서비스 데모 시나리오

## 목적

이 문서는 EdgeX 기반 물리 디바이스 cutover를 과장 없이 시연하는 절차를 정의한다. 현재 서비스 데모의 물리 범위는 MQTT canary `vib-arduino-acceleration-01`과 EdgeX-backed state-aggregator/dashboard다.

```text
physical vibration device
  -> EdgeX MQTT Device Service
  -> EdgeX MessageBus / Core Data
  -> AI services / storage / dashboard
```

## 대표 시나리오

대표 시나리오는 “MQTT 진동 canary의 EdgeX 등록·연결·event freshness·최신 reading과 서비스 consumer 연결을 한 화면에서 확인한다”이다.

이 시나리오가 증명하는 것은 다음과 같다.

- Core Metadata device가 물리 inventory와 상태의 권위다.
- Device Service가 profile과 MQTT protocol로 canary를 소유한다.
- Core Data 최신 event가 freshness와 reading의 권위다.
- AI 서비스, 저장소, dashboard가 EdgeX 경로의 consumer다.
- 운영자는 상태와 데이터 문제를 한 경로에서 좁힐 수 있다.

Live 설치·현장 배포 완료는 별도 실행 증거로만 주장한다. 이 문서와 예시 값은 배포 증거가 아니다.

## 구성 요소

| 구성 요소 | 역할 |
|---|---|
| `vib-arduino-acceleration-01` | 현재 MQTT physical canary |
| EdgeX Core Metadata | device, profile, Device Service, protocol, admin/operating state 제공 |
| EdgeX MQTT Device Service | canary 수집과 event 발행 |
| EdgeX MessageBus / Core Data | event 전달, 최신 event와 history 제공 |
| `edge-orch/state-aggregator/` | EdgeX 응답 정규화와 `/state/devices` 제공 |
| dashboard | 상태, freshness, reading, consumer 관계 가시화 |
| AI service / storage | EdgeX event consumer |
| Kubernetes node diagnostics | 선택적 workload placement·자원 진단 |
| workflow designer | 실제 변경 없는 service-stage/node dry-run preview |

## 데모 진행 순서

### 1. Core Metadata identity 확인

`/state/devices`에서 canary를 찾고 다음을 확인한다.

```text
name = vib-arduino-acceleration-01
source = edgex
profile_name is present
device_service_name is present
protocol_names includes mqtt
admin_state is present
operating_state is present
```

이 단계의 inventory 기준은 EdgeX Core Metadata다.

### 2. Device Service 연결 상태 확인

다음을 함께 본다.

- `admin_state`
- `operating_state`
- `connection_state`
- `device_service_available`

`admin_state=LOCKED` 또는 `operating_state=DOWN`이면 unavailable이다. 상태가 UP이어도 event가 없거나 오래되면 데이터 경로는 degraded로 남는다.

### 3. Core Data event freshness 확인

다음을 확인한다.

- `latest_event_timestamp`
- `telemetry_freshness`: `fresh`, `stale`, `no_events`
- `latest_readings[].source_name`
- `latest_readings[].resource_name`
- `latest_readings[].value_type`, `value`, `units`, `timestamp`

Freshness 기준은 `EDGEX_EVENT_FRESH_SECONDS`다. 최신 event가 fresh하다는 사실은 그 event에 포함되지 않은 모든 resource도 fresh하다는 뜻이 아니다.

### 4. Consumer 관계 확인

Dashboard relation에서 다음 경로를 확인한다.

```text
vib-arduino-acceleration-01
  -> EdgeX MQTT Device Service
  -> Core Data source/readings
  -> vibration AI / storage / dashboard
```

Consumer 연결은 service binding이며 자동 workflow 실행이나 재배치를 뜻하지 않는다.

### 5. Dashboard와 KPI 확인

- `registered_device_count`
- `available_device_count`
- `degraded_device_count`
- `unavailable_device_count`
- `edgex_connected_device_count`, `edgex_connection_ratio`
- `device_service_available_count`, `device_service_availability_ratio`
- `core_data_event_device_count`
- `fresh_core_data_event_device_count`
- `stale_core_data_event_device_count`
- `core_data_freshness_ratio`
- `operator_focus_count`

### 6. 선택적 node diagnostics 확인

AI 또는 dashboard workload의 placement와 자원 상태가 필요할 때만 node 정보를 연다. Node 상태는 물리 canary의 등록·연결·freshness 판정을 대신하지 않으며 physical availability gate가 아니다.

### 7. Dry-run 구조 설명

Workflow designer에서는 device source와 AI/storage/dashboard stage의 target node를 preview할 수 있다. 이 동작은 dry-run이며 Kubernetes workload, EdgeX metadata, device command를 생성·수정하지 않는다.

## 정상·저하 상태 예시

| 상태 | 표시 | 해석 |
|---|---|---|
| UP + connected + fresh event | `available` | Device Service와 Core Data 경로가 관측됨 |
| UP + stale event | `degraded` | 수집 서비스는 UP이나 event 발행 또는 장치 입력 점검 필요 |
| UP + no event | `degraded` | profile resource와 Core Data event 경로 점검 필요 |
| LOCKED | `unavailable` | Core Metadata admin 정책 점검 |
| DOWN/disconnected | `unavailable` | Device Service와 physical connection 점검 |
| node diagnostic unavailable | 별도 diagnostic | 물리 device 상태를 자동으로 낮추지 않음 |

## Protocol 범위

| protocol | 현재 데모 지위 |
|---|---|
| MQTT | canary `vib-arduino-acceleration-01`만 현재 전달 범위 |
| Serial | 미구현 future migration wave |
| Modbus | 미구현 future migration wave |
| OPC-UA | 미구현 future migration wave |
| RTSP | 미구현 future migration wave |

Future wave는 protocol별 Device Service/profile, 실제 장치, event contract, freshness 및 consumer 검증을 각각 통과해야 한다. MQTT canary 결과로 다른 protocol이 구현되었다고 주장하지 않는다.

## 생산성 향상 효과 설명

1. 운영자가 물리 inventory, Device Service 연결, 최신 event를 서로 다른 시스템에서 수작업으로 대조하는 시간을 줄인다.
2. profile, protocol, admin/operating/connection, freshness를 한 화면에서 확인해 원인 후보를 좁힌다.
3. source/resource별 latest reading으로 AI와 저장소의 입력 영향 범위를 빠르게 설명한다.
4. focus list로 점검 순서를 정하되 agent나 dashboard가 직접 변경을 실행하지 않는다.
5. 선택적 node diagnostics를 physical 상태와 분리해 잘못된 장애 판정을 줄인다.

## 성공 기준

- `/state/devices`에 canary가 `source=edgex`로 나타난다.
- profile, Device Service, MQTT protocol, admin/operating/connection 필드가 계약과 일치한다.
- Core Data event timestamp, freshness, latest readings가 표시된다.
- AI/storage/dashboard consumer 관계가 EdgeX 경로로 설명된다.
- node placement는 diagnostics로만 표시된다.
- Serial, Modbus, OPC-UA, RTSP가 현재 구현으로 표시되지 않는다.
- 모든 설계·운영 보조 기능은 read-only 또는 dry-run이며 실제 리소스를 변경하지 않는다.
