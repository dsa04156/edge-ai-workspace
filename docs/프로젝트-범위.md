# 프로젝트 범위

## 목적

이 문서는 현재 PoC에서 무엇을 구현 범위로 볼지, 무엇을 현재 연구 방향에서 제외할지 정리한다.
레포 안에는 현재 구현물, 과거 실험, 운영 도구, 연구 문서가 함께 있으므로 새 작업 판단은 이 문서를 기준으로 한다.


## 범위 분류 용어

이 문서와 `docs/저장소-구조.md`에서 쓰는 분류는 다음 의미로 고정한다.

| 분류 | 의미 | 처리 규칙 |
|---|---|---|
| Current | 현재 서비스 데모, 디바이스-서비스 연결 구조, 통합 운영 가시화에 직접 연결되는 구현 경로 | 새 기능/수정의 기본 대상 |
| Second-year Design Track | 옥동 PLC·MES·센서 기반 AI 서비스 2종과 데이터 통합, 워크플로우, 엣지·서버 분산, 장애복구, 가상디바이스 프로토타입 경로 | 현재 기능으로 주장하지 않고 월별 구현·검증 범위를 명시 |
| Current-supporting | 설치, 배포, 운영, ingress, registry, GPU runtime처럼 현재 경로를 지원하는 자료 | 현재 경로와 연결될 때만 수정 |
| Legacy / Reference | 과거 workflow, placement, offloading, agent-planning 실험 또는 참조 구현 | 히스토리와 비교 근거로만 읽고 현재 요구사항으로 해석하지 않음 |
| Archive | 과거 통합 기록, 연구 초안, 논문/실험 자료 | 현재 판단 기준이 아니며 필요할 때만 인용 |
| Cleanup Review | 캐시, runner 산출물, 대형 바이너리, 운영 중 생성 데이터처럼 보존 여부 검토가 필요한 자료 | 삭제/이동 전 별도 승인 필요 |

`Legacy / Reference`와 `Archive` 자료는 현재 PoC 구현 방향을 바꾸는 근거가 아니다. 해당 자료를 현재 범위로 승격하려면 먼저 이 문서와 `docs/저장소-구조.md`에 승격 이유, 현재 경로와의 연결, 검증 기준을 명시한다.

## 현재 PoC 범위

현재 범위는 혼합 디바이스 엣지 AI 플랫폼을 실공장 기반 서비스 데모 관점에서 설명 가능하게 만들고, 물리 endpoint를 정식 EdgeX Device Service/Profile/Device로 연결해 중앙 EdgeX와 대시보드에서 같은 identity로 관리하는 것이다.

권위 있는 현재 아키텍처:

```text
물리 센서 / PLC / 장비
  -> Jetson 또는 Raspberry Pi의 EdgeX Device Service
  +-> EdgeX Event / Reading -> 중앙 Core Data -> PostgreSQL
  +-> bounded Local Data API -> 같은 node의 고정 AI consumer
      -> state-aggregator / dashboard
```

포함하는 방향:

- Jetson과 Raspberry Pi에서 실제 protocol endpoint를 소유하는 EdgeX Device Service
- Device SDK 기반 protocol 연결, 재연결, resource 표준화, 상태와 지원 command
- `etri-ser0002-cgnmsb`에 한 세트만 배치하는 ingest gateway, EdgeX Core Keeper, Core Metadata, Core Command, 내부 MessageBus, Core Data, PostgreSQL
- EdgeX Core Metadata Device/Profile 기반 inventory·schema·관리 상태
- Core Data Event/Reading 기반 typed telemetry와 freshness
- 합성 identity를 사용하는 Core Data REST → PostgreSQL 1,000-device 저장 기준선 도구와 운영 절차. 운영 Metadata/Device와 root render에는 포함하지 않음
- 선택한 Device의 Core Data history를 `state-aggregator` API로 조회하고 요청 범위·반환 Reading 수·실제 구간을 구분해 표시하는 dashboard
- 같은 edge node의 Workflow Pod가 사용하는 bounded memory recent cache와 read-only Local Data API; 현재 Flannel에서는 client label 기반 NetworkPolicy가 강제되지 않음
- Jetson에서 Arduino 가속도 X/Y/Z와 온도를 실시간에 가까운 주기로 읽어 시간 정렬하고 진동·온도 개별 점수와 종합 점수를 계산하는 고정 `sensor-anomaly-demo` 소스 구현. versioned 입력 계약, 개발용 Replay, model adapter와 application-owned SQLite 결과·알림 저장 포함
- Jetson, Raspberry Pi, x86 서버가 함께 있는 mixed-device 환경
- Prometheus/Kubernetes 기반 node/workload 상태 수집
- 디바이스와 AI 서비스·storage·dashboard의 연결 구조
- 서비스 데모 시나리오와 생산성 향상 효과 설명

대시보드의 `디바이스` 메뉴는 운영 객체를 네 분류로 표시한다. `엣지 AI 서버`와
`물리 디바이스`는 `/state/nodes`를 `node_type`으로 나눈 중앙 서버와 Jetson·Raspberry Pi
엣지 노드다. `가상 디바이스`는 `/state/virtual-resources`의 자원증강형 논리 자원이고,
`센서 디바이스`는 `/state/devices`의 EdgeX Core Metadata Device다. 이 화면 분류는
EdgeX 센서 상태 권위나 KubeEdge workload 관리 경계를 바꾸지 않으며 가상 자원 표시를
동적 Workflow 실행 기능으로 승격하지 않는다.

`운영 현황`은 네 분류의 수와 가용 상태 다음에 중앙 서버와 물리 디바이스 노드 관측을
우선한다. Prometheus/Kubernetes 기반 node snapshot을 두 분류로 나눠 평균 CPU·메모리,
GPU 관측 대수, pressure 주의 대수와 노드별 현재 meter를 표시하고, 누락 metric은
`N/A`로 둔다. 대시보드용 시계열 contract나 Grafana embed는 현재 범위가 아니다.
고정 `sensor-anomaly-demo` 결과는 접힌 보조 영역에서 확인한다.

KubeEdge 범위는 Kubernetes edge node와 workload 관리로 제한한다. EdgeX Metadata의 Device/Device Profile은 KubeEdge `Device`/`DeviceModel` CRD와 서로 다른 관리 객체다. KubeEdge DeviceStatus, MapperFramework, `mqttvirtual`과 mapper direct-write는 legacy physical integration이며 현재 plane의 병행 경로나 fallback이 아니다.

2026-07-21에 `edgex-edge-agent-jetson`, `edgex-edge-agent-sensehat`, 두 outbox PVC와 Agent 전용 Metadata bootstrap을 퇴역했다. 대신 root render는 `edgex-edge`에 공식 EdgeX Device SDK 기반 `device-serial-jetson`, `device-sensehat-raspi`와 각 최소 NetworkPolicy를 배포한다. 중앙 EdgeX와 ingest gateway는 유지하지만, ingest gateway는 현재 Serial/I2C Event 경로에 참여하지 않는다.

1차 수직 슬라이스는 `etri-dev0001-jetorn`의 Arduino Uno다. `/dev/serial/by-id/...` CharDevice를 Pod의 `/dev/arduino-001`에 단독 마운트하고 `device-serial-jetson`이 공유 reader 1개로 읽는다. temperature, light, magnetic, acceleration X/Y/Z는 각각 1-resource Profile과 `virtual-*-001` Device로 등록되며 Core Data Event, Core Command GET과 dashboard의 독립 identity가 된다. Device Service 메모리는 Device/resource별 최근 10분·최대 10,000 sample을 보존하고 latest/recent Local Data API를 제공한다. 이 cache는 Pod 재시작 시 사라지며 durable outbox나 offline replay가 아니다.

두 번째 수직 슬라이스는 `etri-dev0003-raspi5`의 Sense HAT v1이다. `device-sensehat-raspi`가 exact `/dev/i2c-1` CharDevice를 직접 소유하고 RTIMULib reader를 내부 protocol module로 실행한다. temperature, humidity, pressure, compass, orientation, gyroscope는 Profile/Device 6개로 등록되고 총 11개 `Float64` resource를 제공한다. physical `sensehat-001`은 protocol/tag source ID이며 aggregate EdgeX Device가 아니다. 동일한 10분·10,000 sample recent cache, Local Data API와 read-only command 계약을 사용한다.

현재 root render에는 고정 `device-mqtt`와 edge-local broker가 없다. 대신 공식
`device-mqtt:4.0.2` immutable image, 노드별 network binding, 허용 broker 주소와 topic/QoS
설정, 읽기 전용 온도 Profile을 묶은 개발용 managed template가 있다. 대시보드 연결 실행 시
기존 Runtime이 없으면 Controller가 이 template를 대상 노드에 동적으로 배포한다.
broker/publisher simulator는 root 밖의
`edgex/k8s/overlays/development/mqtt-simulator` 선택적 fixture다. 이는 웹 등록 경로와
Core Data first Event를 검증하기 위한 개발 계약이며 운영 TLS/인증 broker나 임의 MQTT
payload 지원 완료를 뜻하지 않는다. Serial과 Sense HAT I2C 정상 경로는 live 지원 증거가 있다. Modbus는 root render 밖의 개발 simulator overlay, digest 고정 공식 `device-modbus:4.0.2`, read-only Profile과 Git에 등록한 Unit 1·2 exact binding에 한해 수동 endpoint 승인부터 Core Data 첫 Event까지 과거 live 검증했다. 검증용 Controller Runtime은 현재 퇴역했으며 이 증거는 개발 fixture의 수직 경로만 확인하고 자동 discovery나 실제 PLC 지원을 뜻하지 않는다. OPC-UA도 profile·실장비·telemetry 검증 전까지 완료로 주장하지 않는다. RTSP frame은 Workflow Pod가 직접 구독하는 별도 media 경로다.

첫 서비스 데모 consumer는 `edge-orch/sensor-anomaly-demo/`다. 2026-08-03 소스 구현은 `etri-dev0001-jetorn`에서 `device-serial-jetson.edgex-edge.svc.cluster.local:59910`의 Local Data API를 500ms마다 조회한다. `virtual-acceleration-{x,y,z}-001`의 같은 nanosecond `origin`을 먼저 한 frame으로 결합하고, 별도 Serial 메시지인 `virtual-temperature-001`은 2초 이내의 가장 가까운 sample만 연결한다. 보간하거나 누락값을 만들지 않으며 시간 범위 안의 온도가 없으면 해당 frame의 종합 점수를 계산하지 않는다.

가속도 최근 20개에서는 RMS·Peak·Kurtosis, 온도 최근 10개에서는 평균·표준편차·변화량을 만든다. 두 feature branch는 각각 30개 warm-up의 online Gaussian baseline 점수를 계산하고 기본 가중치 `진동 0.7 + 온도 0.3`으로 종합한다. 종합 점수가 두 번 연속 threshold 이상이면 anomaly, 세 번 연속 정상 범위면 clear한다. 이는 학습된 고장 분류기나 push stream이 아니다. 2026-08-03에는 ARM64 image `sensor-anomaly-demo@sha256:1a86c54a1a0692a682258b4a9c8a6f7a24e13f98000610afa56c04f95d52af68`을 Jetson에 배포해 Ready/restart 0을 확인했다. 기동 직후 temperature 605개와 acceleration frame 605개를 정렬해 누락 0이었고, 이어진 두 status 조회에서 frame `621 → 623`, origin `1785734602955557669 → 1785734604991104923`, 온도 정렬 차이 약 11~12ms를 확인했다. 중앙 BFF와 외부 dashboard도 같은 개별·종합 점수를 반환했다. 실제 장치를 움직여 anomaly를 유발하는 현장 시연은 여전히 별도 gate다.

2026-08-03 후속 소스는 `okdong.pump-motor.telemetry/v1`과
`okdong.production-quality.telemetry/v1` schema, Float64 Local Data 호환 Replay server,
명시적 `online-baseline` model adapter, idempotent SQLite 결과와 발생·복귀 alert transition을
추가했다. 운영 manifest는 Jetson `local-path` 1Gi RWO PVC를 사용한다. 이 DB는 EdgeX 원시
Event/PostgreSQL과 분리된 AI 파생 결과이며 중앙 HA 저장소나 원시 telemetry outbox가 아니다.
생산품질 계약은 field map schema만 있고 현장 mapping·판별 서비스는 아직 없다.

`state-aggregator`의 `/state/service-demo`와 대시보드는 이 derived 결과와 physical source → Device Service → EdgeX Device 4개 → AI consumer binding을 read-only로 표시한다. 구형 3축 응답도 선택 field 없이 계속 읽을 수 있고, 새 응답에서는 진동·온도 개별 점수, 종합 점수, 온도 정렬 차이를 추가로 표시한다. Device 선택 시 `/state/devices/{device_id}/telemetry`가 Core Data history를 조회하며 dashboard가 PostgreSQL에 직접 연결하지 않는다. UI는 5분·30분·1시간·24시간 범위와 새로고침을 제공하고 최신 1,000 Event 제한, 반환 Reading 수와 실제 구간을 분리해 보여 준다. EdgeX Core Metadata/Core Data의 raw inventory·telemetry 권위는 바뀌지 않는다. 이 고정 Deployment를 동적 Workflow Builder, runtime migration 또는 offloading 완성으로 설명하지 않는다.

2026-07-31에는 제거된 과거 AI Pipeline과 분리된 `서비스 설계` 캔버스를
2차년도 설계 트랙 프로토타입으로 대시보드에 추가했다. 이 화면은
`/state/dashboard`의 EdgeX Device와 `/state/device-profiles`의 안전한 DeviceResource
계약을 센서 입력으로 사용하고, 브라우저 안에서 단계 추가·이동·연결, 속성 편집,
검색 가능한 13종 서비스 카탈로그, 타입·배치 validation과 dry-run 실행 계획 미리보기만
수행한다. EdgeX 입력은 실제 선택 가능한 Device 수를 표시하고 나머지는 `설계용`으로
구분한다. 초안은 브라우저
`localStorage`에만 저장한다. Kubernetes/EdgeX mutation, command, workload 실행,
migration과 offloading은 없다.

### 노드 장비 발견과 등록 후보 관리

일반 `edge-device-discovery`와 I2C 전용 `edge-device-discovery-i2c` DaemonSet은 지정
edge node에서 중앙의 보수적인 Discovery Plan을 30초마다 읽는다. Serial은 stable
`/dev/serial/by-id/*`, 승인 VID/PID와 USB serial을
관측하고, Plan에서 명시했을 때만 WHOAMI Manifest를 probe한다. I2C는 허용 bus/address와
읽기 전용 identity register rule이 모두 있을 때만 센서 후보를 만든다. Sense HAT처럼
여러 chip으로 구성된 보드는 모든 identity가 일치할 때 하나의 composite 후보를 만든다.
`/dev/i2c-N` 버스 파일 자체는 신규 후보가 아니다. 네트워크 대역 scan은 기본 비활성이고 현재
Modbus/OPC-UA/ONVIF scanner와 MQTT subscriber는 구현되지 않았다.

일반 Agent는 dev0001/dev0002/dev0003에서 `serial` scope로 동작하고, dev0003의 I2C 전용
Agent는 `i2c` scope로 동작한다. report의 `scannedProtocols` 범위 안에서만 사라진 후보를
`STALE` 처리하므로 같은 node의 두 Agent가 서로의 후보 상태를 덮어쓰지 않는다. 2026-07-28
dev0003에서 CH340 USB Serial `1a86:7523`을 passive 후보로 live 관측했다. 이 장비를
MPU6050 6축 IMU로 연결하기 위한 exact Raspberry Pi hardware binding,
`mpu6050-imu-v1` Profile/parser와 Controller 배포 template은 구현했다. 배포 뒤 exact
match 후보 승인과 동적 Runtime 배포까지 실행했지만 Serial telemetry가 없어 첫 Event
timeout으로 rollback됐다. 보드는 `ESP32-D0WD-V3 revision 3.1`로 식별했고 운영 firmware
compile·flash와 115200 baud 상태 JSON까지 확인했다. 다만 MPU6050 주소 `0x68`, `0x69`가
I2C ACK하지 않아 6축 JSON과 Core Data Event는 없었다. 2026-07-30 MPU6050 실물을
분리했고 후보는 `STALE`/`ignored` 감사 이력으로 보존되어 기본 운영 목록에서 숨겨지며
활성 동적 Runtime은 없다. Catalog/Profile/parser는 dormant 지원 코드이며 이 장비를 다시
범위에 넣고 후보를 재승인해 신규 Core Data Event를 확인하기 전까지 Device Service 통신
완료 근거로 사용하지 않는다.

```text
edge node의 Plan 제한 관측
  -> HMAC 서명 report
  -> edgex-adapter-controller
  -> PVC SQLite candidate / state / Plan / Saga / audit
  -> state-aggregator /management/discovery
  -> exact Device Catalog match
  -> 운영자 승인 + 외부 인증
  -> 검증 Runtime 재사용/배포와 실제 image digest readback
  -> EdgeX Profile/Device idempotent 등록과 Metadata readback
  -> Core Data first Event
  -> EVENT_CONFIRMED
```

발견 후보는 onboarding 전 staging 정보다. clean node reconciliation에서 사라지면 즉시
`STALE`이 되고 같은 stable identity가 재연결되면 같은 candidate ID와 이전 상태를 복구한다.
어느 candidate 상태도 Core Metadata Device, Device Service 통신 또는 EdgeX
`operatingState`를 대신하지 않는다. 등록 완료는 `EVENT_CONFIRMED`만 의미한다.

- stable identity, Profile, parser와 immutable image가 Device Catalog에서 exact
  match된 후보만 `PENDING_APPROVAL`과 `registration-ready`가 된다. 현재 Modbus는
  Git Catalog의 고정 simulator host/port/unit ID를 수동 선언한 경우에만 이 경로가 열린다.
- ambiguous, Manifest 실패, 미지원 protocol과 Catalog 불일치는 `BLOCKED`다.
- 외부 인증은 fail-closed다. 개발 testbed만 명시적 `AllowAllMockProvider`를 사용한다.
- 승인 후 Runtime, Metadata, first Event 단계는 재시작 가능한 idempotent Saga다.
- 실패 rollback은 이번 Saga가 만든 리소스만 대상으로 하고 기존 Argo Runtime이나 공유
  Profile을 삭제하지 않는다.
- 비밀번호, token, secret 성격의 property와 자격 증명이 포함된 URL은 후보에 저장하지 않는다.
- 후보, 상태 이력, 승인, Plan, Saga와 audit는 1Gi RWO PVC의 SQLite에 저장한다. 기존
  namespaced 후보 ConfigMap은 최초 기동 때 한 번 import한다.
- 일반 발견 Agent의 read-only `/dev`, `/sys` mount는 세 edge node에서 서명된 Serial
  Discovery Plan 범위의
  관측 전용이다. dev0003 I2C 전용 Agent는 container device cgroup 제약 때문에
  privileged 예외를 사용하지만 exact `/dev/i2c-1`, non-root 실행과 host i2c group으로
  범위를 제한한다. 대시보드가 임의 hostPath, image, command 또는 privileged workload를
  제출하는 경로는 없다.
- Arduino 신규 경로는 물리 보드 하나를 여러 DeviceResource를 가진 EdgeX Device 하나로
  등록한다. 기존 센서별 6개 Device는 서비스 데모 하위 호환을 위해 전환 기간 fan-out한다.

### 대시보드 노드별 Adapter Runtime과 Device 연결 관리

`state-aggregator`의 `디바이스 관리` 화면은 운영자가 KubeEdge 노드를 먼저 선택하고, 그
노드의 Adapter Runtime과 EdgeX Device 연결을 한 흐름으로 관리하는 Current 경로다.
`GET /state/nodes`, Runtime `targetNode`, Device `node_name`/`tags.nodeName`과 등록 hardware
binding을 하나의 노드 범위로 합성하되, 이 합성은 배치·운영 탐색용이다. 브라우저는
Kubernetes API에 직접 접근하지 않으며, `state-aggregator`가 내부 HMAC으로 별도
`edgex-adapter-controller`를 호출한다. Controller는 Git에서 검증·등록한 template와 hardware
binding만 `edgex-edge` namespace에 reconcile한다. Profile, Device와 Device Service
binding의 권위는 Core Metadata, 첫 Event와 Reading의 권위는 Core Data에 그대로 남는다.

- Runtime inventory, 재사용·배포 plan과 통합 connection validation은 mutation 없는 조회다.
- `POST /management/connections`, runtime restart/retire와 기존 Device allowlist `PATCH`는
  요청별 `Idempotency-Key`를 요구한다. 후보 승인·거절·재시도와 수동 후보 추가·삭제도
  같은 규칙을 사용하며 브라우저용 `Authorization` header나 관리자 token은 없다.
- 현재 운영 manifest는 `DEVICE_MANAGEMENT_ENABLED=true`,
  `ADAPTER_RUNTIME_MANAGEMENT_ENABLED=true`, `ADAPTER_RUNTIME_MUTATION_ENABLED=true`로
  관리 경로를 활성화한다. `management-hmac-key`와 namespace 사이에 공유하는
  `internal-hmac-key`가 `edgex-adapter-management-auth` Secret에 없으면 Pod가 시작하지
  않는다.
- state-aggregator와 Adapter Controller 사이의 내부 HMAC, 후보 등록 Saga의 외부
  AuthProvider는 유지한다. 전자는 서비스 요청 무결성, 후자는 장비 신뢰 검증이며 둘 다
  대시보드 운영자 인증을 대신하지 않는다. 현재 무인증 관리 BFF는 접근이 제한된 개발
  테스트베드 경계이며 운영 노출 전 별도 사용자 인증·인가가 필요하다.
- 기존 `device-serial-jetson`과 `device-sensehat-raspi`는 Argo CD 소유 external runtime이다.
  dev0003 MPU6050 Serial은 지원 코드를 유지하지만 2026-07-30 실물 분리 뒤
  `STALE`/`ignored` 감사 이력으로 정리했고 활성 Runtime이 없다. 다시 승인하는 경우에만
  Controller가 exact host CharDevice와 검증 template으로 별도 Runtime을 생성하며 root
  static render의 기존 두 Runtime을 대체하지 않는다.
  대시보드는 상태·consumer와 runtime이 소유한 등록 hardware binding 목록을 조회한다. 요청한
  binding이 목록에 있으면 같은 protocol runtime을 재사용하지만 재시작하거나 퇴역하지 않는다.
- Controller가 만든 `AdapterRuntime`만 재시작할 수 있다. EdgeX Device consumer가 0개이고
  exact runtime 이름 확인이 일치할 때만 퇴역한다.
- 노드 카드를 바꾸면 등록 연결/장비 관측/통신/데이터 증거, Runtime inventory, protocol
  package, hardware binding과 기존 EdgeX
  Device 목록이 같은 선택 노드 범위로 함께 바뀐다. 연결 마법사의 target node는 노드 카드
  선택으로 고정하며 임의 입력할 수 없다.
- 등록 마법사는 protocol/Device Service를 먼저 고른 뒤 hardware binding과 protocol별
  Runtime/Device 설정을 입력한다. Runtime 준비 방식은 `auto`로 고정해 기존 인스턴스를
  재사용하고 없으면 검증 template만 배포한다. 현재 노드에서 사용할 수 없는 installed Adapter와 미검증 protocol도 선택
  목록에는 이유와 함께 보이지만 비활성화된다.
- API 요청은 `adapterId`, runtime mode, 등록된 target node/hardware binding, Device/Profile
  계약만 받는다. 임의 image, command, privilege, raw hostPath, hostNetwork, 고정
  ClusterIP/PodIP는 받지 않는다.
- 각 hardware binding은 `Port`/`BaudRate`/`DeviceID` 또는 `Bus`/`DeviceID`처럼
  `reusePolicy.bindingFields`와 정확히 일치하는 `protocolProperties`를 가진다. 서버는 요청
  protocol tuple이 등록 binding과 일치하는지 다시 검증한다.
- Serial/I2C template는 실장비 검증 상태와 기존 runtime을 표시하지만 현재 등록 binding을
  Argo runtime이 점유하므로 `auto`는 재사용한다. Modbus, OPC-UA, MQTT와 RTSP는 image,
  profile, 실장비 검증 전까지 일반 endpoint를 `unverified`/`BLOCKED`로 표시한다. 단, 개발
  simulator와 정확히 일치하는 Modbus TCP binding만 공식 image/Profile 검증을 거친
  `template-verified` 경로로 Controller 배포가 허용된다. MQTT는 별도 scanner 없이
  노드별 network binding과 runtime setting allowlist를 사용하며, 공식 image와 bundled
  temperature Profile을 묶은 개발용 `template-verified` 경로만 Controller 배포가 허용된다.
- 마지막 단계의 `검증하고 연결`은 먼저 mutation-free validation을 실행하고 성공한 동일
  payload로 Runtime 준비, Profile/Device readback과 first Event 확인을 계속한다. 임의
  image, hostPath 또는 Catalog 밖 endpoint를 실행하는 단축 경로는 없다.
- 신규 connection은 `hardwareBindingId`, `physicalDeviceId`, `nodeName`을 EdgeX Device
  system tag로 기록한다. 연결 등록만으로 물리 장비가 감지됐다고 판단하지 않고
  `operatingState`와 latest Event를 별도 증거로 표시한다.
- 웹 Device Profile 편집기는 Core Metadata Profile 목록과 읽기 전용 DeviceResource
  계약의 사전 검증·idempotent 생성·readback을 제공한다. 동일 이름의 다른 계약은
  차단하고 동일 계약은 재사용한다. 웹 생성 Profile은 등록 현황에 즉시 표시하고 전체
  목록은 `장비 연결` 단계에서 선택한다. 후보 model/capability 초안에서 value type과
  units를 추측하지 않으며 parser, Device Service image, raw device path, Catalog
  binding, Device와 command를 생성하지 않는다.
- Serial driver는 `(Port, BaudRate, DeviceID)`별 reader를 만들고 같은 tuple의 여러
  `ResourceName`은 reader를 공유한다. 두 번째 등록 Serial 포트도 같은 Device Service가
  처리하므로 센서마다 Pod를 만들지 않는다. 다만 실제 포트를 추가할 때는 stable host
  identity, exact Pod 장치 마운트, 두 catalog의 binding과 external runtime
  `hardwareBindingIds`를 같은 Git 변경으로 등록해야 한다.
- 같은 service/protocol endpoint와 resource route를 이미 소유한 Device가 있으면
  `protocol_binding_exists`로 차단한다.
- Connection 상태는 `RUNTIME_READY → DEVICE_APPLIED → WAITING_EVENT → ACTIVE`를 구분한다.
  Event가 아직 없는 장비는 Metadata를 임의로 되돌리지 않는다. 신규 runtime 뒤 Metadata
  적용이 실패한 경우에만 consumer 0을 확인하고 해당 runtime의 안전한 퇴역을 시도한다.

KubeEdge는 target node와 workload 상태만 제공하며 `AdapterRuntime`을 물리 Device inventory로
보지 않는다. KubeEdge `Device`/`DeviceModel`/`DeviceStatus`, MapperFramework와 EdgeMesh는 이
관리 경로에서 수정하지 않는다. 2026-07-30에는 실제 실행처럼 보이던 과거 AI
Pipeline/Workflow Builder와 전용 `POST /state/device-source-bindings/sample` API를 제거했다.
2026-07-31의 새 `서비스 설계`는 이 legacy 화면을 복구한 것이 아니라 EdgeX
Device/Profile read-only 계약에 한정한 별도 dry-run 프로토타입이다. Device Service의
휘발성 recent cache와 Local Data API는 고정 `sensor-anomaly-demo` 및 향후 같은 노드
consumer를 위해 유지하며 state-aggregator가 telemetry를 workflow 입력으로 프록시하지
않는다. workflow runtime 실행, command publish, actuator 실행, migration과 offloading은
현재 범위가 아니다.

현재 범위의 핵심 표현:

- 서비스 데모 우선
- EdgeX Device Service와 Device Profile/Device
- 중앙 Core Data·server2 PostgreSQL 권위
- MQTT는 검증 package가 있는 연결만 웹 등록 시 필요에 따라 Device Service 배포
- 프로토콜별 독립 migration gate
- 통합 운영 가시화
- 실공장 기반 PoC
- 현장 적용성
- 생산성 향상 효과
- 단계적 구현

2차년도 공식 본문은 `docs/단계별-추진계획.md`를 따른다. 2026년 7월 29일 옥동

- 메인·보조 유압펌프 및 모터 이상 감지

이 두 서비스를 통해 현장 데이터 통합, AI 서비스 컨테이너 배포, 수집 → 전처리 → 추론 →

단계적으로 구축한다. 아래 구조는 이 목표를 지원하는 기술 설계이며 현재 구현 완료 기능이
아니라 설계 및 프로토타입 승격 대상이다.

- 물리 온디바이스의 기능, 상태, 자원, 입출력을 엣지 AI 서버 쪽 소프트웨어 인스턴스로 표현하는 가상디바이스
- 물리/가상디바이스의 상태, capability, resource, I/O, workflow binding을 관리하는 디바이스트윈
- AI 서비스를 stage 단위로 구성하고 가상디바이스를 동적으로 연결하는 워크플로우
- 컨테이너 기반 워크플로우 통합 개발도구와 validation/실행 계획 UI
- 가상디바이스/엣지 상태 기반 워크로드 스케줄링과 자원 재배치 정책

### 보존 프로토타입: Serial JSON Virtual Device Runtime

`virtual-device/`는 물리 디바이스의 Serial JSON 프로토콜과 원본 필드명을
profile 기반 표준 MQTT telemetry로 변환했던 2차년도 보존 프로토타입 경로다.
물리 디바이스 데이터 수집, 표준화, 로컬 MQTT 발행, 연결 상태와 heartbeat까지만
담당하며 AI 서비스가 아니다.

이 프로토타입에는 KubeEdge CRD, MapperFramework 수정, EdgeX, 중앙 telemetry 전송,
Virtual Device Registry, dashboard, AI 실행, 자원 증강, offloading을 포함하지 않는다.
`sensor-collector/serial_mqtt_collector.py`와 `virtual-device/`는 서로 자동 대체/결합하지 않는 보존 프로토타입 또는 legacy comparison 경로다. 둘 다 EdgeX Serial migration wave 완료, current physical-device plane 또는 fallback으로 간주하지 않는다.

### 프로토타입 승격 후보: Runtime Resource Augmentation Scheduler v1

2026-06-19 기준 다음 작업 후보는 자원증강 리소스를 수동 실행 버튼으로 호출하는 것이 아니라,
runtime 관측값을 기반으로 자동 스케줄링 판단까지 이어지는 최소 경로다.
현재 완료된 자원증강 상태 집계와 dashboard 가시화 위에 pod/service 사용량,
resource pressure, capability matching, selected augmentation resource 상태를 얹는 형태로 다룬다.

포함할 수 있는 범위:

- Prometheus/Kubernetes에서 관측한 pod/service CPU/GPU/memory 사용량을 자원증강 판단 입력으로 사용
- `AugmentationResource`와 `DeviceAugmentation`의 Available/Ready 상태를 scheduling 후보 필터로 사용
- 대상 edge workload와 보강 resource 사이의 capability matching, pressure reason, selected resource role을 status로 기록
- dashboard에는 "왜 증강 대상인지", "어떤 자원이 선택됐는지", "현재 적용/대기/불가 상태인지"를 표시
- 실제 Kubernetes mutation은 dashboard나 버튼이 아니라 별도 scheduler/controller 정책 경로에서만 수행

포함하지 않는 범위:

- 수동 실행 버튼으로 임의 Job을 생성하는 흐름
- 고정 샘플 payload로 analyzer endpoint를 호출하는 smoke-test 실행
- dashboard/state-aggregator가 승인 Controller를 우회해 임의 Kubernetes
  apply/delete/restart를 수행하는 구조
- runtime migration
- cost model 기반 전역 최적화
- legacy `workflow_executor`, `workflow_reporter`, `placement_engine`의 현행 기능 승격
- agent-assisted planning 또는 LLM 기반 전역 제어

## 현재 구현 과정에 포함되는 컴포넌트

현재 구현 과정에서 직접 다루는 컴포넌트는 다음과 같다.

| 구분 | 경로/컴포넌트 | 역할 |
|---|---|---|
| 현재 EdgeX 배포 | `edgex/k8s/` root Kustomize | 중앙 Core/MessageBus/PostgreSQL/gateway, Serial/I2C Device Service, Plan 기반 discovery DaemonSet, AdapterRuntime CRD와 Controller/PVC를 단일 진입점에서 배치. MQTT broker/publisher 개발 fixture는 root에 포함하지 않음 |
| MQTT 웹 등록 개발 fixture | `edgex/k8s/base/mqtt-simulator/`, `edgex/k8s/overlays/development/mqtt-simulator/` | 선택 배포하는 anonymous 개발 broker와 고정 온도 publisher. 웹 등록 시 Controller가 공식 `device-mqtt` Runtime/Profile/Device를 준비하고 first Event를 확인하는 수직 경로 검증용 |
| 현재 physical integration | `edgex/device-serial/`, `edgex/device-sensehat/`와 각 `edgex/k8s/base/device-*/` | Jetson Arduino Serial, Raspberry Pi Sense HAT I2C endpoint, Profile/Device, typed Event/Reading과 read-only 조회 수직 슬라이스 |
| 장비 발견 후보 | `edgex/device-discovery-agent/`, `edgex/k8s/base/device-discovery-agent/` | 서명된 노드별 Plan에 따라 USB Serial stable identity와 allowlist I2C 단일·복합 chip identity를 protocol-scoped 후보로 보고한다. 세 node의 일반 비권한 Serial DaemonSet과 dev0003 exact-device I2C DaemonSet을 분리하며 네트워크 전체 scan, Device 등록과 Device Service 설치는 수행하지 않음 |
| 퇴역 telemetry 코드 | `edgex/telemetry-plane/`의 edge Agent/outbox 부분 | 운영 render가 아니며 과거 설계·검증 이력으로만 사용. 중앙 gateway는 유지 |
| 보존 canary | `edgex/mqtt-bridge/`와 과거 Jetson-local evidence | 과거 장비·profile·Reading 비교 근거이며 현재 배포, 중앙 topology나 fallback이 아님 |

## 현재 연구 방향에서 제외하는 것

다음 항목은 현재 서비스 데모 운영 경로에서는 진행하지 않는다.
따라서 현재 기능 또는 실증 완료 기능처럼 표현하지 않는다.
2차년도 설계 트랙에서 다시 다루는 경우에는 `docs/2차년도-가상디바이스-워크플로-설계.md`의 정의와 경계를 따른다.

- 동적 workflow 분해/실행
- runtime replanning
- placement engine 기반 자동 재배치
- cost model 기반 offloading 판단
- workflow_executor 중심 orchestration
- workflow_reporter 중심 stage event pipeline
- agent-assisted planning layer
- LLM이 전체 플랫폼 제어를 수행하는 구조
- 전체 플랫폼 자율 제어형 orchestration

이 항목들과 KubeEdge Device/DeviceModel/DeviceStatus, MapperFramework, `mqttvirtual`, mapper direct-write physical-device 경로는 필요한 경우 `Legacy / Reference` 또는 `Archive` 자료로만 다룬다. 현재 구현 요구사항, 발표자료의 현행 기능, 병행 status/control plane, fallback, 또는 다음 확정 단계처럼 해석하지 않는다.

|---|---|

## 문서 작성 원칙

현재 문서와 발표자료에서는 다음 표현을 사용한다.

유지할 표현:

- 서비스 데모 우선
- 디바이스-서비스 연결 구조
- 통합 운영 가시화
- 실공장 기반 PoC
- 현장 적용성
- 생산성 향상 효과
- 단계적 구현

피할 표현:

- dynamic offloading을 다음 구현 목표처럼 제시하는 표현
- 전체 플랫폼 자율 제어형 orchestration을 실증 완료처럼 보이게 하는 표현
- LLM 기반 전역 제어를 현재 기능처럼 보이게 하는 표현
- 동적 workflow 실행이 이미 완료된 것처럼 보이는 표현
- agent-assisted planning을 현재 연구 방향처럼 제시하는 표현
- 고도화 기능이 이미 실증 완료된 것처럼 보이는 표현

## 작업 판단 기준

새 작업을 시작할 때는 다음 순서로 판단한다.

1. 서비스 데모 또는 디바이스-서비스 연결 구조에 직접 기여하는가?
2. 통합 운영 가시화 또는 상태 판단을 명확하게 하는가?
3. 중앙 EdgeX Core Metadata의 inventory/schema와 Core Data/PostgreSQL의 persistence authority, protocol별 Device Service connection-owner gate를 지키는가?
4. 실공장 기반 PoC와 현장 적용성 설명에 도움이 되는가?
5. workflow/offloading/agent-planning 계열로 다시 확장되는 작업은 아닌가?

1~4에 해당하면 현재 범위에 포함한다.
5에 해당하면 현재 작업에서 제외하거나 archive/reference로 분리한다.
