# 프로젝트 범위

## 물리 장비의 가상 디바이스 표현 (2026-09-08 승인)

사용자의 명시적인 구현 요청에 따라 물리 source별 읽기 전용 가상 디바이스 표현을 추가한다. `physical-vd:<인코딩된 source ID>`라는 대시보드 논리 ID를 두고 원본 장비, EdgeX 등록 기능, 기존 관측 트윈과 이용 서비스를 연결한다. 이 용어는 장비 수준의 조회 표현에 한정하며 EdgeX inventory·상태 권위나 기능별 관측 트윈의 계약을 변경하지 않는다. simulator·센서 제어·실행 컨테이너가 아니다. 원본 없는 항목에는 가상 ID를 만들지 않는다.

NEXUS의 **가상 디바이스** 탭과 `/#physical-virtual-devices`에서 선택·상세·원본 이동을 제공한다. `source-view.js`의 논리 모델과 기존 GET API를 재사용하며 별도 inventory 저장·등록·쓰기 API는 추가하지 않는다. 상세 계약과 검증 기준은 [물리 장비의 가상 디바이스](물리-가상-디바이스.md)를 따른다.


## 2026-09-08 통합 운영 대시보드 확장

이번 승인 범위는 기존 NEXUS의 서비스 중심 운영 projection, 데이터 비교,
추천·실행 이력 연결과 서버 설계 버전·시험 원장 저장이다. EdgeX 물리 권위와
Kubernetes/KubeEdge node/workload 권위를 유지한다. 설계 저장은 Configured이며
범용 배포·오프로딩을 실행하지 않는다. 현재 실제 가능/부분 구현/미구현과
API·검증·운영 책임은 [통합 운영 대시보드 고도화](통합-운영-대시보드-고도화.md)를 따른다.
로컬 수정 및 검증 상태이며 운영 image 반영은 별도다. 아래 과거 날짜의 운영 기록은
그 시각의 근거로만 읽는다.


## 목적

이 문서는 저장소의 현재 구현, 후속 설계와 과거 실험을 구분하는 최상위 기준이다. 문서와
대시보드는 실제 endpoint·manifest·테스트 근거가 없는 기능을 완료로 표시하지 않는다.

## 현재 범위

### 컨테이너 가상 디바이스 최소 시험 구현

- `edge-orch/virtual-device-runtime/`의 `vd-demo-001`은 CPU 모델을 Pod 내부에서
  실행하는 기능 실행·관리 프로토타입이다. 하드웨어 에뮬레이션, 센서 inventory,
  자동 offloading이나 서비스 설계의 실행 기능이 아니다.
- Git registry의 정의·연결 설정과 Kubernetes 실행체를 분리한다. 시험 namespace
  `virtual-device-test`에서 운영자가 승인된 범위에 한해 replicas 0↔1을 수동 조작한다.
  정지해도 정의와 논리 ID는 남는다. 운영 Argo CD/EdgeX 배포 경로에는 연결하지 않는다.
- 대시보드와 aggregator는 새 GET 관측만 수행한다. Pod UID·소유 관계, 모델/API 준비,
  요청 처리 증거, 자원 선언·관측치와 오류를 분리하며 관측 실패는 확인 불가다.
- 완료 근거는 실행 안내서의 로컬 자동시험 및 별도 승인 후 클러스터·Jetson 시연이다.
  로컬 통과를 현장 연동 성공으로 확대하지 않는다. 시험 배포·정지 책임은 운영자에게 있다.
- 2026-09-07 승인 시험에서 서버 Pod 기동·교체·오류 관측, 실제 Jetson의 Service IP 요청과
  기존 대시보드 반영을 확인했다. 최종 상태는 정의 1개/실행체 0개다. Jetson 호스트의
  Service DNS 해석은 미해결이며 [실시스템 검증](../edge-orch/virtual-device-runtime/실시스템-검증.md)에
  측정 경계와 명령을 기록했다.

### 가상 디바이스 운영 사이클 확장 (2026-09-08 승인 구현)

사용자의 계획·구현 지시에 따라 `vd-demo-001`의 시작 → 준비 확인 → 시험 추론 → 결과 확인 → 정지를 NEXUS에서 제공한다. 기존 최소 시험의 조회 전용 경계에서 이 단일 대상의 운영 사이클을 확장한다. 임의 정의 생성, 모델 업로드, 노드 이동과 범용 오프로딩은 포함하지 않는다.

- 대상은 `virtual-device-test/vd-demo-001`, Git에 고정된 CPU Iris 모델·서버·이미지다. replica 0/1만 허용한다.
- aggregator 가상 디바이스 제어 모듈이 별도 feature flag와 기존 실행 운영 토큰을 확인한다. 해당 이름의 Deployment `/scale` get/update만 추가하며 Pod 생성·삭제·Deployment template 변경 권한은 부여하지 않는다.
- 요청 접수와 실제 Ready/종료 관측을 구분한다. 정지는 정상 Kubernetes 조회의 실행체 0으로 확인한다.
- 작업 요청 키·상태·시험 결과를 aggregator PVC SQLite에 남긴다. 중복 키는 같은 결과를 반환하고 불확실한 추론을 자동 재실행하지 않는다.
- 대시보드 시험 요청의 clientId는 `nexus-dashboard`다. Jetson 요청이나 생산 품질 실증으로 표시하지 않는다.
- 운영 책임은 테스트베드 운영자, 배포 소유자는 Argo CD `edge-orch-state-aggregator`다. 시험 Deployment 정의는 기존 독립 시험 경로에 유지한다.
- 검증 gate: 인증·다른 대상 차단, 중복 요청·충돌·응답 유실 처리, 실제 시작/모델 Ready/추론 응답 identity/정지/정의·이력 유지, 기존 센서 Deployment 보존.

### 물리 디바이스와 데이터

- EdgeX Core Metadata의 Device/Profile/Device Service를 inventory와 schema 권위로 사용한다.
- EdgeX Device Service가 Serial·I2C 등 승인된 endpoint를 직접 소유하고 값을 표준화한다.
- EdgeX Core Data의 Event/Reading과 `origin`을 telemetry·freshness 권위로 사용한다.

- KubeEdge는 edge node와 workload 관리에만 사용한다.

### 현재 수직 슬라이스

| 물리 source | 노드 | 수집 Runtime | EdgeX Device |
|---|---|---|---|
| Arduino Uno | `etri-dev0001-jetorn` | `device-serial-jetson` | 온도·조도·자기·가속도 X/Y/Z 6개 |
| Sense HAT v1 | `etri-dev0003-raspi5` | `device-sensehat-raspi` | 환경·자세·자이로 6개 |

두 Runtime은 같은 물리 연결을 여러 기능별 Device로 fan-out한다. `arduino-001`과
`sensehat-001`은 물리 source ID이며 aggregate EdgeX Device가 아니다.

`device-serial-jetson`에는 established stream 오류 뒤 25·50·100·200ms fast-retry, 첫 유효
sample의 SDK async enqueue 완료 시점까지의 복구시간 계측, 400ms 개발 gate metric과
read-only stats API가 배포돼 있다. 후속 image는 port ready·first byte·first valid frame 구간도
분리한다. 현재 운영 구성은 정상 sample을 1,000ms로 유지하고 established stream 재연결 때
첫 byte가 없을 때만 25ms 간격으로 최대 네 번 고정 `READ_NOW`를 수행한다. USB 재열거는
승인된 udev identity rule과 좁은 `/run/edgeai/devices` endpoint 디렉터리로 따라가며 전체
호스트 `/dev`·`/sys`를 Device Service에 mount하지 않는다. 같은 50ms 단절의 정식 30회는
30/30회 통과했고 p50 196.619ms, p95 304.244ms, max 309.848ms, miss 0이었다. 이후 Core Data의
디바이스별 Event 전체 역순 탐색과 DB connection pool 교착을 수정했다. 수정 뒤 추가한 50ms
단절 canary는 205.724ms에 전송을 재개했고 첫 후속 temperature Event가 4.130ms 뒤 중앙 DB에
저장돼 API로 조회됐다. 따라서 2차년도 400ms process 개발 gate와 중앙 저장 E2E canary는
통과했지만 공식 250ms 목표 달성을 주장하지 않는다.
Kubernetes node/Pod 전체 failover와 통신 단절 중 durable 저장·재전송은 별도 범위다. 상세
측정 경계는 [가상화 노드 오류 복구시간](가상화-노드-오류-복구시간.md)을 따른다.

### 제한된 AI 서비스 신규 배포

- `state-aggregator`의 `POST /api/deployments`는 기존 서비스 자원 프로파일과
  `/api/placements/select` 결과를 이용해 단일 replica의 **신규** Deployment만 생성한다.
- 배포 대상은 전용 `edge-ai-workloads` namespace로 고정하고, 선택 노드는 exact hostname
  `nodeSelector`와 required node affinity를 함께 적용한다.
- CPU·memory와 accelerator requests는 완전하게 선언된 단일 Pod 서비스 프로파일에서
  가져온다. 복수 Pod 집계 프로파일과 requests 누락 프로파일은 배포하지 않는다.
- 입력은 DNS label 배포명, allowlist에 포함된 로컬 registry의 immutable digest image,
  선택적 container port/readiness path로 제한한다. raw manifest, env, command, volume,
  hostPath, privilege, Service와 Ingress 입력은 받지 않는다.
- Controller service account는 전용 namespace의 Deployment `create/get/list/watch`와
  기존 Pod 관측 권한만 가진다. update·patch·delete 권한은 갖지 않는다.
- API는 Placement 탈락, Deployment 생성 성공·실패, Pod Ready와 Kubernetes 실패 reason을
  명시적으로 반환한다. 이 경로는 shared-token으로 보호되는 개발 테스트베드용이다.

### Runtime Recommendation Engine

- Git `ServiceDescriptor`에서 runtime recommendation policy와 observability adapter가
  선언된 AI 서비스만 지속 감시한다.
- Kubernetes Deployment/StatefulSet, Pod와 Node 상태, Prometheus 자원 사용량, 서비스가
  제공하는 입력 freshness·model readiness·latency·backlog·throughput을 서로 다른 근거로
  유지한 채 결합한다.
- 판단 상태는 `NORMAL`, `OBSERVING`, `AUGMENT_RECOMMENDED`,
  `REPLACE_RECOMMENDED`, `BLOCKED`이며 threshold 진입/회복 기준을 분리한 hysteresis,
  dwell과 cooldown을 적용한다.
- EdgeX 입력 장애·stale, model 미준비, 필수 관측 누락은 자원 부족으로 해석하지 않고
  `BLOCKED`와 명시적 reason code로 반환한다.
- 증강·대체가 필요할 때 현재 실행 노드를 제외하고 기존 Placement Engine으로 후보를
  다시 Filter/Score한다. 결과에는 최적 노드와 현재 노드를 포함한 전체 후보의
  `reasonCodes`를 보존한다.
- dwell timer, latch, cooldown과 최신 판단은 PVC의 SQLite에 저장하며 상태 변화와 판단
  근거 이력을 조회 API로 제공한다.
- 이 엔진은 read-only 추천만 수행하며 Deployment 생성·수정·삭제, Service routing,
  traffic cutover, migration과 offloading을 실행하지 않는다.

### sensor-anomaly-demo 제한적 Runtime Offloading PoC

> 이 절은 로컬 구현과 2026-08-26 격리 smoke test 범위다. 2026-08-28 Argo 배포 기준선에는
> 포함되지 않으며 현재 production 요청은 edge-local에 유지된다.

- 전체 workload를 옮기는 `REPLACE_RECOMMENDED` 경로와 별도로, ACTIVE
  `sensor-anomaly-demo`가 입력 수집·전처리·결과 저장을 Jetson에 유지하고 승인된
  Server1 endpoint에 추론 요청만 전달하는 서비스 전용 부분 오프로딩 경로를 둔다.
- edge worker의 공통 `InferenceExecutor` 계약 아래 local executor와 remote executor를
  분리한다. Remote 요청은 Git에 고정된 service/model/target 계약과 `requestId`를 사용하며,
  응답 identity·model version·freshness를 검증한 한 결과만 application-owned SQLite에
  authoritative result로 저장한다.
- Kubernetes Lease는 누가 production polling·저장을 수행하는지를 계속 결정한다. 오프로딩은
  그 ACTIVE workload 내부에서 추론 위치만 `LOCAL`, `REMOTE`, `LOCAL_FALLBACK`으로 바꾸며
  source Deployment·PVC·Service·EdgeX inventory를 수정하지 않는다.
- timeout, 연결 실패, endpoint/model 미준비, 잘못된 응답, model version 불일치 또는 지속적인
  latency 한계 초과는 즉시 local executor로 fail over한다. 늦거나 중복된 remote 응답은 기존
  결과를 덮어쓰지 않는다.
- Runtime Recommendation은 node/workload failure에는 기존 전체 `REPLACE_RECOMMENDED`를
  우선한다. 정상 workload의 지속 자원·서비스 압력에는 Git offloading contract, remote Pod/API
  readiness, network latency와 기존 Placement Filter/Score를 모두 통과한 경우에만
  `OFFLOAD_RECOMMENDED`를 반환한다.
- 현재 `baseline-1.0.0` Server1 후보의 성능 자격은 2026-08-18 실험에서 `rejected`다.
  구현과 장애 fallback 시험이 성공해도 이 실험 gate를 우회해 자동 오프로딩을 권고하거나
  운영 경로로 자동 승격하지 않는다. LOCAL→REMOTE 변경은 승인 Secret을 사용하는 서비스 전용
  API 또는 검토된 Git overlay에서만 허용하며 자동 추천→실행 연결은 범위 밖이다.
- 이 경로는 모델 분할·distributed inference·범용 workflow stage offloading이 아니다.
  첫 PoC 범위는 Jetson 전처리 → Server1 추론 → Jetson 결과 저장의 단일 서비스 경로다.
- 2026-08-26 격리 실클러스터 smoke test에서 새 ARM64 edge image와 AMD64 CPU server
  image로 LOCAL → REMOTE → server 장애 → LOCAL_FALLBACK protocol 경로와 Jetson의 결과
  저장 지속을 확인했다. 첫 REMOTE 결과는 전환 요청 후 약 543ms, remote sample total은
  33.46ms(network 33.12ms, server processing 0.34ms), 장애 후 fallback 결과는 scale 요청 뒤
  약 1.08s 안에 관측됐다. 이는 GPU 성능 자격이나 운영 자동 오프로딩 승격 근거가 아니며
  격리 workload는 시험 후 삭제했다.

### Runtime Execution Plan

- 최신 Runtime Recommendation을 입력으로 사용하는
  `GET /api/runtime-recommendations/{serviceId}/execution-plan`은 실행 가능한 변경 요청이
  아니라 운영자·후속 Controller 검토용 read-only 계획을 반환한다.
- `AUGMENT_RECOMMENDED`는 신규 인스턴스 생성, Ready 확인, 트래픽 분산 순서로 계획한다.
  `REPLACE_RECOMMENDED`는 대체 workload 생성, Ready 확인, 트래픽 전환, 기존 인스턴스
  종료와 조건부 rollback 순서로 계획한다.
- 각 단계에는 순번, 실행 방식, 대상 node/workload, 선행조건과 실패조건을 명시한다.
  계획 ID와 후보 workload 이름은 추천 시각·대상 node·workload identity에서 결정적으로
  생성해 동일한 추천의 조회 결과가 흔들리지 않게 한다.
- `NORMAL`·`OBSERVING`은 `not_applicable`, `BLOCKED`나 선택 node가 불완전한 추천은
  `blocked`로 반환하고 변경 단계는 만들지 않는다.
- API 조회는 `/api/deployments`, Kubernetes apply/update/delete 또는 Service·Ingress와
  외부 traffic API를 호출하지 않는다. rollback도 실행 단계가 아니라 조건부 보상 계획이다.
- 대시보드에서는 이 GET 계획만 `실행 계획 / Read-only`로 표시하며 승인·실행·적용 버튼과
  Execution Controller mutation API를 노출하지 않는다.

### 승인 기반 Execution Controller

- 사용자가 최신 plan의 `planId`를 본문에 다시 제출하고 `approved=true`, 승인자 식별자와
  유효한 관리 token을 함께 제공한 경우에만 실행 record를 만든다. `planId`는 실행의
  idempotency key이며 동일 plan의 재호출은 최초 record를 반환하고 단계를 반복하지 않는다.
- 현재 실행 코드는 고정 `edge-ai-workloads` namespace의 `create_candidate`, `verify_ready`,
  `validate_candidate_pre_activation`, Git 승인 Kubernetes Lease 계약에 의한
  `handoff_execution_ownership`·`verify_active_candidate`·`rollback_execution_ownership`과
  Git 승인 Traffic Routing Contract에 의한 `switch_traffic`,
  `verify_switched_traffic`, 실패 시 `rollback_traffic`까지 구현한다.
  source workload를 복제하지 않고 Git의 서비스별 Candidate Workload Template에 승인된
  immutable image, env, port/probe, resources, securityContext, namespace, architecture/accelerator,
  state policy만 materialize한다. source Deployment·Service·PVC/StorageClass와 target Node를
  읽기 전용 preflight하고 계약 불일치나 미지원 storage는 fail-closed한다.
- `sensor-anomaly-demo` v1은 `fresh_state`다. source의 RWO `local-path` PVC와 `results.db`는
  candidate에 재사용·복제하지 않고 state mount를 `emptyDir`로 제공한다. 생성 candidate와 PVC
  식별자는 실행 record에 저장하며 현재 PVC 목록은 비어 있다. Candidate Validation은 Git의
  서비스별 계약에 따라 handoff 전 SHADOW의 health, fresh input, model ready와 memory-only
  inference를 확인하고, handoff 뒤 ACTIVE의 production `framesProcessed`, 실제 결과 freshness와
  측정 가능한 latency SLO를 다시 확인한다.
- Lease는 실제 AI processing 권한만 소유하고 Traffic Manager는 요청 routing만 소유한다.
  source와 candidate 중 Lease holder 하나만 ACTIVE이며 holder 전환과 rollback은
  resourceVersion CAS, 서비스별 SQLite lock, 영속 snapshot과 audit를 사용한다. Lease 만료,
  stale holder, 충돌 또는 API 관측 실패 시 workload는 production 처리를 하지 않는다.
  handoff/active validation 실패 시 source holder로 rollback하고 candidate는 자동 삭제하지 않는다.
- 단계 상태는 `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `BLOCKED`로 저장한다. 승인,
  상태 전이, 실패 reason과 actor를 SQLite 실행 record·append-only audit log에 기록하며 PVC에서
  재시작 후에도 유지한다. 중단 시 `RUNNING` record는 자동 재실행하지 않고 `BLOCKED`로 복구한다.
- `switch_traffic`은 selectorless Service와 Runtime Controller 단독 소유 EndpointSlice가 있고
  모든 data-plane consumer의 EndpointSlice 호환성이 입증된 계약에서만 atomic source→candidate
  cutover를 수행한다. 전환 후 기존 validation 계약을 Service 주소로 다시 실행하고 실패하면
  저장한 source routing snapshot으로 즉시 복구한다. Service selector는 수정하지 않는다.
- 현재 EdgeMesh는 Service·Endpoints를 관측하지만 EndpointSlice 소비가 입증되지 않았고 실제
  Service도 Argo CD 소유 selector를 유지하므로 `sensor-anomaly-demo` routing 계약은
  `routing_mode_unsupported`로 fail-closed다. 따라서 이 서비스의 실클러스터 traffic mutation은
  아직 운영 기능이 아니다.
- 2026-08-26 격리 실클러스터 시험에서는 selectorless Service와 Controller 소유 core
  `Endpoints`로 Jetson source→Raspberry Pi candidate→Jetson source 전환이 실제 HTTP 응답과
  EdgeMesh libp2p 로그에서 확인됐다. 이는 후속 `runtime-endpoints` 모드의 근거이며 현재
  `runtime-endpointslice` Controller나 production Service가 활성화됐다는 뜻은 아니다.
- `distribute_traffic`, `terminate_current`, source/candidate 삭제·promotion은 여전히
  `unsupported_step`이다. source Deployment·PVC는 유지하고 candidate도 자동 삭제하지 않는다.
- `sensor-anomaly-demo` Service는 Argo CD automated sync/self-heal 대상이다. Runtime Controller는
  Service를 patch하지 않으며, Git이 selectorless 전환과 정적 routing 허용 정책을 소유하고
  Runtime Controller가 전용 EndpointSlice의 동적 active endpoint만 소유하는 구조를 승인안으로 둔다.
- dry-run은 최신 plan 일치, 승인 없이 확인 가능한 preflight와 지원 단계 경계를 반환하며
  Kubernetes와 영속 실행·감사 상태를 변경하지 않는다.

2026-08-28 live 기준 source workload가 Lease holder로 ACTIVE이며 Runtime Recommendation은
`NORMAL/read_only`다. 과거 격리 검증 candidate가 남아 있어도 production traffic이나 source
소유권을 대체하지 않는다. 현재 승인 실행 이력의 최종 상태는 traffic routing 미지원 또는
candidate 장애 검증으로 `FAILED`이며, 자동 migration/offloading 성공으로 집계하지 않는다.

### 제한된 장비 관리

- passive discovery candidate 조회·검토와 exact Catalog binding validation
- 승인된 Profile/Device 등록 Saga와 first Event 확인
- Controller가 소유한 Adapter Runtime만 제한적으로 restart·retire
- 임의 image·hostPath·raw manifest·command 입력 없음
- 제한된 신규 AI 서비스 배포는 별도 allowlist와 immutable digest를 통과한 image만 허용
- 사용자 인증·인가가 추가되기 전까지 테스트베드 접근 경계에서만 사용

## 명시적으로 제외하는 것

- EdgeX와 병행하는 KubeEdge Device/DeviceModel/DeviceStatus 물리 권위
- MapperFramework, mapper direct-to-Influx와 legacy MQTT topic을 fallback으로 사용
- 광역 네트워크 probe나 임의 hostPath/image/command 실행
- 서비스 설계 화면의 Kubernetes apply/delete/restart 또는 EdgeX metadata mutation
- Controller가 생성한 Deployment의 update·patch·delete, 기존 workload 변경
- 승인 없는 Runtime Recommendation/Execution Plan 적용 또는 traffic cutover와 rollback 실행
- EndpointSlice 소비가 입증되지 않은 EdgeMesh 환경의 traffic mutation
- 승인 없는 actuator command와 write command
- 동적 workflow·migration·offloading 전체 구현 완료 주장
- 승인·계약·후보 자격을 우회한 sensor-anomaly-demo 자동 오프로딩

## 완료 증거

기능은 다음 증거를 모두 연결할 수 있을 때만 현재 범위로 승격한다.

1. Git에서 검토한 계약과 immutable image
2. root Kustomize 또는 승인된 선택 overlay
3. 관련 자동 테스트와 manifest render
4. Argo CD 또는 명시적 운영 소유권
5. Pod/endpoint Ready와 실제 API readback
6. 실패·stale·누락 상태가 정상처럼 보이지 않는 대시보드 표시

Server1 후보의 실험 설계, 합성 입력 90회 기준선, 실제 Arduino Reading 120개를 고정한
18회 비교 결과와 승격 gate는
[AI 서비스 자원 증강 부하 실험](AI-서비스-자원-증강-부하-실험.md)을 따른다. CPU/GPU가
존재하거나 endpoint가 Ready라는 사실만으로 오프로딩 효과를 주장하지 않는다.

과거 workflow·placement·replanning 코드는 `edge-orch/workflow_*`,
`edge-orch/placement_engine/`, `workflow/`, `docs/archive/`에 보존하며 현재 요구사항으로
해석하지 않는다.
