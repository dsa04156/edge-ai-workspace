# 옥동 AI 서비스 데이터 계약

## 목적과 현재 상태

이 문서는 2차년도 옥동 PoC 서비스 2종의 입력 경계를 코드와 함께 버전 관리한다.
2026-08-18 현재 계약, simulator/replay, 유압펌프·모터 기준선 서비스의 결과·알림 저장은
구현되어 있다. 옥동 PLC tag, MES column, 실제 단위, 수집주기와 품질 label 시점은 현장
확정 전이므로 구현 완료로 간주하지 않는다.

## 통신 방식과 데이터 형식 분석

다양한 장비를 하나의 protocol로 강제하지 않는다. 연결·decode는 EdgeX Device Service가
소유하고, 상위 서비스에는 EdgeX Event/Reading과 versioned AI 입력 계약으로 표준화한다.

| source | 예상 통신·형식 | 현재 상태 | 표준화 경계 |
|---|---|---|---|
| Arduino 센서 | USB Serial, line-delimited JSON | 실장비 수직 슬라이스 검증 | `device-serial-jetson`이 resource별 Reading 생성 |
| Sense HAT | I2C register/binary | 실장비 수직 슬라이스 검증 | `device-sensehat-raspi`가 단위·resource 이름 부여 |
| PLC | Modbus TCP register 또는 현장 제공 방식 | simulator/fixture만 검증, 옥동 endpoint 미확정 | register type·scale·endianness를 Device Profile에 고정 |
| PLC/SCADA | OPC-UA node/value/status/timestamp | 후보 계약, 실장비 미검증 | node ID를 resource로 매핑하고 source timestamp·quality 보존 |
| MQTT 장비 | topic + JSON/binary payload | 개발 package/fixture 검증 | topic·payload schema를 Device Service adapter가 검증 |
| MES | REST JSON, DB row 또는 파일 batch 중 현장 확정 필요 | 접근 방식·column 미확정 | production ID와 event time 기준으로 별도 adapter가 정규화 |
| 카메라 | RTSP video frame | 후속 후보 | 승인된 AI Pod가 직접 구독하고 결과 metadata만 Event로 전달 |

Modbus·OPC-UA·MES가 표에 있다는 사실은 옥동 실장비 연동 완료를 뜻하지 않는다. endpoint,
인증, tag/node/column, 주기와 장애 동작은 현장 확인 후 adapter binding으로 확정한다.

## 공통 데이터 모델

서비스 입력 envelope는 protocol 차이를 다음 공통 의미로 바꾼다.

| 공통 요소 | 규칙 |
|---|---|
| 계약 식별 | `schemaVersion` 또는 계약 이름을 versioned 값으로 고정 |
| event identity | `eventId`는 source 내 중복 방지 키 |
| source identity | `sourceType`, `deviceId`, `assetId`, 선택 `nodeId`를 분리 |
| 시간 | `observedAt`은 timezone 포함 원 관측 시각, 수집 시각과 혼합 금지 |
| signal | 이름별 `value`, `unit`, `quality`를 보존하고 NaN·무한값 차단 |
| 생산 문맥 | `productionId`, lot, item 등은 현장 join 규칙 확정 후 연결 |
| 확장 | 임의 top-level field 대신 `signals.additional` 또는 version up 사용 |

EdgeX 쪽 공통 모델은 `DeviceProfile`이 resource schema를, `Device`가 endpoint와 물리
identity를, `Event/Reading`이 timestamped value를 제공한다. AI 계약은 여러 Reading을
하나의 분석 frame 또는 생산 건으로 정렬한 서비스 경계다. KubeEdge Device 객체를 이
데이터 모델의 병행 권위로 사용하지 않는다.

## 연동 인터페이스

| 경계 | 인터페이스 | 소유권 |
|---|---|---|
| 물리 장비 → 플랫폼 | EdgeX Device Service protocol driver | 연결, decode, scale, quality |
| inventory/schema | Core Metadata Device/Profile API | EdgeX 권위 |
| 중앙 telemetry | Core Data Event/Reading API·MessageBus | origin과 resource 값 |
| 동일 노드 저지연 입력 | Device Service Local Data v3 read API | service가 read-only 소비 |
| AI 서비스 입력 | `okdong.*.telemetry/v1` JSON Schema | 서비스별 versioned 계약 |
| AI 결과 | 서비스 `/api/v1/results`, `/api/v1/alerts` | application-owned 파생 데이터 |
| 영상 | 승인된 Pod의 RTSP direct subscription | frame은 Core Data에 싣지 않음 |

따라서 공통 모델과 인터페이스의 **플랫폼 기준은 정의돼 있고 현재 Serial/I2C 수직
슬라이스에서 구현**됐다. 하지만 “다양한 센서·PLC·MES 연동 완료”라고 할 단계는 아니다.
옥동별 register/tag/column mapping과 실장비 E2E 증거가 남아 있다.

## 계약 목록

| 계약 | 현재 용도 | 실행 상태 |
|---|---|---|
| `okdong.pump-motor.telemetry/v1` | 가속도 3축·온도와 선택 측정값을 이상감지 서비스 입력으로 전달 | simulator/replay와 현재 Jetson 기준선에서 검증 |
| `okdong.production-quality.telemetry/v1` | 생산 건과 PLC·MES 공정값, 선택 품질 label 연결 | schema만 구현, 현장 mapping·판별 서비스 미구현 |

두 계약의 권위 구현은
`edge-orch/sensor-anomaly-demo/app/contracts.py`이며 서비스의
`GET /api/v1/contracts`에서 JSON Schema를 조회할 수 있다.

## 펌프·모터 입력

| 필드 | 필수 | 의미 |
|---|---|---|
| `eventId` | 예 | source가 부여한 중복 방지 ID |
| `sourceType` | 예 | `sensor`, `simulator`, `replay` 중 하나 |
| `deviceId`, `assetId` | 예 | 입력 장치와 분석 대상 설비 ID |
| `nodeId` | 아니요 | 관측 edge node ID |
| `observedAt` | 예 | timezone을 포함한 원 관측 시각 |
| `signals.accelerationX/Y/Z` | 예 | 값, 단위와 quality가 있는 3축 입력 |
| `signals.temperature` | 예 | 현재 복합 기준선의 온도 입력 |
| `signals.additional` | 아니요 | 현장 확정 후 current, pressure, RPM 등을 연결할 확장 map |
| `production` | 아니요 | 생산 건과 함께 분석할 때 쓰는 context |

현재 Arduino의 raw 값은 이 계약의 실행 가능 기준선일 뿐 옥동 펌프 센서 단위가 아니다.
실제 PLC register와 센서 scale을 확인한 뒤 Adapter mapping으로 단위와 이름을 확정한다.

## 생산품질 입력

`production.productionId`를 join key로 사용하고 `processValues`를 비어 있지 않은 측정값
map으로 받는다. 실제 PLC tag와 MES column을 임의로 필수 필드에 넣지 않는다.
`qualityLabel`은 `good`, `defective`, `unknown` 중 하나이며 label 생성 시점과 판정 기준은
옥동·KPST 협의 뒤 확정한다.

## 개발용 Replay

```text
contract-valid JSONL
  -> replay Local Data v3 server
  -> 기존 LocalDataClient
  -> 시간 정렬
  -> PumpModelAdapter
  -> SQLite result / alert transition
  -> state-aggregator / dashboard
```

```bash
cd edge-orch/sensor-anomaly-demo
PYTHONPATH=. python3 -m app.simulator \
  --count 120 --interval-ms 500 --anomaly-start 80 \
  --output /tmp/pump-replay.jsonl

REPLAY_FILE=/tmp/pump-replay.jsonl REPLAY_REBASE_TO_NOW=true \
  PYTHONPATH=. uvicorn app.replay:create_app_from_env --factory --port 59910
```

Replay는 원래 sample 간 시간차를 유지하면서 첫 origin을 실행 시각으로 옮길 수 있다.
중복 `eventId`, timezone 없는 시각, NaN·무한값, 스키마 밖 필드는 시작 전에 차단한다.

## 결과와 알림 저장

`sensor-anomaly-demo`는 추론 결과를 application-owned SQLite에 먼저 저장한다. 이상 상태
전환 시 `opened`, 정상 복귀 시 같은 `alertId`의 `cleared` transition을 원자적으로
기록한다. 같은 origin을 다시 처리해도 결과나 알림을 중복 생성하지 않는다.

운영 manifest는 `/var/lib/sensor-anomaly-demo/results.db`를 1Gi `local-path` RWO PVC에
저장하며 기본 최대 100,000개 결과를 유지한다. 이는 EdgeX 소유 PostgreSQL schema와
분리된 AI 파생 결과다.

| API | 의미 |
|---|---|
| `GET /api/v1/results?limit=100&anomaly=true` | 서비스 영속 결과 조회 |
| `GET /api/v1/alerts?limit=20` | 발생·복귀 알림 이력 조회 |
| `GET /api/v1/storage` | 결과·알림 수, 열린 알림과 retention 확인 |
| `GET /state/service-demo/results` | 중앙 BFF를 통한 결과 조회 |
| `GET /state/service-demo/alerts` | 중앙 BFF와 dashboard용 알림 조회 |

## 모델 교체 경계

현재 지원 backend는 `online-baseline` 하나다. 실제 AI 모델을 연결할 때는
`PumpModelAdapter`를 구현하고 명시적 `MODEL_VERSION`을 결과와 알림에 기록한다.
지원하지 않는 backend를 기준선으로 대체 실행하지 않는다.

## 남은 현장 입력

- 실제 PLC·MES endpoint와 접근 방식
- 설비, 생산 건, lot, 품목의 식별자 관계
- 각 tag/column의 자료형, 단위, scale, 정상 범위와 수집주기
- 양품·불량 label의 생성 주체와 확정 시점
- 펌프·모터 AI 모델 파일, feature 요구조건과 판정 임계값
- 중앙 장기 결과 저장 및 알림 전달 채널

현재 PVC는 Jetson Pod 재시작 복구용 단일 노드 저장소다. 중앙 HA 저장, 원시 telemetry
offline outbox, 서비스 간 workflow 실행과 실제 고장 분류 실증은 아직 완료되지 않았다.
