# 문서 안내

이 디렉터리는 EdgeX 기반 물리 디바이스 관리와 KubeEdge 기반 엣지 노드·워크로드 관리를 결합한 엣지 AI 플랫폼 PoC 문서의 단일 진입점이다. 처음 읽을 때는 `wiki/지식-지도.md`에서 목적에 맞는 최신 기준 문서를 찾는다.

## 현재 상태

2026-07-21 기준 중앙 `edgex-system`에는 EdgeX Core Keeper, Core Metadata, Core Data, Core Command, 내부 MessageBus, PostgreSQL과 ingest gateway가 유지된다. `edgex-edge`의 과거 커스텀 `edgex-edge-agent-jetson`, `edgex-edge-agent-sensehat`, 전용 SQLite outbox PVC와 Agent 전용 Metadata bootstrap은 퇴역했다.

현재 `edgex-edge`에는 공식 EdgeX Device SDK 기반 `device-serial-jetson`이 배포되어 `etri-dev0001-jetorn`의 Arduino Uno를 `/dev/arduino-001`에서 직접 수집한다. `arduino-001`과 `etri-arduino-serial`이 Core Metadata에 등록되고, 6개 `Int32` Reading이 중앙 Core Data/PostgreSQL과 dashboard까지 같은 identity로 전달되는 정상 경로를 live로 확인했다.

이 완료 범위에는 로컬 MQTT broker, Agent, SQLite outbox, recent cache와 actuator write가 없다. 실제 케이블 분리·복구 시연과 Serial 외 프로토콜은 각각 별도 검증 대상이다.

## 한 문장 목표

물리 장비를 EdgeX Device Service와 Device/Profile로 일관되게 추상화하고, 디바이스-서비스 연결과 실제 telemetry 상태를 대시보드에서 운영 관점으로 통합 가시화한다.

```text
센서 / PLC / 장비
  -> 프로토콜별 EdgeX Device Service
  -> 중앙 EdgeX internal MessageBus / Core Data / Metadata / Command
  -> PostgreSQL / Application Service / AI consumer / dashboard

KubeEdge
  -> 엣지 노드와 Device Service·AI workload 배치/상태 관리
```

MQTT는 EdgeX의 전제조건이 아니다. MQTT-only 장비나 명시적인 로컬 pub/sub 요구가 있을 때만 broker를 배치한다. Serial, Modbus, OPC-UA, I2C 직접 연결에는 해당 프로토콜 Device Service를 사용한다. 카메라 frame은 요청 시 Workflow Pod가 RTSP를 직접 구독하고 상태·분석 결과 metadata만 EdgeX Event로 전달할 수 있다.

## 대시보드에서 확인할 질문

1. Core Metadata에 어떤 Device Service, Device Profile, Device가 등록되어 있는가?
2. Device Service가 실제 endpoint를 소유하고 `adminState`/`operatingState`를 보고하는가?
3. Core Data에 최신 Event/Reading이 있고 freshness가 정상인가?
4. 어떤 AI 서비스, 저장소, dashboard consumer가 같은 device identity를 사용하는가?
5. 관련 node/workload 상태는 KubeEdge에서 어떻게 보이는가?

## 최신성 판단 원칙

- 사용자 승인과 실제 root render, 테스트, live read-only 증거를 우선한다.
- `html/`은 `scripts/build-docs-html.py`로 만드는 생성물이며 직접 편집하지 않는다.
- `superpowers/`와 `archive/`는 현재 완료 상태의 근거가 아니다.
- 동적 workflow/offloading/agent-assisted planning은 별도 범위 승격과 검증 전까지 후속 고도화다.
