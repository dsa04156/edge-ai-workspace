## 문서가 답해야 하는 질문

- 어떤 PLC·MES·센서가 어떤 EdgeX Device/Profile에 연결됐는가?
- Event가 엣지 outbox와 중앙 Core Data에 저장됐는가?
- 품질 판별·펌프/모터 이상감지 서비스가 어떤 입력과 모델을 사용하는가?
- 결과·알림·KPI를 어디서 조회하는가?
- 장애가 Protocol Adapter, outbox, gateway, Core Data, AI consumer 중 어디에서 발생했는가?
- 현재 구현과 2차년도 설계, 과거 workflow 실험을 어떻게 구분하는가?

## 권위 데이터 흐름

```text
물리 센서 / PLC / 카메라
  -> Protocol Adapter
  -> canonical EdgeX Event
  -> edge-telemetry-agent / SQLite WAL outbox
  -> HTTPS/mTLS ingest gateway
  -> EdgeX Core Data / PostgreSQL
  -> 품질 판별·이상감지 서비스 / state-aggregator / dashboard

KubeEdge/Kubernetes
  -> 엣지 노드·워크로드 배치와 운영 진단
```

## 현재 구현의 사실과 한계

- root 배포 진입점은 `edgex/k8s/kustomization.yaml`이다.
- 중앙 EdgeX Core 서비스와 PostgreSQL은 서버 노드에 배치된다.
- edge agent는 direct 입력, SQLite outbox, HTTPS/mTLS 업로드 계약을 가진다.
- `state-aggregator`의 physical inventory·telemetry authority는 EdgeX Core Metadata/Core Data다.
- dashboard workflow 화면은 현재 browser-local dry-run/preview다.
- 모든 protocol, discovery/controller, AI 서비스, live cutover는 실제 endpoint와 테스트 증거가 있을 때만 완료로 표시한다.

## 생성 HTML 확인

```bash
python3 scripts/build-docs-html.py
python3 tools/docs_consistency/generate_report.py
```

`docs/html/`은 로컬 생성물이며 라이브 웹 배포와 다르다. 원본 Markdown을 먼저 수정하고 HTML을 다시 생성한다.
