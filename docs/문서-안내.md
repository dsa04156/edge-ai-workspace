# 문서 안내

이 디렉터리는 EdgeX 기반 물리 디바이스 관리와 KubeEdge 기반 엣지 노드·워크로드 관리를 결합한 엣지 AI 플랫폼 PoC 문서의 단일 진입점이다. 처음 읽을 때는 `wiki/지식-지도.md`에서 목적에 맞는 최신 기준 문서를 찾는다.

## 현재 상태

2026-07-23 기준 중앙 `edgex-system`에는 EdgeX Core Keeper, Core Metadata, Core Data, Core Command, 내부 MessageBus, PostgreSQL과 ingest gateway가 유지된다. `edgex-edge`의 과거 커스텀 `edgex-edge-agent-jetson`, `edgex-edge-agent-sensehat`, 전용 SQLite outbox PVC와 Agent 전용 Metadata bootstrap은 퇴역했다.

현재 root render는 공식 EdgeX Device SDK 기반 `device-serial-jetson`과 `device-sensehat-raspi`를 각각 `etri-dev0001-jetorn`, `etri-dev0003-raspi5`에 배치한다. Jetson은 Arduino Uno를 `/dev/arduino-001`에서 한 번 읽어 6개 `virtual-*-001` Device로 분리하고, Raspberry Pi는 Sense HAT v1을 `/dev/i2c-1`에서 직접 읽어 환경 3개와 IMU 3개의 가상 Device로 분리한다. 물리 source ID `arduino-001`, `sensehat-001`은 protocol/tag metadata이며 aggregate Core Metadata Device가 아니다.

두 Device Service에는 공통 제네릭 ring cache 기반의 휘발성 메모리 cache가 있다. Device/resource별 최근 10분·최대 10,000 sample을 보존하고, 각 서비스의 sample slot 할당 합계를 67,108,864 bytes(64MiB)로 제한한다. Core Command는 이 cache의 최신값을 반환하고, 같은 node의 consumer는 각 Service FQDN의 Local Data API로 최신값과 최근 구간을 읽을 수 있다. `/api/v3/localdata/stats`와 EdgeX custom metrics 네 개가 sample, series, 할당 bytes와 eviction을 노출한다. Jetson에는 고정 서비스 데모 workload `sensor-anomaly-demo`가 배치되어 Arduino 가속도 X/Y/Z의 같은 `origin` sample을 500ms polling으로 묶고 `online-gaussian-baseline-v1` 변화 점수를 계산한다. `state-aggregator`는 이 결과를 `/state/service-demo`로 읽어 대시보드에 표시한다.

cache는 Pod 재시작 시 초기화되며 SQLite outbox나 중앙 장애 재전송 queue가 아니다. 64MiB는 sample ring slot만 계산한 상한이고 Go runtime·map·응답 버퍼까지 포함한 Pod 전체 메모리 상한은 아니다. 로컬 MQTT broker, Agent, 별도 InfluxDB와 actuator write도 없다. Local Data API client label은 현재 Flannel CNI에서 강제되는 보안 경계가 아니며 endpoint는 unauthenticated read-only다. 과거 Event는 중앙 Core Data/PostgreSQL에서 조회한다. 대시보드에서 Device를 선택하면 `state-aggregator`의 이력 API가 Core Data를 조회하며 PostgreSQL에 직접 SQL을 실행하지 않는다. 기본 30분과 5분·1시간·24시간 범위를 선택할 수 있고, 최신 1,000 Event 제한과 실제 반환 구간을 함께 표시한다. Serial/I2C 정상 경로와 driver/reader 장애 복구는 live 검증했다. 실제 케이블·보드 손분리, 실제 장치 움직임에 의한 anomaly 현장 시연, Modbus와 OPC-UA는 별도 검증 대상이다. read-only 종합 점검은 `tools/verify_e2e.sh`를 사용한다.

중앙 저장 기준선은 `tools/edgex-core-data-loadtest/`와 일회성 인클러스터 실행기로 재현한다. 2026-07-22 현재 1,000 devices × 1 Event/분의 약 16.7 events/s는 1,000/1,000 저장, p95 16.17ms로 PASS했다. 반면 1,000 devices × 1Hz는 현재 Core Data limit 300m CPU/256Mi memory에서 OOMKilled로 실패했다. 따라서 안전한 기본 profile은 1/60Hz이며, 1Hz는 운영 절차에 명시한 별도 스트레스 시험이다. 이 도구는 Core Data REST → PostgreSQL 기준선이고 Device Service → MessageBus 전체 경로의 완료 근거가 아니다.

대시보드 `디바이스 관리`는 KubeEdge 노드를 먼저 선택한 뒤 해당 노드의 Adapter Runtime,
등록 hardware binding과 EdgeX Device를 함께 보여 준다. Git 연결 등록, EdgeX 장비 관측,
Device Service 통신과 Core Data 최신 Event를 서로 다른 상태로 표시한다. 선택 노드 범위에서 Runtime
재사용/검증 패키지 배포 plan, EdgeX Profile/Device 등록, Metadata readback과 first Event를 하나의
connection operation으로 관리한다. 노드는 workload 배치·운영 범위이며 Device inventory,
상태, telemetry와 command의 권위는 계속 EdgeX다. 기존 Serial/I2C Argo runtime은
조회·재사용만 하고, 별도 namespaced Controller가 Git allowlist로 만든 Runtime만
재시작·조건부 퇴역한다. 브라우저와 state-aggregator에는 Kubernetes 쓰기 권한이 없고 임의
image/hostPath/고정 IP, EdgeMesh 또는 KubeEdge Device CRD 변경 경로도 없다.
Modbus/OPC-UA/MQTT/RTSP는 검증 전까지 배포가 차단된다. Workflow Builder는 계속
browser-local dry-run이다.

등록 마법사는 연결 프로토콜과 Device Service를 먼저 선택하고, 선택 노드의 등록 hardware
binding과 Device Service 준비 방식을 뒤에서 결정한다. protocol package는 재사용 가능,
설치 가능, 연결 등록 필요, 검증 필요로 나뉘며 미검증 protocol은 선택할 수 없다. 같은 Serial 포트의 여러 resource와 서로 다른 등록
Serial 포트는 하나의 `device-serial-jetson`이 처리할 수 있다. 두 번째 USB Serial은 임의
`/dev/ttyUSB*` 입력으로 추가하지 않고 stable host identity, exact Pod 장치 마운트,
Adapter Controller binding과 `protocolProperties`가 있는 dashboard catalog를 Git에 먼저
등록해야 한다. 현재 live 등록 Serial binding은 `/dev/arduino-001` 한 개다.

## 한 문장 목표

물리 장비를 EdgeX Device Service와 Device/Profile로 일관되게 추상화하고, 디바이스-서비스 연결과 실제 telemetry 상태를 대시보드에서 운영 관점으로 통합 가시화한다.

```text
센서 / PLC / 장비
  -> 프로토콜별 EdgeX Device Service
  -> 중앙 EdgeX internal MessageBus / Core Data / Metadata / Command
  -> PostgreSQL / Application Service / AI consumer / dashboard

Jetson Arduino 가속도 X/Y/Z
  -> device-serial-jetson Local Data API
  -> sensor-anomaly-demo @ Jetson
  -> state-aggregator / service demo dashboard

KubeEdge
  -> 엣지 노드와 Device Service·AI workload 배치/상태 관리
```

MQTT는 EdgeX의 전제조건이 아니다. MQTT-only 장비나 명시적인 로컬 pub/sub 요구가 있을 때만 broker를 배치한다. Serial, Modbus, OPC-UA, I2C 직접 연결에는 해당 프로토콜 Device Service를 사용한다. 카메라 frame은 요청 시 Workflow Pod가 RTSP를 직접 구독하고 상태·분석 결과 metadata만 EdgeX Event로 전달할 수 있다.

## 대시보드에서 확인할 질문

1. Core Metadata에 어떤 Device Service, Device Profile, Device가 등록되어 있는가?
2. Device Service가 실제 endpoint를 소유하고 `adminState`/`operatingState`를 보고하는가?
3. Core Data에 최신 Event/Reading이 있고 freshness가 정상인가?
4. 선택한 Device의 저장 이력이 요청 범위와 실제 반환 구간에서 어떻게 보이는가?
5. 어떤 AI 서비스, 저장소, dashboard consumer가 같은 device identity를 사용하는가?
6. 관련 node/workload 상태는 KubeEdge에서 어떻게 보이는가?
7. 선택한 KubeEdge 노드에 어떤 Adapter Runtime과 EdgeX Device가 연결되어 있으며, Runtime의
   소유자와 재사용·배포·재시작·퇴역 조건은 무엇인가?

## 최신성 판단 원칙

- 사용자 승인과 실제 root render, 테스트, live read-only 증거를 우선한다.
- `html/`은 `scripts/build-docs-html.py`로 만드는 생성물이며 직접 편집하지 않는다.
- `superpowers/`와 `archive/`는 현재 완료 상태의 근거가 아니다.
- 동적 workflow/offloading/agent-assisted planning은 별도 범위 승격과 검증 전까지 후속 고도화다.
