## 현재 상태

2026-08-03 기준 중앙 `edgex-system`에는 EdgeX Core Keeper, Core Metadata, Core Data, Core Command, 내부 MessageBus, PostgreSQL과 ingest gateway가 유지된다. `edgex-edge`의 과거 커스텀 `edgex-edge-agent-jetson`, `edgex-edge-agent-sensehat`, 전용 SQLite outbox PVC와 Agent 전용 Metadata bootstrap은 퇴역했다.

현재 root render는 공식 EdgeX Device SDK 기반 `device-serial-jetson`과 `device-sensehat-raspi`를 각각 `etri-dev0001-jetorn`, `etri-dev0003-raspi5`에 배치한다. Jetson은 Arduino Uno를 `/dev/arduino-001`에서 한 번 읽어 기존 6개 `virtual-*-001` Device로 fan-out하고 승인 Saga에서 만든 aggregate Arduino Device 1개도 전환 identity로 유지한다. Raspberry Pi는 Sense HAT v1을 `/dev/i2c-1`에서 직접 읽어 환경 3개와 IMU 3개의 가상 Device로 분리한다. live Core Metadata의 총 13개 Device는 그대로 보존한다. 대시보드 `디바이스` 화면의 `센서 디바이스` 분류는 13개 identity를 이름·Available 상태·최신 Event·상세보기 열의 목록으로 표시하고, `장비 관리` 화면만 `arduino-001`, `sensehat-001` 두 물리 source 카드로 묶어 연결 작업을 제공한다.

두 Device Service에는 공통 제네릭 ring cache 기반의 휘발성 메모리 cache가 있다. Device/resource별 최근 10분·최대 10,000 sample을 보존하고, 각 서비스의 sample slot 할당 합계를 67,108,864 bytes(64MiB)로 제한한다. Core Command는 이 cache의 최신값을 반환하고, 같은 node의 consumer는 각 Service FQDN의 Local Data API로 최신값과 최근 구간을 읽을 수 있다. `/api/v3/localdata/stats`와 EdgeX custom metrics 네 개가 sample, series, 할당 bytes와 eviction을 노출한다. Jetson에는 고정 서비스 데모 workload `sensor-anomaly-demo`가 배치되어 Arduino 가속도 X/Y/Z의 같은 `origin` sample을 500ms polling으로 묶고, 2초 이내 온도를 정렬해 진동·온도 feature 점수와 0.7/0.3 가중 종합 점수를 계산한다. 2026-08-03 immutable ARM64 rollout과 실제 입력 증가, 중앙 `/state/service-demo`, dashboard readback은 PASS했다. versioned 입력 계약, 개발용 Replay, model adapter와 application-owned SQLite 결과·알림 이력도 배포했으며 Jetson 1Gi RWO PVC bind와 Pod 재시작 전후 동일 origin readback을 확인했다. `state-aggregator`는 상태뿐 아니라 `/state/service-demo/results`, `/state/service-demo/alerts`를 read-only로 중계한다.

Device Service cache는 Pod 재시작 시 초기화되며 SQLite outbox나 중앙 장애 재전송 queue가 아니다. `sensor-anomaly-demo`의 SQLite는 이 cache와 다른 AI 파생 결과 전용 저장소다. 1Gi RWO PVC로 결과와 알림 전환을 보존하지만 원시 Event 재전송이나 중앙 HA 저장을 제공하지 않는다. 64MiB는 sample ring slot만 계산한 상한이고 Go runtime·map·응답 버퍼까지 포함한 Pod 전체 메모리 상한은 아니다. 로컬 MQTT broker, Agent, 별도 InfluxDB와 actuator write도 없다. Local Data API client label은 현재 Flannel CNI에서 강제되는 보안 경계가 아니며 endpoint는 unauthenticated read-only다. 과거 Event는 중앙 Core Data/PostgreSQL에서 조회한다. 대시보드에서 Device를 선택하면 `state-aggregator`의 이력 API가 Core Data를 조회하며 PostgreSQL에 직접 SQL을 실행하지 않는다. 기본 30분과 5분·1시간·24시간 범위를 선택할 수 있고, 최신 1,000 Event 제한과 실제 반환 구간을 함께 표시한다. Serial/I2C 정상 경로와 driver/reader 장애 복구는 live 검증했다. 실제 케이블·보드 손분리와 실제 장치 움직임에 의한 anomaly 현장 시연은 별도 검증 대상이다. Modbus는 자동 discovery나 실제 PLC 지원이 아니라, 운영자가 선언한 고정 개발 simulator endpoint의 Unit 1·2에 대해 공식 EdgeX `device-modbus:4.0.2`를 승인·배포하고 Core Data 첫 Event와 대시보드 `available` 상태까지 과거 live 검증했다. 해당 Controller Runtime은 현재 퇴역했고 root 운영 render에도 없다. 실제 PLC, 임의 endpoint와 Modbus network discovery, OPC-UA는 여전히 별도 검증 대상이다. read-only 종합 점검은 `tools/verify_e2e.sh`를 사용한다.

중앙 저장 기준선은 `tools/edgex-core-data-loadtest/`와 일회성 인클러스터 실행기로 재현한다. 2026-07-22 현재 1,000 devices × 1 Event/분의 약 16.7 events/s는 1,000/1,000 저장, p95 16.17ms로 PASS했다. 반면 1,000 devices × 1Hz는 현재 Core Data limit 300m CPU/256Mi memory에서 OOMKilled로 실패했다. 따라서 안전한 기본 profile은 1/60Hz이며, 1Hz는 운영 절차에 명시한 별도 스트레스 시험이다. 이 도구는 Core Data REST → PostgreSQL 기준선이고 Device Service → MessageBus 전체 경로의 완료 근거가 아니다.

대시보드 `디바이스 관리`는 KubeEdge 노드를 먼저 선택한 뒤 해당 노드의 Adapter Runtime,
등록 hardware binding과 EdgeX Device를 함께 보여 준다. Git 연결 등록, EdgeX 장비 관측,
Device Service 통신과 Core Data 최신 Event를 서로 다른 상태로 표시한다. 선택 노드 범위에서 Runtime
재사용/검증 패키지 배포 plan, EdgeX Profile/Device 등록, Metadata readback과 first Event를 하나의
connection operation으로 관리한다. 노드는 workload 배치·운영 범위이며 Device inventory,
상태, telemetry와 command의 권위는 계속 EdgeX다. 기존 Serial/I2C Argo runtime은
조회·재사용만 하고, 별도 namespaced Controller가 Git allowlist로 만든 Runtime만
재시작·조건부 퇴역한다. 브라우저와 state-aggregator에는 Kubernetes 쓰기 권한이 없고 임의
image/hostPath/고정 IP, EdgeMesh 또는 KubeEdge Device CRD 변경 경로도 없다.
Modbus는 exact 개발 simulator binding에만 `template-verified` 배포가 허용된다.
MQTT는 노드별 등록 network binding, 허용 broker 범위와 공식
`device-mqtt:4.0.2` immutable image를 묶은 개발용 `template-verified` package를 제공한다.
실제 PLC binding, 운영 MQTT TLS/인증, OPC-UA와 RTSP는 검증 전까지 배포가 차단된다.
과거 AI Pipeline/Workflow Builder와 전용 샘플 미리보기 API는 제거했다. 2026-07-31의
새 `서비스 설계`는 실제 EdgeX Device/DeviceResource를 센서 입력으로 사용하는
browser-local validation·dry-run 프로토타입이다. 상단에는 `/state/services`가 반환하는
현재 운영 서비스 목록을 읽기 전용으로 표시한다. 현재 목록은 고정
`sensor-anomaly-demo` 1개이며 응답 장애 시에도 항목을 숨기지 않고 점검 상태로 남긴다.
각 서비스는 이름과 상태만 나열하지 않고 `센서 입력 → 전처리 → AI 분석 → 결과`의
4단계 요약 흐름, 실행 위치, 물리 소스부터 Device Service까지의 수집 경로와 현재 입력·모델
상태를 함께 표시한다. 이 요약은 서비스가 공개한 versioned 계약에서 만들며 계약이 없는
서비스의 구조를 추정하지 않는다.
목록의 `설계 편집`을 누르면 이 서비스가 공개한 versioned 설계 계약을 10개 단계의
브라우저 편집 초안으로 복사한다. 단계·연결·설정·이름을 수정하고 서비스별로 저장·검증할
수 있지만 실제 Deployment와 EdgeX 상태는 바꾸지 않는다. 계약이 없는 서비스는 임의
graph를 만들지 않는다. 기존 일반 초안은 보존되며 `기존 초안으로 돌아가기`로 복구하고,
서비스 초안은 `원본으로 초기화`할 수 있다.
왼쪽에는 EdgeX 입력 2종, 전처리 6종, 추론 3종, 점수 결합 1종과 결과 1종의 검색 가능한
13종 설계 블록을 표시하며 실제 입력 수와 설계용
계약을 구분한다. `3축 데모`는 가속도 X/Y/Z → 벡터 크기 → 온라인 이상 점수 →
대시보드 흐름을, `복합 점수 예시`는 진동 특징과 온도 구간 특징 → 개별 점수 → 종합 점수
흐름을 만들고 실측 입력을 같은 Jetson에 바인딩한다.
실행·배포 기능은 없다. 고정
`sensor-anomaly-demo`만 같은 노드의 Device Service Local Data API를 직접 사용한다.
등록 현황은 등록 장비를 먼저 보여 주고 `장비 연결`을 유일한 신규 연결 진입점으로 둔다.
전역 `간편 보기`/`전체 보기` 구분은 사용하지 않는다. `운영 현황`은 전체 상태, 핵심 KPI,
현재 서버·물리 디바이스 자원 관측과 확인할 항목을 우선 표시하고 플랫폼 기술 지표는
접어 둔다. 서버 상태와 물리 디바이스 상태는 `/state/dashboard`의 동일 node snapshot을
`node_type`으로 분리해 평균 CPU·메모리, GPU 관측 대수, pressure 주의 대수와 노드별
현재 meter를 표시한다. 이는 Prometheus/Kubernetes의 현재 관측값이며 과거 시계열이나
Grafana embed가 아니다. 고정 서비스 데모는 같은 화면의 접힌 보조 영역에서 필요할
때만 펼친다.
`디바이스`는 다음 네 분류를 한 화면의 간결한 목록으로 제공한다.

- `엣지 AI 서버`: `/state/nodes`의 `node_type=cloud_server|server`
- `물리 디바이스`: `/state/nodes`의 나머지 Jetson·Raspberry Pi 엣지 노드
- `가상 디바이스`: `/state/virtual-resources`의 자원증강형 논리 자원
- `센서 디바이스`: `/state/devices`의 EdgeX Core Metadata Device

모든 분류는 이름·상태·최신 관측 또는 이벤트·상세보기만 먼저 보여 준다. 센서의
프로필·수집 서비스·프로토콜·Core Data 이력과 노드/가상 자원의 세부 관측값은 행의
`상세보기` 패널에서 확인한다. 가상 디바이스 목록은 읽기 전용 상태 표시이며 동적
Workflow 실행 완료를 뜻하지 않는다. 서비스 연결 구조도 필요할 때만 펼친다. 375px,
768px, 1024px viewport에서 가로 overflow와 텍스트 잘림을 회귀 검증한다.
웹에서 생성한 Device Profile은 바로 다음 프로필 영역에 표시되며 전체 Core Metadata
Profile은 장비 연결 단계에서 선택한다. `프로필 생성`은 읽기 전용 resource 계약 검증과
idempotent 생성/readback을 제공한다. Profile만으로 parser, Device Service image,
hardware binding이나 후보 승인을 만들지는 않는다.

노드별 장비 발견과 등록은 일반 `edge-device-discovery`, dev0003 I2C 전용
`edge-device-discovery-i2c`와 `edgex-adapter-controller`가 담당한다. Agent는 중앙
SQLite에 직접 쓰지 않고 node별 Discovery Plan을 읽어 stable Serial identity와 허용된
I2C identity만 protocol-scoped HMAC report한다. 일반 Serial Agent는 세 edge node에
배치되고 dev0003에서는 I2C Agent와 병행한다.
Controller는 1Gi PVC의 SQLite에 candidate, 상태 전이, Plan, 승인, Registration Saga와
audit를 영속 저장한다. 기존 후보 ConfigMap은 최초 기동 때 한 번 import할 뿐 더 이상
권위 저장소가 아니다. 후보는 운영자 승인과 외부 인증, 실제 Runtime image digest,
Core Metadata readback, Core Data 첫 Event를 모두 통과한 뒤에만 `EVENT_CONFIRMED`가 된다.
Serial PTY 종단 테스트를 완료했고, I2C는 Sense HAT v1의 네 chip ID를 한 composite
identity로 확인하는 실장비 probe와 승인 후 기존 Runtime/Profile/Device 재사용,
신규 first Event까지 live 검증했다. 이 증거는 dev0003 Sense HAT v1 한 모델에 한정한다.
dev0003에 연결된 CH340 USB Serial `1a86:7523`은 passive 후보로 live 확인했다.
이 장비를 MPU6050 6축 IMU로 연결하기 위한 exact Raspberry Pi hardware binding,
`mpu6050-imu-v1` Profile/parser와 Controller 배포 template을 Catalog에 추가했다.
보드는 ESP32-D0WD-V3로 식별했고 운영 firmware flash와 Serial 상태 출력까지 확인했다.
MPU6050은 I2C ACK와 첫 Core Data Event를 만들지 못한 상태에서 2026-07-30 실물을
분리했다. 후보는 `STALE`/`ignored` 감사 이력으로 보존되어 기본 운영 목록에서는
숨겨지고 활성 동적 Runtime은 없다. Catalog/Profile/parser는 이후 재연결 실험을 위한
dormant 지원 코드다.
MQTT 자기등록 discovery subscriber는 아직 없다. 대신 운영자가 대시보드 `장비 연결`에서
허용된 broker 주소, 수신 topic, QoS와 Device의 command topic/resource를 입력하면 기존
Runtime 재사용 또는 검증 `device-mqtt` 배포, bundled 읽기 전용 Profile 생성, Device 등록과
첫 Event 확인을 한 connection operation으로 수행한다. 개발 broker/publisher는
`edgex/k8s/overlays/development/mqtt-simulator`의 선택적 fixture이며 root 운영 render에는
포함되지 않는다.
Modbus는 수동 개발 endpoint와 공식 Device Service 등록 Saga 테스트만 있으며 scanner는
없다. OPC-UA/ONVIF scanner도 미구현 상태를 오류로 명시한다.
현재 PoC root 배포의 대시보드와 `/management/*` BFF에는 운영자 Bearer token이 없다.
모든 관리 mutation은 기능 플래그, 서버 검증과 요청별 `Idempotency-Key`를 적용하고,
state-aggregator와 Adapter Controller 사이의 내부 HMAC은 유지한다. 후보 승인 단계의
외부 AuthProvider는 장비 신뢰 검증이며 운영자 로그인 수단이 아니다. 따라서 현재 경로는
접근이 제한된 개발 테스트베드용이고, 운영 노출 전에는 Ingress 앞에 별도 사용자 인증·인가를
추가해야 한다.

등록 마법사는 연결 프로토콜과 Device Service를 먼저 선택하고, 선택 노드의 등록 hardware
binding과 프로토콜별 연결 설정을 뒤에서 결정한다. 사용자는 Runtime mode를 고르지 않으며
서버가 기존 Runtime을 재사용하고 없으면 검증 template만 배포한다. 마지막
`검증하고 연결` 한 번으로 validation, Device Service 준비, EdgeX Profile/Device 등록과
첫 Event 확인을 순서대로 실행한다. protocol package는 재사용 가능,
설치 가능, 연결 등록 필요, 검증 필요로 나뉘며 미검증 protocol은 선택할 수 없다. 같은 Serial 포트의 여러 resource와 서로 다른 등록
Serial 포트는 하나의 `device-serial-jetson`이 처리할 수 있다. 두 번째 USB Serial은 임의
`/dev/ttyUSB*` 입력으로 추가하지 않고 stable host identity, exact Pod 장치 마운트,
Adapter Controller binding과 `protocolProperties`가 있는 dashboard catalog를 Git에 먼저
등록해야 한다. 현재 실측 완료 Serial telemetry binding은 Jetson의 `/dev/arduino-001`
한 개다. dev0003의 `/dev/mpu6050-001` binding은 코드·자동 테스트·ESP32 상태 출력
이력만 남아 있고 실물이 분리되어 현재 배포·telemetry 완료 경로가 아니다.

현장 read-only 판정은 두 도구로 나눈다. `tools/verify_e2e.sh`는 전체 정상 경로를 점검하고,
`tools/verify_sensor_service_demo.py`는 실제 움직임 anomaly와 Serial 분리·복구 상태 전이를
판정해 JSON 증거를 남긴다.

## 한 문장 목표

물리 장비를 EdgeX Device Service와 Device/Profile로 일관되게 추상화하고, 디바이스-서비스 연결과 실제 telemetry 상태를 대시보드에서 운영 관점으로 통합 가시화한다.

```text
센서 / PLC / 장비
  -> 프로토콜별 EdgeX Device Service
  -> 중앙 EdgeX internal MessageBus / Core Data / Metadata / Command
  -> PostgreSQL / Application Service / AI consumer / dashboard

Jetson Arduino 가속도 X/Y/Z
  -> device-serial-jetson Local Data API
  -> sensor-anomaly-demo @ Jetson
  -> state-aggregator / service demo dashboard

KubeEdge
  -> 엣지 노드와 Device Service·AI workload 배치/상태 관리
```

MQTT는 EdgeX의 전제조건이 아니다. MQTT-only 장비나 명시적인 로컬 pub/sub 요구가 있을 때만 broker를 배치한다. Serial, Modbus, OPC-UA, I2C 직접 연결에는 해당 프로토콜 Device Service를 사용한다. 카메라 frame은 요청 시 Workflow Pod가 RTSP를 직접 구독하고 상태·분석 결과 metadata만 EdgeX Event로 전달할 수 있다.

## 최신성 판단 원칙

- 사용자 승인과 실제 root render, 테스트, live read-only 증거를 우선한다.
- `html/`은 `scripts/build-docs-html.py`로 만드는 생성물이며 직접 편집하지 않는다.
- `superpowers/`와 `archive/`는 현재 완료 상태의 근거가 아니다.
- 동적 workflow/offloading/agent-assisted planning은 별도 범위 승격과 검증 전까지 후속 고도화다.
