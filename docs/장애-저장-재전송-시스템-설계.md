# 장애 저장·재전송 시스템 설계

> 상태: 1차 설계 제안, 미구현
>
> 기준일: 2026-08-25
>
> 이 문서는 2차년도 장애 저장·재전송 기능의 구현 전 설계안이다. 현재 Serial·I2C
> 운영 경로가 이 구조로 전환됐다는 뜻이 아니다. 운영 범위로 승격하기 전
> `프로젝트-범위.md`, `저장소-구조.md`, `단계별-추진계획.md`에 소유권과 검증 기준을
> 먼저 반영한다.

## 1. 목표

현장 네트워크나 중앙 EdgeX가 일시적으로 사용할 수 없더라도 Device Service가 이미
정상 decode·validation한 telemetry를 노드 로컬 디스크에 보존하고, 연결 복구 후 중앙
EdgeX Core Data에 중복 없이 재전송한다.

완료를 주장하려면 다음을 증명해야 한다.

1. 설정된 용량·장애 시간 범위 안에서 승인된 sample을 조용히 폐기하지 않는다.
2. 중앙 ACK는 MessageBus publish나 HTTP 수신이 아니라 Core Data 저장 완료를 뜻한다.
3. 동일 Event 재전송은 같은 payload면 deduplicate하고, 다른 payload면 conflict로 격리한다.
4. Pod 재시작 후에도 미확인 Event와 재시도 순서를 복구한다.
5. 물리 Device 상태, 중앙 전달 상태와 AI 서비스 상태를 서로 다른 축으로 표시한다.

## 2. 현재 제약

- 물리 inventory와 telemetry의 최종 권위는 EdgeX Core Metadata/Core Data다.
- KubeEdge는 node/workload 관리에만 사용한다.
- Device Service Local Data API는 bounded memory cache이며 durable outbox가 아니다.
- `edgex/telemetry-plane`의 과거 edge Agent는 운영 경로로 복원하지 않는다.
- 중앙 ingest gateway의 검증된 inbox·Core Data reconciliation 개념은 재사용할 수 있지만,
  현재 Serial·I2C 경로에 참여시키려면 별도 범위 승인이 필요하다.
- EdgeX Device SDK v4의 `AsyncValuesChannel`은 driver에 Core Data 저장 ACK를 반환하지 않는다.
  SDK의 MessageBus publish 성공은 중앙 PostgreSQL 저장 완료 증거가 아니다.

## 3. 대안 비교와 결정

| 대안 | 장점 | 결정 사유 |
|---|---|---|
| SDK publish 후 Core Data polling | 현재 경로 변경이 작음 | driver가 SDK 생성 Event ID를 알 수 없고, 확인 timeout 뒤 재발행하면 duplicate race가 생기므로 채택하지 않음 |
| 과거 edge Agent/outbox 복원 | 구현·시험 이력이 있음 | 현재 Device Service 직접 수집 경계와 충돌하고 병행 fallback을 만들므로 채택하지 않음 |
| edge-local MQTT broker 추가 | QoS 1과 persistent session 사용 가능 | Serial·I2C 직접 Device Service에 MQTT를 강제하는 현재 금지 경계와 충돌하므로 채택하지 않음 |
| Device Service 내장 outbox + 중앙 persisted-ack gateway | 물리 연결 소유권을 유지하면서 stable Event ID, dedupe와 명시적 저장 ACK 제공 | **1차 권고안** |

권고안은 과거 Python edge Agent를 되살리는 것이 아니다. 현재 공식 SDK Device Service
프로세스 안에 작은 `ReliableEventSink`를 넣고, 중앙 gateway의 persisted-ack 계약만
사용한다.

## 4. 목표 구조

```text
물리 PLC·센서
  → EdgeX Device Service driver
      → decode / type / unit / origin validation
      → canonical EdgeX v3 Event 생성
      → SQLite outbox commit
          ├─ Local Data recent cache 반영
          └─ reliable forward worker
                → HTTPS + mTLS/HMAC
                → 중앙 ingest gateway
                    → PostgreSQL inbox reserve/dedupe
                    → EdgeX Core Data POST/reconcile
                    → persisted ACK
                ← HTTP 201 persisted
          → local delivery ledger ACK 기록

EdgeX Core Data / PostgreSQL
  → state-aggregator / dashboard / AI consumer

Kubernetes/KubeEdge
  → Device Service Pod·PVC·node placement 관리
```

중앙 gateway와 inbox는 transport 신뢰성과 idempotency를 소유할 뿐 telemetry 권위가 아니다.
최종 Event/Reading과 freshness 권위는 계속 Core Data다.

## 5. 구성요소 책임

### 5.1 Device Service driver

- 물리 endpoint를 단독으로 open하고 sample을 decode한다.
- Device Profile 계약에 맞춰 resource, value type, unit과 `origin`을 검증한다.
- 하나의 물리 sample을 현재와 동일한 기능별 EdgeX Device/Event로 fan-out한다.
- outbox admission이 성공한 sample만 Local Data cache에 반영한다.
- outbox가 full 또는 unavailable이면 조용히 우회하지 않고 delivery 상태를 `blocked`로 둔다.

### 5.2 ReliableEventSink

- canonical Event와 deterministic ID를 생성한다.
- SQLite transaction으로 Event를 먼저 저장한다.
- stream별 FIFO, claim lease와 fencing token을 관리한다.
- 재시도 가능한 오류와 영구 계약 오류를 분리한다.
- ACK된 Event의 짧은 delivery ledger를 유지해 동일 sample 재입력을 식별한다.
- reliable delivery가 활성화된 Event는 기존 SDK async telemetry channel로 동시에 보내지
  않는다. SDK는 Metadata 연동, Device 상태, read command와 service lifecycle에 계속
  사용하며 telemetry transport만 `ReliableEventSink`가 소유한다.

첫 구현은 `device-serial-jetson` 안의 내부 package로 검증한다. Serial 수직 슬라이스가
통과한 뒤 Sense HAT에 적용하면서 공통 package 추출 여부를 결정한다. 검증 전부터 두 Go
module을 억지로 공통화하지 않는다.

### 5.3 중앙 ingest gateway

- edge identity와 request 서명을 검증한다.
- `(edge_id, event_id)`와 payload hash를 inbox에 먼저 저장한다.
- 같은 ID·같은 payload는 idempotent replay로 처리한다.
- 같은 ID·다른 payload는 `409 conflict`로 격리한다.
- Core Data POST 결과가 불확실하면 Event ID로 reconcile한다.
- Core Data 저장을 확인한 뒤에만 `201 persisted`를 반환한다.

### 5.4 state-aggregator와 dashboard

- EdgeX Device availability와 delivery 상태를 합치지 않는다.
- `buffering`, `replaying`, `blocked`, `quarantined`를 별도 delivery rail로 표시한다.
- queue 크기, oldest age, 재전송률, conflict와 admission rejection을 reason과 함께 표시한다.

## 6. Event identity와 중복 계약

### 6.1 stable identity

Event ID는 고정 namespace를 사용하는 UUIDv5로 생성한다.

```text
eventId = UUIDv5(
  edgeai-event-v1,
  deviceName | sourceName | readingOrigin
)
```

- 현재 fan-out 구조에서는 Event 하나가 기능별 Device/resource 하나를 가진다.
- 같은 identity로 payload가 달라지면 덮어쓰지 않고 conflict다.
- payload hash에는 profile, device, source, origin, reading resource, type, value, unit과
  허용된 tags를 포함한다.
- 비밀번호, token과 endpoint credential은 Event/tags에 넣지 않는다.
- Reading ID도 `eventId | resourceName`으로 deterministic하게 생성한다.

현장 계약에서 하나의 Event에 여러 Reading을 묶기로 바뀌면 ID 입력에 contract version과
frame identity를 추가하고 schema version을 올린다.

### 6.2 delivery semantics

외부 계약은 `at-least-once transport + idempotent central persistence`다. 중앙 gateway의
inbox와 stable Event ID가 정상인 범위에서는 동일 Event가 Core Data에 두 번 생성되지
않는다. 인증서 손실, PVC 손실 또는 운영자가 DB를 수동 변경한 경우까지 exactly-once를
주장하지 않는다.

## 7. Edge outbox schema

### 7.1 `outbox_event`

| column | 의미 |
|---|---|
| `event_id` | deterministic UUID, primary key |
| `stream_key` | `deviceName/sourceName` |
| `stream_sequence` | stream별 단조 증가 순번 |
| `payload_json` | canonical EdgeX v3 Event |
| `payload_sha256` | conflict 판정용 hash |
| `payload_bytes` | 용량 계산 |
| `state` | `pending`, `inflight`, `retry_wait`, `quarantined` |
| `attempts` | 전송 시도 횟수 |
| `next_attempt_at` | 다음 재시도 가능 시각 |
| `lease_token`, `lease_until` | crash-safe claim과 fencing |
| `last_error_code`, `last_error` | bounded diagnostic |
| `created_at`, `updated_at` | queue age와 운영 추적 |

### 7.2 `delivery_ledger`

ACK된 `event_id`, payload hash, ACK 시각과 deduplicated 여부를 제한된 TTL 동안 유지한다.
원본 telemetry 장기 보관소가 아니며 TTL이 지나면 삭제할 수 있다.

SQLite는 WAL mode, `busy_timeout`, explicit transaction과 fsync 정책을 사용한다. 자격 증명과
원시 secret은 저장하지 않는다.

## 8. 상태기계

```text
CAPTURED
  → PENDING           SQLite commit 성공
  → ADMISSION_BLOCKED 용량·DB 오류, silent drop 금지

PENDING
  → INFLIGHT          lease 획득 후 전송

INFLIGHT
  → ACKED             정확한 201 persisted ACK
  → RETRY_WAIT        timeout, 429, 5xx, malformed ACK
  → AUTH_BLOCKED      401, 403
  → QUARANTINED       409 conflict, 422 contract rejection

RETRY_WAIT
  → INFLIGHT          backoff 만료

AUTH_BLOCKED
  → INFLIGHT          credential 복구와 운영자 확인 후
```

`ACKED` Event는 outbox에서 제거하고 ledger에 남긴다. `QUARANTINED`는 자동 삭제하지 않는다.
재시도 횟수가 많다는 이유만으로 unacknowledged Event를 폐기하지 않는다.

## 9. ACK API 계약

### 9.1 request

```http
POST /v1/ingest/events
Content-Type: application/json
X-Edge-Id: etri-dev0001-jetorn/device-serial-jetson
X-Edge-Timestamp: <unix-seconds>
X-Edge-Signature: <HMAC>
```

body는 canonical EdgeX v3 Event 한 건이다. gateway가 Core Data에 전달할 때
`AddEventRequest` envelope로 감싼다. 운영에서는 mTLS를 기본 transport identity로 사용하고
HMAC은 request integrity와 replay 방지에 사용한다.

### 9.2 성공 ACK

```json
{
  "edge_id": "etri-dev0001-jetorn/device-serial-jetson",
  "event_id": "11111111-1111-4111-8111-111111111111",
  "status": "persisted",
  "deduplicated": false
}
```

edge client는 다음을 모두 만족할 때만 ACK 처리한다.

- HTTP status가 정확히 `201`
- `edge_id`, `event_id`가 request와 일치
- `status=persisted`
- `deduplicated`가 boolean

`200`, `202`, body 누락과 identifier 불일치는 성공으로 취급하지 않는다.

### 9.3 오류 분류

| 응답 | edge 동작 |
|---|---|
| timeout, network error, 429, 5xx | exponential backoff + jitter 재시도 |
| 401, 403 | 전체 forward 중지, auth blocked |
| 409 | payload conflict 격리 |
| 422 | contract invalid 격리 |
| malformed 2xx | protocol error로 재시도 |

## 10. 순서와 재전송

- FIFO는 `deviceName/sourceName` stream 안에서만 보장한다.
- 한 stream의 앞 Event가 retry 중이면 뒤 Event가 추월하지 않는다.
- 다른 stream은 병렬 drain할 수 있다.
- 복구 시 신규 Event와 replay Event를 무제한 경쟁시키지 않고 replay quota를 둔다.
- AI 서비스의 다중 resource 정렬은 기존처럼 Reading `origin`을 사용한다.

기본 backoff 수치, parallel stream 수와 replay quota는 현장 sample rate와 장애 허용시간을
확정한 뒤 설정한다. 설계 문서에서 임의 수치를 운영값으로 고정하지 않는다.

## 11. 용량과 유실 경계

outbox는 row 수, payload bytes와 oldest age 세 축으로 제한한다.

- unacknowledged Event를 새 Event 때문에 삭제하지 않는다.
- high watermark부터 `buffering_capacity_warning`을 표시한다.
- hard limit에서는 신규 admission을 거부하고 `admission_rejected`를 증가시킨다.
- 물리 stream은 계속 진행될 수 있으므로 hard limit 이후의 손실 가능성을 숨기지 않는다.
- “데이터 유실 0건”은 합의된 sample rate와 장애 지속시간에 맞춘 capacity window 안에서만
  검증한다.

PVC는 node-local RWO로 시작한다. 같은 node의 Pod 재시작은 보호하지만 node disk 손실과
node 교체까지 보호하는 HA 저장소는 1차 PoC 범위가 아니다.

## 12. Local Data와 AI 소비 경계

- SQLite commit이 성공한 뒤에만 동일 sample을 Local Data cache에 넣는다.
- 중앙 장애 중에도 edge AI는 Local Data cache를 계속 읽을 수 있다.
- Device Service 재시작 시 아직 pending이고 cache window 안인 Event는 cache를 재구성할 수 있다.
- ACK된 과거 Event 전체를 Local Data에 재주입하지 않는다.
- AI 결과는 `eventId` 또는 resource별 stable sample identity로 idempotent하게 저장한다.

## 13. 배포 설계

### edge Device Service

- `ReliableDelivery.Enabled=false`를 초기 기본값으로 둔다.
- canary overlay에서만 먼저 활성화한다.
- `/var/lib/edgex-device-service/outbox.db`에 RWO local-path PVC를 mount한다.
- read-only root filesystem과 최소 권한을 유지한다.
- gateway endpoint는 Kubernetes service DNS를 사용한다.
- mTLS key와 HMAC secret은 Kubernetes Secret으로 공급한다.

### central gateway

- `edgex-system`의 중앙 서버에 단일 배치한다.
- PostgreSQL inbox와 Core Data reconciliation을 유지한다.
- command bridge는 이 설계 범위에서 활성화하지 않는다.
- Core Data와 gateway 장애를 분리해 관측한다.

### NetworkPolicy

- Device Service에서 gateway HTTPS endpoint만 추가 허용한다.
- 기존 Core Keeper, Metadata와 MessageBus 접근은 SDK 운영을 위해 유지한다.
- Core Data를 edge에 직접 노출해 ACK를 우회하지 않는다.

## 14. 운영 API와 metric

Device Service read-only endpoint:

```text
GET /api/v3/local-data/outbox/stats
```

필수 metric:

- `delivery_outbox_pending`
- `delivery_outbox_bytes`
- `delivery_outbox_oldest_seconds`
- `delivery_events_enqueued_total`
- `delivery_events_acked_total`
- `delivery_retries_total`
- `delivery_quarantined_total`
- `delivery_conflicts_total`
- `delivery_admission_rejected_total`
- `delivery_ack_latency_seconds`
- `delivery_replay_throughput_per_second`

대시보드 상태:

| 상태 | 의미 |
|---|---|
| `healthy` | 최근 ACK 정상, backlog가 정상 범위 |
| `buffering` | 중앙 불가, 로컬 저장 중 |
| `replaying` | 연결 복구 후 backlog 감소 중 |
| `blocked` | auth, capacity 또는 local DB 문제 |
| `quarantined` | contract/conflict Event 존재 |
| `unknown` | metric/API 관측 실패 |

물리 Device는 central delivery가 막혀도 endpoint 통신이 정상이라면 `UP`일 수 있다. 화면은
`Device UP + delivery buffering`을 올바른 복합 상태로 표시해야 한다.

## 15. 장애 시험

| 시험 | 기대 결과 |
|---|---|
| gateway network 차단 | sample은 outbox에 증가하고 Local Data는 계속 제공 |
| 중앙 Core Data 중단 | gateway는 persisted ACK를 주지 않고 edge는 재시도 |
| gateway가 Core Data 저장 후 응답 유실 | 같은 Event 재전송을 중앙 inbox가 deduplicate |
| Device Service Pod 재시작 | pending queue와 stream 순서를 복구 |
| 같은 Event·같은 payload 재입력 | 중복 결과 없이 ACK |
| 같은 Event·다른 payload 재입력 | `409`, quarantine, 자동 덮어쓰기 없음 |
| malformed 201 ACK | edge Event를 삭제하지 않음 |
| SQLite hard limit | 기존 pending 보존, 신규 admission rejection과 경보 |
| credential 만료 | auth blocked, secret 복구 후 운영자 확인을 거쳐 재개 |
| replay 중 새 telemetry 유입 | quota에 따라 둘 다 진행하고 stream FIFO 유지 |

각 시험에서 captured, enqueued, ACKed, quarantined, rejected와 Core Data readback 수를 함께
기록한다. `data loss = captured - acked - pending - quarantined - rejected`처럼 분모와 상태를
명시하고 원인 불명 건을 0으로 숨기지 않는다.

## 16. 단계별 구현

### 단계 0: 설계 승인

- 이 문서의 gateway 재사용, ACK 의미와 용량 경계를 검토한다.
- 프로젝트 범위·저장소 구조·추진계획에 새 운영 경로를 반영한다.

### 단계 1: contract와 로컬 단위 시험

- Serial Device Service 내부 `ReliableEventSink` interface와 fake 구현
- deterministic Event builder
- SQLite outbox 상태기계·capacity·crash recovery 시험
- gateway ACK contract 시험

### 단계 2: Serial canary

- feature flag 기본 off
- canary overlay와 별도 PVC
- 중앙 정상 경로, 네트워크 단절, Pod 재시작 시험
- 기존 MessageBus 경로와 동시 publish하지 않음을 검증

### 단계 3: Sense HAT 적용

- Serial에서 검증된 계약만 재사용
- I2C resource fan-out과 stream ordering 시험
- 중복 코드가 실제로 확인된 뒤 공통 package 추출

### 단계 4: 운영 가시화

- state-aggregator delivery API
- dashboard buffering/replaying/blocked rail
- KPI와 runbook, 장애 시험결과서 연결

## 17. 완료 gate

1. immutable image와 GitOps manifest가 존재한다.
2. 정상 경로에서 기존 resource/type/origin과 동일한 Core Data Event를 확인한다.
3. 중앙 단절 동안 설정된 capacity window 안의 Event가 모두 로컬에 남는다.
4. 복구 후 동일 stable Event ID가 중앙에 한 번만 저장된다.
5. Pod 재시작 전후 pending 수와 stream sequence가 보존된다.
6. quarantine과 admission rejection이 원인·건수와 함께 노출된다.
7. AI 결과가 Event replay로 중복 생성되지 않는다.
8. dashboard가 Device availability와 delivery 상태를 독립적으로 표시한다.
9. 장애별 복구시간, 유실·중복·재처리 수가 시험결과서에 기록된다.

## 18. 명시적 제외

- KubeEdge Device/DeviceTwin을 telemetry authority로 사용
- edge-local MQTT broker를 Serial·I2C 필수 구성으로 추가
- 과거 edge Agent를 fallback으로 병행 배포
- unacknowledged Event의 자동 oldest-drop
- write command와 actuator command 저장·재전송
- dynamic workflow, 자동 offloading과 runtime migration
- node disk 장애까지 포함한 HA/DR 보장

## 19. 구현 전 확정할 항목

1. 옥동 source별 sample rate와 허용 가능한 최대 통신 단절시간
2. Event당 평균·최대 payload 크기와 PVC capacity
3. gateway mTLS 인증서 발급·회전 책임
4. auth blocked와 quarantine 해제 권한
5. ACK된 delivery ledger의 보존기간
6. replay drain rate와 중앙 Core Data 허용 부하
7. node disk 손실을 2차년도 시험 범위에 포함할지 여부
