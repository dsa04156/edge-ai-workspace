# 대시보드 판단 정책

## 권위와 표시 경계

대시보드는 물리 디바이스에 EdgeX를 단일 authority로 사용한다.

```text
physical Serial / I2C / MQTT / Modbus / OPC-UA / RTSP device
  -> protocol-specific EdgeX Device Service
  -> EdgeX Event / Reading -> Core Data
  -> AI services / storage / state-aggregator / dashboard
```

- inventory/state: EdgeX Core Metadata
- telemetry/freshness: EdgeX Core Data Event와 typed Readings
- command: 현재 비활성; 후속에는 해당 protocol adapter의 검증된 command 경로
- node/workload 관찰: Kubernetes/KubeEdge와 Prometheus

Kubernetes/KubeEdge node placement는 별도 display-only diagnostic이다. node 미할당, Node NotReady 또는 mapper Pod 상태로 physical device availability를 강등하지 않는다. KubeEdge Device/DeviceModel/DeviceStatus, MapperFramework, `mqttvirtual`, mapper direct-write 값은 legacy이며 화면/API의 current physical status/control fallback으로 병합하지 않는다.

이 문서 아래의 `virtual-temperature-001` payload는 현재 Serial 수직 슬라이스의 field 정규화 예시다. 물리 source `arduino-001`, `sensehat-001`은 tag/protocol metadata에만 남는다. 값과 timestamp는 시점에 따라 달라지며 live 판정은 API를 다시 조회한다.

## Inventory 표시

Core Metadata의 다음 필드를 device 응답과 detail에 표시한다.

- `name`
- `profileName`
- `serviceName`
- `protocols` (secret은 마스킹)
- `adminState`
- `operatingState`
- `tags`/properties의 선택적 node diagnostic

Core Metadata에 없는 KubeEdge Device를 current physical inventory에 합치지 않는다. optional node diagnostic이 없는 것은 inventory 또는 availability 오류가 아니다.

## Telemetry와 freshness

Core Data Event에서 다음 contract를 사용한다.

- `deviceName`: inventory join key
- `sourceName`: telemetry source/resource
- `origin`: nanoseconds 단위 event 시각
- typed Readings: `valueType`과 값

freshness 기준은 배포 설정의 EdgeX event threshold이며 최신 유효 Event의 nanosecond `origin` sample 시각에 적용한다. API 조회 시각, legacy DeviceStatus heartbeat 또는 mapper heartbeat로 대신하지 않는다. origin이 없거나 parse 불가하면 fresh로 추정하지 않고 degraded reason을 표시한다.

Telemetry detail은 `deviceName`과 `sourceName`, event origin, typed readings를 보존한다. Device detail의 저장 그래프는 `state-aggregator`를 거쳐 Core Data API에서 읽으며 dashboard가 PostgreSQL에 직접 연결하지 않는다. storage graph나 AI 결과는 Core Data 이후 consumer 결과로 표시하며 physical source authority를 바꾸지 않는다.

## 노드별 디바이스 관리 판단 경계

`디바이스 관리`는 EdgeX 권위를 대체하지 않는 관리 UI다. 화면의 노드 카드는
`/state/nodes`, Runtime `targetNode`, Device `node_name`과 등록 hardware binding을 묶는
운영 범위 선택기다. 노드 상태가 비정상이거나 미관측이어도 그 사실만으로 EdgeX Device의
availability를 변경하지 않는다. Adapter Catalog의 `installed` 표시는 지원 계약이고, 실제
apply 가능 여부는 선택 노드의 등록 hardware binding, package 검증 상태, Core Metadata의
동일 `serviceName` Device Service 존재 또는 검증된 배포 plan,
`adminState=UNLOCKED` readback까지 확인한다. dry-run 결과만으로 등록 완료나 protocol 지원
완료를 표시하지 않는다.

물리 연결 카드는 다음 상태를 합치지 않는다.

- `연결 등록`: Git Adapter Catalog allowlist에 있는가.
- `장비 관측`: 연결된 EdgeX Device가 `UP`이거나 fresh Event를 발행했는가.
- `통신 상태`: `adminState`/`operatingState`를 connected/disconnected/unknown으로 해석한 값.
- `데이터 상태`: Core Data latest Event가 fresh/stale/missing/unknown인지.

따라서 연결이 등록돼도 Device/Event 근거가 없으면 `장비 관측됨`으로 표시하지 않는다.
모든 연결 Device가 `DOWN` 또는 `LOCKED`면 `장비 미관측`, 근거가 불완전하면 `관측 근거
없음`이다. 발견 후보나 Kubernetes Node Ready를 이 physical presence·통신 판정으로 대신하지
않는다. 신규 연결은 `hardwareBindingId`를 EdgeX Device system tag로 보존하며
`physicalDeviceId`와 `nodeName`도 사용자 PATCH에서 바꾸지 않는다.

`장비 발견` 탭은 위 네 상태 앞의 onboarding staging이다.

- `present`: passive Agent의 최근 report에서 USB Serial stable path 또는 I2C 버스를 다시 봄
- `stale`: 후보나 node report가 설정된 기준 시간을 넘김
- `declared`: 운영자가 network/local endpoint 후보를 직접 선언함
- `pending`·`accepted`·`ignored`: 운영자의 검토 상태
- `registration-ready`: exact node/protocol/path가 Git hardware binding과 일치하고 package가
  검증되어 기존 등록 마법사로 넘길 수 있음
- `binding-required`·`verification-required`·`unsupported`: Git 변경이나 실장비 검증 전에는
  등록·설치로 넘길 수 없음

I2C `present`는 `/dev/i2c-N` 버스 파일 존재만 뜻하며 주소 응답이나 센서 모델을 증명하지
않는다. 수동 `declared`도 endpoint 도달성이나 자격 증명 검증을 뜻하지 않는다. 후보 승인,
무시와 삭제는 Core Metadata Device 수, `operatingState`, latest Event와 KPI를 변경하지
않는다. 자동 관측 후보 삭제는 재발견 가능한 사실을 지우는 대신 `ignored`로 표시한다.

- Profile/Device Metadata readback 성공은 `metadata_applied`다.
- 아직 Core Data Event가 없으면 `waiting_for_event`이며 실패나 available로 추정하지 않는다.
- 계약된 `deviceName` Event를 확인했을 때만 `verified`다.
- validation, Metadata mutation 또는 readback 불일치는 `failed`다.
- `DEVICE_MANAGEMENT_ENABLED=false`에서는 create/patch control을 사용할 수 없게 표시한다.
- `ADAPTER_RUNTIME_MUTATION_ENABLED=false`에서는 runtime 배포·재시작·퇴역과 이를 요구하는
  connection apply를 사용할 수 없게 표시한다.

노드 선택을 바꾸면 물리 연결 증거, Runtime inventory, protocol package, 기존 EdgeX Device와 연결 마법사의
target node가 같은 범위로 바뀐다. target node와 raw device path는 직접 입력하지 않는다.
관리 화면은 Device 강제 삭제, actuator command, 임의 Kubernetes workload와 EdgeMesh 상태
변경을 제공하지 않는다. 검증된 Adapter Controller 소유 runtime의 배포·재시작·조건부 퇴역만
별도 관리 경로로 제공한다. Workflow Builder의 browser-local bind/release와 execution plan
preview도 이 관리 상태와 분리하며 계속 dry-run으로 판단한다.

## Availability 판단 순서

State Aggregator와 dashboard는 다음 순서를 동일하게 사용한다.

1. `adminState=LOCKED`이면 `unavailable` / `disconnected`.
2. `operatingState=DOWN`이면 `unavailable` / `disconnected`.
3. `operatingState=UNKNOWN`이면 `degraded` / `unknown`.
4. `operatingState=UP`이고 최신 Core Data event가 freshness threshold 안이면 `available`.
5. `operatingState=UP`이지만 event가 없으면 `degraded` (`latest EdgeX event is missing`).
6. `operatingState=UP`이지만 최신 event가 stale이면 `degraded` (`latest EdgeX event is stale`).
7. 알 수 없는 state나 잘못된 event origin은 `degraded`와 구체적인 reason으로 표시한다.

node/workload 상태는 별도 card/filter에서 관찰한다. node 장애는 AI workload나 service availability에는 영향을 줄 수 있지만 위 physical availability 계산에는 gate로 넣지 않는다.

## KPI

physical-device KPI의 분모는 Core Metadata inventory다.

- registered device count: Core Metadata Device 수
- available/degraded/unavailable count: 위 availability 결과
- event freshness ratio: fresh latest Event device 수 / Core Metadata Device 수
- operating state breakdown: `UP` / `DOWN` / `UNKNOWN`
- admin state breakdown: `UNLOCKED` / `LOCKED`
- operator focus count: degraded/unavailable physical device 수. non-healthy node/workload는 별도 범주로 표시

legacy `device_status_freshness_ratio`, mapper readiness와 mapper direct-write freshness를 current physical-device KPI로 사용하지 않는다.

## Explain Panel

Device 선택 시 최소 표시값은 다음과 같다.

- overall status와 reason
- Core Metadata `name`, `profileName`, `serviceName`
- `adminState`, `operatingState`
- latest Event `sourceName`, origin, age/freshness
- typed Readings
- protocol 요약
- 선택적 node diagnostic
- 저장 이력 범위 제어(5분·30분·1시간·24시간), 새로고침, 반환 Reading 수와 실제 구간

Explain Panel에서 EdgeX state/event 근거와 Kubernetes node/workload 근거를 섞어 하나의 physical availability reason으로 만들지 않는다.
기본 이력 범위는 30분이고 조회 상한은 최신 1,000 Event다. 한 Event에 Reading이 여러 개면 반환 Reading 수는 1,000을 넘을 수 있다. 특히 24시간 조회는 전체 기간의 완전한 결과라고 주장하지 않고, 요청 범위·반환 수·실제 첫/마지막 timestamp와 상한을 함께 표시한다. 이력 조회 중, 빈 결과와 오류는 각각 명시하며 `/state/devices`의 `latest_readings`로 대체하지 않는다. 빠르게 Device나 범위를 바꿀 때 이전 요청의 늦은 응답은 새 선택을 덮어쓰지 않는다.

## API 응답 필드

`/state/devices`는 Core Metadata 필드, 계산된 availability/reason, latest Core Data event metadata를 포함한다. EdgeX 필드가 authoritative이며 legacy 값으로 누락을 보충하지 않는다.

`/state/devices/{device_id}/telemetry`는 `window`과 `limit` query를 받아 선택 device의 최근 Core Data Events/Readings를 event origin 순서로 반환한다. `window` 기본값은 `-30m`, `limit`은 1~1,000이고 dashboard는 1,000을 사용한다. typed value와 `deviceName`, `sourceName`, nanosecond `origin`을 보존한다.

EdgeX v3의 `GET /api/v3/event/device/name/{name}`는 `offset`과 `limit`만 지원한다. `state-aggregator`는 이 API에서 선택 Device의 최신 1,000 Event 이내를 읽은 뒤 요청 `window`를 Event `origin`에 적용하고, 통과한 Event의 Reading만 펼쳐 반환한다. 지원되지 않는 `start`/`end` query가 Core Data에서 적용된다고 가정하지 않으며, 이 처리도 PostgreSQL 직접 조회나 별도 저장소를 만들지 않는다.

`/state/virtual-resources`는 자원증강형 가상디바이스를 Resource Profile 단위로 반환한다.
이 API는 가상 센서 생성 경로가 아니라 AI HAT/GPU/cache 같은 보강 실행 자원 상태 조회 경로다.
실행 인스턴스가 0개여도 registry에 있는 profile은 숨기지 않으며, 상태는 `configured_not_running`으로 표시한다.

`/state/dashboard`는 service resource observation 실패 시 dashboard 전체를 500으로 내리지 않는다.
이 경우 `resource_profiles.observation_error`에 원인을 남기고 service resource KPI만 0으로 degrade한다.
`/state/operator-assistant`와 `/state/operator-chat`도 같은 degraded dashboard snapshot을 사용한다.
resource observation 실패가 먼저 발생하면 chat은 Qwen 호출 전에 read-only degraded observation 응답을 반환한다.

## 전달 범위 해석

2026-07-21 기존 Agent/SQLite/HTTPS edge 경로와 aggregate `sensehat-001` bootstrap은 퇴역했다. dashboard/aggregator는 중앙 Metadata와 Core Data를 authority로 유지하고 Serial 6개와 직접 I2C 6개, 총 12개 가상 Device를 독립 inventory와 최신 Reading으로 표시한다. 각 행의 freshness는 해당 Device latest Event `origin`으로 계산한다.

Modbus, OPC-UA와 다른 I2C 장비·주소는 각각 독립 adapter wave다. RTSP는 frame을 Workflow Pod가 직접 구독하는 별도 media wave다. 해당 adapter/profile, 실제 장비 연결, typed telemetry, dashboard consumer와 실제 배포를 검증하기 전에는 지원 완료 protocol로 표시하지 않는다. 현재 Serial/Sense HAT I2C 정상 경로의 성공을 다른 protocol이나 장애복구 완료 근거로 사용하지 않는다.
