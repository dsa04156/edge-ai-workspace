# 대시보드 판단 정책

## 기본 원칙

대시보드는 서로 다른 권위의 신호를 하나의 “정상” 값으로 섞지 않는다. 각 상태에는 원본,
계산 기준과 reason을 함께 제공한다.

| 대상 | 권위 |
|---|---|
| 물리 Device/Profile/Device Service | EdgeX Core Metadata |
| sensor telemetry와 freshness | EdgeX Core Data Event/Reading `origin` |
| node와 workload | Kubernetes/KubeEdge + Prometheus |
| AI 서비스 정의 | Git `ServiceDescriptor` |
| AI 결과·알림 | 해당 서비스 API와 저장소 |

## 센서 디바이스 상태

| 조건 | 표시 |
|---|---|
| `adminState=LOCKED` | `unavailable` |
| `operatingState=DOWN` | `unavailable` |
| 상태 값 불명 | `degraded` |
| UP + latest Event fresh | `available` |
| UP + Event stale 또는 없음 | `degraded` |
| Metadata/Core Data 조회 실패 | `unknown` + 오류 reason |

Kubernetes node placement나 dashboard polling 시각으로 sensor availability를 판정하지 않는다.

## AI 서비스 상태

서비스는 다음 축을 독립적으로 표시한다.

- workload/endpoint Ready
- 필수 입력 connected·fresh·schema valid
- input window와 시각 정렬
- model ready와 model version
- 결과 저장·알림 sink
- 현재 실행 target과 최근 처리 비율

Device가 available이어도 필수 resource가 빠졌거나 모델이 준비되지 않으면 서비스는
`degraded` 또는 `blocked`다.

## AI 서비스 자원 증강 판단

기존 sensor 전용 자원 증강 rail의 기준은 범용 Runtime Recommendation Engine의 초기
서비스 policy로 유지한다. 엔진은 read-only 판단이며 자동 배포·라우팅·migration을
실행하지 않는다.

| gate | 기준 | 지속 시간 |
|---|---|---:|
| 자원 압력 | CPU limit 대비 85% 이상 또는 memory limit 대비 85% 이상 | 300초 |
| 서비스 압력 | p95 ≥ 4,000ms, backlog > 0 또는 throughput < 0.8/s | 180초 |
| 후보 준비 | Server1 endpoint와 CUDA readiness | 현재 관측 |
| 후보 성능 자격 | 정확한 model version의 부하 실험이 지연 10% 개선, 처리량 5% 비열등, error/OOM 0을 충족 | 실험 보고서 |

자원 압력과 서비스 압력이 모두 지속돼야 후보를 검토한다. 이때 후보가 준비되지 않았거나
성능 자격이 `rejected/pending`이면 `BLOCKED`다. 자격이 `qualified`인 경우에도
`RECOMMENDED`까지만 표시한다.

현재 `baseline-1.0.0` → `cuda-baseline-1.0.0` 후보는 2026-08-18 실험의 15개 조건 중
통과 0개이므로 `rejected`다. 85%/300초와 4,000ms/180초는 일시 spike를 거르는 보수적
관찰 기준이며 최적 임계값으로 실험 입증된 값은 아니다. 상세 근거는
[AI 서비스 자원 증강 부하 실험](AI-서비스-자원-증강-부하-실험.md)을 따른다.

범용 판단 상태는 다음과 같다.

| 상태 | 의미 |
|---|---|
| `NORMAL` | workload와 서비스가 회복 threshold 안에서 안정적 |
| `OBSERVING` | 압력·실패 신호가 진입 dwell 중이거나 회복 dwell/cooldown 적용 중 |
| `AUGMENT_RECOMMENDED` | workload는 Ready지만 자원 압력과 서비스 압력이 함께 지속됨 |
| `REPLACE_RECOMMENDED` | Pod/Deployment/Node 실패가 replacement dwell 이상 지속됨 |
| `BLOCKED` | EdgeX 입력 stale/장애, model 미준비, 필수 지표 누락 또는 적합 후보 없음 |

추천 시 현재 실행 노드는 후보 목록에 남기되 `current_node_excluded`로 탈락시킨다. 다른
노드는 CPU·memory·architecture·accelerator·health로 Filter한 뒤 available 자원과
utilization으로 Score한다. 같은 압력이 지속되는 동안 같은 추천을 반복 기록하지 않으며,
회복 후 재발에는 cooldown을 적용한다. 누락·stale 신호는 0이나 정상으로 대체하지 않는다.

### Runtime Execution Plan 판단 경계

최신 추천 상태가 `AUGMENT_RECOMMENDED` 또는 `REPLACE_RECOMMENDED`이고 Placement가 실제
대체 node를 선택한 경우에만 read-only 실행 계획을 만든다. 증강 계획은 `create → ready →
traffic distribute`, 대체 계획은 `create → ready → traffic cutover → terminate current →
conditional rollback` 순서를 보존한다. 각 단계는 이전 단계 성공, 대상 node 적합성, workload
identity 유지와 health 확인 같은 선행조건 및 timeout, scheduling 실패, readiness 실패,
traffic health 악화 같은 실패조건을 안정적인 code로 제공한다.

`NORMAL`·`OBSERVING`에는 변경할 근거가 없으므로 `not_applicable`, `BLOCKED`나 선택 node가
없는 추천에는 `blocked`를 반환한다. 계획 생성 자체는 dwell/cooldown을 변경하거나 새 판단
이력을 기록하지 않으며 Kubernetes, Service/Ingress, traffic plane과 기존 workload를 수정하지
않는다. rollback 단계도 실패 시 수행할 보상 절차를 기술할 뿐 자동 실행하지 않는다.

대시보드 `서비스 운영`은 최신 판단의 `reasonCodes`, 관측 duration, 현재 node, Placement의
전체 후보와 Execution Plan·판단 이력을 같은 화면에 표시한다. 후보가 추천 응답에 포함되면
화면 갱신을 위해 `/api/placements/select`를 다시 호출하지 않는다. 계획은 항상
`실행 계획 / Read-only`로 표시하고 승인·실행·적용 control을 만들지 않는다. API 실패나
계약에 없는 값은 `N/A`, `관측 불가`, `데이터 없음`으로 드러낸다.

### 승인 기반 실행 정책

Execution Controller는 최신 planId 일치, 명시적 승인 boolean, 승인자 식별자와 관리 token을
모두 통과해야 실행한다. planId당 실행은 하나이며 재시도는 저장된 동일 결과를 조회한다.
지원 범위는 candidate Deployment 생성과 Ready 확인이다. 각 단계 상태와 전이는 영속화하며
첫 `FAILED` 또는 `BLOCKED`에서 멈춘다. traffic 분산·전환, 기존 instance 종료와 rollback은
항상 `unsupported_step`으로 차단하고 후속 단계도 `previous_step_blocked`로 남긴다. 이때 기존
workload를 update/delete하지 않으며 candidate cleanup도 자동 수행하지 않는다.

dry-run은 plan freshness, source workload 종류, Placement completeness와 단계 지원 여부를
보여주지만 승인이나 실행 record를 만들지 않는다. process 재시작 때 남은 `RUNNING`은 임의
재개하지 않고 `execution_interrupted`로 차단해 중복 생성보다 수동 확인을 우선한다.

## 운영 KPI

| KPI | 정의 |
|---|---|
| registered devices | Core Metadata Device 수 |
| fresh devices | latest Event `origin`이 freshness window 이내인 Device 수 |
| operator focus | degraded + unavailable Device 수 |
| node online ratio | unavailable이 아닌 node snapshot 비율 |
| service ready | workload·input·model·sink gate를 모두 통과한 서비스 수 |

누락 metric은 0으로 만들지 않고 `N/A` 또는 `unknown`으로 표시한다. 화면은 read-only 판단을
제공하며 Kubernetes·EdgeX mutation을 수행하지 않는다.
