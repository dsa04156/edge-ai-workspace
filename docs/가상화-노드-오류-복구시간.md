# 가상화 노드 오류 복구시간 구현·시험 기준

> 상태: Arduino 정상 전송을 1,000 ms로 유지하고 재연결 때만 제한된 `READ_NOW` 요청을
> 수행하는 운영 구성을 배포했다. 같은 50 ms 단절·복구 30회가 모두 400 ms 이내여서
> 2차년도 process 개발 gate를 통과했다. 후속 Core Data 수정 뒤 205.724 ms 복구 canary와
> 전송 재개 4.130 ms 뒤 중앙 Event 저장도 확인했다. 과제 최종 250 ms 목표는 별도 시험
> 전까지 미달성으로 유지한다.
>
> 기준일: 2026-09-02

## 지표 경계

성능지표 8의 측정 구간은 다음과 같다.

```text
정상 전송 이력이 있는 Serial stream의 오류 감지
  → 포트 재연결
  → 첫 유효 frame decode·validation
  → EdgeX SDK 비동기 전송 채널 enqueue 완료
```

| 구분 | 값 | 의미 |
|---|---:|---|
| 과제 최종 목표 | 250 ms | 기존 과제 문서의 공식 목표. 별도 변경 승인 전 유지 |
| 2차년도 개발 gate | 400 ms | 현재 구현·반복시험의 중간 합격 기준 |
| 비교값 | 300 ms | 기존 비교 기준인 미국 VMware 값 |

400 ms를 통과해도 250 ms 최종 목표를 달성한 것으로 기록하지 않는다. 반대로 이 지표는
장애 발생부터 Kubernetes/KubeEdge node 판정, 다른 노드의 Pod 생성과 완전 기동까지 걸리는
전체 failover 시간이 아니다.

초기 기동 시 포트를 열지 못한 경우도 복구시간 표본에서 제외한다. 정상 sample을 한 번 이상
전송한 stream에서 오류가 검출된 뒤 다시 유효 sample을 전송한 경우만 한 건으로 센다.

## 현재 구현

`device-serial-jetson`의 shared Serial Reader는 다음 fast-retry profile을 사용한다.

```text
대기:       25 ms → 50 ms → 100 ms → 200 ms → 1 s → 2 s → 4 s → 8 s → 16 s → 30 s
누적 시도: 25 ms → 75 ms → 175 ms → 375 ms → 1.375 s → ...
```

- 포트 `open`, read timeout 설정 또는 established stream의 read 오류에서 `DOWN`을 알린다.
- Linux에서는 serial library가 포트를 열기 전에 현재 termios의 다른 flag를 보존하면서
  `HUPCL`만 해제한다. 포트 close·재open에 따른 DTR 하강과 Uno auto-reset을 억제한다.
- 이미 복구 중이면 후속 오류가 검출 시각을 다시 시작하지 않는다.
- 포트가 다시 열렸다는 사실만으로 완료 처리하지 않는다.
- malformed line은 버리고, 첫 유효 frame이 실제 SDK async channel까지 전달된 뒤 완료한다.
- 복구 중 성공한 port open과 read timeout 설정 완료를 `portReadyAt`, 최초 수신 byte를
  `firstByteAt`으로 기록해 병목 구간을 분리한다.
- `time.Time`의 monotonic 차이를 사용해 process 내부의 감지→재개 시간을 계산한다.
- 400 ms를 넘으면 target miss를 누적하고 warning log를 남긴다.

Arduino Uno 운영 펌웨어는
`edgex/device-serial/firmware/arduino_uno_multisensor/arduino_uno_multisensor.ino`가
소유한다. 기존 A0·A1·D4·A2·A3·A4 pin, 115200 bps와 JSON wire contract를 유지하고 정상
sample 주기는 1,000 ms다. established stream 재연결 직후 `READ_NOW`를 보내며 첫 byte가
없을 때만 25 ms 간격으로 최대 세 번 더 요청한다. byte가 오거나 네 번째 요청을 보낸 뒤에는
정상 1초 read timeout으로 돌아간다. 원본 source와 application rollback image도 같은
디렉터리의 `backup/`에 보존한다.

USB 재열거 때 `ttyACM` 번호가 바뀌어도 실행 중인 Pod가 따라가도록 발견 identity와 실행
endpoint를 분리한다. 호스트 udev는 승인된 VID·PID·USB serial을 exact match해
`/run/edgeai/devices/arduino-001` 문자 장치를 현재 major/minor로 원자 교체한다. Device
Service에는 이 좁은 디렉터리만 `/dev/edgeai`에 read-only mount한다. 전체 호스트 `/dev`나
`/sys`를 mount하지 않는다.

배포 설정은 다음 두 값으로 고정한다.

```yaml
Driver:
  SerialRecoveryTarget: "400ms"
  SerialReconnectDelays: "25ms,50ms,100ms,200ms,1s,2s,4s,8s,16s,30s"
```

재시도 간격은 1~16개의 양수 duration, 비감소 순서, 각 30초 이하만 허용한다. 잘못된 값이면
Device Service 초기화를 실패시켜 조용히 기본값으로 우회하지 않는다.

## 관측값

EdgeX custom metric은 다음과 같다.

| metric | 의미 |
|---|---|
| `SerialRecoveryDetected` | established stream에서 복구를 시작한 누적 횟수 |
| `SerialRecoveryCompleted` | 첫 유효 frame 전송까지 완료한 누적 횟수 |
| `SerialRecoveryLastDurationMs` | 마지막 완료 표본의 감지→전송 재개 시간 |
| `SerialRecoveryLastAttempts` | 마지막 완료 표본의 재개방 시도 횟수 |
| `SerialRecoveryTargetMisses` | 400 ms를 초과한 완료 표본의 누적 횟수 |

같은 값은 Device Service의 read-only API에서도 확인할 수 있다.

```bash
kubectl get --raw \
  '/api/v1/namespaces/edgex-edge/services/http:device-serial-jetson:59910/proxy/api/v3/serial-recovery/stats'
```

응답의 `inProgress`는 `detected > completed`, `last.withinTarget`은 마지막 표본이 현재 target
이하인지를 뜻한다. 값은 process-local 관측 상태이므로 Pod 재시작 전에 시험결과서로
보존한다. 장기 이력이나 durable outbox가 아니다.

`last.detectionToPortReadyMs`, `last.portReadyToFirstByteMs`,
`last.firstByteToResumeMs`는 각각 오류 감지→포트 준비, 포트 준비→첫 byte, 첫 byte→첫 유효
frame 전송 재개의 구간 시간이다. `portReadyAt`은 char device 생성시각이 아니라 Device
Service가 포트를 열고 read timeout 설정까지 마친 process 내부 시각이다.

## 400 ms 내부 qualification

현재 내부 합격 절차는 다음과 같다. TTA 또는 과제 공식 시험절차가 확정되면 그 절차를
우선한다.

1. 새 immutable image를 배포하고 정상 sample과 Core Data `origin` 증가를 먼저 확인한다.
2. API의 초기 counter를 기록한다.
3. 정상 전송 중 승인된 Serial 단절·복구를 30회 반복한다. Pod 삭제나 node 전원 차단은 이
   지표가 아닌 별도 전체 failover 시험으로 분리한다.
4. 각 회차의 process log, recovery API와 첫 후속 Core Data Event를 같은 시험 record에 묶는다.
5. `completed` 증가, `targetMisses=0`, 30회 `max ≤ 400 ms`일 때 400 ms 내부 gate를 통과한다.
6. p50·p95·max, 미완료 건수와 Core Data readback 누락을 함께 보고한다.

## 2026-09-01 구간 계측 진단

구간 계측이 포함된 revision `c3f62556da848e90ed55712004476555d9093604`, image
`edgex-device-serial@sha256:65b31240e1f798c2c8a1bbd9257573520cd95148e03488566b806db99e011146`
를 같은 Jetson에 배포했다. 최초 qualification을 다시 시작한 것이 아니라, 원인을 분리하기
위해 같은 50 ms `cdc_acm` unbind→rebind를 1회 canary와 5회 진단 series로 제한 실행했다.
시험 전 process-local counter는 모두 0이었고 시험 후 `detected=6`, `completed=6`,
`targetMisses=5`였다.

| 표본 | 전체 복구 | 감지→port ready | port ready→첫 byte | 첫 byte→유효 frame | 판정 |
|---|---:|---:|---:|---:|---|
| 진단 canary 1회 | 158.629 ms | 131.299 ms | 26.955 ms | 0.375 ms | 통과 |
| 후속 5회 범위 | 1,817.702~1,843.971 ms | 61.218~84.425 ms | 1,750.519~1,754.341 ms | 4.170~8.704 ms | 5회 모두 실패 |

후속 5회에서 포트는 모두 85 ms 안에 준비됐고 재개방도 각 1회 만에 성공했다. 반면 포트가
준비된 뒤 첫 byte까지 약 1.75초의 정지 구간이 반복됐으며, byte가 도착한 뒤 유효 frame을
전송하기까지는 최대 8.704 ms였다. 따라서 현재 반복 실패의 지배 병목은 heartbeat, retry
backoff, JSON decode가 아니라 **Serial 재개방 뒤 장치가 첫 byte를 보내기 전 구간**이다.

최근 temperature Event 100개에서 계산한 정상 주기는 99개 간격 기준 min 1,013.869 ms,
p50 1,016.088 ms, p95 1,020.303 ms, max 1,021.805 ms였다. 포트 open 때 DTR/RTS를 올리는
현재 라이브러리 기본 동작과 Arduino auto-reset/firmware startup은 강한 원인 후보지만, 이번
계측만으로 DTR reset과 firmware 내부 초기화 시간을 분리해 확정하지는 않는다. 실제 firmware
source와 pin/resource 계약을 확인한 뒤 DTR auto-reset 억제 또는 startup·첫 frame 지연 축소를
한 항목씩 시험해야 한다.

## 2026-09-02 Core Data 복구 및 중앙 저장 E2E canary

### 다섯 살에게 설명하면

센서는 이미 400 ms 안에 다시 말하기 시작했지만, 중앙 창고 직원 네 명이 오래된 상자를
찾다가 각자 열쇠를 하나씩 쥔 채 다른 열쇠를 기다려 창고가 멈췄다. 오래된 센서의 상자를
창고 전체에서 찾지 않고 그 센서 칸에서만 찾게 했고, 첫 열쇠를 반납한 다음 상세 상자를
열게 바꿨다. 그 뒤 센서가 다시 말한 값이 중앙 창고에도 들어오는 것을 확인했다.

Core Data 4.0.2의 DB pool은 최대 4 connection이고 HTTP request timeout은 5초였다. 오래
멈춘 Sense HAT의 latest Event 조회는 전체 origin index에서 약 1,051만 Event row를 훑어
8.383초가 걸렸다. 동시에 네 요청이 들어오면 각 요청이 외부 Event rows connection을 잡은
채 Reading 조회용 다섯 번째 connection을 기다려 신규 Event 저장까지 멈췄다.

revision `3efaa982`, image
`edgex-core-data@sha256:1d0eb4f7a23d0087887de598f74472cbfdd88af27764a084e6899014dae0d9a6`
에는 다음 두 수정을 배포했다.

1. 먼저 `device_info`를 고르고 기존 `(device_info_id, origin DESC)` index로 해당 디바이스의 최근 Event만 읽는다.

## 현장 한계와 후속 조치

- 400 ms heartbeat를 설정하는 것만으로 이 목표를 달성할 수 없다. heartbeat 400 ms는 오류
  검출에만 최대 400 ms를 쓰며 포트 복구와 다음 sample 시간을 포함하지 않는다.
- 2026-09-01의 100 ms 연속 전송 구성은 비교 이력이다. 현재 정상 주기는 약 1초이며 복구
  중에만 최대 네 번의 제한 요청을 사용한다. 정상 수집 주기는 복구시간 자체가 아니므로
  transport 오류 감지와 첫 유효 데이터 완료 시각을 별도로 계측한다.
- 현장 sketch·pin mapping을 확인하고 원본 application을 백업한 뒤 승인된 application
  flash와 host termios 변경만 적용했다. 물리 auto-reset 회로는 변경하지 않았다.
- USB 장치 재열거가 400 ms보다 오래 걸리거나 stable char device가 복구되지 않으면 software
  retry만으로는 통과할 수 없다.
- node 전원·망 장애까지 400 ms 안에 복구하려면 hot-standby Device Service, 이중화된 물리
  수집 경로와 전송 경로가 필요하다. 현재 단일 Arduino→단일 Jetson 연결에는 이 보장이 없다.
- 통신 단절 중 telemetry 보존과 중앙 재전송은 [장애 저장·재전송 시스템 설계](장애-저장-재전송-시스템-설계.md)의
  별도 범위다. 현재 Local Data cache를 durable outbox로 해석하지 않는다.
