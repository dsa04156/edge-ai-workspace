디바이스 연결 복구 표준

상태: 공통 계약은 현재 기준이다. Serial + Arduino Uno의 on-demand-read 구현은 로컬 자동시험을 통과했으며 실장비 배포·반복시험 전까지 운영 완료로 표시하지 않는다. MQTT·Modbus·OPC-UA·RTSP 항목은 후속 Device Service가 따라야 할 설계 계약이다.

기준일: 2026-09-02

다섯 살에게 설명하면

센서가 계속 “나 여기 있어”라고 아주 자주 외치게 하지 않는다. 평소에는 정해진 속도로 말하게 두고, 선이 끊겼다가 다시 이어진 순간에만 컴퓨터가 “지금 값 한 번 알려 줘”라고 묻는다. 센서가 바로 대답하면 EdgeX가 그 값을 받고 복구가 끝난다.

모든 장비가 똑같은 말을 쓰지는 않는다. Arduino Serial은 READ_NOW, MQTT는 다시 구독, Modbus는 즉시 한 번 읽기처럼 장비에 맞는 행동을 한다. 하지만 “끊김 발견 → 다시 연결 → 데이터 재개 행동 → 첫 정상 데이터”라는 순서는 모두 같다.

공통 상태와 측정 경계

CONNECTED
  → DISCONNECTED      연결 오류 감지
  → RECONNECTING      transport 재연결
  → WAITING_FOR_DATA  승인된 데이터 재개 행동 수행
  → RECOVERED         첫 유효 데이터가 Device Service 출력 경계에 도착

복구시간은 DISCONNECTED 진입 시각부터 RECOVERED 시각까지다. 최초 기동 실패, 단순히 포트를 연 시점, malformed frame, Kubernetes node/Pod 전체 failover는 이 표본에 넣지 않는다. 실제 KPI 판정은 가상화 노드 오류 복구시간을 따른다.

표준 복구 전략

전략 뜻 적용 예
on-demand-read 재연결 직후 승인된 현재값 요청을 한 번 수행 Arduino Serial READ_NOW, Modbus 즉시 read
resubscribe session을 복원하고 기존 데이터 구독을 다시 설정 MQTT topic 재구독, OPC-UA subscription 복원
passive-first-data 별도 요청 없이 장비가 보내는 첫 유효 데이터를 기다림 요청 명령이 없는 push-only 센서, RTSP 첫 frame

전략 이름은 공통이지만 실행 코드는 protocol adapter가 소유한다. 대시보드나 Device 등록 입력에서 임의 Serial byte, MQTT topic, shell command, host path를 받지 않는다. Git에서 검토한 Adapter Catalog가 의미 기반 전략을 고정된 안전 동작으로 매핑한다.

Protocol별 연결 끊김 판단과 재개 행동

Protocol 연결 끊김 증거 재연결 뒤 행동 복구 완료
Serial established stream의 read/open 오류 on-demand-read면 고정 요청 1회 첫 유효 frame enqueue
MQTT client disconnect callback 또는 session 오류 topic 재구독 첫 유효 message 수신
Modbus TCP socket/read 오류 연결 후 register 즉시 read 유효 response decode
OPC-UA secure channel/session/subscription 오류 session·subscription 복원 첫 유효 monitored value
RTSP stream read/decode 오류 stream 재연결 첫 유효 frame

데이터가 한동안 안 왔다는 사실만으로 물리 연결 단절이라고 단정하지 않는다. 조용한 센서의 정상 상태와 케이블 단절을 구분할 수 없는 protocol은 별도 timeout/heartbeat 계약과 오탐 시험이 필요하다. 이번 표준의 최소 범위는 transport가 직접 보고한 연결 오류다.

Serial + Arduino 첫 구현 계약

  • 정상 sample 주기는 1,000 ms다.
  • Linux Serial은 HUPCL을 해제해 재open 때 Uno가 자동 재시작하지 않도록 한다.
  • established stream 오류 뒤 포트가 다시 준비되면 Device Service가 READ_NOW\n을 한 번 쓴다.
  • Uno는 줄바꿈으로 끝난 정확한 READ_NOW만 받아 기존 pin·JSON sample을 즉시 한 번 보낸다.
  • READ_NOW는 Device Service 내부 복구 handshake다. EdgeX Core Command의 공개 write나

actuator 제어로 노출하지 않는다.

  • 요청 write가 실패하거나 일부 byte만 기록되면 복구 완료로 처리하지 않고 다시 연결한다.
  • 첫 유효 sample이 EdgeX SDK async channel에 enqueue되어야 복구 완료다.

EdgeX Device의 serial.RecoveryStrategy는 on-demand-read로 선언한다. 이 전략을 지원하지 않는 parser에 설정하면 Device Service는 시작 단계에서 명시적으로 거부한다.

다른 장비에 적용하는 절차

  1. Device Service가 제공하는 실제 연결 오류 신호를 정한다.
  2. on-demand-read, resubscribe, passive-first-data 중 하나를 Adapter Catalog에 고정한다.
  3. 임의 명령 대신 adapter 내부의 검토된 동작만 실행한다.
  4. 최초 기동과 재연결을 구분하고 첫 유효 데이터를 완료 조건으로 삼는다.
  5. 연결 끊김→첫 유효 데이터의 phase metric을 남긴다.
  6. 합성시험 뒤 실제 장비 단절·복원을 반복하고 p50·p95·max·미완료를 기록한다.

다른 protocol이 이 문서에 행만 추가됐다고 구현된 것은 아니다. 실제 Device Service 코드, 장비별 binding, 자동시험과 실장비 반복시험을 모두 통과한 protocol만 운영 완료로 표시한다.

  • node 전원 장애, Kubernetes/KubeEdge node 판정과 다른 node의 Pod 재기동
  • 단절 중 데이터의 durable 저장·재전송
  • 장비가 연결된 채 멈춘 silent failure를 모든 protocol에서 자동 판정
