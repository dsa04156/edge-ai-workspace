저장소 구조

먼저 알아둘 것

이 저장소에는 현재 PoC 코드, 운영 보조 코드, 2차년도 설계, 과거 오케스트레이션 실험이 함께 있다. 작업 대상은 아래 Current/Supporting 경로로 제한하고, live 관찰과 checkout render가 다르면 문서에 둘 다 기록한다.

Slice 0의 state-aggregator projection은 설정된 물리 Device/resource를 stable input ID와 capability/source/resource/AI field map으로 읽어 조합하며, 원본 Event provenance를 보존한다. ready는 권위 있는 Device/Profile identity·상태, 필요한 resource와 신선한 입력, 완전한 provenance가 모두 확인된 경우에만 성립하고, identity·상태·이력·전송·형식 오류와 불완전한 이력은 명시적인 비준비 또는 실패 계약으로 구분한다. EdgeX Core Metadata의 Device/Profile/Device Service와 Core Data의 Event/Reading이 계속 권위이고 projection은 저장소나 fallback이 아니다. 기본값은 비활성이며 이번 실행에서는 주입한 테스트·로컬 개발 설정에서만 켠다. KubeEdge는 node·workload 관측만 담당하고 workflow는 dry-run으로 남는다. Kustomize, Argo, ingress, 접근 정책, 배포, live activation은 별도 승격 gate 전까지 제외한다.

자원 풀은 별도 운영 스케줄러가 아니라 state-aggregator의 read model이다. resource_profile.py가 보존한 Pod identity·Ready·Service endpoint 증거와 virtual_resources.py의 전용 runtime selector·binding 상태를 결합하고, resource_pool.py가 데이터 입력·노드 진단·실행 후보·서비스를 분리해 /state/resource-pool로 제공한다. 화면의 노드 진단은 특수 실행 자원이나 물리 디바이스 availability를 의미하지 않는다.

이 경로의 구현을 현재 dashboard, DeviceStatus, telemetry, command의 권위로 다시 설명하려면 먼저 프로젝트 범위를 변경하고, 별도 테스트·manifest·운영 책임을 추가한다.

배포 재현성 규칙

  1. 적용 전 kubectl kustomize edgex/k8s를 실행한다.
  2. 노드명과 IP는 manifest에 고정하지 않고 nodeSelector/configuration으로 사용한다.
  3. Secret은 ConfigMap이나 문서에 값을 적지 않는다.
  4. PVC·TLS·NetworkPolicy·RBAC를 image와 함께 확인한다.
  5. live Argo revision의 리소스가 checkout에 없으면 “live에서 동작”과 “현재 checkout에서 재현”을 분리한다.

  • 과거 실험이면 Legacy/Archive
