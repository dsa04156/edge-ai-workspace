프로토콜 독립형 디바이스 Discovery 및 Registration 요구사항

상태: 승인된 구현 기준 명세 적용 대상: https://github.com/dsa04156/edge-ai-workspace 구현 상태는 별도 현재-구현-상태 문서에서 완료·부분 구현·미구현·실장비 검증 필요로 구분한다.

1. 목적과 작업 원칙

KubeEdge와 EdgeX를 기반으로 물리 디바이스에 연결된 센서·PLC·카메라 등을 탐색하고, 운영자 승인과 외부 인증을 거쳐 EdgeX에 등록하는 프로토콜 독립형 Discovery 및 Registration 시스템을 실제로 구현한다.

  • 설계 문서만 작성하지 않고 실제 코드를 수정한다.
  • 저장소에 이미 존재하는 코드와 구조를 최대한 재사용한다.
  • 존재하지 않는 기능을 이미 구현됐다고 가정하지 않는다.
  • 작업 전에 AGENTS.md, 상위 안내 문서, docs/, edgex/, k8s/,

edge-orch/ 관련 코드를 조사한다.

  • 문서와 현재 구현이 충돌하면 실제 코드와 배포 manifest를 먼저 확인하고 문서를 정렬한다.
  • 기존 기능을 깨뜨리는 대규모 재작성은 하지 않는다.
  • 기존 API와 배포 구조는 가능한 한 하위 호환성을 유지한다.
  • 외부 실장비가 없어도 검증할 수 있도록 simulator, mock, pseudo terminal 기반 테스트를

제공한다.

  • 지원하지 않는 기능을 지원한다고 표시하지 않는다.
  • 작업을 작은 단계로 나누되 구현 가능한 범위를 질문만 남기고 중단하지 않는다.

2. 전체 흐름

물리 장비 연결
  -> 노드 로컬에서 장비 후보 탐색
  -> 프로토콜 및 장비 모델 식별
  -> 공통 DiscoveryCandidate 생성
  -> 중앙 Adapter Controller에 후보 보고
  -> Device Profile 및 Adapter Catalog 매칭
  -> 운영자 승인 및 외부 인증 모듈 연계
  -> 필요한 EdgeX Device Service 재사용 또는 배포
  -> EdgeX Core Metadata에 Profile 및 Device 등록
  -> 첫 Event가 Core Data에 수신되는지 확인
  -> 등록 완료 처리
  -> 분리·재연결·장애 상태 관리

자동 탐색과 자동 신뢰를 혼동하지 않는다. 발견된 장비는 바로 등록하지 않고 반드시 다음 검증을 거친다.

  1. stable hardware identity 확인
  2. Device Profile 매칭
  3. 검증된 Device Service 이미지 확인
  4. 운영자 승인
  5. 외부 인증 모듈 승인 또는 개발용 mock 승인
  6. EdgeX 등록
  7. 첫 Event 수신 확인

3. 목표 아키텍처

3.1 Node-local Discovery

  • Jetson, Raspberry Pi 등 각 엣지 노드에서 실행한다.
  • 로컬 USB, Serial, I2C 및 허용된 네트워크 endpoint만 관찰한다.
  • 프로토콜별 discovery plugin으로 후보를 식별하고 공통 DiscoveryCandidate로 보고한다.
  • 가능한 경우 EdgeX Device Service SDK의 native discovery를 재사용한다.
  • native discovery가 적합하지 않을 때만 얇은 discovery plugin을 추가한다.
  • 발견 단계에서는 승인되지 않은 장비의 상시 telemetry 수집 Runtime을 시작하지 않는다.

3.2 Adapter Controller

  • 중앙 Edge AI 서버에서 실행한다.
  • 후보 저장, 상태와 이력, 중복 제거, Catalog 매칭, 승인·거절·차단을 관리한다.
  • KubeEdge/Kubernetes를 통해 검증된 Device Service를 배포하거나 기존 Runtime을 재사용한다.
  • EdgeX Core Metadata 등록과 Core Data 첫 Event 확인을 수행한다.
  • 실패 시 Controller가 이번 Saga에서 생성한 리소스만 rollback한다.

3.3 EdgeX Device Service

  • 실제 장비 통신과 센서 데이터 수집을 독점한다.
  • 프로토콜별 parser와 connection logic을 수행하고 Event/Reading을 생성한다.
  • discovery와 지속적인 데이터 수집 코드는 가능한 한 분리한다.

3.4 EdgeX Core

  • Core Metadata는 승인되고 검증된 Device Service, Device Profile, Device만 저장한다.
  • Core Metadata를 발견 후보 Registry로 사용하지 않는다.
  • Core Data는 센서 Event와 Reading을 저장한다.
  • 등록 완료 판정은 Core Data의 첫 Event 확인까지 포함한다.

3.5 KubeEdge/Kubernetes

  • 정확한 target node에 Device Service 또는 Discovery Pod를 배포한다.
  • 기존 Argo CD와 Kustomize 진입점을 유지한다.
  • 고정 노드 IP 대신 node name, 설정, 환경변수를 사용한다.
  • KubeEdge Device/DeviceModel/DeviceStatus를 EdgeX와 병행하는 물리 디바이스 권위로

사용하지 않는다.

3.6 외부 보안·인증

  • 외부 인증 시스템 자체는 새로 만들지 않는다.
  • AuthProvider 또는 SecurityApprovalClient 인터페이스를 정의한다.
  • 개발 환경에는 AllowAllMockProvider를 제공한다.
  • 운영 환경에는 외부 인증 API endpoint와 연동 가능한 provider를 제공한다.
  • 인증 실패 또는 인증 시스템 장애 시 fail-closed하며 EdgeX에 등록하지 않는다.

4. 핵심 데이터 모델

대표 모델은 다음 형태를 따른다.

{
  "candidateId": "stable deterministic ID",
  "nodeId": "factoryName-dev0001-jetorn",
  "protocol": "serial",
  "endpoint": "/dev/serial/by-id/...",
  "hardwareId": "stable hardware identifier",
  "vendor": "Arduino",
  "model": "arduino-multisensor-v1",
  "capabilities": [
    "temperature",
    "humidity",
    "acceleration"
  ],
  "recommendedProfile": "arduino-multisensor-v1",
  "matchConfidence": "exact",
  "presence": "present",
  "reviewState": "detected",
  "authState": "not_checked",
  "firstSeen": "ISO-8601",
  "lastSeen": "ISO-8601",
  "rawMetadata": {}
}

candidateId는 임시 포트 번호나 DHCP IP만으로 만들지 않는다.

SHA-256(nodeId + "|" + protocol + "|" + stableHardwareId)

stable hardware identity 우선순위:

  • Serial: USB serial number 우선, 없으면 VID/PID/interface/path 조합
  • I2C: nodeId + bus + 검증된 sensor chip ID + address
  • Modbus: transport endpoint + unit ID + device identification
  • OPC-UA: application URI 또는 server URI
  • ONVIF: endpoint reference 또는 device UUID
  • MQTT: 장비 자기소개 메시지의 deviceId

상태는 최소 다음을 지원한다.

  • 정상: DETECTED, IDENTIFIED, PENDING_APPROVAL, APPROVED,

SERVICE_READY, METADATA_REGISTERED, EVENT_CONFIRMED

  • 예외: BLOCKED, REJECTED, STALE, FAILED

상태 전이는 명시적 state machine으로 구현하고 임의 점프를 허용하지 않는다. 전이 이력, 실패 사유, 승인자, 재시도 횟수와 등록 단계를 영속 저장한다.

5. Discovery Plan

모든 노드에서 모든 프로토콜을 무작정 스캔하지 않는다. 노드별 Discovery Plan을 API 또는 설정 파일로 조회·변경 가능하게 만들며 기본값은 보수적으로 둔다.

nodeId: factoryName-dev0001-jetorn
discovery:
  serial:
    enabled: true
    allowedVidPid:
      - "2341:0043"
    baudRates:
      - 115200
  i2c:
    enabled: true
    buses:
      - 1
    allowedAddresses:
      - "0x68"
      - "0x76"
  modbusRtu:
    enabled: false
  modbusTcp:
    enabled: false
    cidrs: []
    unitIds: []
  opcua:
    enabled: false
    endpoints: []
  onvif:
    enabled: false
    cidrs: []
  mqtt:
    enabled: true
    discoveryTopic: "edge/discovery/+/+"
  • 네트워크 전체 스캔은 기본 비활성화한다.
  • CIDR, endpoint, bus, address, VID/PID 등 명시적 allowlist만 사용한다.
  • 저장소의 실제 testbed 노드명은 코드가 아닌 배포 설정과 Plan에서 관리한다.

6. 프로토콜별 정책

6.1 Serial / USB

Serial은 1차 구현의 핵심 경로다.

  • Linux udev event 또는 주기적 inventory reconciliation을 사용한다.
  • /dev/ttyUSB*, /dev/ttyACM*보다 /dev/serial/by-id/*를 우선한다.
  • VID, PID, USB serial, manufacturer, product를 수집한다.
  • 연결·해제와 동일 장비 재연결을 감지하고 같은 candidateId를 유지한다.
  • WHOAMI 또는 Manifest 명령을 보낼 수 있는 plugin interface를 제공한다.
  • timeout, 잘못된 JSON, framing 오류를 처리한다.
  • exact profile match에 성공한 경우에만 IDENTIFIED로 전이한다.
  • 응답이 없거나 Profile을 결정할 수 없으면 BLOCKED 또는 PENDING_APPROVAL로 유지한다.

Arduino 또는 ESP32 멀티센서 보드는 센서별 EdgeX Device로 새로 분할하지 않는다.

Arduino/ESP32 1개
  -> EdgeX Device 1개
  -> 내부 센서 값은 여러 DeviceResource

Manifest 예:

{
  "type": "manifest",
  "deviceId": "arduino-001",
  "model": "arduino-multisensor-v1",
  "firmwareVersion": "1.0.0",
  "resources": [
    "temperature",
    "humidity",
    "accelerationX",
    "accelerationY",
    "accelerationZ",
    "gyroX",
    "gyroY",
    "gyroZ"
  ]
}

pseudo terminal Serial simulator로 다음을 검증한다.

  • 장비 연결
  • Manifest 응답
  • telemetry 전송
  • 연결 해제와 동일 장비 재연결
  • 잘못된 Manifest
  • 미지원 장비

기존 서비스 데모의 센서별 Device 구성은 하위 호환 경로로 즉시 파괴하지 않는다. 신규 등록 경로부터 물리 보드 1개와 EdgeX Device 1개 원칙을 적용하고, 기존 데모 마이그레이션은 별도 검증 후 수행한다.

6.2 I2C

  • /dev/i2c-N 존재를 확인한다.
  • Plan에 등록된 bus와 address만 probe하고 전체 주소를 기본 스캔하지 않는다.
  • WHO_AM_I, chip ID 같은 읽기 전용 식별 레지스터를 사용한다.
  • 식별 규칙은 Catalog에 선언한다.
  • read만으로 상태가 바뀔 수 있는 장비를 고려해 allowlist 기반으로 동작한다.
  • 실장비가 없을 때 사용할 mock bus adapter와 단위 테스트를 제공한다.
  • 버스 존재만 확인한 결과를 특정 센서 발견 성공으로 표시하지 않는다.

6.3 Modbus RTU/TCP

  • Serial 완료 후 확장 가능한 plugin contract를 제공한다.
  • 지정된 serial port, IP, CIDR, Unit ID만 탐색한다.
  • 공장망 전체 자동 스캔은 금지한다.
  • Device Identification 또는 명시된 제조사 identification register rule만 사용한다.
  • register map은 Device Profile 또는 binding Catalog에서 관리한다.
  • 실제 미완료 기능은 unsupported 또는 not implemented로 표시한다.

6.4 OPC-UA

  • 운영자가 등록한 endpoint 또는 제한된 discovery endpoint만 사용한다.
  • FindServers/GetEndpoints에 해당하는 plugin contract를 둔다.
  • server URI/application URI를 stable identity로 사용한다.
  • Browse 결과에서 Node ID, data type, browse name을 수집할 수 있게 한다.
  • 자동 Device Profile은 초안까지만 허용하며 운영자 검토 없이 등록하지 않는다.

6.5 MQTT

MQTT는 네트워크 스캔으로 발견하지 않는다. 장비 자기등록 규약을 사용한다.

edge/discovery/{nodeId}/{deviceId}
{
  "deviceId": "vibration-controller-001",
  "model": "vibration-sensor-v1",
  "profile": "vibration-sensor-v1",
  "resources": [
    "accelerationX",
    "accelerationY",
    "accelerationZ"
  ],
  "firmwareVersion": "1.1.0"
}
  • retained message를 지원한다.
  • payload schema와 topic의 nodeId 일치를 검증한다.
  • 중복 메시지는 idempotent하게 처리한다.
  • 허용된 profile과 일치하지 않으면 BLOCKED 처리한다.
  • telemetry topic과 discovery topic을 분리한다.
  • MQTT-only 장비가 없으면 브로커나 Device Service를 존재하는 것처럼 추가하지 않는다.

6.6 카메라

  • ONVIF는 장비 발견과 capability 조회에 사용한다.
  • RTSP는 실제 영상 스트림 소비에 사용한다.
  • RTSP 프레임 전체를 EdgeX Event로 저장하지 않는다.
  • EdgeX에는 카메라 상태, endpoint metadata, AI 분석 결과만 저장할 수 있다.
  • 영상 분석 Workflow는 별도 streaming path를 유지한다.

7. Adapter / Profile Catalog

검증된 장비와 Runtime만 사용할 수 있도록 Git 관리형 YAML 또는 JSON Catalog를 구현한다.

bindingId: jetson-arduino-serial-v1
protocol: serial
match:
  vid: "2341"
  pid: "0043"
  model: "arduino-multisensor-v1"
connection:
  baudRate: 115200
  frameFormat: json-line
  manifestCommand: "WHOAMI"
adapter:
  image: "registry.example/device-serial@sha256:..."
  parser: "arduino-multisensor-v1"
  serviceName: "device-serial"
profile:
  name: "arduino-multisensor-v1"
  file: "profiles/arduino-multisensor-v1.yaml"
security:
  approvalRequired: true

Catalog 요구:

  • schema validation
  • immutable digest image allowlist
  • profile와 parser allowlist
  • exact match 우선
  • 여러 항목이 동시에 match되면 자동 선택하지 않고 BLOCKED
  • API 요청으로 임의 image 실행 금지
  • 재시작 시 자동 반영하고 안전한 reload 기능 제공
  • 잘못된 Catalog 항목은 전체 서비스 대신 해당 항목을 격리하고 오류를 기록

8. API

기존 FastAPI와 BFF 패턴을 재사용하고 기존 /management/* API의 하위 호환성을 유지한다. 최소 API는 다음과 같다.

  • GET /api/v1/discovery/candidates
  • protocol, nodeId, state, presence 필터
  • pagination
  • GET /api/v1/discovery/candidates/{candidateId}
  • POST /api/v1/discovery/candidates/{candidateId}/approve
  • 승인자와 사유 기록
  • POST /api/v1/discovery/candidates/{candidateId}/reject
  • 거절 사유 기록
  • POST /api/v1/discovery/candidates/{candidateId}/retry
  • POST /api/v1/discovery/reconcile
  • 전체 또는 nodeId, protocol 선택
  • GET /api/v1/discovery/plans/{nodeId}
  • PUT /api/v1/discovery/plans/{nodeId}
  • GET /api/v1/registrations/{candidateId}
  • GET /api/v1/catalog/bindings
  • GET /api/v1/discovery/events

명확한 오류 code와 message를 반환하고 OpenAPI를 제공한다. 동일 승인 요청을 반복해도 Device를 중복 생성하지 않는다. mutation API는 인증과 idempotency key를 요구한다.

9. EdgeX 등록 Saga

승인 후 다음 순서를 지킨다.

  1. candidate presence 확인
  2. 대상 KubeEdge node Ready 또는 사용 가능 확인
  3. AuthProvider 승인 확인
  4. Catalog binding 재검증
  5. 기존 Device Service Runtime 재사용 가능 여부 확인
  6. 필요할 때 검증된 template으로 Runtime 생성
  7. Device Service health 확인
  8. EdgeX Device Profile 존재 여부 확인
  9. 없으면 Device Profile 등록
  10. Device 존재 여부 확인
  11. 없으면 Device 등록
  12. Core Metadata readback 검증
  13. Core Data 첫 Event 대기
  14. 첫 Event 확인 후 EVENT_CONFIRMED
  15. timeout 시 FAILED와 원인 기록

Rollback 규칙:

  • 이번 Saga가 새로 만든 리소스만 제거한다.
  • 기존 Profile, 기존 Runtime, 다른 장비가 쓰는 리소스는 삭제하지 않는다.
  • 생성 리소스에는 controller ownership label 또는 annotation을 추가한다.
  • retry 시 중복 생성하지 않는다.
  • 각 단계는 재실행 가능한 idempotent operation으로 구현한다.
  • Core Metadata 등록만으로 완료 처리하지 않는다.

10. 영속성

현재 저장소의 DB와 repository layer를 먼저 확인한다.

  1. 안전하게 재사용 가능한 기존 PostgreSQL 또는 repository layer
  2. 기존 SQLite
  3. 별도 안전한 control-plane persistence가 없다면 SQLite와 migration

EdgeX가 소유한 telemetry DB schema에 Controller 테이블을 임의로 섞지 않는다. 다음 정보는 Controller 재시작 후에도 유지한다.

  • 후보와 stable identity
  • 상태 전이 이력
  • 승인·거절 이력
  • 등록 Saga 단계
  • 실패 원인과 retry count
  • Discovery Plan
  • Catalog version 또는 binding ID
  • audit event

11. Kubernetes / KubeEdge 배포

  • Discovery DaemonSet 또는 Deployment
  • Adapter Controller Deployment와 Service
  • ConfigMap, 필요한 Secret 참조
  • 최소 권한 RBAC
  • 정확한 nodeSelector/affinity
  • Serial 장치 접근을 위한 최소 device/volume mount
  • 개발 overlay와 Jetson/Raspberry Pi 예시 설정

보안 경계:

  • privileged: true를 기본 사용하지 않는다.
  • 필요한 device와 host path만 mount한다.
  • /dev 전체 mount가 불가피하면 Agent 전용 예외 이유를 문서화한다.
  • secret을 ConfigMap에 넣지 않는다.
  • token과 certificate는 Secret 또는 외부 secret mechanism으로 공급한다.
  • Controller에 Kubernetes 전체 삭제 권한을 주지 않는다.
  • Controller가 소유하지 않은 리소스는 rollback 또는 삭제하지 않는다.

명세의 factoryName-* 노드명은 예시다. 실제 testbed 노드명은 저장소의 현재 manifest와 설정값을 사용하며 코드에 하드코딩하지 않는다.

12. 보안

  • 미등록·미승인 장비를 지속 수집 Runtime과 연결하지 않는다.
  • API에서 임의 container image, command, privilege, raw hostPath를 받지 않는다.
  • Catalog allowlist의 digest 고정 image만 배포한다.
  • token, certificate, password를 로그 또는 rawMetadata에 저장하지 않는다.
  • network discovery 범위는 allowlist로 제한한다.
  • 승인·거절·차단·인증 실패를 감사 로그에 남긴다.
  • 외부 인증 timeout과 unavailable을 구분해 기록한다.
  • 인증 시스템 장애 시 fail-open하지 않는다.
  • AllowAllMockProvider는 명시적인 개발 profile에서만 활성화한다.

13. 관측성과 운영

구조화 로그에 가능한 범위에서 다음 필드를 포함한다.

health와 readiness endpoint를 제공한다.

14.1 단위 테스트

14.3 Controller 통합 테스트

  • fake Core Data API
  • fake Kubernetes client
  • fake AuthProvider
  • approve → Runtime ready → Metadata registered → Event confirmed
  • Device Service startup 실패
  • Profile 등록 실패
  • 첫 Event timeout
  • retry 후 성공
  • 기존 Runtime과 Profile을 rollback하지 않는지 확인

14.4 API와 재시작 테스트

18. 완료 조건

  1. 코드가 실제 저장소에 반영된다.
  2. Serial 가상 장비가 후보로 발견된다.
  3. 장비 분리·재연결 시 같은 candidateId를 유지한다.
  4. 승인 전에는 EdgeX Device가 생성되지 않는다.
  5. 승인 후 검증된 Device Service만 배포 또는 재사용된다.
  6. EdgeX Device Profile과 Device가 idempotent하게 등록된다.
  7. 첫 Event 확인 후에만 EVENT_CONFIRMED가 된다.
  8. 미지원 장비는 BLOCKED 처리된다.
  9. 실패 원인과 상태 전이 이력이 영속 저장된다.
  10. Controller 재시작 후 상태가 복구된다.
  11. 단위·통합·회귀 테스트가 통과한다.
  12. 실행·배포·시연 절차가 문서화된다.
  13. 완료·부분 구현·미구현·실장비 검증 필요를 정직하게 구분한다.
  14. 기존 서비스와 기존 테스트를 깨뜨리지 않는다.
