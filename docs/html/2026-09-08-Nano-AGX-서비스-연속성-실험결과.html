Nano–AGX 서비스 연속성 실험 결과

실험일: 2026-09-08 · 문서 작성: 2026-09-09 · 분류: 격리 자격시험 / 개발 참고 최종 판정: 실제 Nano → AGX Orin → Nano 왕복 10회와 Nano 단독 비교 10회 모두 합격.

결과를 쉽게 설명하면

Nano에 일이 몰리면 AGX를 준비하고, 준비가 끝난 뒤 새 일을 AGX에 맡겼다. 준비하는 동안에도 Nano는 계속 일했다. 일이 줄면 Nano로 돌려주고 AGX의 모델 메모리를 비웠다. 이 과정을 실제 장비에서 10번 반복했고, 비교 시험까지 17,520건 모두 결과를 받았다.

이는 양쪽 장비가 켜져 있는 상태의 고정 Llama 데모 시험이다. 모든 요청에 지연이 없었다는 뜻은 아니다. AGX 준비와 겹친 요청의 첫 토큰 지연은 최대 2.407초였다. 외부 서비스용 공용 진입점이나 Nano 전원·네트워크 전체 장애 복구를 검증한 결과로 확대하지 않는다.

무엇을 검증했나

목적은 AI 모델 자체의 품질 평가가 아니라, 서비스를 계속 처리하면서 부하 전환·복귀·자원 해제를 수행할 수 있는지 확인하는 것이다. KubeEdge/Kubernetes는 노드와 workload를 관리하고, 시험 시작·정지·원장 회수는 별도 운영자가 소유한다. 격리된 시험 client가 고정 Kubernetes Service llama-nano, llama-agx 중 요청 대상을 선택한다. Service selector나 EndpointSlice를 동적으로 바꾸지 않는다. EdgeX 물리 디바이스 경로와 기존 센서 서비스를 변경하지 않았다.

  1. AGX는 모델 파일이 SD에 있는 CACHED 상태에서 시작한다. 모델을 GPU에 미리 유지하지 않는다.
  2. Nano의 부하 조건을 만족하면 AGX를 활성화한다. 준비 중 요청은 Nano가 계속 처리한다.
  3. AGX의 실제 추론 응답에서 요청 ID·모델·장비를 확인한 후 새 접수 요청을 AGX에 보낸다.
  4. 전환 전에 Nano에 접수한 요청은 Nano가 마저 처리한다. 복귀 때도 기존 AGX 요청을 마저 처리한다.
  5. 부하 감소 조건과 Nano의 실제 응답을 확인하면 새 요청을 Nano로 돌린다.
  6. AGX의 처리 중·대기 요청이 없고 유휴 시간이 충족되면 모델 메모리를 해제한다.

모델 메모리 해제 이후에도 AGX 관리 Pod와 GPU 공유 슬롯은 유지한다. 실행 중 요청이나 LLM의 KV-cache를 다른 장비로 옮기는 방식은 아니다.

먼저 고정한 기준

저부하 TTFT와 바쁜 상태의 직렬 처리시간을 각각 3회 측정했다. 부하 단계별 시험에서 Nano의 검증 처리율은 4.0건/초였고, AGX의 4.8건/초 수용은 별도 3회, 총 432건으로 확인했다. SD에서 AGX를 준비하는 시간도 10회 측정한 후 baseline과 정책을 동결했다.

첫 실패와 수정 근거

첫 v2-sd-01 왕복도 876건을 모두 처리하고 AGX 전환·Nano 복귀·모델 해제를 수행했다. 그러나 정상 구간 p95 TTFT가 6,640.0ms로 S를 넘어 실패했고, 후속 반복을 자동 중단했다.

원인은 요청이 늘수록 접수·전송·첫 토큰·완료마다 누적 JSON 전체를 다시 저장하는 기록 경로였다. 실제 실패 원본으로 수행한 로컬 진단에서 전체 저장 중앙값은 39.44ms, 변경 항목 저장은 4.11ms였다. 이는 로컬 원장 비용 비교이며 Jetson 추론 성능 측정값이 아니다.

요청·이벤트·표본별 변경분을 저장하도록 수정하면서 SQLite WAL과 synchronous=FULL을 유지했다. 전송 의도와 dispatch 이벤트는 네트워크 전송 전에 같은 트랜잭션으로 확정한다. 재시작 시 변경분을 합쳐 원장을 복구하며, 이미 전송해 결과가 불확실한 요청을 자동 재실행하지 않는다.

그 후 같은 기준선·정책·부하로 v2-sd-02에서 10쌍을 처음부터 다시 실행했다. 첫 실패 기록은 보존했으며 성공 부분만 골라 최종 10쌍에 섞지 않았다.

종료 상태와 검증 범위

2026-09-08 22:48 KST 종료 확인 기록에서 Nano는 추론 가능 상태였고, AGX는 CACHED, 모델 VRAM·active·queue 모두 0이었다. SD 여유는 약 122.76GB, AGX eMMC 여유는 약 14.86GB였으며 저장소 점검을 통과했다. 7개 노드는 Ready이고 Disk/Memory/PID pressure가 없었다. 기존 Llama·EdgeX Pod의 UID·컨테이너 ID·재시작 횟수·Ready 상태는 시험 시작 기록과 같았다. 이 수치는 실험 종료 당시 관측이며 현재 실시간 상태를 대신하지 않는다.

원격 전체 판정과 내보낸 원본 20회로 재계산한 로컬 판정이 일치했다. 원본·verdict 40개 파일의 SHA-256을 확인했고, 미완료 원장은 없었다. 93개 자동시험을 통과한 코드와 실제 controller 코드 해시가 일치했다.

외부 서비스용 공용 gateway, NEXUS 자동 제어, Nano 전체 전원·네트워크 장애, 긴 생성·다른 모델, 실제 SD 재부팅·실행 중 카드 분리는 이번 시험에 포함하지 않았다. 다음 단계는 이 접수·전송·복귀 계약을 외부 서비스의 공용 진입점에 연결하고 같은 기준으로 검증하는 것이다.
