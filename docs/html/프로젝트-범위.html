프로젝트 범위

이 문서는 현재 코드·배포·테스트와 2026년도 2차년도 PoC 목표 사이의 경계를 고정하는 기준 문서다.

1. 현재 PoC의 중심

현재는 대규모 동적 오케스트레이션을 완성하는 단계가 아니다. 옥동의 PLC·MES·센서 데이터를 실제로 연결하고, 생산품질 판별과 유압펌프·모터 이상감지 서비스를 운영 화면까지 이어서 검증하는 단계다.

2. 현재 구현 범위

데이터 플레인

  • 물리 장비 입력은 Protocol Adapter가 소유한다.
  • Adapter는 canonical EdgeX v3 Event를 생성한다.
  • edge-telemetry-agent는 Event를 SQLite WAL outbox에 먼저 commit한다.
  • 중앙 연결이 복구되면 HTTPS/mTLS로 gateway에 재전송한다.
  • gateway는 Core Data 저장 결과를 확인한 뒤에만 persisted ACK를 반환한다.
  • Core Metadata는 Device/Profile/Device Service inventory의 원본이다.
  • Core Data/PostgreSQL은 Event/Reading과 이력의 원본이다.

운영 플레인

  • KubeEdge/Kubernetes는 edge node와 workload의 배치·재시작·상태 진단만 담당한다.
  • state-aggregator는 Core Metadata/Core Data와 Prometheus/Kubernetes 상태를 읽어 dashboard API를 제공한다.
  • dashboard의 workflow 화면은 현재 browser-local 구성, validation, execution-plan preview만 수행한다.
  • dashboard의 자원 풀은 데이터 입력, 노드 진단, 특수 실행 후보, 서비스를 읽기 전용으로 구분한다. 특수 실행 후보는 registry ID가 일치하는 Pod, Pod Ready, Service endpoint, 명시적 바인딩 상태가 모두 확인된 경우에만 선택 가능 상태로 표시한다.
  • 노드 health와 배치 가능성은 실행 runtime 또는 물리 디바이스 availability의 증거로 대체하지 않는다. 자원 풀 API와 화면은 Kubernetes apply/delete/restart, EdgeX mutation, command, migration/offloading을 수행하지 않는다.

서비스 플레인

  • 품질 판별 서비스: MES 생산 건과 센서 window를 받아 양품/불량 결과를 만든다.
  • 펌프·모터 이상감지 서비스: 진동·전류·온도 등 입력 window를 받아 이상 점수와 원인을 만든다.
  • 결과는 서비스별 schema로 저장하되, Device/Event 식별자는 EdgeX 계약을 유지한다.

3. 2차년도 설계 범위

다음은 현재 기능의 즉시 완료가 아니라 단계적 승격 대상이다.

  • 물리 Device를 참조하는 virtual-device 인스턴스
  • capability/resource/I/O를 보유한 Device Twin
  • 여러 입력을 묶는 workflow source/binding
  • AI 서비스 컨테이너의 엣지·서버 배치 후보
  • 장애 시 재실행·재배치 정책

Slice 0: virtual-device 읽기 전용 projection

현재 실행 범위에는 state-aggregator에 추가하는 read-only virtual-device projection만 포함한다. 기본 설정에서는 비활성이고, 이번 실행에서는 주입한 테스트·로컬 개발 설정으로만 활성화한다.

  • EdgeX Core Metadata는 Device/Profile/Device Service identity와 상태의 권위이고, EdgeX Core Data는 Event/Reading 이력의 권위다. projection은 telemetry를 저장하거나 이들 원본의 fallback이 되지 않는다.
  • 설정된 물리 Device와 resource를 stable input ID로 참조하고, capability·source·resource와 선언형 AI field를 명시적으로 매핑한다. 각 입력은 원본 Event provenance를 완전하게 보존한다.
  • ready는 권위 있는 Device/Profile identity·상태와 필요한 resource, 신선한 입력, 완전한 provenance가 모두 확인된 경우에만 성립한다. identity·상태·이력·전송·형식 오류와 불완전한 이력은 명시적인 비준비 또는 실패 계약으로 노출한다.
  • KubeEdge/Kubernetes는 node·workload 관측 책임만 유지한다. 현재 workflow는 계속 dry-run이다.
  • Kustomize, Argo, ingress, 접근 정책, 배포, live activation은 이 Slice에 포함하지 않으며 별도 승격 gate로 미룬다.

새 기능을 운영 기능으로 승격할 때는 범위, API, 권한, 실패 처리, 테스트, 배포 manifest를 이 문서와 저장소 구조에 먼저 추가한다.

4. 프로토콜 지원 원칙

프로토콜 현재 문서상 지위 승격 조건
I2C Sense HAT fixture와 direct telemetry 검증 실제 endpoint, Profile, Event, freshness, 서비스 소비
Serial adapter/agent 설계·테스트 wave pseudo terminal과 실장비 재연결·장애 검증
Modbus 확장 계약/시뮬레이터 범위 지정 endpoint·unit ID와 register map 검증
OPC-UA 확장 계약 등록된 endpoint, browse identity, Profile 검토
MQTT optional compatibility 입력 자기등록 schema, broker, topic, idempotency 검증
RTSP/ONVIF 영상 workflow 별도 경로 RTSP 직접 구독과 결과 metadata만 EdgeX 전달

지원하지 않은 wave는 UI나 문서에서 “등록 완료”로 표시하지 않는다.

5. 제외 범위

  • 전체 공장망 자동 스캔
  • 발견 즉시 자동 신뢰·자동 등록
  • 임의 container image 실행
  • 운영자 승인 없는 actuator command
  • RTSP frame의 Core Data 저장
  • LLM 기반 전역 제어
  • workflow_executor, workflow_reporter, placement_engine의 현행 기능 승격
  • MapperFramework, KubeEdge Device/DeviceStatus, mapper direct-to-Influx의 병행·fallback authority화

6. 현재 checkout과 live 차이

root 배포 진입점은 edgex/k8s/kustomization.yaml이다. 현재 checkout render와 과거 live Argo revision의 discovery/controller/Device Service 구성 차이는 별도 증거로 기록한다. live에서 관찰됐다는 이유만으로 checkout에 존재한다고 쓰지 않는다.

7. 완료 기준

현재 서비스 데모는 다음을 모두 확인해야 완료로 판정한다.

  1. 입력 Device/Profile과 Protocol Adapter가 명시돼 있다.
  2. EdgeX Event가 outbox부터 Core Data까지 동일 ID로 추적된다.
  3. 장애 동안 데이터가 보존되고 복구 후 중복 없이 재전송된다.
  4. AI 서비스가 입력 window와 모델 버전을 기록한다.
  5. 결과와 알림을 API/dashboard에서 조회한다.
  6. 운영자가 장애 위치와 다음 조치 명령을 runbook으로 재현한다.
