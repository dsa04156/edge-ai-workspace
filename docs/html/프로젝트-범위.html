목적

이 문서는 현재 PoC에서 무엇을 구현 범위로 볼지, 무엇을 현재 연구 방향에서 제외할지 정리한다. 레포 안에는 현재 구현물, 과거 실험, 운영 도구, 연구 문서가 함께 있으므로 새 작업 판단은 이 문서를 기준으로 한다.

현재 PoC 범위

현재 범위는 혼합 디바이스 엣지 AI 플랫폼을 실공장 기반 서비스 데모 관점에서 설명 가능하게 만들고, 물리 endpoint를 정식 EdgeX Device Service/Profile/Device로 연결해 중앙 EdgeX와 대시보드에서 같은 identity로 관리하는 것이다.

권위 있는 현재 아키텍처:

물리 센서 / PLC / 장비
  -> Jetson 또는 Raspberry Pi의 EdgeX Device Service
  +-> EdgeX Event / Reading -> 중앙 Core Data -> PostgreSQL
  +-> bounded Local Data API -> 같은 node의 고정 AI consumer
      -> state-aggregator / dashboard

포함하는 방향:

  • Jetson과 Raspberry Pi에서 실제 protocol endpoint를 소유하는 EdgeX Device Service
  • Device SDK 기반 protocol 연결, 재연결, resource 표준화, 상태와 지원 command
  • etri-ser0002-cgnmsb에 한 세트만 배치하는 ingest gateway, EdgeX Core Keeper, Core Metadata, Core Command, 내부 MessageBus, Core Data, PostgreSQL
  • EdgeX Core Metadata Device/Profile 기반 inventory·schema·관리 상태
  • Core Data Event/Reading 기반 typed telemetry와 freshness
  • 합성 identity를 사용하는 Core Data REST → PostgreSQL 1,000-device 저장 기준선 도구와 운영 절차. 운영 Metadata/Device와 root render에는 포함하지 않음
  • 선택한 Device의 Core Data history를 state-aggregator API로 조회하고 요청 범위·반환 Reading 수·실제 구간을 구분해 표시하는 dashboard
  • 같은 edge node의 Workflow Pod가 사용하는 bounded memory recent cache와 read-only Local Data API; 현재 Flannel에서는 client label 기반 NetworkPolicy가 강제되지 않음
  • Jetson에서 Arduino 가속도 X/Y/Z를 실시간에 가까운 주기로 읽어 변화 점수를 계산하는 고정 sensor-anomaly-demo Deployment
  • Jetson, Raspberry Pi, x86 서버가 함께 있는 mixed-device 환경
  • Prometheus/Kubernetes 기반 node/workload 상태 수집
  • 디바이스와 AI 서비스·storage·dashboard의 연결 구조
  • 서비스 데모 시나리오와 생산성 향상 효과 설명

KubeEdge 범위는 Kubernetes edge node와 workload 관리로 제한한다. EdgeX Metadata의 Device/Device Profile은 KubeEdge Device/DeviceModel CRD와 서로 다른 관리 객체다. KubeEdge DeviceStatus, MapperFramework, mqttvirtual과 mapper direct-write는 legacy physical integration이며 현재 plane의 병행 경로나 fallback이 아니다.

2026-07-21에 edgex-edge-agent-jetson, edgex-edge-agent-sensehat, 두 outbox PVC와 Agent 전용 Metadata bootstrap을 퇴역했다. 대신 root render는 edgex-edge에 공식 EdgeX Device SDK 기반 device-serial-jetson, device-sensehat-raspi와 각 최소 NetworkPolicy를 배포한다. 중앙 EdgeX와 ingest gateway는 유지하지만, ingest gateway는 현재 Serial/I2C Event 경로에 참여하지 않는다.

1차 수직 슬라이스는 etri-dev0001-jetorn의 Arduino Uno다. /dev/serial/by-id/... CharDevice를 Pod의 /dev/arduino-001에 단독 마운트하고 device-serial-jetson이 공유 reader 1개로 읽는다. temperature, light, magnetic, acceleration X/Y/Z는 각각 1-resource Profile과 virtual-*-001 Device로 등록되며 Core Data Event, Core Command GET과 dashboard의 독립 identity가 된다. Device Service 메모리는 Device/resource별 최근 10분·최대 10,000 sample을 보존하고 latest/recent Local Data API를 제공한다. 이 cache는 Pod 재시작 시 사라지며 durable outbox나 offline replay가 아니다.

두 번째 수직 슬라이스는 etri-dev0003-raspi5의 Sense HAT v1이다. device-sensehat-raspi가 exact /dev/i2c-1 CharDevice를 직접 소유하고 RTIMULib reader를 내부 protocol module로 실행한다. temperature, humidity, pressure, compass, orientation, gyroscope는 Profile/Device 6개로 등록되고 총 11개 Float64 resource를 제공한다. physical sensehat-001은 protocol/tag source ID이며 aggregate EdgeX Device가 아니다. 동일한 10분·10,000 sample recent cache, Local Data API와 read-only command 계약을 사용한다.

현재 root render에는 device-mqtt와 edge-local broker가 없다. MQTT-only 장비가 들어오면 별도 Device Service와 프로토콜별 검증 gate를 추가한 뒤에만 배포한다. Serial과 Sense HAT I2C 정상 경로만 지원 증거가 있으며 Modbus와 OPC-UA는 profile·실장비·telemetry 검증 전까지 완료로 주장하지 않는다. RTSP frame은 Workflow Pod가 직접 구독하는 별도 media 경로다.

첫 서비스 데모 consumer는 edge-orch/sensor-anomaly-demo/다. 이 고정 Deployment는 etri-dev0001-jetorn에서 device-serial-jetson.edgex-edge.svc.cluster.local:59910의 Local Data API를 500ms마다 조회한다. virtual-acceleration-{x,y,z}-001의 같은 nanosecond origin을 한 frame으로 결합하고, 30개 warm-up 뒤 online Gaussian baseline으로 magnitude 변화 점수를 계산한다. 두 번 연속 threshold 이상이면 anomaly, 세 번 연속 정상 범위면 clear한다. 이는 학습된 고장 분류기나 push stream이 아니며, 실제 장치를 움직여 anomaly가 발생하는 현장 실증은 별도 gate다.

state-aggregator의 /state/service-demo와 대시보드는 이 derived 결과와 physical source → Device Service → 세 EdgeX Device → AI consumer binding을 read-only로 표시한다. Device 선택 시 /state/devices/{device_id}/telemetry가 Core Data history를 조회하며 dashboard가 PostgreSQL에 직접 연결하지 않는다. UI는 5분·30분·1시간·24시간 범위와 새로고침을 제공하고 최신 1,000 Event 제한, 반환 Reading 수와 실제 구간을 분리해 보여 준다. EdgeX Core Metadata/Core Data의 raw inventory·telemetry 권위는 바뀌지 않는다. 이 고정 Deployment를 동적 Workflow Builder, runtime migration 또는 offloading 완성으로 설명하지 않는다.

노드 장비 발견과 등록 후보 관리

edge-device-discovery DaemonSet은 지정된 세 edge node에서 30초마다 USB Serial의 stable /dev/serial/by-id/* symlink와 /dev/i2c-N 버스 존재를 read-only로 관측한다. I2C 후보는 버스가 있다는 뜻일 뿐 특정 센서 주소가 응답하거나 Sense HAT이 연결됐다는 뜻이 아니다. 능동 I2C 주소 probe와 네트워크 대역 scan은 수행하지 않는다. MQTT, Modbus, OPC-UA, RTSP, REST는 운영자가 대시보드에서 node와 endpoint를 후보로 직접 선언한다.

edge node의 수동 관측
  -> HMAC 서명 report
  -> edgex-adapter-controller
  -> edgex-device-discovery-registry ConfigMap
  -> state-aggregator /management/discovery
  -> 대시보드 검토 대기·승인·무시
  -> exact Git hardware binding + 검증 package 일치
  -> 기존 EdgeX 등록 마법사

발견 후보는 onboarding 전 임시 staging 정보다. present는 해당 stable path나 I2C 버스를 최근 report에서 다시 봤다는 뜻이고, declared는 수동 endpoint 선언, stale은 관측 report가 기준 시간을 넘겼다는 뜻이다. 어느 값도 Core Metadata Device, Device Service 통신, operatingState=UP 또는 first Event를 대신하지 않는다. 후보 accepted도 운영자 검토 결과일 뿐 자동 등록·자동 설치가 아니다.

  • exact node/protocol/path가 Git Adapter Catalog의 등록 binding과 일치하고 package가

검증된 후보만 registration-ready다.

  • 새 Serial path, I2C 버스나 미검증 네트워크 protocol은 각각 binding-required 또는

verification-required로 남고 설치·등록 실행으로 이어지지 않는다.

  • 수동 후보의 삭제는 목록에서 숨기는 soft delete다. 자동 관측 후보는 다시 나타날 수 있으므로

삭제 요청을 ignored tombstone으로 처리한다.

  • 비밀번호, token, secret 성격의 property와 자격 증명이 포함된 URL은 후보에 저장하지 않는다.
  • 후보는 최대 2,000개, 직렬화 payload는 900KB 미만으로 제한한 namespaced ConfigMap에

resourceVersion 조건부 갱신으로 보관한다. 이는 장기 inventory DB나 KubeEdge Device CRD가 아니다.

  • 발견 Agent의 read-only /dev, /sys mount는 고정된 수동 관측 전용이다. 대시보드가

임의 hostPath, image, command 또는 privileged workload를 제출하는 경로는 없다.

대시보드 노드별 Adapter Runtime과 Device 연결 관리

state-aggregator의 디바이스 관리 화면은 운영자가 KubeEdge 노드를 먼저 선택하고, 그 노드의 Adapter Runtime과 EdgeX Device 연결을 한 흐름으로 관리하는 Current 경로다. GET /state/nodes, Runtime targetNode, Device node_name/tags.nodeName과 등록 hardware binding을 하나의 노드 범위로 합성하되, 이 합성은 배치·운영 탐색용이다. 브라우저는 Kubernetes API에 직접 접근하지 않으며, state-aggregator가 내부 HMAC으로 별도 edgex-adapter-controller를 호출한다. Controller는 Git에서 검증·등록한 template와 hardware binding만 edgex-edge namespace에 reconcile한다. Profile, Device와 Device Service binding의 권위는 Core Metadata, 첫 Event와 Reading의 권위는 Core Data에 그대로 남는다.

  • Runtime inventory, 재사용·배포 plan과 통합 connection validation은 mutation 없는 조회다.
  • POST /management/connections, runtime restart/retire와 기존 Device allowlist PATCH는

관리자 Bearer token과 Idempotency-Key를 요구한다.

  • 현재 운영 manifest는 DEVICE_MANAGEMENT_ENABLED=true,

ADAPTER_RUNTIME_MANAGEMENT_ENABLED=true, ADAPTER_RUNTIME_MUTATION_ENABLED=true로 관리 경로를 활성화하되, token과 HMAC key 세 개가 namespace별 edgex-adapter-management-auth Secret에 없으면 Pod가 시작하지 않는다.

  • 기존 device-serial-jetson과 device-sensehat-raspi는 Argo CD 소유 external runtime이다.

대시보드는 상태·consumer와 runtime이 소유한 등록 hardware binding 목록을 조회한다. 요청한 binding이 목록에 있으면 같은 protocol runtime을 재사용하지만 재시작하거나 퇴역하지 않는다.

  • Controller가 만든 AdapterRuntime만 재시작할 수 있다. EdgeX Device consumer가 0개이고

exact runtime 이름 확인이 일치할 때만 퇴역한다.

  • 노드 카드를 바꾸면 등록 연결/장비 관측/통신/데이터 증거, Runtime inventory, protocol

package, hardware binding과 기존 EdgeX Device 목록이 같은 선택 노드 범위로 함께 바뀐다. 연결 마법사의 target node는 노드 카드 선택으로 고정하며 임의 입력할 수 없다.

  • 등록 마법사는 protocol/Device Service를 먼저 고른 뒤 hardware binding과 Runtime 준비

방식을 고른다. 현재 노드에서 사용할 수 없는 installed Adapter와 미검증 protocol도 선택 목록에는 이유와 함께 보이지만 비활성화된다.

  • API 요청은 adapterId, runtime mode, 등록된 target node/hardware binding, Device/Profile

계약만 받는다. 임의 image, command, privilege, raw hostPath, hostNetwork, 고정 ClusterIP/PodIP는 받지 않는다.

  • 각 hardware binding은 Port/BaudRate/DeviceID 또는 Bus/DeviceID처럼

reusePolicy.bindingFields와 정확히 일치하는 protocolProperties를 가진다. 서버는 요청 protocol tuple이 등록 binding과 일치하는지 다시 검증한다.

  • Serial/I2C template는 실장비 검증 상태와 기존 runtime을 표시하지만 현재 등록 binding을

Argo runtime이 점유하므로 auto는 재사용한다. Modbus, OPC-UA, MQTT와 RTSP는 image, profile, 실장비 검증 전까지 unverified/BLOCKED이며 배포 가능 기능으로 표시하지 않는다.

  • 신규 connection은 hardwareBindingId, physicalDeviceId, nodeName을 EdgeX Device

system tag로 기록한다. 연결 등록만으로 물리 장비가 감지됐다고 판단하지 않고 operatingState와 latest Event를 별도 증거로 표시한다.

  • Serial driver는 (Port, BaudRate, DeviceID)별 reader를 만들고 같은 tuple의 여러

ResourceName은 reader를 공유한다. 두 번째 등록 Serial 포트도 같은 Device Service가 처리하므로 센서마다 Pod를 만들지 않는다. 다만 실제 포트를 추가할 때는 stable host identity, exact Pod 장치 마운트, 두 catalog의 binding과 external runtime hardwareBindingIds를 같은 Git 변경으로 등록해야 한다.

  • 같은 service/protocol endpoint와 resource route를 이미 소유한 Device가 있으면

protocol_binding_exists로 차단한다.

  • Connection 상태는 RUNTIME_READY → DEVICE_APPLIED → WAITING_EVENT → ACTIVE를 구분한다.

Event가 아직 없는 장비는 Metadata를 임의로 되돌리지 않는다. 신규 runtime 뒤 Metadata 적용이 실패한 경우에만 consumer 0을 확인하고 해당 runtime의 안전한 퇴역을 시도한다.

KubeEdge는 target node와 workload 상태만 제공하며 AdapterRuntime을 물리 Device inventory로 보지 않는다. KubeEdge Device/DeviceModel/DeviceStatus, MapperFramework와 EdgeMesh는 이 관리 경로에서 수정하지 않는다. Workflow Builder의 device/resource bind, validation과 execution plan은 계속 browser-local dry-run이며 command publish, actuator 실행, migration 또는 offloading을 활성화하지 않는다.

현재 범위의 핵심 표현:

  • 서비스 데모 우선
  • EdgeX Device Service와 Device Profile/Device
  • 중앙 Core Data·server2 PostgreSQL 권위
  • MQTT는 필요가 확인된 장비의 Device Service 검증 이후에만 배포
  • 프로토콜별 독립 migration gate
  • 통합 운영 가시화
  • 실공장 기반 PoC
  • 현장 적용성
  • 생산성 향상 효과
  • 단계적 구현

2차년도 설계 트랙

2차년도 협약 방향에서는 현재 PoC의 운영 가시화 기반 위에 다음 구조를 설계 대상으로 둔다. 이 항목은 현재 구현 완료 기능이 아니라 설계 및 프로토타입 승격 대상이다.

  • 물리 온디바이스의 기능, 상태, 자원, 입출력을 엣지 AI 서버 쪽 소프트웨어 인스턴스로 표현하는 가상디바이스
  • 물리/가상디바이스의 상태, capability, resource, I/O, workflow binding을 관리하는 디바이스트윈
  • AI 서비스를 stage 단위로 구성하고 가상디바이스를 동적으로 연결하는 워크플로우
  • 컨테이너 기반 워크플로우 통합 개발도구와 validation/실행 계획 UI
  • 가상디바이스/엣지 상태 기반 워크로드 스케줄링과 자원 재배치 정책

기준 문서:

  • docs/2차년도-가상디바이스-워크플로-설계.md
  • docs/(2차년도협약용) 연구개발계획서-엣지 컴퓨팅 시스템을 위한 대규모 혼합 디바이스 제어·관리 플랫폼 개발_0415.pdf

주의:

  • 이 트랙의 가상디바이스는 test_device.py가 가짜 값을 MQTT로 publish하는 legacy test device를 뜻하지 않는다.
  • 이 트랙의 워크플로우는 기존 edge-orch/workflow_executor/, workflow_reporter/, placement_engine/ 구현을 그대로 현재 기능으로 승격한다는 뜻이 아니다.
  • 새 workflow 구현은 별도 설계와 검증 기준을 갖는 2차년도 프로토타입 경로로 다룬다.

보존 프로토타입: Serial JSON Virtual Device Runtime

virtual-device/는 물리 디바이스의 Serial JSON 프로토콜과 원본 필드명을 profile 기반 표준 MQTT telemetry로 변환했던 2차년도 보존 프로토타입 경로다. 물리 디바이스 데이터 수집, 표준화, 로컬 MQTT 발행, 연결 상태와 heartbeat까지만 담당하며 AI 서비스가 아니다.

이 프로토타입에는 KubeEdge CRD, MapperFramework 수정, EdgeX, 중앙 telemetry 전송, Virtual Device Registry, dashboard, AI 실행, 자원 증강, offloading을 포함하지 않는다. sensor-collector/serial_mqtt_collector.py와 virtual-device/는 서로 자동 대체/결합하지 않는 보존 프로토타입 또는 legacy comparison 경로다. 둘 다 EdgeX Serial migration wave 완료, current physical-device plane 또는 fallback으로 간주하지 않는다.

프로토타입 승격 후보: Runtime Resource Augmentation Scheduler v1

2026-06-19 기준 다음 작업 후보는 자원증강 리소스를 수동 실행 버튼으로 호출하는 것이 아니라, runtime 관측값을 기반으로 자동 스케줄링 판단까지 이어지는 최소 경로다. 현재 완료된 자원증강 상태 집계와 dashboard 가시화 위에 pod/service 사용량, resource pressure, capability matching, selected augmentation resource 상태를 얹는 형태로 다룬다.

포함할 수 있는 범위:

  • Prometheus/Kubernetes에서 관측한 pod/service CPU/GPU/memory 사용량을 자원증강 판단 입력으로 사용
  • AugmentationResource와 DeviceAugmentation의 Available/Ready 상태를 scheduling 후보 필터로 사용
  • 대상 edge workload와 보강 resource 사이의 capability matching, pressure reason, selected resource role을 status로 기록
  • dashboard에는 "왜 증강 대상인지", "어떤 자원이 선택됐는지", "현재 적용/대기/불가 상태인지"를 표시
  • 실제 Kubernetes mutation은 dashboard나 버튼이 아니라 별도 scheduler/controller 정책 경로에서만 수행

포함하지 않는 범위:

  • 수동 실행 버튼으로 임의 Job을 생성하는 흐름
  • 고정 샘플 payload로 analyzer endpoint를 호출하는 smoke-test 실행
  • dashboard/state-aggregator가 승인 Controller를 우회해 임의 Kubernetes

apply/delete/restart를 수행하는 구조

  • runtime migration
  • cost model 기반 전역 최적화
  • legacy workflow_executor, workflow_reporter, placement_engine의 현행 기능 승격
  • agent-assisted planning 또는 LLM 기반 전역 제어

  • 동적 workflow 분해/실행
  • runtime replanning
  • placement engine 기반 자동 재배치
  • cost model 기반 offloading 판단
  • workflow_executor 중심 orchestration
  • workflow_reporter 중심 stage event pipeline
  • agent-assisted planning layer
  • LLM이 전체 플랫폼 제어를 수행하는 구조
  • 전체 플랫폼 자율 제어형 orchestration

이 항목들과 KubeEdge Device/DeviceModel/DeviceStatus, MapperFramework, mqttvirtual, mapper direct-write physical-device 경로는 필요한 경우 Legacy / Reference 또는 Archive 자료로만 다룬다. 현재 구현 요구사항, 발표자료의 현행 기능, 병행 status/control plane, fallback, 또는 다음 확정 단계처럼 해석하지 않는다.

문서 작성 원칙

현재 문서와 발표자료에서는 다음 표현을 사용한다.

유지할 표현:

  • 서비스 데모 우선
  • 디바이스-서비스 연결 구조
  • 통합 운영 가시화
  • 실공장 기반 PoC
  • 현장 적용성
  • 생산성 향상 효과
  • 단계적 구현

피할 표현:

  • dynamic offloading을 다음 구현 목표처럼 제시하는 표현
  • 전체 플랫폼 자율 제어형 orchestration을 실증 완료처럼 보이게 하는 표현
  • LLM 기반 전역 제어를 현재 기능처럼 보이게 하는 표현
  • 동적 workflow 실행이 이미 완료된 것처럼 보이는 표현
  • agent-assisted planning을 현재 연구 방향처럼 제시하는 표현
  • 고도화 기능이 이미 실증 완료된 것처럼 보이는 표현

작업 판단 기준

새 작업을 시작할 때는 다음 순서로 판단한다.

  1. 서비스 데모 또는 디바이스-서비스 연결 구조에 직접 기여하는가?
  2. 통합 운영 가시화 또는 상태 판단을 명확하게 하는가?
  3. 중앙 EdgeX Core Metadata의 inventory/schema와 Core Data/PostgreSQL의 persistence authority, protocol별 Device Service connection-owner gate를 지키는가?
  4. 실공장 기반 PoC와 현장 적용성 설명에 도움이 되는가?
  5. workflow/offloading/agent-planning 계열로 다시 확장되는 작업은 아닌가?

1~4에 해당하면 현재 범위에 포함한다. 5에 해당하면 현재 작업에서 제외하거나 archive/reference로 분리한다.
