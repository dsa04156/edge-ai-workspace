프로젝트 범위

목적

이 문서는 저장소의 현재 구현, 후속 설계와 과거 실험을 구분하는 최상위 기준이다. 문서와 대시보드는 실제 endpoint·manifest·테스트 근거가 없는 기능을 완료로 표시하지 않는다.

현재 범위

물리 디바이스와 데이터

  • EdgeX Core Metadata의 Device/Profile/Device Service를 inventory와 schema 권위로 사용한다.
  • EdgeX Device Service가 Serial·I2C 등 승인된 endpoint를 직접 소유하고 값을 표준화한다.
  • EdgeX Core Data의 Event/Reading과 origin을 telemetry·freshness 권위로 사용한다.
  • 중앙 EdgeX Core와 PostgreSQL은 etri-ser0002-cgnmsb에 한 세트만 배치한다.
  • KubeEdge는 edge node와 workload 관리에만 사용한다.

현재 수직 슬라이스

물리 source 노드 수집 Runtime EdgeX Device
Arduino Uno etri-dev0001-jetorn device-serial-jetson 온도·조도·자기·가속도 X/Y/Z 6개
Sense HAT v1 etri-dev0003-raspi5 device-sensehat-raspi 환경·자세·자이로 6개

두 Runtime은 같은 물리 연결을 여러 기능별 Device로 fan-out한다. arduino-001과 sensehat-001은 물리 source ID이며 aggregate EdgeX Device가 아니다.

device-serial-jetson에는 established stream 오류 뒤 25·50·100·200ms fast-retry, 첫 유효 sample의 SDK async enqueue 완료 시점까지의 복구시간 계측, 400ms 개발 gate metric과 read-only stats API가 배포돼 있다. 후속 image는 port ready·first byte·first valid frame 구간도 분리한다. 최초 실장비 canary 1회는 2,215.225ms로 실패했고, 같은 50ms 단절의 후속 원인 진단 6건도 1건 통과·5건 실패했다. 실패 5건에서 port ready는 61~85ms였지만 첫 byte 대기가 약 1.75초로 반복돼 이 구간이 지배 병목으로 확인됐다. 30회 max ≤ 400ms qualification은 여전히 실패 상태이며 400ms 달성을 주장하지 않는다. Kubernetes node/Pod 전체 failover와 통신 단절 중 durable 저장·재전송은 별도 범위다. 상세 측정 경계는 가상화 노드 오류 복구시간을 따른다.

서비스와 운영 화면

  • sensor-anomaly-demo 고정 서비스와 application-owned SQLite 결과·알림 저장
  • HAMi GPU와 CUDA probe를 사용하는 Server1 observed-only 추론 후보. 2026-08-18 현재

기준선 후보는 부하 실험에서 성능 자격이 거부되어 요청을 전환하지 않는다.

  • Git ServiceDescriptor 기반 서비스 목록과 실행 DAG
  • EdgeX·Kubernetes·Prometheus를 결합하는 state-aggregator read model
  • 센서 freshness, 노드/workload와 서비스 입력·모델·결과의 가시화
  • 대시보드 서비스 운영 화면에서 Runtime Recommendation의 상태·reason code·dwell,

기존 Placement Engine이 반환한 전체 후보와 read-only Execution Plan·판단 이력을 조회

  • 디바이스 상세에서 Prometheus 실사용률과 Kubernetes allocatable/requested/available을

서로 다른 근거로 분리 표시

  • 브라우저 안에서만 동작하는 workflow 설계·validation·execution plan preview

제한된 AI 서비스 신규 배포

  • state-aggregator의 POST /api/deployments는 기존 서비스 자원 프로파일과

/api/placements/select 결과를 이용해 단일 replica의 신규 Deployment만 생성한다.

  • 배포 대상은 전용 edge-ai-workloads namespace로 고정하고, 선택 노드는 exact hostname

nodeSelector와 required node affinity를 함께 적용한다.

  • CPU·memory와 accelerator requests는 완전하게 선언된 단일 Pod 서비스 프로파일에서

가져온다. 복수 Pod 집계 프로파일과 requests 누락 프로파일은 배포하지 않는다.

  • 입력은 DNS label 배포명, allowlist에 포함된 로컬 registry의 immutable digest image,

선택적 container port/readiness path로 제한한다. raw manifest, env, command, volume, hostPath, privilege, Service와 Ingress 입력은 받지 않는다.

  • Controller service account는 전용 namespace의 Deployment create/get/list/watch와

기존 Pod 관측 권한만 가진다. update·patch·delete 권한은 갖지 않는다.

  • API는 Placement 탈락, Deployment 생성 성공·실패, Pod Ready와 Kubernetes 실패 reason을

명시적으로 반환한다. 이 경로는 shared-token으로 보호되는 개발 테스트베드용이다.

Runtime Recommendation Engine

  • Git ServiceDescriptor에서 runtime recommendation policy와 observability adapter가

선언된 AI 서비스만 지속 감시한다.

  • Kubernetes Deployment/StatefulSet, Pod와 Node 상태, Prometheus 자원 사용량, 서비스가

제공하는 입력 freshness·model readiness·latency·backlog·throughput을 서로 다른 근거로 유지한 채 결합한다.

  • 판단 상태는 NORMAL, OBSERVING, AUGMENT_RECOMMENDED,

REPLACE_RECOMMENDED, BLOCKED이며 threshold 진입/회복 기준을 분리한 hysteresis, dwell과 cooldown을 적용한다.

  • EdgeX 입력 장애·stale, model 미준비, 필수 관측 누락은 자원 부족으로 해석하지 않고

BLOCKED와 명시적 reason code로 반환한다.

  • 증강·대체가 필요할 때 현재 실행 노드를 제외하고 기존 Placement Engine으로 후보를

다시 Filter/Score한다. 결과에는 최적 노드와 현재 노드를 포함한 전체 후보의 reasonCodes를 보존한다.

  • dwell timer, latch, cooldown과 최신 판단은 PVC의 SQLite에 저장하며 상태 변화와 판단

근거 이력을 조회 API로 제공한다.

  • 이 엔진은 read-only 추천만 수행하며 Deployment 생성·수정·삭제, Service routing,

traffic cutover, migration과 offloading을 실행하지 않는다.

sensor-anomaly-demo 제한적 Runtime Offloading PoC

이 절은 로컬 구현과 2026-08-26 격리 smoke test 범위다. 2026-08-28 Argo 배포 기준선에는 포함되지 않으며 현재 production 요청은 edge-local에 유지된다.

  • 전체 workload를 옮기는 REPLACE_RECOMMENDED 경로와 별도로, ACTIVE

sensor-anomaly-demo가 입력 수집·전처리·결과 저장을 Jetson에 유지하고 승인된 Server1 endpoint에 추론 요청만 전달하는 서비스 전용 부분 오프로딩 경로를 둔다.

  • edge worker의 공통 InferenceExecutor 계약 아래 local executor와 remote executor를

분리한다. Remote 요청은 Git에 고정된 service/model/target 계약과 requestId를 사용하며, 응답 identity·model version·freshness를 검증한 한 결과만 application-owned SQLite에 authoritative result로 저장한다.

  • Kubernetes Lease는 누가 production polling·저장을 수행하는지를 계속 결정한다. 오프로딩은

그 ACTIVE workload 내부에서 추론 위치만 LOCAL, REMOTE, LOCAL_FALLBACK으로 바꾸며 source Deployment·PVC·Service·EdgeX inventory를 수정하지 않는다.

  • timeout, 연결 실패, endpoint/model 미준비, 잘못된 응답, model version 불일치 또는 지속적인

latency 한계 초과는 즉시 local executor로 fail over한다. 늦거나 중복된 remote 응답은 기존 결과를 덮어쓰지 않는다.

  • Runtime Recommendation은 node/workload failure에는 기존 전체 REPLACE_RECOMMENDED를

우선한다. 정상 workload의 지속 자원·서비스 압력에는 Git offloading contract, remote Pod/API readiness, network latency와 기존 Placement Filter/Score를 모두 통과한 경우에만 OFFLOAD_RECOMMENDED를 반환한다.

  • 현재 baseline-1.0.0 Server1 후보의 성능 자격은 2026-08-18 실험에서 rejected다.

구현과 장애 fallback 시험이 성공해도 이 실험 gate를 우회해 자동 오프로딩을 권고하거나 운영 경로로 자동 승격하지 않는다. LOCAL→REMOTE 변경은 승인 Secret을 사용하는 서비스 전용 API 또는 검토된 Git overlay에서만 허용하며 자동 추천→실행 연결은 범위 밖이다.

  • 이 경로는 모델 분할·distributed inference·범용 workflow stage offloading이 아니다.

첫 PoC 범위는 Jetson 전처리 → Server1 추론 → Jetson 결과 저장의 단일 서비스 경로다.

  • 2026-08-26 격리 실클러스터 smoke test에서 새 ARM64 edge image와 AMD64 CPU server

image로 LOCAL → REMOTE → server 장애 → LOCAL_FALLBACK protocol 경로와 Jetson의 결과 저장 지속을 확인했다. 첫 REMOTE 결과는 전환 요청 후 약 543ms, remote sample total은 33.46ms(network 33.12ms, server processing 0.34ms), 장애 후 fallback 결과는 scale 요청 뒤 약 1.08s 안에 관측됐다. 이는 GPU 성능 자격이나 운영 자동 오프로딩 승격 근거가 아니며 격리 workload는 시험 후 삭제했다.

Runtime Execution Plan

  • 최신 Runtime Recommendation을 입력으로 사용하는

GET /api/runtime-recommendations/{serviceId}/execution-plan은 실행 가능한 변경 요청이 아니라 운영자·후속 Controller 검토용 read-only 계획을 반환한다.

  • AUGMENT_RECOMMENDED는 신규 인스턴스 생성, Ready 확인, 트래픽 분산 순서로 계획한다.

REPLACE_RECOMMENDED는 대체 workload 생성, Ready 확인, 트래픽 전환, 기존 인스턴스 종료와 조건부 rollback 순서로 계획한다.

  • 각 단계에는 순번, 실행 방식, 대상 node/workload, 선행조건과 실패조건을 명시한다.

계획 ID와 후보 workload 이름은 추천 시각·대상 node·workload identity에서 결정적으로 생성해 동일한 추천의 조회 결과가 흔들리지 않게 한다.

  • NORMAL·OBSERVING은 not_applicable, BLOCKED나 선택 node가 불완전한 추천은

blocked로 반환하고 변경 단계는 만들지 않는다.

  • API 조회는 /api/deployments, Kubernetes apply/update/delete 또는 Service·Ingress와

외부 traffic API를 호출하지 않는다. rollback도 실행 단계가 아니라 조건부 보상 계획이다.

  • 대시보드에서는 이 GET 계획만 실행 계획 / Read-only로 표시하며 승인·실행·적용 버튼과

Execution Controller mutation API를 노출하지 않는다.

승인 기반 Execution Controller

  • 사용자가 최신 plan의 planId를 본문에 다시 제출하고 approved=true, 승인자 식별자와

유효한 관리 token을 함께 제공한 경우에만 실행 record를 만든다. planId는 실행의 idempotency key이며 동일 plan의 재호출은 최초 record를 반환하고 단계를 반복하지 않는다.

  • 현재 실행 코드는 고정 edge-ai-workloads namespace의 create_candidate, verify_ready,

validate_candidate_pre_activation, Git 승인 Kubernetes Lease 계약에 의한 handoff_execution_ownership·verify_active_candidate·rollback_execution_ownership과 Git 승인 Traffic Routing Contract에 의한 switch_traffic, verify_switched_traffic, 실패 시 rollback_traffic까지 구현한다. source workload를 복제하지 않고 Git의 서비스별 Candidate Workload Template에 승인된 immutable image, env, port/probe, resources, securityContext, namespace, architecture/accelerator, state policy만 materialize한다. source Deployment·Service·PVC/StorageClass와 target Node를 읽기 전용 preflight하고 계약 불일치나 미지원 storage는 fail-closed한다.

  • sensor-anomaly-demo v1은 fresh_state다. source의 RWO local-path PVC와 results.db는

candidate에 재사용·복제하지 않고 state mount를 emptyDir로 제공한다. 생성 candidate와 PVC 식별자는 실행 record에 저장하며 현재 PVC 목록은 비어 있다. Candidate Validation은 Git의 서비스별 계약에 따라 handoff 전 SHADOW의 health, fresh input, model ready와 memory-only inference를 확인하고, handoff 뒤 ACTIVE의 production framesProcessed, 실제 결과 freshness와 측정 가능한 latency SLO를 다시 확인한다.

  • Lease는 실제 AI processing 권한만 소유하고 Traffic Manager는 요청 routing만 소유한다.

source와 candidate 중 Lease holder 하나만 ACTIVE이며 holder 전환과 rollback은 resourceVersion CAS, 서비스별 SQLite lock, 영속 snapshot과 audit를 사용한다. Lease 만료, stale holder, 충돌 또는 API 관측 실패 시 workload는 production 처리를 하지 않는다. handoff/active validation 실패 시 source holder로 rollback하고 candidate는 자동 삭제하지 않는다.

  • 단계 상태는 PENDING, RUNNING, SUCCEEDED, FAILED, BLOCKED로 저장한다. 승인,

상태 전이, 실패 reason과 actor를 SQLite 실행 record·append-only audit log에 기록하며 PVC에서 재시작 후에도 유지한다. 중단 시 RUNNING record는 자동 재실행하지 않고 BLOCKED로 복구한다.

  • switch_traffic은 selectorless Service와 Runtime Controller 단독 소유 EndpointSlice가 있고

모든 data-plane consumer의 EndpointSlice 호환성이 입증된 계약에서만 atomic source→candidate cutover를 수행한다. 전환 후 기존 validation 계약을 Service 주소로 다시 실행하고 실패하면 저장한 source routing snapshot으로 즉시 복구한다. Service selector는 수정하지 않는다.

  • 현재 EdgeMesh는 Service·Endpoints를 관측하지만 EndpointSlice 소비가 입증되지 않았고 실제

Service도 Argo CD 소유 selector를 유지하므로 sensor-anomaly-demo routing 계약은 routing_mode_unsupported로 fail-closed다. 따라서 이 서비스의 실클러스터 traffic mutation은 아직 운영 기능이 아니다.

  • 2026-08-26 격리 실클러스터 시험에서는 selectorless Service와 Controller 소유 core

Endpoints로 Jetson source→Raspberry Pi candidate→Jetson source 전환이 실제 HTTP 응답과 EdgeMesh libp2p 로그에서 확인됐다. 이는 후속 runtime-endpoints 모드의 근거이며 현재 runtime-endpointslice Controller나 production Service가 활성화됐다는 뜻은 아니다.

  • distribute_traffic, terminate_current, source/candidate 삭제·promotion은 여전히

unsupported_step이다. source Deployment·PVC는 유지하고 candidate도 자동 삭제하지 않는다.

  • sensor-anomaly-demo Service는 Argo CD automated sync/self-heal 대상이다. Runtime Controller는

Service를 patch하지 않으며, Git이 selectorless 전환과 정적 routing 허용 정책을 소유하고 Runtime Controller가 전용 EndpointSlice의 동적 active endpoint만 소유하는 구조를 승인안으로 둔다.

  • dry-run은 최신 plan 일치, 승인 없이 확인 가능한 preflight와 지원 단계 경계를 반환하며

Kubernetes와 영속 실행·감사 상태를 변경하지 않는다.

2026-08-28 live 기준 source workload가 Lease holder로 ACTIVE이며 Runtime Recommendation은 NORMAL/read_only다. 과거 격리 검증 candidate가 남아 있어도 production traffic이나 source 소유권을 대체하지 않는다. 현재 승인 실행 이력의 최종 상태는 traffic routing 미지원 또는 candidate 장애 검증으로 FAILED이며, 자동 migration/offloading 성공으로 집계하지 않는다.

제한된 장비 관리

  • passive discovery candidate 조회·검토와 exact Catalog binding validation
  • 승인된 Profile/Device 등록 Saga와 first Event 확인
  • Controller가 소유한 Adapter Runtime만 제한적으로 restart·retire
  • 임의 image·hostPath·raw manifest·command 입력 없음
  • 제한된 신규 AI 서비스 배포는 별도 allowlist와 immutable digest를 통과한 image만 허용
  • 사용자 인증·인가가 추가되기 전까지 테스트베드 접근 경계에서만 사용

승인과 검증이 필요한 범위

다음은 코드나 개발 fixture가 있어도 일반 운영 기능으로 보지 않는다.

명시적으로 제외하는 것

  • EdgeX와 병행하는 KubeEdge Device/DeviceModel/DeviceStatus 물리 권위
  • MapperFramework, mapper direct-to-Influx와 legacy MQTT topic을 fallback으로 사용
  • 광역 네트워크 probe나 임의 hostPath/image/command 실행
  • 서비스 설계 화면의 Kubernetes apply/delete/restart 또는 EdgeX metadata mutation
  • Controller가 생성한 Deployment의 update·patch·delete, 기존 workload 변경
  • 승인 없는 Runtime Recommendation/Execution Plan 적용 또는 traffic cutover와 rollback 실행
  • EndpointSlice 소비가 입증되지 않은 EdgeMesh 환경의 traffic mutation
  • 승인 없는 actuator command와 write command
  • 동적 workflow·migration·offloading 전체 구현 완료 주장
  • 승인·계약·후보 자격을 우회한 sensor-anomaly-demo 자동 오프로딩

완료 증거

기능은 다음 증거를 모두 연결할 수 있을 때만 현재 범위로 승격한다.

  1. Git에서 검토한 계약과 immutable image
  2. root Kustomize 또는 승인된 선택 overlay
  3. 관련 자동 테스트와 manifest render
  4. Argo CD 또는 명시적 운영 소유권
  5. Pod/endpoint Ready와 실제 API readback
  6. 실패·stale·누락 상태가 정상처럼 보이지 않는 대시보드 표시

Server1 후보의 실험 설계, 합성 입력 90회 기준선, 실제 Arduino Reading 120개를 고정한 18회 비교 결과와 승격 gate는 AI 서비스 자원 증강 부하 실험을 따른다. CPU/GPU가 존재하거나 endpoint가 Ready라는 사실만으로 오프로딩 효과를 주장하지 않는다.

과거 workflow·placement·replanning 코드는 edge-orch/workflow_*, edge-orch/placement_engine/, workflow/, docs/archive/에 보존하며 현재 요구사항으로 해석하지 않는다.
