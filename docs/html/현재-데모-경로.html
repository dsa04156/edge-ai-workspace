현재 데모 경로

목적

이 문서는 현재 PoC의 물리 디바이스 권위 경로와 그 경로를 state-aggregator/dashboard가 어떻게 읽는지 정리한다. 물리 디바이스 inventory, state, telemetry의 권위는 EdgeX 하나이며, KubeEdge는 edge node와 workload 관리에만 사용한다.

서비스 데모와 device-service binding을 운영 관점에서 보여주는 목적은 유지한다. 다만 저장소에 코드와 설정이 있다는 사실과 실제 장비의 live cutover가 검증됐다는 주장은 구분한다.

한 줄 요약

물리 센서 / PLC / 장비
  -> Jetson 또는 Raspberry Pi의 EdgeX Device Service
  -> etri-ser0002-cgnmsb의 중앙 EdgeX MessageBus
  -> Core Data -> PostgreSQL
  -> Application Service / AI consumer / state-aggregator / dashboard

KubeEdge
  -> 엣지 노드 / 워크로드 배치와 상태 관리

MapperFramework, mqttvirtual, KubeEdge Device/DeviceStatus, direct Influx 수집은 이 물리 경로의 현재 plane, 병행 plane, fallback이 아니다. 관련 파일이나 기록이 남아 있더라도 legacy test/integration history로만 해석한다.

현재 권위와 책임

영역 권위 컴포넌트 책임
물리 device inventory EdgeX Core Metadata Device Profile, Device, Device Service 등록 정보
protocol 연결/정규화 EdgeX Device Service MQTT/Serial/Modbus/OPC-UA/RTSP endpoint 연결, 읽기, 지원 command
event/reading EdgeX MessageBus / Core Data 표준 Event/Reading 전달과 조회
분석과 보관 AI services / storage Core Data 이후 소비, 분석, 장기 보관
통합 조회 edge-orch/state-aggregator/ EdgeX inventory/state/latest event를 dashboard API로 정규화
운영 가시화 edge-orch/state-aggregator/app/static/ device, node, service, KPI 표시
node/workload Kubernetes/KubeEdge edge node 상태, workload 배치와 실행

KubeEdge node 이름은 선택적 placement/진단 정보다. node가 Ready인지 또는 특정 node에 device가 매핑됐는지는 물리 device availability의 권위나 선행 gate가 아니다.

protocol별 경로

모든 protocol의 목표 경로는 동일한 책임 경계를 따른다.

physical endpoint
  -> matching EdgeX Device Service
  -> EdgeX MessageBus
  -> Core Data Event / Reading
  -> downstream AI service or storage
  -> state-aggregator read model
  -> dashboard
protocol EdgeX 경계 현재 주장 가능한 수준
MQTT EdgeX device-mqtt와 canary 설정 telemetry namespace의 KubeEdge/Kubernetes workload로 실행한다. 2026-07-14 live smoke에서 Jetson local MQTT의 arduino-001 입력 네 종류를 Core Data typed Event/Reading과 dashboard에서 확인했다. 2026-07-15에는 Raspberry Pi 5의 existing Sense HAT publisher와 local Mosquitto를 유지한 채 별도 device-mqtt_sensehat instance로 sensehat-001의 여섯 source를 Core Data와 /state/devices에서 확인했다.
Serial Serial Device Service 목표 경로만 고정되어 있다. 실장비 연결과 Core Data event 증거 전에는 지원 완료가 아니다.
Modbus Modbus Device Service 목표 경로만 고정되어 있다. 실장비 연결과 Core Data event 증거 전에는 지원 완료가 아니다.
OPC-UA OPC-UA Device Service 목표 경로만 고정되어 있다. 실장비 연결과 Core Data event 증거 전에는 지원 완료가 아니다.
RTSP RTSP/video Device Service 목표 경로만 고정되어 있다. 실장비 연결과 downstream frame/event 증거 전에는 지원 완료가 아니다.

한 protocol의 성공은 다른 protocol의 지원 증거로 대체할 수 없다. 각 protocol은 Device Service 실행, physical endpoint 연결, Core Data Event/Reading, downstream consumer까지 독립 검증해야 한다.

현재 제공되는 MQTT 물리 경로

현재 코드와 live 환경은 기존 장비 publisher를 유지하고 stock EdgeX Device MQTT instance가 각 southbound broker를 구독하는 두 경로를 제공한다.

arduino-001
sensehat-001

관련 설정과 검증 도구:

edgex/k8s/kustomization.yaml
edgex/k8s/device-mqtt.yaml
edgex/k8s/config/etri-uno-mqtt.yaml
edgex/k8s/config/arduino-001.yaml
edgex/k8s/config/etri-sensehat-mqtt.yaml
edgex/k8s/config/sensehat-001.yaml
edgex/scripts/smoke_test.py

southbound 입력 topic은 다음과 같다.

etri/etri-dev0001-jetorn/arduino-001/{temperature,light,magnetic,acceleration}
etri/etri-dev0003-raspi5/sensehat-001/{temperature,humidity,pressure,compass,orientation,gyroscope}

edgex-device-mqtt는 Jetson host network에서 127.0.0.1:1883을 구독하고 arduino-001/{source}를 etri-uno-mqtt Device Command와 typed Reading에 매핑한다. edgex-device-mqtt-sensehat는 etri-dev0003-raspi5에 배치되며 host network를 사용하지 않고 node endpoint 192.168.0.6:1883을 구독한다. 이 instance는 sensehat-001/{source}를 etri-sensehat-mqtt의 Float64 Reading에 매핑한다. 두 instance는 EdgeX 내부 edgex-messagebus에서 서로 다른 client ID를 사용한다.

Kubernetes 배포의 단일 진입점은 kubectl apply -k edgex/k8s이고 namespace는 telemetry다. EdgeX Core Keeper, Core Metadata, Core Data, Core Command, 내부 MessageBus, PostgreSQL은 etri-ser0002-cgnmsb에 배치한다. UNO Device MQTT는 etri-dev0001-jetorn, Sense HAT Device MQTT는 etri-dev0003-raspi5에 배치한다. Docker Compose는 현재 운영 배포 경로가 아니다.

현재 1차 수직 슬라이스에는 SQLite offline replay가 없다. 중앙 MessageBus 또는 네트워크 장애 시 telemetry가 유실될 수 있고, 복구 기준은 연결 회복 뒤 새 Event 수집이 재개되는 것이다.

2026-07-14 live 실행에서 UNO의 temperature, light, magnetic, acceleration을 확인했다. 2026-07-15 live 실행에서는 sensehat-001이 Core Metadata에 등록되고 여섯 Float64 Event/Reading이 fresh 상태로 노출되는 것을 확인했다. 이 장비·profile 증거를 중앙 server2 topology live cutover나 Serial/Modbus/OPC-UA/RTSP 완료로 확장하지 않는다.

EdgeX 등록과 수집

물리 device는 EdgeX Core Metadata에 Device Profile과 Device로 사전 등록한다. Device는 자신을 관리하는 Device Service와 protocol properties를 가져야 한다. 임의의 topic publish만으로 권위 inventory가 생성되는 것으로 설명하지 않는다.

EdgeX Device Service는 다음을 소유한다.

  1. 물리 endpoint와 protocol 연결
  2. protocol payload의 표준화
  3. adminState와 operatingState를 포함한 관리 상태
  4. 지원되는 read/command contract
  5. MessageBus를 통한 Event/Reading 전달

Core Data 이후 AI service와 storage는 Event/Reading consumer다. 이 downstream consumer를 Device Service나 Core Data를 우회하는 물리 수집 권위로 설명하지 않는다.

state-aggregator

state-aggregator는 EdgeX read model을 dashboard에 제공하는 FastAPI 컴포넌트다.

관련 경로:

edge-orch/state-aggregator/

현재 데모 핵심 API:

GET /state/nodes
GET /state/devices
GET /state/dashboard
GET /state/virtual-resources
GET /state/summary
GET /state/operator-assistant
GET /metrics
API 용도
GET /state/nodes Kubernetes/Prometheus 기반 node와 workload 진단
GET /state/devices EdgeX Core Metadata device와 Core Data latest event 조회
GET /state/dashboard dashboard용 EdgeX device 상태와 KPI
GET /state/virtual-resources 물리 디바이스의 AI 연산/GPU/NPU/storage/cache 보강 자원 조회
GET /state/summary 전체 운영 상태 요약
GET /state/operator-assistant read-only 운영 보조 요약과 우선 점검 대상
GET /metrics Prometheus scrape metric

GET /state/devices의 주요 EdgeX 필드는 다음과 같다.

필드 의미
source 물리 source authority. 현재 값은 edgex
name Core Metadata Device 이름
profile_name 연결된 Device Profile
device_service_name 관리하는 EdgeX Device Service
protocol_names 등록된 protocol 종류
admin_state Core Metadata 관리 허용 상태
operating_state Device Service가 보고하는 동작 상태
connection_state connected, disconnected, unknown 정규화 값
device_service_available operating_state=UP 여부
latest_event_timestamp 최신 Core Data Event/Reading 시각
latest_readings 최신 event의 source_name, resource_name, value_type, value, timestamp, event_id, units
telemetry_freshness fresh, stale, no_events
node_name workload placement 실행 범위에서 제외한 선택적 노드 진단 정보. availability gate가 아님

기본 EdgeX event freshness 설정은 다음과 같다.

EDGEX_EVENT_FRESH_SECONDS=90

Core Metadata 또는 Core Data 조회 실패는 다른 inventory/state/telemetry source로 fallback하지 않는다. 오류나 미관측 상태로 드러내고 EdgeX 연결을 복구한다.

Legacy/compatibility API:

GET /state/cost-model
POST /workflow-event
GET /state/workflows

위 API는 과거 workflow/placement/cost-model 실험 호환용이다. 물리 디바이스 현재 경로나 workflow/offloading/placement/autonomous agent의 현재 구현 근거가 아니다.

/state/virtual-resources는 센서 생성기가 아니라 물리 디바이스의 부족한 AI 연산/GPU/NPU/storage/cache를 보강하는 논리 자원 상태를 표시한다. Prometheus/service resource observation이 실패해도 registry에 등록된 Resource Profile은 숨기지 않고 configured_not_running과 observation error로 표시한다. /state/dashboard도 이 경우 dashboard shell과 device/node KPI를 유지하고 service resource KPI만 0과 observation error로 degrade한다.

자원증강을 Kubernetes 관리 객체로 표시하는 AugmentationResource와 DeviceAugmentation CRD는 edge node의 부족한 연산/저장 자원을 외부 실행 자원으로 보강하는 관리 표면이다. 읽기 전용 controller와 dashboard는 관측 상태를 보여줄 뿐 workload 생성/이동, 자동 offloading, runtime migration을 수행하지 않는다.

availability

dashboard와 state-aggregator의 물리 device 판단은 EdgeX 필드만 사용한다.

상태 의미
available admin_state가 잠기지 않고, operating_state=UP, connection_state=connected, 최신 Core Data event가 fresh
degraded Device Service가 UP이더라도 connection을 확인할 수 없거나 event가 stale/no_events인 등 경로가 불완전한 상태
unavailable admin_state=LOCKED, operating_state=DOWN 또는 connection_state=disconnected

device_service_available은 Device Service 동작 상태를 빠르게 보여주는 필드이고, 그 값만으로 최종 available이 되지는 않는다. 최신 Core Data event freshness와 connection state까지 함께 본다.

다음 값은 물리 device availability gate가 아니다.

  • KubeEdge/Kubernetes node Ready
  • KubeEdge Device/DeviceStatus
  • mapper pod 상태
  • direct Influx latest timestamp
  • legacy MQTT heartbeat

dashboard

dashboard는 state-aggregator의 EdgeX-backed API를 읽는다. 운영자는 각 device에서 다음을 함께 확인한다.

  1. Device Profile과 Device Service
  2. protocol 목록
  3. admin_state / operating_state
  4. connection_state / device_service_available
  5. latest Core Data event 시각과 age
  6. 최신 Reading의 source/resource/value/unit
  7. telemetry_freshness
  8. 선택적 node placement와 연결된 service demo

dashboard KPI도 EdgeX 기준으로 읽는다.

  • Core Metadata 등록 device 수
  • available device 수
  • Device Service binding 비율
  • fresh Core Data event device 수와 freshness 비율
  • degraded/unavailable device와 non-healthy node를 합친 operator focus 수

node/workload 문제는 서비스 실행과 배치의 진단 대상이지만 물리 device의 EdgeX availability를 덮어쓰지 않는다.

운영 점검 순서

MQTT canary 또는 이후 protocol device를 점검할 때는 다음 순서를 따른다.

  1. 해당 protocol의 EdgeX Device Service가 실행 중이고 health endpoint가 응답하는지 확인한다.
  2. Core Metadata에서 Device Profile, Device, Device Service binding과 protocol properties를 확인한다.
  3. physical endpoint 또는 canary publisher가 지정된 broker/port/topic에 연결되는지 확인한다.
  4. Core Data에서 해당 device의 최신 Event/Reading과 origin timestamp를 확인한다.
  5. AI service/storage consumer가 필요한 Event/Reading을 받는지 확인한다.
  6. /state/devices에서 EdgeX 필드와 telemetry_freshness를 확인한다.
  7. /state/dashboard와 dashboard에서 동일한 availability/KPI가 보이는지 확인한다.
  8. 별도로 KubeEdge/Kubernetes node와 workload 상태를 진단한다.

대표적인 degraded 원인은 다음과 같다.

  • Core Metadata에는 등록됐지만 Device Service 연결 상태를 확인할 수 없음
  • Device Service는 UP이지만 최신 Core Data event가 없음
  • 최신 event가 freshness 기준보다 오래됨
  • canary가 다른 broker/topic으로 publish함
  • protocol properties 또는 Device Service binding이 실제 endpoint와 다름
  • MessageBus/Core Data 또는 downstream consumer가 event를 처리하지 못함

degraded는 전체 플랫폼 실패를 뜻하지 않는다. EdgeX 권위 경로에서 어느 관측 조건이 부족한지를 상태 reason과 함께 확인한다.

live cutover 증거 경계

현재 저장소가 제공하는 것은 MQTT canary와 EdgeX-backed aggregator/dashboard의 코드, 설정, 테스트 asset이다. 다음은 별도 실행 증거 없이는 완료로 주장하지 않는다.

  • 실제 장비와 운영 broker를 사용한 MQTT live cutover
  • 운영 환경의 EdgeX MessageBus/Core Data 지속 수집
  • AI service/storage의 운영 데이터 소비
  • Serial/Modbus/OPC-UA/RTSP Device Service와 실장비 연결
  • protocol별 장애/복구와 freshness 판정

각 cutover 기록은 최소한 실행 시각, 환경, Device Service health, Core Metadata Device, Core Data latest Event/Reading, downstream consumer, state-aggregator/dashboard 관측 결과를 포함해야 한다.

위 항목은 현재 연구 방향에서 진행하는 다음 단계로 표현하지 않는다. 필요한 경우 과거 검토/실험 자료 또는 보관 경로로만 다룬다.

Workflow Designer에서 보는 현재 데모 경로

Workflow Designer는 이 경로를 하나의 node-column 화면으로 합치지 않고 다음 3개 관점으로 나누어 본다.

  1. Service Workflow DAG
  • input device에서 시작해 collect -> preprocess/normalize -> inference/rule-check -> event-publish -> sink로 이어지는 서비스 논리 흐름을 표시한다.
  • raw-signal, feature-vector, mqtt-event, environment-state 같은 output data 이름은 stage 사이 edge label로 표시한다.
  1. Stage Placement
  • 각 stage가 factoryName-ser0001-CG0MS0, etri-dev0001-jetorn, etri-dev0002-raspi5 중 어디서 실행되는지 별도 표/카드로 표시한다.
  • target node 변경은 이 dry-run placement view에서만 수행한다.
  1. Data Transport / Endpoint
  • output data가 어떤 transport로 어느 consumer stage 또는 platform endpoint에 전달되는지 표시한다.
  • platform endpoint는 compute node와 분리하며 MQTT Broker, EdgeX Device Service / Core Data, AI/Storage Consumer, State Aggregator, Dashboard로 구분한다.

이 기능은 read-only + dry-run 설계 도구이며 실제 배포, Kubernetes 또는 EdgeX metadata/state 변경, command publish, runtime migration/offloading을 수행하지 않는다.
