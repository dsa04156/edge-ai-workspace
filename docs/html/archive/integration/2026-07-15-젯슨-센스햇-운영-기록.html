2026-07-15 젯슨·센스햇 운영 검증 기록

상태: 중앙 MessageBus 분리 배치 이전의 운영 검증 기록. 현재 운영 절차가 아니다.

목적과 운영 경계

이 문서는 현재 운영 중인 EdgeX MQTT canary를 조회하고 장애 범위를 좁히는 절차다. 물리 디바이스 inventory, 관리 상태, telemetry의 권위는 EdgeX이며, KubeEdge는 edge node에 workload를 배치하고 실행 상태를 관찰하는 역할만 맡는다.

현재 검증된 MQTT 물리 경로는 두 개다.

arduino-001
sensehat-001

Serial, Modbus, OPC-UA, RTSP는 목표 protocol이지만 아직 완성된 운영 경로가 아니다. 각 protocol은 Device Service, profile, 실장비 연결, Core Data Event/Reading 증거를 별도로 확보해야 한다.

운영 배포 계약은 다음과 같다.

항목 현재 값
Argo CD Application edgex-telemetry
Kustomize entrypoint edgex/k8s
namespace telemetry
target nodes Core/UNO: etri-dev0001-jetorn, Sense HAT Device MQTT: etri-dev0003-raspi5
EdgeX release/image EdgeX 4.0.2, ARM64
Core Metadata edgex-core-metadata:59881
Core Data edgex-core-data:59880
internal MessageBus ClusterIP edgex-messagebus:1883
southbound MQTT Jetson 127.0.0.1:1883, Raspberry Pi 5 192.168.0.6:1883
persistence PostgreSQL StatefulSet와 retained PVC
state-aggregator namespace default의 state-aggregator:8000

Docker Compose는 현재 운영 배포 경로가 아니다. Git 반영 후에는 edgex/k8s를 소스로 삼는 Argo CD Application이 유일한 소유자다. 2026-07-14 live workload와 ingestion은 수동 Kustomize 적용으로 검증됐지만, edgex-telemetry Application의 live 등록은 repository 변경 반영 전이므로 별도 완료 조건이다. 일반 점검은 조회 전용이며 apply, delete, restart, scale, patch 명령을 포함하지 않는다.

현재 데이터 경로

Arduino UNO
  -> Jetson serial collector
  -> Jetson local Mosquitto 127.0.0.1:1883
  -> hostNetwork edgex-device-mqtt
  -> ClusterIP edgex-messagebus:1883
  -> edgex-core-data:59880
  -> PostgreSQL PVC
  -> state-aggregator

Sense HAT
  -> existing Sense HAT publisher
  -> Raspberry Pi 5 local Mosquitto 192.168.0.6:1883
  -> edgex-device-mqtt-sensehat
  -> ClusterIP edgex-messagebus:1883
  -> edgex-core-data:59880
  -> PostgreSQL PVC
  -> state-aggregator

edgex-device-mqtt만 hostNetwork를 사용해 Jetson의 southbound Mosquitto에 접속한다. edgex-device-mqtt-sensehat는 host network를 사용하지 않고 Raspberry Pi 5 node endpoint에 접속한다. 두 instance는 내부 MessageBus에서 고유 client ID를 사용한다. edgex-messagebus는 EdgeX 내부 통신용 ClusterIP이며 southbound broker나 외부 접속 주소가 아니다.

입력 topic은 다음과 같다.

etri/etri-dev0001-jetorn/arduino-001/{temperature,light,magnetic,acceleration}
etri/etri-dev0003-raspi5/sensehat-001/{temperature,humidity,pressure,compass,orientation,gyroscope}

Device MQTT instance는 각 node prefix를 구독하고 {device-name}/{source} suffix를 해당 Device와 Device Command에 매핑한다.

데모 전 빠른 점검

다음 순서로 확인한다.

  1. Argo CD의 edgex-telemetry가 Synced/Healthy인지 확인한다.
  2. etri-dev0001-jetorn과 etri-dev0003-raspi5가 Ready인지 확인한다.
  3. telemetry의 EdgeX Pod, Service, Endpoint, PostgreSQL PVC를 확인한다.
  4. Core Metadata에서 Device/Profile/Device Service를 확인한다.
  5. Core Data에서 canary의 최신 Event/Reading을 확인한다.
  6. 필요할 때만 Kubernetes smoke를 실행한다.
  7. namespace default의 state-aggregator와 dashboard API를 확인한다.
  8. 이상이 있으면 Argo -> placement -> southbound -> EdgeX Core -> persistence -> dashboard 순서로 격리한다.

1. Argo CD와 배포 소스 확인

Application 상태와 실제 source/destination을 조회한다.

kubectl -n argocd get application.argoproj.io edgex-telemetry -o wide
kubectl -n argocd get application.argoproj.io edgex-telemetry \
  -o jsonpath='{.status.sync.status}{"\t"}{.status.health.status}{"\t"}{.spec.source.path}{"\t"}{.spec.destination.namespace}{"\n"}'

정상 결과는 차례로 Synced, Healthy, edgex/k8s, telemetry다. Application이 없으면 live ingestion 성공과 별개로 GitOps adoption이 아직 완료되지 않은 상태다. Application 상세 조건과 마지막 동기화 결과가 필요하면 다음을 조회한다.

kubectl -n argocd get application.argoproj.io edgex-telemetry -o yaml

Argo가 정상인데 live object가 예상과 다르면 source path, target revision, sync condition을 먼저 확인한다. 이 runbook에서 수동 apply로 차이를 덮지 않는다.

2. node와 workload placement 확인

kubectl get node etri-dev0001-jetorn etri-dev0003-raspi5 -o wide
kubectl -n telemetry get pod \
  -l app.kubernetes.io/part-of=edgex-telemetry \
  -o wide
kubectl -n telemetry get deployment,statefulset,job \
  -l app.kubernetes.io/part-of=edgex-telemetry

확인 기준:

  • Jetson과 Raspberry Pi 5 node가 Ready다.
  • Core와 UNO Device MQTT Pod는 etri-dev0001-jetorn, Sense HAT Device MQTT Pod는 etri-dev0003-raspi5에 배치된다.
  • edgex-postgres StatefulSet이 Ready다.
  • edgex-messagebus, edgex-core-keeper, edgex-core-data, edgex-core-metadata, edgex-core-command, edgex-device-mqtt, edgex-device-mqtt-sensehat Deployment가 Available이다.
  • edgex-core-common-config-bootstrapper Job이 Complete다.
  • EdgeX 서비스 image는 edgexfoundry/*-arm64:4.0.2다.

실제 image와 host network 설정은 조회만 한다.

kubectl -n telemetry get pod \
  -l app.kubernetes.io/part-of=edgex-telemetry \
  -o custom-columns='NAME:.metadata.name,NODE:.spec.nodeName,HOST_NETWORK:.spec.hostNetwork,IMAGES:.spec.containers[*].image'

HOST_NETWORK=true는 edgex-device-mqtt에만 있어야 한다.

3. Service, Endpoint, MessageBus 확인

kubectl -n telemetry get service \
  edgex-postgres edgex-messagebus edgex-core-keeper \
  edgex-core-data edgex-core-metadata edgex-device-mqtt \
  edgex-device-mqtt-sensehat -o wide
kubectl -n telemetry get endpoints \
  edgex-postgres edgex-messagebus edgex-core-keeper \
  edgex-core-data edgex-core-metadata edgex-device-mqtt \
  edgex-device-mqtt-sensehat

확인 기준:

  • Service는 ClusterIP다.
  • edgex-messagebus는 port 1883을 제공한다.
  • Core Data는 59880, Core Metadata는 59881을 제공한다.
  • 각 Endpoint에 준비된 Pod 주소가 있다.

API server의 Service proxy로 Core health를 확인한다. 별도 port-forward나 외부 노출은 필요 없다.

kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-metadata:59881/proxy/api/v3/ping'
kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-data:59880/proxy/api/v3/ping'

4. EdgeX inventory와 MQTT Event 확인

Core Metadata에서 두 Device, Profile, Device Service를 조회한다.

kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-metadata:59881/proxy/api/v3/device/name/arduino-001'
kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-metadata:59881/proxy/api/v3/device/name/sensehat-001'
kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-metadata:59881/proxy/api/v3/deviceprofile/name/etri-uno-mqtt'
kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-metadata:59881/proxy/api/v3/deviceprofile/name/etri-sensehat-mqtt'
kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-metadata:59881/proxy/api/v3/deviceservice/name/device-mqtt'
kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-metadata:59881/proxy/api/v3/deviceservice/name/device-mqtt_sensehat'

확인 기준:

  • arduino-001은 etri-uno-mqtt와 device-mqtt에 연결된다.
  • sensehat-001은 etri-sensehat-mqtt와 device-mqtt_sensehat에 연결된다.
  • 두 Device 모두 adminState=UNLOCKED, operatingState=UP다.

Core Data의 최근 Event/Reading을 조회한다.

kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-data:59880/proxy/api/v3/event/device/name/arduino-001?limit=20'
kubectl get --raw \
  '/api/v1/namespaces/telemetry/services/http:edgex-core-data:59880/proxy/api/v3/event/device/name/sensehat-001?limit=20'

최근 Event 집합에서 다음 source/typed Reading을 확인한다.

arduino-001:
temperature  -> raw
light        -> value
magnetic     -> value
acceleration -> x, y, z

sensehat-001:
temperature -> temp_humidity, temp_pressure
humidity    -> humidity
pressure    -> pressure
compass     -> compass
orientation -> pitch, roll, yaw
gyroscope   -> gyro_x, gyro_y, gyro_z

이 Core Metadata/Core Data 응답이 물리 MQTT 경로의 inventory와 telemetry 근거다.

5. PostgreSQL PVC 확인

kubectl -n telemetry get statefulset edgex-postgres -o wide
kubectl -n telemetry get pvc data-edgex-postgres-0 -o wide
kubectl get pv \
  -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,CLAIM_NAMESPACE:.spec.claimRef.namespace,CLAIM:.spec.claimRef.name,STORAGECLASS:.spec.storageClassName,CAPACITY:.spec.capacity.storage'

정상 기준은 data-edgex-postgres-0가 Bound이고 StatefulSet이 Ready인 것이다. PVC는 Event/Reading 보존 경로이며 Argo workload 동기화와 별도로 유지된다. 운영 점검 중 PVC를 삭제하거나 재생성하지 않는다.

6. Kubernetes MQTT smoke

Core Service는 ClusterIP이며 KubeEdge edge Pod에 대한 workstation port-forward는 지원되지 않을 수 있다. cluster 내부의 기존 Python workload에서 read-only smoke를 실행한다.

POD=$(kubectl -n default get pod -l app=state-aggregator \
  -o jsonpath='{.items[0].metadata.name}')
kubectl cp edgex/scripts/smoke_test.py \
  "default/${POD}:/tmp/edgex-smoke.py"
kubectl exec -n default "${POD}" -- python /tmp/edgex-smoke.py \
  --metadata-url http://edgex-core-metadata.telemetry.svc.cluster.local:59881 \
  --data-url http://edgex-core-data.telemetry.svc.cluster.local:59880 \
  --timeout 15 \
  --freshness-seconds 120
kubectl exec -n default "${POD}" -- rm /tmp/edgex-smoke.py

성공 출력은 정확히 다음과 같다.

PASS: device=arduino-001 sources=temperature,light,magnetic,acceleration

이 smoke는 Core Metadata의 Profile/Device와 Core Data의 최근 Event를 GET으로만 조회한다. temperature, light, magnetic, acceleration source가 모두 fresh하고 profile에 정의된 typed Reading을 포함해야 성공한다.

2026-07-14 live 실행에서 다음 경로와 성공 출력을 확인했다.

Jetson serial collector
  -> Jetson local Mosquitto
  -> device-mqtt
  -> internal MessageBus
  -> Core Data/PostgreSQL

PASS: device=arduino-001 sources=temperature,light,magnetic,acceleration

이 증거는 현재 MQTT compatibility ingestion과 read-only GET 경로에만 해당한다. direct UART Device Service, Serial/Modbus/OPC-UA/RTSP 완료 증거나 새 state-aggregator image가 live 배포됐다는 증거가 아니다.

7. state-aggregator와 dashboard 확인

state-aggregator는 namespace default에 있고 다음 FQDN으로 EdgeX Core를 읽어야 한다.

http://edgex-core-metadata.telemetry.svc.cluster.local:59881
http://edgex-core-data.telemetry.svc.cluster.local:59880

Deployment, Service, Endpoint와 환경을 조회한다.

kubectl -n default get deployment,service,endpoints \
  -l app=state-aggregator -o wide
kubectl -n default get deployment state-aggregator \
  -o jsonpath='{range .spec.template.spec.containers[?(@.name=="state-aggregator")].env[?(@.name=="EDGEX_CORE_METADATA_URL")]}{.name}{"="}{.value}{"\n"}{end}'
kubectl -n default get deployment state-aggregator \
  -o jsonpath='{range .spec.template.spec.containers[?(@.name=="state-aggregator")].env[?(@.name=="EDGEX_CORE_DATA_URL")]}{.name}{"="}{.value}{"\n"}{end}'

API server Service proxy로 dashboard 입력을 조회한다.

kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/nodes'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/devices'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/dashboard'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/summary'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/virtual-resources'

/state/devices에서 확인할 핵심 필드:

  • source=edgex
  • name, profile_name, device_service_name, protocol_names
  • admin_state, operating_state, connection_state
  • device_service_available
  • latest_event_timestamp, latest_readings, telemetry_freshness
  • 선택적 placement 진단인 node_name

node_name과 Kubernetes Ready는 workload 진단 정보이며 물리 device availability의 권위가 아니다. Dashboard availability는 EdgeX의 관리 상태와 Core Data 최신 Event freshness로 해석한다.

브라우저 UI를 확인해야 하면 별도 터미널에서 조회용 port-forward를 연다.

kubectl -n default port-forward service/state-aggregator 8000:8000

그 뒤 http://127.0.0.1:8000/과 http://127.0.0.1:8000/state/dashboard를 확인한다. 점검 종료 시 port-forward 프로세스만 종료한다.

새 state-aggregator image 배포 증거

2026-07-14 ingestion smoke와 dashboard image cutover를 혼동하지 않는다. 새 image 배포를 주장하려면 다음 live 값을 릴리스 대상 digest와 대조하고 rollout 상태가 완료됐음을 별도로 기록한다.

kubectl -n argocd get application.argoproj.io edge-orch-state-aggregator \
  -o jsonpath='{.status.sync.status}{"\t"}{.status.health.status}{"\t"}{.spec.source.path}{"\t"}{.spec.destination.namespace}{"\n"}'
kubectl -n default get deployment state-aggregator \
  -o jsonpath='{.metadata.generation}{"\t"}{.status.observedGeneration}{"\t"}{.status.updatedReplicas}{"\t"}{.status.availableReplicas}{"\n"}'
kubectl -n default get pod -l app=state-aggregator \
  -o custom-columns='NAME:.metadata.name,IMAGE:.spec.containers[0].image,IMAGE_ID:.status.containerStatuses[0].imageID,READY:.status.containerStatuses[0].ready,STARTED:.status.startTime'

Synced/Healthy, generation 일치, updated/available replica 충족, 기대한 immutable IMAGE_ID가 모두 있어야 새 image의 live deployment 증거다. 이어서 /state/devices와 /state/dashboard가 EdgeX 필드를 반환해야 dashboard cutover 증거가 완성된다.

8. 로그 기반 failure isolation

로그 조회는 상태를 변경하지 않는다. 먼저 최근 로그를 좁혀 확인한다.

kubectl -n telemetry logs deployment/edgex-device-mqtt \
  --since=10m --tail=200
kubectl -n telemetry logs deployment/edgex-messagebus \
  --since=10m --tail=200
kubectl -n telemetry logs deployment/edgex-core-data \
  --since=10m --tail=200
kubectl -n telemetry logs deployment/edgex-core-metadata \
  --since=10m --tail=200
kubectl -n telemetry logs statefulset/edgex-postgres \
  --since=10m --tail=200
kubectl -n default logs deployment/state-aggregator \
  --since=10m --tail=200

재시작이 있었다면 직전 container 로그도 확인한다.

kubectl -n telemetry logs deployment/edgex-device-mqtt \
  --previous --tail=200
kubectl -n telemetry logs deployment/edgex-core-data \
  --previous --tail=200
kubectl -n default logs deployment/state-aggregator \
  --previous --tail=200

A. Argo가 OutOfSync 또는 Degraded

  1. Application YAML의 status.conditions와 operationState를 본다.
  2. source가 edgex/k8s, destination이 telemetry인지 확인한다.
  3. 누락 object, health probe 실패, image pull 실패를 Pod 상태와 events로 좁힌다.
kubectl -n telemetry get events \
  --sort-by=.metadata.creationTimestamp

B. EdgeX Pod가 Pending 또는 Ready가 아님

  1. Jetson Ready와 Pod NODE를 확인한다.
  2. Pod 상세에서 scheduling, image pull, probe, volume mount 이유를 확인한다.
  3. PostgreSQL PVC가 Bound인지 확인한다.
kubectl -n telemetry get pod \
  -l app.kubernetes.io/part-of=edgex-telemetry -o wide
kubectl -n telemetry describe pod \
  -l app.kubernetes.io/part-of=edgex-telemetry
kubectl -n telemetry get pvc data-edgex-postgres-0 -o wide

C. Metadata/Data Service proxy가 실패

  1. Service port와 Endpoint 존재 여부를 확인한다.
  2. 해당 Core Pod의 Ready와 로그를 확인한다.
  3. Core dependency인 Keeper/PostgreSQL 상태를 확인한다.
kubectl -n telemetry get service,endpoints \
  edgex-core-metadata edgex-core-data edgex-core-keeper edgex-postgres
kubectl -n telemetry get pod \
  -l app.kubernetes.io/part-of=edgex-telemetry -o wide

D. Metadata는 정상이지만 최신 Event가 없음

  1. Jetson serial collector가 네 UNO topic을 local 127.0.0.1:1883에 계속 발행하는지 확인한다.
  2. edgex-device-mqtt가 Ready이고 etri/etri-dev0001-jetorn/# subscription 및 Event publish 오류가 없는지 본다.
  3. edgex-messagebus Endpoint와 로그를 확인한다.
  4. Core Data와 PostgreSQL 로그를 확인한다.
  5. smoke를 실행해 네 source의 최근 Event/Reading을 GET으로 확인한다.

Jetson local Mosquitto와 serial collector는 host 서비스이며 Argo CD가 소유하지 않는다. Kubernetes 객체가 모두 정상인데 Device MQTT 로그에 127.0.0.1:1883 연결 실패가 있으면 Jetson host broker와 collector를 별도 host 운영 절차로 점검한다.

E. Core Data는 정상이지만 dashboard가 비었거나 stale

  1. state-aggregator Service/Endpoint와 Pod Ready를 확인한다.
  2. EDGEX_CORE_METADATA_URL과 EDGEX_CORE_DATA_URL이 .telemetry.svc.cluster.local FQDN인지 확인한다.
  3. state-aggregator 로그에서 Core timeout/HTTP 오류를 확인한다.
  4. Core service-proxy 응답과 /state/devices 응답을 같은 시점에 비교한다.
  5. 새 image를 기대했다면 live IMAGE_ID를 릴리스 digest와 비교한다.

다른 inventory/state/telemetry source로 fallback하지 않는다. EdgeX 조회 실패는 dashboard에서 오류 또는 미관측 상태로 드러내고 EdgeX 연결을 복구한다.

9. cutover exclusion 확인

Cutover 후 legacy mqttvirtual-mapper는 실행되면 안 된다. 다음 조회 결과에 Pod가 없어야 한다.

kubectl -n default get pod -l app=mqttvirtual-mapper -o wide

Pod가 보이면 현재 경로와 병행 운영하지 말고 배포 소유자와 잔존 workload를 식별한다. 이 확인은 삭제 명령을 수행하지 않는다.

10. Dashboard와 Workflow Builder 경계

Dashboard에서는 다음을 확인한다.

  1. EdgeX 등록 device 수와 canary 이름
  2. Device Profile과 Device Service 연결
  3. adminState, operatingState, connection state
  4. 최신 Event 시각, reading 값, freshness
  5. node/workload 진단과 service relation
  6. issue/reason을 통한 우선 점검 대상

Workflow Builder는 브라우저 상태 안에서만 service stage 구성, device/resource bind/release dry-run, validation, execution plan preview를 보여주는 읽기 전용 설계 표면이다. 다음 동작은 수행하지 않는다.

  • Kubernetes apply/delete/restart/scale/patch
  • EdgeX metadata 또는 관리 상태 변경
  • MQTT/actuator command publish
  • workload 생성, 이동, runtime migration, offloading
  • 자동 placement나 agent-assisted execution

Dry-run plan이 바뀌어도 live cluster와 EdgeX 권위 상태는 바뀌지 않는다. 이를 동적 orchestration이 운영 완료된 증거로 설명하지 않는다.
