2026-07-14 MQTT 브리지 CI/CD 기록

상태: 중앙 MessageBus 분리 배치 이전의 브리지 배포 기록. 현재 운영 기준이 아니다.

목적과 운영 경계

이 문서는 EdgeX가 물리 디바이스, telemetry, command의 권위를 가지는 Kubernetes 운영 경로의 이미지 빌드와 배포 기준이다. KubeEdge는 edge node와 workload 관리에만 사용하며, MQTT 입력은 canary 호환 입력으로만 취급한다.

현재 이 문서의 CI/CD 대상 이미지는 다음 세 가지다.

  • 192.168.0.56:5000/state-aggregator:latest
  • 192.168.0.56:5000/mqtt-edge-bridge:latest 및 배포에 사용하는 불변 @sha256: 참조
  • 192.168.0.56:5000/docs-html:latest 및 배포에 사용하는 불변 @sha256: 참조

Docker Compose는 운영 배포 경로가 아니다. 이 문서에서 Docker Buildx는 Kubernetes가 pull할 OCI 이미지를 만드는 도구일 뿐이며, 컨테이너를 Compose로 실행하거나 배포하는 방법을 제공하지 않는다.

GitHub Actions workflow

workflow는 .github/workflows/docker-build-push.yml이다. main push와 workflow_dispatch에서 실행되며, workflow 또는 BuildKit 설정 변경은 세 이미지의 변경 감지를 모두 활성화한다.

대상 변경 감지 build context 배포 대상
state-aggregator edge-orch/state-aggregator/ edge-orch/state-aggregator default namespace의 deployment/state-aggregator
mqtt-edge-bridge edgex/mqtt-bridge/ edgex/mqtt-bridge telemetry namespace의 EdgeX Application
docs-html docs/ 또는 docs-site/ 저장소 루트 (docs-site/Dockerfile) default namespace의 deployment/docs-html

push trigger는 edgex/**도 포함한다. job 내부의 bridge build 조건은 edgex/mqtt-bridge/이므로 EdgeX manifest/config 변경이 bridge 이미지 build를 불필요하게 만들지 않도록 구분한다. docs 변경은 build 전에 python3 scripts/build-docs-html.py로 runner workspace의 docs/html을 생성한다.

세 이미지 모두 Buildx로 linux/amd64,linux/arm64 manifest를 registry에 push한다. state-aggregator는 :latest를 사용하고 Deployment의 imagePullPolicy: Always 및 rollout으로 새 tag를 pull한다. bridge와 docs job은 --metadata-file의 containerimage.digest를 읽어 다음처럼 immutable 참조를 만든다.

192.168.0.56:5000/mqtt-edge-bridge@sha256:<registry-digest>
192.168.0.56:5000/docs-html@sha256:<registry-digest>

tag는 build 입력이고, bridge와 docs의 배포 입력은 workflow가 확보한 registry digest다. 배포 시 이전 tag나 source manifest의 초기 digest를 추측해서 사용하지 않는다.

EdgeX telemetry Argo CD Application

edge-orch-argocd/argocd-apps.yaml의 edgex-telemetry Application이 EdgeX Kubernetes 운영 배포의 단일 진입점이다.

metadata:
  name: edgex-telemetry
  namespace: argocd
spec:
  source:
    repoURL: https://github.com/dsa04156/edge-ai-workspace.git
    path: edgex/k8s
    targetRevision: main
    kustomize: {}
  destination:
    server: https://kubernetes.default.svc
    namespace: telemetry
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

edgex/k8s/kustomization.yaml renders the EdgeX resources and mqtt-edge-bridge Deployment into telemetry. The bridge is node-pinned to the Jetson and uses host networking only to reach that device's local MQTT broker; it does not make KubeEdge a physical-device authority.

The Application has a digest Image Updater annotation for mqtt-edge-bridge. The workflow also patches the Application with the digest produced by the current build, which is the immediate promotion path; the updater remains the digest-tracking convergence mechanism.

argocd-image-updater.argoproj.io/image-list: mqtt-edge-bridge=192.168.0.56:5000/mqtt-edge-bridge:latest
argocd-image-updater.argoproj.io/mqtt-edge-bridge.update-strategy: digest
argocd-image-updater.argoproj.io/mqtt-edge-bridge.force-update: "true"
argocd-image-updater.argoproj.io/write-back-method: argocd

First-time Application bootstrap

Before the first bridge promotion, render the committed Kustomization and ask the API server to validate that rendered output. These are preflight checks; they do not create resources.

kubectl kustomize edgex/k8s > /tmp/edgex-telemetry-rendered.yaml
kubectl apply --dry-run=server -f /tmp/edgex-telemetry-rendered.yaml

Then run the workflow with workflow_dispatch (or a qualifying bridge change). Its Deploy MQTT EdgeX bridge through Argo CD step first applies the Application manifest:

kubectl apply -f edge-orch-argocd/argocd-apps.yaml

That application apply bootstraps or reconciles edgex-telemetry; CreateNamespace=true allows Argo CD to create telemetry during sync. The workflow builds and pushes the bridge before this step, so the digest passed to the Application is a registry-published artifact.

Bridge promotion and rollout wait

After Buildx records the registry digest in MQTT_EDGE_BRIDGE_IMAGE, the workflow applies it as an Argo Kustomize image override, requests a hard refresh, waits until the Deployment template contains the exact immutable image, and then waits for rollout completion.

kubectl patch application edgex-telemetry -n argocd --type=merge \
  -p "{\"spec\":{\"source\":{\"kustomize\":{\"images\":[\"${MQTT_EDGE_BRIDGE_IMAGE}\"]}}}}"
kubectl annotate application edgex-telemetry -n argocd \
  argocd.argoproj.io/refresh=hard --overwrite
kubectl rollout status deployment/mqtt-edge-bridge -n telemetry --timeout=180s

The workflow's polling gate is required before rollout status: it reads the mqtt-edge-bridge container image from deployment/mqtt-edge-bridge and requires exact equality with MQTT_EDGE_BRIDGE_IMAGE. A successful rollout alone proves readiness, not artifact identity.

Verify the immutable artifact identity from the running container as well as the Pod template. The imageID must contain the same digest as the workflow's MQTT_EDGE_BRIDGE_IMAGE; do not accept only :latest as evidence.

kubectl get deployment mqtt-edge-bridge -n telemetry \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="mqtt-edge-bridge")].image}{"\n"}'
kubectl get pods -n telemetry -l app.kubernetes.io/name=mqtt-edge-bridge \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[?(@.name=="mqtt-edge-bridge")].imageID}{"\n"}{end}'

state-aggregator deployment

state-aggregator remains a default namespace Deployment. It reads EdgeX Core Metadata and Core Data through the telemetry service DNS names; it is not part of the edgex-telemetry Application and must not be moved into that namespace as part of an image promotion.

For a qualifying state-aggregator build, the workflow updates the dashboard CSS ConfigMap in default, sets the Deployment container image to 192.168.0.56:5000/state-aggregator:latest, restarts it when the template already has that same tag, and waits for rollout completion.

kubectl create configmap state-aggregator-dashboard-screen-css -n default \
  --from-file=dashboard-screen.css=edge-orch/state-aggregator/app/static/dashboard-screen.css \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl set image deployment/state-aggregator \
  state-aggregator=192.168.0.56:5000/state-aggregator:latest -n default
kubectl rollout status deployment/state-aggregator -n default --timeout=180s

Because this target deliberately uses a mutable tag, deployment evidence is the successful default namespace rollout and the current Pod imageID; it is not a replacement for the digest-pinned bridge verification.

docs-html Image Updater and promotion

docs-html is a separate Argo CD Application sourced from docs-site and deployed to default. Its Application declares digest tracking:

argocd-image-updater.argoproj.io/image-list: docs-html=192.168.0.56:5000/docs-html:latest
argocd-image-updater.argoproj.io/docs-html.update-strategy: digest
argocd-image-updater.argoproj.io/docs-html.force-update: "true"
argocd-image-updater.argoproj.io/write-back-method: argocd

After rebuilding the static HTML image, the workflow obtains DOCS_HTML_IMAGE from Buildx metadata, patches the docs-html Application's Kustomize image override to that immutable reference, requests an Argo hard refresh, and waits for deployment/docs-html in default. Image Updater keeps the Application converged on registry digest changes; the workflow patch makes the build's digest the immediate deployment input.

kubectl patch application docs-html -n argocd --type=merge \
  -p "{\"spec\":{\"source\":{\"kustomize\":{\"images\":[\"${DOCS_HTML_IMAGE}\"]}}}}"
kubectl annotate application docs-html -n argocd \
  argocd.argoproj.io/refresh=hard --overwrite
kubectl rollout status deployment/docs-html -n default --timeout=180s

Use the same template-image plus running-container imageID check described for the bridge, substituting docs-html and DOCS_HTML_IMAGE, when proving a docs release.

Post-cutover legacy absence

mqttvirtual-mapper image build, DaemonSet, 현재 Argo Application은 cutover 후 없어야 한다. mappers/mqttvirtual/ 소스는 Legacy/Reference로 남을 수 있지만 current build path, Kubernetes 배포, Argo source, rollout 대상이 아니다.
