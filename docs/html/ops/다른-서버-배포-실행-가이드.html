다른 서버 배포 및 실행 가이드

목적

이 문서는 현재 PoC를 새 Kubernetes/KubeEdge 환경에 신규 설치하는 절차를 정리한다. 대상 경로는 다음과 같다.

물리 센서 / PLC / 장비
  -> Protocol Adapter
  -> edge-telemetry-agent -> SQLite outbox
  -> HTTPS/mTLS ingest gateway
  -> EdgeX Core Data -> PostgreSQL
  -> state-aggregator / dashboard

물리 디바이스 inventory와 schema는 EdgeX Core Metadata, telemetry와 freshness는 EdgeX Core Data가 권위다. KubeEdge는 edge node와 workload 관리에만 사용한다. MapperFramework, KubeEdge Device/DeviceStatus, mapper direct-to-Influx는 이 배포의 대체 경로나 fallback이 아니다.

이 문서는 빈 클러스터 기준이다. 기존 PostgreSQL 데이터와 edge outbox까지 옮기는 데이터 마이그레이션은 데이터 보존과 이전의 제한을 먼저 확인한다.

배포 범위

전체 데모 배포

전체 데모에는 다음 구성이 필요하다.

영역 기본 배치 주요 workload
중앙 EdgeX x86_64/amd64 server 또는 worker 1대 Core Keeper, Metadata, Data, Command, internal MessageBus, PostgreSQL, ingest gateway
Sense HAT 검증 edge ARM64 Raspberry Pi 계열 1대 direct-mode telemetry agent, SQLite outbox, I2C Protocol Adapter
Jetson 기반 edge ARM64 Jetson 1대 direct-mode telemetry agent, SQLite outbox, 인증 heartbeat
운영 화면 중앙 server 또는 별도 worker 1대 state-aggregator/dashboard
관측 cloud/worker Prometheus, node exporter, 선택적 ServiceMonitor

두 edge agent는 hostNetwork=true이고 기본적으로 같은 host port 18080과 8443을 사용한다. 두 agent를 같은 노드에 배치하면 포트가 충돌하므로 서로 다른 노드에 배치하거나 포트 계약을 별도로 변경해야 한다.

중앙 전용 기동

edge node가 아직 없으면 중앙 stack만 먼저 기동할 수 있다. 아래 명령은 1~7절의 nodeSelector·image·Secret 준비와 server-side dry-run을 마친 뒤 전체 root 대신 사용하는 적용 경로다.

kubectl apply -k edgex/k8s/overlays/testbed/server2

이 모드는 EdgeX API와 PostgreSQL 기동 점검에는 사용할 수 있지만 Protocol Adapter, SQLite outbox, edge-to-cloud replay가 빠지므로 전체 서비스 데모 완료로 판정하지 않는다. Metadata bootstrap의 sensehat-001도 실제 adapter가 없으면 no_events 또는 stale 상태가 정상이다.

현재 매니페스트의 이식 제약

현재 저장소의 매니페스트는 기존 테스트베드 값이 들어 있으므로 다른 서버에 그대로 적용하면 안 된다.

고정값 현재 값 예 변경 위치
중앙 EdgeX 노드 etri-ser0002-cgnmsb edgex/k8s/base/server/core.yaml, gateway.yaml, metadata.yaml의 모든 nodeSelector
dashboard 노드 etri-ser0001-cg0msb edge-orch/state-aggregator/k8s/deployment.yaml
edge 노드/identity etri-dev0001-jetorn, etri-dev0003-raspi5 edgex/k8s/overlays/testbed/sensor-gateways/*.yaml
private registry 192.168.0.56:5000 gateway, edge agent, state-aggregator image 필드
StorageClass local-path PostgreSQL과 edge outbox PVC
Prometheus Service prometheus-kube-prometheus-prometheus.kube-system:9090 state-aggregator Deployment
Metadata fixture sensehat-001, etri-sensehat edgex/k8s/base/server/config/metadata-contract.json
node exporter 매핑 기존 192.168.0.x:9100 edge-orch/state-aggregator/app/config/instance_map.json
ingress host/IP 기존 192.168.0.56 edge-orch-argocd/, docs-site/, 필요한 Traefik 리소스

운영 환경별 값은 장기적으로 별도 Kustomize overlay로 관리하는 것이 안전하다. 임시 문자열 치환으로 base 파일을 바꿀 경우 다음 저장소 업데이트에서 값이 다시 섞일 수 있다.

1. 배포값 결정

먼저 실제 환경값을 정한다.

export CONTROL_PLANE_IP=<CONTROL_PLANE_IP>
export CENTRAL_NODE=<CENTRAL_KUBERNETES_HOSTNAME>
export DASHBOARD_NODE=<DASHBOARD_KUBERNETES_HOSTNAME>
export JETSON_NODE=<JETSON_KUBERNETES_HOSTNAME>
export SENSEHAT_NODE=<RASPBERRY_PI_KUBERNETES_HOSTNAME>
export REGISTRY=<REGISTRY_HOST_AND_PORT>
export IMAGE_TAG=<IMMUTABLE_RELEASE_TAG>

이 환경변수는 아래 명령 예제를 위한 것이다. Kustomize YAML에 자동 반영되지 않으므로 매니페스트 또는 환경별 overlay에는 값을 명시적으로 반영해야 한다.

다음 identity 규칙은 반드시 함께 유지한다.

edge Deployment의 nodeSelector
  = 실제 Kubernetes node의 kubernetes.io/hostname

Deployment의 EDGE_ID
  = gateway HMAC allowlist key
  = 해당 edge client 인증서 identity
  = Metadata/Event의 edge_node_id

노드 hostname과 논리 EDGE_ID를 다르게 둘 수는 있지만, 그러면 위 항목을 의도적으로 매핑하고 문서화해야 한다. 단순 배포에서는 같은 값을 사용하는 편이 안전하다.

2. 호스트와 네트워크 사전 조건

공통 소프트웨어

  • Linux server와 edge node의 시간이 동기화되어 있어야 한다. HMAC replay 방지 때문에 큰 시각 오차는 인증 실패를 만든다.
  • runtime은 현재 도구 기준 containerd다.
  • cloud/control-plane에는 kubeadm, kubelet, kubectl, openssl, Git이 필요하다.
  • image build host에는 Docker Buildx 또는 동일한 multi-architecture builder가 필요하다.
  • 모든 배포 노드가 container image registry에 접근할 수 있어야 한다.
  • kubectl kustomize 또는 호환 Kustomize가 필요하다.

현재 검증 기준은 Kubernetes v1.31.x, containerd 1.7.x, KubeEdge v1.22.x 계열이다. 다른 버전은 먼저 빈 클러스터에서 CRD, CNI, EdgeMesh, Service routing을 검증한다.

네트워크

환경 방화벽에서 최소한 다음 경로를 확인한다.

출발지 목적지/포트 용도
운영자/cloud node Kubernetes API TCP 6443 cluster 관리
edge node CloudCore TCP 10000 edgecore websocket
edge node CloudCore TCP 10002, TCP 10004 HTTP/stream 기능을 사용할 때
모든 node registry TCP 443 또는 운영 registry port image pull
edge workload cluster DNS와 edgex-ingest-gateway.edgex-system.svc:8443 DNS, HTTPS telemetry
WireGuard peer UDP 51820 외부망 edge를 VPN으로 붙일 때만

edge agent는 중앙 gateway의 고정 Pod IP나 node IP를 사용하지 않는다. Cluster DNS와 Service routing이 edge node까지 동작해야 한다.

스토리지

현재 manifest가 요구하는 영속 볼륨은 다음과 같다.

PVC 기본 크기 용도
PostgreSQL data 20GiB EdgeX Event/Reading와 gateway inbox
Sense HAT agent outbox 2GiB SQLite WAL outbox
Jetson agent outbox 2GiB SQLite WAL outbox

현재 storageClassName은 local-path다.

kubectl get storageclass

새 클러스터에 local-path가 없으면 해당 provisioner를 설치하거나 모든 manifest를 실제 StorageClass 이름으로 바꾼다. PVC가 Pending인 상태에서 다음 단계로 넘어가지 않는다. local volume은 node disk 장애를 보호하는 backup이나 HA storage가 아니다.

Prometheus

state-aggregator 기본 manifest는 다음을 전제로 한다.

  • Prometheus Service: prometheus-kube-prometheus-prometheus.kube-system.svc:9090
  • monitoring.coreos.com/v1의 ServiceMonitor CRD 존재
  • 기본 ServiceMonitor selector label: release: prometheus

다른 namespace/release를 사용하면 PROMETHEUS_URL과 service-monitor.yaml label을 바꾼다. Prometheus Operator가 없다면 환경별 dashboard overlay에서 service-monitor.yaml을 제외해야 한다.

3. Kubernetes/KubeEdge 클러스터 준비

이미 정상 cluster가 있으면 이 절을 건너뛴다. 신규 구성은 kubeedge-tools/README.md를 기준으로 한다.

cloud/control-plane

cd kubeedge-tools
./download.sh
sudo KUBEEDGE_VERSION=v1.22.0 ./setup-cloud.sh

Kubernetes control-plane이 없다면 실제 IP로 초기화한다.

sudo kubeadm init \
  --apiserver-advertise-address="${CONTROL_PLANE_IP}" \
  --pod-network-cidr=10.244.0.0/16

mkdir -p "$HOME/.kube"
sudo cp /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"

중앙 workload를 control-plane에도 배치할 계획이면 해당 taint를 제거하거나 manifest에 toleration을 추가한다.

kubectl taint nodes --all node-role.kubernetes.io/control-plane- || true
kubectl taint nodes --all node-role.kubernetes.io/master- || true

CloudCore를 초기화하고 현재 repository의 patch를 적용한다.

sudo keadm init \
  --advertise-address="${CONTROL_PLANE_IP}" \
  --kubeedge-version=1.22.0
sudo ./patch-cloud.sh
sudo ./install-flannel-cloud.sh

각 edge node

각 Jetson/Raspberry Pi에서 반복한다.

cd kubeedge-tools
sudo KUBEEDGE_VERSION=v1.22.0 ./setup-edge.sh

cloud node에서 token을 발급한 뒤 edge node에서 join한다.

# cloud node
keadm gettoken

# edge node
sudo keadm join \
  --cloudcore-ipport="${CONTROL_PLANE_IP}:10000" \
  --token=<TOKEN> \
  --kubeedge-version=1.22.0
sudo ./patch-edge.sh

cloud node에서 edge용 Flannel을 적용하고, 환경에 필요하면 kubeedge-tools/README.md의 EdgeMesh 절차를 수행한다.

sudo ./install-flannel-edge.sh
cd ..

클러스터와 edgecore를 확인한다.

kubectl get nodes -o wide
kubectl -n kubeedge get pods -o wide
bash edge-orch/scripts/check-edgecore-node.sh "${JETSON_NODE}"
bash edge-orch/scripts/check-edgecore-node.sh "${SENSEHAT_NODE}"

정상 기준:

  • 모든 대상 node가 Ready
  • 실제 kubernetes.io/hostname이 1절에서 정한 이름과 일치
  • edge node의 edgecore가 active
  • cloud/edge Flannel과 EdgeMesh를 사용하는 경우 해당 DaemonSet이 정상
  • edge Pod에서 cluster DNS와 중앙 ClusterIP Service 접근 가능

git clone <REPOSITORY_URL> edge-ai-workspace
cd edge-ai-workspace
git checkout <DEPLOY_REVISION>

운영 배포는 branch 이름보다 검증한 commit SHA를 기록한다.

multi-architecture image build

edgex/telemetry-plane/Dockerfile은 gateway와 edge agent가 공유한다. 현재 중앙은 amd64, edge는 arm64이므로 두 architecture를 모두 publish하는 편이 안전하다.

docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t "${REGISTRY}/edgex-ingest-gateway:${IMAGE_TAG}" \
  -t "${REGISTRY}/edgex-telemetry-plane:${IMAGE_TAG}" \
  --push \
  edgex/telemetry-plane

docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t "${REGISTRY}/state-aggregator:${IMAGE_TAG}" \
  --push \
  edge-orch/state-aggregator

registry가 multi-architecture manifest와 각 layer를 제공하는지 확인한다.

docker buildx imagetools inspect \
  "${REGISTRY}/edgex-ingest-gateway:${IMAGE_TAG}"
docker buildx imagetools inspect \
  "${REGISTRY}/edgex-telemetry-plane:${IMAGE_TAG}"
docker buildx imagetools inspect \
  "${REGISTRY}/state-aggregator:${IMAGE_TAG}"

운영 manifest에는 가능하면 다음 형식의 immutable reference를 넣는다.

<registry>/<image>:<tag>@sha256:<manifest-digest>

수정 대상:

  • edgex/k8s/base/server/gateway.yaml
  • edgex/k8s/base/server/metadata.yaml
  • edgex/k8s/overlays/testbed/sensor-gateways/jetson.yaml
  • edgex/k8s/overlays/testbed/sensor-gateways/sensehat.yaml
  • edge-orch/state-aggregator/k8s/deployment.yaml

registry 인증이 필요하면 edgex-system, edgex-edge, default namespace의 해당 ServiceAccount 또는 Pod spec에 imagePullSecrets를 추가한다. HTTP insecure registry보다 TLS registry를 권장한다. 모든 node의 containerd가 같은 registry trust 설정을 가져야 한다.

5. 환경별 manifest 수정

중앙 배치

다음 파일의 모든 kubernetes.io/hostname 값을 ${CENTRAL_NODE}로 바꾼다.

  • edgex/k8s/base/server/core.yaml
  • edgex/k8s/base/server/gateway.yaml
  • edgex/k8s/base/server/metadata.yaml

Core, MessageBus, PostgreSQL, gateway는 중앙 노드에 한 세트만 둔다.

edge agent 배치와 identity

jetson.yaml에서 다음을 ${JETSON_NODE} 또는 별도로 정한 Jetson EDGE_ID에 맞춘다.

  • Deployment nodeSelector
  • EDGE_ID
  • edge.etri.io/id label
  • image reference
  • StorageClass

sensehat.yaml에서도 같은 항목을 ${SENSEHAT_NODE}에 맞춘다.

새 identity를 사용하면 edgex/k8s/scripts/provision-runtime-secrets.sh의 다음 항목도 함께 바꾼다.

  • edge-auth-secrets.json key
  • issue_edge_certificate의 edge ID
  • 필요하면 role별 Secret 이름과 preflight 검사 항목

Secret 이름을 바꾼 경우 Deployment의 secretKeyRef, TLS volume과 preflight-runtime-secrets.sh도 같은 이름으로 맞춘다.

Metadata와 실제 장비

Sense HAT을 그대로 쓰는 경우 metadata-contract.json의 다음 값만 새 배치와 맞춘다.

  • Device description
  • tags.edge_node_id

다른 센서/PLC를 쓰는 경우 sensehat-001을 실제 장비처럼 남겨 두지 않는다. 다음 항목을 실제 장비 계약으로 바꾼다.

  • Device Profile name과 typed resources
  • Device name, protocol, labels, tags
  • Protocol Adapter의 canonical Event deviceName, profileName, sourceName, Reading mapping

Serial, Modbus, OPC-UA, 추가 I2C와 MQTT-only 장비는 각각 실제 endpoint reconnect, profile mapping, local queue, 중앙 readback, dashboard freshness 검증을 통과한 뒤 지원으로 표시한다. 현재 command 실행은 비활성이다.

state-aggregator/dashboard

edge-orch/state-aggregator/k8s/deployment.yaml에서 다음을 수정한다.

  • nodeSelector -> ${DASHBOARD_NODE}
  • image -> 새 registry의 immutable image
  • PROMETHEUS_URL -> 실제 Prometheus Service
  • 필요하면 EDGEX_EVENT_FRESH_SECONDS

edge-orch/state-aggregator/app/config/instance_map.json에는 실제 node exporter endpoint와 Kubernetes hostname을 넣고 image를 다시 build한다.

자원증강/Workflow Builder의 node 이름은 read-only/dry-run 데모 fixture다. 새 환경에서 해당 화면도 정확히 보여야 하면 다음 값도 실제 node/resource 이름으로 정리한 뒤 state-aggregator image를 다시 build한다.

  • edge-orch/state-aggregator/app/runtime_augmentation_models.py
  • edge-orch/state-aggregator/app/virtual_resource_registry.py
  • edge-orch/state-aggregator/app/static/resource-augmentation-panels.js
  • edge-orch/state-aggregator/app/static/workflow-state.js

이 fixture를 바꿔도 Kubernetes apply/delete/restart, EdgeX mutation, command, runtime migration/offloading 기능이 생기는 것은 아니다.

6. Runtime Secret 생성

먼저 5절의 edge identity를 Secret script에 반영했는지 다시 확인한다.

빈 클러스터에서는 argument 없이 실행한다.

edgex/k8s/scripts/provision-runtime-secrets.sh
edgex/k8s/scripts/preflight-runtime-secrets.sh

이 스크립트는 다음을 생성한다.

  • PostgreSQL username/password와 gateway database URL
  • gateway TLS certificate와 CA
  • edge별 mTLS client certificate
  • edge별 HMAC secret과 gateway allowlist

주의:

  • 생성된 private key, HMAC secret, DB credential을 Git에 저장하지 않는다.
  • 기존 Secret이 있으면 기본 모드는 rotation을 거부한다.
  • 운영 중 --replace는 PostgreSQL credential까지 바꾸므로 기존 DB를 접근 불가 상태로 만들 수 있다. 파괴적 변경 승인 없이 사용하지 않는다.
  • --replace-telemetry는 DB credential을 보존하지만 gateway와 모든 edge agent의 mTLS/HMAC을 함께 바꾼다. 적용 직후 관련 Pod를 모두 재시작해야 한다.

9. Protocol Adapter 연결

현재 direct agent의 local admission endpoint는 edge host의 loopback에만 열린다.

http://127.0.0.1:18080/v1/events

Protocol Adapter는 다음 조건을 지켜야 한다.

  • canonical EdgeX v3 Event 생성
  • Metadata의 Device/Profile/resource와 정확히 일치
  • nanosecond origin 유지
  • agent가 반환한 202 queued와 동일 Event ID 확인
  • 실패 또는 507 outbox_full을 성공으로 처리하지 않음
  • RTSP frame 자체를 이 endpoint로 보내지 않음

현재 Sense HAT 참고 구현은 edge-device/publishers/에 있지만 교체 가능한 검증 fixture다. adapter 실행 사용자, Python 환경, I2C 권한과 systemd 경로를 새 edge host에 맞춰 설치한다.

승인된 adapter event로 loopback admission을 확인한다.

curl --fail-with-body \
  -H 'Content-Type: application/json' \
  --data-binary @canonical-event.json \
  http://127.0.0.1:18080/v1/events

정상 응답은 202 queued와 정확한 event_id를 포함한다.

정상 기준:

  • local admission과 같은 Event ID 존재
  • deviceName, profileName, sourceName이 Metadata/Event 계약과 일치
  • origin이 adapter sample의 nanosecond 시각
  • Reading의 resourceName, valueType, value가 profile과 일치

dashboard API

kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/devices'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/dashboard'

정상 기준:

  • inventory가 Core Metadata와 일치
  • 최신 Event/Reading과 freshness가 Core Data와 일치
  • node/workload 상태는 physical availability와 분리된 진단 정보
  • command, actuator mutation, runtime migration/offloading이 실행 기능으로 표시되지 않음

장애 복구 검증

gateway 중단 중 outbox 보존과 복구 후 replay는 telemetry 중단이 허용된 점검 창에서만 수행한다. Argo CD self-heal이 켜져 있으면 먼저 해당 Application의 sync 정책을 확인한다. 상세 순서와 persisted ACK 판정은 docs/ops/현재-데모-운영-절차.md를 따른다.

증상 우선 확인
Pod Pending 잘못된 nodeSelector, node taint, 없는 StorageClass, PVC 미결합
ImagePullBackOff registry 주소, TLS trust, 인증, imagePullSecret, CPU architecture, digest 존재 여부
edge agent 둘 중 하나만 기동 같은 node의 host-network port 18080/8443 충돌 여부
gateway 401 unknown edge EDGE_ID, HMAC allowlist key, edge credential Secret의 일치 여부

edge에서 gateway DNS timeout edgecore, EdgeMesh/CNI, cluster DNS, Service proxy 경로

dashboard에 node metric 없음 PROMETHEUS_URL, node exporter, instance_map.json, ServiceMonitor selector

12. Argo CD로 전환할 때

직접 kubectl apply와 live 검증이 통과한 뒤 GitOps로 전환한다.

  • edge-orch-argocd/argocd-apps.yaml의 repoURL, targetRevision, path를 실제 운영 repository와 환경 overlay로 변경한다.
  • 기존 registry 192.168.0.56:5000 annotation과 ingress host를 새 환경값으로 변경한다.
  • Runtime Secret은 Git에 넣지 않고 Argo CD sync 전에 별도 provision한다.
  • 전체 argocd-apps.yaml을 무조건 적용하지 않는다. 현재 배포에 필요한 edgex-telemetry와 edge-orch-state-aggregator Application부터 분리 적용한다.
  • automated prune/self-heal이 장애 복구 시험이나 수동 점검 변경을 되돌릴 수 있음을 고려한다.

데이터 보존과 이전

현재 자동화는 신규 설치를 기준으로 하며 다음을 자동 이전하지 않는다.

  • 기존 PostgreSQL Event/Reading와 gateway inbox
  • edge node local-path PVC의 SQLite outbox
  • 기존 runtime Secret과 인증서
  • ingress/Prometheus/Grafana의 운영 데이터

기존 데이터를 보존해야 하면 별도 변경 창에서 다음 원칙을 지킨다.

  1. 기존 edge outbox를 중앙 persisted ACK까지 drain한다.
  2. PostgreSQL은 검증된 logical backup/restore 절차로 이전한다.
  3. DB credential을 보존할지 새 credential로 restore할지 먼저 결정한다.
  4. mTLS/HMAC generation은 gateway와 모든 edge agent에 원자적으로 반영한다.
  5. 새 환경에서 같은 Event ID readback과 dashboard freshness를 확인하기 전 기존 환경을 제거하지 않는다.

PostgreSQL과 outbox의 현재 local-path 구성은 단일 node disk 장애를 견디는 HA나 backup이 아니다. 운영 전 backup, retention, restore drill을 별도 설계해야 한다.
