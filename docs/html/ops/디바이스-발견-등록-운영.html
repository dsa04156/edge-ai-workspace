디바이스 발견 및 등록 운영 절차

적용 범위

edge-device-discovery와 edgex-adapter-controller를 배포하고 Serial candidate를 발견·승인해 첫 EdgeX Event까지 확인하는 절차다. 현재 testbed는 개발용 AllowAllMockProvider를 명시적으로 사용한다. 운영 환경은 외부 HTTPS 인증 endpoint와 Secret token으로 교체해야 한다.

보안 기본값은 edgex/k8s/base/adapter-controller의 external fail-closed mode다. 현재 root 진입점은 edgex/k8s/overlays/development/adapter-management를 명시적으로 포함해 testbed에서만 development-mock으로 덮어쓴다. 이 개발 overlay를 운영 배포에 복사하지 않는다.

사전 조건

edgex/k8s/scripts/provision-adapter-management-secrets.sh
edgex/k8s/scripts/preflight-adapter-management-secrets.sh

kubectl get node \
  etri-dev0001-jetorn \
  etri-dev0002-raspi5 \
  etri-dev0003-raspi5

HMAC key와 관리자 token을 Git, ConfigMap, shell 출력 또는 문서에 기록하지 않는다.

배포

운영 진입점은 edgex/k8s와 Argo CD edgex-telemetry 하나다.

kubectl kustomize edgex/k8s >/dev/null
kubectl kustomize edgex/k8s/base/adapter-controller >/dev/null
kubectl kustomize \
  edgex/k8s/overlays/development/adapter-management >/dev/null
kubectl get application edgex-telemetry -n argocd
kubectl annotate application edgex-telemetry -n argocd \
  argocd.argoproj.io/refresh=hard --overwrite

kubectl rollout status deployment/edgex-adapter-controller \
  -n edgex-edge --timeout=180s
kubectl rollout status daemonset/edge-device-discovery \
  -n edgex-edge --timeout=240s
kubectl rollout status deployment/device-serial-jetson \
  -n edgex-edge --timeout=180s

확인:

kubectl get deployment,daemonset,pod -n edgex-edge -o wide
kubectl get pvc edgex-adapter-controller-state -n edgex-edge
kubectl get networkpolicy -n edgex-edge

정상 기준:

  • Controller와 Serial Device Service가 Ready다.
  • Discovery DaemonSet desired/current/ready가 대상 edge node 수와 같다.
  • edgex-adapter-controller-state PVC가 Bound다.
  • Controller가 /var/lib/adapter-controller/discovery.db에 쓸 수 있다.
  • Agent는 privileged나 host network를 사용하지 않는다.
  • Controller/Agent/Device Service image가 digest 형식이다.
  • EdgeMesh 리소스와 고정 ClusterIP/PodIP를 변경하지 않는다.

Discovery Agent는 동적 serial/I2C inventory 때문에 /dev와 /sys를 read-only로 mount한다. 이 broad mount는 발견 전용 DaemonSet에만 존재하며 ServiceAccount token, privileged 권한, host network는 없다. Active Serial/I2C probe에는 host 장치 group 권한이 추가로 필요할 수 있으므로 실장비 node의 group ID를 확인한 전용 overlay 없이 무작정 권한을 넓히지 않는다.

노드 하나만 대상으로 manifest를 검토할 때는 배포에 포함되지 않은 예시 overlay를 render할 수 있다.

kubectl kustomize \
  edgex/k8s/overlays/examples/discovery-agent-jetson >/dev/null
kubectl kustomize \
  edgex/k8s/overlays/examples/discovery-agent-raspi >/dev/null

두 예시는 각각 etri-dev0001-jetorn, etri-dev0003-raspi5만 선택한다. 실제 root 배포는 하나의 DaemonSet으로 승인된 세 edge node를 관리하며 node IP를 사용하지 않는다.

후보와 node 상태 확인

대시보드 BFF:

kubectl -n default port-forward service/state-aggregator 18000:8000

curl --fail --silent --show-error \
  'http://127.0.0.1:18000/management/discovery?includeIgnored=true&limit=2000'

대시보드 디바이스 관리 → 장비 발견에서 node, protocol, 상태와 검색어로 필터한다. 다음 필드를 함께 본다.

  • hardwareId: candidate ID의 stable 근거
  • model, recommendedProfile, matchConfidence
  • state, authState, registrationStep
  • presence, lastSeen
  • packageState, packageReason
  • failureReason

PENDING_APPROVAL이 아니거나 registrationReady=false인 후보는 승인하지 않는다. I2C bus 파일만 보이는 항목은 센서가 아니며 신규 Agent는 Plan 기반 실행에서 bus를 candidate로 만들지 않는다. 이전 ConfigMap에서 import된 bus 항목은 clean reconciliation 후 STALE이 된다.

Discovery Plan 운영

초기 Plan은 edgex/adapter-controller/config/discovery_plans.json에서 DB가 비어 있을 때 seed한다. 이후 SQLite 값이 권위다.

보수적인 원칙:

  • 사용하지 않는 protocol은 enabled=false
  • Serial은 승인 VID/PID만 등록
  • I2C는 bus/address/identity rule을 모두 등록하고 실장비 검증 창에서만 active probe
  • Modbus/OPC-UA/ONVIF/MQTT는 scanner/subscriber 구현 전까지 disabled
  • CIDR 전체 scan을 켜지 않음

Plan API 요청 형식은 디바이스-등록-API.md를 따른다. 변경 후 최대 한 scan interval 이내에 Agent report의 candidate와 scan error를 확인한다.

현재 Jetson Plan은 Device Service가 이미 같은 port를 점유하므로 manifestProbeEnabled=false다. Active WHOAMI를 검증할 때는 Device Service와의 동시 open/reset 가능성을 먼저 제거한 유지보수 창에서 수행한다.

Serial PTY 시연

실장비 없이 Manifest, telemetry, disconnect, reconnect, invalid JSON과 timeout을 검증한다.

cd edgex/device-discovery-agent
PYTHONPATH=. pytest -q tests/test_serial_plugin.py

수동 simulator:

cd edgex/device-discovery-agent
PYTHONPATH=. python -m simulators.serial_arduino \
  --behavior valid \
  --link /tmp/edge-discovery-demo/serial/by-id/usb-Arduino-sim-001

명령은 PTY slave 경로를 출력하고 link를 만든다. 다른 terminal에서 scanner 단위 테스트나 probe_serial_manifest를 실행한다. Ctrl-C로 종료하면 link가 제거된다.

오류 시연:

PYTHONPATH=. python -m simulators.serial_arduino --behavior invalid
PYTHONPATH=. python -m simulators.serial_arduino --behavior silent
PYTHONPATH=. python -m simulators.serial_arduino --behavior unsupported
  • invalid: SERIAL_MANIFEST_INVALID_JSON
  • silent: SERIAL_MANIFEST_TIMEOUT
  • unsupported: Manifest는 유효하지만 Catalog Profile mismatch로 BLOCKED

PTY 번호가 바뀌어도 같은 stable by-id link 이름을 사용하면 candidate ID는 같다.

후보 승인

운영자는 대시보드에서 후보의 물리 라벨, 설치 기록, node, USB serial, Catalog Profile을 확인한 후 검토 승인을 누른다. 승인 직후 상태는 APPROVED이며 최대 수 회의 10초 reconciliation 동안 다음과 같이 이동한다.

APPROVED
  -> SERVICE_READY
  -> METADATA_REGISTERED
  -> EVENT_CONFIRMED

승인을 여러 번 클릭해도 BFF의 idempotency key와 Controller SQLite 기록으로 중복 Device를 만들지 않는다. 외부 인증 장애이면 BLOCKED/authState=unavailable이며 인증 재확인을 사용한다. 명시적으로 denied된 장비는 자동 재시도하지 않는다.

EdgeX 등록과 첫 Event 확인

후보의 registration 응답에서 결정된 deviceName을 사용한다.

DEVICE_NAME='arduino-<stable-id>-<identity-hash-prefix>'

kubectl -n edgex-system run edgex-registration-check \
  --rm -i --restart=Never \
  --image=curlimages/curl:8.10.1 \
  -- \
  curl --fail --silent --show-error \
  "http://edgex-core-metadata:59881/api/v3/device/name/${DEVICE_NAME}"

kubectl -n edgex-system run edgex-event-check \
  --rm -i --restart=Never \
  --image=curlimages/curl:8.10.1 \
  -- \
  curl --fail --silent --show-error \
  "http://edgex-core-data:59880/api/v3/event/device/name/${DEVICE_NAME}?limit=1"

Metadata만 있고 Event가 없으면 완료가 아니다. Controller가 EVENT_CONFIRMED로 바꾼 뒤에만 등록 완료로 판정한다.

기존 6개 Arduino virtual Device를 즉시 삭제하지 않는다. 새 aggregate Device는 ResourceName: "*"를 사용하며 새 Device Service driver가 legacy route와 aggregate route로 동시에 fan-out한다. 동일 유형 route 중복은 계속 차단한다.

장애 코드와 조치

코드 원인 조치
CANDIDATE_DISCONNECTED clean scan에서 stable identity가 사라짐 케이블/전원 확인, 같은 ID 재연결 확인
SERIAL_MANIFEST_TIMEOUT WHOAMI 무응답 baud/firmware/port 경쟁 확인
CATALOG_AMBIGUOUS exact binding 여러 개 Catalog 조건을 서로 배타적으로 수정
AUTH_DENIED 외부 인증 거절 인증 시스템과 장비 신뢰 정보 검토
AUTH_TIMEOUT, AUTH_UNAVAILABLE 인증 시스템 장애 복구 후 인증 재확인
NODE_NOT_READY target KubeEdge node NotReady node/edgecore 상태 복구 후 retry
RUNTIME_START_FAILED Device Service 미기동 Pod event/log와 장치 mount 확인
RUNTIME_IMAGE_NOT_VERIFIED 실행 digest와 Catalog 불일치 CI/Argo image override와 Catalog 정렬
METADATA_REGISTRATION_FAILED Profile/Device create/readback 실패 Core Metadata 응답과 기존 object 충돌 확인
CORE_DATA_UNAVAILABLE Core Data 조회 실패 Core Data/PostgreSQL 상태 확인
FIRST_EVENT_TIMEOUT 제한 시간 내 Event 없음 Device Service route/parser/MessageBus 확인 후 retry

rollback과 복구

  • Saga 실패는 이번 attempt가 만든 리소스만 제거한다.
  • 기존 Argo Runtime, 기존 Profile/Device는 제거하지 않는다.
  • owned Device 삭제가 실패하면 의존 Profile/Runtime 삭제도 진행하지 않는다.
  • rollback이 남은 상태에서는 retry를 차단한다.
  • PVC와 SQLite를 유지한 Pod 재시작은 진행 단계에서 안전하게 이어진다.
  • SQLite 데이터 삭제는 개발 환경에서만 PVC 삭제로 수행하며 candidate/audit/Saga가 모두

복구 불가능하게 사라진다.

등록 완료 Device의 삭제/decommission은 이번 API 범위가 아니다. Candidate delete로 우회할 수 없으며 별도 ownership-aware decommission workflow를 구현하기 전에는 Core Metadata에서 수동 삭제하지 않는다.
