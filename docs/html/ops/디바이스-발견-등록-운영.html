디바이스 발견 및 등록 운영 절차

적용 범위

일반 edge-device-discovery, I2C 전용 edge-device-discovery-i2c와 edgex-adapter-controller를 배포하고 Serial/I2C candidate를 발견·승인해 첫 EdgeX Event까지 확인하는 절차다. 현재 testbed는 개발용 AllowAllMockProvider를 명시적으로 사용한다. 운영 환경은 외부 HTTPS 인증 endpoint와 Secret token으로 교체해야 한다.

보안 기본값은 edgex/k8s/base/adapter-controller의 external fail-closed mode다. 현재 root 진입점은 edgex/k8s/overlays/development/adapter-management를 명시적으로 포함해 testbed에서만 development-mock으로 덮어쓴다. 이 개발 overlay를 운영 배포에 복사하지 않는다.

사전 조건

edgex/k8s/scripts/provision-adapter-management-secrets.sh
edgex/k8s/scripts/preflight-adapter-management-secrets.sh

kubectl get node \
  etri-dev0001-jetorn \
  etri-dev0002-raspi5 \
  etri-dev0003-raspi5

HMAC key와 외부 인증 credential을 Git, ConfigMap, shell 출력 또는 문서에 기록하지 않는다.

배포

운영 진입점은 edgex/k8s와 Argo CD edgex-telemetry 하나다.

kubectl kustomize edgex/k8s >/dev/null
kubectl kustomize edgex/k8s/base/adapter-controller >/dev/null
kubectl kustomize \
  edgex/k8s/overlays/development/adapter-management >/dev/null
kubectl get application edgex-telemetry -n argocd
kubectl annotate application edgex-telemetry -n argocd \
  argocd.argoproj.io/refresh=hard --overwrite

kubectl rollout status deployment/edgex-adapter-controller \
  -n edgex-edge --timeout=180s
kubectl rollout status daemonset/edge-device-discovery \
  -n edgex-edge --timeout=240s
kubectl rollout status daemonset/edge-device-discovery-i2c \
  -n edgex-edge --timeout=240s
kubectl rollout status deployment/device-serial-jetson \
  -n edgex-edge --timeout=180s

확인:

kubectl get deployment,daemonset,pod -n edgex-edge -o wide
kubectl get pvc edgex-adapter-controller-state -n edgex-edge
kubectl get networkpolicy -n edgex-edge

정상 기준:

  • Controller와 Serial Device Service가 Ready다.
  • 일반 Serial Discovery DaemonSet은 dev0001/dev0002/dev0003에서 3/3 Ready이고, I2C 전용

DaemonSet은 dev0003에서 1/1 Ready다.

  • edgex-adapter-controller-state PVC가 Bound다.
  • Controller가 /var/lib/adapter-controller/discovery.db에 쓸 수 있다.
  • 일반 Agent는 privileged와 host network를 사용하지 않는다. I2C 전용 Agent만 아래의

제한적 예외를 사용한다.

  • Controller/Agent/Device Service image가 digest 형식이다.
  • EdgeMesh 리소스와 고정 ClusterIP/PodIP를 변경하지 않는다.

일반 Discovery Agent는 동적 Serial inventory 때문에 /dev와 /sys를 read-only로 mount한다. 이 broad mount는 dev0001/dev0002/dev0003의 발견 전용 DaemonSet에만 존재하며 ServiceAccount token, privileged 권한과 host network는 없다.

dev0003의 I2C 전용 Agent는 /dev/i2c-1만 exact CharDevice로 mount한다. Kubernetes hostPath만으로는 해당 character device가 container device cgroup에 추가되지 않아 실측상 EPERM이 발생했으므로, 현재 testbed에서는 privileged: true를 예외로 사용한다. 컨테이너는 계속 non-root UID/GID 2002, read-only root filesystem, supplemental group 988로 실행한다. 988은 dev0003 host의 현재 i2c group ID이므로 다른 노드에서는 실제 group을 확인해 manifest/overlay를 검토하고, /dev 전체 mount나 root 실행으로 넓히지 않는다.

노드 하나만 대상으로 manifest를 검토할 때는 배포에 포함되지 않은 예시 overlay를 render할 수 있다.

kubectl kustomize \
  edgex/k8s/overlays/examples/discovery-agent-jetson >/dev/null
kubectl kustomize \
  edgex/k8s/overlays/examples/discovery-agent-raspi >/dev/null

두 예시는 각각 etri-dev0001-jetorn의 일반 Discovery와 etri-dev0003-raspi5의 I2C 전용 Discovery만 남긴다. 실제 root 배포도 node name으로 일반 DaemonSet 3개 node와 I2C 전용 DaemonSet 1개 node를 선택하며 node IP를 사용하지 않는다.

후보와 node 상태 확인

대시보드 BFF:

kubectl -n default port-forward service/state-aggregator 18000:8000

curl --fail --silent --show-error \
  'http://127.0.0.1:18000/management/discovery?includeIgnored=true&limit=2000'

대시보드 장비 관리에서 노드를 먼저 선택하고 연결 대기의 검색·필터를 열어 protocol, 상태와 검색어로 후보를 좁힌다. 후보의 identity·binding·failure 근거는 후보 상세정보를 펼쳐 확인한다. 다음 필드를 함께 본다.

  • hardwareId: candidate ID의 stable 근거
  • model, recommendedProfile, matchConfidence
  • state, authState, registrationStep
  • presence, lastSeen
  • packageState, packageReason
  • failureReason

PENDING_APPROVAL이 아니거나 registrationReady=false인 후보는 승인하지 않는다. I2C bus 파일만 보이는 항목은 센서가 아니며 신규 Agent는 Plan 기반 실행에서 bus를 candidate로 만들지 않는다. 이전 ConfigMap에서 import된 bus 항목은 clean reconciliation 후 STALE이 된다.

Discovery Plan 운영

초기 Plan은 edgex/adapter-controller/config/discovery_plans.json에서 node Plan이 없을 때 seed한다. Git seed의 version이 SQLite의 현재 version보다 높으면 새 검증 계약으로 업그레이드하고, 같거나 낮으면 SQLite 값을 유지한다.

보수적인 원칙:

  • 사용하지 않는 protocol은 enabled=false
  • Serial은 알려진 장비에 승인 VID/PID를 등록한다. 빈 allowlist는 Raspberry Pi의 passive

inventory에만 쓰며 Manifest probe와 자동 등록을 허용하지 않는다.

  • I2C는 bus/address/identity rule을 모두 등록하고 실장비 검증 창에서만 active probe
  • Modbus/OPC-UA/ONVIF/MQTT는 scanner/subscriber 구현 전까지 disabled
  • CIDR 전체 scan을 켜지 않음

Plan API 요청 형식은 디바이스-등록-API.md를 따른다. 변경 후 최대 한 scan interval 이내에 Agent report의 candidate와 scan error를 확인한다.

현재 Jetson Plan은 Device Service가 이미 같은 port를 점유하므로 manifestProbeEnabled=false다. Active WHOAMI를 검증할 때는 Device Service와의 동시 open/reset 가능성을 먼저 제거한 유지보수 창에서 수행한다.

Raspberry Pi USB Serial passive 발견

dev0002/dev0003 Plan은 Serial을 켜되 VID/PID allowlist를 비우고 manifestProbeEnabled=false로 둔다. Agent는 /dev/serial/by-id/*와 /sys의 USB metadata만 읽으며 장치 파일을 열지 않는다. 발견과 신뢰·등록을 분리하기 위한 설정이다.

kubectl get pod -n edgex-edge \
  -l app.kubernetes.io/name=edge-device-discovery -o wide
kubectl logs -n edgex-edge \
  -l app.kubernetes.io/name=edge-device-discovery --since=5m --prefix

2026-07-28 Catalog 배포 전 dev0003 live 확인값은 다음과 같다.

devicePath: /dev/serial/by-id/usb-1a86_USB_Serial-if00-port0
kernelDevice: ttyUSB0
VID/PID: 1a86:7523
state: BLOCKED
presence: present
packageState: binding-required
registrationReady: false

이 상태는 발견 성공이면서 당시 등록 차단 성공이었다. 이후 MPU6050 6축 IMU용 exact binding raspi5-mpu6050-serial-v1, mpu6050-imu-v1 Profile/parser와 검증 Runtime template을 추가했다. 새 Catalog 반영 뒤 동일 후보는 PENDING_APPROVAL, registrationReady=true가 됐고 실제 승인 Saga도 실행했다. 당시 Serial telemetry가 없어 첫 Event timeout으로 FAILED가 됐으며 Controller가 자신이 만든 동적 Runtime을 rollback했다. Profile 생성만으로 이 오류가 해결되지는 않는다.

실장비는 CH340 bridge를 쓰는 ESP32-D0WD-V3 revision 3.1로 식별했다. edgex/device-serial/examples/mpu6050_json/mpu6050_json.ino를 esp32:esp32@3.3.11로 compile·flash했고 hash 검증과 115200 baud 상태 출력을 확인했다. 센서가 없을 때 출력은 다음과 같다.

{"type":"status","device_id":"mpu6050-001","status":"sensor_not_found","who_am_i_0x68":null,"who_am_i_0x69":null}

이 상태 JSON은 진단용이며 mpu6050-imu-v1 Event가 아니다. ESP32 pin pair 진단과 Raspberry Pi bus 1 read에서 0x68, 0x69 모두 ACK가 없었으므로 다음 실물 배선을 확인한다.

ESP32 MPU6050/GY-521
3V3 VCC
GND GND
GPIO21 SDA
GPIO22 SCL
GND AD0 (0x68)

운영 firmware는 1초마다 센서를 다시 탐색하므로 배선 복구 뒤 재부팅 없이 다음 필드를 포함한 JSON-line으로 전환해야 한다.

{"device_id":"mpu6050-001","sensor":"imu","acceleration_x":0.1,"acceleration_y":0.2,"acceleration_z":9.8,"gyro_x":0.01,"gyro_y":0.02,"gyro_z":0.03}

6축 JSON을 먼저 확인한 다음 candidate의 retry를 실행한다. Controller가 만든 Runtime Pod가 Ready가 되고 Core Data 첫 Event가 도착한 뒤에만 EVENT_CONFIRMED다. 출력이 없으면 다시 FIRST_EVENT_TIMEOUT이다. USB serial number가 없는 동일 CH340 장비를 여러 대 연결할 계획이면 현재 by-id 이름만으로 충분히 구분되는지 먼저 검증하고, 구분되지 않으면 포트 topology 등 검토된 stable identity 규칙을 추가한다.

같은 dev0003에서 일반 Agent는 DISCOVERY_PROTOCOLS=serial, I2C 전용 Agent는 DISCOVERY_PROTOCOLS=i2c로 보고한다. Controller는 report의 scannedProtocols 범위에서만 missing candidate를 STALE 처리한다. Serial 후보가 갱신될 때 Sense HAT 후보가 EVENT_CONFIRMED, present를 유지하는지 함께 확인한다.

Sense HAT I2C 실장비 시연

현재 dev0003 Plan은 bus 1과 주소 0x1c, 0x5c, 0x5f, 0x6a만 허용한다. 각 주소의 read-only register 0x0f가 각각 0x3d, 0xbd, 0xbc, 0x68일 때만 raspberry-pi-sense-hat-v1 후보 하나를 만든다.

kubectl logs -n edgex-edge \
  daemonset/edge-device-discovery-i2c --since=5m --prefix

정상 로그는 scan마다 candidates=1 scanErrors=0이다. 대시보드에서는 다음 evidence를 확인한다.

nodeName: etri-dev0003-raspi5
devicePath: /dev/i2c-1
model: raspberry-pi-sense-hat-v1
IdentityFingerprint: 1c3d-5cbd-5fbc-6a68
recommendedProfile: etri-sensehat-gyroscope
state: PENDING_APPROVAL
registrationReady: true

후보 승인

운영자는 대시보드에서 후보의 물리 라벨, 설치 기록, node, USB serial, Catalog Profile을 확인한 후 검토 승인을 누른다. 승인 직후 상태는 APPROVED이며 최대 수 회의 10초 reconciliation 동안 다음과 같이 이동한다.

현재 PoC 대시보드와 /management/* BFF에는 운영자 Bearer 토큰이 없다. 후보 승인·거절·재시도 PATCH는 browser Authorization header 없이 요청하고, 요청별 Idempotency-Key와 BFF→Controller 내부 HMAC은 계속 적용한다. 수동 후보 추가·삭제, Runtime 재시작·퇴역, Device/connection mutation도 같은 계약을 사용한다.

외부 AuthProvider 승인은 후보 장비의 신뢰 검증이며 대시보드 운영자 인증이 아니다. 따라서 이 경로는 접근이 제한된 개발 테스트베드에서만 사용한다. 운영 환경에 노출하려면 Ingress 앞에 별도 사용자 인증·인가를 추가하고, 내부 HMAC을 사용자 인증으로 설명하지 않는다.

APPROVED
  -> SERVICE_READY
  -> METADATA_REGISTERED
  -> EVENT_CONFIRMED

승인을 여러 번 클릭해도 BFF의 idempotency key와 Controller SQLite 기록으로 중복 Device를 만들지 않는다. 외부 인증 장애이면 BLOCKED/authState=unavailable이며 인증 재확인을 사용한다. 명시적으로 denied된 장비는 자동 재시도하지 않는다.

rollback과 복구

  • Saga 실패는 이번 attempt가 만든 리소스만 제거한다.
  • 기존 Argo Runtime, 기존 Profile/Device는 제거하지 않는다.
  • owned Device 삭제가 실패하면 의존 Profile/Runtime 삭제도 진행하지 않는다.
  • rollback이 남은 상태에서는 retry를 차단한다.
  • PVC와 SQLite를 유지한 Pod 재시작은 진행 단계에서 안전하게 이어진다.
  • SQLite 데이터 삭제는 개발 환경에서만 PVC 삭제로 수행하며 candidate/audit/Saga가 모두

복구 불가능하게 사라진다.

등록 완료 candidate는 일반 DELETE로 지울 수 없고, 대시보드의 명시적 decommission 경로가 exact candidate 확인값과 사유를 요구한다. Controller가 이번 Saga에서 만든 Device/Profile/Runtime만 정리하며 reuse-existing으로 검증한 Sense HAT Runtime/Profile/ Device는 삭제하지 않는다. Core Metadata에서 수동 삭제해 이 소유권 검사를 우회하지 않는다.

decommission한 장비가 물리적으로 계속 연결돼 있으면 다음 Discovery Agent report에서 같은 stable candidate ID가 다시 PENDING_APPROVAL로 나타난다. 이는 자동 재등록이 아니므로 운영자가 다시 승인해야 하고 첫 Event를 새로 확인해야 한다. 장비를 후보 목록에서 계속 제외하려면 등록 연결을 퇴역시킨 뒤 재발견 후보를 무시 처리한다.

물리 장비를 먼저 분리해 후보가 STALE이 된 경우에도 이력으로 정리를 누르면 ignored decision으로 바뀌어 기본 운영 목록에서 사라지고 candidate·상태 전이·실패 이력은 SQLite audit에 남는다. 이 동작은 Core Metadata Device, 기존 Runtime 또는 Profile을 삭제하지 않는다. 2026-07-30 분리한 MPU6050 후보는 이 경로의 대상이며 활성 동적 Runtime은 이미 실패 Saga rollback으로 남아 있지 않다. 같은 날 이력으로 정리를 적용해 후보는 STALE/ignored 감사 이력으로 보존되고 기본 목록에서는 숨겨진다.

2026-07-28 Sense HAT live 검증에서는 후보 candidate-f0829ddd...를 decommission한 뒤 30초 이내 같은 ID와 presence=present로 재탐색됐고, 재승인 뒤 EVENT_CONFIRMED로 복귀했다. 전후 EdgeX Device는 13개, Sense HAT Device는 6개로 동일했다.
