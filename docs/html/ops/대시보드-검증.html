대시보드 검증 점검표

목적과 현재 경계

이 문서는 state-aggregator가 EdgeX Core Metadata와 Core Data를 읽어 만든 dashboard API/UI와 별도 Device Management 관리 경계를 확인한다. 2026-07-21 기존 custom Agent와 aggregate sensehat-001 bootstrap은 퇴역했다. 2026-07-30 현재 관측 검증 목표는 기존 Serial 6개, Sense HAT I2C 6개와 승인 Saga의 Arduino aggregate 1개, 총 13개 EdgeX Device identity를 정확히 집계하면서 등록 목록에서는 두 물리 source로 묶는 것이다.

물리 디바이스 inventory, 관리 상태와 telemetry의 authority는 EdgeX다. KubeEdge는 node/workload 관찰에만 사용한다.

API 확인

운영 acceptance는 ClusterIP, Pod IP, port-forward 우회나 LoadBalancer IP의 /aggregator 경로가 아니라 GitOps로 관리하는 외부 Traefik host route를 사용한다. 배포 절차와 소유권은 대시보드 배포를 따른다.

DASHBOARD_BASE_URL="http://aggregator.192.168.0.56.sslip.io"

curl -fsS "${DASHBOARD_BASE_URL}/state/devices"
curl -fsS "${DASHBOARD_BASE_URL}/state/device-profiles"
curl -fsS "${DASHBOARD_BASE_URL}/state/dashboard"
curl -fsS "${DASHBOARD_BASE_URL}/state/summary"
curl -fsS "${DASHBOARD_BASE_URL}/management/adapters"
curl -fsS "${DASHBOARD_BASE_URL}/management/adapter-runtimes"

현재 정상 기준:

  • source가 EdgeX Core Metadata/Core Data다.
  • 삭제한 aggregate sensehat-001/edge-telemetry-agent가 live inventory로 남지 않는다.
  • virtual-temperature-001, virtual-light-001, virtual-magnetic-001, virtual-acceleration-{x,y,z}-001이 각각 독립 행이다.
  • env-sensehat-{temperature,humidity,pressure}-01, imu-sensehat-{compass,orientation,gyroscope}-01도 각각 독립 행이다.
  • 각 Device의 service/profile/protocol이 device-serial-jetson/Serial 또는 device-sensehat-raspi/I2C 계약과 일치한다.
  • 총 13개 Device가 UNLOCKED, UP, connected, available, fresh이고 계약된 typed latest Reading을 반환한다.
  • arduino-multisensor-v1 Profile의 승인 Saga Device는 기존 resource별 6개 Device를 삭제하지 않고 함께 유지된다. 물리 source arduino-001은 대시보드 그룹 key이며 exact Device 이름으로 가정하지 않는다.
  • 과거 Event가 남아 있어도 Metadata에 없는 device를 available로 부활시키지 않는다.
  • node/workload 상태를 physical device availability로 합치지 않는다.
  • 과거 AI Pipeline/Workflow Builder 이름과 전용 샘플 실행 API는 노출되지 않는다.
  • 서비스 설계는 실제 EdgeX Device/Profile resource만 선택하고 브라우저 초안,

validation, dry-run 계획만 제공하며 배포·실행 버튼과 mutation API가 없다.

  • Adapter Runtime inventory에서 기존 Serial/I2C는 owner=external로 관측되고 대시보드의

restart/retire action이 비활성화된다.

  • /state/devices가 EdgeX tag의 physical_device_id와 선택적

hardware_binding_id를 반환한다. 신규 connection은 두 값을 모두 보존한다.

  • Modbus 개발 simulator Runtime은 퇴역 상태이고 root 운영 render에 없다. MQTT는 개발용

검증 package만 설치 가능하며 root render에 broker나 고정 Device Service가 없다. 운영 MQTT TLS/auth, OPC-UA와 RTSP 일반 endpoint 배포는 활성화되지 않는다.

strict API 계약 검증도 같은 Ingress 기준 URL을 사용한다.

python3 tools/check_dashboard_api.py --base-url "${DASHBOARD_BASE_URL}"

검증기는 현재 EdgeX 단일 권위 계약인 profile_name, device_service_name, protocol_names, admin_state, operating_state, connection_state, device_service_available, telemetry_freshness와 available/degraded/unavailable·Core Data KPI를 확인한다. 퇴역한 Mapper/DeviceStatus의 mapper_running, telemetry_enabled, device_status_freshness_ratio는 필수 field나 physical availability 근거로 검사하지 않는다.

Dashboard UI 확인

  1. 요약 카드가 실제 registered_device_count와 일치한다.
  2. device 목록이 Core Metadata 응답과 일치한다.
  3. 12개 가상 Device detail이 각 Metadata와 latest Event 값을 동일하게 표시한다.
  4. stale/no events 상태를 fresh로 보정하지 않는다.
  5. KubeEdge node와 workload는 별도 진단 영역에 표시한다.
  6. aggregate sensehat-001이나 Agent outbox를 현재 점검 대상으로 안내하지 않고, 직접 I2C Device 6개를 현재 inventory로 표시한다.
  7. 디바이스 관리 첫 영역에서 연결 등록, 장비 관측, 통신, 데이터 상태를 별도 칸으로

표시하고 등록만으로 장비 관측을 주장하지 않는다.

  1. protocol package가 Serial/I2C는 재사용 가능, MQTT 개발 package는 Runtime이 없으면

설치 가능, Modbus는 exact simulator binding에서만 설치 가능으로 표시된다. OPC-UA/RTSP와 일반 미검증 endpoint에는 설치/등록 버튼이 없다.

  1. Device Management가 Runtime owner/phase/node/consumer와 등록 binding만 표시하고 raw

manifest, image, hostPath, hostNetwork, ClusterIP/PodIP 입력을 제공하지 않는다.

  1. 관리자 token 입력란이 없고, 검증하고 연결은 validation 실패 시 mutation을

수행하지 않는다. Runtime mode 선택은 노출하지 않고 auto plan만 사용한다.

  1. 외부/Argo runtime의 restart/retire는 비활성화되고 Controller 소유 runtime에만 action이

표시된다.

  1. ${DASHBOARD_BASE_URL}/#management로 열었을 때 관리 API도 같은 Traefik host의

/management/*로 요청되고 200을 반환한다. ClusterIP 또는 Pod IP로 우회하지 않는다.

  1. 데스크톱 1440px와 모바일 390px에서 문서 가로 overflow가 없고 세 노드 전환 결과가

각각의 등록 연결·Device 수와 일치한다.

  1. ${DASHBOARD_BASE_URL}/#designer에서 Device/Profile resource와 node 수가 실제 API와

일치하고, 기본 설계가 local_recent source node 일치 검증을 통과한다.

  1. 단계 추가·삭제, 포트 연결, inspector 설정, 오류 항목 선택, localStorage 저장이

반응한다. 전체 보기, 확대·축소, 배경 이동, 단계 이동, 미니맵과 단계/설정 패널을 확인하며 390/768/1024/1440px에서 문서와 캔버스 모두 가로 overflow가 없다.

현재 테스트베드 dashboard는 관리자 credential 입력란이나 browser Authorization header를 사용하지 않는다. 이 상태는 인증 완료가 아니라 운영자 인증이 없는 개발 PoC다. 실제 운영 mutation을 노출하려면 신뢰 가능한 TLS와 별도 사용자 인증·인가를 Ingress 앞에 먼저 적용해야 한다.

Device Management 안전 검증

실제 빈 hardware binding이 없는 현재 테스트베드에서는 기존 endpoint를 빼앗는 배포 canary를 만들지 않는다. 대신 다음을 확인한다.

  1. Serial과 I2C의 runtime plan이 기존 exact runtime을 REUSE한다.
  2. 이미 소비 중인 endpoint/deviceName을 사용한 connection validation은 충돌을 명시하고

mutation하지 않는다.

  1. Controller와 state-aggregator의 Secret preflight가 통과하고 두 namespace의 internal HMAC

key가 일치한다.

  1. Kubernetes server-side dry-run에서 CRD, 최소 RBAC, Deployment와 NetworkPolicy가

수락된다.

  1. Controller 단위/통합 테스트에서 owner collision, node NotReady, Metadata 조회 실패,

consumer가 남은 retire와 동일 idempotency 재요청이 fail-closed다.

실장비 연결을 실제 생성할 때는 Adapter Runtime과 Device 연결 관리의 사전 조건과 rollback 절차를 따른다.

현재 Device Service PASS 기준

관찰 대상 authority/API PASS 기준
inventory/state Core Metadata → /state/devices Device/Profile/Device Service/protocol과 상태 일치
telemetry/freshness Core Data Event/Reading 실제 sample timestamp와 typed reading 일치
physical availability state-aggregator 정규화 Metadata 상태와 Event freshness 정책 일치
node/workload Kubernetes/KubeEdge 별도 진단이며 physical availability gate가 아님
service binding dashboard detail 같은 device identity와 consumer relation 표시

실패 시 점검 순서

  1. physical endpoint와 Device Service 상태
  2. Core Metadata binding
  3. Core Data latest Event/Reading
  4. state-aggregator normalization/freshness
  5. frontend rendering
  6. Core Metadata에 퇴역 fixture가 남았거나 frontend가 sample payload를 하드코딩하지 않았는지

live API와 UI를 확인하지 않고 repository 문서나 fixture만으로 PASS를 선언하지 않는다.
