Jetson Arduino Uno의 Serial 경로와 Raspberry Pi Sense HAT v1의 직접 I2C 경로가 각각…

운영 문서 원본: ops/현재-데모-운영-절차.md 수정: 2026-07-23 11:22 HTML 생성: 2026-07-23 11:41

현재 서비스 데모 운영 절차

목적

이 문서는 Jetson Arduino Uno의 Serial 경로와 Raspberry Pi Sense HAT v1의 직접 I2C 경로가 각각 EdgeX Device Service → 기능별 가상 Device 6개 → 중앙 MessageBus/Core Data/PostgreSQL → state-aggregator/dashboard로 이어지는 현재 정상 경로를 점검한다. 또한 Jetson acceleration X/Y/Z Local Data → sensor-anomaly-demo → /state/service-demo → dashboard로 이어지는 첫 실측 AI 서비스 데모를 검증한다. 기존 Agent, SQLite outbox, aggregate Sense HAT bootstrap, edge-local MQTT broker와 InfluxDB workload는 현재 경로가 아니다.

Core Data telemetry freshness는 latest Event의 nanosecond origin을 sample 시각으로 계산하며 API 조회 시각이나 Kubernetes 상태로 대체하지 않는다.

배치 기준

구분 현재 기준
중앙 namespace edgex-system
edge namespace edgex-edge
중앙 노드 etri-ser0002-cgnmsb
중앙 workload Core Keeper/Metadata/Data/Command, internal MessageBus, PostgreSQL, 유지 중인 ingest gateway
edge workload device-serial-jetson, device-sensehat-raspi 각 1 replica
AI service workload sensor-anomaly-demo 1 replica, etri-dev0001-jetorn
physical node etri-dev0001-jetorn, etri-dev0003-raspi5
physical source Arduino Uno /dev/arduino-001, Sense HAT v1 /dev/i2c-1
EdgeX inventory Serial 6개 + I2C 6개, 총 가상 Device/Profile 12개 / Device Service 2개
운영 진입점 edgex/k8s/kustomization.yaml
Argo CD Application edgex-telemetry
AI service Argo CD Application edge-orch-sensor-anomaly-demo

EdgeMesh 리소스는 이 절차의 변경 대상이 아니다. Kubernetes ClusterIP Service 객체는 정상 서비스 디스커버리에 사용하지만 고정 ClusterIP, PodIP와 node IP를 설정에 넣거나 우회 경로로 사용하지 않는다. Device Service는 중앙 Keeper, Metadata와 MessageBus의 .svc.cluster.local FQDN을 사용한다.

KubeEdge cloudcore Helm release가 설치한 kubeedge/DaemonSet/edge-eclipse-mosquitto는 edge node 3개에 legacy 호환 구성으로 남아 있다. 이 DaemonSet은 edgex/k8s나 현재 서비스 데모가 생성한 local broker가 아니며 Serial/I2C → Local Data API → AI consumer 경로에서 사용하지 않는다. 현재 데모의 MQTT 부재 판정은 edgex-device-mqtt, edge Agent와 데모 전용 broker/consumer가 없다는 뜻이며, KubeEdge Helm 구성 제거는 별도 작업 범위다.

가상 Device 계약

Device Profile Resource Command
virtual-temperature-001 etri-arduino-temperature temperature_raw temperature
virtual-light-001 etri-arduino-light light_raw light
virtual-magnetic-001 etri-arduino-magnetic magnetic_raw magnetic
virtual-acceleration-x-001 etri-arduino-acceleration-x acceleration_x_raw acceleration_x
virtual-acceleration-y-001 etri-arduino-acceleration-y acceleration_y_raw acceleration_y
virtual-acceleration-z-001 etri-arduino-acceleration-z acceleration_z_raw acceleration_z

여섯 Device는 같은 Port=/dev/arduino-001, BaudRate=115200, DeviceID=arduino-001을 사용하고 ResourceName만 다르다. Driver는 이 공통 연결을 공유 Serial reader 1개로 열며, acceleration wire sample 하나를 X/Y/Z Event 세 개로 나눈다.

Sense HAT Device Profile Resources Command
env-sensehat-temperature-01 etri-sensehat-temperature temp_humidity, temp_pressure temperature
env-sensehat-humidity-01 etri-sensehat-humidity humidity humidity
env-sensehat-pressure-01 etri-sensehat-pressure pressure pressure
imu-sensehat-compass-01 etri-sensehat-compass compass compass
imu-sensehat-orientation-01 etri-sensehat-orientation pitch, roll, yaw orientation
imu-sensehat-gyroscope-01 etri-sensehat-gyroscope gyro_x, gyro_y, gyro_z gyroscope

Sense HAT Device 6개는 Bus=/dev/i2c-1, DeviceID=sensehat-001을 공유하고 ResourceGroup으로 기능별 route를 구분한다. Device Service 내부 RTIMULib reader process 하나가 실제 보드를 읽고 총 11개 Float64 Reading으로 fan-out한다. sensehat-001은 물리 source ID이며 aggregate EdgeX Device가 아니다.

1. 로컬 render 검증

kubectl kustomize edgex/k8s >/tmp/edgex-current.yaml
kubectl apply --dry-run=server -f /tmp/edgex-current.yaml

정상 기준:

  • 중앙 Core/MessageBus/PostgreSQL/gateway가 render된다.
  • Namespace/edgex-edge, default-deny와 Device Service별 최소 NetworkPolicy가 render된다.
  • 두 Service와 Deployment/device-serial-jetson, Deployment/device-sensehat-raspi가 render된다.
  • Device Service는 각각 etri-dev0001-jetorn, etri-dev0003-raspi5에 고정되고 hostNetwork: true를 사용하지 않는다.
  • host의 Arduino by-id CharDevice와 Sense HAT I2C CharDevice만 각 Pod의 /dev/arduino-001, /dev/i2c-1에 정확히 마운트된다.
  • 각 ConfigMap에는 해당 Profile 6개와 Device list 1개가 포함된다.
  • 중앙 Keeper/Metadata/MessageBus는 .svc.cluster.local FQDN으로 참조된다.
  • edgex-edge-agent-*, Agent PVC/ConfigMap/bootstrap, device-mqtt, edge-local broker와 InfluxDB workload를 배포하지 않는다.

현재 PoC의 Serial/I2C 장치 접근은 각 Device Service Pod에 privileged: true, UID/GID 0을 허용한다. 이 예외는 정확한 CharDevice mount, Recreate 전략과 service-account token 비마운트로 범위를 줄인다. NetworkPolicy는 manifest에 선언되어 있지만 현재 Flannel CNI에서는 강제되지 않는다. 후속 운영 강화에서는 Device Plugin 또는 더 좁은 장치 권한으로 대체한다.

2. Argo CD 상태

kubectl -n argocd get application edgex-telemetry \
  -o jsonpath='{.spec.source.targetRevision}{"\n"}{.status.sync.status}{"\n"}{.status.health.status}{"\n"}{.status.operationState.phase}{"\n"}'

정상 기준은 대상 revision이 의도한 Git commit이고 Synced, Healthy, Succeeded인 것이다. Application은 prune/self-heal을 사용하므로 live 리소스를 임의 수정하지 않고 Git의 root Kustomize를 고친다.

서비스 데모는 EdgeX root render와 분리된 Application이다.

kubectl -n argocd get application edge-orch-sensor-anomaly-demo \
  -o jsonpath='{.spec.source.targetRevision}{"\n"}{.status.sync.status}{"\n"}{.status.health.status}{"\n"}{.status.operationState.phase}{"\n"}'

edgex-telemetry revision을 불필요하게 바꾸지 않고, edge-orch-sensor-anomaly-demo와 edge-orch-state-aggregator만 같은 검증된 Git revision을 가리키게 한다.

3. live workload와 장치 mount

kubectl -n edgex-system get deploy,statefulset,job,pod,service,pvc -o wide
kubectl -n edgex-edge get deploy,pod,service,pvc,configmap,networkpolicy -o wide
kubectl -n edgex-edge get deployment device-serial-jetson \
  -o jsonpath='{.spec.template.spec.nodeSelector.kubernetes\.io/hostname}{"\n"}{.spec.template.spec.hostNetwork}{"\n"}{.spec.template.spec.containers[0].image}{"\n"}'

kubectl -n edgex-edge get deployment device-sensehat-raspi \
  -o jsonpath='{.spec.template.spec.nodeSelector.kubernetes\.io/hostname}{"\n"}{.spec.template.spec.hostNetwork}{"\n"}{.spec.template.spec.containers[0].image}{"\n"}'

정상 기준:

  • 중앙 Core 서비스와 PostgreSQL이 Ready다. common-config bootstrap Job은 Completed일 수 있다.
  • device-serial-jetson과 device-sensehat-raspi Pod가 각각 Jetson과 Raspberry Pi에서 1/1 Running이다.
  • 두 image는 immutable ARM64 digest다.
  • Pod restart가 반복 증가하지 않는다.
  • edgex-edge에 Agent outbox PVC, local broker와 별도 telemetry DB가 없다.
  • sensor-anomaly-demo가 Jetson에서 1/1 Running, restart 0이고 immutable ARM64 digest를 실행한다.
  • AI service는 hostNetwork, host device mount, PVC, MQTT/InfluxDB 연결을 사용하지 않는다.

Serial 로그에서 시작 중 잘린 line 1~2개가 malformed로 폐기될 수 있다. 이후 metric 등록, reader restart, Metadata update가 반복되거나 ERROR가 계속 나오면 정상으로 보지 않는다. Sense HAT reader는 시작 시 IMU를 prime한 뒤 pressure/humidity를 초기화하며, bounded retry 이후에도 sample 응답이 없거나 reader가 반복 재시작하면 정상으로 보지 않는다.

for name in \

정상 기준:

  • Device Service base address는 http://device-serial-jetson.edgex-edge.svc.cluster.local:59910이다.
  • 위 Device 6개가 각각 UNLOCKED, UP이고 service/profile binding이 일치한다.
  • 각 Device의 Serial protocol은 공통 물리 endpoint와 고유 ResourceName을 가진다.
  • tags.physicalDeviceId=arduino-001, tags.nodeName=etri-dev0001-jetorn이다.
  • aggregate EdgeX Device arduino-001과 Profile etri-arduino-serial은 없다.
  • Sense HAT Device Service base address는 http://device-sensehat-raspi.edgex-edge.svc.cluster.local:59911이다.
  • Sense HAT Device 6개도 각각 UNLOCKED, UP이고 Profile과 i2c protocol binding이 일치한다.
  • 각 I2C protocol은 공통 Bus=/dev/i2c-1, DeviceID=sensehat-001과 고유 ResourceGroup을 가진다.
  • tags.physicalDeviceId=sensehat-001, tags.nodeName=etri-dev0003-raspi5이며 aggregate EdgeX Device sensehat-001은 없다.

5. Core Data Event/Reading

for name in \
  virtual-temperature-001 virtual-light-001 virtual-magnetic-001 \
  virtual-acceleration-x-001 virtual-acceleration-y-001 virtual-acceleration-z-001
do
  kubectl get --raw \
    "/api/v1/namespaces/edgex-system/services/http:edgex-core-data:59880/proxy/api/v3/event/device/name/${name}?limit=1"
done

for name in \
  env-sensehat-temperature-01 env-sensehat-humidity-01 env-sensehat-pressure-01 \
  imu-sensehat-compass-01 imu-sensehat-orientation-01 imu-sensehat-gyroscope-01
do
  kubectl get --raw \
    "/api/v1/namespaces/edgex-system/services/http:edgex-core-data:59880/proxy/api/v3/event/device/name/${name}?limit=1"
done

정상 기준:

  • Device별 latest Event에 계약된 Int32 Reading 하나만 있다.
  • units는 raw이고 Event/Reading의 nanosecond origin이 계속 증가한다.
  • acceleration wire sample은 X/Y/Z Device에 각각 독립 Event로 저장된다.
  • Sense HAT Device 6개의 latest Event에는 각 Profile에 계약된 Float64 Reading만 있고 총 resource 수는 11개다.
  • API readback으로 저장을 확인하며 중앙 MessageBus의 MQTT ACK만으로 persistence를 주장하지 않는다.

6. read-only Core Command

for pair in \
  virtual-temperature-001/temperature \
  virtual-light-001/light \
  virtual-magnetic-001/magnetic \
  virtual-acceleration-x-001/acceleration_x \
  virtual-acceleration-y-001/acceleration_y \
  virtual-acceleration-z-001/acceleration_z
do
  kubectl get --raw \
    "/api/v1/namespaces/edgex-system/services/http:edgex-core-command:59882/proxy/api/v3/device/name/${pair}"
done


for pair in \
  env-sensehat-temperature-01/temperature \
  env-sensehat-humidity-01/humidity \
  env-sensehat-pressure-01/pressure \
  imu-sensehat-compass-01/compass \
  imu-sensehat-orientation-01/orientation \
  imu-sensehat-gyroscope-01/gyroscope
do
  kubectl get --raw \
    "/api/v1/namespaces/edgex-system/services/http:edgex-core-command:59882/proxy/api/v3/device/name/${pair}"
done

정상 기준은 두 Device Service가 10분 recent cache에서 해당 Device의 최신값과 origin을 반환하는 것이다. multi-resource command인 Sense HAT temperature, orientation과 gyroscope는 각각 2개, 3개, 3개 Reading을 반환한다. sample이 10분 보존 범위를 벗어나거나 Pod가 재시작해 아직 새 sample이 없으면 최신값 조회가 실패할 수 있다. Profile에는 writable resource가 없으므로 PUT이나 actuator command를 보내지 않는다.

7. Jetson Local Data API

주의: 현재 테스트베드의 Flannel CNI는 Kubernetes NetworkPolicy를 집행하지 않는다. 2026-07-21 실측에서 edge-ai.io/local-data-client=true label이 없는 기존 Pod도 이 API에 접근했다. 따라서 label은 배치·정책 의도 표식이며 현재 보안 경계가 아니다. Local Data API는 unauthenticated read-only endpoint이므로 실제 접근 차단이 필요하면 NetworkPolicy 지원 CNI 또는 mTLS/애플리케이션 인증을 먼저 적용한다.

8A. 12개 Device 저장 이력과 dashboard 그래프

dashboard는 PostgreSQL에 직접 연결하지 않는다. 브라우저가 state-aggregator의 선택 Device API를 호출하고, state-aggregator가 중앙 EdgeX Core Data API에서 PostgreSQL-backed Event/Reading을 읽는다.

Dashboard
  -> GET /state/devices/{device}/telemetry?window={range}&limit=1000
  -> state-aggregator
  -> EdgeX Core Data API
  -> PostgreSQL

Core Data의 GET /api/v3/event/device/name/{name}에는 start/end query를 붙이지 않는다. 이 endpoint는 offset/limit만 지원하므로 state-aggregator가 최신 1,000 Event 이내에서 Event origin을 기준으로 window를 적용한다. 5분 결과의 가장 오래된 origin이 요청 시작시각보다 이전이면 정상으로 판정하지 않는다.

12개 Device의 기본 30분 이력을 API에서 확인한다.

for name in \
  virtual-temperature-001 virtual-light-001 virtual-magnetic-001 \
  virtual-acceleration-x-001 virtual-acceleration-y-001 virtual-acceleration-z-001 \
  env-sensehat-temperature-01 env-sensehat-humidity-01 env-sensehat-pressure-01 \
  imu-sensehat-compass-01 imu-sensehat-orientation-01 imu-sensehat-gyroscope-01
do
  kubectl get --raw \
    "/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/devices/${name}/telemetry?window=-30m&limit=1000"
done

정상 기준:

  • 모든 응답은 배열이고 각 Reading의 device_name이 요청 Device와 같다.
  • source_name, resource_name, value_type, value, timestamp, nanosecond origin과 event_id가 보존된다.
  • Serial Device 6개는 각각 계약된 Int32 resource series로 분리된다.
  • Sense HAT Device 6개는 Profile별 Float64 series로 분리되며 temperature는 2개, orientation과 gyroscope는 각각 3개 resource를 표시할 수 있다.
  • 조회 오류나 빈 결과를 /state/devices의 latest_readings로 대체하지 않는다.

브라우저에서는 Assets의 Device 행을 선택해 다음을 확인한다.

  1. 선택 직후 기본 30분 이력을 조회한다.
  2. 5분, 30분, 1시간, 24시간과 새로고침이 선택 Device에만 적용된다.
  3. resource별 series, 반환 Reading 수, 실제 첫/마지막 timestamp가 보인다.
  4. 최신 1000 events 제한 문구가 보인다. 한 Event에 Reading이 여러 개면 반환 Reading 수는 1,000보다 클 수 있다.
  5. 긴 범위가 최신 1,000 Event로 잘렸을 때 요청한 전체 기간을 모두 읽었다고 해석하지 않는다.
  6. 빠르게 Device나 범위를 바꿔도 이전 요청의 늦은 응답이 현재 선택을 덮어쓰지 않는다.
  7. 조회 중·빈 결과·오류 상태가 각각 구분되고 오류가 다른 Device나 dashboard 전체를 가짜 정상값으로 바꾸지 않는다.

8B. Dashboard Device Management와 온보딩 dry-run

Device Management는 EdgeX Core Metadata의 Device/Profile을 제한적으로 등록·수정하는 관리 화면이다. 기존 Assets와 /state/*는 계속 read-only이고 Workflow Builder의 browser-local dry-run과도 상태를 공유하지 않는다.

기본 Deployment는 DEVICE_MANAGEMENT_ENABLED=false다. 다음 조회와 dry-run은 Metadata를 수정하지 않으므로 기본 상태에서 실행할 수 있다.

    "device":{
      "name":"onboarding-dryrun-serial-001",
      "description":"dry-run only",

      "tags":{"physicalDeviceId":"arduino-001","nodeName":"etri-dev0001-jetorn"},
      "protocolProperties":{
        "Port":"/dev/arduino-001",

정상 기준:

  • adapter 응답의 Serial/Sense HAT I2C는 Device Service readback이 성공할 때 installed,

미실행이면 unavailable이며 Modbus/OPC-UA/MQTT/RTSP는 unsupported다.

  • 기본 배포에서는 모든 adapter의 mutationEnabled=false이고 화면 상단에

DRY-RUN ONLY · MUTATION DISABLED가 표시된다.

  • 위 예시는 이미 virtual-temperature-001이 소유한 endpoint/resource를 다시 요청하므로

valid=false와 protocol_binding_exists를 반환하는 것이 정상이다. dry-run은 valid, issues, warnings, plan만 반환하며 Profile이나 Device를 생성하지 않는다.

  • create/PATCH를 호출해도 404이고 Core Metadata에 새 객체가 생기지 않는다.

mutation 활성화는 edge-orch/state-aggregator/k8s/README.md의 Secret/TLS gate를 먼저 충족한 뒤 GitOps로 수행한다. 활성화 후에도 관리자 Bearer token과 요청별 Idempotency-Key가 모두 필요하다. 적용 결과는 metadata_applied 또는 waiting_for_event와 verified를 구분해 표시한다. 동일 key·동일 payload 재시도는 같은 operation을 복구하고, 같은 key·다른 payload는 409다.

자동 검증에서는 live Metadata mutation을 실행하지 않는다. live canary가 필요하면 기존 12개 route와 겹치지 않는 격리된 Device Service endpoint를 먼저 마련하고 onboarding-canary-*처럼 정확한 prefix와 정리 대상을 사전 승인한다. 기존 12개 Device와 EdgeMesh를 변경하지 않는 별도 절차로만 수행한다.

9. 저장과 캐시 경계

  • Device Service 메모리: 공통 Go ring cache, Device/resource별 최근 10분·최대 10,000 sample, 서비스별 sample slot 합계 최대 64MiB, Core Command와 Local Data API용
  • 중앙 Core Data/PostgreSQL: 최근·과거 Event/Reading의 영구 저장과 조회
  • 로컬 recent window cache: 있음; /api/v3/localdata/stats와 custom metrics로 관측, Pod 재시작 시 초기화, 중앙 history fallback 없음
  • 64MiB 계산 경계: sample slot 배열만 포함; Go map/runtime/HTTP buffer는 제외되며 Pod memory limit가 전체 프로세스 상한
  • SQLite outbox/offline replay: 없음
  • 별도 InfluxDB: 없음
  • sensor-anomaly-demo 결과: process memory의 최근 최대 1,000건; Pod 재시작 시 초기화, raw history 저장소가 아님

따라서 각 Device Service와 같은 edge node의 Workflow Pod는 edge-ai.io/local-data-client=true label과 Service FQDN으로 최근 구간을 직접 소비한다. 이 label은 현재 Flannel 환경에서 접근 제어를 강제하지 않는다. 이 기능은 bounded read cache일 뿐 중앙 단절 중 미전송 Event 보존·재전송이나 장기 history를 제공하지 않는다.

10.2 재실행 조건과 기대 결과

Test Scenario: source 장애 후 Device 상태와 수집 복구

  • 시작 조건: 중앙 Core 서비스와 두 Device Service가 Ready이고 12개 Device가 UP, latest origin이 증가한다.
  • 실행 역할: 테스트베드 운영자. 실제 장치 또는 kernel driver/reader process를 하나씩만 중단한다.
  • 확인 순서: 장애 전 tools/verify_e2e.sh 실행 → 대상 source 중단 → Core Metadata의 해당 6개 Device DOWN 확인 → source 복구 → 6개 UP 확인 → Local Data와 Core Data origin 증가 확인.
  • 기대 결과: 비대상 Device Service와 EdgeMesh는 변경되지 않고 대상 physical source에 묶인 6개 Device만 함께 상태 전이한다.

Test Scenario: 중앙 MessageBus 장애 중 로컬 연속성

  • 시작 조건: Argo CD Application policy와 MessageBus replica를 기록하고 두 local stats 및 대표 Core Data Event를 저장한다.
  • 실행 역할: 데이터 유실과 중앙 중단을 승인받은 운영자. MessageBus endpoint가 실제 0 Pod인지 확인한 뒤 제한된 시간만 중단한다.
  • 확인 순서: 장애 중 두 Local Data latest/stats와 sensor-anomaly-demo 증가 확인 → Core Data count/origin 고정 확인 → MessageBus 1 replica와 Argo self-heal 원복 → 중앙 새 Event 확인.
  • 기대 결과: 로컬 ring과 같은-node AI consumer는 지속되지만 중앙 Event는 멈춘다. 복구 후 새 Event는 재개되지만 outage 구간은 replay되지 않는다.

재검증 후에는 다음 read-only 진입점으로 전체 상태를 다시 확인한다.

rtk bash tools/verify_e2e.sh

이 결과는 실제 케이블·보드 손분리 현장 시연을 대체하지 않는다. 실제 손분리 → 해당 6개 Device DOWN/dashboard degraded → 재연결 → 새 Event 발행은 현장 gate로 남긴다. 현재 Device Service에는 durable outbox가 없으므로 중앙 단절 중 데이터 보존을 완료 기능으로 설명하지 않는다. Modbus와 OPC-UA는 실제 endpoint가 없어 완료로 판정하지 않는다.

sensor-anomaly-demo는 실제 증가 raw origin과 로컬 inference/중앙 readback을 배포 gate로 검증한다. detector anomaly/clear 전이는 결정론적 테스트 대상이고 실제 장치 움직임 anomaly는 별도 현장 시연 gate다. 이 고정 Deployment를 동적 workflow 실행, runtime migration 또는 offloading 완료로 설명하지 않는다.
