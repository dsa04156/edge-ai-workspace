프로젝트 배경

한 줄 정의

현재 단계는 혼합 디바이스 엣지 AI 플랫폼의 전체 동적 오케스트레이션을 먼저 완성하는 단계가 아니라, 디바이스와 서비스를 실제로 연결하고 이를 대시보드에서 가시화하며 현장 생산성 향상 효과를 설명 가능한 서비스 데모로 만드는 단계다.

현재 단계에서는 이 기반을 서비스 데모, 디바이스-서비스 연결 구조, 통합 운영 가시화 중심으로 정리한다.

대상 환경

  • x86 엣지 AI 서버
  • Jetson 엣지 AI 디바이스
  • Raspberry Pi 5 엣지 디바이스
  • 물리 센서 디바이스
  • 가상 디바이스 / 디바이스트윈

현재 테스트베드 노드:

구분 hostname 역할
서버 1 etri-ser0001-cg0msb control-plane / 운영 서버
서버 2 etri-ser0002-cgnmsb worker / 추론 서버
Jetson etri-dev0001-jetorn edge AI device
Raspberry Pi 5 etri-dev0002-raspi5 edge light device

현재 우선순위

  1. 서비스 데모 1종을 먼저 완성한다.
  2. 디바이스 등록/관리 체계를 정리한다.
  3. 디바이스-서비스 바인딩 구조를 구현한다.
  4. 통합 대시보드에서 디바이스, 노드, 서비스, 상태, KPI를 함께 보이게 한다.
  5. 옥동 시나리오의 생산성 향상 효과를 설명 가능한 지표로 정리한다.
  6. 현재 문서와 데모에서는 workflow/offloading/agent-assisted planning 계열을 현행 연구 방향과 분리된 과거 검토/보관 경로로 둔다.

현재 아키텍처와 구현 상태

물리 디바이스 통합의 권위 경로는 다음 하나뿐이다.

물리 센서 / PLC / 장비
  -> Jetson 또는 Raspberry Pi의 EdgeX Device Service
  -> etri-ser0002-cgnmsb의 중앙 EdgeX MessageBus
  -> Core Data -> PostgreSQL
  -> Application Service / AI consumer / state-aggregator / dashboard
  • Core Metadata가 물리 디바이스 inventory·schema·관리 상태의 원본이다.
  • Core Data Event가 telemetry와 freshness의 원본이다.
  • command는 Core Command에서 해당 프로토콜을 독점 연결한 EdgeX Device Service로 전달한다.
  • KubeEdge는 Kubernetes edge node와 workload의 등록·배치·상태 관찰에만 사용한다.
  • 중앙 Core Keeper, Metadata, Data, Command, MessageBus, PostgreSQL은 etri-ser0002-cgnmsb에 한 세트만 배치한다.
  • edgex-device-mqtt는 etri-dev0001-jetorn, edgex-device-mqtt-sensehat는 etri-dev0003-raspi5에 배치한다.

현재 root edgex/k8s/kustomization.yaml은 이 중앙 MessageBus topology를 렌더링한다. edgex/telemetry-plane/, HTTPS ingest gateway, edge telemetry agent, SQLite outbox와 edgex/k8s/base/ overlays는 비활성 대안 설계·프로토타입이며 현재 배포 경로가 아니다.

1차 MQTT 수직 슬라이스에는 SQLite offline replay가 없다. 중앙 MessageBus 또는 네트워크 장애 시 telemetry가 유실될 수 있고, 복구 기준은 연결 회복 뒤 새 Event 수집이 재개되는 것이다.

2026-07-14 UNO 네 source와 2026-07-15 Sense HAT 여섯 source의 typed Event/Reading을 기존 canary에서 확인했다. 이 증거는 장비·profile·Reading 계약의 근거이며 중앙 server2 topology live cutover 완료를 자동으로 뜻하지 않는다.

Serial, Modbus, OPC-UA, RTSP는 목표 아키텍처에 포함되지만 아직 완료로 주장하지 않는다. 각 프로토콜은 해당 EdgeX Device Service, profile, 실제 장비 연결, 명령·상태·telemetry 검증을 독립 migration wave로 통과한 뒤 현재 범위로 승격한다.

state-aggregator와 대시보드는 중앙 EdgeX Core Metadata/Core Data를 소비하는 현재 cutover 대상이다. Prometheus/Kubernetes 정보는 node/workload 관찰을 보조하지만 물리 디바이스 상태를 결정하지 않는다. 과거 워크플로 실행·배치 실험 컴포넌트는 현행 대시보드와 데모 운영 경로에서 제외한다.

디바이스 등록과 상태 전략

EdgeX Core Metadata에 Device Profile과 Device를 사전 등록한다. Device Service는 Device의 protocols에 정의된 endpoint를 독점 사용하고, profile resource에 따라 값을 정규화하며, operating state와 command를 관리한다. 임의의 MQTT topic 발행만으로 Core Metadata Device가 자동 생성되지는 않는다. discovery를 지원하는 프로토콜도 승인과 profile 검증 없이 current inventory로 승격하지 않는다.

availability는 EdgeX 관리 상태와 최신 Core Data event를 다음 순서로 해석한다.

  1. adminState=LOCKED 또는 operatingState=DOWN이면 unavailable/disconnected.
  2. operatingState=UNKNOWN이면 degraded/unknown.
  3. operatingState=UP이고 최신 event가 freshness 기준 안이면 available.
  4. operatingState=UP이어도 event가 없거나 stale이면 degraded.

MQTT canary

현재 첫 canary 입력은 다음 canonical topic을 사용한다.

factory/devices/{device-name}/telemetry

canary bridge는 payload를 route profile로 검증/정규화하여 EdgeX device-mqtt async topic으로 전달하고, stock device-mqtt가 typed Event/Readings를 Core Data에 기록한다. 이는 MQTT canary의 전달 범위이며 Serial/Modbus/OPC-UA/RTSP 완료나 live cluster cutover 완료를 뜻하지 않는다.

mappers/script/test_device.py, mappers/mqttvirtual/, KubeEdge DeviceModel/Device/DeviceStatus, mapper의 direct-to-Influx 경로와 다음 topic 규칙은 legacy physical integration/test 경로다.

factory/devices/{device-name}/command
factory/devices/{device-name}/heartbeat

이 legacy 경로는 현재 EdgeX status/control plane과 병행해서 실행하거나 fallback으로 사용하지 않는다. 과거 데이터나 manifest는 마이그레이션 비교 자료일 수 있지만 Core Metadata inventory, Core Data telemetry, EdgeX Device Service command보다 우선하지 않는다.
