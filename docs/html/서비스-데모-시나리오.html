서비스 데모 시나리오

현재 상태

기존 MQTT 기반 Sense HAT Agent 데모는 2026-07-21 퇴역했다. 현재 서비스 데모는 Jetson Arduino Uno의 실측 acceleration X/Y/Z를 정식 EdgeX Device Service의 Local Data API로 읽고, 같은 Jetson의 sensor-anomaly-demo가 변화 점수를 계산해 중앙 대시보드에 디바이스-서비스-AI 연결과 결과를 표시하는 것이다. Raspberry Pi Sense HAT 직접 I2C는 전체 물리 디바이스 inventory와 telemetry 수직 슬라이스로 함께 유지하지만 첫 이상 탐지 입력은 아니다.

Core Data telemetry freshness는 latest Event의 nanosecond origin을 sample 시각으로 계산하며 API 조회 시각이나 Kubernetes 상태로 대체하지 않는다.

두 protocol의 정상 수집·저장·조회·대시보드 경로를 live 검증했다. 이상 탐지 서비스도 Jetson에서 Ready이고 두 번의 local status 조회에서 실제 raw origin과 framesProcessed가 각각 증가했으며, 중앙 /state/service-demo와 브라우저 dashboard readback까지 확인했다. detector의 anomaly/clear 상태 전이는 결정론적 테스트로 검증했다. 실제 장치를 움직여 anomaly를 발생시키는 현장 시연과 케이블/보드 분리·복구는 아직 남아 있으므로 실제 고장 검출 실증으로 표현하지 않는다.

Arduino sensor
  -> Serial endpoint on etri-dev0001-jetorn
  -> custom EdgeX Serial Device Service
  -> acceleration virtual Device X/Y/Z
  +-> Local Data API -> sensor-anomaly-demo @ Jetson
  |                  -> online-gaussian-baseline-v1
  |                  -> state-aggregator / dashboard
  -> Core Data Event / Reading -> PostgreSQL raw history

Sense HAT v1
  -> /dev/i2c-1 on etri-dev0003-raspi5
  -> custom EdgeX Sense HAT I2C Device Service
  -> environment/IMU Profile 6개 / Device 6개
  -> Core Data Event / Float64 Reading
  -> PostgreSQL / state-aggregator / dashboard

데모가 증명해야 하는 것

  • Core Metadata Device가 physical inventory와 관리 상태의 권위다.
  • Device Service가 실제 Serial/I2C endpoint, reader 재시작·재연결, 값 표준화와 상태를 관리한다.
  • Device Profile이 resource 이름, value type, 단위와 read/write 계약을 정의한다.
  • Core Data 최신 Event/Reading이 telemetry와 freshness의 권위다.
  • KubeEdge는 Device Service와 AI workload의 배치·상태만 관리한다.
  • dashboard가 device, profile, Device Service, protocol, 상태, 최신 reading과 consumer 연결을 한 흐름으로 보여준다.
  • Jetson AI consumer가 X/Y/Z의 같은 origin만 결합하고 실제 raw sample의 증가를 따라간다.
  • detector 결과는 raw telemetry와 분리된 derived service output이며 EdgeX 물리 Device를 새로 꾸며내지 않는다.

사전 조건

  1. Jetson의 Arduino by-id 장치 파일과 Raspberry Pi의 /dev/i2c-1을 확인하고 각 Pod에 /dev/arduino-001, /dev/i2c-1로 정확히 마운트한다.
  2. Serial은 115200 baud newline-delimited JSON, I2C는 컨테이너 내부 RTIMULib reader와 허용 field/value type을 사용한다.
  3. device-serial-jetson, device-sensehat-raspi와 각 Profile/Device 6개 identity를 사용한다. arduino-001, sensehat-001은 물리 source ID다.
  4. 두 Device Service image를 immutable ARM64 digest로 배포한다.
  5. 중앙 EdgeX Core 서비스와 PostgreSQL이 Ready여야 한다.
  6. edgex-edge에는 DNS와 중앙 Keeper/Metadata/MessageBus, 중앙 command와 의도된 Workflow client를 선언하는 NetworkPolicy가 있다. 현재 Flannel CNI는 이를 강제하지 않으므로 보안 경계로 주장하지 않는다.
  7. sensor-anomaly-demo는 etri-dev0001-jetorn에 배치되고, 고정 IP가 아닌 device-serial-jetson.edgex-edge.svc.cluster.local:59910을 사용한다.

MQTT broker는 Arduino가 MQTT-only 장비가 아닌 이상 사전 조건이 아니다.

시연 순서

1. Device Service workload 확인

Jetson과 Raspberry Pi에 각 Device Service Pod가 배치되고 Ready인지 확인한다. KubeEdge node 상태는 workload 진단 정보이며 physical device availability를 단독 결정하지 않는다.

2. Metadata binding 확인

Core Metadata에서 다음 관계를 확인한다.

Device Service
  -> Device Profile
  -> Device
  -> serial 또는 i2c protocol binding

adminState, operatingState와 endpoint 연결 상태가 실제 Device Service 보고와 일치해야 한다.

3. 실제 telemetry 확인

Arduino와 Sense HAT의 실제 sample을 발생시키고 Core Data에서 같은 deviceName의 Event/Reading을 조회한다. resource 이름과 valueType, 단위, timestamp가 profile과 일치해야 한다.

4. 장애와 복구 확인

장치 분리 또는 통신 오류 시 Device Service가 DOWN/degraded 상태와 원인을 보고하고, 장치 복구 뒤 backoff 재연결해 새 Event를 발행하는지 확인한다. 재연결 로직은 단위 테스트했지만 실제 케이블 분리 시연은 남아 있다. 현재 outbox는 없으므로 중앙 단절 중 데이터 보존을 주장하지 않는다.

5. dashboard 확인

dashboard에서 다음을 한 화면으로 확인한다.

  • Device/Profile/Device Service/protocol
  • admin_state, operating_state, connection_state
  • 최신 Event 시각과 telemetry_freshness
  • typed latest_readings
  • 관련 AI service/storage/dashboard consumer
  • 선택적 node/workload 진단 정보
  • physical source arduino-001 → device-serial-jetson → acceleration Device 3개 → sensor-anomaly-demo binding
  • raw X/Y/Z, magnitude, score/threshold, sample origin, input/model 상태

6. Jetson 로컬 이상 탐지 확인

sensor-anomaly-demo의 /api/v1/status를 두 번 조회한다. 두 번째 조회에서 latest.origin과 counters.framesProcessed가 증가하고 inputState=fresh, mode=live, 세 acceleration Device identity가 일치해야 한다. 30개 frame warm-up 뒤 model은 ready가 된다.

이 consumer는 Local Data API를 500ms마다 조회하는 polling 방식이다. push stream이나 고주기 연속 스트리밍으로 설명하지 않는다. algorithm은 3축 magnitude의 online-gaussian-baseline-v1 변화 탐지이며 학습된 고장 종류 분류기가 아니다. 두 sample 연속 threshold 이상에서 anomaly로 전이하고 세 sample 연속 정상 범위에서 clear되는 계약은 결정론적 테스트로 검증한다.

상태 판정

조건 dashboard 상태 의미
UNLOCKED + UP + connected + fresh Event available 수집과 저장 경로가 실제로 관측됨
Device Service UP이지만 stale/no events degraded 등록은 되었지만 데이터 경로 점검 필요
LOCKED/DOWN/disconnected unavailable 관리 상태 또는 endpoint 연결 점검 필요
Device Service 미배포 not_deployed 또는 등록 없음 배포/등록 문제, 완료 아님

PASS 기준

  1. 실제 Jetson Serial과 Raspberry Pi I2C endpoint 및 Device Service 연결 증거가 있다.
  2. Device Service/Profile/Device가 정확한 관계로 등록된다.
  3. 실제 sample의 typed Event/Reading이 Core Data에서 조회된다.
  4. 장애·복구 시 상태와 새로운 Event가 기대대로 변한다.
  5. dashboard가 같은 EdgeX device identity와 freshness를 표시한다.
  6. 문서, manifest, 테스트와 live 상태가 같은 구조를 설명한다.
  7. sensor-anomaly-demo가 같은 Jetson에서 실제 증가하는 세 축 raw origin을 처리하고 중앙 /state/service-demo가 같은 결과를 반환한다.
  8. dashboard가 normal/anomaly/degraded를 텍스트로 구분하고 관측 실패 시 가짜 0 값을 표시하지 않는다.

현재값을 반환하는 read-only Core Command GET은 확인했다. detector의 anomaly 상태 전이는 테스트 PASS 대상이지만 실제 사람이 장치를 움직여 anomaly를 유발하는 장면은 별도 현장 시연 gate다. write command/actuator, 동적 workflow 실행, runtime migration/offloading은 이 데모의 PASS 범위가 아니다.
