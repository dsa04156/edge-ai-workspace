처음부터 배우는 Edge AI 시스템

이 문서는 컴퓨터와 AI를 처음 보는 사람도 현재 시스템을 처음부터 끝까지 이해할 수 있도록 아주 쉬운 말로 설명한다. 어려운 이름이 나오면 바로 뜻을 붙인다.

1. 이 시스템은 무엇을 하나요?

한 문장으로 말하면 다음과 같다.

기계에 붙은 센서의 숫자를 받아서, AI가 이상한 변화가 있는지 보고, 사람이 화면에서 확인하게 해 주는 시스템이다.

어린이집에 비유하면 이렇다.

실제 시스템 쉬운 비유
센서 교실의 온도계와 흔들림 측정기
EdgeX 선생님에게 숫자를 전달하는 반장
AI 서비스 숫자를 보고 “평소와 다른가?” 생각하는 선생님
Device1 교실 안의 작은 컴퓨터
Server GPU 어려운 계산을 도와주는 큰 컴퓨터
대시보드 모든 상황을 한눈에 보는 상황판

2. 무엇이 어디에 있나요?

센서

센서는 실제 세상의 값을 숫자로 바꾼다.

  • 가속도 X: 좌우 방향으로 얼마나 흔들렸는지 나타낸다.
  • 가속도 Y: 앞뒤 방향으로 얼마나 흔들렸는지 나타낸다.
  • 가속도 Z: 위아래 방향으로 얼마나 흔들렸는지 나타낸다.
  • 온도: 얼마나 뜨겁거나 차가운지 나타낸다.

현재 데모는 Arduino 센서의 X/Y/Z/온도를 사용한다. 이것은 시스템 연결을 확인하는 테스트베드다. 옥동 공장의 실제 펌프 고장을 학습한 완성 모델이라는 뜻은 아니다.

Device1

Device1은 센서 가까이에 있는 작은 컴퓨터다. 현재 이름은 etri-dev0001-jetorn이고 Jetson 장비다.

Device1은 센서 값을 읽고, 값을 정리하고, 기본 AI 계산을 하고, 결과를 저장하고, 자기 CPU와 메모리가 얼마나 바쁜지 알려 준다.

Server GPU

Server GPU는 Device1보다 큰 서버다. 현재 여유 GPU가 확인된 실제 노드는 etri-ser0002-cgnmsb다. API의 server1 이름은 기존 호환을 위해 유지한다.

Server GPU의 AI 추론 Pod는 HAMi를 통해 GPU 일부를 배정받는다. GPU backend 이름은 cuda-online-baseline, 모델 버전은 cuda-baseline-1.0.0이다. CUDA는 NVIDIA GPU에서 계산을 실행하는 기술 이름이다.

Server GPU는 다음 세 가지가 모두 맞아야 “준비됨”이 된다.

  1. HAMi가 GPU를 실제로 배정한다.
  2. 프로그램이 CUDA 장치를 연다.
  3. GPU에서 시험 계산을 실행하고 올바른 답을 받는다.

GPU 이름만 붙이고 CPU로 계산하는 구조가 아니다. CUDA 시험 계산이 실패하면 모델은 준비되지 않은 것으로 처리한다. 다만 이 GPU 모델도 현재 통계 기준선의 GPU 실행 버전이다. 옥동 현장 데이터로 학습한 최종 고장 분류 모델은 아직 아니다.

EdgeX

EdgeX는 “어떤 센서가 있고, 그 센서가 무슨 값을 보냈는지”를 관리한다.

  • Core Metadata: 센서의 이름과 설명을 보관한다.
  • Device Profile: 센서가 어떤 종류의 값을 보내는지 정한다.
  • Device Service: 실제 센서와 이야기한다.
  • Core Data: 센서가 보낸 최신 값과 이력을 보관한다.

물리 센서에 관한 정답은 EdgeX가 가진다. 대시보드가 센서를 마음대로 새로 만들거나 값을 고치지 않는다.

Kubernetes와 KubeEdge

Kubernetes와 KubeEdge는 프로그램을 컴퓨터에 올리고 살아 있는지 확인한다.

  • Node: 프로그램을 실행하는 컴퓨터다.
  • Pod: 실행 중인 프로그램 한 묶음이다.
  • Service: 다른 프로그램이 Pod를 찾아가는 고정 입구다.
  • Ready: 지금 요청을 받을 준비가 됐다는 뜻이다.

Kubernetes는 센서 값의 주인이 아니다. 컴퓨터와 프로그램의 실행 상태를 관리한다.

HAMi

HAMi는 여러 프로그램이 GPU를 나누어 쓸 수 있게 도와주는 GPU 스케줄러다.

현재 Server GPU AI Pod는 다음처럼 GPU를 요청한다.

요청 뜻
nvidia.com/gpu: 1 GPU 장치 하나를 사용할 수 있게 해 달라
nvidia.com/gpucores: 20 GPU 연산 자원의 20%를 사용하겠다
nvidia.com/gpumem: 1024 GPU 메모리 1,024MiB를 사용하겠다

이 숫자는 Pod가 요청하는 몫이다. 실제 GPU 사용률은 Prometheus와 GPU exporter가 따로 관측한다.

Prometheus

Prometheus는 컴퓨터의 계기판 숫자를 모은다. CPU, 메모리, GPU, 처리 시간, 기다리는 작업 수, 1초에 처리한 작업 수를 모은다. 값이 없거나 너무 오래됐으면 0으로 거짓 표시하지 않고 “관측 불가”로 표시한다.

state-aggregator와 대시보드

state-aggregator는 여러 곳의 정보를 읽어 한 화면에 모은다.

EdgeX의 센서 상태 ─┐
Kubernetes의 Pod 상태 ├─→ state-aggregator ─→ 대시보드
Prometheus의 자원 값 ┤
AI 서비스의 결과 ───┘

대시보드는 읽고 보여주는 역할이다. 현재 화면에서 자동으로 센서를 제어하거나 Pod를 증설하지 않는다.

3. 센서 값 한 건은 어떻게 움직이나요?

센서 수집 → 전처리 → 특징 추출 → AI 추론 → 결과 저장 → 대시보드
                                      ├→ Device1 CPU
                                      └→ Server GPU 후보

1단계: 센서 수집

Device Service가 Arduino에서 X/Y/Z/온도를 읽는다. 각 값에는 측정 시각인 origin이 붙는다.

2단계: 전처리

프로그램이 같은 시각의 X/Y/Z를 한 묶음으로 맞춘다. 온도는 그 시각에서 2초 안에 있는 가장 가까운 값을 고른다. 필수 값이 하나라도 없거나 너무 오래됐으면 계산을 멈추고 이유를 남긴다.

3단계: 특징 추출

원래 숫자를 바로 판단하지 않고 이해하기 쉬운 특징으로 바꾼다.

  • RMS: 흔들림의 전체 크기
  • peak: 가장 큰 흔들림
  • kurtosis: 갑자기 튀는 충격의 모양
  • temperature mean: 최근 평균 온도
  • temperature stddev: 온도가 얼마나 들쭉날쭉한지
  • temperature delta: 처음과 마지막 온도의 차이

4단계: AI 추론

처음 30개 값으로 “평소 모습”을 준비한다. 그 뒤 새 값이 평소와 얼마나 다른지 점수를 낸다. 진동 점수 70%와 온도 점수 30%를 합친다.

기본 경로는 Device1 CPU다. Server GPU 후보는 같은 설명 가능한 기준선 계산의 점수 계산 부분을 CUDA GPU에서 실행한다.

5단계: 결과 저장

결과에는 측정 시각, 특징, 점수, 정상/이상 상태, 모델 버전, 실제 처리 위치가 들어간다. 서비스가 소유한 SQLite 저장소에 기록한다.

6단계: 대시보드 표시

대시보드는 현재 실행 중인 단계를 밝게 표시하고 다음 정보를 함께 보여준다.

  • 센서가 신선한지
  • 모델이 준비됐는지
  • Device1과 Server GPU가 몇 건씩 처리했는지
  • CPU, GPU, latency, backlog, throughput
  • 설비 이상 알림

4. “설비 이상”과 “컴퓨터가 바쁨”은 왜 다른가요?

센서 특징과 이상 점수는 설비 상태를 판단하는 근거다. CPU·메모리·GPU와 처리 지연은 노드와 서비스의 운영 상태를 확인하는 별도 근거다. 대시보드는 두 상태를 섞어 하나의 정상/비정상 값으로 만들지 않는다.

5. 대시보드는 어디서 보고 무엇을 보나요?

브라우저에서 다음 주소를 연다.

6. 문제가 생기면 무엇부터 확인하나요?

항상 왼쪽에서 오른쪽 순서로 확인한다.

센서 → EdgeX → Device1 서비스 → Prometheus → Server GPU → 대시보드
  1. 센서의 최신 값이 EdgeX에 있는지 본다.
  2. Device Service와 AI Pod가 Ready인지 본다.
  3. AI 모델이 warm-up을 끝내고 Ready인지 본다.
  4. Prometheus 지표의 시각이 최신인지 본다.
  5. Server GPU Pod에 HAMi GPU 할당 표시가 있는지 본다.
  6. Server GPU 준비 API에 accelerator: cuda와 GPU 이름이 나오는지 본다.

더 자세한 명령은 현재 데모 운영 절차를 따른다.

7. 지금 되는 것과 아직 안 되는 것

지금 되는 것

  • 실제 센서 값을 EdgeX로 수집한다.
  • 센서 freshness를 판단한다.
  • Device1에서 기준선 이상감지를 실행한다.
  • 결과와 알림을 저장한다.
  • Server GPU에 HAMi GPU 추론 후보를 준비한다.
  • DAG와 운영 지표를 대시보드에서 본다.

아직 자동으로 하지 않는 것

  • AI가 마음대로 Kubernetes Pod를 늘리지 않는다.
  • 운영자 승인 없이 Server GPU로 요청을 보내지 않는다.
  • 센서나 액추에이터에 쓰기 명령을 보내지 않는다.
  • 옥동 현장 고장 종류를 완성된 정확도로 분류하지 않는다.
  • 모든 장비를 자동 발견하고 등록하지 않는다.

8. 딱 세 문장만 기억하기

  1. EdgeX는 센서의 이름과 값을 책임진다.
  2. Kubernetes·KubeEdge·HAMi는 프로그램과 GPU 실행을 책임진다.
  3. 대시보드는 센서·서비스·노드의 서로 다른 근거를 섞지 않고 함께 보여준다.
