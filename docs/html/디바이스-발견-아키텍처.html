디바이스 발견 및 등록 아키텍처

기준일: 2026-07-24 상태: Current 구현 기준 요구사항 원문: 프로토콜-독립형-디바이스-발견-등록-요구사항.md

목적

물리 장비를 자동으로 발견하는 것과 그 장비를 신뢰해 EdgeX에 등록하는 것을 분리한다. 노드 로컬 Agent는 후보 증거만 수집하고, 중앙 Adapter Controller가 Git Catalog, 운영자 승인, 외부 인증, Runtime 상태, EdgeX Metadata readback과 첫 Core Data Event를 차례로 확인한다.

USB Serial / I2C / 허용된 endpoint
  -> edge-device-discovery DaemonSet
  -> 공통 DiscoveryObservation
  -> HMAC report
  -> edgex-adapter-controller
     -> SQLite candidate / Plan / Saga / audit
     -> Device Binding Catalog exact match
     -> 운영자 승인
     -> AuthProvider 승인
     -> 기존 Device Service 재사용 또는 검증 template 배포
     -> Core Metadata Profile / Device 등록과 readback
     -> Core Data 첫 Event 확인
  -> EVENT_CONFIRMED

Core Metadata는 승인된 Device의 inventory이고 발견 후보 저장소가 아니다. KubeEdge는 노드와 workload 배치를 담당하며 KubeEdge Device CRD를 별도 물리 inventory plane으로 사용하지 않는다.

구성 요소와 코드

구성 요소 책임 구현 경로

중앙과 엣지의 책임 경계

엣지 노드

  • /dev/serial/by-id/*와 Plan에 허용된 VID/PID를 reconciliation한다.
  • Active Manifest probe가 켜진 경우에만 Serial endpoint를 열고 WHOAMI를 보낸다.
  • I2C는 Plan의 bus/address/identity rule만 읽는다. 버스 파일만으로 센서 후보를 만들지 않는다.
  • 발견 Agent는 telemetry를 지속 수집하거나 EdgeX Device를 생성하지 않는다.
  • 승인 후 실제 통신과 Event 생성은 EdgeX Device Service가 담당한다.

현재 custom Serial/I2C Device Service에는 재사용할 native discovery 구현이 없어 얇은 노드 플러그인을 사용한다. 이후 공식 Device Service가 같은 identity와 allowlist 정책을 만족하는 native discovery를 제공하면 Agent가 중복 probe하지 않고 해당 결과를 공통 Observation으로 변환하는 쪽을 우선한다.

중앙 Edge AI 서버

  • Adapter Controller의 SQLite가 승인 전 candidate와 등록 Saga의 권위다.
  • Device Binding Catalog는 Git에서 검토된 image digest, parser, Profile과 hardware

identity만 허용한다.

  • EdgeX Core Metadata에는 승인된 Profile과 Device만 등록한다.
  • Core Data 첫 Event가 없으면 등록 완료로 판정하지 않는다.
  • PostgreSQL은 Core Data Event/Reading의 중앙 저장소이고 candidate Registry가 아니다.

기존 PostgreSQL은 EdgeX Core Data 소유 스키마이며 Adapter Controller용 repository layer가 없다. Core Data DB에 별도 제어 테이블을 섞지 않기 위해 candidate/Plan/Saga/audit는 Controller 단일 replica의 SQLite PVC를 사용한다. 이는 HA 구성이 아니며 다중 replica로 확장할 때는 transaction과 leader election을 제공하는 공유 저장소로 이관해야 한다.

stable identity와 중복 제거

신규 candidate ID는 다음 식의 전체 SHA-256이다.

candidate- + SHA-256(nodeId + "|" + protocol + "|" + stableHardwareId)

Serial은 USB serial number를 우선하고, 없으면 /dev/serial/by-id의 stable 이름을 사용한다. WHOAMI 응답의 논리 deviceId는 ManifestDeviceID 속성으로 보존하되 USB hardware identity를 덮어쓰지 않는다. 따라서 /dev/ttyACM0 번호나 PTY 번호가 바뀌어도 같은 candidate ID를 유지한다.

기존 ConfigMap의 24자리 candidate ID는 최초 SQLite 기동 때 한 번 import해 하위 호환한다. 이후 신규 후보는 전체 64자리 hash를 사용한다.

상태 머신

정상 등록 경로:

DETECTED
  -> IDENTIFIED
  -> PENDING_APPROVAL
  -> APPROVED
  -> SERVICE_READY
  -> METADATA_REGISTERED
  -> EVENT_CONFIRMED

예외 경로:

DETECTED / IDENTIFIED / PENDING_APPROVAL -> BLOCKED
PENDING_APPROVAL / BLOCKED / FAILED     -> REJECTED
APPROVED / SERVICE_READY /
METADATA_REGISTERED                     -> FAILED
node clean reconciliation에서 사라짐    -> STALE
STALE에서 같은 stable identity 재관측    -> 이전 상태 복구
FAILED에서 명시적 retry                  -> APPROVED

임의 상태 점프는 discovery_state.py에서 거부한다. 각 전이는 actor, reason, timestamp, errorCode와 함께 candidate history와 audit event에 저장된다. 인증 denied, unavailable, error로 차단된 후보는 새 관측만으로 승인 대기로 되돌아가지 않는다. unavailable과 error만 운영자가 새 요청으로 인증 재확인을 할 수 있다.

Registration Saga

승인 요청은 다음 gate를 통과한다.

  1. candidate가 PENDING_APPROVAL이고 현재 present인지 확인한다.
  2. Device Catalog exact match를 다시 계산한다.
  3. 외부 AuthProvider를 호출한다. 장애 시 fail-closed한다.
  4. target KubeEdge node Ready를 확인한다.
  5. Runtime plan을 계산해 기존 Argo Runtime을 재사용하거나 Controller template을 배포한다.
  6. 실행 중인 Deployment image가 Catalog의 immutable digest와 정확히 같은지 확인한다.
  7. Device Service가 SERVICE_READY인지 확인한다.
  8. Profile을 조회하고 없을 때만 등록한 뒤 readback한다.
  9. Device를 조회하고 없을 때만 등록한 뒤 readback한다.
  10. Metadata 등록 시각 이후 origin을 가진 해당 deviceName의 첫 Event를 Core Data에서

확인한다. 과거 Event 존재만으로 완료하지 않는다.

  1. Event가 확인된 경우에만 EVENT_CONFIRMED로 완료한다.

각 단계는 SQLite에 저장되어 Controller 재시작 후 이어진다. 요청 ID와 payload hash도 영속 저장하므로 같은 승인 요청을 반복해도 Runtime, Profile 또는 Device를 중복 생성하지 않는다.

timeout이나 실패 시 이번 Saga가 만든 Device, 사용되지 않는 Profile, Controller 소유 Runtime만 역순으로 정리한다. 기존 Argo Runtime, 기존 Profile, 기존 Device는 삭제하지 않는다. Device ownership은 tags.controllerCandidateId, Profile은 edge-adapter-controller label, Kubernetes 리소스는 controller label과 owner reference로 구분한다.

프로토콜별 Discovery 정책

프로토콜 구현 상태 현재 동작
Serial/USB 구현 완료, PTY 검증 stable by-id inventory, VID/PID allowlist, 선택적 WHOAMI/Manifest
I2C plugin·mock 검증, 실장비 미검증 허용 bus/address와 identity register만 active probe
MQTT schema parser 구현, subscriber 미구현 edge/discovery/{nodeId}/{deviceId} topic과 payload 검증만 제공
Modbus RTU/TCP contract만 구현 Plan에서 켜면 not implemented 오류를 보고하고 후보를 만들지 않음
OPC-UA contract만 구현 등록 endpoint scanner 미구현, 가짜 성공 없음
ONVIF contract만 구현 camera discovery 미구현, 가짜 성공 없음
RTSP discovery 대상 아님 영상 Workflow가 직접 소비하고 상태·분석 결과만 EdgeX에 저장

MQTT parser는 retained 여부, topic의 node/device 일치, JSON schema, 중복 가능한 stable device ID를 검증한다. 실제 broker subscription과 telemetry adapter는 아직 구현되지 않았다.

Arduino 멀티센서 모델

신규 등록 경로는 Arduino 보드 하나를 EdgeX Device 하나로 등록한다.

Arduino physical board
  -> Device: arduino-<stable-hardware-id>
  -> Profile: arduino-multisensor-v1
  -> temperature_raw
  -> light_raw
  -> magnetic_raw
  -> acceleration_x_raw
  -> acceleration_y_raw
  -> acceleration_z_raw

device-serial-jetson은 ResourceName: "*" binding을 지원한다. 기존 서비스 데모의 센서별 6개 Device와 신규 aggregate Device가 전환 기간에 같은 reader를 공유할 수 있도록 legacy 단일-resource route와 aggregate route에 동시에 fan-out한다. 동일 resource의 legacy Device 두 개 또는 aggregate Device 두 개는 계속 거부한다.

장애와 복구

장애 처리
Agent가 Plan을 읽지 못함 fail-closed, 후보 0개와 scan error 보고; 기존 후보를 즉시 삭제하지 않음
clean scan에서 장비가 사라짐 즉시 STALE, 같은 identity 재연결 시 이전 상태 복구
Manifest timeout/invalid JSON evidence에 오류 코드 기록, Catalog exact match 차단
Catalog ambiguous match BLOCKED, 운영자 자동 선택 금지
외부 인증 timeout/unavailable BLOCKED, EdgeX 등록 없음
Runtime image digest 불일치 FAILED, 새로 만든 Controller Runtime만 rollback하고 Metadata 등록 없음
Profile/Device 등록 실패 FAILED, 이번 Saga 생성 리소스만 rollback
첫 Event timeout FAILED, 생성 리소스 rollback 후 명시적 retry 가능
Controller 재시작 PVC의 SQLite에서 candidate/Plan/Saga를 복원해 현재 단계부터 재개

보안 경계

  • API를 통해 image, hostPath, container command를 입력받지 않는다.
  • Catalog의 immutable digest와 allowlist에 없는 image는 실행하지 않는다.
  • Discovery Plan의 네트워크 기능은 기본 꺼짐이며 현재 scanner도 구현되지 않았다.
  • HMAC key와 외부 인증 token은 Secret/env로만 주입하고 응답·로그·candidate metadata에

기록하지 않는다.

  • base Controller는 ADAPTER_AUTH_MODE=external이고 HTTPS endpoint/token을 Secret에서

읽으며 설정이 없으면 fail-closed한다. 현재 root testbed만 overlays/development/adapter-management에서 development-mock을 명시한다.

  • Controller는 edgex-edge namespace 리소스와 cluster node get/list만 접근한다.
  • EdgeMesh 또는 고정 ClusterIP/PodIP를 변경하지 않는다. Service DNS를 사용한다.
  • 상태 전이 audit와 등록 reconciliation 로그는 candidate/node/protocol, 전후 상태,

registration step, duration과 error code를 구조화된 JSON으로 남긴다.
