가상화 노드 오류 복구시간 구현·시험 기준

상태: 구간 계측 immutable image 배포 완료. 최초 qualification canary는 2,215.225 ms로 실패했고, 후속 원인 진단 6건도 1건 통과·5건 실패해 400 ms gate는 미달성

기준일: 2026-09-01

지표 경계

성능지표 8의 측정 구간은 다음과 같다.

정상 전송 이력이 있는 Serial stream의 오류 감지
  → 포트 재연결
  → 첫 유효 frame decode·validation
  → EdgeX SDK 비동기 전송 채널 enqueue 완료
구분 값 의미
과제 최종 목표 250 ms 기존 과제 문서의 공식 목표. 별도 변경 승인 전 유지
2차년도 개발 gate 400 ms 현재 구현·반복시험의 중간 합격 기준
비교값 300 ms 기존 비교 기준인 미국 VMware 값

400 ms를 통과해도 250 ms 최종 목표를 달성한 것으로 기록하지 않는다. 반대로 이 지표는 장애 발생부터 Kubernetes/KubeEdge node 판정, 다른 노드의 Pod 생성과 완전 기동까지 걸리는 전체 failover 시간이 아니다.

초기 기동 시 포트를 열지 못한 경우도 복구시간 표본에서 제외한다. 정상 sample을 한 번 이상 전송한 stream에서 오류가 검출된 뒤 다시 유효 sample을 전송한 경우만 한 건으로 센다.

현재 구현

device-serial-jetson의 shared Serial Reader는 다음 fast-retry profile을 사용한다.

대기:       25 ms → 50 ms → 100 ms → 200 ms → 1 s → 2 s → 4 s → 8 s → 16 s → 30 s
누적 시도: 25 ms → 75 ms → 175 ms → 375 ms → 1.375 s → ...
  • 포트 open, read timeout 설정 또는 established stream의 read 오류에서 DOWN을 알린다.
  • 이미 복구 중이면 후속 오류가 검출 시각을 다시 시작하지 않는다.
  • 포트가 다시 열렸다는 사실만으로 완료 처리하지 않는다.
  • malformed line은 버리고, 첫 유효 frame이 실제 SDK async channel까지 전달된 뒤 완료한다.
  • 복구 중 성공한 port open과 read timeout 설정 완료를 portReadyAt, 최초 수신 byte를

firstByteAt으로 기록해 병목 구간을 분리한다.

  • time.Time의 monotonic 차이를 사용해 process 내부의 감지→재개 시간을 계산한다.
  • 400 ms를 넘으면 target miss를 누적하고 warning log를 남긴다.

배포 설정은 다음 두 값으로 고정한다.

Driver:
  SerialRecoveryTarget: "400ms"
  SerialReconnectDelays: "25ms,50ms,100ms,200ms,1s,2s,4s,8s,16s,30s"

재시도 간격은 1~16개의 양수 duration, 비감소 순서, 각 30초 이하만 허용한다. 잘못된 값이면 Device Service 초기화를 실패시켜 조용히 기본값으로 우회하지 않는다.

관측값

EdgeX custom metric은 다음과 같다.

metric 의미
SerialRecoveryDetected established stream에서 복구를 시작한 누적 횟수
SerialRecoveryCompleted 첫 유효 frame 전송까지 완료한 누적 횟수
SerialRecoveryLastDurationMs 마지막 완료 표본의 감지→전송 재개 시간
SerialRecoveryLastAttempts 마지막 완료 표본의 재개방 시도 횟수
SerialRecoveryTargetMisses 400 ms를 초과한 완료 표본의 누적 횟수

같은 값은 Device Service의 read-only API에서도 확인할 수 있다.

kubectl get --raw \
  '/api/v1/namespaces/edgex-edge/services/http:device-serial-jetson:59910/proxy/api/v3/serial-recovery/stats'

응답의 inProgress는 detected > completed, last.withinTarget은 마지막 표본이 현재 target 이하인지를 뜻한다. 값은 process-local 관측 상태이므로 Pod 재시작 전에 시험결과서로 보존한다. 장기 이력이나 durable outbox가 아니다.

last.detectionToPortReadyMs, last.portReadyToFirstByteMs, last.firstByteToResumeMs는 각각 오류 감지→포트 준비, 포트 준비→첫 byte, 첫 byte→첫 유효 frame 전송 재개의 구간 시간이다. portReadyAt은 char device 생성시각이 아니라 Device Service가 포트를 열고 read timeout 설정까지 마친 process 내부 시각이다.

400 ms 내부 qualification

현재 내부 합격 절차는 다음과 같다. TTA 또는 과제 공식 시험절차가 확정되면 그 절차를 우선한다.

  1. 새 immutable image를 배포하고 정상 sample과 Core Data origin 증가를 먼저 확인한다.
  2. API의 초기 counter를 기록한다.
  3. 정상 전송 중 승인된 Serial 단절·복구를 30회 반복한다. Pod 삭제나 node 전원 차단은 이

지표가 아닌 별도 전체 failover 시험으로 분리한다.

  1. 각 회차의 process log, recovery API와 첫 후속 Core Data Event를 같은 시험 record에 묶는다.
  2. completed 증가, targetMisses=0, 30회 max ≤ 400 ms일 때 400 ms 내부 gate를 통과한다.
  3. p50·p95·max, 미완료 건수와 Core Data readback 누락을 함께 보고한다.

2026-09-01 최초 qualification canary 결과

Jetson etri-dev0001-jetorn의 실제 Arduino stream이 정상 전송 중일 때 USB 전체 전원이나 node·Pod를 끄지 않고 cdc_acm 인터페이스 1-2.1:1.0만 50 ms unbind→rebind했다. 장애 주입은 운영 기능이 아닌 일회성 관리자 qualification Pod에서 수행했고 시험 뒤 삭제했다.

항목 관측값

Device Service image edgex-device-serial@sha256:db8e21c3bf8ad6ad984ac0b3178a009308aa3dae55111a5f17e957781232e141

복구시간 API와 process log는 같은 2,215.225 ms를 기록했고, 첫 후속 temperature Event는 서비스의 전송 재개 시각 뒤 약 4.216 ms에 Core Data에서 조회됐다. 장애 전 마지막 temperature Event와 첫 후속 Event의 origin 간격은 약 2,563.902 ms였다. 따라서 자동 재연결과 중앙 readback은 성공했지만 데이터 공백을 피하지 못했고 400 ms gate는 통과하지 못했다.

30회 합격 조건은 max ≤ 400 ms와 targetMisses=0이므로 첫 canary의 초과만으로 이번 qualification은 실패가 확정됐다. 불필요한 추가 물리 장애를 피하기 위해 나머지 29회는 실행하지 않았으며 p50·p95 분포도 산출하지 않는다. 이 결과를 30회 시험 완료나 공식 250 ms 목표 달성으로 해석하지 않는다.

장치 파일은 오류 감지 뒤 약 301.410 ms에 다시 생성됐지만 첫 유효 frame까지 추가로 약 1,913.815 ms가 걸렸다. 이 결과를 근거로 port-ready와 first-byte 구간 계측을 추가했다.

2026-09-01 구간 계측 진단

구간 계측이 포함된 revision c3f62556da848e90ed55712004476555d9093604, image edgex-device-serial@sha256:65b31240e1f798c2c8a1bbd9257573520cd95148e03488566b806db99e011146 를 같은 Jetson에 배포했다. 최초 qualification을 다시 시작한 것이 아니라, 원인을 분리하기 위해 같은 50 ms cdc_acm unbind→rebind를 1회 canary와 5회 진단 series로 제한 실행했다. 시험 전 process-local counter는 모두 0이었고 시험 후 detected=6, completed=6, targetMisses=5였다.

표본 전체 복구 감지→port ready port ready→첫 byte 첫 byte→유효 frame 판정
진단 canary 1회 158.629 ms 131.299 ms 26.955 ms 0.375 ms 통과
후속 5회 범위 1,817.702~1,843.971 ms 61.218~84.425 ms 1,750.519~1,754.341 ms 4.170~8.704 ms 5회 모두 실패

후속 5회에서 포트는 모두 85 ms 안에 준비됐고 재개방도 각 1회 만에 성공했다. 반면 포트가 준비된 뒤 첫 byte까지 약 1.75초의 정지 구간이 반복됐으며, byte가 도착한 뒤 유효 frame을 전송하기까지는 최대 8.704 ms였다. 따라서 현재 반복 실패의 지배 병목은 heartbeat, retry backoff, JSON decode가 아니라 Serial 재개방 뒤 장치가 첫 byte를 보내기 전 구간이다.

최근 temperature Event 100개에서 계산한 정상 주기는 99개 간격 기준 min 1,013.869 ms, p50 1,016.088 ms, p95 1,020.303 ms, max 1,021.805 ms였다. 포트 open 때 DTR/RTS를 올리는 현재 라이브러리 기본 동작과 Arduino auto-reset/firmware startup은 강한 원인 후보지만, 이번 계측만으로 DTR reset과 firmware 내부 초기화 시간을 분리해 확정하지는 않는다. 실제 firmware source와 pin/resource 계약을 확인한 뒤 DTR auto-reset 억제 또는 startup·첫 frame 지연 축소를 한 항목씩 시험해야 한다.

자동 단위시험은 초기 open 실패가 표본에 포함되지 않는지, port ready·first byte·first valid frame의 단조 시각과 구간 계산, malformed line이 복구 완료로 오인되지 않는지를 검증한다. 이 합성시험은 실장비 400 ms 통과 증거가 아니다.

현장 한계와 후속 조치

  • 400 ms heartbeat를 설정하는 것만으로 이 목표를 달성할 수 없다. heartbeat 400 ms는 오류

검출에만 최대 400 ms를 쓰며 포트 복구와 다음 sample 시간을 포함하지 않는다.

  • 현재 live Arduino의 특정 resource Event는 약 1.016초 간격이다. 정상 수집 주기는 복구시간

자체가 아니지만, 재연결 뒤 첫 frame과 정상 cadence가 400 ms보다 길면 retry 간격만 줄여서는 gate를 통과할 수 없다.

  • firmware flash, DTR/reset 동작 변경과 물리 auto-reset 회로 변경은 현재 배포 변경보다 위험

범위가 크다. 현장 sketch·pin mapping을 확보하고 별도 승인한 뒤 한 변수씩 적용한다.

  • USB 장치 재열거가 400 ms보다 오래 걸리거나 stable char device가 복구되지 않으면 software

retry만으로는 통과할 수 없다.

  • node 전원·망 장애까지 400 ms 안에 복구하려면 hot-standby Device Service, 이중화된 물리

수집 경로와 전송 경로가 필요하다. 현재 단일 Arduino→단일 Jetson 연결에는 이 보장이 없다.

  • 통신 단절 중 telemetry 보존과 중앙 재전송은 장애 저장·재전송 시스템 설계의

별도 범위다. 현재 Local Data cache를 durable outbox로 해석하지 않는다.
