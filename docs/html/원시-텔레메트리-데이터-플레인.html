EdgeX Device Service 기반 원시 텔레메트리 데이터 플레인

문서 상태

이 문서는 2026-07-22 Agent 퇴역 이후의 현재 기준을 설명한다. 이전 Protocol Adapter → edge-telemetry-agent → SQLite outbox → HTTPS gateway 경로는 운영 배포에서 제거되었으며 설계·검증 이력으로만 남는다.

현재 중앙 EdgeX Core는 유지된다. Jetson의 device-serial-jetson은 실제 Arduino endpoint를 공유 reader 하나로 수집하고, Raspberry Pi의 device-sensehat-raspi는 Sense HAT v1 /dev/i2c-1을 직접 수집한다. 각 resource route가 6개 가상 Device identity를 만들어 총 12개 Device가 중앙 저장, read-only 조회와 dashboard freshness의 결합 key가 된다.

목표 권위 경로

물리 센서 / PLC / 장비
  -> 프로토콜별 EdgeX Device Service
       ├─ endpoint 연결과 재연결
       ├─ resource 표준화
       ├─ bounded recent cache / Local Data API
       ├─ operating state
       └─ 지원 command
  -> EdgeX Event / Reading
  -> 중앙 internal MessageBus
  -> 중앙 Core Data
  -> PostgreSQL
  -> Application Service / AI consumer / state-aggregator / dashboard
데이터 권위
Device Service/Profile/Device, admin/operating state Core Metadata
Event/Reading와 최신성 Core Data
EdgeX 영구 저장 PostgreSQL
같은 node의 최근 구간 조회 Device Service memory recent cache / Local Data API
edge node와 workload 상태 Kubernetes/KubeEdge
카메라 frame RTSP 원본 endpoint와 이를 직접 구독하는 Workflow Pod

KubeEdge Device/DeviceModel/DeviceStatus와 MapperFramework는 이 경로의 병행 plane이나 fallback이 아니다.

배포 상태

계층 현재 상태
중앙 edgex-system Core Keeper/Metadata/Data/Command, internal MessageBus, PostgreSQL, ingest gateway 유지
edge edgex-edge device-serial-jetson, device-sensehat-raspi, 각 ConfigMap, default-deny와 최소 허용 NetworkPolicy
custom edge Agent Deployment/PVC/contract manifest 퇴역
Agent Metadata bootstrap 퇴역
정식 Device Service Jetson Arduino Serial과 Raspberry Pi Sense HAT I2C 정상 경로 live 검증

중앙 ingest gateway는 기존 중앙 구성 보존을 위해 남아 있지만 현재 Serial/I2C Device Service는 이를 사용하지 않는다. 현재 Event는 EdgeX SDK async 경로로 중앙 MessageBus와 Core Data에 전달된다.

Device Service 계약

각 Device Service는 한 종류의 프로토콜 구현을 소유하고 여러 Device 인스턴스를 관리할 수 있다.

현재 첫 계약의 한 Device 예시는 다음과 같다. 나머지 5개 Device도 같은 물리 connection과 서로 다른 ResourceName을 사용한다.

serviceName: device-serial-jetson
profileName: etri-arduino-temperature
deviceName: virtual-temperature-001
protocols:
  serial:
    Port: /dev/arduino-001
    BaudRate: "115200"
    DeviceID: arduino-001
    ResourceName: temperature_raw
tags:
  physicalDeviceId: arduino-001
  nodeName: etri-dev0001-jetorn

Sense HAT I2C 계약은 exact /dev/i2c-1, DeviceID=sensehat-001과 ResourceGroup을 사용한다. temperature, humidity, pressure, compass, orientation, gyroscope의 6개 Device가 총 11개 Float64 resource를 제공한다. RTIMULib Python reader는 Device Service 컨테이너 내부 protocol module이며 MQTT publisher나 별도 Agent가 아니다.

host의 정확한 by-id CharDevice만 Pod에 마운트하며 hostNetwork는 사용하지 않는다. 현재 PoC는 이 장치 접근을 위해 단일 Pod에 privileged: true와 root 실행을 허용한다. 후속 운영 강화에서는 Device Plugin 또는 더 좁은 장치 권한으로 대체한다.

Device Profile에는 최소한 다음을 명시한다.

  • resource 이름과 의미
  • valueType과 단위
  • read/write 권한
  • 허용 범위와 변환 규칙
  • device command가 있으면 resource operation과 안전 제약

MessageBus와 MQTT

중앙 edgex-messagebus는 EdgeX Core 내부 통신용이며 Service type은 ClusterIP다. 현재 구현은 이 중앙 서비스의 MQTT 구현을 EdgeX SDK 내부 Event 전송에 사용하지만, Arduino 입력 프로토콜은 Serial이며 edge-local broker는 없다.

입력 프로토콜 기본 수집 방식 local MQTT 필요 여부
Serial/I2C Device Service가 장치 파일/버스를 직접 사용 불필요
Modbus Device Service가 TCP/RTU endpoint 직접 사용 불필요
OPC-UA Device Service가 endpoint/session/subscription 관리 불필요
MQTT-only 장비 MQTT Device Service 또는 검증된 adapter 필요할 수 있음
RTSP Workflow Pod가 stream 직접 구독 불필요

EdgeX 내부 MessageBus 구현과 물리 장비 protocol은 서로 다른 선택이다.

조회와 실시간 처리

저장된 최근·과거 데이터는 deviceName을 기준으로 Core Data에서 조회한다.

GET /api/v3/event/device/name/{deviceName}?limit=20

고주기 실시간 추론은 REST polling으로 구현하지 않는다. 필요하면 Device Service/Application Service의 stream consumer 또는 장비의 native stream을 별도 데이터 계약으로 사용한다. 카메라는 RTSP를 직접 사용한다.

같은 Jetson 또는 Raspberry Pi의 Workflow Pod가 짧은 입력 window를 사용할 때는 해당 Device Service의 Local Data API를 호출한다.

GET /api/v3/localdata/device/name/{deviceName}/resource/name/{resourceName}/latest
GET /api/v3/localdata/device/name/{deviceName}/resource/name/{resourceName}?from={origin_ns}&to={origin_ns}&limit={1..10000}
GET /api/v3/localdata/stats
  • cache key: (deviceName, resourceName)
  • 구현: 두 Device Service가 공유하는 제네릭 Go ring cache; 정상적인 증가 origin append는 O(1), 순서가 뒤섞인 입력만 안정 정렬 slow path 사용
  • 보존: 최근 10분, 시계열별 최대 10,000 sample
  • 전체 할당 상한: Device Service별 sample ring slot 67,108,864 bytes(64MiB); 활성 series 수에 따라 균등 quota를 다시 계산
  • 상한 계산 범위: sample slot 배열만 포함하며 Go map, 문자열, HTTP 응답과 runtime overhead는 포함하지 않음; 컨테이너 memory limit가 프로세스 전체 hard cap 역할
  • recent 기본 limit: 1,000; 가장 최근 sample을 선택한 뒤 origin 오름차순 반환
  • latest sample 없음: 404
  • 알려진 source의 recent 결과 없음: 200과 빈 samples
  • stats: series, samples, slotBytes, allocatedBytes, retention과 age/series-limit/global-rebalance eviction 누계 반환
  • EdgeX custom metrics: LocalDataCacheSamples, LocalDataCacheSeries, LocalDataCacheAllocatedBytes, LocalDataCacheEvictions
  • Pod 재시작: cache 초기화
  • 중앙 Core Data fallback: 없음

Workflow Pod에는 edge-ai.io/local-data-client=true label을 붙이고 대상 Runtime과 같은 edge node에 배치한다. 호출 주소는 고정 IP가 아니라 Serial의 device-serial-jetson.edgex-edge.svc.cluster.local:59910 또는 I2C의 device-sensehat-raspi.edgex-edge.svc.cluster.local:59911이다. 이 접근 계약은 현재 Workflow Builder가 Kubernetes 실행을 수행한다는 뜻이 아니다.

recent cache와 장애 outbox는 다음처럼 목적을 분리한다.

  • recent cache: 같은 node의 Workflow Pod가 최신 구간을 읽는 용도
  • outbox: 중앙 전송 실패 중 아직 영구 저장되지 않은 Event 보존 용도

현재 두 Device Service에는 recent cache와 Local Data API가 있지만 SQLite outbox와 offline replay는 없다. 따라서 중앙 연결 장애 중 이미 파싱한 sample을 로컬 Workflow가 cache 보존 범위 안에서 읽을 수는 있어도, 미전송 Event의 재전송이나 데이터 무손실을 보장하지 않는다. 과거 Agent의 SQLite 구현을 정식 Device Service 기능으로 간주하거나 재배포하지 않는다.

보안과 네트워크

  • 고정 ClusterIP/PodIP/node IP를 설정에 넣지 않는다.
  • Kubernetes/EdgeMesh DNS와 정상 서비스 디스커버리를 사용한다.
  • edgex-edge는 기본 deny를 유지하고 Device Service별 필요한 egress/ingress만 추가한다.
  • Local Data API ingress manifest는 edge-ai.io/local-data-client=true label을 의도된 client로 선언한다.
  • 장치 파일 권한은 필요한 Device Service Pod에만 최소 범위로 부여한다.
  • 현재값 read-only command만 허용한다. write/actuator command는 allow-list, timeout, validation, audit와 fail-closed 동작을 검증하기 전까지 Profile에 두지 않는다.
  • EdgeMesh는 Local Data API 추가에서도 변경하지 않는다.

현재 테스트베드의 Flannel CNI는 NetworkPolicy를 집행하지 않으며 label 없는 Pod의 Local Data API 접근도 실측됐다. 따라서 위 ingress manifest와 label은 현재 보안 경계가 아니다. API는 unauthenticated read-only이고, 실제 호출 주체 제한은 정책 지원 CNI 또는 mTLS/애플리케이션 인증을 추가한 뒤 주장한다.

완료 증거

프로토콜별 수직 슬라이스는 다음을 모두 만족해야 현재 지원으로 승격한다.

  1. 실제 endpoint 연결과 재연결 증거
  2. Device Service/Profile/Device 등록과 상태 조회
  3. typed Event/Reading의 Core Data readback
  4. 잘못된 payload, 장치 분리, 중앙 단절 시 실패 동작
  5. dashboard inventory/state/freshness 일치
  6. 필요한 경우 read-only와 write/actuator를 구분한 command의 허용·거부·timeout 증거

Serial 공유 reader와 6-way route, malformed line 복구, 재연결 backoff를 단위 테스트했다. I2C reader는 실제 Sense HAT의 온도·습도·압력·나침반·자세·자이로 값을 읽고 reader process 재시작/backoff를 단위 테스트했다. 12-Device cutover는 Metadata/Event/Command/dashboard와 두 Local Data API live readback을 같은 revision에서 통과했다. 실제 케이블/보드 분리, 중앙 단절 중 데이터 보존과 NetworkPolicy 차단은 완료 증거가 아니다.
