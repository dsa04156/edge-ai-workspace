400 ms 복구 체험하기

상태: 2026-09-02 평소 1초 전송과 재연결 시 제한된 즉시 요청 방식을 운영 배포했다. 50 ms Serial 단절·복원 30회는 30/30회 400 ms 이내였고 max는 309.848 ms였다. 이 페이지의 패널은 원리를 이해하기 위한 교육용 시뮬레이터이며 운영 제어·실시간 계측· 공식 시험 도구가 아니다.

먼저, 다섯 살에게 설명하면

센서는 평소에는 1초마다 쪽지를 보낸다. 선이 잠깐 끊겼다가 다시 이어지면 컴퓨터가 “지금 값 알려 줘”라고 묻는다. 첫 질문이 USB 준비 중 사라지면 25 ms 간격으로 최대 세 번만 더 묻고, 답이 오면 바로 멈춘다. 계속 0.1초마다 쪽지를 보내지 않아도 복구 순간의 기다림을 줄이는 방식이다.

현재 1초 + 제한 요청 방식은 “고장을 알아챈 뒤 다음 정상 쪽지가 EdgeX에 전달될 때까지”의 내부 400 ms gate를 30번 모두 통과했다. p50 196.619 ms, p95 304.244 ms, 가장 느린 한 번은 309.848 ms였다. 2026-09-01의 100 ms 연속 전송 시험도 비교 이력으로 보존한다.

손으로 바꿔 보기

위 패널에서 “지금 값” 요청을 끄면 1초 주기의 다음 쪽지를 기다리게 된다. 반대로 요청을 켜면 재연결 순간에만 즉시 답을 받아 평소 트래픽을 늘리지 않는다. 아두이노 자동 리셋이 다시 생기면 요청을 처리할 수도 없으므로 여전히 늦어진다. 하트비트는 고장을 알아차리는 데 도움이 되지만 공식 400 ms 측정은 알아챈 뒤부터 시작하므로 하트비트만 400 ms로 맞춘다고 해결되지 않는다.

실제로 바꾼 것

  • Linux Serial은 HUPCL을 해제해 포트를 다시 열 때 Uno auto-reset이 일어나지 않게 했다.
  • Arduino의 pin과 JSON 계약은 유지하면서 평소 sample 주기를 1,000 ms로 둔다.
  • 재연결 직후 Device Service가 고정 READ_NOW를 보내고, 첫 byte가 없을 때만 25 ms 간격으로

최대 세 번 재요청하면 Arduino가 현재 sample을 즉시 응답하도록 했다.

  • 이 요청은 내부 복구 handshake이며 공개 EdgeX write command나 actuator 제어가 아니다.
  • bootloader, fuse, EEPROM과 물리 auto-reset 회로는 바꾸지 않았다.

다른 장비에 같은 원칙을 적용하는 방법은 디바이스 연결 복구 표준을 따른다.

꼭 구분할 것

이 문서의 400 ms는 오류 감지 → 첫 유효 sample의 EdgeX SDK async enqueue 구간이다. Kubernetes node 장애 판정, 다른 node에 Pod를 새로 띄우는 시간이나 과제의 최종 250 ms 목표를 통과했다는 뜻은 아니다. 정확한 시험 경계와 원본 evidence는 가상화 노드 오류 복구시간을 따른다.
