프로토콜 독립형 디바이스 발견·등록 현재 구현 상태

기준일: 2026-08-04 판정 기준: 실제 코드, 테스트, edgex/k8s render “구현”과 “실장비 운영 검증”을 구분한다.

요약

Serial은 PTY 후보 발견부터 승인, 검증 Runtime 재사용, EdgeX Profile/Device idempotent 등록, Core Data 첫 Event 확인까지 자동화된 코드와 fake backend 통합 테스트가 있다. 2026-07-24 실제 Jetson Arduino stable 후보를 운영자가 승인했고 기존 Device Service Runtime을 재사용해 aggregate Device arduino-75035303230351e0d171-57fc03a907의 EVENT_CONFIRMED와 Core Data Event까지 live 확인했다.

I2C는 allowlist bus/address와 여러 read-only identity register를 하나의 물리 보드 identity로 묶는 composite probe까지 구현했다. 2026-07-28 etri-dev0003-raspi5의 Sense HAT v1에서 0x1c=0x3d, 0x5c=0xbd, 0x5f=0xbc, 0x6a=0x68을 확인해 후보를 승인했고, 기존 device-sensehat-raspi, Profile etri-sensehat-gyroscope, Device imu-sensehat-gyroscope-01을 재사용한 뒤 신규 Core Data Event로 EVENT_CONFIRMED까지 live 검증했다. 이어서 등록 연결을 decommission하고 다음 30초 탐색 주기에 같은 candidate ID가 PENDING_APPROVAL로 자동 복귀하는지 확인했으며, 재승인 뒤 다시 EVENT_CONFIRMED가 됐다. 기존 EdgeX Device 13개와 Sense HAT Device 6개는 삭제되거나 중복 생성되지 않았다.

고정 서비스 데모는 2026-08-03 Jetson에 복합 센서 image sensor-anomaly-demo@sha256:1a86c54a1a0692a682258b4a9c8a6f7a24e13f98000610afa56c04f95d52af68을 rollout했다. 가속도 X/Y/Z와 온도 네 Local Data source를 정렬해 실제 origin/frame 증가, 누락 0, 약 11~12ms 정렬 차이를 확인했고 중앙 BFF와 외부 dashboard도 같은 진동·온도 개별 점수와 0.7/0.3 종합 점수를 표시했다. 이는 고정 read-only consumer이며 범용 workflow 실행이나 실제 고장 분류 완료를 뜻하지 않는다.

후속 소스에는 펌프·모터와 생산품질용 versioned Pydantic/JSON Schema, contract-valid JSONL simulator와 Local Data v3 Replay server를 추가했다. 현재 통계 모델은 PumpModelAdapter 뒤의 명시적 online-baseline backend로 분리했다. 파생 결과와 이상 발생·정상 복귀 transition은 application-owned SQLite에 idempotent하게 저장하며 manifest는 Jetson 1Gi RWO PVC를 선언한다. 중앙 BFF 결과·알림 API와 dashboard 최근 알림 표시를 포함한 자동 테스트는 통과했다. commit 849f10f3eefa9c719bb18c5a8de16687f115e98e와 GitHub Actions run 30796771024를 통해 새 ARM64 image를 배포했고 Argo CD Application은 같은 revision에서 Synced/Healthy다. Jetson의 sensor-anomaly-demo@sha256:9f0736a1c6b6eda612a3dd4257ff526d483c2f45cb5d94c52a66f61214232796와 1Gi RWO sensor-anomaly-demo-state PVC를 확인했다. Pod 재시작 전 SQLite 결과 172건과 origin 1785746192559462095를 기록한 뒤 새 Pod에서 같은 origin을 재조회했고 결과가 217건으로 계속 증가해 restart persistence를 live 검증했다. 생산품질 계약은 현장 field mapping 전 schema 단계다.

실제 장치 움직임 anomaly와 USB 손분리·복구를 동일한 운영 API 계약으로 반복 판정하는 read-only 도구 tools/verify_sensor_service_demo.py를 추가했다. 정상 기준선 이후 필요한 상태 전이가 모두 발생해야만 종료 코드 0과 JSON passed=true를 반환한다. 현재 live 관측에서는 정상 입력 증가만 확인했고 anomaly와 실제 분리는 발생하지 않았으므로 현장 gate는 계속 미완료다.

같은 날 일반 Discovery DaemonSet의 Serial-only passive inventory를 dev0003까지 확장했다. Raspberry Pi에 연결된 CH340 계열 USB Serial 장비를 /dev/serial/by-id/usb-1a86_USB_Serial-if00-port0(VID/PID 1a86:7523)에서 후보 candidate-fb7190f...로 반복 관측했다. 이후 exact Raspberry Pi hardware binding, mpu6050-imu-v1 Profile/parser, Controller 배포 template과 MPU6050 6축 Float64 JSON-line 처리를 구현했다. exact 후보 승인부터 Runtime, Profile/Device, first Event까지의 fake backend 통합 테스트는 통과했다. live 승인도 실행했지만 당시 Serial telemetry가 없어 첫 Event timeout으로 FAILED가 됐고 Controller가 자신이 만든 동적 Runtime을 rollback했다. 이후 보드를 ESP32-D0WD-V3 revision 3.1로 식별하고 운영 firmware를 compile·flash해 115200 baud 상태 JSON까지 확인했다. firmware는 MPU6050을 1초마다 재탐색하지만 ESP32의 일반 I2C pin pair와 Raspberry Pi bus 1에서 0x68, 0x69 모두 ACK가 없었다. 2026-07-30 MPU6050 실물을 분리했고 후보는 STALE/ignored 감사 이력으로 정리했으며 동적 Runtime은 없는 상태다. Profile/parser/template과 자동 테스트는 재연결 실험을 위한 dormant 지원 코드로 남기되 현재 연결 장비나 완료된 telemetry 경로로 표시하지 않는다. Serial Agent와 I2C Agent가 같은 node를 보고해도 서로의 후보를 STALE 처리하지 않도록 report에 scannedProtocols scope를 추가했고, Sense HAT 후보는 계속 EVENT_CONFIRMED를 유지했다. MQTT 자기등록 subscriber는 아직 없다. 대신 공식 device-mqtt:4.0.2 immutable image, 노드별 network binding, allowlist broker/topic/QoS Runtime 설정, Device command topic/resource와 bundled edgeai-mqtt-temperature-v1 Profile을 묶은 개발용 웹 연결 package를 구현했다. 대시보드의 검증하고 연결 한 번으로 validation, Runtime 재사용/배포, Profile/Device readback과 first Event 확인을 진행한다. anonymous broker/publisher는 root 운영 render 밖의 선택적 development fixture다. 이 경로는 자동 테스트와 manifest render뿐 아니라 2026-07-30 실제 클러스터 웹 canary도 통과했다. Jetson에 adapter-mqtt-978887c832를 배포하고 mqtt-temperature-sim-001 Device와 edgeai-mqtt-temperature-v1 Profile을 등록한 뒤 Core Data의 temperature Float64 Event와 ACTIVE operation을 확인했다. 첫 Event 뒤 operatingState=UP Metadata readback까지 성공해야 연결 완료로 판정한다. Modbus는 네트워크 discovery 없이 운영자가 선언한 고정 개발 endpoint에 한해 공식 EdgeX device-modbus:4.0.2 Runtime, read-only Profile, Modbus TCP simulator와 승인 Saga를 연결했다. 2026-07-28 Unit 2 가상 온도 센서를 승인해 Controller-owned Runtime, Core Metadata Device, 1초 AutoEvent, Core Data 저장과 대시보드 available 상태까지 live 확인했다. 개발용 Modbus endpoint simulator Deployment는 root 운영 render 밖에 남아 있지만 해당 Controller Device Service Runtime은 검증 뒤 퇴역했으며 현재 live EdgeX inventory에는 포함되지 않는다. 이는 개발 simulator 수직 경로의 과거 증거이며 실제 PLC 지원 완료가 아니다. OPC-UA와 ONVIF는 확장 contract와 명시적 not implemented 상태만 있다.

대시보드는 전역 간편 보기/전체 보기 토글을 제거했다. 기본 화면에는 핵심 상태만 두고 기술 KPI, 서비스 연결 근거, 후보 세부정보와 개별 EdgeX Device는 클릭해 펼친다. 등록 목록은 기본 운영 경로의 Core Metadata 13개 Device identity를 유지하면서 arduino-001과 sensehat-001 물리 source별 카드로 묶는다. 375px, 768px, 1024px 실제 브라우저 viewport와 MQTT 연결 마법사의 1440px viewport에서 문서 가로 overflow와 잘린 텍스트가 없음을 확인했다.

디바이스 화면은 엣지 AI 서버, 물리 디바이스, 가상 디바이스, 센서 디바이스를 전환 탭 없이 한 화면의 네 연속 목록으로 렌더링한다. 공통 노드 필터가 네 목록에 함께 적용되고, 각 행은 이름·상태·최신 관측 또는 Event·상세보기만 유지한다. 1440/768/375px 실제 브라우저에서 네 목록 동시 표시와 문서 가로 overflow 부재를 확인했다.

서비스 설계 캔버스는 실제 /state/dashboard Device/node와 /state/device-profiles DeviceResource 계약을 읽어 센서 입력·전처리·추론·결과 단계를 구성한다. 상단의 현재 실행 서비스는 /state/services를 읽어 고정 sensor-anomaly-demo 1개의 상태, 입력 상태, 모델 상태, 배치 노드와 입력 수를 표시한다. 서비스 응답 장애도 목록에서 숨기지 않고 점검 필요로 표시한다. 왼쪽은 EdgeX 입력 2종, 전처리 6종, 추론 3종, 점수 결합 1종과 결과 1종을 검색하는 13종 설계 블록이며 EdgeX 입력 가능 Device 수와 실행되지 않는 설계용 계약을 구분한다. 단계 이동·추가·삭제, 포트 연결, 속성 편집, DAG·타입·노드 배치 validation, dry-run 실행 계획과 versioned localStorage 초안을 구현했다. 센서 설정 패널은 선택 DeviceResource의 최근 5분 Core Data Reading을 최대 300 Event 범위에서 읽어 최신값, 최근 5개 값, 표본 수와 수집 간격 중앙값을 표시한다. no_events, stale, 같은 처리 단계로 들어가는 local_recent 입력의 물리 node 불일치와 resource 최신 시각 차이 2초 초과는 실행 계획을 BLOCKED로 표시한다. 입력·설계 검증은 graph의 모든 센서 입력을 Device별 한 번의 최근 5분 이력 조회로 점검하고, 입력별 최신값·경과 시간·관측/필요 표본·수집 간격과 판정 이유를 표시한다. 첫 window 전처리의 필요 표본 부족, 이력 조회 실패, 300개 점검 상한 초과와 실제 Reading 최신 시각 차이 2초 초과도 실행 계획을 차단한다. 중앙 캔버스는 pan·zoom, fit view, 미니맵, 24px grid·정렬선 snap, Shift 축 고정·Alt 자유 이동과 방향키 미세 이동을 제공한다. 단계 좌표는 기준 작업 영역과 현재 viewport에 고정하지 않고, 드래그 가장자리 자동 이동과 graph·현재 보이는 구간을 합친 동적 미니맵을 제공한다. 멀리 배치한 단계도 전체 보기로 모두 복구한다. 드롭 뒤 viewport를 다시 이동하지 않으며 390/768/1024/1440px에서 문서·캔버스 가로 overflow가 없음을 브라우저로 확인했다. 이는 브라우저 설계 프로토타입이며 서버 저장, Kubernetes/EdgeX mutation과 실제 Workflow 실행은 미구현이다.

/state/services에는 고정 workload의 sensor-anomaly-demo-v1 설계 계약을 추가했다. 서비스 행의 설계 편집은 가속도 X/Y/Z와 온도 입력, 두 feature branch, 두 점수, 0.7/0.3 결합과 결과를 10개 단계의 브라우저 편집 초안으로 복사한다. 입력 Device/DeviceResource, 알고리즘, 20/10 sample window, warm-up, threshold와 model version을 inspector에서 수정할 수 있고 단계·연결·이름도 편집한다. 기존 일반 초안과 서비스별 초안은 분리 보존하며 편집 중·편집 계속, 기존 초안으로 돌아가기, 원본으로 초기화 상태를 제공한다. 주기적 inventory/service/Profile 갱신은 편집 중 graph를 덮어쓰지 않는다. 지원하지 않는 계약은 임의 graph로 표시하지 않는다.

2026-08-04에는 현재 실행 서비스를 단순 상태 열에서 서비스 흐름 요약으로 바꿨다. sensor-anomaly-demo-v1 계약을 기준으로 가속도 3축 + 온도 → 진동·온도 특징 → 이상 점수 결합 → 대시보드 결과를 4단계로 표시하고, 실행 노드, 물리 소스 → Device Service 수집 경로와 입력·모델 상태를 함께 보여 준다. 680px 이하에서는 같은 순서를 세로로 전환하며 375/768/1440px에서 문서 가로 overflow가 없음을 로컬 브라우저로 확인했다.

보안·운영 주의

  • Controller base는 ADAPTER_AUTH_MODE=external로 fail-closed한다. 현재 root testbed만

overlays/development/adapter-management에서 development-mock을 적용하며 운영 profile이 아니다.

  • Catalog API는 read-only이며 임의 image 실행 API가 없다.
  • 일반 edge-device-discovery는 dev0001/dev0002/dev0003에서 비권한 상태로 read-only

/dev, /sys Serial inventory만 수행한다. dev0003의 edge-device-discovery-i2c는 container device cgroup 때문에 privileged 예외가 필요하지만 non-root UID/GID, exact /dev/i2c-1 CharDevice 하나와 보조 group 988만 사용한다. 이 값은 현재 testbed host 권한에 종속되며 다른 노드에 그대로 복사하지 않는다.

  • Controller SQLite는 1Gi RWO PVC를 사용해 단일 replica 기준이다. 다중 replica HA를

활성화하지 않는다.

  • SQLite PVC를 삭제하면 candidate, 전이 이력, 승인, Saga와 audit를 복구할 수 없다.
  • Service는 ClusterIP 객체와 DNS를 사용하지만 고정 ClusterIP 우회는 없다.
  • EdgeMesh manifest는 수정하지 않았다.
  • 현재 PoC의 /management/* mutation은 browser 관리자 token이나 Authorization

header를 요구하지 않는다. 기능 플래그, allowlist 검증, Idempotency-Key와 내부 HMAC은 유지하지만 이는 운영자 인증이 아니다. 접근이 제한된 개발 테스트베드 경계이며 운영 노출 전 별도 사용자 인증·인가가 필요하다.
