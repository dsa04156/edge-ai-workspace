문서 안내

이 디렉터리는 EdgeX 기반 물리 디바이스 데이터 플레인과 KubeEdge 기반 엣지 노드·워크로드 관리를 결합한 엣지 AI 플랫폼 PoC 문서의 단일 진입점이다. 처음 읽을 때는 전체 파일을 훑지 말고 wiki/지식-지도.md에서 목적에 맞는 최신 기준 문서를 찾는다.

한 문장 목표

Jetson·Raspberry Pi의 Protocol Adapter와 durable telemetry agent에서 HTTPS ingest gateway·Core Data·PostgreSQL까지 원시 텔레메트리 권위 경로를 단일화하고, 디바이스·서비스·노드·워크로드 상태를 대시보드에서 운영 관점으로 통합 가시화한다.

짧은 표현:

센서 데이터와 엣지 AI 서비스를 실제로 연결하고 운영 상태를 한눈에 보여주는 시스템

현재 문서와 구현은 아래 세 가지를 우선한다.

  1. 교체 가능한 Protocol Adapter 입력을 SQLite edge agent와 HTTPS gateway·Core Data·PostgreSQL 경로로 검증한다.
  2. EdgeX 디바이스·프로필·서비스와 AI 서비스의 연결 구조를 대시보드에서 보이게 한다.
  3. 실공장 기반 PoC의 현장 적용성과 생산성 향상 효과를 설명하되, 중앙 전환과 추가 프로토콜 지원은 실행 증거가 있을 때만 완료로 판정한다.

과거 워크플로·오프로딩·에이전트 보조 계획 자료는 현재 판단 기준이 아니다. 필요할 때만 docs/archive/와 docs/superpowers/에서 설계 이력으로 확인한다.

목표 데이터 흐름

물리 센서 / PLC / 장비
  -> Protocol Adapter -> edge-telemetry-agent -> SQLite outbox
  -> HTTPS/mTLS ingest gateway
  -> EdgeX Core Data -> PostgreSQL
  -> Application Service / AI consumer / state-aggregator / dashboard

KubeEdge
  -> 엣지 노드 / 워크로드 배치와 상태 관리

현재 root render는 Raspberry Pi와 Jetson의 노드별 direct-mode edge agent, 독립 SQLite outbox와 Core Data persisted ACK를 포함한다. sensehat-001은 canonical Event까지 연결한 교체 가능한 live 검증 fixture다. Jetson agent는 SQLite와 인증 heartbeat 기반만 제공하며 Arduino Serial adapter, Device Profile/Device와 Event 연결은 아직 다음 migration wave다. MQTT-mode agent, device-mqtt, edge-local broker는 현재 EdgeX 배포에 포함하지 않는다. MQTT-only·Serial·Modbus·OPC-UA·추가 I2C adapter 및 RTSP workflow는 독립 검증 전까지 지원 완료로 표시하지 않는다.

dashboard에서 확인할 핵심 질문:

  1. EdgeX Core Metadata에 어떤 device/profile/Device Service가 등록되어 있는가?
  2. admin_state, operating_state, connection_state, device_service_available은 무엇인가?
  3. latest_event_timestamp, latest_readings, telemetry_freshness가 최신인가?
  4. 어떤 AI service, storage, service demo group에 연결되어 있는가?
  5. 문제가 있다면 Protocol Adapter, agent outbox, HTTPS gateway, Core Data, consumer 중 어디부터 봐야 하는가?
  6. 관련 edge node/workload는 KubeEdge에서 정상인가?
  7. 이 상태가 현장 생산성 향상 효과로 어떻게 설명되는가?

최신성 판단 원칙

  • 프로젝트-범위.md와 저장소-구조.md가 현재/레거시 경계의 최우선 기준이다.
  • 같은 주제의 문서가 충돌하면 수정 시각이 아니라 근거와 실행 증거가 명시된 기준 문서를 따른다.
  • wiki/는 탐색용 요약이며 정책의 원본이 아니다.
  • html/은 scripts/build-docs-html.py로 다시 만드는 보기용 산출물이다.
  • superpowers/는 설계·구현 계획 이력이며 현재 완료 상태의 근거가 아니다.

보관 문서 사용 원칙

docs/archive/는 과거 실험, 이전 통합 문서, 논문/연구 초안, legacy orchestration 자료를 보관하는 위치다. 새 작업 판단은 최신 기준 문서를 우선한다.

보관 문서를 읽을 때 주의할 점:

  • 현재 구현 방향으로 간주하지 않는다.
  • 발표자료에 그대로 옮기지 않는다.
  • workflow/offloading/agent-assisted planning을 다음 확정 단계처럼 표현하지 않는다.
  • 현재 데모 설명은 서비스 데모, 디바이스-서비스 연결 구조, 통합 운영 가시화, 현장 적용성, 생산성 향상 효과 중심으로 작성한다.
