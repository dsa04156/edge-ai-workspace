가상디바이스 Runtime과 중앙 EdgeX 설계

상태: 후속 설계 이력 / 재정렬 필요. 2026-07-21 운영 결정으로 기존 custom edge Agent는 퇴역했다. 현재 우선순위는 별도 Agent/Runtime 배포가 아니라 공식 EdgeX Device SDK 기반 Device Service 1종, Device Profile/Device, Core Data Event/Reading과 대시보드 수직 슬라이스다. 이 문서의 Runtime 모듈 구상은 custom Device Service 내부 확장으로 재검토하기 전까지 현재 배포 계약이나 완료 근거가 아니다.

상태와 목적

상태: 사용자 확정 설계. 구현 완료 여부는 코드, 테스트, 배포 manifest와 live 검증으로 판단한다.

이 문서는 수집 서비스를 단순 전송 Agent가 아니라 가상디바이스 구현체로 정의한다. 물리 프로토콜, 데이터의 실제 생성 위치, 저장 위치와 시뮬레이션 여부를 Workflow에서 감추고, 모든 입력을 deviceName, resourceName, accessMode로 동일하게 바인딩하는 것이 목적이다.

이 설계는 기존 2026-07-21-젯슨-아두이노-시리얼-에이전트-설계.md의 단방향 Agent 중심 구조를 대체한다. 중앙 EdgeX 배치와 PostgreSQL 권위는 유지하고 엣지 수집 계층의 역할과 Workflow 입력 계약을 바로잡는다.

핵심 정의

가상디바이스는 실제 하드웨어 존재 여부와 관계없이 Workflow가 동일한 방식으로 데이터를 읽고 명령할 수 있는 추상화된 디바이스다.

구분 정의 예시
물리 디바이스 실제 센서, PLC, 카메라, Jetson과 프로토콜 endpoint Arduino, Modbus PLC, RTSP camera
수집 서비스 물리 또는 논리 source를 읽고 표준화하는 container runtime Serial Runtime, replay Runtime, simulator Runtime
가상디바이스 인스턴스 수집 서비스가 제공하며 EdgeX Device로 등록되는 Workflow-facing source virtual-arduino-001, virtual-history-replay-001
Device Profile resource 형과 지원 command를 고정하는 계약 etri-virtual-arduino
Workflow source 가상디바이스의 resource와 접근 방식을 참조하는 stage 입력 virtual-arduino-001/temperature_raw

EdgeX 공식 device-virtual의 무작위 테스트 장치를 사용한다는 의미가 아니다. 이 프로젝트의 가상디바이스는 실제 물리 endpoint, 과거 데이터 또는 simulator를 같은 Device/Profile/I/O 계약으로 노출하는 프로젝트 도메인 객체다.

EdgeX Core, 내부 MessageBus와 PostgreSQL은 etri-ser0002-cgnmsb에 한 세트만 배치한다. Jetson과 Raspberry Pi에는 전체 EdgeX Core를 복제하지 않는다. 각 edge node에는 물리 또는 논리 source를 소유하는 가상디바이스 Runtime만 배치한다.

중앙 edgex-messagebus는 중앙 EdgeX 내부 통신용이다. 물리 프로토콜, edge-local Workflow handoff 또는 SQLite 장애 버퍼 역할을 하지 않는다. 고정 ClusterIP, PodIP, node IP를 구성에 넣지 않고 기존 Service DNS와 EdgeMesh 설정을 변경하지 않는다.

EdgeX 객체 매핑

Kubernetes Pod와 EdgeX Device를 같은 객체로 취급하지 않는다. 문서와 API에서는 다음 관계를 명시한다.

실행/관리 객체 EdgeX 표현 역할
수집 Runtime Deployment/Pod Device Service adapter, cache, API, Event와 command 실행 주체
가상디바이스 인스턴스 Device Workflow가 선택하는 deviceName
가상디바이스 형 Device Profile resource와 command schema
수집 sample Event / Reading deviceName에 귀속되는 typed data

한 Runtime Pod가 여러 가상디바이스 인스턴스를 관리할 수 있다. 반대로 Pod 이름을 그대로 Workflow source ID로 사용하지 않는다. Pod가 재시작돼도 deviceName과 Profile 계약은 유지돼야 한다.

첫 Arduino vertical slice는 다음 identity를 사용한다.

항목 값
Device Service virtual-device-runtime-jetson
Device Profile etri-virtual-arduino
Device virtual-arduino-001
physical reference arduino-001
node etri-dev0001-jetorn

Core Metadata Device의 properties 또는 tags에는 최소한 다음 정보를 기록한다.

kind: virtual-device
physicalRef: arduino-001
nodeName: etri-dev0001-jetorn
runtimeId: virtual-device-runtime-jetson
accessModes:
  - current
  - recent
  - history

live는 local stream 구현과 저지연 검증을 통과한 Runtime에만 추가한다. Metadata에 광고한 access mode는 실제 API와 반드시 일치해야 한다.

Serial 경로, baud rate와 encoding은 protocols.serial에 기록한다. 인증서, password, RTSP credential 같은 secret 값은 Metadata에 평문으로 넣지 않고 Secret reference만 기록한다.

가상디바이스 Runtime 책임

Runtime은 다음 책임을 한 경계에서 제공한다.

  1. 하나 이상의 protocol adapter를 통해 source를 독점 연결한다.
  2. 원본 sample을 Device Profile의 typed resource로 표준화한다.
  3. resource별 latest snapshot과 bounded recent cache를 갱신한다.
  4. Event를 SQLite Outbox에 먼저 commit한다.
  5. HTTPS/mTLS로 중앙 ingest gateway에 재전송한다.
  6. local Workflow에 current/recent/live API를 제공한다.
  7. 지원 command를 adapter로 실행하고 결과를 반환한다.
  8. 연결 상태, 데이터 freshness, invalid sample과 outbox 상태를 진단한다.

첫 구현은 Runtime 하나를 단일 Pod로 배치하되 내부 코드는 다음 모듈 경계를 유지한다.

VirtualDeviceRuntime
├─ ProtocolAdapter
│  └─ Serial / Modbus / OPC-UA / I2C
├─ DataNormalizer
│  └─ deviceName / resourceName / valueType / value / origin
├─ LatestSnapshotRepository
├─ RecentCacheRepository
├─ OutboxRepository
├─ LocalDataAPI
├─ UplinkClient
└─ CommandAdapter

LatestSnapshotRepository, RecentCacheRepository와 OutboxRepository는 서로 다른 수명주기와 삭제 정책을 가진다. 하나의 SQLite 파일을 재사용할 수는 있지만 table, transaction과 repository API를 분리한다. Local Data API는 repository 구현을 외부에 노출하지 않는다.

Runtime은 여러 프로토콜 구현을 하나의 거대한 조건문으로 합치지 않는다. 공통 Runtime 계약 아래 Serial, Modbus, OPC-UA, replay와 simulator adapter를 독립적으로 구현하고 검증한다. 한 protocol 성공을 다른 protocol 지원 완료 근거로 사용하지 않는다.

현재 edge-telemetry-agent의 canonical Event validation, SQLite outbox, gateway client, heartbeat와 command bridge는 Runtime 내부 공통 모듈로 재사용할 수 있다. 최종 배포에서 별도 Agent Pod와 Runtime Pod가 같은 데이터를 연쇄 전달하는 구조는 만들지 않는다.

표준 데이터 접근 계약

Workflow는 물리 프로토콜이나 저장소 URL 대신 다음 source binding만 사용한다.

collection:
  deviceName: virtual-arduino-001
  resourceNames:
    - acceleration_x_raw
    - acceleration_y_raw
    - acceleration_z_raw
  accessMode: history
  window: 10m
  limit: 300

지원 접근 방식은 다음처럼 구분한다.

accessMode 의미 실제 데이터 경로
current 현재 resource snapshot을 한 번 읽음 Runtime latest cache 또는 EdgeX Core Command GET
recent edge에 남아 있는 제한된 최근 window 조회 Runtime recent API
history 중앙에 저장된 Event/Reading 조회 EdgeX Core Data GET
live 배치 이후 들어오는 sample을 연속 소비 Runtime local stream

저장된 Event의 기준 조회는 다음 EdgeX Core Data 경로다.

GET /api/v3/event/device/name/{deviceName}?offset=0&limit=20

시간 window가 필요한 Workflow는 중앙 read model의 기존 facade를 사용할 수 있다.

GET /state/devices/{deviceName}/telemetry?window=-10m&limit=300

현재값을 EdgeX command plane으로 읽을 때는 Profile의 read command를 사용한다.

GET /api/v3/device/name/{deviceName}/{commandName}

Arduino처럼 비동기 Serial sample을 계속 보내는 장비는 GET 시마다 장치를 다시 읽지 않는다. Runtime이 마지막으로 검증한 snapshot과 origin, quality/freshness를 반환한다. 아직 유효 sample이 없거나 freshness 정책을 넘겼으면 가짜 기본값을 반환하지 않고 명시적 unavailable/stale 오류를 반환한다.

local recent/live API는 모든 Runtime이 동일한 wire envelope를 사용한다. Workflow는 SQLite 파일을 직접 mount하거나 Runtime 내부 table을 조회하지 않는다. live consumer가 없을 때는 구독자 수가 0일 뿐 중앙 수집과 outbox flush는 계속된다.

Event와 resource 계약

가상디바이스가 중앙에 올리는 Event의 deviceName은 물리 ID가 아니라 Workflow가 바인딩하는 가상디바이스 이름이다. 물리 ID는 Event tag 또는 Metadata의 physicalRef로 추적한다.

Arduino 첫 slice는 다음 resource를 사용한다.

source Reading valueType
temperature temperature_raw Int32
light light_raw Int32
magnetic magnetic_raw Int32
acceleration acceleration_x_raw, acceleration_y_raw, acceleration_z_raw Int32

Firmware가 단위나 source timestamp를 제공하지 않으므로 값을 임의로 Celsius, lux, tesla 또는 g로 변환하지 않는다. Event origin은 Runtime이 완전한 Serial line을 받은 시각의 Unix nanoseconds다.

Profile은 resource 단건 읽기와 acceleration, telemetry 같은 read-only grouping command를 제공한다. Arduino 첫 slice에는 쓰기 가능한 actuator command를 추가하지 않는다.

저장 경계

edge에 전체 이력을 복제하지 않는다.

저장소 데이터 수명
latest snapshot resource별 마지막 정상값 새 값으로 교체
recent cache Workflow의 짧은 window 조회용 시간과 byte 상한으로 삭제
SQLite Outbox 아직 중앙 persisted ACK를 받지 못한 Event ACK 뒤 삭제
Workflow workspace 실행에 stage-in한 과거 dataset Workflow 종료 뒤 삭제
PostgreSQL/Core Data 가상디바이스 전체 운영 이력 중앙 retention 정책
선택적 InfluxDB 고주기 시계열 분석용 export 사본 Application Service와 별도 retention 정책

latest/recent와 outbox는 역할과 삭제 조건이 다르므로 같은 SQLite 파일을 사용하더라도 별도 table과 repository 경계를 가진다. Outbox ACK 삭제가 recent 조회 결과를 바꾸거나, recent retention이 미전송 Event를 삭제해서는 안 된다.

Workflow가 local cache보다 오래된 window를 요구하면 중앙 Core Data에서 필요한 범위만 조회하거나 실행 전에 stage-in한다. 중앙 연결이 없고 필요한 범위도 local에 없으면 validation에서 실행 불가로 판단한다. 전체 중앙 이력을 edge에 미리 복제하지 않는다.

현재 live 배포의 영구 저장 권위는 Core Data/PostgreSQL이다. InfluxDB가 필요한 경우 Application Service가 typed Event를 별도 시계열 backend로 export하고, Workflow는 Historical Data API를 통해 backend 차이를 감춘다. InfluxDB를 현재 배포 또는 첫 Arduino slice의 필수 구성으로 간주하지 않는다.

Workflow 동작

Workflow Orchestrator는 Core Metadata의 Device/Profile과 가상디바이스 properties를 조회해 source 후보를 만든다. Workflow의 수집 stage는 protocol driver가 아니라 가상디바이스 client다.

Virtual Device selection
  -> access mode와 window validation
  -> Runtime/central endpoint resolution
  -> KubeEdge placement
  -> collection
  -> preprocess
  -> inference
  -> postprocess/control

첫 실행 slice에서는 저장된 history GET과 current GET을 우선 검증한다. live는 실제 저지연 Workflow 요구가 있는 Profile에만 명시적으로 활성화한다. 모든 디바이스에 항상 stream endpoint나 local broker를 강제하지 않는다.

같은 Profile/resource 계약을 만족하면 Workflow는 다음 source를 교체할 수 있다.

  • virtual-temp-001: 실제 Modbus 센서 Runtime
  • virtual-temp-replay-001: 과거 DB replay Runtime
  • virtual-temp-sim-001: simulator Runtime

replay와 simulator는 별도 deviceName을 사용해 실제 장비 Event 이력을 오염시키지 않는다. Profile compatibility가 맞지 않으면 이름이 비슷해도 bind를 거부한다.

카메라 경계

virtual-camera-001도 Metadata, 상태, capability와 command 관점에서는 가상디바이스다. 그러나 raw frame을 Core Data Event, SQLite Outbox 또는 일반 JSON stream에 넣지 않는다.

  • camera metadata/status/command: 가상디바이스와 EdgeX 계약
  • frame input: Workflow Pod가 RTSP/GStreamer로 직접 구독
  • inference result: 별도 typed Event로 중앙 EdgeX에 저장
  • 영상 보관: 명시된 clip/object-storage 정책이 있을 때만 수행

명령 경계

Core Command는 가상디바이스의 표준 command entry point다. 중앙 command gateway는 대상 Runtime으로 요청을 전달하고 Runtime은 Profile과 allowlist에 선언된 command만 adapter로 실행한다.

명령은 telemetry Outbox에 넣지 않는다. 만료된 명령을 연결 복구 후 뒤늦게 실행하지 않으며, timeout·TTL·idempotency와 terminal result를 명시한다. actuator write는 read-only Arduino slice와 분리된 승인 및 live 검증 뒤에만 활성화한다.

상태와 권위

정보 권위
가상디바이스 inventory/schema EdgeX Core Metadata Device/Profile
현재 연결과 latest freshness Runtime 진단 + Core Metadata operating state
저장된 telemetry EdgeX Core Data/PostgreSQL
중앙 command API EdgeX Core Command
미전송 복구 queue edge SQLite Outbox
workflow binding/execution Workflow Orchestrator
derived twin snapshot DeviceTwin

DeviceTwin은 raw Event를 다시 전부 저장하지 않는다. physicalRef, capability, 현재 binding, derived status와 last error를 참조하는 관리 snapshot이다.

장애 동작

  • 중앙 연결 장애: current/recent/live local access는 계속되고 Event는 Outbox에 보존된다.
  • Runtime 재시작: latest/recent의 보존 정책에 따라 복구하며 outbox는 PVC에서 재전송한다.
  • 물리 endpoint 장애: stale snapshot을 정상 current로 반환하지 않고 상태와 오류를 노출한다.
  • Workflow 장애: Runtime과 중앙 전송을 중단하지 않는다.
  • history backend 장애: local current/recent로 자동 의미 변경하지 않고 history unavailable을 반환한다.
  • outbox full: 기존 미전송 Event를 조용히 삭제하지 않고 rejection과 오류를 기록한다.

현재 구조에서의 전환

현재 live cluster는 중앙 EdgeX Core와 edge별 custom telemetry Agent로 구성되어 있다. 목표 구조로 전환할 때 다음 순서를 지킨다.

  1. 중앙 EdgeX Core, MessageBus, PostgreSQL, gateway와 EdgeMesh를 변경하지 않는다.
  2. 기존 Agent 공통 기능을 가상디바이스 Runtime library로 분리한다.
  3. Arduino Serial adapter와 latest/recent/read command를 Runtime에 추가한다.
  4. virtual-arduino-001 Profile/Device/Device Service를 멱등 등록한다.
  5. Core Data stored GET과 current GET을 검증한다.
  6. Workflow builder source를 physical fixture가 아닌 가상디바이스 Device/resource에 bind한다.
  7. 같은 live 증거가 확보된 뒤 Jetson Agent Deployment를 Runtime Deployment로 교체한다.

Sense HAT과 과거 MQTT workload는 별도 migration wave다. Arduino 성공을 이유로 함께 변경하거나 지원 완료로 표시하지 않는다.

기존 중앙 EdgeX 변경 경계

기존 edgex-system Core 서비스를 삭제하거나 재설치하지 않는다. Core Data, Core Metadata, Core Command, Core Keeper, 중앙 MessageBus와 PostgreSQL의 image, Deployment, Service와 저장 schema는 현재 구성을 유지한다. EdgeMesh 설정도 변경하지 않는다.

필요한 변경은 중앙 EdgeX 자체 재구축이 아니라 다음 통합 데이터와 설정이다.

대상 필요한 변경
Core Metadata Runtime Device Service, Device Profile, virtual Device 멱등 등록
Ingest Gateway 새 service/profile/device allowlist와 canonical Event admission
Core Data 변경 없음. 기존 Event 저장과 device-name GET 재사용
PostgreSQL 변경 없음. 기존 Core Data persistence 재사용
Core Command Core binary 변경 없음. Profile command와 Runtime endpoint routing 추가
Application/read model Workflow용 virtual-device/resource/accessMode 조회 모델 추가
Dashboard physical reference와 virtual device/service binding 표시

중앙 command를 사용하지 않는 첫 stored-data GET까지는 Core Command routing 변경도 필수 조건이 아니다. current read command와 actuator command를 활성화할 때 기존 HTTPS command bridge의 target mapping과 allowlist를 Runtime 단위로 확장한다.

edge 쪽에서는 edgex-edge-agent-jetson을 즉시 삭제하지 않는다. 새 Runtime이 실제 Serial Event, GET, outbox replay와 dashboard source binding을 통과한 뒤 같은 기능을 인수하고 Deployment를 교체한다. edgex-edge-agent-sensehat은 별도 migration 전까지 유지한다.

자동 검증 기준

  • Metadata contract에 Device Service/Profile/Device가 정확히 한 번 존재한다.
  • deviceName=virtual-arduino-001인 typed Event가 Core Data에 저장된다.
  • Core Data device-name GET이 limit와 시간 범위를 지킨다.
  • current GET이 마지막 정상 sample의 값, origin과 freshness를 반환한다.
  • sample 없는 상태, stale 상태와 endpoint 오류가 명시적으로 실패한다.
  • recent cache와 outbox retention/ACK가 서로 간섭하지 않는다.
  • Workflow binding은 Profile/resource/accessMode/window를 검증한다.
  • replay/simulator deviceName이 실제 source 이력을 오염시키지 않는다.
  • local consumer가 없어도 중앙 전송과 outbox flush가 정상이다.
  • Workflow 종료가 Runtime의 물리 연결을 닫지 않는다.
  • 카메라 frame이 Core Data/SQLite JSON Event에 들어가지 않는다.
  • Kustomize render에 고정 ClusterIP, PodIP, node IP가 없다.
  • 기존 Sense HAT과 중앙 EdgeX 테스트가 회귀하지 않는다.

Live 검증 기준

  • Runtime Pod가 etri-dev0001-jetorn에서 실제 Arduino Serial을 독점 연결한다.
  • Core Metadata에서 virtual-arduino-001과 Profile/Service binding을 조회할 수 있다.
  • Core Data device-name GET에서 네 source와 여섯 raw Reading을 실제 값으로 읽는다.
  • current GET이 같은 시점의 latest snapshot을 반환한다.
  • 중앙 단절 동안 local current/recent가 동작하고 outbox가 증가한다.
  • 복구 뒤 Event가 FIFO로 전송되고 persisted ACK 뒤 outbox가 감소한다.
  • Workflow preview가 virtual device/resource/window를 source로 표시한다.
  • 중앙 Core/PostgreSQL, 기존 Sense HAT과 EdgeMesh Pod가 변경 없이 정상이다.

완료 경계

첫 완료는 virtual-arduino-001의 등록, 실제 Serial Event, Core Data GET, current GET, outbox replay와 Workflow source binding까지의 수직 slice다. Runtime Pod가 Ready거나 Metadata에 Device만 보이는 것으로 완료를 주장하지 않는다.

다음 항목은 별도 검증 전까지 완료 범위가 아니다.

  • Modbus/OPC-UA adapter
  • actuator write command
  • RTSP inference Workflow 실행
  • replay/simulator Runtime
  • 범용 live stream broker
  • 동적 Workflow 실행과 stage-level offloading
  • 전체 가상디바이스 registry/twin 자동화
