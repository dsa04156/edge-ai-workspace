대시보드 어댑터 런타임 관리 설계

목적

운영자가 물리 장비를 연결할 때 Kubernetes manifest나 kubectl을 직접 다루지 않고 대시보드 한곳에서 다음 흐름을 완료하게 한다.

  1. 프로토콜과 대상 edge node를 선택한다.
  2. 이미 실행 중인 EdgeX Device Service Adapter를 재사용할 수 있는지 확인한다.
  3. 재사용할 수 없으면 플랫폼이 승인한 템플릿으로 Adapter runtime을 배포한다.
  4. EdgeX Device Profile과 Device를 등록한다.
  5. Metadata readback과 첫 Event/Reading 수신을 확인한다.
  6. 이후 runtime 상태 확인, 재시작과 안전한 퇴역을 대시보드에서 수행한다.

물리 디바이스 inventory, state, telemetry와 command의 권위는 계속 EdgeX다. KubeEdge와 Kubernetes는 node와 workload만 관리하며, Adapter runtime 자체를 물리 디바이스 inventory로 간주하지 않는다.

현재 설계에서 바꾸는 범위

기존 대시보드 디바이스 온보딩 MVP는 설치된 Device Service에 Device를 등록하는 데까지만 허용하고 Kubernetes workload mutation은 금지했다. 이번 기능은 다음 제한 안에서 그 경계를 확장한다.

  • 대시보드가 승인된 Adapter runtime 인스턴스를 조회·재사용·배포·재시작·퇴역할 수 있다.
  • 대시보드는 Kubernetes API에 직접 접근하지 않고 state-aggregator 관리 API만 호출한다.
  • 별도 Adapter Controller만 namespaced Kubernetes workload mutation 권한을 가진다.
  • Controller는 Git에 등록된 allowlist 템플릿만 렌더링한다.
  • EdgeX Profile/Device 생성과 첫 Event 검증은 기존 온보딩 계층이 담당한다.
  • Workflow Builder의 browser-local dry-run 경계와 legacy orchestration 경로는 바꾸지 않는다.
  • EdgeMesh, KubeEdge Device/DeviceModel CRD와 중앙 EdgeX Core 배포는 건드리지 않는다.

docs/프로젝트-범위.md, docs/저장소-구조.md, docs/단계별-추진계획.md, docs/대시보드-정보-구조.md와 운영 절차에 이 범위 변경을 함께 반영한다.

선택한 구조

Operator
  -> Dashboard / Device Management
      -> state-aggregator Management API
          -> Adapter Catalog
          -> Connection Onboarding Orchestrator
              -> Adapter Controller internal API
                  -> AdapterRuntime CR
                      -> Deployment / Service / Secret
              -> EdgeX Core Metadata
                  -> Device Service / Profile / Device
              -> EdgeX Core Data
                  -> first Event / Reading verification

Adapter Controller를 별도 서비스로 두는 이유는 state-aggregator의 기존 read-only Kubernetes 권한을 유지하고, workload mutation 권한과 장애 범위를 격리하기 위해서다. 브라우저가 Kubernetes credential을 가지거나 임의 manifest를 전달하는 API는 만들지 않는다.

선택하지 않은 방식

  • state-aggregator에 Deployment·Service·Secret 쓰기 권한을 직접 부여하지 않는다.
  • 대시보드가 Git commit이나 Argo CD sync를 즉석에서 생성하는 방식은 사용하지 않는다.

승인 템플릿 배포보다 느리고 운영 흐름에 Git credential까지 결합되기 때문이다.

  • 센서 하나마다 Adapter Pod를 만들지 않는다. 같은 node와 protocol을 공유하고 Device

Service가 다중 endpoint를 지원하면 기존 runtime을 재사용한다.

  • 여러 protocol library를 하나의 범용 Adapter Pod에 넣지 않는다.
  • MQTT를 공통 수집 protocol로 강제하지 않는다.
  • 임의 container image, command, privileged 값, raw hostPath, hostNetwork, 고정

ClusterIP 또는 Pod IP를 요청 payload로 받지 않는다.

  • KubeEdge Device/DeviceModel/DeviceStatus를 물리 inventory로 추가하지 않는다.

운영자가 대시보드에서 관리하는 범위

대시보드는 Adapter runtime 운영의 단일 사용자 진입점이다.

  • 설치된 runtime과 관리 주체 확인
  • protocol, target node, hardware binding별 재사용 가능 여부 확인
  • 신규 연결 validation과 실행 plan preview
  • 승인 템플릿 기반 runtime 배포
  • EdgeX Profile/Device 등록과 첫 Event 확인
  • controller-managed runtime 재시작
  • 사용 중인 Device가 없는 controller-managed runtime 퇴역
  • 실패 단계, 보상 결과와 다음 운영 조치 확인

플랫폼 템플릿의 이미지·권한·volume 정의를 승인하거나 새 protocol 구현을 배포 가능 상태로 승격하는 작업은 Git 검토 대상이다. 이는 runtime 인스턴스 운영과 구분한다. 운영자는 대시보드에서 승인된 템플릿만 선택할 수 있다.

권위와 소유권

대상 권위 설명
물리 Device, Profile, resource, protocol property EdgeX Core Metadata dashboard와 controller가 별도 inventory를 만들지 않는다.
latest Event/Reading과 freshness EdgeX Core Data 첫 데이터 확인과 dashboard telemetry의 기준이다.
Device command EdgeX Device Service/Core Command 이번 기능은 actuator command를 추가하지 않는다.
Adapter workload desired state AdapterRuntime CR Controller가 생성한 runtime만 대상이다.
edge node와 Pod 배치 상태 Kubernetes/KubeEdge 물리 Device availability의 권위로 사용하지 않는다.
승인된 배포 템플릿 Git의 Adapter Catalog dashboard에서 이미지나 권한을 수정할 수 없다.
기존 Serial/I2C workload Argo CD 조회·재사용은 가능하지만 dashboard 퇴역·재시작은 차단한다.

Controller가 생성한 리소스에는 app.kubernetes.io/managed-by=edge-adapter-controller, edgeai.etri.re.kr/runtime=<runtime-name> label과 AdapterRuntime owner reference를 부여한다. 이 표지가 없는 기존 Deployment나 Service를 Controller가 수정하거나 삭제하지 않는다.

Adapter Catalog와 검증 상태

Catalog는 runtime image나 Kubernetes manifest를 API 요청에 싣지 않고 안정적인 templateId로 참조하기 위한 allowlist다.

각 항목은 다음 정보를 가진다.

필드 의미
adapterId dashboard와 온보딩 API가 사용하는 protocol adapter 식별자
protocolName EdgeX Device의 protocol key
serviceNamePattern 동적 Device Service 이름 생성 규칙
runtimeMode external, managed-template, unavailable
verificationState hardware-verified, template-verified, unverified
templateId 승인된 runtime 템플릿 버전
supportedNodes 허용된 node와 hardware binding alias
connectionSchema Device protocol property 입력 schema
secretSchema Secret로만 저장할 값의 schema
reusePolicy 다중 Device, endpoint 충돌과 capacity 판정 규칙
profileCapabilities 지원 resource/value type/read-write 제약

초기 상태는 다음과 같다.

  • Jetson Serial과 Raspberry Pi Sense HAT I2C는 실제 설치 상태를

hardware-verified로 표시하고 기존 Argo CD runtime 재사용을 우선한다.

  • 같은 endpoint 또는 resource route가 기존 Device에 독점 할당된 경우 runtime이 Ready여도

protocol_binding_exists로 새 Device 연결을 차단한다.

  • Serial/I2C 신규 배포 템플릿은 현재 검증된 image와 고정된 hardware binding alias만

사용할 수 있다. 요청자가 /dev/* 경로를 입력할 수 없다.

  • 신규 배포용 Device Service image는 runtime별 serviceName과 MessageBus client ID를

환경 설정으로 분리할 수 있어야 한다. 서비스 식별자가 binary에 고정된 기존 image는 external runtime 재사용에만 쓰고 managed-template로 승격하지 않는다.

  • Modbus, OPC-UA, MQTT, REST와 RTSP는 image, Device Profile과 실장비 검증이 끝날 때까지

unverified이며 배포 버튼을 비활성화한다.

  • unverified 항목은 필요한 검증 항목을 보여 줄 수 있지만 성공 가능한 기능으로 표현하지 않는다.

Hardware binding

raw hostPath 대신 Git에서 승인한 alias를 사용한다.

jetson-arduino-serial-001
  node: etri-dev0001-jetorn
  devicePath: /dev/arduino-001
  access: read-write

raspi5-sensehat-i2c-001
  node: etri-dev0003-raspi5
  devicePath: /dev/i2c-1
  access: read-write

이 path는 템플릿 내부에만 존재하고 API 응답에서는 진단 정보로만 redacted 표시한다. Controller는 요청의 targetNode, adapterId, hardwareBindingId 조합이 catalog와 정확히 일치할 때만 workload를 생성한다. binding이 다른 Ready runtime이나 다른 node의 runtime을 잘못 재사용하지 않는다.

AdapterRuntime CRD

API group은 edgeai.etri.re.kr/v1alpha1, Kind는 AdapterRuntime, scope는 Namespaced로 한다. 인스턴스 namespace는 edgex-edge로 제한한다.

spec

spec:
  templateId: serial-device-service-v1
  adapterId: serial-jetson
  targetNode: etri-dev0001-jetorn
  hardwareBindingId: jetson-arduino-serial-001
  edgeX:
    serviceName: device-serial-jetson-02
    messageBusHost: edgex-messagebus.edgex-system.svc.cluster.local
    messageBusPort: 1883
  config:
    logLevel: INFO
  secretRefs: {}
  desiredState: Running
  restartNonce: ""
  requestRef:
    requestId: <HMAC-derived-id>
    payloadHash: <sha256>

사용자가 CR YAML을 제출하지 않는다. Controller가 validated request와 catalog template에서 spec을 만든다. image, command, securityContext, volumes, hostNetwork, service.clusterIP, node selector key와 message bus address는 요청에서 받을 수 없다.

status

status:
  phase: ServiceReady
  observedGeneration: 4
  managementMode: controller
  workloadRef:
    kind: Deployment
    name: adapter-runtime-serial-02
  serviceRef:
    name: adapter-runtime-serial-02
  edgeXServiceObserved: true
  consumers: 0
  conditions:
    - type: WorkloadReady
      status: "True"
      reason: MinimumReplicasAvailable
  lastTransitionTime: "2026-07-23T10:00:00Z"
  lastError:
    code: ""
    message: ""

상태 단계는 다음과 같다.

PLANNED
  -> DEPLOYING
  -> WORKLOAD_READY
  -> SERVICE_READY

DEPLOYING | WORKLOAD_READY
  -> FAILED

SERVICE_READY
  -> RESTARTING
  -> SERVICE_READY

SERVICE_READY | FAILED
  -> RETIRING
  -> RETIRED

SERVICE_READY는 Deployment readiness만 뜻하지 않는다. EdgeX Core Metadata에서 계약된 Device Service 이름을 readback했을 때만 된다.

Runtime 재사용 계획

Connection validation은 mutation 전에 다음 순서로 runtime plan을 만든다.

  1. protocol, node, binding과 Device Service capability가 일치하는 runtime을 찾는다.
  2. SERVICE_READY인지 확인한다.
  3. 기존 EdgeX Devices의 protocol properties를 기준으로 endpoint/route 충돌을 확인한다.
  4. reusePolicy가 다중 Device를 허용하고 capacity가 남아 있으면 REUSE를 선택한다.
  5. 재사용할 수 없고 승인된 배포 템플릿과 빈 hardware binding이 있으면 DEPLOY를 선택한다.
  6. 둘 다 불가능하면 BLOCKED와 기계 판독 가능한 이유를 반환한다.

운영자는 auto, reuse, deploy 중 하나를 선택할 수 있다. auto는 위 규칙을 적용하고, 명시적 reuse나 deploy가 검증 결과와 다르면 apply 전에 차단한다. runtime 선택 결과는 execution plan에서 Device Service 이름, 대상 node, 관리 주체와 차단 이유까지 보여 준다.

통합 Connection 온보딩 상태

runtime과 EdgeX Metadata를 서로 다른 성공으로 오해하지 않도록 하나의 operation 상태로 묶는다.

PLANNED
  -> RUNTIME_REQUESTED
  -> RUNTIME_READY
  -> PROFILE_APPLIED
  -> DEVICE_APPLIED
  -> WAITING_EVENT
  -> ACTIVE

REUSE plan은 RUNTIME_REQUESTED를 거치지 않고 기존 runtime readback으로 RUNTIME_READY에 진입한다.

  • RUNTIME_READY: Device Service workload와 EdgeX service 등록을 확인했다.
  • PROFILE_APPLIED: 요청한 Profile 또는 기존 Profile을 readback했다.
  • DEVICE_APPLIED: service/profile/protocol binding이 요청과 일치한다.
  • WAITING_EVENT: Metadata는 성공했지만 아직 Event가 없거나 Core Data 조회가 일시 실패했다.
  • ACTIVE: 해당 deviceName과 resource 계약에 맞는 첫 Event/Reading을 확인했다.
  • FAILED: 어느 단계에서 실패했는지와 보상 결과를 함께 표시한다.

passive 장비의 Event timeout은 Metadata를 삭제하지 않고 WAITING_EVENT로 유지한다.

외부 Management API

기존 /management/devices* API는 하위 호환을 위해 유지하고, dashboard 신규 wizard는 Connection API를 사용한다.

Method Path 역할
GET /management/adapter-runtimes 외부·controller-managed runtime과 소비 Device 조회
POST /management/adapter-runtimes/plan 재사용·배포·차단 plan 생성
POST /management/adapter-runtimes/{name}/restart controller-managed runtime 재시작
DELETE /management/adapter-runtimes/{name} 소비 Device가 없는 runtime 퇴역
POST /management/connections/validate runtime과 EdgeX 변경의 통합 dry-run
POST /management/connections 승인된 통합 plan 실행
GET /management/connections/operations/{requestId} 전체 상태와 보상 결과 조회

mutation endpoint는 관리자 Bearer token과 Idempotency-Key를 요구한다. 퇴역은 추가로 runtime 이름을 담은 X-Confirm-Runtime header가 정확히 일치해야 한다.

요청은 adapterId, targetNode, hardwareBindingId, runtime 선택 모드, Device/Profile 계약과 catalog schema에 정의된 connection value만 받는다. Kubernetes object나 image 필드는 API schema 자체에 존재하지 않는다.

Controller 내부 API

Controller Service는 cluster 내부 DNS로만 접근한다. state-aggregator만 내부 HMAC 인증으로 호출할 수 있고 browser에는 노출하지 않는다.

Method Path 역할
GET /internal/v1/runtimes 관리 중 CR과 승인된 외부 runtime 조회
POST /internal/v1/runtimes/plan catalog 기반 immutable plan 생성
PUT /internal/v1/runtimes/{name} 동일 request로 idempotent create/reconcile
POST /internal/v1/runtimes/{name}/restart restartNonce 갱신
DELETE /internal/v1/runtimes/{name} dependency 확인 후 desired state를 Retired로 변경
GET /healthz process health
GET /readyz Kubernetes·catalog 준비 상태

Controller는 raw manifest endpoint, shell command endpoint와 arbitrary patch endpoint를 제공하지 않는다.

Idempotency와 상태 복구

외부 요청은 기존 온보딩 MVP와 같은 HMAC-derived requestId와 canonical payload hash를 사용한다.

  • 같은 key와 같은 payload는 기존 operation과 CR을 반환한다.
  • 같은 key에 다른 payload를 제출하면 409 Conflict다.
  • runtime name은 request ID와 template identity로 결정해 재시도가 새 Deployment를 만들지 않는다.
  • AdapterRuntime.spec.requestRef와 EdgeX Device의 예약 tags에 request ID와 hash를 기록한다.
  • process memory operation store는 polling cache일 뿐 권위가 아니다.
  • Pod 재시작 후 CR status, EdgeX Device tags와 Core Data Event로 operation을 재구성한다.
  • raw idempotency key와 관리자 token은 CR, tag, log와 API 응답에 저장하지 않는다.

실패 보상

Kubernetes workload와 EdgeX Metadata는 하나의 transaction이 아니므로 단계별 saga를 사용한다.

  1. runtime 생성 전에 실패하면 mutation 없이 operation만 실패한다.
  2. 이번 operation이 만든 runtime이 SERVICE_READY 전에 실패하면 CR을 FAILED로 남겨

진단 가능하게 하고, 사용자가 retry 또는 retire를 선택하게 한다.

  1. Profile 생성 뒤 Device 생성이 실패하면 이번 operation이 새로 만든 미사용 Profile만

exact-name으로 삭제한다.

  1. Device 생성 뒤 readback이 다르면 성공으로 표시하지 않고 Device를 임의 삭제하지 않는다.
  2. 이번 operation이 만든 runtime 뒤 Metadata apply가 실패하면 consumers가 0일 때에만

자동 퇴역을 시도하고 보상 결과를 기록한다.

  1. 기존 external runtime과 다른 operation이 만든 runtime은 자동 보상으로 재시작·삭제하지 않는다.
  2. Event timeout은 runtime, Profile 또는 Device를 되돌리지 않는다.

재시작과 퇴역

재시작은 Deployment 이름을 직접 patch하지 않고 AdapterRuntime.spec.restartNonce를 갱신해 Controller reconciliation으로 수행한다. external/Argo-managed runtime은 대시보드에서 재시작할 수 없고 운영 진입점을 안내한다.

퇴역은 다음 조건을 모두 만족할 때만 가능하다.

  • managementMode=controller
  • EdgeX Core Metadata에서 해당 service를 사용하는 Device가 0개
  • 동일 hardware binding을 참조하는 진행 중 operation이 없음
  • 관리자 인증과 exact-name 확인 header가 일치

Controller는 owner reference로 자신이 만든 Deployment, Service와 owned Secret만 정리한다. EdgeX Device/Profile, Argo CD resource와 사용자 제공 Secret는 삭제하지 않는다.

Secret 처리

  • secret 값은 catalog의 secretSchema에 정의된 필드만 허용한다.
  • dashboard는 token과 secret을 URL, browser storage나 조회 가능한 form state에 지속 저장하지 않는다.
  • 외부 TLS가 확인되지 않은 배포에서는 새 secret 값 입력을 비활성화하고 기존 Secret ref만 선택한다.
  • Controller는 secret 값을 redacted request로 받고 namespaced Secret에 저장한 뒤 CR에는 ref만 남긴다.
  • API response, audit event, exception과 Kubernetes Event에 평문을 포함하지 않는다.
  • 사용자 제공 Secret는 owner reference를 붙이지 않으며 runtime 퇴역 때 삭제하지 않는다.

현재 hardware-verified Serial/I2C에는 secret 입력이 필요하지 않는다.

인증, 기능 flag와 감사

기본 배포값은 다음과 같다.

DEVICE_MANAGEMENT_ENABLED=false
ADAPTER_RUNTIME_MANAGEMENT_ENABLED=false
ADAPTER_RUNTIME_MUTATION_ENABLED=false

read-only runtime discovery는 management flag가 꺼져도 dashboard 진단에 표시할 수 있지만 모든 mutation control은 닫힌다. 활성화된 mutation은 기존 관리자 token과 별도 Controller internal HMAC key를 Kubernetes Secret에서 읽는다.

감사 event에는 actor, request ID, action, runtime/template/node, EdgeX Device/Profile, redacted 변경 요약, 각 단계 상태, 보상 결과와 timestamp를 기록한다. raw secret, token, idempotency key와 전체 Kubernetes object는 기록하지 않는다.

최소 RBAC와 네트워크

state-aggregator ServiceAccount에는 기존 node/pod read 권한 외 Kubernetes write 권한을 추가하지 않는다.

Adapter Controller 권한은 다음으로 제한한다.

  • cluster scope read-only: 허용 node의 존재와 label을 확인하는 nodes get/list
  • edgex-edge namespace:
  • adapterruntimes get/list/watch/create/update/patch
  • adapterruntimes/status get/update/patch
  • controller-owned deployments, services, configmaps, secrets,

networkpolicies get/list/watch/create/update/patch/delete

  • readiness 진단용 pods, events get/list/watch

admission과 controller 코드가 edgex-edge 밖의 namespace, host PID/IPC, arbitrary host network와 allowlist 밖 volume을 거부한다. image, security context와 volume은 요청값이 아니라 승인 템플릿에서만 온다. 현재 hardware 접근 때문에 root 또는 privileged가 필요한 템플릿은 그 필요성과 대상 binding을 별도로 검증·표시하고, 일반 템플릿으로 확장하지 않는다. 가능한 runtime은 non-root, allowPrivilegeEscalation=false, capability drop과 device plugin 방식으로 승격한다.

Controller Service는 고정 ClusterIP를 지정하지 않고 Kubernetes Service DNS를 사용한다. NetworkPolicy는 state-aggregator에서 Controller로 가는 internal API와 Controller가 Kubernetes API·EdgeX Metadata에 접근하는 경로만 허용한다. 기존 EdgeMesh 설정과 중앙 edgex-messagebus Service를 변경하지 않는다.

Kubernetes 검증

  • CRD와 manifest schema validation
  • kubectl apply --server-side --dry-run=server로 전체 manifest 확인
  • Controller ServiceAccount가 허용 리소스만 조작할 수 있는지 kubectl auth can-i 확인
  • 임의 image/hostPath와 namespace 이탈 요청이 차단되는지 확인
  • 임시 canary runtime이 controller-owned workload만 만들고 퇴역 시 정확히 정리되는지 확인

canary template은 protocol 지원 항목으로 노출하지 않는 내부 검증 전용 health runtime이다. hardware device를 mount하지 않으며 짧은 TTL과 exact-name cleanup을 사용한다. canary 성공은 Controller reconciliation 검증일 뿐 Modbus/OPC-UA/MQTT/RTSP 지원 근거가 아니다.

live read-only 검증

  • Jetson Serial runtime과 Raspberry Pi Sense HAT runtime을 external/Argo-managed로 발견한다.
  • EdgeX Device Service 이름, target node, hardware binding과 연결된 Device 수를 대조한다.
  • 현재 endpoint를 선택한 reuse plan이 기존 runtime을 찾고 route 충돌 여부를 정확히 반환한다.
  • 기존 Serial/I2C Event/Reading과 dashboard freshness가 계속 정상인지 확인한다.
  • EdgeMesh generation, workload와 설정을 변경하지 않았음을 전후 비교한다.

Browser 검증

  • 좁은 화면과 desktop에서 runtime 목록과 wizard가 사용할 수 있다.
  • unverified protocol과 external runtime mutation 버튼이 비활성화된다.
  • admin token과 secret이 browser storage 또는 URL에 남지 않는다.
  • validation, apply, polling, 실패와 보상 결과가 단계별로 표시된다.
  • browser에서 Kubernetes API로 직접 요청하지 않는다.

배포 순서

  1. 범위·저장소·로드맵·운영 문서를 먼저 갱신한다.
  2. CRD, Controller와 RBAC를 edgex/k8s 진입점에 추가하되 mutation flag는 끈다.
  3. state-aggregator에 Controller client와 read-only runtime inventory를 추가한다.
  4. planner와 통합 Connection validation을 활성화한다.
  5. 자동·server-side dry-run과 browser 검증을 통과한다.
  6. live Serial/I2C discovery와 reuse plan을 read-only로 확인한다.
  7. 내부 canary만 잠시 mutation 활성화해 배포·readiness·퇴역을 확인한다.
  8. canary를 정리하고 mutation flag를 다시 기본값으로 둔다.
  9. 실제 protocol template은 실장비 검증 후 각각 승인 상태로 승격한다.

Argo CD는 CRD, Controller, catalog와 base workload를 배포한다. 대시보드 요청으로 생성된 AdapterRuntime과 그 owned workload는 Controller가 관리하며 Argo CD resource로 가장하지 않는다.
