대시보드 디바이스 온보딩 MVP 설계

목적

설치되어 실행 중인 EdgeX Device Service에 새 물리 장비를 대시보드에서 등록하고, Device Profile·Device·Device Service binding과 첫 Event를 한 흐름으로 검증한다. 장비 inventory, state, telemetry와 command의 권위는 계속 EdgeX이며 대시보드는 관리 UI다.

이 MVP는 어떤 프로토콜이 들어올지 미리 확정할 수 없는 상황을 다룬다. 하나의 범용 multi-protocol runtime을 만들지 않고, protocol별 EdgeX Device Service를 Adapter Catalog로 노출해 설치된 adapter에만 Device를 등록한다.

결정

선택한 방식

protocol별 EdgeX Device Service + 공통 Adapter Catalog + Device Onboarding API를 사용한다.

Dashboard Device Management
  -> Device Onboarding API
      -> Adapter Catalog
      -> validation / dry-run
      -> EdgeX Core Metadata
          -> Device Profile
          -> Device
          -> Device Service binding
      -> Core Data first-Event verification
      -> structured audit event

하나의 Device Service instance는 같은 protocol과 node placement를 공유하는 여러 Device를 관리한다. 센서마다 Pod를 만들지 않는다.

선택하지 않은 방식

  • 모든 protocol library를 하나의 범용 Pod에 넣지 않는다. 의존성, host device 권한과 장애

범위가 결합되기 때문이다.

  • MQTT를 공통 변환 protocol로 강제하지 않는다. MQTT-only 장비일 때만 MQTT Device

Service를 사용한다.

  • 사용 여부를 모르는 Device Service를 모두 미리 배포하지 않는다.
  • KubeEdge Device/DeviceModel CRD를 physical inventory로 사용하지 않는다.
  • Dashboard나 Onboarding API가 PostgreSQL을 physical inventory 권위로 사용하지 않는다.

현재 범위 변경

현재 state-aggregator와 dashboard의 physical-device API는 read-only다. 구현 전에 docs/프로젝트-범위.md, docs/저장소-구조.md, docs/대시보드-판단-정책.md, docs/대시보드-정보-구조.md에 다음 제한된 mutation 범위를 명시한다.

  • 관리자만 Device Profile과 Device를 생성할 수 있다.
  • Device의 description, labels, tags, protocol properties와 admin state를 제한적으로 수정할 수 있다.
  • validation과 dry-run은 mutation 없이 누구나 현재 catalog와 충돌을 확인할 수 있다.
  • Device 삭제, Device Profile 강제 삭제, actuator command와 Kubernetes workload mutation은 없다.
  • Workflow Builder의 browser-local dry-run 경계는 그대로 유지한다.

Adapter Catalog

Adapter Catalog는 데이터 plane이나 inventory가 아니라 dashboard form과 validation을 위한 capability schema다. runtime 상태는 EdgeX Core Metadata의 Device Service 응답으로 확인한다.

catalog 항목은 다음 필드를 갖는다.

필드 의미
adapterId UI와 API에서 사용하는 안정적인 adapter 식별자
displayName 운영자 표시 이름
serviceName EdgeX Device Service 이름
protocolName EdgeX Device protocols key
nodeName 선택적 workload placement 진단값
fields endpoint 입력 field, type, required, secret, validation 규칙
profileCapabilities 지원 value type, read/write 여부와 resource 제약
status installed, unavailable, unsupported
mutationEnabled 전역 feature flag를 UI에 전달해 create/PATCH control을 닫는 값

초기 catalog에는 이미 검증된 device-serial-jetson과 device-sensehat-raspi만 installed로 노출한다. Modbus, OPC-UA, MQTT와 RTSP는 해당 Device Service와 실제 endpoint 검증 전까지 unsupported 또는 catalog 미등록이다.

현재 설치된 Serial adapter의 Port, BaudRate, DeviceID와 Sense HAT adapter의 Bus, DeviceID는 실제 mount/source에 맞춘 상수다. 같은 service/protocol의 endpoint와 resource route를 기존 Device가 소유하면 protocol_binding_exists로 차단한다. 따라서 installed는 runtime capability이며 빈 route capacity를 의미하지 않는다.

secret field는 API 응답, audit event와 UI 재조회에서 평문으로 반환하지 않는다. 초기 MVP는 secret이 필요한 protocol의 등록을 지원하지 않고 unsupported로 차단한다.

Dashboard 정보 구조

기존 read-only dashboard에 별도 Device Management 영역을 추가한다. Workflow Builder와 같은 화면이나 상태 저장소를 공유하지 않는다.

목록

  • EdgeX Device name, Profile, Device Service, protocol과 admin/operating state
  • Adapter Catalog 설치 상태
  • latest Core Data Event freshness
  • 등록, 수정, 연결 확인 action

등록 wizard

  1. 설치된 adapter를 선택한다.
  2. deviceName, description, labels, optional node tag를 입력한다.
  3. catalog schema에 따라 protocol endpoint를 입력한다.
  4. 기존 Device Profile을 선택하거나 제한된 resource form으로 새 Profile을 정의한다.
  5. dry-run에서 생성될 Profile, Device, binding과 충돌을 확인한다.
  6. 관리자 인증 후 apply한다.
  7. Metadata readback과 첫 Event verification 결과를 표시한다.

unsupported protocol을 선택하면 자동으로 임의 adapter를 만들거나 배포하지 않는다. 필요한 Device Service, SDK 개발과 실제 장비 검증이 별도 작업임을 표시한다.

API 계약

관리 API는 기존 /state/* read-only API와 분리해 /management/*에 둔다.

Method Path 역할
GET /management/adapters catalog와 Core Metadata Device Service 상태 조회
POST /management/devices/validate 이름, endpoint, Profile, binding 충돌 dry-run
POST /management/devices Profile과 Device 생성 후 readback
PATCH /management/devices/{name} allowlist field만 수정
GET /management/operations/{requestId} apply와 first-Event verification 상태 조회

POST와 PATCH는 Idempotency-Key와 관리자 Bearer token을 요구한다. 같은 key와 같은 payload 재시도는 기존 결과를 반환하고, 같은 key에 다른 payload가 오면 409 Conflict다.

Device 삭제, Profile 삭제와 command endpoint는 만들지 않는다.

Idempotency와 operation 복구

서버는 raw idempotency key를 저장하지 않는다. Kubernetes Secret의 별도 HMAC key로 안정적인 requestId를 만들고 canonical request payload의 SHA-256 digest와 함께 생성 Device의 예약 tags edgeAiOnboardingRequestId, edgeAiOnboardingPayloadHash에 기록한다.

  • 요청 전에 Core Metadata의 동일 Device name과 예약 tag를 확인한다.
  • 같은 request ID와 payload hash면 기존 Metadata를 readback하고 verification을 재개한다.
  • request ID 또는 payload가 충돌하면 새 객체를 만들지 않고 409를 반환한다.
  • 최근 operation은 process memory의 bounded store에도 두어 UI polling을 빠르게 처리한다.
  • Pod 재시작으로 memory state가 사라지면 예약 tags와 Core Data Event로 상태를 재구성한다.
  • Device 생성 전 실패는 exact compensation 뒤 재시도하므로 persistent operation record가 없어도

중복 Profile을 만들지 않는다.

예약 tags는 API와 audit에서 request ID만 표시하고 raw idempotency key는 반환하지 않는다.

인증과 기본 비활성화

  • DEVICE_MANAGEMENT_ENABLED=false가 기본값이다.
  • 활성화된 mutation endpoint는 Kubernetes Secret에서 읽은 관리자 token을 요구한다.
  • idempotency request ID 생성용 HMAC key도 같은 Secret의 별도 key로 주입한다.
  • browser는 token을 localStorage, URL, 로그 또는 audit payload에 저장하지 않고 현재 session

memory에서만 사용한다.

  • read-only /state/* endpoint와 dashboard 조회는 기존 동작을 유지한다.
  • 인증 실패는 401, validation 실패는 422, 충돌은 409를 반환한다. 역할별 403 구분은

OIDC/RBAC 도입 전에는 제공하지 않는다.

이 token 방식은 내부 PoC 범위다. 외부 운영 노출 전에 OIDC와 역할 기반 권한으로 교체한다.

생성 순서와 실패 처리

EdgeX Core Metadata의 Profile 생성과 Device 생성은 하나의 DB transaction이 아니므로 Onboarding API가 제한된 saga로 처리한다.

  1. catalog, schema, 이름, 기존 Profile/Device와 Device Service 상태를 모두 검증한다.
  2. 새 Profile이 필요할 때 Profile을 생성하고 동일 내용을 readback한다.
  3. Device를 생성하고 service/profile/protocol binding을 readback한다.
  4. Device 생성이 실패하면 이번 operation이 새로 만든 미사용 Profile만 보상 삭제한다.
  5. readback 불일치는 operation을 failed로 남기고 성공으로 표시하지 않는다.
  6. first Event는 설정된 timeout까지 Core Data를 확인한다.

Metadata 생성 성공과 first Event verification은 분리된 상태다.

  • metadata_applied: Profile/Device readback 성공
  • waiting_for_event: 아직 Event가 없음
  • verified: 계약된 deviceName의 Event/Reading 수신
  • failed: validation, Metadata 또는 readback 실패

Event가 없는 passive 장비는 Metadata 등록을 되돌리지 않고 waiting_for_event로 남긴다. Core Data가 일시적으로 조회 불가능해도 Metadata readback 성공을 failed로 바꾸지 않고 오류 설명이 있는 waiting_for_event로 유지해 이후 operation polling에서 다시 확인한다.

수정 제한

MVP의 PATCH allowlist는 description, labels, user tags, protocol properties와 adminState다. edgeAiOnboardingRequestId, edgeAiOnboardingPayloadHash, nodeName, physicalDeviceId는 system tag이므로 PATCH할 수 없다. 다음 변경은 새 validation/apply flow로만 처리하거나 차단한다.

  • Device name 변경
  • Profile name 교체
  • Device Service 교체
  • resource의 value type 변경
  • write command 추가

adminState=LOCKED 전환은 허용하지만 장비 command를 전송하지 않는다.

감사 event

각 validate/apply 요청은 다음 값을 포함한 구조화 JSON event를 남긴다.

  • request ID와 idempotency key hash
  • actor 식별자
  • action과 target Device/Profile
  • redacted 변경 전후 요약
  • validation/apply/verification 상태
  • EdgeX 응답 status와 오류 분류
  • 시작·종료 timestamp

MVP의 감사 event는 application stdout에 기록해 Kubernetes log로 확인한다. 영구 보존과 검색 API는 이 단계의 완료 조건이 아니며, 운영 승격 전에 중앙 log sink 또는 별도 audit store를 정한다.

테스트 전략

자동 테스트

  • Adapter Catalog schema와 secret redaction
  • validate의 필수 field, type, name, duplicate와 unsupported protocol 판정
  • 관리자 token과 feature flag
  • idempotency key 재시도와 payload 충돌
  • Profile 생성 → Device 생성 → readback 순서
  • Device 생성 실패 시 이번 operation이 만든 미사용 Profile만 보상 삭제
  • allowlist 밖 PATCH 차단
  • first Event의 verified/waiting_for_event/failed 전이
  • 기존 /state/*, dashboard와 Workflow Builder read-only 회귀

live 검증

live mutation은 기본 테스트에서 실행하지 않는다. 명시적 관리자 승인과 isolated prefix를 사용하는 canary만 허용한다.

  1. 기존 12개 route와 겹치지 않는 격리된 adapter endpoint를 준비하고

onboarding-canary-* Profile과 Device를 등록한다.

  1. 설치된 검증용 Device Service에 binding한다.
  2. Metadata readback과 first Event를 확인한다.
  3. canary만 정확한 이름으로 정리한다.
  4. 기존 12개 Device와 dashboard freshness가 계속 정상인지 확인한다.

실제 물리 endpoint 없이 simulator로 통과한 결과는 protocol 실장비 지원 완료 근거로 사용하지 않는다.

배포와 운영 경계

  • Onboarding API는 기존 state-aggregator 내부 모듈로 시작하되 read-only service 코드와

management client를 분리한다.

  • 운영 Kubernetes manifest 변경은 계속 edgex/k8s와 Argo CD 경로를 따른다.
  • Dashboard가 kubectl apply, Deployment scale/restart 또는 EdgeMesh mutation을 수행하지 않는다.
  • Device Service가 설치되어 있지 않으면 unsupported를 반환하며 자동 배포하지 않는다.
  • 고정 ClusterIP나 PodIP를 저장하지 않고 Kubernetes Service DNS와 EdgeX service identity를 사용한다.

완료 조건

  1. feature flag가 꺼진 기본 배포에서 모든 mutation endpoint가 닫혀 있다.
  2. 관리자는 설치된 adapter를 선택해 dry-run하고 Profile/Device를 생성할 수 있다.
  3. 동일 요청 재시도가 중복 Device/Profile을 만들지 않는다.
  4. 생성 결과가 Core Metadata readback과 일치한다.
  5. first Event 결과를 Metadata 성공과 구분해 표시한다.
  6. 기존 12개 Device의 read-only dashboard와 telemetry history가 회귀하지 않는다.
  7. 삭제, command, Kubernetes mutation, adapter 자동 배포와 EdgeMesh 변경이 없다.

후속 단계

MVP 이후에만 다음을 별도 설계한다.

  • Device/Profile 삭제와 dependency-safe cleanup
  • OIDC/RBAC와 durable audit storage
  • allowlist 기반 adapter GitOps 배포 요청
  • 실제 Modbus/OPC-UA/MQTT/RTSP Device Service onboarding
  • 검증된 actuator command와 승인 workflow
