실측 센서 이상 탐지 서비스 데모 설계

상태

  • 진행 결정일: 2026-07-22
  • 입력 장비: etri-dev0001-jetorn에 연결된 Arduino Uno
  • 입력 가상 디바이스: virtual-acceleration-{x,y,z}-001
  • 배포 대상: Jetson의 고정 서비스 데모 workload
  • 결정 근거: 별도 학습 모델 artifact가 없으므로 실제 센서 데이터 기반 온라인 통계 모델을 첫 데모로 선택한다.

목표

현재 검증된 Serial 수집 경로를 실제 AI 서비스 consumer까지 연결한다. 데모는 Arduino의 가속도 X/Y/Z raw Reading을 Jetson에서 직접 읽고, 전처리와 경량 이상 탐지를 실행한 뒤, 그 결과와 디바이스-서비스 연결 관계를 중앙 dashboard에서 관측할 수 있어야 한다.

이 데모가 증명하는 범위는 다음과 같다.

  1. 실제 물리 입력이 EdgeX Device Service에서 세 개 가상 Device로 표준화된다.
  2. 같은 Jetson의 AI 서비스가 Local Data API로 최근 입력을 읽는다.
  3. AI 서비스가 세 축을 하나의 sample로 정렬하고 명시적인 모델로 상태를 판정한다.
  4. 중앙 dashboard가 입력 Device, AI consumer, 최신 추론 결과와 장애 상태를 한 흐름으로 보여준다.
  5. KubeEdge/Argo CD가 AI workload의 배치와 실행 상태를 관리한다.

완전한 동적 workflow 실행, 모델 registry, actuator 제어, runtime migration이나 offloading은 이 첫 서비스 데모의 완료 주장에 포함하지 않는다.

현재 사실과 제약

  • device-serial-jetson은 실제 /dev/arduino-001을 한 번 읽고 가속도 세 축을 같은

nanosecond origin으로 fan-out한다.

  • 각 가상 Device에는 최근 10분·최대 10,000 sample의 휘발성 cache와 read-only Local

Data API가 있다.

  • 중앙 EdgeX Core Data/PostgreSQL은 원시 Event/Reading의 장기 권위다.
  • 현재 저장소의 vision_stage_runner는 실제 camera/model 입력 없이 workflow ID에서

결정론적 가짜 결과를 만드는 샘플이다. 현재 서비스 데모 근거로 사용할 수 없다.

  • 외부에서 제공된 학습 모델, label 또는 정상/불량 dataset이 없다.
  • Arduino 값은 Int32 raw 값이며 물리 단위로 보정된 가속도라고 단정하지 않는다.
  • 현재 Flannel CNI는 NetworkPolicy를 집행하지 않는다. client label과 policy는 의도

선언이며 실제 인증·인가 경계가 아니다.

접근 방식 비교

채택: Jetson Local Data API 증분 조회

AI 서비스가 500ms 간격으로 세 축 recent API를 조회하고 마지막 처리 origin 이후의 sample만 결합한다.

  • 이미 구현·검증된 local recent cache를 재사용한다.
  • 원시 데이터가 중앙 서버를 왕복하지 않아 edge-local 전처리/추론을 증명한다.
  • 별도 MQTT broker나 MessageBus consumer를 추가하지 않는다.
  • Device Service 변경 없이 bounded service demo를 완성할 수 있다.
  • 엄밀한 push stream이 아니라 준실시간 polling이라는 사실을 API와 문서에 표시한다.

제외: Device Service SSE/gRPC stream 추가

push latency에는 유리하지만 Device Service의 public contract, connection lifecycle, backpressure와 재연결 정책까지 새로 검증해야 한다. 고주기 stream 요구가 확인되기 전에는 첫 데모 범위를 불필요하게 넓힌다.

제외: 중앙 EdgeX MessageBus 구독

Application Service가 중앙 MessageBus를 구독하면 stream 처리는 쉬워지지만, 추론 입력이 Jetson local path가 아니라 중앙 round-trip에 종속된다. 이번 데모의 edge-local 처리 목표와 맞지 않는다.

전체 구조

Arduino Uno
  -> /dev/arduino-001
  -> device-serial-jetson
     -> virtual-acceleration-x-001 / acceleration_x_raw
     -> virtual-acceleration-y-001 / acceleration_y_raw
     -> virtual-acceleration-z-001 / acceleration_z_raw
     -> Device Service memory recent cache
        -> Local Data API
           -> sensor-anomaly-demo @ etri-dev0001-jetorn
              -> origin join / deduplicate
              -> vector magnitude
              -> online baseline model
              -> normal / anomaly / degraded result
              -> read-only demo API
                 -> state-aggregator
                    -> service demo dashboard

같은 raw sample
  -> EdgeX MessageBus -> Core Data -> PostgreSQL

원시 telemetry의 inventory, state와 history 권위는 계속 EdgeX다. 이상 탐지 결과는 물리 Device telemetry가 아니라 AI 서비스의 파생 결과이므로 이번 범위에서는 새로운 EdgeX Device로 등록하지 않는다. dashboard는 세 입력 Device에 sensor-anomaly-demo consumer를 연결해 표시한다.

sensor-anomaly-demo 책임

새 서비스는 다음 모듈을 분리한다.

모듈 책임
Local Data client 세 Service FQDN API 증분 조회, timeout와 오류 정규화
Frame joiner 같은 origin의 X/Y/Z를 하나의 frame으로 결합, 중복·불완전 frame 제거
Feature extractor sqrt(x^2 + y^2 + z^2) raw magnitude 계산
Online detector 초기 baseline 학습, score와 anomaly 상태 계산
Result store 최근 결과를 bounded memory ring으로 보존
HTTP API health, current state, recent result를 read-only로 제공

프로세스는 입력 장치 파일을 직접 열지 않는다. Serial endpoint의 유일 소유자는 계속 device-serial-jetson이다.

입력과 frame 결합

각 source는 다음 경로를 사용한다.

GET http://device-serial-jetson.edgex-edge.svc.cluster.local:59910
    /api/v3/localdata/device/name/{device}/resource/name/{resource}
    ?from={last_origin_plus_one}&to={now_ns}&limit=1000

매 polling cycle에서 세 응답을 origin으로 inner join한다. 세 축이 모두 있는 frame만 모델 입력으로 사용한다. 같은 origin을 다시 받아도 한 번만 처리한다. 한 축이 일시적으로 늦으면 작은 pending map에 보관하되, 10초가 지나거나 1,000개를 넘은 불완전 frame은 버린다. 서비스 시작 시 최근 API의 최신 구간부터 읽으며 중앙 history로 fallback하지 않는다.

Local Data API가 반환한 valueType은 Int32여야 한다. 잘못된 type, JSON, source identity, 비정상적으로 큰 응답은 모델에 넣지 않고 입력 오류 계수에 반영한다.

온라인 이상 탐지 모델

외부 학습 dataset이 없으므로 magnitude의 정상 기준을 현장에서 자동 학습하는 단변량 온라인 Gaussian baseline을 사용한다. 이는 학습된 분류 모델이나 고장 원인 진단 모델로 표현하지 않고, raw 가속도 변화 이상 탐지로 표시한다.

  1. 시작 후 완전한 frame 30개를 warming_up baseline으로 수집한다.
  2. baseline의 평균과 분산은 Welford 알고리즘으로 계산한다.
  3. warm-up 뒤 각 frame의 score를 다음과 같이 계산한다.
score = abs(magnitude - baseline_mean) / max(baseline_stddev, stddev_floor)
  1. score >= 4.0이 2회 연속이면 anomaly, threshold 미만이 3회 연속이면 normal로

복귀한다.

  1. normal sample만 EWMA(alpha=0.05)로 baseline을 천천히 갱신한다. anomaly sample은

baseline 오염을 막기 위해 학습에서 제외한다.

  1. 최근 완전한 frame이 10초 이상 없거나 upstream 조회가 연속 실패하면 degraded다.

threshold, warm-up count, stddev floor, poll interval과 stale interval은 환경변수로 설정할 수 있지만 dashboard 응답에 effective configuration을 함께 노출한다. 운영자가 threshold를 알 수 없는 black box 결과는 만들지 않는다.

서비스 API 계약

상태

GET /api/v1/status

대표 응답은 다음과 같다.

{
  "apiVersion": "v1",
  "service": "sensor-anomaly-demo",
  "mode": "live",
  "status": "normal",
  "inputState": "fresh",
  "modelState": "ready",
  "source": {
    "physicalSource": "arduino-001",
    "deviceService": "device-serial-jetson",
    "devices": [
      "virtual-acceleration-x-001",
      "virtual-acceleration-y-001",
      "virtual-acceleration-z-001"
    ]
  },
  "latest": {
    "origin": 1784600000000000000,
    "observedAt": "2026-07-22T10:00:00Z",
    "values": {"x": 12, "y": -3, "z": 1012},
    "magnitude": 1012.075,
    "score": 0.42,
    "anomaly": false
  },
  "model": {
    "algorithm": "online-gaussian-baseline-v1",
    "sampleCount": 84,
    "warmupSamples": 30,
    "threshold": 4.0,
    "baselineMean": 1011.8,
    "baselineStddev": 2.4
  },
  "counters": {
    "framesProcessed": 84,
    "duplicatesIgnored": 2,
    "incompleteFramesDropped": 0,
    "inputErrors": 0
  },
  "lastError": null
}

status 값은 starting, warming_up, normal, anomaly, degraded 중 하나다. mode=live는 fixture나 합성 입력이 아님을 나타낸다.

최근 결과

GET /api/v1/results?limit={1..1000}

최근 최대 1,000개 결과를 origin 오름차순으로 반환한다. 이는 재시작 비보존의 UI용 최근 결과이며 중앙 원시 history를 대체하지 않는다.

Kubernetes probe

  • GET /healthz: 프로세스 event loop가 동작하면 200
  • GET /readyz: 설정을 읽고 polling worker가 시작됐으면 200

물리 입력이 stale인 경우에도 Pod를 무한 재시작하지 않도록 readiness와 input state를 분리한다. upstream 장애는 /api/v1/status의 degraded로 표현한다.

API는 read-only다. 합성 anomaly 주입, EdgeX state mutation, calibration reset과 actuator command endpoint를 현재 운영 데모에 넣지 않는다.

state-aggregator와 dashboard

state-aggregator는 다음 Service FQDN을 timeout이 있는 read-only client로 조회한다.

http://sensor-anomaly-demo.edgex-edge.svc.cluster.local:8080

새 endpoint GET /state/service-demo는 AI 서비스 응답을 dashboard schema로 정규화한다. AI 서비스가 없거나 timeout이면 dashboard 전체를 실패시키지 않고 degraded snapshot과 관측 오류를 반환한다.

dashboard에는 다음 정보를 한 패널에 표시한다.

  • 실제 physical source와 세 EdgeX 가상 Device
  • Device Service와 serial protocol
  • AI service Pod/node와 consumer binding
  • warm-up/normal/anomaly/degraded 상태
  • 최신 X/Y/Z raw 값, magnitude, score, threshold와 sample origin
  • baseline sample 수와 최근 input age
