엣지엑스 중앙 코어와 엣지 임시 버퍼 배치 설계

1. 결정

각 KubeEdge EdgeCore 노드는 센서 수집과 실시간 추론을 담당한다. EdgeX Core와 PostgreSQL은 x86 엣지 AI 서버에 한 세트만 배치해 raw telemetry를 통합 영구 저장한다. EdgeCore 노드에는 네트워크 또는 서버 장애 동안 사용할 디스크 기반 임시 버퍼만 둔다.

현재 Jetson에 배치된 EdgeX 전체 스택은 MQTT-only 수직 슬라이스를 검증하기 위한 구조다. 목표 구조에서는 다음처럼 역할을 분리한다.

센서가 연결된 EdgeCore 노드
  Sensor / collector
    -> local Mosquitto 127.0.0.1:1883
       ├-> local AI inference service
       └-> edge-telemetry-agent
           - MQTT source adapter / allowlist normalizer
           - SQLite durable outbox
           - EdgeX Event uploader
              |
              | HTTPS + persisted acknowledgement
              v

etri-ser0002-cgnmsb (x86 Edge AI 서버)
  edgex-ingest-gateway
    -> EdgeX Core Data REST API
       ├-> PostgreSQL (저장 확인 기준)
       └-> EdgeX internal MessageBus (후속 소비자용, 비동기)

etri-ser0001-cg0msb (운영 서버)
  state-aggregator / dashboard (후속 연계)
    -> 필요할 때 EdgeX Core Data API 조회

따라서 센서 엣지마다 EdgeX Pod 6~7개를 복제하지 않는다. 기존 로컬 Mosquitto와 AI 서비스를 제외하면 센서 엣지에 추가되는 것은 edge-telemetry-agent 한 Pod다. 중앙 EdgeX 서비스는 etri-ser0002-cgnmsb 한 곳에서만 실행한다.

실시간성과 영구 저장도 분리한다.

  • 실시간 추론: 센서 데이터를 노드 로컬 MQTT에서 바로 소비한다.
  • 영구 저장: edge agent가 데이터를 outbox에 먼저 기록한 뒤 중앙으로 계속 전송한다.
  • 대시보드 조회: 후속 연계 시 대시보드는 각 엣지를 직접 조회하지 않고 중앙 Core

Data에서 필요할 때 조회한다. 이번 변경 동안 기존 InfluxDB 조회는 유지한다.

2. 목표와 비목표

목표

  • 센서가 연결된 EdgeCore 노드마다 EdgeX 전체 Pod를 복제하지 않는다.
  • 센서 수집과 실시간 추론은 중앙 서버 또는 네트워크 장애와 무관하게 계속한다.
  • raw telemetry의 영구 저장 위치를 Edge AI 서버의 PostgreSQL로 단일화한다.
  • 장애 중 telemetry를 엣지 디스크에 임시 저장하고 연결 복구 후 재전송한다.
  • 중앙 수신 broker 확인이 아니라 Core Data의 PostgreSQL 저장 결과를 기준으로 엣지

record를 제거한다.

  • KubeEdge DeviceStatus에는 raw telemetry를 기록하지 않는다.
  • Kustomize와 Argo CD에서 서버 data plane과 엣지 agent를 별도 배포 단위로 관리한다.

비목표

  • Modbus, OPC-UA, RTSP adapter를 이번 변경에서 동시에 구현하지 않는다.
  • EdgeX Core Data와 PostgreSQL의 고가용성 클러스터를 구현하지 않는다.
  • 현재 dashboard의 InfluxDB 조회 경로를 즉시 EdgeX로 교체하지 않는다.
  • 동적 workflow, placement, offloading 또는 Device CR 자동 생성을 추가하지 않는다.
  • 모든 후속 소비자까지 포함한 exactly-once 처리를 보장하지 않는다. 엣지에서 중앙까지의

전송은 at-least-once이고, Event UUID를 이용해 중앙 저장을 멱등 확인한다. internal MessageBus의 후속 소비자는 같은 Event UUID를 기준으로 중복을 처리해야 한다.

3. 노드별 배치

etri-ser0002-cgnmsb: Edge AI 서버

프로젝트 문서에서 worker/추론 서버로 정의된 etri-ser0002-cgnmsb를 기본 EdgeX 영구 저장 서버로 사용한다.

상시 실행 workload는 여섯 개다.

  1. edgex-ingest-gateway
  2. EdgeX Core Keeper
  3. EdgeX Core Metadata
  4. EdgeX internal MessageBus
  5. EdgeX Core Data
  6. PostgreSQL StatefulSet

Device/Profile bootstrap Job은 등록 작업이 끝나면 Completed가 되므로 상시 실행 Pod로 세지 않는다. 중앙 경로에서는 Device MQTT를 사용하지 않는다. edge agent가 이미 payload를 검증하고 EdgeX Event를 만들기 때문에 Device MQTT를 다시 거치면 변환 단계만 늘고 영구 저장 확인 문제는 해결되지 않는다.

Core Data, Metadata, Keeper, internal MessageBus와 PostgreSQL은 ClusterIP로 유지한다. EdgeCore 노드에는 제한된 edgex-ingest-gateway만 노출한다. PostgreSQL은 외부에 노출하지 않는다.

PostgreSQL은 local-path 20Gi PVC를 사용한다. 여기서 영구 저장은 Pod 재시작과 재배포 후에도 데이터가 유지된다는 뜻이다. 단일 서버와 local-path 자체는 서버 디스크 장애를 보호하지 않으므로 운영 전 백업 또는 복제 정책이 별도로 필요하다.

센서가 연결된 KubeEdge EdgeCore 노드

edgeai.etrilab/sensor-gateway=true 라벨이 붙은 EdgeCore 노드에 edge-telemetry-agent DaemonSet을 한 개씩 배치한다. Jetson과 Raspberry Pi의 포함 여부는 이 라벨로 관리하고 모든 edge-role 노드에 무조건 배포하지 않는다.

edge agent 책임:

  • 노드 로컬 Mosquitto의 factory/devices/+/telemetry 구독
  • route profile에 선언된 device와 field만 allowlist 변환
  • source timestamp를 EdgeX Event/Reading의 origin으로 보존
  • 정상·장애 상태와 관계없이 SQLite durable outbox에 먼저 기록
  • 각 record에 클라이언트 생성 UUID와 안정적인 payload fingerprint 부여
  • 중앙 ingest gateway에 HTTPS로 Event 업로드
  • 중앙의 영구 저장 확인 응답 후에만 outbox record 제거
  • buffer depth, bytes, oldest age, dropped/rejected count를 metric과 health로 제공

현재 구현 범위의 source adapter는 MQTT 하나다. 이후 Modbus 또는 OPC-UA adapter를 추가하더라도 정규화 이후의 outbox와 업로드 경로는 재사용한다. RTSP 영상 frame은 이 경로로 보내지 않는다.

실시간 추론 서비스는 edge agent에 합치지 않는다. AI 서비스와 edge agent가 같은 로컬 MQTT telemetry를 각각 구독하므로 중앙 연결이 끊겨도 추론은 계속된다.

4. 데이터 흐름과 저장 확인

  1. 센서 또는 collector가 로컬 Mosquitto의

factory/devices/{device-name}/telemetry에 발행한다.

  1. Mosquitto는 같은 sample을 로컬 AI 서비스와 edge agent에 fan-out한다.
  2. edge agent가 route profile로 payload를 검증하고 EdgeX v3 AddEventRequest를 만든다.
  3. edge agent가 Event와 전달 메타데이터를 SQLite outbox에 transaction commit한다.
  4. uploader가 Device별 가장 오래된 record부터 중앙 gateway의 POST /v1/events로

전송한다.

  1. gateway가 token, 크기, device/profile/source allowlist를 검증한다.
  2. gateway가 Core Data의 다음 API로 요청을 전달한다.
   POST /api/v3/event/edge-telemetry-agent/{profileName}/{deviceName}/{sourceName}
  1. Writable.PersistData=true인 Core Data가 Event와 Reading을 PostgreSQL에 저장한 뒤

201 Created를 반환한다.

  1. gateway는 Core Data의 201을 받은 경우에만 agent에 201 persisted를 반환한다.
  2. agent는 201 persisted를 받은 뒤 해당 outbox record를 삭제한다.

MQTT PUBACK은 broker 수신만 확인하므로 outbox 삭제 기준으로 사용하지 않는다. EdgeX internal MessageBus도 영구 저장 확인이나 장애 완충 계층으로 사용하지 않는다. Core Data가 REST 입력 Event를 MessageBus로 발행하는 동작은 후속 소비자 통합용이며, PostgreSQL 저장 성공 여부는 Core Data REST 결과로 판단한다. 응답 유실 후 같은 Event를 재전송하면 internal MessageBus에는 중복 Event가 발행될 수 있으므로 후속 소비자는 Event UUID로 deduplicate해야 한다.

응답이 유실된 경우

Core Data가 저장한 직후 gateway 또는 네트워크 응답이 유실될 수 있다. agent는 record를 지우지 않고 같은 Event UUID로 다시 전송한다.

  1. Core Data는 이미 존재하는 UUID에 409 Conflict를 반환한다.
  2. gateway가 내부 API GET /api/v3/event/id/{id}로 기존 Event를 조회한다.
  3. gateway는 agent가 보낸 hash를 그대로 신뢰하지 않고, server-generated field를

제외한 device/profile/source, origin, tag와 Reading 값으로 canonical fingerprint를 다시 계산해 비교한다.

  1. 내용이 같으면 200 already_persisted를 반환하고 agent가 record를 삭제한다.
  2. UUID는 같지만 내용이 다르면 409 id_collision을 반환하고 agent가 record를

quarantine한다.

이 방식은 네트워크상 at-least-once 재전송을 허용하면서 같은 UUID의 중복 row 생성을 막는다. 전체 시스템의 exactly-once를 주장하지는 않는다.

Core Metadata bootstrap은 논리 Device Service edge-telemetry-agent, Device Profile과 Device를 사전 등록한다. 이는 관리 조회와 schema의 기준이고, raw telemetry는 Device 또는 DeviceStatus CR에 복제하지 않는다.

수집 mapping의 기준은 Git에 저장된 route profile이다. 같은 route profile에서 agent의 field allowlist와 EdgeX Device Profile bootstrap 입력을 만들고, test에서 resource 이름과 value type 일치를 검증한다. agent는 연결이 끊긴 동안에도 동작해야 하므로 runtime마다 Core Metadata에서 profile을 가져오지 않는다.

여기서 EdgeX Device/Profile은 EdgeX Metadata의 관리 객체이며 KubeEdge Device/DeviceModel CRD와 다른 객체다. 이 변경은 KubeEdge CRD를 새로 정의하거나 Device CR을 자동 생성하지 않는다. 기존 KubeEdge Device는 프로젝트 정책대로 사전 등록 상태를 유지한다.

6. 임시 버퍼 정책

임시 버퍼는 프로세스 메모리가 아니라 node-local hostPath의 SQLite WAL database를 사용한다.

/var/lib/edge-telemetry-buffer/outbox.db

기본 정책:

  • 최대 보존 시간: 24시간
  • 최대 크기: 노드당 1GiB
  • 제거 기준: 보존 시간과 크기 중 먼저 한도에 도달한 조건 적용
  • 전송 순서: Device별 FIFO
  • 재시도: exponential backoff, 1초에서 시작해 최대 60초
  • 재연결 후 drain: live 수집을 막지 않도록 rate limit 적용
  • 한도 초과: 가장 오래된 record부터 제거하고 dropped counter 증가
  • Pod 재시작: hostPath SQLite를 다시 열어 미전송 record 재개
  • 잘못된 sensor payload: outbox에 넣지 않고 field 이름과 오류 code만 기록
  • 중앙의 schema 오류 또는 과대 payload: dead-letter table로 이동하고 다음 record 진행
  • 인증 실패: 전체 업로드를 중단하고 outbox를 유지한 채 degraded 상태로 재시도
  • UUID 충돌: 해당 record를 quarantine하고 critical 상태 발생

terminal record를 별도 table로 옮겨 한 record가 같은 Device의 전체 FIFO를 영구히 막지 않게 한다. dead-letter와 quarantine record는 자동 삭제하지 않고 운영자가 metadata와 오류 code를 확인한 후 처리한다. 로그와 metric에는 원본 telemetry를 노출하지 않는다.

버퍼는 장애 복구용이며 영구 telemetry store가 아니다. backlog가 70%를 넘거나 oldest age가 30분을 넘으면 degraded, 90% 또는 dropped/quarantined record 발생 시 critical로 관측한다. 초기 구현에서는 다음 값을 Prometheus metric과 agent health API로 제공한다.

  • edge_outbox_pending_records
  • edge_outbox_bytes
  • edge_outbox_oldest_age_seconds
  • edge_outbox_dropped_total
  • edge_outbox_rejected_total
  • edge_upload_errors_total

이 값은 raw telemetry처럼 DeviceStatus에 기록하지 않는다.

8. 네트워크와 보안 경계

edge agent는 테스트베드 LAN의 다음 단일 endpoint만 사용한다.

https://192.168.0.5:30443/v1/events

edgex-ingest-gateway는 server2에 고정 배치하고 externalTrafficPolicy: Local인 NodePort 30443으로 노출한다. 나머지 EdgeX API와 PostgreSQL은 ClusterIP다.

현재 PoC에 적용할 보안 기준은 다음과 같다.

  • gateway는 Kubernetes TLS Secret의 인증서로 HTTPS만 제공한다.
  • 서버 인증서의 subject alternative name에는 server2 InternalIP 192.168.0.5를 넣는다.
  • agent는 배포된 CA bundle로 서버 인증서를 검증하며 검증 해제를 허용하지 않는다.
  • sensor-gateway agent는 Kubernetes Secret에 저장된 공용 PoC bearer token을 사용한다.
  • 익명 요청, token 불일치, 허용되지 않은 device/profile/source는 거부한다.
  • gateway는 POST /v1/events만 외부에 제공하며 범용 Core Data reverse proxy로 동작하지

않는다.

  • 요청 크기, 동시 요청 수와 source subnet을 제한한다.
  • server2 host firewall은 sensor-gateway가 속한 테스트베드 대역에서 오는 30443만

허용한다. 이 규칙 적용과 외부 대역 차단 확인을 배포 검증에 포함한다.

  • 로그에 원본 telemetry, token, 인증서 key를 기록하지 않는다.
  • command endpoint와 actuator 실행은 이번 변경에 포함하지 않는다.

노드별 credential 또는 mTLS는 운영 전 필수 고도화 항목이지만 현재 PoC 범위에는 넣지 않는다. 따라서 이 단계에서 edge_node_id는 데이터 출처 tag이지 독립적으로 인증된 노드 신원이라고 설명하지 않는다.

12. 운영상 제약

  • server2와 모든 sensor-gateway EdgeCore 사이의 테스트베드 LAN 연결을 전제로 한다.
  • PostgreSQL local-path는 server2 장애에 대한 HA가 아니다.
  • 24시간/1GiB는 초기 기본값이며 실제 sensor rate 측정 후 조정한다.
  • 장기간 단절로 buffer 한도를 넘으면 oldest-drop이 발생하므로 무손실 장기 보관 구조가

아니다.

  • outbox 보호는 edge agent가 MQTT sample을 받은 시점부터 시작한다. 현재 QoS 0

publisher가 agent 또는 로컬 broker 중단 중 발행한 sample까지 복구하지는 않는다. 로컬 MQTT 구간의 무손실 처리는 publisher QoS 1, persistent session과 broker persistence를 함께 적용하는 별도 고도화 범위다.

  • 고대역폭 RTSP frame은 SQLite outbox나 Core Data Event에 넣지 않는다. RTSP는 별도

media buffer와 추론 event metadata 경로로 설계한다.

  • dashboard의 EdgeX 전환은 별도 작업이다. 이번 단계의 완료 기준은 MQTT 수직

슬라이스, 중앙 영구 저장과 장애 복구 검증까지다.

13. 검토한 대안

EdgeX 전체 스택을 모든 EdgeCore에 배치

각 노드가 독립적으로 동작하는 장점은 있지만 Keeper, Metadata, MessageBus, Core Data와 PostgreSQL까지 노드마다 운영해야 한다. 현재 PoC의 중앙 통합 저장 요구와 맞지 않아 선택하지 않는다.

edge agent에서 중앙 MQTT/Device MQTT로 전달

현재 수직 슬라이스를 가장 적게 바꾸는 방법이다. 그러나 QoS 1 PUBACK은 중앙 broker가 메시지를 받았다는 뜻일 뿐 Core Data의 PostgreSQL 저장을 보장하지 않는다. Core Data 장애 중 outbox를 안전하게 비울 수 없으므로 목표 구조로 선택하지 않는다.

Core Data API를 EdgeCore에 직접 노출

구현은 단순하지만 EdgeX Core API의 읽기·삭제 surface까지 센서망에 노출하기 쉽고, 인증·allowlist·중복 확인 책임이 agent마다 분산된다. 제한된 ingest gateway 한 곳에서 이 책임을 처리하는 방식을 선택한다.
