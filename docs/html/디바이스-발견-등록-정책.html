디바이스 발견·승인·등록 정책

목적

이 문서는 물리 장비가 노드에 연결된 순간부터 EdgeX 등록과 최초 telemetry 확인까지의 운영 절차와 권위 경계를 정의한다.

한 줄로 요약하면 다음과 같다.

/dev 전체를 무작정 뒤져 Device로 등록하지 않는다. 노드별 discovery agent가 제한된 하드웨어 증거를 수집해 후보로 보고하고, 정확한 binding·운영자 승인·EdgeX Metadata 등록·최초 Core Data Event 확인을 모두 통과해야 운영 Device로 인정한다.

권위 경계

발견 후보와 등록 Device는 서로 다른 집합이다.

단계 데이터 의미 권위
발견 전 Kubernetes Node, host 장치 파일 스캔할 노드와 접근 범위 Kubernetes/KubeEdge
발견 discovery report, candidate 장비가 연결됐을 가능성을 보여 주는 onboarding 증거 discovery/controller 운영 상태
승인·등록 Device Profile, Device Service, Device 관리 대상과 schema EdgeX Core Metadata
동작 확인 Event, Reading, origin 실제 데이터 수신과 freshness EdgeX Core Data
운영 판단 availability, reason Metadata 상태와 최신 Event의 결합 결과 state-aggregator 계산

Discovery candidate는 pre-onboarding 관찰값이다. candidate 수를 registered device 수로 세거나 physical inventory의 fallback으로 사용하지 않는다.

KubeEdge Device, DeviceModel, DeviceStatus, MapperFramework와 legacy mapper도 이 과정의 inventory 또는 fallback이 아니다.

전체 상태 흐름

물리 장비 연결
  -> 노드 discovery agent가 제한된 증거 수집
  -> candidate 생성/갱신
  -> stable identity와 catalog exact match 확인
  -> 운영자 승인
  -> Protocol Adapter / Device Service 준비
  -> EdgeX Core Metadata Profile·Device 등록
  -> 최초 Core Data Event 확인
  -> EVENT_CONFIRMED
  -> Metadata state + Event freshness로 availability 계산

주요 controller state:

state 의미 운영 해석
DETECTED 하드웨어 증거를 처음 관측 아직 등록 대상 아님
IDENTIFIED stable identity를 구성 binding 검토 가능
PENDING_APPROVAL 운영자 판단 대기 자동 등록 금지
APPROVED 운영자가 후보를 승인 이후 단계 실패 가능
SERVICE_READY 대응 Device Service가 준비됨 Event 수신 전
METADATA_REGISTERED Core Metadata 등록 확인 telemetry 확인 전
EVENT_CONFIRMED 최초 Core Data Event 확인 onboarding 완료
BLOCKED catalog, 권한 또는 정책 조건 불충족 원인 해소 전 진행 금지
REJECTED 운영자가 등록 대상에서 제외 inventory에 포함하지 않음
STALE stale 기준 동안 다시 관측되지 않음 분리·agent 장애·스캔 범위 확인
FAILED 등록 단계 실패 failureReason과 registrationStep 확인

decision=accepted는 EVENT_CONFIRMED와 같은 뜻이 아니다. 승인 후 Device Service 준비, Metadata 등록 또는 최초 Event timeout에서 실패할 수 있다.

프로토콜별 발견 기준

USB Serial

Serial discovery는 host의 /dev와 /sys를 읽어 다음 증거를 결합한다.

  • /dev/serial/by-id/... stable path
  • USB VID/PID
  • 제조사와 product 정보
  • 장비 serial number
  • 실제 kernel device 예: ttyACM0, ttyUSB0

Device Service에는 /dev/ttyACM0처럼 재부팅·재연결 때 바뀔 수 있는 번호보다 /dev/serial/by-id/... 경로를 binding한다. stable identity와 catalog가 정확히 일치하지 않으면 자동 승인하지 않는다.

현재 Serial discovery DaemonSet은 edge 노드의 host /dev와 /sys를 /host-dev, /host-sys에 read-only로 mount한다. non-root, read-only root filesystem, privilege escalation 금지와 capability drop을 적용한다.

I2C

I2C bus 파일이 있다는 사실만으로 센서가 있다고 판단하지 않는다. I2C는 USB처럼 장비 종류를 일반적으로 self-enumerate하지 않기 때문이다.

현재 Sense HAT 탐지는 다음 제한된 증거를 사용한다.

  • 허용된 /dev/i2c-1만 mount
  • allowlist에 정의된 identity register만 read-only로 확인
  • 응답 주소와 identity fingerprint가 기대값과 일치하는지 확인
  • catalog의 hardware binding과 exact match 확인

/dev/i2c-1 존재 또는 bus-wide 주소 스캔만으로 Device를 만들지 않는다. 화면에 남은 과거 bus-only candidate도 실제 센서 응답 증거로 해석하지 않는다.

현재 I2C discovery Pod는 char device 접근 때문에 privileged로 실행된다. 이는 테스트베드 예외이며 운영 승격 전 최소 device 권한, 별도 노드 제한, seccomp/AppArmor 또는 동등 통제를 검토한다.

네트워크·산업 프로토콜

MQTT, Modbus, OPC-UA, ONVIF, RTSP, REST 장비는 /dev 스캔 대상이 아니다. 명시적 endpoint, allowlist, credential, Device Profile과 프로토콜별 identity probe를 사용한다.

네트워크 주소가 열려 있다는 이유만으로 등록하지 않으며 광범위한 자동 포트 스캔도 기본 정책으로 두지 않는다.

현재 테스트베드 구성값

2026-07-30 live 조회 기준:

항목 값
Serial scan interval 30초
I2C scan interval 30초
candidate stale 기준 90초
controller reconcile interval 10초
등록 후 최초 Event timeout 60초
dashboard Event freshness 기본값 90초
discovery report 인증 controller 내부 HMAC
자동 runtime mutation 테스트베드에서 활성
운영자 승인 인증 development-mock

development-mock 인증과 runtime mutation 활성 상태는 실공장 운영 보안 기준이 아니다. 외부 운영자 인증·인가, 감사 로그, 승인 권한 분리와 rollback 절차를 붙이기 전에는 테스트베드 범위로만 사용한다.

연결 해제와 재연결

장비가 빠졌을 때 candidate나 EdgeX Device를 즉시 삭제하지 않는다.

  1. discovery report가 90초 동안 갱신되지 않으면 candidate presence=stale, state=STALE로 전환한다.
  2. Core Data Event가 freshness 기준을 넘으면 등록 Device는 degraded가 된다.
  3. stable identity가 같은 장비가 다시 나타나면 기존 candidate를 갱신하고 registration state를 재조정한다.
  4. Metadata Device 자동 삭제는 하지 않는다.
  5. 명시적 decommission은 영향 범위와 소유 리소스를 확인한 운영자 변경 작업으로 수행한다.

이 방식은 케이블 접촉 불량이나 짧은 재부팅 때문에 inventory가 사라지는 일을 막는다. 반대로 오래된 candidate가 화면에 남을 수 있으므로 present와 stale, decision, registrationStep을 함께 본다.

Dashboard와 API 해석

발견 후보:

GET /management/discovery

주요 필드:

  • node: nodeName, agentId, lastReportAt, presence, candidateCount, scanErrors
  • candidate identity: candidateId, protocol, devicePath, hardwareId, properties, evidence
  • matching: recommendedProfile, matchConfidence, matchedAdapterId, matchedHardwareBindingId
  • decision: decision, decisionNote, authState
  • lifecycle: state, registrationStep, failureReason, retryCount
  • recency: presence, firstSeen, lastSeen, updatedAt
  • readiness: packageState, packageReason, registrationReady

등록 이후 권위 상태:

GET /state/devices
GET /state/devices/{device_id}/telemetry

화면에서 다음 수를 섞지 않는다.

  • discovery candidate 수
  • present candidate 수
  • EVENT_CONFIRMED candidate 수
  • Core Metadata registered Device 수
  • fresh Event를 가진 available Device 수

2026-07-30 live evidence

이 절은 특정 시점의 관찰 기록이며 장기 계약이나 재배포 가능성의 근거가 아니다.

  • edge node 3대의 Serial discovery agent가 online이고 scan error가 없었다.
  • etri-dev0003-raspi5의 I2C discovery agent가 online이었다.
  • Jetson Arduino USB Serial 후보는 stable by-id path, exact catalog match, 운영자 승인, Metadata 등록과 최초 Event 확인을 거쳐 EVENT_CONFIRMED였다.
  • Raspberry Pi Sense HAT 후보는 allowlist identity register 4개와 exact binding을 거쳐 EVENT_CONFIRMED였다.
  • Raspberry Pi의 별도 USB Serial 후보는 승인됐지만 최초 Event timeout 이후 장치가 보이지 않아 STALE이었다.
  • /management/discovery에는 총 14개 후보가 있었고 이 중 present·EVENT_CONFIRMED 후보는 2개였다. 나머지는 과거 scan의 stale 후보였다.
  • /state/devices에는 13개 EdgeX Device가 있었고 조회 순간 모두 fresh/available이었다. 하나의 Arduino 또는 Sense HAT 물리 장비가 여러 논리 resource Device로 표현되므로 candidate 수와 Device 수는 일치하지 않는다.

목표 아키텍처와 live 배포의 차이

프로젝트의 목표 telemetry 경로는 Protocol Adapter가 canonical Event를 edge-telemetry-agent의 SQLite outbox에 먼저 commit하고 HTTPS gateway의 persisted ACK 뒤에 삭제하는 구조다.

2026-07-30 live Device Service 두 개의 배포 설정은 중앙 edgex-messagebus와 edgex-core-metadata에 직접 연결되며, edgex-edge에는 controller state PVC 외에 Device Service outbox PVC가 보이지 않았다. 따라서 현재 live evidence로 주장할 수 있는 것은 다음까지다.

  • Serial/I2C 하드웨어 발견
  • exact binding과 운영자 승인
  • Device Service 실행
  • EdgeX Metadata 등록
  • Core Data Event와 dashboard freshness

다음은 별도 증거가 필요하다.

  • 각 live Device Service Event가 SQLite outbox에 먼저 commit됨
  • 중앙 장애 동안 lossless 보존됨
  • HTTPS ingest gateway의 persisted ACK 뒤에만 삭제됨

중앙 MessageBus 직접 연결을 목표 durable telemetry 경로의 동등한 구현이나 fallback으로 간주하지 않는다. 다음 배포 정합화 작업에서 Device Service 출력이 edge-telemetry-agent 계약을 따르도록 맞추거나, 범위를 변경하려면 먼저 프로젝트-범위.md와 관련 설계 문서를 승인해 수정한다.

저장소 재현성 상태

현재 checkout:

항목 값
branch agent/edgex-central-docs
commit fa3b49dd31d84f91f2875277d2ae1d4765a69702
root path edgex/k8s

현재 checkout의 root Kustomize render에는 live의 discovery DaemonSet, adapter controller, device-serial-jetson, device-sensehat-raspi가 없다.

live Argo CD:

항목 값
Application edgex-telemetry
repository https://github.com/dsa04156/edge-ai-workspace.git
path edgex/k8s
revision 8ece29189f2956489d5f3018ffc72e3f8bde062c
observed status Synced/Healthy

따라서 현재 checkout에서 kubectl apply -k edgex/k8s를 실행해 live discovery 구성을 재현하거나 갱신하면 안 된다. 먼저 live revision의 source와 현재 branch의 의도된 변경을 비교·통합하고 root render, Secret, PVC, RBAC, security context와 rollback을 검증한다.

운영 점검 명령

읽기 전용 점검:

kubectl -n edgex-edge get daemonset,deploy,pod,pvc -o wide

kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/management/discovery'

kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/devices'

후보 승인, reject, retry, manual candidate 생성, runtime restart와 decommission은 상태를 변경한다. 대시보드/API에서 실행하기 전에 candidate identity, exact binding, 영향 Device, 현재 인증 모드와 rollback을 확인한다.

운영 승격 체크리스트

  • [ ] stable hardware identity가 있고 재연결 후에도 같은 candidate로 귀속된다.
  • [ ] catalog match가 exact이며 ambiguous/partial 후보를 자동 승인하지 않는다.
  • [ ] 운영자 인증이 development-mock이 아니다.
  • [ ] discovery report와 승인·등록 변경이 감사 가능하다.
  • [ ] Device Service는 필요한 char device만 mount한다.
  • [ ] I2C privileged 예외를 최소화하거나 대체 통제를 적용한다.
  • [ ] Profile, parser, image digest와 hardware binding이 함께 고정된다.
  • [ ] Metadata 등록 뒤 실제 Core Data Event를 확인한다.
  • [ ] 분리 시 candidate stale와 Event freshness 저하를 각각 확인한다.
  • [ ] 목표 SQLite outbox·HTTPS persisted-ACK 경로의 장애 보존을 같은 배포에서 검증한다.
  • [ ] 현재 checkout의 root render가 live revision을 재현한다.
