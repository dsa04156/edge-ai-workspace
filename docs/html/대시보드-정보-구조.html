대시보드 정보 구조

목적

이 문서는 엣지 AI 서버, 현장 엣지 노드, 논리 자원과 EdgeX 센서 endpoint를 구분하는 운영 dashboard 정보 구조를 정의한다. 센서 디바이스는 EdgeX를 유일한 상태 권위로 사용하고, Dashboard는 Core Metadata의 등록·연결 상태와 Core Data event freshness를 함께 보여 주어 운영자가 점검 대상을 빠르게 좁히도록 돕는다.

physical device -> EdgeX Device Service -> Core Data -> AI services / storage / dashboard

2026-07-30 live Core Metadata에는 Jetson의 기존 resource별 Device 6개, 승인 Saga로 추가된 Arduino aggregate Device 1개, Sense HAT Device 6개로 총 13개 EdgeX Device가 있다. 디바이스 화면의 센서 디바이스 분류는 이 13개 identity를 한 행씩 표시하고, 장비 관리 화면만 physicalDeviceId와 승인 hardware binding을 사용해 arduino-001, sensehat-001 두 물리 장비 카드로 묶는다. 관리 카드 상세에서는 개별 Device 이름과 수정·삭제 동작을 확인할 수 있다. 별도 Discovery Agent의 onboarding 후보는 이 inventory에 합치지 않는다. 아래 payload는 Arduino 온도 Device의 API schema 예시이며 실제 판정은 live API 시각과 값을 다시 조회한다.

정보 구조 원칙

  1. 센서 디바이스 inventory는 EdgeX Core Metadata Device만 사용한다.
  2. 연결 상태는 Device Service, adminState, operatingState, connection_state로 설명한다.
  3. 데이터 최신성은 EdgeX Core Data의 최신 event timestamp로 판단한다.
  4. latest_readings는 최신 event에 포함된 reading이며, 저장 이력 그래프와 구분한다.
  5. 저장 이력 그래프는 state-aggregator → EdgeX Core Data API → PostgreSQL 경로를 사용하고 dashboard가 DB에 직접 연결하지 않는다.
  6. Kubernetes node와 workload 상태는 엣지 AI 서버와 물리 디바이스 분류의

관측 근거다. 센서 디바이스 availability의 선행조건이나 권위는 아니다.

  1. Service binding은 orchestration이 아니라 EdgeX device data가 AI 서비스, 저장소, dashboard consumer로 전달되는 관계다.
  2. 디바이스 관리는 노드를 먼저 선택해 등록 물리 연결·Runtime·protocol package·EdgeX Device를 같은 운영 범위로 좁힌다. node_type=edge_* 노드와 Runtime·Device·등록 binding이 실제로 참조하는 노드만 관리 카드에 표시하고, 관계없는 중앙 cloud_server 노드는 제외한다. 이 노드 필터는 탐색·배치 범위이며 EdgeX 상태 판정을 덮어쓰지 않는다.
  3. 기본 등록 현황의 연결 대기 영역은 onboarding 후보를 다룬다. USB Serial stable identity와 allowlist I2C chip identity는 노드별 Discovery Plan에 따라 읽는다. MQTT 자기등록 subscriber와 Modbus/OPC-UA/ONVIF network scan은 구현하지 않았다. MQTT broker 연결은 자동 후보가 아니라 장비 연결의 검증된 network package에서 운영자가 선언한다. 후보 목록을 Core Metadata inventory에 합치지 않는다.
  4. 후보 presence, 명시적 state, authState, Catalog packageState를 서로 분리한다. pending·accepted·ignored decision은 기존 Dashboard BFF 하위 호환 표현이다.
  5. binding-required·verification-required로 차단된 후보에는 연결 설정 액션을

표시한다. 이 액션은 node와 protocol 문맥을 등록 화면으로 넘기고 차단 사유를 보여 줄 뿐, exact Git binding이 없는 장비를 승인하거나 임의 Runtime으로 배포하지 않는다.

  1. 후보 승인은 exact Catalog match와 presence를 재검증한 뒤 외부 인증, 검증 Runtime, Metadata readback과 첫 Event를 순서대로 실행한다. 첫 Event 확인 전에는 등록 완료로 표시하지 않는다.
  2. 노드 현황은 연결 등록, 실제 장비 관측, Device Service 통신과 Core Data 최신성을 네 상태로 분리한다. Git binding이나 발견 후보만으로 물리 장비가 통신 중이라고 추정하지 않는다.
  3. 관리 화면은 노드 선택을 공통 범위로 유지한다. 기본 등록 현황에는 등록 장비, 디바이스 프로필, 연결 대기, 수집 서비스를 순서대로 표시하고, 장비 연결과 기존 디바이스 수정만 별도 화면으로 전환한다. 등록 입력은 4단계 중 현재 단계만 표시한다. 1단계에서는 protocol package, 노드, 등록 연결과 protocol별 Runtime/Device 설정을 입력한다. Runtime mode는 auto로 고정해 기존 service 재사용 또는 검증 template 배포를 서버가 결정한다.
  4. protocol package는 재사용 가능, 설치 가능, 연결 등록 필요, 검증 필요를 구분한다. 검증된 template과 exact 또는 제한된 network binding이 없으면 설치할 수 없고 raw path 직접 입력이나 미검증 Adapter 활성화로 이어지지 않는다. MQTT 개발 package는 broker scheme/host/CIDR/port, topic과 QoS를 서버에서 다시 검증한다.
  5. Device Profile은 대시보드 BFF에서 목록 조회, mutation 없는 검증, idempotent 생성을

제공한다. 웹에서 생성한 Profile은 등록 현황에 즉시 표시하고, 전체 Profile은 장비 연결 단계의 선택 목록에 넣는다. 웹 생성 Profile은 읽기 전용 DeviceResource만 허용하며 command, parser, Device Service image와 hardware binding을 함께 만들지 않는다. 후보 capability는 편집 초안일 뿐 value type·units의 자동 추론 근거가 아니다. 검증 protocol package가 bundled Profile을 제공하면 연결할 때 자동으로 생성/readback하고 기존 동일 Profile은 재사용한다.

  1. 대시보드 전체에 간편 보기와 전체 보기를 따로 두지 않는다. 운영 현황에는

엣지 AI 서버, 물리 디바이스, 가상 디바이스, 센서 디바이스의 수와 상태, 현재 서버·물리 디바이스 자원 관측과 조치 항목을 먼저 표시한다. 두 패널은 /state/dashboard의 node snapshot을 node_type으로 분리해 평균 CPU·메모리, GPU 관측 대수, pressure 주의 대수와 노드별 현재 meter를 만든다. 누락 metric은 N/A로 표시하고 과거 시계열을 추정하지 않는다. 고정 서비스 데모는 접힌 보조 영역으로 둔다. 플랫폼 기술 지표와 서비스 연결 구조는 필요할 때만 펼친다.

  1. 디바이스 메뉴는 네 분류 모두 반복 카드가 아니라 이름·상태·최신 관측 또는

Event·상세보기의 목록을 사용한다. 센서 Profile, Device Service, protocol, 상태 근거와 저장 이력, 노드 자원 관측값과 가상 자원 상태는 선택 행의 상세 패널에서 확인한다.

  1. 375px, 768px, 1024px viewport에서 문서 전체의 가로 overflow와 잘린 텍스트가 없어야

한다. 표·캔버스처럼 내부 스크롤이 필요한 요소만 자체 scroll container를 사용한다.

  1. 화면 분류의 권위는 다음과 같다.
  • 엣지 AI 서버: /state/nodes에서 node_type=cloud_server|server
  • 물리 디바이스: /state/nodes의 나머지 Jetson·Raspberry Pi 엣지 노드
  • 가상 디바이스: /state/virtual-resources의 자원증강형 논리 자원
  • 센서 디바이스: /state/devices의 EdgeX Core Metadata Device
  1. 서비스 설계는 /state/devices와 /state/device-profiles의 실제 EdgeX

Device/DeviceResource를 입력으로 사용한다. 왼쪽의 검색 가능한 서비스 카탈로그는 EdgeX 입력 2종, 전처리 4종, 추론 2종과 결과 1종을 보여 주며 실제 입력 가능 수와 설계용 계약을 구분한다. 브라우저 localStorage 초안, 단계·포트, 타입·DAG·node 배치 validation과 dry-run 계획만 제공하고 운영 상태 판정, Kubernetes/EdgeX mutation과 실제 workload 실행에는 참여하지 않는다.

Telemetry freshness 시계는 EdgeX Core Data latest Event의 nanosecond origin sample 시각이다. API 조회 시각이나 Kubernetes 상태로 대체하지 않는다.

주요 API

API 역할
GET /state/dashboard device, node diagnostics, summary, KPI를 포함한 dashboard 전체 상태
GET /state/devices EdgeX 기반 센서 디바이스 상태 목록
GET /state/device-profiles 서비스 설계용 Device Profile/DeviceResource 읽기 전용 계약. resource protocol attributes 제외
GET /state/devices/{device_id}/telemetry?window=-30m&limit=1000 해당 EdgeX device의 Core Data Event/Reading history. window은 음수 duration, limit은 최대 1,000 Event
GET /state/nodes 엣지 AI 서버와 물리 디바이스의 Kubernetes/KubeEdge 관측
GET /state/virtual-resources 자원증강형 가상 디바이스의 읽기 전용 상태
GET /state/summary 운영 상태 요약
GET /metrics Prometheus scrape metric
GET /management/adapters Adapter Catalog, Device Service 상태와 전역 mutationEnabled 조회

운영자 해석 순서

  1. source=edgex와 registered_device_count로 관리 범위를 확인한다.
  2. profile, Device Service, protocol이 의도한 바인딩인지 본다.
  3. admin/operating/connection 상태를 확인한다.
  4. latest_event_timestamp와 telemetry_freshness를 본다.
  5. latest_readings의 source/resource/value를 확인한다.
  6. Device를 선택해 저장 이력의 요청 범위, 반환 Reading 수, 실제 구간과 resource별 series를 확인한다.
  7. 새 장비를 다룰 때 디바이스 관리에서 대상 KubeEdge 노드를 먼저 선택한다. 기본 등록 현황의 연결 대기에서 node report online/stale, 후보의 presence·상태·인증·Catalog match를 확인한다. USB Serial은 stable identity와 선택적 Manifest로, I2C는 Plan의 bus/address 및 read-only chip ID 규칙으로 후보를 식별한다. 네트워크 protocol은 기본 비활성화하며 임의 CIDR scan을 하지 않는다. 후보는 운영자 승인과 외부 인증, Runtime/Profile/Device 검증, 첫 Event 확인을 모두 통과해야 등록 완료가 된다.
  8. 등록 현황의 물리 장비 카드를 선택해 등록 연결과 실제 장비 상태의 네 증거, Runtime,

protocol package와 개별 EdgeX Device를 펼쳐 확인한다. 장비 연결 1단계는 protocol/Device Service를 먼저 고르고, 그 결과에 종속된 등록 hardware binding과 protocol별 Runtime/Device 설정을 입력한다. target node와 binding의 Port/Bus/DeviceID 값은 직접 입력하지 않는다. auto plan이 기존 runtime을 재사용하는지, 검증된 빈 binding에 새 runtime을 배포하는지, 또는 차단 이유가 무엇인지 마지막 단계에서 확인한다. 검증하고 연결이 통합 validation을 먼저 수행하고 유효할 때만 요청별 idempotency key로 연결하고 runtime, Metadata readback과 first Event 상태를 구분해 본다. 기존 Device는 펼친 개별 Device 행의 수정 동작으로 들어가 allowlist 필드만 변경한다.

디바이스 관리는 browser 관리자 token과 Authorization header를 사용하지 않는다. 외부/Argo runtime의 restart/retire 버튼은 비활성화하고, Controller 소유 runtime만 관리한다. 브라우저는 raw manifest, image, hostPath 또는 Kubernetes credential을 전달하지 않는다. Profile/Device 강제 삭제, command publish, actuator control, EdgeMesh와 KubeEdge Device CRD 변경은 제공하지 않는다. 과거 AI Pipeline/Workflow Builder와 전용 샘플 미리보기 API는 제거했다. 현재 메뉴는 운영 현황, 디바이스, 장비 관리, 서비스 설계 네 화면이다. 서비스 설계는 EdgeX read-only 계약의 browser-local validation·dry-run이고 실제 edge consumer는 같은 노드의 Device Service Local Data API를 직접 사용한다. 미검증 Adapter는 protocol 선택 목록과 접힌 현황 영역에서 상태를 확인할 수 있지만 비활성화된다. MQTT는 개발용 검증 package 범위에서만 활성화되고 운영 TLS/auth broker나 임의 payload를 지원한다고 표시하지 않는다. idempotency key와 기존 Device의 protocol properties JSON은 고급 영역을 열었을 때만 표시한다. 이 progressive disclosure는 표시 밀도를 줄이기 위한 UI 규칙이며 API 검증과 권한 경계를 완화하지 않는다. 현재 BFF 자체에는 운영자 인증·인가가 없으며 Idempotency-Key와 내부 HMAC도 사용자 인증 수단이 아니다. 따라서 이 mutation 경로는 접근이 제한된 개발 테스트베드에서만 사용하고, 운영 노출 전 Ingress 앞의 별도 인증·인가 계층을 추가한다. 웹 Profile 생성도 같은 경계를 따른다. 서버가 edge-ai-web-managed label을 추가하고 Core Metadata readback을 확인하지만, 이 label은 검증된 parser/image/binding의 대체 증거가 아니다. 발견 후보의 비밀번호·token·URL userinfo는 서버에서 거부한다. 발견 목록과 상태 이력은 Adapter Controller의 SQLite Registry에 영속 저장하는 onboarding staging 자료이며 Core Metadata Device 수, availability와 physical-device KPI 분모에 넣지 않는다. 기존 edgex-device-discovery-registry ConfigMap이 있으면 최초 기동 때 한 번만 migration 입력으로 읽고 이후 권위 저장소로 사용하지 않는다. Adapter가 installed여도 현재 endpoint/resource route를 다른 Device가 소유하면 새 등록은 protocol_binding_exists다. edgeAiOnboarding*, nodeName, physicalDeviceId는 system tag로 보고 사용자 PATCH에서 변경하지 않는다. 새 connection으로 생성한 Device의 hardwareBindingId도 system tag이며 같은 규칙을 적용한다.

현재 cutover 범위

기존 loopback Agent/SQLite/HTTPS edge 경로와 aggregate sensehat-001 bootstrap은 퇴역했다. 두 Device Service의 10분·10,000 sample 메모리 cache는 로컬 Workflow 입력용이며 재시작하면 사라진다. dashboard는 이 로컬 cache나 과거 Core Data record로 현재 연결을 보정하지 않고, 계속 Core Metadata와 최신 Core Data Event origin으로 상태와 freshness를 판단한다. Serial 6개와 I2C 6개 가상 Device의 Metadata, 계약된 Reading Event와 freshness를 각각 확인하고 실제 케이블/보드 분리·복구 검증은 별도 PASS 항목으로 남긴다.
