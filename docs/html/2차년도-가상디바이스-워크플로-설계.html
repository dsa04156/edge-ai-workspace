2차년도 가상디바이스·디바이스트윈·워크플로 설계

목적과 적용 경계

이 문서는 2차년도 협약 방향에 맞춘 확장 설계다. 기준 문서는 docs/(2차년도협약용) 연구개발계획서-엣지 컴퓨팅 시스템을 위한 대규모 혼합 디바이스 제어·관리 플랫폼 개발_0415.pdf다.

현재 PoC에서 가상 Device inventory, state, telemetry, command 권위는 EdgeX로 단일화한다. KubeEdge DeviceModel/Device/DeviceStatus, mqttvirtual, MapperFramework와 mapper direct-to-storage 실험은 legacy/reference 경로이며 현재 status/control plane, 병행 plane 또는 EdgeX fallback이 아니다. KubeEdge/Kubernetes node와 workload 정보는 placement/resource 진단에는 사용할 수 있다.

2026-07-21 현재 중앙 EdgeX는 유지되고 custom edge Agent/SQLite outbox 배포와 aggregate sensehat-001 bootstrap은 퇴역했다. 공식 EdgeX Device SDK 기반 서비스가 Jetson Arduino Serial과 Raspberry Pi Sense HAT I2C source를 각각 한 번 읽고 기능별 가상 Device 6개씩, 총 12개로 분리한다. 물리 arduino-001, sensehat-001은 protocol/tag source ID일 뿐 Core Metadata Device가 아니다. Agent 관련 예시는 과거 baseline을 설명하는 설계 이력이며 현재 배포 계약이 아니다.

핵심 정의

용어 정의 현재 PoC와의 관계
물리 온디바이스 Jetson, Raspberry Pi, 센서, 액추에이터, 카메라처럼 현장에 존재하는 장비 EdgeX Device Service가 endpoint를 연결하며 physical ID와 endpoint는 protocol/tag metadata로 유지
가상디바이스 물리 온디바이스의 기능, 상태, 자원, 입출력을 소프트웨어 identity로 표현한 대상 현재 Arduino Serial 6개와 Sense HAT I2C 6개가 EdgeX Device/Profile로 구현; 범용 별도 registry는 후속 범위
디바이스트윈 physical/virtual device의 capability, resource, I/O, binding을 담는 관리 snapshot EdgeX 원본을 참조하는 후속 모델이며 별도 physical authority가 아님
AI 서비스 워크플로우 collect, preprocess, inference, postprocess, event, dashboard sink stage를 구성하고 source/resource 후보를 연결하는 구조 dashboard의 현재 builder는 browser-local dry-run/preview 범위
Input source workflow stage가 읽는 데이터 입력 단위 현재 physical source는 EdgeX Core Metadata Device와 Core Data Event/Reading을 기준으로 노출

test_device.py가 MQTT 가짜 값을 만들고 mqttvirtual/MapperFramework/DeviceStatus로 전달하는 방식은 legacy test일 뿐 가상디바이스의 본류가 아니다. 2차년도 가상디바이스는 "가짜 센서 publisher"가 아니라 물리 온디바이스와 매핑되는 소프트웨어 관리 인스턴스로 설계한다.

현재와 목표 구조

Physical On-Device Layer
  Jetson / Raspberry Pi / sensor / actuator / camera
  -> protocol-specific EdgeX Device Service (shared physical connection)
  -> EdgeX SDK async Event -> central internal MessageBus

Virtual Device Authority
  EdgeX Core Metadata Device/Profile inventory/state
  -> Core Data Event/Reading -> PostgreSQL

Consumers
  AI services / storage / state-aggregator / dashboard
  -> Core Metadata fields and Core Data event origin/typed readings

Node and Workload Diagnostics
  Kubernetes / KubeEdge node, pod, resource metrics
  -> optional placement/resource diagnostics only

Future Virtual Device and Workflow Layer
  Virtual Device Registry / Twin Engine / Workflow Runtime
  -> EdgeX physical references plus Kubernetes resource candidates
  -> does not replace or duplicate EdgeX physical authority

PostgreSQL persists Core Data Event/Reading. 현재 Serial/I2C Device Service에는 각각 10분·10,000 sample memory recent cache와 Local Data API가 있지만 edge SQLite outbox나 offline replay는 없다. A mapper direct-to-storage path is not current telemetry authority. Physical freshness is calculated from the latest valid Core Data Event origin, not from query time, Kubernetes heartbeat, or legacy DeviceStatus timestamps.

현재 PoC Workflow Source 모델

현재 workflow builder는 별도 Virtual Device Registry를 만들지 않는다. state-aggregator가 EdgeX Core Metadata Device와 Core Data latest Event freshness를 결합한 read-only source view를 제공하며, Kubernetes node/workload 정보는 별도 placement 진단으로만 결합한다.

현재 physical source API 표현은 EdgeX 필드를 보존한다.

name: virtual-temperature-001
profileName: etri-arduino-temperature
serviceName: device-serial-jetson
protocols:
  serial:
    Port: /dev/arduino-001
    BaudRate: "115200"
    DeviceID: arduino-001
    ResourceName: temperature
tags:
  physicalDeviceId: arduino-001
  nodeName: etri-dev0001-jetorn
adminState: UNLOCKED
operatingState: UP
latestEvent:
  deviceName: virtual-temperature-001
  sourceName: temperature
  origin: 1784016000000000000
  readings:
    - resourceName: temperature
      valueType: Int32
      value: "283"

현재 최소 API 표면은 state-aggregator의 read-only GET API다.

API 역할
GET /state/devices Core Metadata Device inventory/state와 Core Data latest Event freshness 조회
GET /state/devices/{device_id}/telemetry 해당 EdgeX deviceName의 Core Data 기반 window Event/Reading 조회
GET /state/nodes AI HAT 등 placement/resource 진단에 필요한 Kubernetes node 상태 조회

GET /state/nodes 결과는 physical device availability gate가 아니다. GET /state/devices의 availability는 EdgeX adminState, operatingState, latest Event origin만으로 계산한다.

물리 환경 예시는 다음처럼 구분한다.

노드 장착 장치 현재 사용 범위
etri-dev0001-jetorn Arduino Uno device-serial-jetson의 공유 physical input, EdgeX 가상 Device 6개로 fan-out
etri-dev0002-raspi5 AI HAT lightweight inference/resource placement 후보 진단
etri-dev0003-raspi5 Sense HAT v1 device-sensehat-raspi의 직접 /dev/i2c-1 input, 환경/IMU 가상 Device 6개로 fan-out

디바이스트윈 모델

후속 Twin Engine은 raw telemetry stream 전체를 저장하거나 physical state authority를 재정의하지 않는다. EdgeX Device를 physical_ref로 참조하고 workflow가 필요한 derived snapshot과 binding 상태만 관리한다.

영역 필드 예시 권위/출처
물리 참조 physical_ref, profileName, serviceName EdgeX Core Metadata
물리 상태 adminState, operatingState, event_origin, freshness EdgeX Core Metadata/Core Data에서 읽은 값
capability inputs, outputs, operations, supported_models Device Profile 및 virtual-device schema
자원 cpu_class, memory_class, accelerator, resource_profile Kubernetes/Prometheus 진단
입출력 telemetry_sources, command_endpoints, result_outputs EdgeX resource/command reference
workflow binding bound_workflow, bound_stage, binding_state future workflow registry/runtime
오류 last_error_code, last_error_message, recovery_hint 각 소유 서비스의 명시적 오류

제외 항목:

  • 고빈도 raw temperature/humidity/vibration/gyro stream 전체
  • 이미지 frame 또는 waveform 원본
  • 모든 Event/Reading의 복제본
  • Kubernetes/KubeEdge 상태로 추정한 physical availability
  • legacy DeviceStatus summary 또는 mapper freshness

워크플로우와의 관계

AI 서비스 workflow는 EdgeX 등록 Device를 source로, Kubernetes node resource를 실행 위치 후보로 사용할 수 있다.

AI Service Workflow preview
  source stage
    -> /state/devices/{device_id}/telemetry
  preprocess stage
    -> feature extraction
  inference stage
    -> anomaly model
  event stage
    -> alert/event output
  dashboard sink
    -> operator view

현재 dashboard workflow UI의 동작 범위는 브라우저 상태 안의 stage 구성, source/resource bind/release dry-run, validation, execution plan preview다. Kubernetes apply/delete/restart, EdgeX metadata/state mutation, Device Service command, actuator command, runtime migration/offloading을 실행하지 않는다.

후속 구현에서 검토할 항목은 다음과 같다.

  • virtual-device instance를 workflow stage에 bind하는 registry 계약
  • EdgeX input source를 stage 입력으로 참조하는 방법
  • stage를 실행할 node/container 후보와 자원 요구량
  • stale/error 상태의 validation 및 명시적 operator 승인 정책

이를 현재 동적 orchestration 또는 자동 failover 완성 기능으로 표현하지 않는다.

30개 가상디바이스 해석

2차년도 목표의 "30개"는 가짜 센서 30개를 MQTT로 만들었거나 30개 physical protocol cutover가 끝났다는 뜻이 아니다. 향후 물리 장비, sensor capability, EdgeX resource, resource profile, service I/O를 조합한 virtual-device instance로 정의하고 각각 검증해야 한다.

분류 예시 설명
센서 capability 단위 humidity, pressure, gyro, orientation 한 장비의 여러 I/O capability를 논리적으로 구분
물리 디바이스 단위 Jetson sensor bundle, Raspberry Pi bundle EdgeX physical reference 아래 여러 resource를 묶는 후보
자원 profile 단위 Jetson GPU-lite, Raspberry Pi AI HAT, x86 GPU server Kubernetes placement/resource 판단에 쓰는 표현
서비스 I/O 단위 anomaly input, environment input, actuator state workflow stage가 참조할 수 있는 입력/출력 계약

개수 산정에는 registry instance, physical reference, profile/resource 계약과 검증 상태를 함께 명시한다.

현재 재사용 경계

기존 구성 재사용 방식
EdgeX Core Metadata physical inventory/state authority
EdgeX Core Data/PostgreSQL physical Event/Reading persistence와 telemetry authority
Device Service recent cache 같은 edge node Workflow Pod의 latest/짧은 window 조회; 재시작 비보존
edge SQLite outbox 현재 배포 없음; 필요성이 생기면 recent cache와 분리해 별도 설계
state-aggregator EdgeX-backed device/state/freshness read model과 API
dashboard UI 운영 가시화 및 browser-local workflow preview
Prometheus/Kubernetes node/workload resource와 placement 진단
KubeEdge Device manifests/MapperFramework migration 비교와 legacy test reference만 허용

후속 설계 항목

구성 역할 현재 상태
Virtual Device Registry EdgeX physical ref, capability, resource, I/O schema 관리 future design
Virtual Device Runtime 범용 virtual instance API와 lifecycle Serial/I2C slice의 Local Data API만 구현, 범용 lifecycle은 future design
Twin Engine EdgeX 참조 기반 derived snapshot과 binding 상태 future design
Workflow Builder stage 구성과 virtual-device 연결 browser-local preview만 전달
Workflow Runtime stage 실행, I/O handoff, lifecycle, 장애 처리 future design
Orchestration Policy resource/twin 상태 기반 bind/rebind/placement 판단 future design

virtual-device/의 Serial JSON runtime은 이 목록과 독립적으로 보존되는 프로토타입이다. 이것을 EdgeX Serial Device Service, EdgeX Core Metadata/Core Data 연동 완료, 또는 Serial migration wave 완료로 설명하지 않는다. 향후 결합하려면 Serial Device Service/Profile, 실제 endpoint, typed Reading, state/freshness, command/failure, downstream consumer와 live cutover를 별도로 검증해야 한다.

단계별 진행안

1단계: EdgeX 등록 Device 기반 source pool

현재 전달 범위:

  • state-aggregator의 EdgeX-backed GET /state/devices
  • state-aggregator의 EdgeX-backed GET /state/devices/{device_id}/telemetry
  • dashboard의 source 조회와 browser-local workflow preview
  • Jetson physical arduino-001 공유 Serial reader와 6개 가상 Device 수집·저장·dashboard 수직 슬라이스
  • Raspberry Pi physical sensehat-001 직접 I2C reader와 환경/IMU 6개 가상 Device 수집·저장·dashboard 수직 슬라이스
  • 필요성이 검증된 MQTT-only 장비용 별도 adapter 후보(현재 workload 없음)

live deployment/cutover 여부는 배포 환경에서 별도로 확인한다.

2단계: protocol migration waves

Serial/I2C의 남은 물리 분리·복구 검증과 Modbus, OPC-UA, RTSP workflow별로 다음 gate를 독립적으로 통과한다. Sense HAT I2C 정상 경로 성공을 다른 I2C 장비·주소의 지원 근거로 확장하지 않는다.

  • EdgeX Device Service와 Device Profile 선택/구현
  • 실제 endpoint 독점 연결
  • normalization과 typed Reading 검증
  • 중앙 단절 시 실패 동작 검증; offline buffer가 요구되면 별도 durable replay 계약 검증
  • Core Metadata state와 Core Data Event freshness 검증
  • 지원 command와 실패 동작 검증
  • AI services/storage/dashboard consumer 검증
  • live deployment cutover 확인

3단계: virtual-device/twin contracts

  • EdgeX physical_ref와 capability/I/O schema 정의
  • derived snapshot의 소유권과 refresh 규칙 정의
  • raw Event/Reading을 복제하지 않는 storage 경계 정의

4단계: workflow builder 확장

  • stage input/output type과 validation rule 정의
  • registry-backed bind/release 계약 정의
  • 실행 권한과 operator 승인 경계 정의

5단계: runtime/orchestration

  • workflow runtime과 container lifecycle 연계
  • resource 기반 placement 후보 계산
  • stale/error 처리와 명시적 retry/rebind 정책 검증
  • 결과와 이벤트의 EdgeX/consumer 경계 확정

각 단계는 구현과 검증이 완료된 뒤에만 current 기능으로 승격한다.

표현 원칙

사용할 표현:

  • EdgeX 기반 physical inventory/state/telemetry
  • 물리·가상 디바이스 연계 설계
  • 가상디바이스 인스턴스
  • AI 서비스 workflow preview
  • node/workload placement 진단
  • 단계별 protocol migration

피할 표현:

  • KubeEdge DeviceStatus가 current physical status/control plane이라는 표현
  • MapperFramework 또는 storage가 EdgeX의 병행/fallback authority라는 표현
  • virtual-device/ Serial JSON prototype이 EdgeX Serial Device Service라는 표현
  • MQTT canary가 모든 protocol 또는 live cutover 완료를 증명한다는 표현
  • 30개 물리 센서나 동적 orchestration이 이미 완성됐다는 표현

현재 PoC와의 경계

현재 PoC 문서는 서비스 데모와 EdgeX-backed 운영 가시화를 중심으로 유지한다. 이 문서는 2차년도 설계 트랙이며 future registry, twin, workflow runtime이 이미 운영된다고 주장하지 않는다. 구현으로 승격할 때는 docs/프로젝트-범위.md, docs/저장소-구조.md, docs/단계별-추진계획.md에서 현재 범위, 검증 기준, 운영 책임을 먼저 갱신한다.
