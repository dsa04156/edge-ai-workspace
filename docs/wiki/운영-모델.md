# 운영 모델

## 운영 목표

현재 PoC의 운영 목표는 “센서 데이터를 중앙에 안전하게 적재하고, 디바이스·서비스·노드 상태를 한 화면에서 설명하는 것”이다. 2차년도에는 이 기반으로 생산품질 판별과 유압펌프·모터 이상감지 서비스 데모를 연결한다.

## 현재 책임 분리

| 책임 | 담당 | 운영자가 확인할 근거 |
|---|---|---|
| 장비 통신·Event 생성 | 노드 로컬 EdgeX Device Service | Device Service health, typed Event |
| 최근 엣지 입력 | Device Service Local Data API | bounded memory cache, latest/recent sample |
| 중앙 영구 저장 | Core Data/PostgreSQL | Core Data Event/Reading |
| Device/Profile·관리 상태 | EdgeX Core Metadata | Device/Profile API |
| 노드·워크로드 | Kubernetes/KubeEdge | Node/Pod 상태 |
| 운영 해석 | `state-aggregator` + dashboard | `/state/devices`, `/state/dashboard` |

KubeEdge의 노드 상태가 정상이어도 Core Data Event가 stale하면 physical device는 degraded다. 반대로 최신 Event가 있어도 Kubernetes 배치 정보만으로 장비 연결을 추정하지 않는다.

## 현재 수직 슬라이스

```text
physical endpoint -> EdgeX Device Service -> Core Data/PostgreSQL
                  -> Local Data API -> edge AI consumer
                  -> state-aggregator -> dashboard
```

`edgex/k8s/kustomization.yaml`이 배포 진입점이며 중앙은 `edgex-system`, Device Service는
`edgex-edge` namespace를 사용한다. 현재 대표 물리 source는 `arduino-001`과
`sensehat-001`이다. 이 기준선이 모든 프로토콜과 2차년도 AI 서비스를 구현했다는 뜻은 아니다.

## 2차년도 서비스 기준

1. 생산품질 양품·불량 판별: PLC/MES/센서 데이터와 생산 건 식별자를 묶는다.
2. 메인·보조 유압펌프 및 모터 이상감지: 진동 3축, 전류, 온도 등 입력을 공통 timestamp로 정렬한다.

두 서비스는 수집→전처리→추론→결과 저장→알림의 컨테이너화된 흐름으로 설계하되, 현재 checkout에서 실제 AI 모델·배포 실행이 완료됐다고 표시하지 않는다.

## 운영자가 먼저 답할 질문

- Core Metadata에 Device/Profile이 등록돼 있는가?
- Core Data의 최신 Event가 fresh한가?
- Core Data Event와 Device Service Local Data가 같은 source identity와 시각으로 이어지는가?
- 서비스 데모 입력 Device와 리소스가 명세에 맞는가?
- node/workload 문제인가, physical telemetry 문제인가?

상세 판단은 [대시보드 판단 정책](../대시보드-판단-정책.md), 실행은 [운영 Runbook](../ops/현재-데모-운영-절차.md)을 따른다.

## 금지하는 해석

`workflow_executor`, `placement_engine`, legacy mapper와 과거 MQTT 경로를 현재 운영의 fallback으로 해석하지 않는다. workflow builder는 현재 브라우저 상태의 validation/dry-run과 plan preview까지만 제공한다.
