# 운영 모델

## 한 줄 요약

현재 시스템은 중앙 EdgeX Core·PostgreSQL과 KubeEdge 노드·워크로드 관리 기반을 유지한 채, 정식 EdgeX Device Service로 실제 장비 1종을 연결한 PoC다.
핵심은 Device Service/Profile/Device와 실제 Event/Reading을 대시보드에서 같은 identity로 해석 가능하게 만드는 것이다.

## 현재 기준

이 프로젝트는 동적 오케스트레이션 전체를 먼저 완성하는 단계가 아니다.
현재 우선순위는 Jetson Arduino → Serial Device Service → Core Data → dashboard 수직 슬라이스와 서비스 데모 1종을 운영 관점에서 설명 가능하게 만드는 것이다.

1. EdgeX Device Service가 실제 endpoint를 연결하고 typed Event를 만든다.
2. Core Data와 PostgreSQL이 Event/Reading을 저장한다.
3. 중앙 EdgeX Core Metadata와 Core Data가 inventory·schema·telemetry 권위를 가진다.
4. KubeEdge는 엣지 노드와 워크로드만 관리한다.
5. `state-aggregator`와 대시보드가 디바이스·서비스·노드·KPI를 함께 보여준다.

2026-07-21 기존 custom edge Agent/SQLite outbox와 `sensehat-001` bootstrap은 퇴역했다. 현재 `device-serial-jetson`이 `arduino-001`의 typed telemetry를 중앙에 저장하고 dashboard에서 fresh 상태로 표시한다. 이 완료 범위에는 offline replay와 물리 분리·복구 시연이 없다.

짧은 정의:

```text
센서 데이터와 엣지 AI 서비스를 실제로 연결하고 운영 상태를 한눈에 보여주는 시스템
```

## 경계

현재 모델은 다음을 주장하지 않는다.

- 완전 자율형 orchestration
- LLM 기반 인프라 제어
- dynamic offloading이 현재 데모 경로라는 주장
- `workflow_executor` 또는 `placement_engine`이 현재 데모 제어 컴포넌트라는 주장
- runtime replanning 구현 완료
- node disk backup이나 전체 downstream exactly-once가 구현됐다는 주장

Legacy workflow, offloading, selective replanning, agent-assisted planning 자료는 `docs/프로젝트-범위.md`에서 승격하지 않는 한 과거 맥락 또는 설계 후보로만 본다.

## 운영상 의미

새 문서나 기능이 현재 PoC 범위인지 판단할 때 이 페이지를 기준으로 삼는다.
아래 질문에 직접 답하면 현재 경로에 가깝다.

- 중앙 EdgeX Core Metadata에 어떤 디바이스와 프로필이 등록되어 있는가?
- 센서 Event가 중앙 PostgreSQL에 저장되었는가?
- 최근 텔레메트리와 source timestamp가 fresh한가?
- physical endpoint, Device Service, Core Data, consumer 중 어디에서 문제가 발생했는가?
- 관련 엣지 노드와 워크로드가 KubeEdge에서 정상인가?
- 어떤 서비스 데모가 이 디바이스 입력에 의존하는가?
- 이 상태가 옥동 생산성 설명과 어떻게 연결되는가?

주요 내용이 dynamic workflow 실행, placement 최적화, agent control 확장이라면 먼저 2차년도 설계 트랙 또는 legacy/reference로 분류한다.
