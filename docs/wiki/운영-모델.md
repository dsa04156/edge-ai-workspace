# 운영 모델

## 한 줄 요약

현재 시스템은 중앙 EdgeX Core·PostgreSQL과 KubeEdge 노드·워크로드 관리 기반을 유지한 채, 정식 EdgeX Device Service로 실제 Serial/I2C 장비 2종을 연결하고 Jetson 실측 가속도 이상 탐지 서비스 1종을 붙인 PoC다.
핵심은 Device Service/Profile/Device와 실제 Event/Reading, 이를 소비하는 AI service를 대시보드에서 같은 identity로 해석 가능하게 만드는 것이다.

## 현재 기준

이 프로젝트는 동적 오케스트레이션 전체를 먼저 완성하는 단계가 아니다.
현재 우선순위는 Jetson Arduino Serial과 Raspberry Pi Sense HAT 직접 I2C → 각 Device Service → Core Data → dashboard 수직 슬라이스와 서비스 데모를 운영 관점에서 설명 가능하게 만드는 것이다.

1. EdgeX Device Service가 실제 endpoint를 연결하고 typed Event를 만든다.
2. Core Data와 PostgreSQL이 Event/Reading을 저장한다.
3. 중앙 EdgeX Core Metadata와 Core Data가 inventory·schema·telemetry 권위를 가진다.
4. KubeEdge는 엣지 노드와 워크로드만 관리한다.
5. `state-aggregator`와 대시보드가 디바이스·서비스·노드·KPI를 함께 보여준다.
6. `sensor-anomaly-demo`는 Jetson Local Data API에서 acceleration 3축을 500ms polling하고 같은 `origin` frame의 online baseline 변화 점수를 제공한다.
7. 새 장비 연결은 dashboard `Device Management`가 승인된 Adapter Runtime 재사용/배포와
   EdgeX Profile/Device 등록, 첫 Event 확인을 하나의 operation으로 추적한다.
8. 검증 protocol package는 웹에서 Runtime/Device 설정을 받고, 기존 Device Service가
   없으면 Controller가 공식 immutable image만 배포한다. 현재 신규 설치 예시는 MQTT 개발
   package이며 운영 TLS/auth broker는 별도 승격 대상이다.

2026-07-21 기존 custom edge Agent/SQLite outbox와 aggregate `sensehat-001` bootstrap은 퇴역했다. 현재 `device-serial-jetson`과 `device-sensehat-raspi`는 물리 source `arduino-001`, `sensehat-001`을 각각 한 번 읽고 기능별 가상 Device 6개씩의 typed Event로 중앙에 저장한다. Device/resource별 최근 10분·최대 10,000 sample의 휘발성 cache와 same-node Local Data API는 제공하지만 offline replay와 durable outbox는 없다. 현재 Flannel에서는 Local Data API의 client label NetworkPolicy가 강제되지 않는다.

2026-07-22 `sensor-anomaly-demo`는 `virtual-acceleration-{x,y,z}-001`을 첫 실제 service binding으로 사용한다. 결과는 raw physical Device가 아니라 derived service output이며 `/state/service-demo`로 failure-isolated 조회한다. polling은 push stream이 아니고 detector는 학습된 고장 분류기가 아니다. 실제 장치 움직임에 의한 anomaly 시연 전에는 실제 고장 검출 실증으로 표현하지 않는다.

2026-07-23 Adapter Runtime 관리는 dashboard → state-aggregator BFF →
`edgex-adapter-controller` 경로로 제한했다. Controller는 Git allowlist의 image, target node와
hardware binding만 사용하고, 기존 Argo Serial/I2C runtime은 조회·재사용한다. Controller가
만든 runtime만 재시작·consumer-safe 퇴역할 수 있다. 물리 inventory/state/telemetry 권위는
계속 EdgeX이고 KubeEdge Device CRD나 EdgeMesh를 변경하지 않는다.

짧은 정의:

```text
센서 데이터와 엣지 AI 서비스를 실제로 연결하고 운영 상태를 한눈에 보여주는 시스템
```

## 경계

현재 모델은 다음을 주장하지 않는다.

- 완전 자율형 orchestration
- LLM 기반 인프라 제어
- dynamic offloading이 현재 데모 경로라는 주장
- `workflow_executor` 또는 `placement_engine`이 현재 데모 제어 컴포넌트라는 주장
- runtime replanning 구현 완료
- 고정 `sensor-anomaly-demo` Deployment가 동적 Workflow Builder 실행이라는 주장
- online baseline 변화 점수가 학습된 고장 분류 결과라는 주장
- node disk backup이나 전체 downstream exactly-once가 구현됐다는 주장

Legacy workflow, offloading, selective replanning, agent-assisted planning 자료는 `docs/프로젝트-범위.md`에서 승격하지 않는 한 과거 맥락 또는 설계 후보로만 본다.

## 운영상 의미

새 문서나 기능이 현재 PoC 범위인지 판단할 때 이 페이지를 기준으로 삼는다.
아래 질문에 직접 답하면 현재 경로에 가깝다.

- 중앙 EdgeX Core Metadata에 어떤 디바이스와 프로필이 등록되어 있는가?
- 센서 Event가 중앙 PostgreSQL에 저장되었는가?
- 최근 텔레메트리와 source timestamp가 fresh한가?
- physical endpoint, Device Service, Core Data, consumer 중 어디에서 문제가 발생했는가?
- 관련 엣지 노드와 워크로드가 KubeEdge에서 정상인가?
- 어떤 서비스 데모가 이 디바이스 입력에 의존하는가?
- 어떤 Adapter Runtime이 이 endpoint를 소유하고 있으며 대시보드에서 재사용 또는 승인 배포할
  수 있는가?
- 이 상태가 옥동 생산성 설명과 어떻게 연결되는가?

주요 내용이 dynamic workflow 실행, placement 최적화, agent control 확장이라면 먼저 2차년도 설계 트랙 또는 legacy/reference로 분류한다.
