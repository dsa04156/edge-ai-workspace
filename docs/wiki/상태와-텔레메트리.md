# 상태와 텔레메트리

## 한 줄 요약

현재 physical-device 상태는 EdgeX Core Metadata 관리 상태와 Core Data 최신 Event/Reading freshness로 판단한다. KubeEdge/Kubernetes는 node와 workload만 관리·관찰한다.

## 목표 권위와 데이터 경로

```text
물리 센서 / PLC / 장비
  -> Protocol Adapter -> edge-telemetry-agent -> SQLite outbox
  -> HTTPS/mTLS ingest gateway
  -> EdgeX Core Data -> PostgreSQL
  -> state-aggregator -> 대시보드
```

| 구분 | authority | 현재 사용 데이터 |
|---|---|---|
| inventory / management state | EdgeX Core Metadata | Device/Profile/Device Service, `adminState`, `operatingState` |
| telemetry / freshness | EdgeX Core Data | Event `deviceName`, `sourceName`, nanosecond `origin`, typed Readings |
| node / workload | Kubernetes / KubeEdge | placement, Node readiness, workload 상태 |

Core Metadata의 Device와 Profile은 중앙에 사전 등록하고, Protocol Adapter가 프로토콜 연결과 표준화를, edge agent가 durable 전달을 담당한다. KubeEdge/Kubernetes는 physical Device inventory, telemetry, command, availability의 원본이 아니다.

## Event/Reading과 freshness

Core Data Event의 `deviceName`은 inventory join key이고 `sourceName`은 telemetry source/resource다. `origin`은 nanoseconds 단위의 Event 시각이며, Reading은 `valueType`과 typed 값을 보존한다.

`state-aggregator`는 이를 다음 dashboard API field로 정규화한다.

| API field | 의미 |
|---|---|
| `latest_event_timestamp` | 최신 Core Data Event/Reading 시각 |
| `latest_readings` | 최신 Event의 `source_name`, `resource_name`, `value_type`, `value`, `timestamp`, `event_id`, `units` |
| `telemetry_freshness` | `fresh`, `stale`, `no_events` |
| `connection_state` | `connected`, `disconnected`, `unknown` |
| `device_service_available` | `operating_state=UP` 여부 |

Freshness는 deployment의 `EDGEX_EVENT_FRESH_SECONDS` threshold(현재 기본값 `90`)를 최신 유효 Event `origin`에 적용한다. Event origin이 없거나 parse할 수 없으면 fresh로 추정하지 않고 `degraded` reason으로 표시한다. API 조회 시각이나 다른 저장소의 timestamp로 Core Data Event freshness를 보충하지 않는다.

## Availability 해석

Dashboard와 `state-aggregator`는 아래 순서로 physical availability를 해석한다.

1. `admin_state=LOCKED`, `operating_state=DOWN`, 또는 `connection_state=disconnected`이면 `unavailable`/`disconnected`다.
2. `operating_state=UNKNOWN`, `connection_state=unknown`, event origin 오류면 `degraded`/`unknown`이다.
3. `operating_state=UP`, `connection_state=connected`, 최신 Core Data Event가 fresh이면 `available`이다.
4. Device Service가 UP이어도 event가 없거나 stale이면 `degraded`다.

`device_service_available`은 빠른 Device Service 상태 표시에 사용하지만 final availability를 단독으로 결정하지 않는다. `node_name`, Node Ready, workload 배치·상태는 별도 Kubernetes/KubeEdge diagnostic이며 physical availability의 선행 조건이나 gate가 아니다.

## 운영 진단 순서

Physical device가 `degraded` 또는 `unavailable`이면 다음 근거를 순서대로 확인한다.

1. Core Metadata Device, Profile, Device Service가 의도한 binding으로 등록되어 있는지
2. `admin_state`, `operating_state`, `connection_state`와 `device_service_available`
3. Core Data 최신 Event의 `deviceName`, `sourceName`, `origin`, typed Readings
4. `latest_event_timestamp`와 `telemetry_freshness`
5. Protocol Adapter, agent outbox, HTTPS gateway, Core Data/PostgreSQL, state-aggregator 연결
6. 필요할 때만 관련 KubeEdge/Kubernetes node와 workload placement

Kubernetes node/workload 문제는 EdgeX physical state와 분리해 서비스 실행 또는 placement 진단으로 설명한다.

## direct agent와 중앙 전환 상태

현재 `sensehat-001`은 loopback agent → SQLite → HTTPS gateway → Core Data/PostgreSQL 경로를 확인하는 교체 가능한 fixture다. 과거 MQTT canary는 비교 기록에만 남고 현재 Jetson compatibility workload는 없다.

이 결과는 장비·profile·Reading 계약의 근거다. 중앙 server2 topology와 대시보드 중앙 조회 전환은 각각 별도 live evidence를 확보해야 한다.

1차 수직 슬라이스는 SQLite offline replay와 Core Data persisted ACK를 포함한다. Serial, Modbus, OPC-UA와 추가 I2C adapter는 profile, 실장비 연결, typed telemetry와 dashboard consumer 증거를 확보하기 전까지 완료로 주장하지 않는다. RTSP frame은 별도 Workflow Pod가 직접 구독한다.

## 제외한 legacy 신호

다음은 current physical health, telemetry freshness, dashboard KPI의 입력이나 fallback이 아니다.

- KubeEdge `DeviceStatus` 및 DeviceStatus freshness
- MapperFramework, mapper readiness, `mqttvirtual`
- mapper direct-to-Influx latest sample
- legacy `command`/`heartbeat` topic과 mapper heartbeat

이 경로는 과거 test/integration 또는 migration 비교 자료로만 남는다. EdgeX Core Metadata 또는 Core Data 조회 실패 시 legacy source로 fallback하지 않고 오류 또는 미관측 상태를 표시한 뒤 EdgeX 경로를 복구한다.

## Workflow/augmentation 경계

Workflow Designer와 resource augmentation은 read-only/dry-run 표면이다. telemetry 상태를 근거로 Kubernetes apply/delete/restart, EdgeX metadata/state mutation, command publish, actuator command, runtime migration/offloading을 실행하지 않는다.
