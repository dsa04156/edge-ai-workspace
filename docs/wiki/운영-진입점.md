# 운영 진입점

## 한 줄 요약

운영자는 Jetson Serial/Raspberry Pi I2C Device Service, Jetson `sensor-anomaly-demo`, 중앙 EdgeX와 dashboard를 차례로 확인하는 현재 운영 절차에서 시작한다. 과거 Agent 또는 폐기된 중앙 MessageBus 재구축 문서는 실행하지 않는다.

## 현재 기준

운영 문서는 개념 문서와 분리한다. 실행, 검증, 장애 원인 좁히기 질문은 Ops 문서에서 시작한다.

| 상황 | 시작 문서 |
|---|---|
| Arduino Serial·Sense HAT I2C 종단간 상태 점검 | [현재 서비스 데모 운영 Runbook](../ops/현재-데모-운영-절차.md) |
| 중앙 Core Data/PostgreSQL 1,000-device 저장 기준선 | [Core Data 1,000-device 부하 검증](../ops/엣지엑스-코어데이터-1000-디바이스-부하검증.md) |
| EdgeX state-aggregator dashboard API/UI 확인 | [Dashboard 검증](../ops/대시보드-검증.md) |
| pod 또는 network 경로 점검 | [네트워크 트러블슈팅](../ops/네트워크-문제해결.md), [파드 통신 점검](../ops/파드-연결성-점검.md) |
| edge node join 확인 | [Edge 노드 조인 점검](../ops/엣지-노드-조인-점검.md) |
| GPU runtime 맥락 확인 | [HAMi GPU runtime](../ops/gpu-hami-런타임-운영.md) |

현재 중앙 EdgeX runtime은 `edgex-system`, `device-serial-jetson`, `device-sensehat-raspi`와 `sensor-anomaly-demo`는 `edgex-edge`, state-aggregator는 `default` namespace에 있다. 물리 inventory, 관리 상태, telemetry는 EdgeX가 authority이며 KubeEdge node/workload 정보와 AI derived result는 별도 진단이다.

## 운영자 읽기 순서

라이브 데모에서는 다음 순서로 본다.

1. [현재 서비스 데모 운영 Runbook](../ops/현재-데모-운영-절차.md)에서 Argo, 중앙 EdgeX와 두 Device Service 상태를 확인한다.
2. EdgeX Core Metadata에서 `device-serial-jetson`, `device-sensehat-raspi`와 각 Profile/Device 6개, 총 12개 binding을 확인한다.
3. EdgeX Core Data의 최신 Event/Reading `origin`, `sourceName`, typed value와 freshness를 확인한다.
4. `sensor-anomaly-demo`의 `/api/v1/status`를 두 번 읽어 세 acceleration Device, 증가하는 `latest.origin`/`framesProcessed`, `inputState=fresh`, `model.algorithm=online-gaussian-baseline-v1`을 확인한다.
5. namespace `default`의 state-aggregator API에서 기존 EdgeX device 상태와 별도 `/state/service-demo` derived 결과를 확인한다.
6. [Dashboard 검증](../ops/대시보드-검증.md)으로 device row, 서비스 데모 panel, Explain Panel, EdgeX KPI와 node/workload 진단의 분리를 확인한다.
7. 자원증강 탭에서 AI HAT/GPU/cache Resource Profile과 실행 인스턴스 상태를 확인한다.
8. 기술 상태가 보인 뒤 KPI 문서를 사용한다.

KubeEdge node readiness와 workload placement는 dashboard에서 볼 수 있지만 물리 availability를 결정하지 않는다. 물리 availability는 EdgeX 관리 상태와 Core Data 최신 Event freshness로만 해석한다.

## 현재 live 판정

2026-07-21 immutable ARM64 digest로 배포한 Serial 6개와 I2C 6개, 총 12개 가상 Device revision에서 Metadata/Core Data/Core Command, Local Data API와 dashboard를 같은 실행으로 확인했다. 12개 모두 `UNLOCKED`, `UP`, `connected`, `available`, `fresh`였고 protocol별 local cache/API 계약도 통과했다. 2026-07-22 Serial USB driver detach/rebind와 Sense HAT reader 종료로 각 6개 Device의 `DOWN → UP`과 새 Event 재개도 확인했다. 실제 케이블·보드 손분리, offline replay와 NetworkPolicy 차단은 별도 gate다.

2026-07-22 서비스 데모 코드·manifest·API와 anomaly/clear 상태 전이 테스트를 완료했다. Jetson live status에서 raw origin과 processed frame 증가, 중앙 `/state/service-demo`, 실제 브라우저의 NORMAL/fresh panel과 데스크톱·모바일 반응형 표시를 확인했다. 실제 장치를 움직여 anomaly를 발생시키는 현장 시연은 별도 gate다.

2026-07-22 Core Data REST 기준선에서 1,000 devices × 1/60Hz는 1,000/1,000 저장과 p95 16.17ms로 PASS했다. 1,000 devices × 1Hz는 현재 300m CPU/256Mi Core Data가 OOMKilled되어 FAIL했다. 따라서 기본 운영 검증은 저주기 profile이고, 1Hz는 resource tuning과 단계별 rate gate 전까지 지원 처리량으로 보지 않는다.

## 경계

Ops 문서는 operator assistant, workflow builder, 자원증강 화면이 infrastructure를 변경할 수 있는 것처럼 표현하지 않는다. 별도 승인된 control path가 생기기 전까지 이 기능은 read-only 요약, troubleshooting 안내, dry-run validation/plan preview로 제한한다.
