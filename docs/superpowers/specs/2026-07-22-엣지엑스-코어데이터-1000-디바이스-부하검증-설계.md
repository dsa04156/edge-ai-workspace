# EdgeX Core Data 1,000 디바이스 부하검증 설계

## 목적

기본 EdgeX Core Data의 Event 단위 즉시 저장 방식을 변경하기 전에, 현재 단일 Core Data와 PostgreSQL이 목표 입력률을 실제로 처리하는지 재현 가능하게 측정한다. 이 검증은 물리 Device inventory를 늘리거나 운영 Device Service를 변경하지 않고, 실행별로 격리된 합성 Event를 Core Data REST ingress에 입력해 저장 경로만 측정한다.

## 범위

- 1,000개의 합성 device identity를 사용한다.
- `device 수 × device별 Hz`로 목표 Event/s를 계산한다.
- 각 Event는 Float64 Reading 한 개를 포함한다.
- Core Data의 HTTP `201 Created`를 PostgreSQL 커밋 완료로 계산한다.
- 실행별 device 이름을 사용해 저장 건수를 다시 조회한다.
- 성공률, 달성 Event/s, p50/p95/p99/max 응답 지연과 readback 일치 여부를 JSON으로 남긴다.
- 검증 후 실행별 합성 Event만 device 이름으로 삭제한다.
- 운영 Device/Profile/Device Service, EdgeMesh, Argo CD Application과 root Kustomization은 변경하지 않는다.

## 비범위

- Device Service protocol 수집 성능
- 중앙 MessageBus publish/subscribe 처리량
- NATS JetStream 전환
- Core Data 다중 Event batch insert
- PostgreSQL schema, partition 또는 retention 변경
- Core Metadata에 합성 Device 등록
- 현재 대시보드의 물리 Device inventory 변경

이번 결과는 Core Data REST → PostgreSQL 저장 경로의 기준선이다. Device Service → MessageBus → Core Data 전체 처리량은 별도 후속 검증으로 분리한다.

## 구조

```text
일회성 Kubernetes Job @ etri-ser0002-cgnmsb
  -> Service FQDN: edgex-core-data.edgex-system.svc.cluster.local:59880
  -> POST /api/v3/event/{service}/{profile}/{device}/{source}
  -> EdgeX Core Data
  -> PostgreSQL
  -> GET /api/v3/event/count/device/name/{device}
  -> DELETE /api/v3/event/device/name/{device}
  -> count=0 확인
```

부하 생성기는 Go 표준 라이브러리만 사용한다. 실행 스크립트는 amd64 정적 바이너리를 로컬에서 빌드하고, 이미 중앙 배포에서 사용 중인 digest 고정 BusyBox image의 일회성 Pod에 복사해 실행한다. 별도 장기 workload나 registry image를 요구하지 않으며 Pod는 결과 수집 후 제거한다.

## 입력과 기본값

| 항목 | 기본값 | 의미 |
|---|---:|---|
| devices | 1,000 | 합성 device identity 수 |
| per-device-hz | 1/60 | device별 약 1 Event/분의 안전한 기본값 |
| duration | 60s | 측정 구간 |
| concurrency | 128 | 동시 HTTP worker 수 |
| maintenance-concurrency | 8 | readback·cleanup 동시 요청 상한 |
| request-timeout | 5s | 요청별 제한 |
| max-error-rate | 0 | 허용 실패율 |
| max-p95 | 1s | 허용 p95 응답 지연 |
| verify | true | device별 전용 Event count API readback |
| cleanup | true | 합성 Event 삭제 |

부하 생성기는 목표 Event 수를 `round(devices × per-device-hz × durationSeconds)`로 계산하고, device를 round-robin으로 선택한다. 스케줄러가 뒤처지더라도 Event를 버리지 않고 worker queue backpressure를 받는다. 따라서 `attempted`와 `achievedEventsPerSecond`를 함께 보고 목표 입력률을 실제로 달성했는지 판정한다.

## Event 계약

- service name: `core-data-loadtest`
- profile name: `loadtest-profile-v1`
- source/resource name: `value`
- device name: `loadtest-{runId}-{index}`
- Event와 Reading ID: UUID v4
- Event/Reading origin: 실제 생성 시각의 Unix nanoseconds
- value type: `Float64`
- tag: `loadTestRunId`

합성 이름은 Core Metadata에 등록하지 않는다. Core Data의 저장 성능만 측정하며, 대시보드는 Core Metadata inventory를 권위로 사용하므로 합성 Event를 물리 Device로 표시하지 않는다.

## 성공 판정

다음 조건을 모두 만족해야 PASS다.

1. 모든 예정 Event가 시도된다.
2. HTTP `201` 응답 수가 예정 Event 수와 같다.
3. 오류율이 `max-error-rate` 이하이다.
4. p95 지연이 `max-p95` 이하이다.
5. 달성 Event/s가 목표의 95% 이상이다.
6. 전용 Event count API의 device별 `count` 합계가 성공 Event 수와 같다.
7. readback 또는 cleanup HTTP 오류가 없다.

HTTP 성공은 Core Data가 `AddEvent`의 PostgreSQL 트랜잭션을 커밋한 뒤 반환한다. readback은 API 응답 성공과 저장된 실행별 건수를 독립적으로 확인한다.

## 실패와 정리

- 전송 실패는 상태 코드와 오류 종류별로 집계하되 무한 재시도하지 않는다.
- context 취소 시 새 Event 생성을 중단하고 이미 queue에 들어간 요청을 회수한다.
- readback과 cleanup도 같은 context 취소를 존중해 종료 신호 뒤 maintenance가 계속 대기하지 않게 한다.
- 검증 실패도 JSON report와 비정상 종료 코드로 남긴다.
- cleanup은 `loadtest-{runId}-*`의 정확한 device 이름만 삭제하며 age 기반 광역 삭제를 사용하지 않는다. `202 Accepted` 뒤 전용 count API가 0이 될 때까지 확인한다.
- readback과 cleanup 상세 오류는 각 20건까지만 남기고 나머지는 `suppressedErrors`로 집계한다.
- 운영 Event는 삭제하지 않는다.
- 일회성 Pod는 Argo CD 대상에 추가하지 않는다.

## 검증 프로파일

1. 단위 테스트: Event 계약, 설정 검증, percentile, PASS/FAIL 판정, HTTP 저장/readback/cleanup을 `httptest.Server`로 검증한다.
2. 1,000-device 저주기 기본 기준선: `1/60 Hz × 1,000`, 60초, 약 16.7 Event/s.
3. 1,000-device 1Hz 스트레스 기준선: `1 Hz × 1,000`, 최소 30초 후 필요 시 60초.
4. 실행 전후 Core Data/PostgreSQL Pod Ready와 재시작 횟수를 기록한다.

10Hz는 1Hz 결과와 저장 증가량을 확인한 후 별도 승인된 stress profile로 실행한다. 현재 첫 구현에서 자동 실행하지 않는다.

## 2026-07-22 구현 피드백

최종 저주기 실행은 1,000/1,000 저장, 16.678 Event/s, p95 16.17ms, device별 readback과 cleanup 모두 PASS했다. 1Hz × 1,000의 30초 실행은 현재 Core Data limit 300m CPU/256Mi memory에서 OOMKilled되어 0/30,000으로 FAIL했다. 이에 따라 도구 기본값은 저주기 profile로 고정하고 1Hz는 별도 스트레스 profile로 분리한다.

초기 구현은 일반 device Event API의 `totalCount`를 readback에 사용했으나 1,000회 Event/Reading join으로 조회 경로를 정체시켰다. 최종 구현은 EdgeX 전용 `/api/v3/event/count/device/name/{device}`와 `count` 응답 필드를 사용하고, 저장 동시성과 maintenance 동시성을 분리한다.
