# 엣지엑스 MQTT 수집 수직 슬라이스 설계

> **상태: 과거 MQTT canary 설계.** Jetson compatibility 근거로만 유지한다. 현재 기본 서비스 데모는 broker-free Sense HAT I2C -> SQLite agent -> HTTPS gateway 경로다.

> 분류: 설계 이력. 현재 운영 기능의 완료 근거가 아니다.

## 1. 목적

이 설계는 `etri-dev0001-jetorn`의 로컬 MQTT telemetry를 EdgeX 물리 디바이스
통합 계층으로 수집하는 첫 번째 canary를 정의한다. 첫 ingestion 완료 기준은 MQTT 메시지
한 건이 EdgeX `Event/Reading`으로 저장되고 Core Data API에서 최신값으로 조회되는 것이다.

이 canary는 물리 디바이스 연동 계층을 MapperFramework에서 EdgeX Device Service로
교체하는 전체 cutover의 첫 단계다. canary가 EdgeX로 전환된 뒤에는 KubeEdge
Device/DeviceStatus와 `mqttvirtual` mapper를 병행 status/control plane이나 fallback으로
사용하지 않는다. KubeEdge는 edge node와 workload 관리에만 남긴다.

## 2. 범위

### 포함

- 기존 로컬 Mosquitto의 MQTT telemetry 구독
- profile 기반 topic 및 payload 변환
- EdgeX `device-mqtt` 표준 async topic으로 재발행
- 진동/가속도 디바이스용 EdgeX Device Profile과 Device 정의
- EdgeX Core Data 단기 저장 및 최신 event 조회
- 변환기 단위 테스트와 broker/EdgeX smoke test
- 잘못된 topic, JSON, 필드, 자료형 및 broker 장애 처리

### 제외

- 전체 MQTT device migration 완료 주장
- Serial, Modbus, OPC-UA, RTSP protocol wave 완료 주장
- 중앙 서버로 raw telemetry 상시 전송
- EdgeX App Service 기반 장기 저장
- 실제 actuator command 실행과 Workflow 실행
- 실제 Arduino collector와 `virtual-device/`의 자동 결합 또는 대체
- Kubernetes CRD 추가

## 3. 검토한 방식

### A. profile 기반 MQTT-to-EdgeX Bridge

기존 MQTT topic을 유지하고 독립 Bridge가 EdgeX topic/payload로 변환한다. publisher가
EdgeX를 몰라도 되고, 이후 MQTT 디바이스는 route profile만 추가하면 된다. 이 방식을
채택한다.

### B. publisher의 이중 발행

각 publisher가 기존 topic과 EdgeX topic을 동시에 발행한다. 초기 코드는 적지만 모든
publisher가 EdgeX naming과 Device Profile을 알아야 하므로 채택하지 않는다.

### C. 커스텀 EdgeX Device Service

기존 factory topic을 직접 해석하는 새 Device Service를 SDK로 작성한다. 가장 자유롭지만
첫 PoC에 필요한 코드와 운영 책임이 커서 채택하지 않는다.

## 4. 아키텍처

```text
MQTT publisher / sensor collector
  -> edge-local Mosquitto
       topic: factory/devices/{device-name}/telemetry
  -> MQTT-to-EdgeX Bridge
       route validation
       allowlist projection
       type conversion
       source timestamp validation
  -> edge-local Mosquitto
       topic: incoming/data/{device-name}/{source-name}
  -> EdgeX device-mqtt
  -> EdgeX MessageBus
  -> EdgeX Core Data
  -> edge-local PostgreSQL persistent volume
```

Bridge의 southbound 입력과 EdgeX async 출력은 같은 로컬 Mosquitto를 사용할 수 있다.
EdgeX 내부 MessageBus broker는 EdgeX compose network 안에서 별도로 유지한다. topic
namespace가 다르므로 Bridge는 자신이 발행한 `incoming/data/#`를 다시 구독하지 않는다.

EdgeX 배포는 ARM64를 지원하는 안정 release tag `v4.0.2`에 고정한다. 개발 smoke
환경은 no-security profile을 사용하되 API port는 loopback에만 노출한다. 운영 배포에서
no-security profile을 사용하지 않는다.

## 5. 컴포넌트 경계

### MQTT-to-EdgeX Bridge

한 edge node에서 한 인스턴스를 실행한다. 여러 MQTT device route를 한 process가
처리한다. protocol 연결, schema 검증과 EdgeX async topic 변환만 담당하며 데이터를
저장하지 않는다.

Bridge route는 다음 정보를 선언한다.

```yaml
routes:
  - inputTopic: factory/devices/vib-arduino-acceleration-01/telemetry
    deviceName: vib-arduino-acceleration-01
    sourceName: telemetry
    outputTopic: incoming/data/vib-arduino-acceleration-01/telemetry
    timestampFields:
      - source_ts
      - ts
      - timestamp
    fields:
      x:
        target: acceleration_x
        type: float
      y:
        target: acceleration_y
        type: float
      z:
        target: acceleration_z
        type: float
```

route의 `outputTopic`은 반드시
`incoming/data/{deviceName}/{sourceName}`과 일치해야 한다. Bridge는 시작할 때 이
관계를 검증하고 일치하지 않으면 실행을 중단한다.

### EdgeX Device MQTT

공식 `device-mqtt`를 수정하지 않는다. Bridge가 발행한 표준 async topic을 구독하고
Device Profile에 따라 payload를 EdgeX readings로 변환한다. Device 정의에는 SDK가
요구하는 `CommandTopic`을 `command/vib-arduino-acceleration-01`로 선언하지만, 첫 단계의
resource와 command는 숨김 처리해 센서 GET/SET 요청을 노출하지 않는다.

### EdgeX Core Data

수집된 Event/Reading을 edge node의 PostgreSQL persistent volume에 단기 저장한다.
첫 단계에서는 기본 retention을 사용하며, 장기 historian 역할은 부여하지 않는다.

## 6. 데이터 계약

### Bridge 입력

```text
topic: factory/devices/vib-arduino-acceleration-01/telemetry
```

```json
{
  "x": "0.12",
  "y": "0.08",
  "z": "0.91",
  "ts": "1783935600"
}
```

숫자 문자열과 JSON number를 모두 허용한다. route에 선언되지 않은 `health`,
`severity`, `alarm_latched` 같은 status 필드는 출력에서 제외한다.

### Bridge 출력

```text
topic: incoming/data/vib-arduino-acceleration-01/telemetry
```

```json
{
  "acceleration_x": 0.12,
  "acceleration_y": 0.08,
  "acceleration_z": 0.91,
  "source_timestamp": 1783935600
}
```

`source_timestamp`는 route의 `timestampFields`에서 처음 발견한 유효한 epoch-second
값이다. timestamp가 없거나 정수로 변환할 수 없으면 전체 sample을 거부한다. Bridge
수신 시각을 원본 시각처럼 대체하지 않는다.

### EdgeX Device Profile

Device Profile 이름은 `etri-vibration-mqtt`로 한다. 다음 read-only resource를 가진다.

| resource | EdgeX valueType | unit | isHidden |
|---|---|---|---|
| `acceleration_x` | `Float64` | `g` | `true` |
| `acceleration_y` | `Float64` | `g` | `true` |
| `acceleration_z` | `Float64` | `g` | `true` |
| `source_timestamp` | `Int64` | `s` | `true` |

`telemetry` read-only Device Command가 네 resource를 묶고 `isHidden: true`로 등록된다.
센서는 push 방식이므로 Core Command GET을 센서에 보내지 않는다.

## 7. 최신값 조회 의미

첫 단계의 `getLatest`는 별도 서비스 API가 아니라 Core Data 조회로 검증한다.

```text
Core Data event query
  deviceName = vib-arduino-acceleration-01
  sourceName = telemetry
  limit = 1
```

반환 event의 `source_timestamp`가 입력 sample의 timestamp와 같고, 세 가속도 reading이
Device Profile 자료형으로 저장돼야 한다. 이후 state-aggregator 연동 단계에서 이 조회를
공통 `getLatest` 서비스 계약으로 감싼다.

## 8. 오류 처리

| 상황 | 동작 |
|---|---|
| 등록되지 않은 topic | payload를 읽지 않고 warning counter 증가 |
| UTF-8/JSON 오류 | sample 거부, 구조화 로그와 invalid-json counter 기록 |
| 필수 x/y/z 누락 | 전체 sample 거부, 누락 field 목록 기록 |
| 숫자 변환 실패 | 전체 sample 거부, field 이름만 기록하고 원본 payload는 로그에 남기지 않음 |
| timestamp 누락/오류 | 전체 sample 거부 |
| retained telemetry | 기본적으로 거부해 과거 sample을 신규 데이터로 저장하지 않음 |
| input broker 연결 끊김 | 1초에서 30초까지 exponential backoff로 재연결 |
| output publish 실패 | QoS 1 publish 실패를 오류로 기록하고 연결 복구 후 다음 sample부터 처리 |
| route 설정 오류 | fail-fast로 process 종료 |
| EdgeX device-mqtt 중단 | Bridge 출력은 broker에 남을 수 있지만 장기 재전송을 보장하지 않음 |

Bridge의 영구 store-and-forward는 첫 단계에서 구현하지 않는다. 누락 없는 수집이 필요한
운영 단계에서는 durable MQTT session과 디스크 기반 spool을 별도 설계한다.

## 9. 관측성

Bridge 로그는 한 줄 JSON으로 출력하며 다음 키를 포함한다.

```text
level, event, device_name, source_name, input_topic, output_topic, reason
```

원본 payload와 MQTT password는 로그에 기록하지 않는다. process health는 다음 상태로
판단한다.

- `starting`: route 검증 및 broker 연결 전
- `ready`: input/output broker 연결 완료
- `degraded`: broker 연결 끊김 또는 최근 publish 실패

첫 단계에서는 별도 Prometheus endpoint를 추가하지 않고 로그와 container healthcheck로
검증한다.

## 10. 테스트 설계

### 단위 테스트

- 정확한 input topic이 EdgeX output topic으로 매핑되는지 검증
- x/y/z 숫자 문자열과 JSON number가 `float`로 변환되는지 검증
- 선언되지 않은 status field가 출력에 포함되지 않는지 검증
- timestamp field 우선순위와 정수 변환 검증
- 잘못된 JSON, 필수 field 누락, 숫자 오류, timestamp 오류 거부 검증
- retained message 거부 검증
- route의 topic/device/source 불일치 시 startup 실패 검증

테스트는 실제 변환 함수를 사용하고 broker client만 경계에서 대체한다.

### broker 통합 테스트

테스트 Mosquitto에 factory topic을 publish하고, EdgeX async topic에서 변환된 payload 한
건을 수신하는지 확인한다. QoS는 1, retain은 false로 검증한다.

### EdgeX smoke test

1. EdgeX stable compose와 Device MQTT를 시작한다.
2. Device Profile과 Device가 Core Metadata에 등록됐는지 확인한다.
3. factory topic에 고정 sample을 한 건 publish한다.
4. Core Data에서 device/source 최신 event 한 건을 조회한다.
5. x/y/z 값과 `source_timestamp`가 입력과 일치하는지 확인한다.
6. 해당 canary의 KubeEdge DeviceStatus와 `mqttvirtual` mapper 경로가 비활성 상태인지 확인한다.

## 11. 완료 조건

- Bridge의 모든 단위 테스트가 통과한다.
- Mosquitto broker 통합 테스트가 통과한다.
- EdgeX Core Metadata에 `vib-arduino-acceleration-01`과
  `etri-vibration-mqtt`가 등록된다.
- MQTT sample 한 건이 Core Data의 `telemetry` event로 조회된다.
- 조회된 네 reading이 입력 payload와 일치한다.
- 중앙 서버가 없어도 edge-local 수집과 최신값 조회가 동작한다.
- canary의 inventory, state, telemetry는 EdgeX만 제공하며 MapperFramework,
  `mqttvirtual`, KubeEdge DeviceStatus가 병행 처리하거나 fallback하지 않는다.

## 12. 후속 단계

첫 수직 흐름 완료 후 protocol별 별도 gate로 다음을 진행한다.

1. 나머지 MQTT device를 EdgeX Device MQTT로 batch migration하고 임시 bridge를 제거한다.
2. EdgeX App Service에서 AI service와 장기 storage로 event를 전달한다.
3. Serial Device Service를 실제 장비 endpoint로 검증한다.
4. Modbus Device Service를 실제 register/read-write 정책으로 검증한다.
5. OPC-UA Device Service를 endpoint security와 subscription recovery까지 검증한다.
6. RTSP Device Service/media adapter를 AI/storage consumer까지 검증한다.
