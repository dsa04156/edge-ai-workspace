# 대시보드 어댑터 런타임 관리 구현 계획

> **실행 기준:** 각 작업은 실패 테스트를 먼저 확인하고 최소 구현으로 통과시킨 뒤 관련 회귀
> 테스트를 실행한다. 기존 EdgeMesh와 KubeEdge Device CRD는 어떤 단계에서도 변경하지 않는다.

**목표:** 대시보드에서 기존 EdgeX Device Service runtime을 발견·재사용하거나 승인된
template로 KubeEdge node에 배포하고, EdgeX Profile/Device 등록과 첫 Event 검증까지 하나의
operation으로 관리한다.

**구조:** `state-aggregator`는 browser-facing BFF와 EdgeX saga를 담당한다. 별도
`adapter-controller`가 allowlist template와 `AdapterRuntime` CR을 reconcile하고
Kubernetes write 권한을 독점한다. EdgeX는 물리 Device 권위이며 CR은 workload desired
state만 표현한다.

**기술:** Python 3.12, FastAPI, Pydantic v2, Kubernetes Python client, pytest, Node test
runner, Kubernetes CRD/RBAC/Kustomize, Go Device SDK, Playwright.

## 작업 13: 전체 검증, live canary, main 배포

**자동 검증**

1. Controller Python, state-aggregator Python/Node, EdgeX Go와 repository Python 테스트를 실행한다.
2. `git diff --check`, Kustomize render와 manifest security test를 실행한다.
3. Kubernetes server-side dry-run으로 CRD/Controller 전체를 검증한다.
4. Playwright로 desktop/mobile runtime 목록, wizard validation과 disabled action을 캡처·검증한다.

**live 검증**

1. 현재 Serial/I2C Deployment, EdgeX Device Service, 12개 Device와 latest Event 기준값을 기록한다.
2. runtime inventory가 두 external runtime과 consumer mapping을 정확히 반환하는지 확인한다.
3. 동일 endpoint reuse plan이 runtime은 발견하되 이미 사용 중인 route를 정확히 차단하는지 확인한다.
4. hidden controller canary를 exact-name/TTL로 생성해 readiness, restart와 retire cleanup을 확인한다.
5. canary 외 Deployment/Service/Secret/NetworkPolicy와 EdgeX Device/Profile이 변하지 않았는지 확인한다.
6. EdgeMesh generation/observed generation과 Ready pod가 전후 동일한지 확인한다.

**배포**

1. 변경을 의미 단위로 main에 직접 commit한다.
2. origin/main에 push한다.
3. GitHub Actions가 image build와 digest update를 완료했는지 확인한다.
4. Argo CD `edgex-telemetry`와 `edge-orch-state-aggregator`가 목표 revision에서
   `Synced/Healthy`인지 확인한다.
