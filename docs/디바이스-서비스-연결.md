# 디바이스-서비스 연결

Core Data telemetry freshness는 latest Event의 nanosecond `origin`을 sample 시각으로 계산하며 API 조회 시각이나 Kubernetes 상태로 대체하지 않는다.

## 목적

이 문서는 물리 디바이스와 EdgeX Device Service, 서비스 consumer 사이의 바인딩 계약을 정의한다. 바인딩은 동적 workflow 배치가 아니라 다음 소유·전달 관계다.

```text
physical endpoint
  -> EdgeX Device Service
  -> Device Profile / Device
  -> Event / Reading / Command
  -> AI service / storage / dashboard consumer
```

2026-07-21 현재 기존 `edge-telemetry-agent`와 aggregate `sensehat-001` bootstrap은 퇴역했다. Jetson Arduino Serial과 Raspberry Pi Sense HAT I2C 수직 슬라이스는 각 물리 source를 기능별 6개 가상 Device로 나누는 계약을 사용한다.

## 바인딩 원칙

정상적인 device-service binding은 다음을 함께 가진다.

1. Device Service가 실제 protocol endpoint를 독점 소유한다.
2. Core Metadata에 Device Service, Device Profile, Device가 등록되어 있다.
3. Device의 `profileName`, `serviceName`, `protocols`, `adminState`, `operatingState`를 조회할 수 있다.
4. Device Service가 profile에 맞는 typed Event/Reading을 Core Data에 전달한다.
5. Core Data에서 `deviceName`, `sourceName`, timestamp와 readings를 조회할 수 있다.
6. AI 서비스, 저장소와 dashboard가 같은 device identity를 consumer key로 사용한다.

KubeEdge node/workload 상태는 배치 진단 정보이며 물리 디바이스 inventory/state/telemetry의 권위가 아니다.

## 대시보드 기반 새 바인딩 관리

운영자는 새 장비를 연결할 때 protocol별 Pod manifest를 직접 작성하지 않는다. Dashboard
`Device Management`에서 다음 계약을 함께 검증하고 적용한다.

1. Adapter Catalog의 검증 상태와 승인 hardware binding
2. 기존 Runtime 재사용 또는 Controller 소유 Runtime 배포 plan
3. target KubeEdge node `Ready`와 Device Service Metadata readback
4. Device Profile/resource와 Device protocol binding 충돌
5. Profile/Device Metadata readback과 첫 Core Data Event

기존 `device-serial-jetson`과 `device-sensehat-raspi`는 Argo CD 소유이므로 조회·재사용만
한다. Controller가 만든 runtime만 대시보드에서 재시작할 수 있고, consumer가 0개일 때만
exact-name 확인 뒤 퇴역한다. Modbus/OPC-UA/MQTT/RTSP는 실장비와 typed telemetry 검증 전
`BLOCKED`다. 자세한 절차는
[Adapter Runtime과 Device 연결 관리](ops/어댑터-런타임-디바이스-연결-관리.md)를 따른다.

Dashboard는 protocol/Device Service를 먼저 선택한 뒤 선택 노드의 승인 hardware binding을
보여 준다. Binding은 Serial의 `Port`/`BaudRate`/`DeviceID`, I2C의 `Bus`/`DeviceID`처럼
물리 연결을 식별하는 protocol tuple을 가진다. UI가 이 값을 read-only로 채우고 서버가 선택
binding과 다시 대조한다. 같은 Serial tuple의 여러 `ResourceName`은 reader 하나를 공유하고,
서로 다른 승인 Serial tuple은 같은 `device-serial-jetson` 안에서 별도 reader를 사용한다.
Serial baud는 Device Service와 catalog가 공통으로 허용한
`1200`~`921600` 표준 allowlist 안에서 binding별로 정한다. 따라서 센서마다 Pod를 만들지
않는다. 단, 이 재사용은 같은 serial frame JSON과 지원 resource 계약일 때다. 새 장비의 wire
format이나 resource가 다르면 binding만 추가하지 않고 parser, Device Profile과 Adapter
검증을 먼저 추가한다.

두 번째 USB Serial을 실제로 추가할 때는 다음 항목이 같은 Git 변경에 있어야 한다.

1. host의 stable `/dev/serial/by-id/...` identity와 Pod의 고정 container path
2. `device-serial-jetson` workload의 exact CharDevice 장치 마운트
3. Adapter Controller template의 hardware binding과 external runtime
   `hardwareBindingIds`
4. state-aggregator Adapter Catalog의 같은 `bindingId`, `devicePath`와
   `protocolProperties`

현재 live catalog에는 `jetson-arduino-serial-001` 한 개만 있으므로 두 번째 포트는 아직
선택할 수 없다. `/dev/ttyUSB*`를 dashboard에서 임의 입력하거나 미검증 Pod를 자동 생성하지
않는다. 기존 Device의 물리 binding field를 PATCH해 다른 포트로 이동하는 것도 허용하지
않으며, 새 binding의 신규 Device 연결로 검증한다.

## `/state/devices` 바인딩 필드

| 필드 | 의미 |
|---|---|
| `name` | EdgeX Device identity |
| `source` | authoritative source, 현재 `edgex` |
| `profile_name` | resource 계약을 정의한 Device Profile |
| `device_service_name` | 실제 endpoint를 관리하는 Device Service |
| `protocol_names` | Device가 선언한 protocol 목록 |
| `admin_state` | 운영 허용/잠금 상태 |
| `operating_state` | Device Service가 보고한 장비 상태 |
| `connection_state` | dashboard용 정규화 연결 상태 |
| `device_service_available` | Device Service 경로 가용성 |
| `latest_event_timestamp` | 최신 Core Data Event 시각 |
| `latest_readings` | 최신 Event의 source/resource/value |
| `telemetry_freshness` | `fresh`, `stale`, `no_events` |
| `node_name` | 선택적 Kubernetes 배치 진단값 |

## 정상 바인딩 판단

1. `source=edgex`다.
2. profile, Device Service, protocol 필드가 비어 있지 않다.
3. `admin_state`가 잠금 상태가 아니고 `operating_state=UP`이다.
4. Device Service가 실제 endpoint 연결 상태를 보고한다.
5. 최신 Event가 존재하고 `telemetry_freshness=fresh`다.
6. `latest_readings`가 기대한 resource와 value type을 포함한다.
7. 필요한 consumer가 같은 device identity를 사용한다.

Device Service가 UP이어도 Event가 `stale` 또는 `no_events`이면 `degraded`다. 잠금 또는 DOWN 상태는 `unavailable`이다.

## 실측 센서 서비스 데모 consumer 계약

| 항목 | 현재 계약 |
|---|---|
| physical source | `arduino-001` |
| Device Service | `device-serial-jetson` |
| input Devices | `virtual-acceleration-x-001`, `virtual-acceleration-y-001`, `virtual-acceleration-z-001` |
| input resources | `acceleration_x_raw`, `acceleration_y_raw`, `acceleration_z_raw` |
| consumer | `sensor-anomaly-demo` Deployment, `etri-dev0001-jetorn` |
| discovery | `http://device-serial-jetson.edgex-edge.svc.cluster.local:59910`; 고정 ClusterIP/PodIP/node IP 없음 |
| ingest method | Local Data API recent 조회, 500ms polling, 축별 cursor와 같은 `origin` frame join |
| detector | `online-gaussian-baseline-v1`, warm-up 30, threshold 4.0, anomaly 2연속, clear 3연속 |
| service API | `/api/v1/status`, `/api/v1/results`; read-only derived output |
| central view | `state-aggregator` `/state/service-demo` → dashboard panel |
| raw authority/history | EdgeX Core Metadata/Core Data/PostgreSQL; AI 결과가 raw Device를 대체하지 않음 |

세 축 중 하나라도 같은 `origin`에 없으면 추론 frame으로 처리하지 않는다. pending frame은 10초·1,000개로 제한하고 중복 origin은 무시한다. Local Data 호출이 3회 연속 실패하거나 최신 origin이 10초보다 오래되면 service status는 `degraded`다. 이 바인딩은 고정 서비스 Deployment의 읽기 전용 소비 계약이며 동적 Workflow Builder 실행, EdgeX metadata mutation, command publish 또는 actuator 제어를 활성화하지 않는다.

## 프로토콜별 승격 gate

| 프로토콜 | 현재 상태 | 승격 조건 |
|---|---|---|
| Serial | 정상 경로 검증 | Jetson endpoint, custom Device Service, Profile/Device, typed Event와 dashboard 확인. 실제 분리·복구 시연은 남음 |
| I2C | 정상 경로 검증 | Raspberry Pi Sense HAT endpoint, custom Device Service, 6개 Profile/Device, `Float64` Event·Command·Local API·dashboard 확인. 실제 분리·복구 시연은 남음 |
| MQTT | 조건부 | MQTT-only 장비 또는 local pub/sub 요구가 확인될 때만 broker와 Device Service 배포 |
| Modbus | 미구현 | 주소/register/read-write와 재연결 검증 |
| OPC-UA | 미구현 | endpoint security, node mapping, subscription recovery 검증 |
| RTSP | 별도 media 경로 | Workflow Pod 직접 구독과 상태/결과 metadata 계약 검증 |

후속 프로토콜은 profile 초안이나 과거 fixture만으로 현재 binding에 포함하지 않는다.

## workflow 경계

현재 Workflow Builder는 EdgeX Device 목록과 resource를 조회해 browser 안에서 bind/release dry-run, validation과 execution plan preview만 제공할 수 있다. `sensor-anomaly-demo`는 별도 Argo CD Application으로 배치하는 고정 consumer의 첫 사례이며 Builder가 동적으로 생성한 Pod가 아니다. 같은 node의 consumer는 Service FQDN의 `/api/v3/localdata/device/name/{device}/resource/name/{resource}`를 사용해 최근 구간을 읽고 `edge-ai.io/local-data-client=true` label로 정책 의도를 표시한다. 현재 Flannel CNI에서는 NetworkPolicy가 강제되지 않으므로 이 label은 보안 경계가 아니다.

Serial과 Sense HAT Device Service의 Local Data API는 같은 공통 ring cache 계약을 사용한다. 기본 보존은 최근 10분·series별 최대 10,000 sample이고, 각 서비스가 sample slot 기준 최대 64MiB를 공유한다. `/api/v3/localdata/stats`는 현재 series/sample/할당 bytes와 eviction 원인을 반환한다. 이 메모리 상한에는 Go runtime과 map overhead가 포함되지 않으며 Pod 재시작 시 내용이 초기화된다. SQLite outbox, 중앙 장애 재전송과 장기 history 책임은 이 바인딩에 포함하지 않는다.

이 Local Data API 구현이 Workflow Builder의 Kubernetes apply/delete/restart, EdgeX metadata mutation, command publish, actuator command, runtime migration/offloading을 활성화한 것은 아니다.
