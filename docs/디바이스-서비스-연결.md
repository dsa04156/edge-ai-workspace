# 디바이스-서비스 연결

## 목적

이 문서는 EdgeX cutover 이후 물리 디바이스와 서비스 consumer 사이의 바인딩 계약을 정의한다. 바인딩은 동적 workflow 배치가 아니라 다음 데이터 소유·전달 관계다.

```text
EdgeX Device
  -> Protocol Adapter / edge-telemetry-agent
  -> SQLite outbox / HTTPS gateway / Core Data
  -> AI service / storage / dashboard consumer
```

물리 디바이스의 inventory와 상태 권위는 EdgeX뿐이다.

## 바인딩 원칙

정상적인 device-service binding은 다음 정보를 함께 가진다.

1. Core Metadata에 device가 등록되어 있다.
2. device의 `profileName`, `serviceName`, `protocols`, `adminState`, `operatingState`를 읽을 수 있다.
3. Protocol Adapter가 profile에 맞는 Event를 만들고 agent가 SQLite/HTTPS/Core Data 경로로 전달한다.
4. Core Data 최신 event의 `sourceName`, timestamp, readings를 읽을 수 있다.
5. AI 서비스, 저장소, dashboard는 이 EdgeX 경로의 consumer로 연결된다.

이 바인딩은 runtime scheduling, 자동 재배치, offloading, 자동 복구 또는 actuator 제어를 의미하지 않는다.

## `/state/devices` 바인딩 필드

| 필드 | 바인딩에서의 의미 |
|---|---|
| `name` | EdgeX device identity |
| `source` | authoritative source. 현재 `edgex` |
| `profile_name` | device resource 계약을 정의하는 profile |
| `device_service_name` | 현재 수집 경로를 나타내는 논리 EdgeX Device Service |
| `protocol_names` | 현재 device가 선언한 protocol 목록 |
| `admin_state` | 운영 허용/잠금 상태 |
| `operating_state` | device 운영 상태 |
| `connection_state` | 정규화된 연결 상태 |
| `device_service_available` | Device Service 수집 경로 가용성 |
| `latest_event_timestamp` | 최신 Core Data event 시각 |
| `latest_readings` | 최신 event의 source/resource/value 목록 |
| `telemetry_freshness` | `fresh`, `stale`, `no_events` |
| `node_name` | 선택적 Kubernetes 배치 진단값 |

Core Metadata 이름은 API에서 snake_case로 정규화된다. 즉 `profileName` → `profile_name`, `serviceName` → `device_service_name`, `protocols` → `protocol_names`, `adminState` → `admin_state`, `operatingState` → `operating_state`다.

## 바인딩 예시: Sense HAT I2C

현재 서비스 데모 device는 `sensehat-001`이다.

| 항목 | 계약 |
|---|---|
| device | `sensehat-001` |
| source | `edgex` |
| profile | `etri-sensehat` |
| Device Service | `edge-telemetry-agent` |
| protocol | `i2c` |
| metadata state | `adminState`, `operatingState` |
| connection | `connection_state`, `device_service_available` |
| event | Core Data `sourceName`, event/reading timestamp |
| readings | `latest_readings[].resource_name`, `value_type`, `value`, `units` |
| consumers | AI service, storage, dashboard |

이 예시는 broker-free I2C direct 계약을 설명한다. 실환경의 최신 값은 EdgeX 응답으로 확인해야 하며, 문서 자체는 live 배포 완료 증거가 아니다.

## 서비스 consumer 연결

| consumer | 입력 | 역할 |
|---|---|---|
| AI service | Core Data event/readings | 센서 특징 계산과 상태 추론 입력 |
| storage | EdgeX event stream 또는 consumer가 정규화한 결과 | 이력·분석 저장 |
| dashboard/state-aggregator | Core Metadata device + Core Data latest/history | inventory, 상태, freshness, reading 가시화 |

Consumer는 동일한 EdgeX device identity와 `source_name`/`resource_name`을 유지해야 한다. 별도 inventory나 별도 최신값 조회를 물리 상태 권위로 승격하지 않는다.

## 정상 바인딩 판단

1. `source=edgex`다.
2. profile, Device Service, protocol 필드가 비어 있지 않다.
3. `admin_state`가 잠금 상태가 아니고 `operating_state=UP`이다.
4. `connection_state=connected`이고 `device_service_available=true`다.
5. `latest_event_timestamp`가 존재하고 `telemetry_freshness=fresh`다.
6. `latest_readings`가 기대한 `source_name`과 `resource_name`을 포함한다.
7. 필요한 consumer가 같은 EdgeX event identity를 처리한다.

Event가 `stale` 또는 `no_events`이면 Device Service가 UP이어도 degraded로 해석한다. 잠금 또는 DOWN 상태는 unavailable이다.

## Kubernetes node placement 경계

`node_name`은 EdgeX tags/properties에서 제공될 수 있는 선택적 진단 정보다. AI workload 위치, 네트워크 경로 또는 자원 문제를 설명할 때만 사용한다. Node가 없거나 준비 상태를 확인할 수 없다는 이유만으로 물리 device binding을 끊거나 availability를 낮추지 않는다.

Workflow designer의 node 배치 preview는 read-only dry-run이다. Kubernetes workload 생성·변경, EdgeX device 변경, command 발행을 수행하지 않는다.

## Protocol migration waves

| wave | 상태 | 범위 |
|---|---|---|
| Sense HAT I2C | 현재 검증 fixture | 교체 가능한 `sensehat-001` adapter와 SQLite/HTTPS 경로 |
| MQTT-only adapter | 미배포 조건부 경로 | 실제 장비 또는 local pub/sub 요구를 검증한 뒤에만 broker 사용 |
| Serial | Jetson agent 기반만 배포 | `etri-dev0001-jetorn`의 direct agent/PVC/auth는 준비하지만 별도 adapter/profile, hardware validation, Event acceptance는 아직 필요 |
| Modbus | 미구현 future wave | 주소·register 계약과 현장 검증 필요 |
| OPC-UA | 미구현 future wave | endpoint/security/node mapping 검증 필요 |
| RTSP | 미구현 future wave | Workflow Pod 직접 stream 구독과 metadata/AI 경로 검증 필요 |

후속 protocol은 설계 가능성이나 profile 초안만으로 현재 binding으로 계산하지 않는다. 각 wave가 구현·검증되기 전에는 현재 fixture 성공을 다른 protocol의 성공으로 일반화하지 않는다.

## 생산성 해석

바인딩 정보는 운영자가 device 이름만 보고 여러 시스템을 교차 조회하는 대신 profile, Device Service, protocol, 연결 상태, event freshness, latest readings, consumer 영향 범위를 한 흐름으로 확인하게 한다. 이는 점검 경로 단축과 원인 후보 축소를 설명하는 운영 생산성 지표이며 자동 제어 성능 주장이 아니다.
