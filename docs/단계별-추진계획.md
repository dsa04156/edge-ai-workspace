# 단계별 추진계획

## 현재 단계

현재 단계는 서비스 데모와 통합 운영 가시화가 우선이다.

목표:

1. 디바이스가 실제로 등록되고 관리되는지 보인다.
2. 디바이스와 서비스가 실제로 연결되는지 보인다.
3. 전체 관계와 상태가 대시보드에서 보인다.
4. 옥동 시나리오 등 현장 적용 효과를 생산성 언어로 설명한다.
5. 새 물리 장비 후보의 발견·검색·검토와 승인된 Adapter Runtime, EdgeX Profile/Device
   등록을 분리해 대시보드에서 운영한다.

현재 데모 운영 경로는 `state-aggregator` 중심으로 단순화한다.
워크플로우 실행기, placement engine, workflow reporter, 동적 offloading 계열은 현행 연구 방향과 데모 경로에서 제외한다.

그 다음 정리 산출물:

1. 현재 PoC 범위 정의서

3. 현재 데모 실행/점검 runbook
4. 운영 상태 판단 기준과 troubleshooting guide
5. 실공장 적용성 설명 자료

## 현재 구현 방향

물리 디바이스 연동은 다음 권위 경로로 교체한다.

```text
physical I2C / Serial / Modbus / OPC-UA device
  -> protocol-specific EdgeX Device Service
  -> EdgeX Event / Reading -> central Core Data
  -> AI services / storage / state-aggregator
  -> dashboard / service demo view
```

RTSP frame은 이 telemetry 경로에 넣지 않고 요청 시 Workflow Pod가 직접 구독한다. 카메라 상태와 분석 결과 metadata만 canonical Event로 전달한다. MQTT는 MQTT-only 장비나 명시적 local pub/sub 요구가 실제로 확인된 뒤 별도 Protocol Adapter로 검증한다. 현재 MQTT workload는 없다. 중앙 EdgeX internal MessageBus는 stock Core runtime 내부 구성이지 물리 노드의 northbound 전송 경로가 아니다.

KubeEdge는 edge node와 workload 관리에만 사용한다. MapperFramework, `mqttvirtual`,
KubeEdge Device/DeviceStatus와 mapper direct-to-Influx는 legacy physical integration
경로이며 병행 status/control plane 또는 fallback으로 사용하지 않는다.

2026-07-21 현재 기존 direct Agent/SQLite outbox/aggregate Metadata bootstrap은 퇴역했다.
`edgex-edge`의 Jetson Arduino Serial과 Raspberry Pi Sense HAT I2C Device Service/Profile/Device는
실제 Event/Reading, read-only command, Local Data API와 state-aggregator/dashboard freshness까지
정상 경로를 종단간 검증했다.

2026-07-22 첫 서비스 데모 consumer로 `sensor-anomaly-demo`를 구현했다. 같은 Jetson에서
acceleration X/Y/Z Local Data API를 500ms polling하고 같은 `origin` frame만 결합해
`online-gaussian-baseline-v1` 변화 점수를 계산한다. 중앙 `state-aggregator`와 dashboard는
이 결과와 physical source → Device Service → Device 3개 → AI consumer binding을 read-only로
표시한다. 이는 고정 Deployment이며 동적 workflow orchestration이나
학습된 고장 분류기 구현 완료를 뜻하지 않는다.

2026-07-30 대시보드의 AI Pipeline/Workflow Builder와 전용
`POST /state/device-source-bindings/sample` API를 제거했다. 실행 기능이 없는 browser-local
미리보기가 현재 운영 기능처럼 보이는 혼선을 없애기 위한 정리다. Device Service의
Local Data API와 ring cache는 고정 `sensor-anomaly-demo`가 같은 노드에서 직접 읽는
데이터 경로로 유지한다. Workflow 실행, Kubernetes mutation, EdgeX metadata mutation과
command는 계속 현재 범위에서 제외한다.

실제 증가 raw origin의 live inference/central readback과 browser panel은 통과했다. 2026-07-22
Serial USB driver detach/rebind와 Sense HAT reader process 종료로 두 Device Service의 `DOWN → UP`,
새 local origin과 중앙 Event 재개도 확인했다. 중앙 MessageBus 중단 중 local ring과 AI service는
계속 동작했지만 미전송 Event는 복구 후 replay되지 않았다. 다음 현장 검증은 실제 장치 움직임
anomaly와 케이블·보드 손분리 시연이다. Modbus, OPC-UA, 다른 I2C 장비·주소와 RTSP workflow는
protocol별 migration gate 전까지 완료로 주장하지 않는다.

2026-07-22에는 중앙 Core Data REST → PostgreSQL 저장 기준선을 추가했다. 1,000개 합성 identity가
각 1분에 한 번 보내는 약 16.7 events/s는 1,000/1,000 저장과 p95 16.17ms로 통과했다. 반면
1,000개 × 1Hz는 현재 Core Data resource limit 300m CPU/256Mi memory에서 OOMKilled로 실패했다.
따라서 “1,000개”라는 inventory 수만으로 batch 저장을 먼저 도입하지 않고 실제 device별 Hz와
resource 수를 산정한다. 다음 저장 성능 gate는 100/250/500 events/s 단계별 시험, Core Data
memory profile·right-sizing, PostgreSQL retention/index 관측, Device Service → MessageBus → Core Data
전체 경로 시험 순서다. 1Hz는 이 gate 전까지 운영 지원 처리량으로 주장하지 않는다.

2026-07-23에는 `Device Management`를 Adapter Runtime과 EdgeX Device 연결 관리 경로로
승격했다. `state-aggregator`는 브라우저용 BFF와 connection saga를 담당하고 Kubernetes
쓰기 권한은 갖지 않는다. 별도 `edgex-adapter-controller`가 `edgex-edge` namespace의
`AdapterRuntime` CR, Deployment, Service, ConfigMap과 NetworkPolicy만 관리한다. 현재
Serial/I2C Argo runtime은 조회·재사용만 하며, 신규 배포는 Git allowlist의 검증 완료
template와 빈 hardware binding이 있을 때만 허용한다. MQTT는 공식 immutable
`device-mqtt:4.0.2`, 제한된 network binding/runtime setting과 bundled 온도 Profile을
묶은 개발 package로 웹 연결 자동화 범위에 승격했다. Modbus는 exact simulator binding만
개발 검증됐고 실제 PLC, 운영 MQTT TLS/auth, OPC-UA와 RTSP는 여전히 미검증이다.
이 기능은 Workflow Builder, runtime migration 또는 동적 offloading을 구현한
것이 아니다.

Adapter Runtime·Device 연결 관리의 현재 완료 gate:

1. Runtime 조회와 plan이 exact adapter/node/hardware binding, KubeEdge node Ready와 EdgeX
   Device Service readback을 함께 확인한다.
2. 외부/Argo runtime은 재사용만 가능하고 Controller가 만든 runtime만 재시작·퇴역한다.
3. Runtime 배포 뒤 `SERVICE_READY`가 되어야 EdgeX Profile/Device mutation을 시작한다.
4. Device/connection/runtime 및 후보 mutation은 browser 관리자 token 없이
   idempotency key, 내부 HMAC과 namespace별 Secret을 사용한다. 내부 HMAC은
   state-aggregator와 Controller 사이 요청 무결성용이며 운영자 인증이 아니다. 현재
   무인증 BFF는 접근이 제한된 개발 테스트베드 경계로 두고 운영 노출 전 별도 인증·인가를
   추가한다.
5. 임의 image/hostPath/고정 IP/EdgeMesh/KubeEdge Device CRD 입력 경로가 없다.
6. Metadata readback과 first Event를 분리하고 신규 runtime 이후 실패만 consumer-safe하게
   보상한다.

2026-07-24에는 후보 staging을 프로토콜 독립형 Discovery와 Registration control plane으로
승격했다. `edge-device-discovery` DaemonSet은 중앙 Discovery Plan의 allowlist 안에서
USB Serial stable identity와 선택적 WHOAMI, I2C identity rule을 실행한다. Adapter
Controller는 candidate, 상태 전이, Plan, 승인, Registration Saga와 audit를 PVC SQLite에
영속 저장하고 기존 ConfigMap은 최초 1회 import한다. Device Catalog exact match, 운영자
승인, 외부 인증, 실제 Runtime image digest, EdgeX Metadata readback과 Core Data first
Event를 모두 통과해야 `EVENT_CONFIRMED`가 된다.

장비 발견 후보 관리의 현재 완료 gate:

1. Serial은 stable ID, PTY Manifest/telemetry, invalid/timeout, disconnect/reconnect를
   자동 테스트한다.
2. I2C는 allowlist bus/address의 단일·복합 identity register와 mock test가 있고 bus
   파일만으로 candidate를 만들지 않는다. 2026-07-28 dev0003 Sense HAT v1의 네 chip
   identity, 후보 승인, 기존 Runtime/Profile/Device 재사용과 신규 first Event를 live
   검증했다. 다른 I2C 모델은 별도 gate다.
3. MQTT discovery는 자기등록 schema parser까지만 구현했고 subscriber는 없다. 별도의
   웹 connection 경로는 운영자가 허용 broker와 Device 정보를 입력해 검증된 Device
   Service/Profile/Device/first Event를 처리한다. Modbus/OPC-UA/ONVIF scanner는
   `not implemented`를 명시하며 가짜 후보를 반환하지 않는다.
4. `present`/`stale`/`declared`는 후보 evidence이며 EdgeX Device inventory,
   `operatingState`, 통신 성공과 first Event를 대신하지 않는다.
5. 상태 머신은 `DETECTED`부터 `EVENT_CONFIRMED`까지 임의 점프를 거부하고 실패·인증
   차단·재시도와 이력을 저장한다.
6. 승인 전에는 EdgeX Profile/Device를 만들지 않으며, 승인 후 실제 first Event까지
   확인한다.
7. Saga는 Controller가 이번 attempt에서 만든 리소스만 rollback하고 기존 Runtime/Profile/
   Device를 보존한다.
8. 후보 registry는 KubeEdge Device CRD나 장기 telemetry inventory가 아니다. 최종
   Profile/Device, state와 Event authority는 EdgeX에 남는다.
9. UI/API에는 임의 image, command, privileged 설정, 입력형 hostPath, 고정 IP와 EdgeMesh
   변경 경로가 없다.

Sense HAT 능동 탐색은 일반 Agent의 권한을 넓히지 않고 별도 node-scoped DaemonSet으로
분리했다. 일반 Agent는 dev0001/dev0002/dev0003에서 non-privileged read-only Serial
inventory를 유지한다. dev0003의 Serial/I2C report는 `scannedProtocols`로 분리해 한
Agent가 다른 protocol 후보를 `STALE` 처리하지 않는다. dev0003 CH340 USB Serial은 passive
후보로 확인했지만 exact Catalog binding이 없어 `BLOCKED`로 유지한다.
I2C 전용 Agent는 container device cgroup 제약 때문에 dev0003의 exact `/dev/i2c-1`에만
privileged 예외를 사용하며 non-root와 host i2c group을 함께 적용한다. 대시보드나 API가
이 권한·hostPath를 동적으로 바꾸는 경로는 없다.

다음 protocol 확장 순서는 실장비 endpoint 확보 → Device Profile/resource 계약 →
Device Service image 검증 → hardware binding allowlist → template 검토 → 대시보드 배포
승격이다. 센서가 들어올 때마다 임의 Pod manifest를 화면에 입력하는 방식은 사용하지 않는다.

## 현재 범위에서 제외하는 경로

다음 경로는 현재 연구 방향에서 진행하지 않는다.
새 문서나 발표자료에서 현재 예정된 기능처럼 표현하지 않는다.

- 동적 workflow 분해/실행
- runtime replanning
- placement engine 기반 자동 재배치
- cost model 기반 offloading 판단
- workflow_executor 중심 orchestration
- workflow_reporter 중심 stage event pipeline
- agent-assisted planning layer
- LLM이 전체 플랫폼 제어를 수행하는 구조
- 전체 플랫폼 자율 제어형 orchestration

위 항목들은 필요한 경우 과거 검토/실험 자료 또는 archive로만 다룬다.

## 첫 서비스 데모 완료 gate

1. `sensor-anomaly-demo`가 `etri-dev0001-jetorn`에서 Ready이고 immutable ARM64 image를 실행한다.
2. Service FQDN으로 `device-serial-jetson` Local Data API를 사용하며 고정 IP 경로가 없다.
3. `/api/v1/status`를 두 번 조회할 때 세 acceleration Device identity가 같고 `latest.origin`과 `framesProcessed`가 증가한다.
4. model은 30 sample warm-up 뒤 `ready`이고 score가 유한하다.
5. 중앙 `/state/service-demo`와 dashboard가 같은 derived result를 표시하고 관측 실패 때 가짜 0을 만들지 않는다.
6. EdgeX `/state/devices`의 세 raw Device가 계속 `available`·`fresh`이며 AI 결과가 physical inventory 권위를 대체하지 않는다.
7. anomaly/clear 상태 전이는 결정론적 테스트로 검증한다. 실제 장치 움직임 anomaly는 현장 시연 전까지 미완료로 남긴다.

## 2차년도 설계 방향

2차년도 협약 방향에서는 현재 운영 가시화 PoC를 기반으로 다음 설계를 별도 트랙으로 추진한다.
이 내용은 현재 기능 완료 주장이 아니라 설계 및 프로토타입 방향이다.

1. 물리 온디바이스의 기능, 상태, 자원, 입출력을 엣지 AI 서버 쪽 가상디바이스 인스턴스로 표현한다.
2. 디바이스트윈은 raw telemetry 저장소가 아니라 상태, capability, resource, I/O, workflow binding snapshot으로 둔다.
3. AI 서비스를 workflow stage로 분해하고, 가상디바이스를 stage input/output 또는 실행 후보로 동적으로 연결한다.
4. 웹페이지는 단순 dashboard가 아니라 가상디바이스 풀, twin inspector, workflow canvas, binding/validation, execution plan을 포함하는 워크플로우 통합 개발도구로 설계한다.
5. `test_device.py` 기반 가짜 MQTT publisher는 이 방향의 가상디바이스 정의로 사용하지 않고 legacy test 경로로만 취급한다.

## 다음 작업 기록: Runtime Resource Augmentation Scheduler v1

기록일: 2026-06-19

현재 완료된 것은 자원증강 리소스의 등록, 상태 집계, dashboard 가시화, dry-run/validation 중심의 실행 계획 확인이다.
`AugmentationResource`와 `DeviceAugmentation` 상태가 Ready/Available로 보이고, state-aggregator API와 dashboard에서 이를 확인할 수 있다.
다만 이 상태는 실제 AI workload offloading이나 runtime migration이 이미 동작한다는 뜻은 아니다.

다음 구현 후보는 `Runtime Resource Augmentation Scheduler v1`이다.
목표는 버튼으로 임의 Job을 만드는 것이 아니라, 이미 수집 중인 pod/service 사용량과
`AugmentationResource`/`DeviceAugmentation` 상태를 결합해 자원증강이 필요한 workload와
선택 가능한 보강 resource를 자동으로 판단하는 최소 경로를 검증하는 것이다.

범위:

1. `state-aggregator`가 관측 중인 pod/service CPU/GPU/memory 사용량을 자원증강 판단 입력으로 정규화한다.
2. 대상 workload, target edge device, 필요한 capability를 `DeviceAugmentation`과 연결한다.
3. `AugmentationResource` 후보 중 Available/Ready, endpointReady, capability 조건을 만족하는 자원을 선택한다.
4. scheduler policy는 v1에서 threshold/rule 기반으로 시작하고, cost model 기반 전역 최적화는 후속으로 둔다.
5. 결과는 실행 artifact가 아니라 `recommendation/status`로 노출한다: pressure reason, selected resource, confidence, apply state.
6. dashboard는 수동 실행 버튼이 아니라 현재 부하, 증강 필요성, 선택 자원, 적용 상태를 보여준다.

검증 기준:

1. pod/service usage snapshot이 특정 workload와 resource profile에 매핑된다.
2. resource pressure가 있을 때만 증강 recommendation이 생성된다.
3. `AugmentationResource`가 Available/Ready가 아니면 selected resource로 사용하지 않는다.
4. dashboard에서 recommendation의 근거와 선택 자원이 설명 가능하게 보인다.
5. 기존 DeviceStatus/raw telemetry 분리 정책을 깨지 않는다.
6. dashboard/API가 직접 Kubernetes workload mutation을 수행하지 않는다.

명시적으로 제외하는 것:

- 버튼 클릭마다 Kubernetes Job을 생성하는 방식
- 고정 vibration sample 또는 dummy payload를 analyzer로 보내는 smoke-test 실행
- placement engine 기반 자동 재배치
- runtime migration
- cost model 기반 offloading 최적화
- legacy `workflow_executor`/`placement_engine`의 무조건 승격
- LLM 또는 agent가 전체 플랫폼 제어를 수행하는 구조
