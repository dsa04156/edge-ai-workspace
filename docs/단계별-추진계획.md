# 2026년도 2차년도 옥동 PoC 추진계획(안)

## 2026-09-08 통합 운영 대시보드 확장

기존 NEXUS의 서비스 관측·이력·데이터 비교와 서버 설계 버전·시험 원장 저장을 로컬 구현한다. 저장은 Configured이며 범용 실행·오프로딩과 운영 배포는 별도다. 범위·API·검증은 [통합 운영 대시보드 고도화](통합-운영-대시보드-고도화.md)를 따른다.

## 2026-09-08 가상 디바이스 운영 사이클

사용자 승인 구현 범위는 `virtual-device-test/vd-demo-001` 한 개의 시작·시험 추론·정지와 영속 작업 이력이다. `state-aggregator/app/virtual_device_control.py`가 기존 운영 토큰, 고정 계약과 SQLite 요청 원장을 사용하고 `static/virtual-device-controls.js`가 NEXUS 내부 가상 디바이스 화면에 연결된다. Argo CD `edge-orch-state-aggregator`는 UI/API 및 해당 이름의 `/scale` 권한을 배포한다. 시험 Deployment 자체는 기존 독립 경로를 유지한다. 상세 경계와 검증 gate는 [프로젝트 범위](프로젝트-범위.md)의 가상 디바이스 운영 사이클 절을 따른다. 범용 워크플로우 실행·오프로딩·옥동 현장 모델 실증 완료를 뜻하지 않는다.

> 이 문서는 보고서 본문용 추진계획이다. 아래 내용은 2차년도 목표이며 현재 구현 완료
> 상태를 뜻하지 않는다. 세부 데이터 항목, 기술 설계, 장애 시나리오, 화면 목록과 실제 검증 결과는 문서 하단의 별첨 기준 문서에서 관리한다.

> 현재 테스트베드에서는 HAMi GPU와 CUDA readiness를 사용하는 Server1 observed-only 후보까지 운영한다. 2026-08-18 현재 통계 기준선 후보는 90-run 부하 실험에서 성능 자격이 거부됐다. 이는 10월 엣지·서버 배치 검토의 선행 증거이며 승인 기반 요청 전환 완료를 뜻하지 않는다.

> 2026-08-25 승인된 선행 구현 범위는 서비스 자원 프로파일과 노드 자원 snapshot을 이용한 **신규 단일 replica Deployment 생성**까지다. 전용 namespace, immutable image allowlist, exact-node placement와 Pod Ready 확인을 포함하지만 기존 workload migration, offloading, runtime replanning과 자동 장애복구를 완료 기능으로 포함하지 않는다.

> Runtime Recommendation은 자원·서비스 지표로 증강/대체 필요성과 후보를 read-only로 추천하고 dwell/cooldown 이력을 남기지만 자동 배포·전환·삭제는 하지 않는다. 별도 승인 Controller의 candidate 생성, SHADOW validation, Lease handoff/rollback과 core `Endpoints` 전환은 2026-08-26 격리 시험에서 확인했다. production은 Argo CD selector와 EndpointSlice 계약을 유지하므로 traffic 단계가 `routing_mode_unsupported`로 차단되고, 기존 workload 종료·candidate promotion·자동 정리도 지원하지 않는다.

> Jetson 수집·저장을 유지하고 Server1에 추론만 요청하는 LOCAL/REMOTE/LOCAL_FALLBACK도 격리 시험에서 확인했다. 2026-08-28 현재 관련 코드는 테스트를 통과했지만 미커밋·미배포이며, Server1 성능 자격은 `rejected`이므로 범용 offloading이나 운영 요청 전환 완료가 아니다.

## 1. 추진 배경

2026-09-07 추가 승인된 선행 자격시험은 별도 Llama 시연 버튼의 GPU 임시 확보,
고정 부하·Nano→RTX 5080 신규 요청 전환, 종료·중단·재시작 후 원 소유 서비스 복원이다.
운영 책임은 시연 운영자에게 있으며, 실제 응답 identity·READY 선행·부하 감소 후 복귀·
GPU 예약 반환 및 원 서비스 Ready를 검증한다. 실제 AGX/DGX와 옥동 서비스 2종의
실증 완료를 대신하지 않는다. 상세 범위는 [프로젝트 범위](프로젝트-범위.md)를 따른다.

2차년도에는 대규모 혼합 디바이스 제어·관리 플랫폼의 요소기술을 개발하고 프로토타입을
구축한다.

2026년 7월 29일 옥동 현장회의 결과, 신규 장비가 필요한 서비스보다 현재 확보된
PLC·MES·센서 데이터를 활용할 수 있는 서비스를 우선 추진하기로 하였다.

우선 실증 대상은 다음과 같다.

- 센서·MES 데이터 기반 생산품질 양품·불량 판별
- 메인·보조 유압펌프 및 모터 이상 감지

두 서비스는 개별 AI 모델 개발에 그치지 않고, 플랫폼의 데이터 수집·서비스 배포·장애복구
기능을 검증하는 대표 PoC 시나리오로 활용한다.

## 2026-09-11 AI 추론 지표·승인 기반 증강

사용자 요청으로 NEXUS 자원·오프로딩 화면에 AI 추론의 실측 지연·처리량·대기 요청,
제한된 부하 시험, 추천 후보와 승인 버튼을 추가한다. 첫 대상은 공통 RuntimeService의
`llama-inference`(실제 AGX·Spark, 고정 모델·8토큰)다. `policy.approvalRequired`로
승인 대기를 명시하며 추천만으로 대상 모델을 준비하거나 요청 경로를 전환하지 않는다.
승인 API는 서비스 UID·추천 ID·최신 후보 자격을 재검증하고 기존 제어기의 준비·전환·drain을
사용한다. 기존 추론은 준비 중 계속 처리하며, 저부하 복귀·중지·장애 처리는 기존 정책을 따른다.
센서 수집·EdgeX·서비스 설계 dry-run에는 쓰기를 추가하지 않는다.

운영 소유자는 기존 runtime-operator(원장·모델 수명주기)와 state-aggregator(화면·동일 출처
제한 API)다. 검증 기준은 승인 전 무전환, 만료/중복/재시작/후보 변경 처리, 제한 부하의
중지·요청 원장, 승인 후 실제 경로·결과 확인이다. 자동시험·브라우저 검증과 실장비 승인
실행 증거를 구분하며 실제 증강 승인은 사용자 클릭으로 수행한다. 상세는
[AI 서비스 증강 승인](AI-서비스-증강-승인.md)을 따른다.


### 2026-09-11 Llama 승인 증강 3단계 확대
사용자 승인 범위를 Orin Nano(`etri-dev0001-jetorn`) → AGX Orin(`etri-dev0005-jetagx`) → DGX Spark(`etri-ser0003-cg0ms0`)로 확대한다. `edge-orch/runtime-operator`의 명시적 단계 순서와 `examples/llama-three-tier`의 Llama 계약·Nano resident runtime을 사용한다. 부하/지연에 따른 증강은 바로 다음 단계만 추천하고 운영자가 매번 승인한다. 저부하 복귀는 기존 자동 정책 안에서 단계별로 수행한다. 장애 시 가용 후보 복구는 별도 사유로 표시한다. 센서 수집과 기존 legacy controller 중지 상태는 유지한다. Nano 모델 digest·GPU 실제 실행·동일 8-token 입력의 처리 성능·자원 예약, 3단계 순서 및 승인·중지 회귀 테스트, 실제 노드 지도와 API를 검증해야 운영 완료로 보고한다. 런타임/계약 소유자는 runtime-operator 운영자이며 대시보드는 기존 Argo CD 배포를 따른다. 3단계 계약·지도 배포와 Nano GPU/gateway 응답, 센서 Device Service Ready를 확인했다. 단계별 승인·역순 복귀는 자동시험으로 검증했다. 운영에서 두 번의 승인 클릭을 포함한 실장비 왕복은 아직 수행하지 않았으며 사용자가 실행한다. 상세 실측과 경계는 `docs/AI-서비스-증강-승인.md`를 따른다.


### Llama 무부하 자동 축소·복귀 (2026-09-14)

기존 승인형 3단계 resident AI 서비스에 무부하 복귀 판단을 추가한다. 최근 응답 표본이 없으면 지연 회복을 판단할 수 없어 상위 노드에 남던 문제를 수정한다. 현재 노드의 정상 관측, gateway 대기·처리와 worker 처리 0건, 최근 window의 유입·완료·실패 기록 없음, 새 프로세스/전환 후 window 관측과 추가 returnSeconds 유지를 모두 확인한다. 현재 Llama 계약은 20초 window + 8초 유지이며 cooldown·후보 qualification·readiness·drain 조건도 유지한다.

증강은 운영자 승인, 무부하 복귀는 Spark → Orin → Nano 순서로 자동 수행한다. 요청 재유입은 무부하 대기를 초기화하고 준비 중인 무부하 복귀를 취소한다. 관측 실패·긴 관측 공백·제어기 재시작 후에는 새 관측부터 시작한다. 대시보드 `/state/runtime-services`의 `returnState`는 확인·대기·모델 준비·상위 메모리 해제·기본 노드·보류 상태를 표시한다. GPU 예약·worker Pod는 유지하며 모델 메모리만 해제한다. 실행 책임은 runtime-operator 운영자, 화면 배포는 기존 Argo CD 소유다. 검증은 무요청 역순 복귀, 재유입·실패·중간 노드 제한·재시작 회귀 및 실장비 관측으로 구분한다.


### 기존 서비스 선택·운영과 서비스 부하 (2026-09-14)

사용자 승인 범위는 기존 `llama-inference`, `quality-api-demo`,
`telemetry-transform-demo` 선택과 운영, 서비스 단위 부하다. 새 서비스 생성·복제는
포함하지 않는다. Llama는 실제 추론, 나머지 둘은 합성 HTTP 시험으로 구분한다.
NEXUS `/#offload-demo`에서 선택한 서비스 UID에 지도·실행/중지·요청 지표·추천과
이력을 묶는다. 선택은 `runtimeService` URL 값으로 유지하며, 삭제된 UID를 다른
서비스로 자동 치환하지 않는다. 서비스 설계 dry-run과 센서 수집 경계는 유지한다.

`spec.demo`가 명시된 기존 서비스만 시작·중지할 수 있다. `service-load`는 계약에
등록된 고정 입력과 동시성으로 제거할 때까지 요청을 보낸다. 노드 전환 후 신규 요청은
같은 서비스의 새 경로를 따르며, 이미 전달한 요청은 다른 노드에서 재실행하지 않는다.
부하 제거는 exact service UID/run ID에 한정하고 다른 서비스와 서비스 실행을 유지한다.
개별 노드 시험 `node-load`는 카드의 펼침 메뉴에 유지하며 노드 변경 시 종료한다.
서비스별 동시 시험 1개·전체 2개, 종료 후 10초 대기, 재시작 시 자동 재실행 금지와
미완료 요청 식별을 유지한다. 지속 부하의 최근 응답 목록은 64개와 진행 중 요청으로
제한하고 전체 dispatch 원장은 기존 저장소에 남긴다.

Llama 증강은 운영자가 매 단계 직접 승인하고 무부하 시 기존 정책으로 역순 복귀한다.
HTTP 시험 서비스는 기존 자동 배치·복귀 정책을 따른다. runtime-operator 운영자는
계약·부하·제어 원장을 소유하고, aggregator는 기존 Argo CD Application으로 배포한다.
검증 기준은 UID 격리·노드 전환 후 부하 지속·부하 제거·서비스 중지/재시작·관측 장애·
데스크톱/모바일 선택 유지이며, 실제 AI 승인 왕복과 HTTP 자동 전환 시험을 구분한다.


## AI 서비스 목록과 공통 자동 운영 (2026-09-14 현재 기준)

사용자의 최신 요구로 OFFLOAD DEMO를 AI 서비스 목록·선택 운영 화면으로 확장한다.
이 절이 위의 Llama 직접 승인 기본값을 대체한다. `llama-inference`는
`serviceKind: ai`, `policy.mode: automatic`, `approvalRequired: false`로 자동 증강·복귀한다.
서비스별 승인 정책은 호환 옵션으로 남긴다. 기존 별도 Llama 제어기는 계속 중지한다.

- 공통 `RuntimeService`의 AI 판별은 모델명이 아니라 `serviceKind: ai`다.
  기존 resident Llama inference 계약도 호환한다. 일반 HTTP AI도 동일한 배치·준비·전환·
  drain·복귀와 서비스별 부하 시작/제거를 사용한다. 단계는 계약에 선언된 후보 순서다.
- 대시보드는 AI 목록에서 상태·실행 위치·운영 방식·시험 부하를 표시하고, 선택 UID의
  지표·노드 경로·CPU/메모리/GPU/온도·실행/중지·부하 시작/제거를 연결한다.
  HTTP 합성 시험 서비스는 AI 목록과 구분한다. 지연 정책이 없어도 요청 실측을 제공한다.
- 기존 `/state/services`의 AI 서비스도 목록에 포함하되 공통 실행 계약에 미연결이면
  기존 배치·실행 권한·후보 자격 사유와 제어 불가를 표시한다. `sensor-anomaly-demo`의
  STANDBY와 후보 qualification 거부를 정상 추론 또는 자동 전환 성공으로 설명하지 않는다.
- 모든 AI 모델을 코드 분기 없이 등록할 수 있는 공통 경로를 제공한다. 임의 기존 Pod를
  자동 복제하거나 미검증 모델을 이동시키지는 않는다. 실행 이미지·호환 노드·입출력·
  readiness·자원/성능 검증이 필요하며 부하 시험에는 고정 시험 입력을 등록한다.
- 책임: platform-runtime 운영자가 계약·후보 qualification·제어기 배포를 관리한다.
  state-aggregator는 기존 Argo CD 경로로 배포한다. 센서 수집·EdgeX 권위·설계 dry-run은 유지한다.
- 검증 기준: 모델명 무관 AI 자동 증강/무요청 복귀, 실행체 장애 대체, 후보 불가 보류,
  UID별 부하 격리·중지, stale 지표 제거, 목록 선택 유지, 실제 Llama 자동 왕복과 부하 제거.
  자동시험과 실장비 증거는 `edge-orch/runtime-operator/results/2026-09-14-ai-operations/`에 구분한다.

공통 등록 요건은 [AI 서비스 공통 운영](AI-서비스-공통-운영.md)을 따른다.


### AI 노드 부하 지속 및 용량 기반 복귀 정책 (2026-09-14 후속)

이 절은 앞선 노드 이동 시 시험 종료, AI 공통 서비스 부하 버튼과 짧은 복귀 대기 규칙을 대체한다.
AI 서비스는 현재 실행 노드의 버튼으로 시험을 시작하고, 같은 서비스 UID/run ID의 요청을
이동한 실행 경로에 계속 보낸다. 부하 제거 버튼은 현재 부하 실행 노드에 표시한다.
운영자가 제거하거나 서비스를 중지하면 새 요청과 미전송 대기는 취소하고 전송된 요청은 마무리한다.
제어기 재시작은 시험을 Interrupted로 종료하며 자동 재전송하지 않는다.

증강은 대기 요청이 있고 동시 처리 한도 대비 부하가 highWatermark 이상으로 pressureSeconds
유지되거나, 유효한 p95가 maxP95Milliseconds를 breachSeconds 초과할 때 판단한다.
단일 요청 처리 중이라는 이유만으로 증강하지 않는다. 복귀 후보는 노드·실행체 가용성과 검증
지연 조건 외에 최근 window의 서비스 전체 유입률이 후보 qualifiedRps × highWatermark 이하인지
확인한다. 경로 변경 전후 유입은 같은 서비스 UID로 합산한다. 현재 처리 한도의 lowWatermark
이하 부하와 지연 회복, 또는 완전 무부하가 returnSeconds 유지되어야 한다.
프로세스 재시작·관측 실패·15초 이상 관측 공백 뒤에는 관측 window와 지속 시간을 새로 쌓는다.

첫 Llama 적용값은 대기·p95 초과 10초, 복귀 조건 유지 60초, 전환 후 재판단 대기 60초다.
window 20초, p95 표본 10개, 증강 900ms/복귀 750ms, highWatermark 0.8을 사용한다.
무부하 복귀는 각 단계에서 최근 유입·응답이 사라진 뒤 60초를 추가 확인하므로 즉시 내려가지 않는다.
후보 검증 요청률은 해당 고정 입력에서 측정한 운용점이며 모든 AI 입력의 최대 성능 보장이 아니다.
대시보드는 지속 시간·재판단 대기·복귀 허용 유입률·보류 이유를 최신 관측에 한해 표시한다.

운영 책임은 runtime-operator의 계약·측정·배치 소유자이며 화면 배포는 기존 Argo CD를 따른다.
변경 경로는 runtime-operator의 controller/latency/demo와 state-aggregator의 common_runtime 및
NEXUS 공통 운영 화면이다. 등록된 AI 공통 계약에 적용하며 EdgeX 센서 수집과 서비스 설계 dry-run의
권한은 확장하지 않는다. 검증 기준은 경로 이동 후 동일 부하 유지, 정확한 실행 ID 제거,
단일 처리·지속 대기 구분, 하위 용량 부족 복귀 차단, 관측 공백 시 시간 초기화, 실제 3단계 왕복이다.


### 요청 진단 기록 (2026-09-14)

공통 runtime의 유효 서비스 UID·요청 ID별 시도를 수신부터 종료까지 별도 진단 원장에 기록한다.
전송 전 거절·대기 초과도 보존하며, 전송 원장의 재실행 방지 의미는 바꾸지 않는다.
진입 노드와 실제 처리 노드, gateway 대기·worker 왕복·worker 보고 추론 시간, HTTP 상태와
정규화한 실패 사유를 저장한다. 입력·응답 본문과 원시 예외 문자열은 진단 기록에 포함하지 않는다.
종료 기록은 최대 7일, 실패·미확인과 그 밖의 기록 각각 10,000건을 60초 간격으로 정리한다.
재시작 당시 미종료 요청은 전송 전 중단/전송 후 결과 미확인으로 구분한다.
대시보드의 서비스별 요청 진단 기록은 실패·미확인/전체 요청, 수동 새로고침과 페이지 조회를
제공한다. 과거 수집 전의 실패 사유는 복원하거나 추정하지 않는다. 소유자는 runtime-operator
운영자이며 dashboard는 기존 Argo CD 배포를 따른다. 검증은 전송 전 실패 영속성·재시작·UID
격리·페이지 경계·원시 입력 비노출·재조회 무재전송 및 실제 고정 입력 요청과 부하 시험을 포함한다.


## 2026-09-15 범용 모델 실행 연결 1차

사용자의 구현 요청에 따라 기존 runtime-operator에 선택적인 JSON 텐서 V2 추론 adapter를
추가하고, 학습된 손글씨 숫자 분류 모델을 두 번째 실제 AI 실행 검증 서비스로 연결한다.
첫 범위는 독립 요청의 실행·결과 검증·준비 후 경로 전환·drain·중지와 기존 노드별 시험 버튼
재사용이다. 기존 Llama·EdgeX 입력과 수집을 유지하고 legacy workflow를 사용하지 않는다.
새 모델은 실행 검증을 마친 노드만 후보로 등록하고 성능 자격을 별도로 측정하기 전에는
선호 배치 모드로 운영한다. 성능값을 추정해 과부하 자동 이동을 활성화하지 않는다.
기존 Llama의 자동 정책은 유지한다. 담당은 platform-runtime 운영자이며 검증 기준은
ARM64/AMD64 실제 모델 결과, 모델 identity 거부, 신규 요청 경로 전환, 중지·자원 반환,
서비스 격리와 대시보드 연결이다. 합성 HTTP 응답이나 현장 옥동 판별 모델로 설명하지 않는다.
구현·운영 결과는 후속 실측 기록으로 구분한다.
