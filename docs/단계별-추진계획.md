# 단계별 추진계획

## 추진 원칙

2차년도에는 서비스 데모를 먼저 완성하고, 그 위에 디바이스·서비스 연결과 장애 대응을 쌓는다. 동적 workflow, offloading, agent-assisted planning은 현재 운영 목표가 아니라 후속 설계 트랙이다.

## 단계 0: 범위·데이터 확정 (8월)

### 할 일

- PLC·MES·센서·카메라 목록과 실제 소유 노드 확정
- 품질 판별과 펌프·모터 이상감지의 입력·출력·주기·생산 건 연결키 확정
- Device/Profile/Protocol Adapter/서비스 담당자 지정
- 현재 checkout과 live 배포 차이 목록화

### 통과 조건

- 각 입력에 endpoint, sample 주기, 책임자, 장애 연락 경로가 있다.
- EdgeX Device/Profile과 서비스 binding 초안이 있다.
- 지원하지 않는 protocol은 미지원으로 표시한다.

## 단계 1: 수집·저장 수직 슬라이스 (9월)

### 할 일

- Protocol Adapter가 canonical EdgeX v3 Event 생성
- edge agent가 SQLite WAL outbox에 먼저 저장
- HTTPS/mTLS gateway가 Core Data persisted ACK 제공
- Core Data/PostgreSQL에서 Event history와 latest freshness 조회

### 통과 조건

- 동일 Event ID가 outbox→gateway→Core Data에서 추적된다.
- 중앙 연결 단절 중 데이터가 보존되고 복구 후 FIFO로 재전송된다.
- 중복 replay와 payload conflict가 구분된다.

## 단계 2: AI 서비스 연결 (10월)

### 품질 판별

- MES 생산 건과 센서 window join
- 전처리·모델·결과 schema 컨테이너화
- 양품/불량/unknown과 confidence 저장

### 펌프·모터 이상감지

- 진동 3축·전류·온도 입력 정렬
- anomaly score·severity·reason code 저장
- 입력 결측·stale 시 결과 보류 또는 unknown

### 통과 조건

- 같은 input window를 재실행해 같은 결과를 얻는다.
- model version과 source Event ID를 결과에서 역추적한다.

## 단계 3: 분산 실행·장애 검증 (11월)

- 노드 자원·GPU·memory를 기준으로 실행 후보를 표시한다.
- KubeEdge/Kubernetes에서 서비스 Pod의 배치와 재시작을 검증한다.
- 통신 단절, Core Data 장애, 모델 Pod 실패를 구분한다.
- 자동 migration/offloading은 실행하지 않고 정책·preview까지만 검증한다.

## 단계 4: 통합 PoC (12월)

```text
Device 등록 → 수집 → 전처리 → 추론 → 결과 저장
     → 알림 → dashboard → 장애 재현·복구 → KPI 보고
```

### 최종 산출물

- 옥동 PoC 시스템·서비스 설계서
- 디바이스·데이터 명세서
- Protocol Adapter/telemetry agent 프로토타입
- AI 서비스 2종 프로토타입
- 서비스 binding·workflow preview
- 장애·복구 시험결과서
- 통합 dashboard와 운영 runbook

## 승격 gate

새 protocol·서비스·workflow는 모두 다음 gate를 독립적으로 통과한다.

1. Profile/resource schema 검증
2. 실제 endpoint 독점 연결
3. typed Event와 timestamp 검증
4. outbox·HTTPS replay 검증
5. Core Metadata/Core Data readback
6. AI consumer와 결과 저장 검증
7. 장애·재연결·중복 처리 검증
8. 문서·manifest·테스트 갱신
