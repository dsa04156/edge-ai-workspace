# 프로젝트 배경

## 한 줄 정의

현재 단계는 혼합 디바이스 엣지 AI 플랫폼의 전체 동적 오케스트레이션을 먼저 완성하는 단계가 아니라, 디바이스와 서비스를 실제로 연결하고 이를 대시보드에서 가시화하며 현장 생산성 향상 효과를 설명 가능한 서비스 데모로 만드는 단계다.

현재 단계에서는 이 기반을 서비스 데모, 디바이스-서비스 연결 구조, 통합 운영 가시화 중심으로 정리한다.

## 2차년도 옥동 추진 기준

2차년도 보고 본문은 `docs/단계별-추진계획.md`를 따른다. 2026년 7월 29일 옥동
현장회의 결과에 따라 신규 장비 의존 서비스보다 현재 확보된 PLC·MES·센서 데이터를
활용할 수 있는 생산품질 양품·불량 판별과 메인·보조 유압펌프 및 모터 이상감지 서비스
2종을 우선 추진한다.

현재 테스트베드의 고정 센서 이상탐지 데모는 데이터 수집·배포·가시화 기술 기준선이다.
이를 옥동 서비스 2종의 모델과 데이터 연계가 이미 구현된 것으로 해석하지 않는다.

## 현재 아키텍처와 구현 상태

물리 디바이스 통합의 권위 경로는 다음 하나뿐이다.

```text
물리 센서 / PLC / 장비
  -> Jetson 또는 Raspberry Pi의 EdgeX Device Service
  -> EdgeX Event / Reading
  -> EdgeX Core Data -> PostgreSQL
  -> Application Service / AI consumer / state-aggregator / dashboard
```

- Core Metadata가 물리 디바이스 inventory·schema·관리 상태의 원본이다.
- Core Data Event가 telemetry와 freshness의 원본이다.
- 현재 Device Profile은 read-only schema와 최신값 GET만 제공하며 write/actuator command는 없다.
- Jetson Serial과 Raspberry Pi Sense HAT I2C Device Service는 Device/resource별 최근 10분·최대 10,000 sample을 메모리에 보관하고 같은 node의 Workflow Pod에 read-only Local Data API를 제공한다. 이 cache는 재시작 비보존이며 durable queue가 아니다. 현재 Flannel은 client label NetworkPolicy를 강제하지 않으므로 이 label을 보안 경계로 보지 않는다.
- KubeEdge는 Kubernetes edge node와 workload의 등록·배치·상태 관찰에만 사용한다.
- 중앙 ingest gateway, Core Keeper, Metadata, Data, Command, internal MessageBus, PostgreSQL은 `etri-ser0002-cgnmsb`에 한 세트만 배치한다.
- 2026-07-21 기존 direct Agent 두 개, SQLite PVC와 aggregate `sensehat-001` Metadata
  bootstrap은 퇴역했다. 현재 `edgex-edge`에는 Jetson Arduino용
  `device-serial-jetson`, Raspberry Pi Sense HAT용 `device-sensehat-raspi`와 승인된 신규
  runtime을 관리하는 `edgex-adapter-controller`가 있다. 각 Device Service는 한 물리
  Serial/I2C source를 기능별 6개 가상 Device로 fan-out한다.

현재 root `edgex/k8s/kustomization.yaml`은 중앙 `edgex-system` overlay, `edgex-edge`
Namespace/default-deny base, Jetson Serial Device Service, Raspberry Pi I2C Device Service,
`AdapterRuntime` CRD와 namespaced Controller를 렌더링한다. 중앙 ingest gateway는
유지하지만 현재 두 Event 경로는 Device Service → 중앙 MessageBus → Core Data/PostgreSQL이며
gateway를 사용하지 않는다.

과거 Sense HAT MQTT Agent/SQLite offline replay 결과는 설계·검증 이력이며 현재 배포 완료 근거가 아니다. 현재 완료 근거는 `device-sensehat-raspi`의 직접 I2C read와 6개 가상 Device의 Metadata/Core Data/Core Command/Local Data API/dashboard readback이다.

2026-07-14 UNO 네 source와 2026-07-15 Sense HAT 여섯 source의 typed Event/Reading을 기존 canary에서 확인했다. 이 증거는 장비·profile·Reading 계약의 근거이며 중앙 server2 topology live cutover 완료를 자동으로 뜻하지 않는다.

Serial과 Sense HAT I2C는 정상 수집뿐 아니라 2026-07-22 driver/reader 장애 복구도 live 검증했다. Jetson Arduino `cdc_acm` interface detach 시 Serial 가상 Device 6개가 `DOWN`이 됐고 rebind 약 31초 뒤 `UP`과 새 Event로 복구됐다. Sense HAT Python reader 종료 시 I2C 가상 Device 6개가 `DOWN`이 됐고 새 reader가 시작되며 약 1.3초 뒤 `UP`과 새 Event로 복구됐다. 이 검증은 kernel driver와 reader process 장애 주입이며 사람이 실제 케이블이나 보드를 분리하는 현장 시연은 별도 gate다.

같은 날 중앙 MessageBus를 실제 0 replica로 중단했을 때 두 로컬 ring cache와 `sensor-anomaly-demo`는 계속 증가했지만 Core Data Event는 멈췄다. 복구 후 outage 구간은 재전송되지 않고 새 Event부터 저장돼 durable outbox/offline replay가 없다는 경계를 확인했다. Modbus와 OPC-UA, 다른 장비·주소의 추가 adapter는 profile, 실제 장비 연결과 typed telemetry 검증을 독립 wave로 통과한 뒤 승격한다. RTSP frame은 Workflow Pod가 직접 구독하는 별도 media wave다.

`state-aggregator`와 대시보드는 중앙 EdgeX Core Metadata/Core Data를 소비하는 현재 cutover
대상이다. `Device Management`는 기존 Argo runtime을 조회·재사용하고 Controller가 Git
allowlist로 만든 runtime만 배포·재시작·조건부 퇴역한다. Profile/Device 등록과 first Event도
connection operation으로 추적하지만 물리 inventory/state/telemetry 권위는 계속 EdgeX다.
Prometheus/Kubernetes 정보는 node/workload 관찰과 target node Ready 검증을 보조하지만 물리
디바이스 상태를 결정하지 않는다. 과거 워크플로 실행·배치 실험 컴포넌트는 현행 대시보드와
데모 운영 경로에서 제외한다.

## 디바이스 등록과 상태 전략

EdgeX Core Metadata에 Device Profile과 Device를 등록한다. 기존 수직 슬라이스는 Git manifest
bootstrap을 사용하고, 새 장비는 dashboard의 승인된 connection flow가 runtime 준비 뒤 같은
Metadata API에 등록한다. Device Service는 Device의 `protocols`에 정의된 endpoint를 사용하고
profile resource에 맞는 canonical Event를 만든 뒤 EdgeX SDK async 채널로 중앙 MessageBus에
전달한다. 현재 edge durable queue는 없다. 임의의 MQTT topic이나 HTTP POST만으로 Core
Metadata Device가 자동 생성되지는 않는다.

availability는 EdgeX 관리 상태와 최신 Core Data event를 다음 순서로 해석한다.

1. `adminState=LOCKED` 또는 `operatingState=DOWN`이면 `unavailable`/`disconnected`.
2. `operatingState=UNKNOWN`이면 `degraded`/`unknown`.
3. `operatingState=UP`이고 최신 event가 freshness 기준 안이면 `available`.
4. `operatingState=UP`이어도 event가 없거나 stale이면 `degraded`.

## 과거 MQTT canary와 현재 경계

과거 canary 입력은 다음 canonical topic을 사용했다.

```text
factory/devices/{device-name}/telemetry
```

이 Jetson MQTT agent는 현재 root render와 live EdgeX Metadata에서 제거되었다. MQTT-only 장비나 local pub/sub 요구가 확인되면 별도 Protocol Adapter와 broker를 독립 검증한 뒤에만 새 운영 경로로 추가한다.

`mappers/script/test_device.py`, `mappers/mqttvirtual/`, KubeEdge `DeviceModel`/`Device`/`DeviceStatus`와 mapper의 과거 direct-write 경로는 legacy physical integration/test 경로다.

```text
factory/devices/{device-name}/command
factory/devices/{device-name}/heartbeat
```

이 legacy 경로는 현재 EdgeX status/control plane과 병행해서 실행하거나 fallback으로 사용하지 않는다. 과거 데이터나 manifest는 마이그레이션 비교 자료일 수 있지만 Core Metadata inventory, Core Data telemetry와 별도 승인된 Adapter/command 경로보다 우선하지 않는다.
