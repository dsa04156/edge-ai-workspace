# 프로젝트 배경

## 한 줄 정의

현재 단계는 혼합 디바이스 엣지 AI 플랫폼의 전체 동적 오케스트레이션을 먼저 완성하는 단계가 아니라, 디바이스와 서비스를 실제로 연결하고 이를 대시보드에서 가시화하며 현장 생산성 향상 효과를 설명 가능한 서비스 데모로 만드는 단계다.

현재 단계에서는 이 기반을 서비스 데모, 디바이스-서비스 연결 구조, 통합 운영 가시화 중심으로 정리한다.

## 대상 환경

- x86 엣지 AI 서버
- Jetson 엣지 AI 디바이스
- Raspberry Pi 5 엣지 디바이스
- 물리 센서 디바이스
- 가상 디바이스 / 디바이스트윈

## 현재 우선순위

1. 서비스 데모 1종을 먼저 완성한다.
2. 디바이스 등록/관리 체계를 정리한다.
3. 디바이스-서비스 바인딩 구조를 구현한다.
4. 통합 대시보드에서 디바이스, 노드, 서비스, 상태, KPI를 함께 보이게 한다.
5. 옥동 시나리오의 생산성 향상 효과를 설명 가능한 지표로 정리한다.
6. 현재 문서와 데모에서는 workflow/offloading/agent-assisted planning 계열을 현행 연구 방향과 분리된 과거 검토/보관 경로로 둔다.

## 현재 아키텍처와 구현 상태

물리 디바이스 통합의 권위 경로는 다음 하나뿐이다.

```text
물리 센서 / PLC / 장비
  -> Jetson 또는 Raspberry Pi의 EdgeX Device Service
  -> EdgeX Event / Reading
  -> EdgeX Core Data -> PostgreSQL
  -> Application Service / AI consumer / state-aggregator / dashboard
```

- Core Metadata가 물리 디바이스 inventory·schema·관리 상태의 원본이다.
- Core Data Event가 telemetry와 freshness의 원본이다.
- 현재 Device Profile은 read-only schema와 최신값 GET만 제공하며 write/actuator command는 없다.
- KubeEdge는 Kubernetes edge node와 workload의 등록·배치·상태 관찰에만 사용한다.
- 중앙 ingest gateway, Core Keeper, Metadata, Data, Command, internal MessageBus, PostgreSQL은 `etri-ser0002-cgnmsb`에 한 세트만 배치한다.
- 2026-07-21 기존 direct Agent 두 개, SQLite PVC와 `sensehat-001` Metadata bootstrap은 퇴역했다. 현재 `edgex-edge`의 Jetson Arduino용 `device-serial-jetson`은 한 물리 Serial 연결을 6개 가상 Device로 fan-out한다.

현재 root `edgex/k8s/kustomization.yaml`은 중앙 `edgex-system` overlay, `edgex-edge` Namespace/default-deny base와 Jetson Serial Device Service를 렌더링한다. 중앙 ingest gateway는 유지하지만 현재 Serial Event 경로는 Device Service → 중앙 MessageBus → Core Data/PostgreSQL이며 gateway를 사용하지 않는다.

과거 Sense HAT Agent/SQLite offline replay 결과는 설계·검증 이력이며 현재 배포 완료 근거가 아니다.

2026-07-14 UNO 네 source와 2026-07-15 Sense HAT 여섯 source의 typed Event/Reading을 기존 canary에서 확인했다. 이 증거는 장비·profile·Reading 계약의 근거이며 중앙 server2 topology live cutover 완료를 자동으로 뜻하지 않는다.

Serial은 Arduino 정상 수집 경로에 한해 live 검증했다. Modbus, OPC-UA와 추가 I2C 장비는 해당 adapter, profile, 실제 장비 연결과 typed telemetry 검증을 독립 wave로 통과한 뒤 승격한다. RTSP frame은 Workflow Pod가 직접 구독하는 별도 media wave다.

`state-aggregator`와 대시보드는 중앙 EdgeX Core Metadata/Core Data를 소비하는 현재 cutover 대상이다. Prometheus/Kubernetes 정보는 node/workload 관찰을 보조하지만 물리 디바이스 상태를 결정하지 않는다. 과거 워크플로 실행·배치 실험 컴포넌트는 현행 대시보드와 데모 운영 경로에서 제외한다.

## 디바이스 등록과 상태 전략

EdgeX Core Metadata에 Device Profile과 Device를 사전 등록한다. Device Service는 Device의 `protocols`에 정의된 endpoint를 사용하고 profile resource에 맞는 canonical Event를 만든 뒤 EdgeX SDK async 채널로 중앙 MessageBus에 전달한다. 현재 edge durable queue는 없다. 임의의 MQTT topic이나 HTTP POST만으로 Core Metadata Device가 자동 생성되지는 않는다.

availability는 EdgeX 관리 상태와 최신 Core Data event를 다음 순서로 해석한다.

1. `adminState=LOCKED` 또는 `operatingState=DOWN`이면 `unavailable`/`disconnected`.
2. `operatingState=UNKNOWN`이면 `degraded`/`unknown`.
3. `operatingState=UP`이고 최신 event가 freshness 기준 안이면 `available`.
4. `operatingState=UP`이어도 event가 없거나 stale이면 `degraded`.

## 과거 MQTT canary와 현재 경계

과거 canary 입력은 다음 canonical topic을 사용했다.

```text
factory/devices/{device-name}/telemetry
```

이 Jetson MQTT agent는 현재 root render와 live EdgeX Metadata에서 제거되었다. MQTT-only 장비나 local pub/sub 요구가 확인되면 별도 Protocol Adapter와 broker를 독립 검증한 뒤에만 새 운영 경로로 추가한다.

`mappers/script/test_device.py`, `mappers/mqttvirtual/`, KubeEdge `DeviceModel`/`Device`/`DeviceStatus`와 mapper의 과거 direct-write 경로는 legacy physical integration/test 경로다.

```text
factory/devices/{device-name}/command
factory/devices/{device-name}/heartbeat
```

이 legacy 경로는 현재 EdgeX status/control plane과 병행해서 실행하거나 fallback으로 사용하지 않는다. 과거 데이터나 manifest는 마이그레이션 비교 자료일 수 있지만 Core Metadata inventory, Core Data telemetry와 별도 승인된 Adapter/command 경로보다 우선하지 않는다.
