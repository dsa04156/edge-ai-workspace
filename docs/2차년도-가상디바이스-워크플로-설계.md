# 2차년도 가상디바이스·디바이스트윈·워크플로 설계

> 이 문서는 2차년도 확장 설계의 요약이다. 현재 운영 기능은 [2026년도 2차년도 ETRI 실행계획](2차년도-ETRI-실행계획.md)과 [프로젝트 범위](프로젝트-범위.md)를 우선한다.

## 설계 목적

실제 PLC·센서·카메라와 simulator/replay 데이터를 서비스가 같은 입력 계약으로 사용할 수 있게 한다. 물리 장비의 inventory·state·telemetry 권위는 계속 EdgeX에 두고, 가상디바이스와 디바이스트윈은 EdgeX 대체 저장소가 아니라 참조·조합 계층으로 둔다.

## 용어와 책임

| 용어 | 의미 | 권위 |
|---|---|---|
| 물리 디바이스 | Jetson, Raspberry Pi, PLC, 센서, 모터·펌프, 카메라 | 실제 adapter와 EdgeX Device/Profile |
| 가상디바이스 | 설정된 물리 입력을 state-aggregator의 read-only projection으로 노출하는 소프트웨어 인스턴스 | Slice 0은 EdgeX physical ref; 후속 registry |
| 디바이스트윈 | capability, resource, I/O, binding의 derived snapshot | 후속 twin store; 원본 상태는 EdgeX/Kubernetes |
| 서비스 workflow | 수집→전처리→추론→결과→알림 단계의 실행 명세 | 현재 dashboard는 dry-run/preview |

`virtual-device/`의 JSON Serial prototype이나 legacy MQTT publisher를 EdgeX Device Service 또는 운영 virtual-device로 표현하지 않는다.

## Slice 0: 읽기 전용 virtual-device projection

현재 기능 우선 경계는 `state-aggregator`의 additive read-only projection이다. 기본값은 비활성이며, 이번 실행에서는 주입한 테스트·로컬 개발 설정으로만 활성화한다. EdgeX Core Metadata는 Device/Profile/Device Service identity·상태의 권위이고, EdgeX Core Data는 Event/Reading 이력의 권위다. projection은 telemetry를 저장하거나 원본의 fallback이 되지 않는다.

projection은 설정된 물리 Device와 resource를 stable input ID로 참조하고, capability·source·resource와 선언형 AI field를 명시적으로 매핑한다. 각 입력은 원본 Event provenance를 완전하게 보존한다. `ready`는 권위 있는 Device/Profile identity·상태, 필요한 resource와 신선한 입력, 완전한 provenance가 모두 확인된 경우에만 성립하며, identity·상태·이력·전송·형식 오류와 불완전한 이력은 명시적인 비준비 또는 실패 계약으로 구분한다.

KubeEdge/Kubernetes는 node·workload 관측 책임만 유지하고 workflow는 dry-run이다. `virtual-device/`는 비운영 Serial JSON → local-MQTT 프로토타입으로 EdgeX 완료 경로가 아니며 import·배포하지 않는다. Kustomize, Argo, ingress, 접근 정책, 배포, live activation은 이 Slice에 포함하지 않고 별도 승격 gate로 미룬다.
## 목표 연결 구조

```text
EdgeX Core Metadata Device/Profile + Core Data Event/Reading
  -> physical source view
  -> virtual-device/twin reference
  -> service workflow input binding
  -> AI service container
  -> result store / alert / dashboard

Kubernetes/KubeEdge node·resource
  -> 실행 후보 진단
```

가상 계층은 raw Event/Reading 전체를 복제하지 않는다. 물리 상태는 EdgeX의 `adminState`, `operatingState`, 최신 Event `origin`을 사용하고, 자원·배치 정보는 Kubernetes/Prometheus 관측으로 분리한다.

## 2차년도 서비스 입력 예

### 생산품질 판별

- MES 생산 건 식별자와 공정 상태
- PLC·센서 resource의 공통 timestamp window
- 결과: `good`, `defect`, `unknown`, confidence, model version

### 펌프·모터 이상 감지

- 진동 X/Y/Z, 전류, 온도, 운전 상태
- timestamp 정렬, 결측·stale 처리
- 결과: anomaly score, severity, reason code, model version

결과는 원본 Device/Profile/Event와 역추적 가능해야 하며, 입력이 stale하거나 누락되면 임의 결과 대신 `unknown/degraded`로 처리한다.

## 현재 UI 경계

현재 workflow builder에서 허용하는 것은 다음뿐이다.

- stage 구성
- EdgeX Device/resource source 선택
- binding validation과 release dry-run
- execution plan preview

현재 실행하지 않는 것:

- Kubernetes apply/delete/restart
- EdgeX Metadata 변경
- Device Service command와 actuator mutation
- runtime migration/offloading
- 자동 failover나 운영자 승인 없는 배포

실제 runtime으로 승격하려면 API 계약, 권한·승인, 결과 저장, 재시도·rollback, node placement, 장애 시험을 별도 gate로 통과해야 한다.

## 단계별 승격 기준

1. **Source pool**: EdgeX Device/Profile, Core Data latest/history, freshness API 확인
2. **Service contract**: 입력 resource, timestamp, output/result schema 고정
3. **Container test**: simulator/replay로 정상·이상·결측 결과 재현
4. **Edge/server test**: 실제 배치와 중앙/로컬 저장 경계, 장애복구 검증
5. **운영 승격**: human approval, audit, rollback, dashboard와 KPI를 같은 실행에서 확인

이 기준을 통과하기 전에는 설계·prototype으로만 기록한다. `workflow_executor/`, `placement_engine/`, `workflow/` 및 archive의 selective replanning 자료는 현재 운영 경로가 아니다.
