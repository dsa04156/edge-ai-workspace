# 펌프·모터 이상감지 서비스

## 한눈에 보기

`sensor-anomaly-demo`는 가속도 3축과 온도를 결합해 펌프·모터의 진동·온도 변화 징후를
보여주는 Edge AI 기준선 서비스다. Jetson에서 EdgeX Device Service의 최근 데이터를 읽고,
특징과 이상 점수를 계산해 결과·알림을 저장한다.

> 현재 모델은 옥동 설비에서 학습한 고장 분류 AI가 아니라 `online-baseline` 통계 모델이다.
> Arduino 입력은 디바이스 연결과 서비스 운영을 검증하는 테스트베드 기준선이며, 실제 설비
> 고장 종류나 잔여 수명을 판정하지 않는다.

| 항목 | 현재 값 |
|---|---|
| 서비스 ID | `sensor-anomaly-demo` |
| 화면 이름 | 펌프·모터 진동·온도 이상감지 |
| 실행 위치 | Device1 · `etri-dev0001-jetorn` |
| 입력 권위 | EdgeX Core Data / Device Service Local Data API |
| 입력 계약 | `okdong.pump-motor.telemetry/v1` |
| 모델 | `online-baseline` · `baseline-1.0.0` |
| 결과 저장 | 서비스 소유 SQLite와 1Gi RWO PVC |
| Server1 | HAMi GPU·CUDA 준비 상태를 관측하는 승인 기반 선택 경로 |

## 어떤 데이터를 사용하는가

현재 실행 가능한 입력은 네 가지다.

| 역할 | EdgeX Device | resource |
|---|---|---|
| 진동 X축 | `virtual-acceleration-x-001` | `acceleration_x_raw` |
| 진동 Y축 | `virtual-acceleration-y-001` | `acceleration_y_raw` |
| 진동 Z축 | `virtual-acceleration-z-001` | `acceleration_z_raw` |
| 온도 문맥 | `virtual-temperature-001` | `temperature_raw` |

X/Y/Z는 같은 nanosecond `origin`을 가진 값으로 한 frame을 만든다. 온도는 이 frame에서
2초 이내의 가장 가까운 sample만 결합한다. 입력이 10초 이상 갱신되지 않거나 필수 값이
누락되면 fresh 입력으로 처리하지 않는다.

상세 schema와 옥동 현장 확정 항목은 [옥동 AI 서비스 데이터 계약](옥동-데이터-계약.md)을
기준으로 한다.

## 어떻게 판단하는가

```text
센서 수집 → origin 정렬 → 특징 추출 → 기준선 추론 → 결과 저장
                                          ├→ Device1 기본 경로
                                          └→ Server1 승인 후보
```

1. 가속도 20개 window에서 진동 크기의 `RMS`, `peak`, `kurtosis`를 계산한다.
2. 온도 10개 window에서 `mean`, `stddev`, `delta`를 계산한다.
3. 처음 30개 sample로 각 특징의 기준 분포를 준비한다.
4. 특징별 기준선 이탈 정도를 계산하고 진동 70%, 온도 30%로 종합한다.
5. 점수가 임계값 4.0 이상인 상태가 2회 연속이면 이상 상태로 전환한다.
6. 임계값 미만이 3회 연속이면 정상 상태로 복귀한다.

이 값은 테스트베드에서 서비스 흐름을 검증하기 위한 변화 점수다. 실제 고장 분류 정확도,
오탐률과 생산성 효과는 옥동 현장 label 데이터로 별도 검증해야 한다.

## 무엇을 출력하는가

| 출력 | 의미 |
|---|---|
| 최신 상태 | 입력 freshness, model readiness, 최신 점수와 상태 |
| 결과 이력 | origin, 특징, component score, 종합 점수, model version |
| 알림 이력 | 이상 상태 진입과 정상 복귀 transition |
| 운영 지표 | processing p95 latency, backlog, throughput |
| 실행 경로 | Device1/Server1 처리 비율, timeout·retry·rollback 상태 |
| 증강 판단 | gate, 상태, reason, 압박 지속시간, 전후 성능 |

대시보드는 다음 read-only API를 `state-aggregator`를 통해 보여준다.

```text
/state/service-demo
/state/service-demo/results
/state/service-demo/alerts
/state/service-demo/augmentation
```

## 설비 이상과 자원 증강은 별개다

```text
특징·anomaly 증가
  → 설비 이상 알림

CPU·Memory·GPU 압박 + latency·backlog·throughput 악화
  → 자원 증강 평가
```

`anomaly_score`는 자원 증강 evaluator에 들어가지 않는다. 설비 상태가 정상이어도 처리 지연이
지속되면 증강 후보가 될 수 있고, 설비 이상이 발생해도 컴퓨팅 압박이 없다면 증강하지 않는다.

### 증강 권고 조건

다음 조건을 모두 만족해야 `RECOMMENDED`가 된다.

```text
입력·모델·메트릭 유효
AND CPU/Memory/GPU 중 하나가 85% 이상으로 5분 지속
AND p95 latency 4초 이상 OR backlog > 0 OR throughput < 0.8/s가 3분 지속
AND Server1 Pod·endpoint·모델·여유 자원 준비
```

이 서비스의 약 1Hz 테스트베드 입력은 최근 정상 운전에서 throughput 약 0.99/s와 processing
p95 약 2.7초를 보였다. 작은 주기 지터를 압박으로 오판하지 않도록 위 기준을 적용하며,
축소 후보는 p95 3초 미만과 backlog 0을 15분 동안 유지해야 한다.

현재 evaluator는 `observed-only`다. 권고를 화면과 API에 기록하지만 Kubernetes workload를
자동 증설하거나 요청을 자동 전환하지 않는다.

### `BLOCKED`는 무엇인가

`BLOCKED`는 “증강 판단이나 전환을 안전하게 진행할 근거가 없다”는 뜻이다.

| reason | 의미 | 먼저 확인할 것 |
|---|---|---|
| `sensor_disconnected` | 입력 서비스 연결 실패 | Device Service와 네트워크 |
| `sensor_stale` | 최신 sample이 freshness 기준 초과 | Core Data `origin`과 수집 상태 |
| `required_input_missing` | X/Y/Z/온도 또는 최신 결과 누락 | Device/resource별 latest Event |
| `input_schema_invalid` | 입력 계약 불일치 | schema version과 adapter |
| `model_not_ready` | edge 모델 준비 전 | warm-up과 model 상태 |
| `metrics_invalid_or_stale` | SLI 또는 자원 metric 근거 부족 | metric 시각과 coverage |
| `server1_pod_not_ready` | Server1 Pod 미준비 | Pod/EndpointSlice |
| `server1_endpoint_not_ready` | 추론 endpoint 미준비 | readiness와 HTTP 응답 |
| `server1_model_not_ready` | Server1 모델 미준비 | model readiness/version |
| `server1_resource_insufficient` | Server1 여유 instance 없음 | resource pool과 binding 상태 |

`BLOCKED` 자체가 서비스 Pod를 중지하는 명령은 아니다. 증강 권고·전환 경로만 막는다. 다만
차단 원인이 센서 stale이나 모델 미준비라면 같은 원인으로 새 추론 결과도 생성되지 않을 수
있으므로 서비스 상태를 함께 확인해야 한다.

정상 상태 흐름은 다음과 같다.

```text
NORMAL → OBSERVING → RECOMMENDED → AUGMENTED → COOLDOWN → NORMAL
                         ↘ 조건 불충족 시 BLOCKED
```

## Server1 전환 경계

기본 배포는 Device1 로컬 추론만 사용한다. Server1은 HAMi가 GPU core 20%와 GPU memory
1,024MiB를 배정하고 CUDA 시험 계산에 성공해야 준비 상태가 된다. 현재 backend는 같은 통계
기준선을 GPU에서 계산하는 `cuda-online-baseline`이며 옥동 현장 학습 모델은 아니다.
운영자가 별도 GitOps 변경과 승인 ID를 제공한 경우에만 요청 전환 overlay를 사용할 수 있다.

승인 경로에서도 요청은 1초 timeout, 최대 2회 시도를 사용한다. 3회 연속 실패하면 15분 동안
Device1 로컬 추론으로 돌아간다. 이는 단일 서비스의 승인된 요청 전환이며 자동 workload
증설, 범용 migration 또는 동적 offloading 완료 기능이 아니다.

## 운영자가 확인할 순서

1. 센서 네 개가 connected·fresh·schema valid인지 확인한다.
2. model state가 `ready`인지 확인한다.
3. 최신 결과의 `origin`, score와 alert transition을 확인한다.
4. latency, backlog, throughput과 자원 metric freshness를 확인한다.
5. 증강 상태가 `BLOCKED`면 첫 reason과 실패한 gate를 확인한다.
6. Server1 전환은 승인 ID와 rollback 책임이 확인된 경우에만 진행한다.

실제 점검 명령은 [현재 서비스 데모 운영 절차](ops/현재-데모-운영-절차.md), 상태 표시 원칙은
[대시보드 판단 정책](대시보드-판단-정책.md)을 따른다. 새 서비스를 추가하는 방법은
[AI 서비스 등록 가이드](AI-서비스-등록-가이드.md)를 확인한다.
