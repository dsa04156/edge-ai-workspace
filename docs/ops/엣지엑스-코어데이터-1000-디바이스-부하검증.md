# EdgeX Core Data 1,000 디바이스 부하 검증

## 목적

이 문서는 현재 단일 EdgeX Core Data와 PostgreSQL이 합성 가상 디바이스 Event를 어느 입력률까지 저장하는지 재현 가능하게 확인하는 절차와 2026-07-22 실측 결과를 정리한다. 센서 수가 많다는 이유만으로 Event batch 저장이나 별도 시계열 DB를 먼저 추가하지 않고, 실제 `device 수 × device별 Hz`를 기준으로 현재 저장 경로의 한계를 측정한다.

이 검증은 Core Data REST ingress부터 PostgreSQL까지의 기준선이다. 운영 정상 경로인 Device Service → 중앙 internal MessageBus → Core Data 전체 처리량을 검증한 결과가 아니며, 합성 identity를 Core Metadata Device로 등록하지 않는다.

## 구현 경계

```text
일회성 Pod @ etri-ser0002-cgnmsb
  -> edgex-core-data.edgex-system.svc.cluster.local:59880
  -> POST /api/v3/event/{service}/{profile}/{device}/{source}
  -> Core Data / PostgreSQL
  -> GET /api/v3/event/count/device/name/{device}
  -> DELETE /api/v3/event/device/name/{device}
  -> count=0 확인
```

- 실행기는 `tools/edgex-core-data-loadtest/`의 Go 표준 라이브러리 구현이다.
- `tools/run_edgex_core_data_loadtest.sh`가 amd64 정적 바이너리를 빌드해 digest 고정 BusyBox 일회성 Pod에서 실행한다.
- Core Data는 고정 ClusterIP나 PodIP가 아니라 Service FQDN으로 접근한다.
- Pod는 `etri-ser0002-cgnmsb`에 배치하고 ServiceAccount token, privilege escalation과 쓰기 가능한 root filesystem을 사용하지 않는다.
- 운영 `edgex/k8s` root render, Argo CD Application, EdgeMesh, Device/Profile/Device Service는 변경하지 않는다.
- 합성 이름은 `loadtest-{runId}-{index}`이고 각 Event는 `Float64` Reading 한 개와 `loadTestRunId` tag를 갖는다.
- 실행별 JSON은 `artifacts/edgex-loadtest/`에 남지만 운영 생성물이므로 Git에는 포함하지 않는다.

## 안전한 기본 프로파일

아무 옵션 없이 실행하면 1,000개 identity가 각 1분에 한 번 Event를 보내는 저주기 기준선을 사용한다.

```bash
rtk bash tools/run_edgex_core_data_loadtest.sh
```

| 항목 | 기본값 | 의미 |
|---|---:|---|
| `DEVICES` | `1000` | 합성 device identity 수 |
| `PER_DEVICE_HZ` | `0.0166666667` | device별 약 1 Event/분 |
| `DURATION` | `60s` | 부하 생성 구간 |
| `CONCURRENCY` | `128` | POST worker 상한 |
| `MAINTENANCE_CONCURRENCY` | `8` | readback·cleanup 동시성 상한 |
| `REQUEST_TIMEOUT` | `5s` | HTTP 요청별 제한 |
| `MAX_ERROR_RATE` | `0` | 허용 저장 실패율 |
| `MAX_P95` | `1s` | 허용 POST p95 |
| `MIN_RATE_RATIO` | `0.95` | 목표 Event/s 대비 최소 달성률 |
| `VERIFY` | `true` | device별 전용 count API readback |
| `CLEANUP_EVENTS` | `true` | 합성 Event만 삭제하고 `count=0` 확인 |

Core Data의 일반 device Event 이력 API를 count 용도로 반복 호출하지 않는다. 검증기는 전용 `/api/v3/event/count/device/name/{device}`를 사용한다. 삭제 API의 성공 응답은 `202 Accepted`이므로 응답 수신만으로 삭제 완료를 선언하지 않고 같은 count API가 0을 반환할 때까지 제한 시간 안에서 확인한다.

## 스트레스 프로파일

1,000 devices × 1Hz는 현재 배포에서 OOM이 확인된 스트레스 프로파일이다. 정상 데모 중 기본 명령으로 실행하지 않는다.

```bash
rtk env \
  RUN_ID=baseline-1hz-yyyymmdd \
  DEVICES=1000 \
  PER_DEVICE_HZ=1 \
  DURATION=30s \
  REQUEST_TIMEOUT=10s \
  bash tools/run_edgex_core_data_loadtest.sh
```

실행 전후에 다음을 기록한다.

```bash
rtk kubectl -n edgex-system get pod \
  -l app.kubernetes.io/name=edgex-core-data -o wide
rtk kubectl -n edgex-system get pod edgex-postgres-0 -o wide
rtk kubectl -n edgex-system top pod
```

10Hz나 더 높은 profile은 현재 자동 실행 범위가 아니다. 1Hz 실패 원인을 해소하고 100 → 250 → 500 → 1,000 events/s 순서의 단계별 gate를 통과한 뒤에만 확장한다.

## PASS 판정

다음 조건을 모두 만족해야 저장 기준선 PASS다.

1. `attempted == planned`다.
2. `succeeded == planned`이고 Core Data가 각 POST에 `201 Created`와 동일 Event ID를 반환한다.
3. `errorRate <= MAX_ERROR_RATE`다.
4. `latency.p95Ms <= MAX_P95`다.
5. `achievedEventsPerSecond >= targetEventsPerSecond × MIN_RATE_RATIO`다.
6. 1,000개 device의 count 합계가 성공 Event 수와 일치한다.
7. cleanup이 각 합성 device의 `count=0`까지 확인한다.
8. Core Data/PostgreSQL이 Ready이고 재시작 횟수가 증가하지 않는다.
9. 대표 Arduino·Sense HAT 실제 Event의 `origin`이 시험 뒤에도 증가한다.

`pass=true`만 보지 않고 Pod restart와 실제 sensor 회귀를 함께 확인한다. OOM이나 재시작이 있으면 Event 보고서가 일부 성공했더라도 운영 PASS가 아니다.

## 2026-07-22 실측 결과

환경은 중앙 `etri-ser0002-cgnmsb`의 Core Data 1 replica와 PostgreSQL 1 replica다. Core Data resource는 request `50m/64Mi`, limit `300m/256Mi`; PostgreSQL은 request `100m/128Mi`, limit `500m/512Mi`였다.

| 프로파일 | 결과 | 저장 결과 | POST 지연 | 운영 영향 |
|---|---|---|---|---|
| smoke, 2 devices × 2Hz × 2s | PASS | 8/8, 오류 0, readback 8, cleanup 2 devices | p95 `14.83ms` | 재시작 없음 |
| 저주기, 1,000 × 1/60Hz × 60s | PASS | 1,000/1,000, `16.678 events/s`, readback 1,000, cleanup 1,000 | p50 `12.84ms`, p95 `16.17ms`, p99 `17.82ms`, max `44.39ms` | 합성 잔존 0, 실제 sensor origin 증가 |
| 스트레스, 1,000 × 1Hz × 30s | FAIL | 0/30,000, 오류율 1.0 | 성공 응답 없음 | Core Data `OOMKilled`, exit 137, restart `1 → 2` |

1Hz 실패 보고서의 오류 분포는 HTTP 503 `9,390`, transport `13,064`, 기타 `7,546`이었다. worker backpressure와 요청 timeout 때문에 전체 시도 회수에는 약 375.74초가 걸렸다. PostgreSQL에는 해당 실행의 합성 Event가 남지 않았고, Core Data 자동 재시작 뒤 Arduino와 Sense HAT의 최신 Event `origin` 증가를 다시 확인했다.

초기 저주기 시험에서는 검증기가 일반 Event 이력 API를 128개 동시 호출해 조회 경로를 정체시키는 도구 결함이 있었다. 최종 구현은 이를 다음처럼 수정했다.

- 저장 동시성과 검증·정리 동시성을 분리했다.
- 일반 이력 API 대신 전용 Event count API를 사용한다.
- cleanup의 `202 Accepted` 뒤 `count=0`을 확인한다.
- 검증·정리 상세 오류는 각 20건까지만 JSON에 남기고 나머지는 `suppressedErrors`로 집계한다.
- 저장, readback과 cleanup이 같은 취소 context를 사용하므로 종료 신호 뒤 maintenance 요청을 계속 기다리지 않는다.
- 기본 profile을 검증된 1/60Hz로 낮췄다.

## 현재 결론

- “센서 1,000개라서 Event마다 저장하면 무조건 안 된다”는 결론은 아니다. 1,000개가 분당 한 번 보내는 약 16.7 events/s는 현재 구성에서 여유 있게 통과했다.
- 현재 `300m CPU / 256Mi memory` Core Data 1 replica에 1,000 events/s를 바로 넣는 구성은 지원 근거가 없고 실제로 OOM 실패했다.
- 따라서 저장 batch나 별도 DB를 먼저 넣기 전에 실제 장비별 sampling rate, 저장 대상 resource 수와 retention을 확정해야 한다.
- 다음 성능 작업은 Core Data memory profile과 resource right-sizing, 100/250/500 events/s 단계별 시험, PostgreSQL index·retention 관측, Device Service → MessageBus → Core Data 전체 경로 시험 순서로 진행한다.
- 현재 운영 Device Service, MessageBus와 PostgreSQL 배포는 이번 기준선 도구 추가만으로 변경하지 않는다.

## 장애 후 회복 확인

부하 시험이 실패하면 합성 데이터 정리보다 먼저 Core Data가 Ready인지 확인한다. OOM 뒤 Deployment가 자동 복구하지 못할 때만 정확한 Core Data Pod 하나를 재생성하고, manifest·Service·EdgeMesh는 수정하지 않는다.

회복 완료 조건:

1. Core Data와 PostgreSQL이 Ready다.
2. 새 OOM/restart가 더 증가하지 않는다.
3. `virtual-temperature-001`과 `env-sensehat-temperature-01` 최신 Event가 조회된다.
4. 두 Event의 `origin`이 시험 전보다 증가한다.
5. 실행 prefix의 합성 Event가 0건이다.

전체 현재 데모 회귀는 다음 명령으로 확인한다.

```bash
rtk bash tools/verify_e2e.sh
```
