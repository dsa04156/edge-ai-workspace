# 현재 서비스 데모 운영 절차

## 점검 대상

이 절차는 다음 두 흐름을 확인한다.

```text
Arduino / Sense HAT → EdgeX Device Service → Core Data → dashboard
Arduino 가속도·온도 → sensor-anomaly-demo → 결과·알림 → 서비스 DAG
```

운영 namespace는 중앙 `edgex-system`, 물리 Device Service `edgex-edge`다. root 배포
진입점은 `edgex/k8s/kustomization.yaml`, Argo CD Application은 `edgex-telemetry`다.

## 1. Git과 manifest 확인

```bash
git status --short
kubectl kustomize edgex/k8s >/tmp/edgex-current.yaml
kubectl apply --dry-run=server -f /tmp/edgex-current.yaml
```

render에는 중앙 EdgeX Core·MessageBus·PostgreSQL, `device-serial-jetson`,
`device-sensehat-raspi`, Adapter Controller와 discovery workload가 포함돼야 한다.
`edgex-edge-agent-*`, Agent outbox PVC, device-mqtt와 edge-local broker는 현재 정상 경로가
아니다.

## 2. Argo CD와 workload 확인

```bash
kubectl -n argocd get application edgex-telemetry \
  -o jsonpath='{.status.sync.status}{"/"}{.status.health.status}{" "}{.status.sync.revision}{"\n"}'

kubectl -n edgex-system get deploy,statefulset,pod,service
kubectl -n edgex-edge get deploy,pod,service,pvc
```

정상 기준:

- `edgex-telemetry`가 `Synced/Healthy`
- 중앙 Core와 PostgreSQL이 Ready
- 두 Device Service가 각각 `1/1 Ready`
- `sensor-anomaly-demo`가 Jetson에서 Ready
- image가 immutable digest이며 restart가 반복 증가하지 않음

## 3. Device Service와 물리 binding 확인

| Runtime | node | exact device | 기능별 Device 수 |
|---|---|---|---|
| `device-serial-jetson` | `etri-dev0001-jetorn` | `/dev/arduino-001` | 6 |
| `device-sensehat-raspi` | `etri-dev0003-raspi5` | `/dev/i2c-1` | 6 |

```bash
kubectl -n edgex-edge get deployment device-serial-jetson device-sensehat-raspi \
  -o wide
```

두 Runtime은 host 전체가 아니라 필요한 CharDevice만 사용한다. 각 물리 연결은 내부 shared
reader 하나가 소유하며 기능별 Profile/Device로 값을 fan-out한다.

## 4. Core Metadata 확인

```bash
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-metadata:59881/proxy/api/v3/device/all?offset=0&limit=100'
```

확인 항목:

- Device Service, Profile과 Device 이름이 manifest와 일치
- `adminState=UNLOCKED`, `operatingState=UP`
- Serial Device는 `physicalDeviceId=arduino-001`
- Sense HAT Device는 `physicalDeviceId=sensehat-001`
- aggregate Device를 중복 생성하지 않음

## 5. Core Data freshness 확인

```bash
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-data:59880/proxy/api/v3/event/device/name/virtual-acceleration-x-001?limit=1'

kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-data:59880/proxy/api/v3/event/device/name/env-sensehat-temperature-01?limit=1'
```

Event/Reading의 resource와 type이 Profile과 일치하고 nanosecond `origin`이 증가해야 한다.
API 응답 시각이나 Kubernetes node 상태로 freshness를 대신하지 않는다.

## 6. AI 서비스 확인

```bash
curl -fsS http://aggregator.192.168.0.56.sslip.io/state/services
curl -fsS http://aggregator.192.168.0.56.sslip.io/state/service-demo
```

확인 항목:

- 필수 X/Y/Z/온도 입력 connected·fresh·schema valid
- model ready와 model version
- latest result와 최근 alert
- 현재 target과 Device1/Server1 처리 비율
- 증강 evaluator state, gate, metric과 `BLOCKED` reason

설비 anomaly가 발생해도 서비스 입력·모델이 정상이라면 서비스 실행 상태와 혼합하지 않는다.
반대로 anomaly가 없어도 latency/backlog 자원 압박은 별도로 평가한다.

## 7. 대시보드 확인

공식 주소:

```text
http://aggregator.192.168.0.56.sslip.io
```

브라우저에서 확인한다.

1. 서비스 목록에 `sensor-anomaly-demo`가 보인다.
2. 센서 수집→전처리→특징 추출→AI 추론→결과 저장 DAG가 보인다.
3. 현재 단계, Device1/Server1 target, event timeline과 실시간 metric이 표시된다.
4. stale·missing·not ready를 정상처럼 표시하지 않는다.
5. 브라우저 console에 JavaScript 오류가 없다.

## 장애 시 우선순위

1. Core Metadata 조회 가능 여부
2. Device `adminState`·`operatingState`
3. Core Data latest Event와 `origin`
4. Device Service log와 physical mount
5. AI input schema·window·model readiness
6. Server1 endpoint와 metric freshness
7. node·Pod 자원 상태

고정 ClusterIP, PodIP와 node IP를 설정에 넣거나 우회 경로로 사용하지 않는다. write command,
actuator mutation, 자동 migration/offloading은 이 절차의 정상 조치가 아니다.
