# 현재 서비스 데모 운영 절차

## 목적

이 문서는 Jetson Arduino Uno의 Serial 경로와 Raspberry Pi Sense HAT v1의 직접 I2C 경로가 각각 EdgeX Device Service → 기능별 가상 Device 6개 → 중앙 MessageBus/Core Data/PostgreSQL → state-aggregator/dashboard로 이어지는 현재 정상 경로를 점검한다. 또한 Jetson acceleration X/Y/Z Local Data → `sensor-anomaly-demo` → `/state/service-demo` → dashboard로 이어지는 첫 실측 AI 서비스 데모를 검증한다. 기존 Agent, SQLite outbox, aggregate Sense HAT bootstrap, edge-local MQTT broker와 InfluxDB workload는 현재 경로가 아니다.

Core Data telemetry freshness는 latest Event의 nanosecond `origin`을 sample 시각으로 계산하며 API 조회 시각이나 Kubernetes 상태로 대체하지 않는다.

## 배치 기준

| 구분 | 현재 기준 |
|---|---|
| 중앙 namespace | `edgex-system` |
| edge namespace | `edgex-edge` |
| 중앙 노드 | `etri-ser0002-cgnmsb` |
| 중앙 workload | Core Keeper/Metadata/Data/Command, internal MessageBus, PostgreSQL, 유지 중인 ingest gateway |
| edge workload | `device-serial-jetson`, `device-sensehat-raspi` 각 1 replica |
| AI service workload | `sensor-anomaly-demo` 1 replica, `etri-dev0001-jetorn` |
| physical node | `etri-dev0001-jetorn`, `etri-dev0003-raspi5` |
| physical source | Arduino Uno `/dev/arduino-001`, Sense HAT v1 `/dev/i2c-1` |
| EdgeX inventory | Serial 6개 + I2C 6개, 총 가상 Device/Profile 12개 / Device Service 2개 |
| 운영 진입점 | `edgex/k8s/kustomization.yaml` |
| Argo CD Application | `edgex-telemetry` |
| AI service Argo CD Application | `edge-orch-sensor-anomaly-demo` |

EdgeMesh 리소스는 이 절차의 변경 대상이 아니다. Kubernetes `ClusterIP Service` 객체는 정상 서비스 디스커버리에 사용하지만 고정 ClusterIP, PodIP와 node IP를 설정에 넣거나 우회 경로로 사용하지 않는다. Device Service는 중앙 Keeper, Metadata와 MessageBus의 `.svc.cluster.local` FQDN을 사용한다.

KubeEdge `cloudcore` Helm release가 설치한 `kubeedge/DaemonSet/edge-eclipse-mosquitto`는
edge node 3개에 legacy 호환 구성으로 남아 있다. 이 DaemonSet은 `edgex/k8s`나 현재 서비스
데모가 생성한 local broker가 아니며 Serial/I2C → Local Data API → AI consumer 경로에서
사용하지 않는다. 현재 데모의 MQTT 부재 판정은 `edgex-device-mqtt`, edge Agent와
데모 전용 broker/consumer가 없다는 뜻이며, KubeEdge Helm 구성 제거는 별도 작업 범위다.

| Sense HAT Device | Profile | Resources | Command |
|---|---|---|---|
| `env-sensehat-temperature-01` | `etri-sensehat-temperature` | `temp_humidity`, `temp_pressure` | `temperature` |
| `env-sensehat-humidity-01` | `etri-sensehat-humidity` | `humidity` | `humidity` |

## 1. 로컬 render 검증

```bash
kubectl kustomize edgex/k8s >/tmp/edgex-current.yaml
kubectl apply --dry-run=server -f /tmp/edgex-current.yaml
```

정상 기준:

- 중앙 Core/MessageBus/PostgreSQL/gateway가 render된다.
- `Namespace/edgex-edge`, default-deny와 Device Service별 최소 NetworkPolicy가 render된다.
- 두 `Service`와 `Deployment/device-serial-jetson`, `Deployment/device-sensehat-raspi`가 render된다.
- Device Service는 각각 `etri-dev0001-jetorn`, `etri-dev0003-raspi5`에 고정되고 `hostNetwork: true`를 사용하지 않는다.
- host의 Arduino by-id CharDevice와 Sense HAT I2C CharDevice만 각 Pod의 `/dev/arduino-001`, `/dev/i2c-1`에 정확히 마운트된다.
- 각 ConfigMap에는 해당 Profile 6개와 Device list 1개가 포함된다.
- 중앙 Keeper/Metadata/MessageBus는 `.svc.cluster.local` FQDN으로 참조된다.
- `edgex-edge-agent-*`, Agent PVC/ConfigMap/bootstrap, `device-mqtt`, edge-local broker와 InfluxDB workload를 배포하지 않는다.

현재 PoC의 Serial/I2C 장치 접근은 각 Device Service Pod에 `privileged: true`, UID/GID 0을 허용한다. 이 예외는 정확한 CharDevice mount, `Recreate` 전략과 service-account token 비마운트로 범위를 줄인다. NetworkPolicy는 manifest에 선언되어 있지만 현재 Flannel CNI에서는 강제되지 않는다. 후속 운영 강화에서는 Device Plugin 또는 더 좁은 장치 권한으로 대체한다.

## 3. live workload와 장치 mount

```bash
kubectl -n edgex-system get deploy,statefulset,job,pod,service,pvc -o wide
kubectl -n edgex-edge get deploy,pod,service,pvc,configmap,networkpolicy -o wide
kubectl -n edgex-edge get deployment device-serial-jetson \
  -o jsonpath='{.spec.template.spec.nodeSelector.kubernetes\.io/hostname}{"\n"}{.spec.template.spec.hostNetwork}{"\n"}{.spec.template.spec.containers[0].image}{"\n"}'

kubectl -n edgex-edge get deployment device-sensehat-raspi \
  -o jsonpath='{.spec.template.spec.nodeSelector.kubernetes\.io/hostname}{"\n"}{.spec.template.spec.hostNetwork}{"\n"}{.spec.template.spec.containers[0].image}{"\n"}'
```

정상 기준:

- 중앙 Core 서비스와 PostgreSQL이 Ready다. common-config bootstrap Job은 Completed일 수 있다.
- `device-serial-jetson`과 `device-sensehat-raspi` Pod가 각각 Jetson과 Raspberry Pi에서 `1/1 Running`이다.
- 두 image는 immutable ARM64 digest다.
- Pod restart가 반복 증가하지 않는다.
- `edgex-edge`에 Agent outbox PVC, local broker와 별도 telemetry DB가 없다.
- `sensor-anomaly-demo`가 Jetson에서 `1/1 Running`, restart 0이고 immutable ARM64 digest를 실행한다.
- AI service는 `hostNetwork`, host device mount, PVC, MQTT/InfluxDB 연결을 사용하지 않는다.

Serial 로그에서 시작 중 잘린 line 1~2개가 malformed로 폐기될 수 있다. 이후 metric 등록, reader restart, Metadata update가 반복되거나 ERROR가 계속 나오면 정상으로 보지 않는다. Sense HAT reader는 시작 시 IMU를 prime한 뒤 pressure/humidity를 초기화하며, bounded retry 이후에도 `sample` 응답이 없거나 reader가 반복 재시작하면 정상으로 보지 않는다.

## 7. Jetson Local Data API

의도된 client label과 같은-node 배치를 함께 확인하려면 임시 client Pod를 Jetson에 배치한다.

```bash
kubectl run local-data-check \
  --namespace default \
  --image=curlimages/curl:8.12.1 \
  --restart=Never \
  --labels=edge-ai.io/local-data-client=true \
  --overrides='{"spec":{"nodeSelector":{"kubernetes.io/hostname":"etri-dev0001-jetorn"}}}' \
  --command -- sleep 3600

kubectl wait --namespace default \
  --for=condition=Ready pod/local-data-check \
  --timeout=120s

kubectl exec --namespace default local-data-check -- \
  curl --fail --silent --show-error \
  'http://device-serial-jetson.edgex-edge.svc.cluster.local:59910/api/v3/localdata/device/name/virtual-temperature-001/resource/name/temperature_raw/latest'

kubectl exec --namespace default local-data-check -- \
  curl --fail --silent --show-error \
  'http://device-serial-jetson.edgex-edge.svc.cluster.local:59910/api/v3/localdata/device/name/virtual-temperature-001/resource/name/temperature_raw?limit=20'

kubectl exec --namespace default local-data-check -- \
  curl --fail --silent --show-error \
  'http://device-serial-jetson.edgex-edge.svc.cluster.local:59910/api/v3/localdata/stats'

kubectl delete pod --namespace default local-data-check
```

정상 기준:

- latest는 `count=1`이고 `temperature_raw`, `Int32`, 원본 nanosecond `origin`을 반환한다.
- recent는 `origin` 오름차순이며 `count`와 `samples` 길이가 같다.
- latest/recent의 `retention.maxAge=10m0s`, `retention.maxSamples=10000`, `retention.maxBytes=67108864`이다.
- stats는 `series=6`, `samples>0`, `slotBytes>0`, `allocatedBytes<=67108864`이고 eviction 원인별 누계를 반환한다.
- 알려진 source에 범위 데이터가 없으면 `200`과 빈 `samples`, latest가 없으면 `404`다.
- `limit`은 1~10,000이고 기본값은 1,000이다.

다른 5개 가상 Device도 각 Profile의 resource 이름으로 같은 계약을 확인한다. 임시 Pod는 검증 뒤 반드시 삭제한다.

주의: 현재 테스트베드의 Flannel CNI는 Kubernetes NetworkPolicy를 집행하지 않는다. 2026-07-21 실측에서 `edge-ai.io/local-data-client=true` label이 없는 기존 Pod도 이 API에 접근했다. 따라서 label은 배치·정책 의도 표식이며 현재 보안 경계가 아니다. Local Data API는 unauthenticated read-only endpoint이므로 실제 접근 차단이 필요하면 NetworkPolicy 지원 CNI 또는 mTLS/애플리케이션 인증을 먼저 적용한다.

## 7B. Jetson 실측 센서 이상 탐지 서비스

```bash
rtk kubectl -n edgex-edge get deployment,pod,service \
  -l app.kubernetes.io/name=sensor-anomaly-demo -o wide

rtk kubectl -n edgex-edge exec deploy/sensor-anomaly-demo -- \
  python -c 'import json,urllib.request; print(json.load(urllib.request.urlopen("http://127.0.0.1:8080/api/v1/status")))'

rtk kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/service-demo'
```

2초 이상 간격으로 local status를 두 번 읽어 다음을 함께 확인한다.

- `mode=live`, `inputState=fresh`, `modelState=ready`
- source devices가 `virtual-acceleration-x-001`, `virtual-acceleration-y-001`, `virtual-acceleration-z-001`과 정확히 일치
- 두 번째 `latest.origin`과 `counters.framesProcessed`가 첫 번째보다 큼
- `latest.values`가 실제 `Int32` raw X/Y/Z이고 `magnitude`, `score`가 유한함
- `model.algorithm=online-gaussian-baseline-v1`, `warmupSamples=30`, `threshold=4.0`
- 중앙 `/state/service-demo`가 `mode=live`, 같은 binding/result를 반환하고 `observation_error=null`

서비스는 세 Local Data source를 500ms마다 조회한다. 이는 push stream이 아니다. 같은 nanosecond `origin`이 모두 모인 frame만 계산하며 10초보다 오래된 입력, 3회 연속 조회 실패는 `degraded`다. anomaly/clear 전이는 자동 테스트로 검증하지만 실제 장치를 움직여 anomaly를 만드는 현장 시연 전에는 실제 고장 검출 실증으로 판정하지 않는다.

```bash
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/service-demo'
```

정상 기준:

- Serial 6개와 I2C 6개, 총 12개 가상 Device가 서로 다른 inventory 행으로 나타난다.
- 각 행의 `device_service_name`이 `device-serial-jetson` 또는 `device-sensehat-raspi`이고 profile과 resource가 계약과 일치한다.
- `admin_state=UNLOCKED`, `operating_state=UP`, `connection_state=connected`다.
- `overall_status=available`, `telemetry_freshness=fresh`이고 latest Reading 집합이 각 Profile 계약과 일치한다.
- service demo 응답은 raw inventory와 분리된 derived 결과이며 physical source, Device Service, acceleration Device 3개, AI consumer와 node binding을 포함한다.
- upstream 장애 시 HTTP 200의 `mode=unavailable`, `status=degraded`, `observation_error`를 반환하고 값을 0으로 꾸며내지 않는다.

Kubernetes node/workload 상태는 별도 진단이며 위 Device availability를 덮어쓰지 않는다.

## 8A. 12개 Device 저장 이력과 dashboard 그래프

dashboard는 PostgreSQL에 직접 연결하지 않는다. 브라우저가 `state-aggregator`의 선택 Device API를 호출하고, `state-aggregator`가 중앙 EdgeX Core Data API에서 PostgreSQL-backed Event/Reading을 읽는다.

```text
Dashboard
  -> GET /state/devices/{device}/telemetry?window={range}&limit=1000
  -> state-aggregator
  -> EdgeX Core Data API
  -> PostgreSQL
```

Core Data의 `GET /api/v3/event/device/name/{name}`에는 `start`/`end` query를 붙이지 않는다. 이 endpoint는 `offset`/`limit`만 지원하므로 `state-aggregator`가 최신 1,000 Event 이내에서 Event `origin`을 기준으로 `window`를 적용한다. 5분 결과의 가장 오래된 `origin`이 요청 시작시각보다 이전이면 정상으로 판정하지 않는다.

12개 Device의 기본 30분 이력을 API에서 확인한다.

```bash
for name in \
  virtual-temperature-001 virtual-light-001 virtual-magnetic-001 \
  virtual-acceleration-x-001 virtual-acceleration-y-001 virtual-acceleration-z-001 \
  env-sensehat-temperature-01 env-sensehat-humidity-01 env-sensehat-pressure-01 \
  imu-sensehat-compass-01 imu-sensehat-orientation-01 imu-sensehat-gyroscope-01
do
  kubectl get --raw \
    "/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/devices/${name}/telemetry?window=-30m&limit=1000"
done
```

정상 기준:

- 모든 응답은 배열이고 각 Reading의 `device_name`이 요청 Device와 같다.
- `source_name`, `resource_name`, `value_type`, `value`, `timestamp`, nanosecond `origin`과 `event_id`가 보존된다.
- Serial Device 6개는 각각 계약된 `Int32` resource series로 분리된다.
- Sense HAT Device 6개는 Profile별 `Float64` series로 분리되며 temperature는 2개, orientation과 gyroscope는 각각 3개 resource를 표시할 수 있다.
- 조회 오류나 빈 결과를 `/state/devices`의 `latest_readings`로 대체하지 않는다.

브라우저에서는 Assets의 Device 행을 선택해 다음을 확인한다.

1. 선택 직후 기본 `30분` 이력을 조회한다.
2. `5분`, `30분`, `1시간`, `24시간`과 `새로고침`이 선택 Device에만 적용된다.
3. resource별 series, 반환 Reading 수, 실제 첫/마지막 timestamp가 보인다.
4. `최신 1000 events 제한` 문구가 보인다. 한 Event에 Reading이 여러 개면 반환 Reading 수는 1,000보다 클 수 있다.
5. 긴 범위가 최신 1,000 Event로 잘렸을 때 요청한 전체 기간을 모두 읽었다고 해석하지 않는다.
6. 빠르게 Device나 범위를 바꿔도 이전 요청의 늦은 응답이 현재 선택을 덮어쓰지 않는다.
7. 조회 중·빈 결과·오류 상태가 각각 구분되고 오류가 다른 Device나 dashboard 전체를 가짜 정상값으로 바꾸지 않는다.

## 8B. Dashboard Adapter Runtime과 Device 연결 관리

`Device Management`는 Adapter Runtime 조회·재사용/승인 배포 plan과 EdgeX Profile/Device
onboarding을 한 operation으로 관리한다. 자세한 Secret, API, 상태, 재시작·퇴역과 protocol
승격 절차는 [어댑터 런타임과 디바이스 연결 관리](어댑터-런타임-디바이스-연결-관리.md)를
따른다. Assets와 `/state/*`, Workflow Builder의 browser-local dry-run 경계는 바뀌지 않는다.

현재 Deployment는 management feature flag를 활성화하고 namespace별
`edgex-adapter-management-auth` Secret을 요구한다. 다음 조회와 validation은 mutation을
수행하지 않는다.

```bash
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/management/adapters'

kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/management/adapter-runtimes'

# 아래 curl을 사용할 때는 별도 터미널에서 실행한다.
kubectl -n default port-forward service/state-aggregator 18000:8000

curl --fail --silent --show-error \
  -H 'Content-Type: application/json' \
  -d '{
    "adapterId":"serial-jetson",
    "targetNode":"etri-dev0001-jetorn",
    "hardwareBindingId":"jetson-arduino-serial-001",
    "mode":"auto"
  }' \
  http://127.0.0.1:18000/management/adapter-runtimes/plan
```

Connection 전체 dry-run은 runtime 선택을 함께 전달한다.

```bash
curl --fail --silent --show-error \
  -H 'Content-Type: application/json' \
  -d '{
    "adapterId":"serial-jetson",
    "runtime":{
      "mode":"auto",
      "targetNode":"etri-dev0001-jetorn",
      "hardwareBindingId":"jetson-arduino-serial-001"
    },
    "device":{
      "name":"onboarding-dryrun-serial-001",
      "description":"dry-run only",
      "labels":["serial","dry-run"],
      "tags":{"physicalDeviceId":"arduino-001","nodeName":"etri-dev0001-jetorn"},
      "protocolProperties":{
        "Port":"/dev/arduino-001",
        "BaudRate":115200,
        "DeviceID":"arduino-001",
        "ResourceName":"temperature_raw"
      },
      "adminState":"UNLOCKED"
    },
    "profile":{"mode":"existing","name":"etri-arduino-temperature"}
  }' \
  http://127.0.0.1:18000/management/connections/validate
```

정상 기준:

- adapter 응답의 Serial/Sense HAT I2C는 Device Service readback이 성공할 때 `installed`다.
  Device Service가 없더라도 검증된 managed template과 `deploymentEnabled=true`이면
  `installable`, 그 외에는 `unavailable`이다. Modbus/OPC-UA/MQTT/RTSP는 현재
  `unsupported`다.
- runtime inventory의 Serial/I2C는 `managementMode=external`,
  `managementOwner=argocd`, `phase=SERVICE_READY`이고 대시보드 restart/retire가 비활성화된다.
- Serial runtime plan은 exact binding의 기존 `device-serial-jetson`을 `REUSE`한다.
- 위 예시는 이미 `virtual-temperature-001`이 소유한 endpoint/resource를 다시 요청하므로
  `valid=false`와 `protocol_binding_exists`를 반환하는 것이 정상이다. dry-run은 `valid`,
  `issues`, `warnings`, `runtimePlan`, `edgeXPlan`을 반환하며 runtime/Profile/Device를
  생성하지 않는다.
- 유효한 연결 실행은 browser 관리자 token 없이 요청별 `Idempotency-Key`를 요구한다.
  결과는 runtime, Metadata와 first Event 상태를 분리한다. 내부 HMAC은 BFF와 Controller
  사이 요청 무결성용이며 운영자 인증이 아니므로 운영 노출 전 별도 인증·인가가 필요하다.
- 기존 12개 route, external runtime과 EdgeMesh는 자동 검증에서 변경하지 않는다. live
  connection canary는 충돌하지 않는 실장비 endpoint와 등록 binding이 생긴 뒤 수행한다.

## 9. 저장과 캐시 경계

- Device Service 메모리: 공통 Go ring cache, Device/resource별 최근 10분·최대 10,000 sample, 서비스별 sample slot 합계 최대 64MiB, Core Command와 Local Data API용
- 중앙 Core Data/PostgreSQL: 최근·과거 Event/Reading의 영구 저장과 조회
- 로컬 recent window cache: 있음; `/api/v3/localdata/stats`와 custom metrics로 관측, Pod 재시작 시 초기화, 중앙 history fallback 없음
- 64MiB 계산 경계: sample slot 배열만 포함; Go map/runtime/HTTP buffer는 제외되며 Pod memory limit가 전체 프로세스 상한
- SQLite outbox/offline replay: 없음
- 별도 InfluxDB: 없음
- `sensor-anomaly-demo` 결과: process memory의 최근 최대 1,000건; Pod 재시작 시 초기화, raw history 저장소가 아님

따라서 각 Device Service와 같은 edge node의 Workflow Pod는 `edge-ai.io/local-data-client=true` label과 Service FQDN으로 최근 구간을 직접 소비한다. 이 label은 현재 Flannel 환경에서 접근 제어를 강제하지 않는다. 이 기능은 bounded read cache일 뿐 중앙 단절 중 미전송 Event 보존·재전송이나 장기 history를 제공하지 않는다.

### 10.2 재실행 조건과 기대 결과

**Test Scenario: source 장애 후 Device 상태와 수집 복구**

- 시작 조건: 중앙 Core 서비스와 두 Device Service가 Ready이고 12개 Device가 `UP`, latest origin이 증가한다.
- 실행 역할: 테스트베드 운영자. 실제 장치 또는 kernel driver/reader process를 하나씩만 중단한다.
- 확인 순서: 장애 전 `tools/verify_e2e.sh` 실행 → 대상 source 중단 → Core Metadata의 해당 6개 Device `DOWN` 확인 → source 복구 → 6개 `UP` 확인 → Local Data와 Core Data origin 증가 확인.
- 기대 결과: 비대상 Device Service와 EdgeMesh는 변경되지 않고 대상 physical source에 묶인 6개 Device만 함께 상태 전이한다.

**Test Scenario: 중앙 MessageBus 장애 중 로컬 연속성**

- 시작 조건: Argo CD Application policy와 MessageBus replica를 기록하고 두 local stats 및 대표 Core Data Event를 저장한다.
- 실행 역할: 데이터 유실과 중앙 중단을 승인받은 운영자. MessageBus endpoint가 실제 0 Pod인지 확인한 뒤 제한된 시간만 중단한다.
- 확인 순서: 장애 중 두 Local Data latest/stats와 `sensor-anomaly-demo` 증가 확인 → Core Data count/origin 고정 확인 → MessageBus 1 replica와 Argo self-heal 원복 → 중앙 새 Event 확인.
- 기대 결과: 로컬 ring과 같은-node AI consumer는 지속되지만 중앙 Event는 멈춘다. 복구 후 새 Event는 재개되지만 outage 구간은 replay되지 않는다.

재검증 후에는 다음 read-only 진입점으로 전체 상태를 다시 확인한다.

```bash
rtk bash tools/verify_e2e.sh
```

이 결과는 실제 케이블·보드 손분리 현장 시연을 대체하지 않는다. 실제 손분리 → 해당 6개 Device `DOWN`/dashboard degraded → 재연결 → 새 Event 발행은 현장 gate로 남긴다. 현재 Device Service에는 durable outbox가 없으므로 중앙 단절 중 데이터 보존을 완료 기능으로 설명하지 않는다. Modbus와 OPC-UA는 실제 endpoint가 없어 완료로 판정하지 않는다.

`sensor-anomaly-demo`는 실제 증가 raw origin과 로컬 inference/중앙 readback을 배포 gate로 검증한다. detector anomaly/clear 전이는 결정론적 테스트 대상이고 실제 장치 움직임 anomaly는 별도 현장 시연 gate다. 이 고정 Deployment를 동적 workflow 실행, runtime migration 또는 offloading 완료로 설명하지 않는다.
