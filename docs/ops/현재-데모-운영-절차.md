# 현재 서비스 데모 운영 절차

## 목적

이 문서는 2026-07-21 Agent 퇴역 이후의 중앙 EdgeX 유지 상태와 비어 있는 `edgex-edge` 전환 상태를 점검한다. 실제 센서 수집 데모 절차는 Jetson Serial Device Service가 구현된 뒤 추가한다.

## 배치 기준

| 구분 | 현재 기준 |
|---|---|
| 중앙 namespace | `edgex-system` |
| edge namespace | `edgex-edge` |
| 중앙 노드 | `etri-ser0002-cgnmsb` |
| 중앙 workload | ingest gateway, Core Keeper/Metadata/Data/Command, internal MessageBus, PostgreSQL |
| edge workload | 없음; Namespace와 default-deny NetworkPolicy만 유지 |
| 운영 진입점 | `edgex/k8s/kustomization.yaml` |
| Argo CD Application | `edgex-telemetry` |

EdgeMesh 리소스는 이 절차의 변경 대상이 아니다. 고정 ClusterIP/PodIP/node IP로 우회하지 않는다.

## 1. 로컬 render 검증

```bash
kubectl kustomize edgex/k8s >/tmp/edgex-current.yaml
kubectl apply --dry-run=server -f /tmp/edgex-current.yaml
```

정상 기준:

- 중앙 Core/MessageBus/PostgreSQL/gateway가 render된다.
- `Namespace/edgex-edge`와 `NetworkPolicy/edgex-edge-default-deny`가 render된다.
- `edgex-edge-agent-jetson`, `edgex-edge-agent-sensehat`이 없다.
- Agent PVC, Agent contract ConfigMap과 Agent 전용 egress policy가 없다.
- `edgex-metadata-bootstrap`과 `edgex-metadata-contract`이 없다.
- `device-mqtt`와 edge-local broker가 없다.
- 중앙 `edgex-messagebus` Service type은 `ClusterIP`다.

빠른 확인:

```bash
kubectl kustomize edgex/k8s | grep -E \
  'edgex-edge-agent|edgex-metadata-bootstrap|sensor-gateways'
```

정상 상태에서는 출력이 없고 `grep` exit code가 1이다.

## 2. Argo CD 상태

```bash
kubectl -n argocd get application edgex-telemetry \
  -o jsonpath='{.spec.source.targetRevision}{"\n"}{.status.sync.status}{"\n"}{.status.health.status}{"\n"}'
```

Application은 자동 prune/self-heal을 사용한다. 파드부터 수동 삭제하지 말고 Agent가 제거된 Git revision을 먼저 적용해야 한다. 그렇지 않으면 self-heal로 Agent가 다시 생성된다.

## 3. live workload와 storage

```bash
kubectl -n edgex-system get deploy,statefulset,job,pod,service,pvc -o wide
kubectl -n edgex-edge get deploy,pod,pvc,configmap,networkpolicy
```

정상 기준:

- 중앙 Core 서비스, gateway와 PostgreSQL이 Ready다.
- Core common-config bootstrap Job은 Completed일 수 있다.
- 중앙 PostgreSQL PVC는 Bound다.
- `edgex-edge`에 Deployment, Pod와 Agent outbox PVC가 없다.
- `edgex-edge-default-deny`만 유지된다.
- 중앙 `edgex-messagebus`는 ClusterIP다.

## 4. Agent 전용 Metadata 제거 확인

```bash
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-metadata:59881/proxy/api/v3/deviceservice/name/edge-telemetry-agent'
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-metadata:59881/proxy/api/v3/deviceprofile/name/etri-sensehat'
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-metadata:59881/proxy/api/v3/device/name/sensehat-001'
```

Agent 퇴역 완료 후 세 객체는 조회되지 않아야 한다. 삭제 순서는 Device → Device Profile → Device Service다. 이름이 다른 Device/Profile이 같은 service/profile을 참조하는지 먼저 조회하고, 정확한 세 객체 외에는 삭제하지 않는다.

## 5. 중앙 API 확인

```bash
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-metadata:59881/proxy/api/v3/ping'
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-data:59880/proxy/api/v3/ping'
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-command:59882/proxy/api/v3/ping'
```

중앙 API가 응답하더라도 실제 Device Service와 Event가 없으므로 physical device demo가 완료된 것은 아니다.

## 6. dashboard 해석

Agent 전용 Metadata가 삭제되면 `sensehat-001`이 현재 inventory에서 사라지는 것이 정상이다. dashboard가 캐시된 과거 device를 계속 표시하면 state-aggregator cache와 Core Metadata 응답을 분리해 점검한다.

현재 정상 표현:

- 중앙 EdgeX: available
- edge Device Service: not deployed / transition
- registered physical devices: 실제 Metadata 응답 기준
- telemetry: `no_events` 또는 등록 device 없음

이 상태를 `available device`나 service demo 완료로 보정하지 않는다.
