# 현재 서비스 데모 운영 절차

## 목적

이 문서는 Jetson Arduino Uno → EdgeX Serial Device Service → 가상 Device 6개 → 중앙 MessageBus/Core Data/PostgreSQL → state-aggregator/dashboard로 이어지는 현재 정상 경로를 점검한다. 기존 Agent, SQLite outbox, Sense HAT bootstrap, edge-local MQTT broker와 InfluxDB workload는 현재 경로가 아니다.

Core Data telemetry freshness는 latest Event의 nanosecond `origin`을 sample 시각으로 계산하며 API 조회 시각이나 Kubernetes 상태로 대체하지 않는다.

## 배치 기준

| 구분 | 현재 기준 |
|---|---|
| 중앙 namespace | `edgex-system` |
| edge namespace | `edgex-edge` |
| 중앙 노드 | `etri-ser0002-cgnmsb` |
| 중앙 workload | Core Keeper/Metadata/Data/Command, internal MessageBus, PostgreSQL, 유지 중인 ingest gateway |
| edge workload | `device-serial-jetson` 1 replica |
| physical node | `etri-dev0001-jetorn` |
| physical source | Arduino Uno, wire `device_id=arduino-001`, `/dev/arduino-001` |
| EdgeX inventory | 가상 Device 6개 / 1-resource Profile 6개 / `device-serial-jetson` |
| 운영 진입점 | `edgex/k8s/kustomization.yaml` |
| Argo CD Application | `edgex-telemetry` |

EdgeMesh 리소스는 이 절차의 변경 대상이 아니다. Kubernetes `ClusterIP Service` 객체는 정상 서비스 디스커버리에 사용하지만 고정 ClusterIP, PodIP와 node IP를 설정에 넣거나 우회 경로로 사용하지 않는다. Device Service는 중앙 Keeper, Metadata와 MessageBus의 `.svc.cluster.local` FQDN을 사용한다.

## 가상 Device 계약

| Device | Profile | Resource | Command |
|---|---|---|---|
| `virtual-temperature-001` | `etri-arduino-temperature` | `temperature_raw` | `temperature` |
| `virtual-light-001` | `etri-arduino-light` | `light_raw` | `light` |
| `virtual-magnetic-001` | `etri-arduino-magnetic` | `magnetic_raw` | `magnetic` |
| `virtual-acceleration-x-001` | `etri-arduino-acceleration-x` | `acceleration_x_raw` | `acceleration_x` |
| `virtual-acceleration-y-001` | `etri-arduino-acceleration-y` | `acceleration_y_raw` | `acceleration_y` |
| `virtual-acceleration-z-001` | `etri-arduino-acceleration-z` | `acceleration_z_raw` | `acceleration_z` |

여섯 Device는 같은 `Port=/dev/arduino-001`, `BaudRate=115200`, `DeviceID=arduino-001`을 사용하고 `ResourceName`만 다르다. Driver는 이 공통 연결을 공유 Serial reader 1개로 열며, acceleration wire sample 하나를 X/Y/Z Event 세 개로 나눈다.

## 1. 로컬 render 검증

```bash
kubectl kustomize edgex/k8s >/tmp/edgex-current.yaml
kubectl apply --dry-run=server -f /tmp/edgex-current.yaml
```

정상 기준:

- 중앙 Core/MessageBus/PostgreSQL/gateway가 render된다.
- `Namespace/edgex-edge`, default-deny와 Device Service별 최소 NetworkPolicy가 render된다.
- `Service`와 `Deployment/device-serial-jetson`이 render된다.
- Device Service는 `etri-dev0001-jetorn`에 고정되고 `hostNetwork: true`를 사용하지 않는다.
- host의 Arduino by-id CharDevice만 Pod의 `/dev/arduino-001`에 마운트된다.
- ConfigMap에는 위 Profile 6개와 Device list 1개가 포함된다.
- 중앙 Keeper/Metadata/MessageBus는 `.svc.cluster.local` FQDN으로 참조된다.
- `edgex-edge-agent-*`, Agent PVC/ConfigMap/bootstrap, `device-mqtt`, edge-local broker와 InfluxDB workload를 배포하지 않는다.

현재 PoC의 Serial 장치 접근은 단일 Pod에 `privileged: true`, UID/GID 0을 허용한다. 이 예외는 정확한 CharDevice mount, `Recreate` 전략, service-account token 비마운트와 최소 NetworkPolicy로 제한한다. 후속 운영 강화에서는 Device Plugin 또는 더 좁은 장치 권한으로 대체한다.

## 2. Argo CD 상태

```bash
kubectl -n argocd get application edgex-telemetry \
  -o jsonpath='{.spec.source.targetRevision}{"\n"}{.status.sync.status}{"\n"}{.status.health.status}{"\n"}{.status.operationState.phase}{"\n"}'
```

정상 기준은 대상 revision이 의도한 Git commit이고 `Synced`, `Healthy`, `Succeeded`인 것이다. Application은 prune/self-heal을 사용하므로 live 리소스를 임의 수정하지 않고 Git의 root Kustomize를 고친다.

## 3. live workload와 장치 mount

```bash
kubectl -n edgex-system get deploy,statefulset,job,pod,service,pvc -o wide
kubectl -n edgex-edge get deploy,pod,service,pvc,configmap,networkpolicy -o wide
kubectl -n edgex-edge get deployment device-serial-jetson \
  -o jsonpath='{.spec.template.spec.nodeSelector.kubernetes\.io/hostname}{"\n"}{.spec.template.spec.hostNetwork}{"\n"}{.spec.template.spec.containers[0].image}{"\n"}'
```

정상 기준:

- 중앙 Core 서비스와 PostgreSQL이 Ready다. common-config bootstrap Job은 Completed일 수 있다.
- `device-serial-jetson` Pod가 Jetson에서 `1/1 Running`이다.
- image는 immutable ARM64 digest다.
- Pod restart가 반복 증가하지 않는다.
- `edgex-edge`에 Agent outbox PVC, local broker와 별도 telemetry DB가 없다.

로그에서 시작 중 잘린 Serial line 1~2개가 malformed로 폐기될 수 있다. 이후 metric 등록, reader restart, Metadata update가 반복되거나 ERROR가 계속 나오면 정상으로 보지 않는다.

## 4. Core Metadata binding

```bash
kubectl get --raw \
  '/api/v1/namespaces/edgex-system/services/http:edgex-core-metadata:59881/proxy/api/v3/deviceservice/name/device-serial-jetson'

for name in \
  virtual-temperature-001 virtual-light-001 virtual-magnetic-001 \
  virtual-acceleration-x-001 virtual-acceleration-y-001 virtual-acceleration-z-001
do
  kubectl get --raw \
    "/api/v1/namespaces/edgex-system/services/http:edgex-core-metadata:59881/proxy/api/v3/device/name/${name}"
done
```

정상 기준:

- Device Service base address는 `http://device-serial-jetson.edgex-edge.svc.cluster.local:59910`이다.
- 위 Device 6개가 각각 `UNLOCKED`, `UP`이고 service/profile binding이 일치한다.
- 각 Device의 Serial protocol은 공통 물리 endpoint와 고유 `ResourceName`을 가진다.
- `tags.physicalDeviceId=arduino-001`, `tags.nodeName=etri-dev0001-jetorn`이다.
- aggregate EdgeX Device `arduino-001`과 Profile `etri-arduino-serial`은 없다.

## 5. Core Data Event/Reading

```bash
for name in \
  virtual-temperature-001 virtual-light-001 virtual-magnetic-001 \
  virtual-acceleration-x-001 virtual-acceleration-y-001 virtual-acceleration-z-001
do
  kubectl get --raw \
    "/api/v1/namespaces/edgex-system/services/http:edgex-core-data:59880/proxy/api/v3/event/device/name/${name}?limit=1"
done
```

정상 기준:

- Device별 latest Event에 계약된 `Int32` Reading 하나만 있다.
- units는 `raw`이고 Event/Reading의 nanosecond `origin`이 계속 증가한다.
- acceleration wire sample은 X/Y/Z Device에 각각 독립 Event로 저장된다.
- API readback으로 저장을 확인하며 중앙 MessageBus의 MQTT ACK만으로 persistence를 주장하지 않는다.

## 6. read-only Core Command

```bash
for pair in \
  virtual-temperature-001/temperature \
  virtual-light-001/light \
  virtual-magnetic-001/magnetic \
  virtual-acceleration-x-001/acceleration_x \
  virtual-acceleration-y-001/acceleration_y \
  virtual-acceleration-z-001/acceleration_z
do
  kubectl get --raw \
    "/api/v1/namespaces/edgex-system/services/http:edgex-core-command:59882/proxy/api/v3/device/name/${pair}"
done
```

정상 기준은 각 Device Service가 10분 recent cache에서 최신값 1개와 `origin`을 반환하는 것이다. sample이 10분 보존 범위를 벗어나거나 Pod가 재시작해 아직 새 sample이 없으면 최신값 조회가 실패할 수 있다. Profile에는 writable resource가 없으므로 PUT이나 actuator command를 보내지 않는다.

## 7. Jetson Local Data API

NetworkPolicy 허용과 같은-node 배치를 함께 확인하려면 임시 client Pod를 Jetson에 배치한다.

```bash
kubectl run local-data-check \
  --namespace default \
  --image=curlimages/curl:8.12.1 \
  --restart=Never \
  --labels=edge-ai.io/local-data-client=true \
  --overrides='{"spec":{"nodeSelector":{"kubernetes.io/hostname":"etri-dev0001-jetorn"}}}' \
  --command -- sleep 3600

kubectl wait --namespace default \
  --for=condition=Ready pod/local-data-check \
  --timeout=120s

kubectl exec --namespace default local-data-check -- \
  curl --fail --silent --show-error \
  'http://device-serial-jetson.edgex-edge.svc.cluster.local:59910/api/v3/localdata/device/name/virtual-temperature-001/resource/name/temperature_raw/latest'

kubectl exec --namespace default local-data-check -- \
  curl --fail --silent --show-error \
  'http://device-serial-jetson.edgex-edge.svc.cluster.local:59910/api/v3/localdata/device/name/virtual-temperature-001/resource/name/temperature_raw?limit=20'

kubectl delete pod --namespace default local-data-check
```

정상 기준:

- latest는 `count=1`이고 `temperature_raw`, `Int32`, 원본 nanosecond `origin`을 반환한다.
- recent는 `origin` 오름차순이며 `count`와 `samples` 길이가 같다.
- `retention.maxAge=10m0s`, `retention.maxSamples=10000`이다.
- 알려진 source에 범위 데이터가 없으면 `200`과 빈 `samples`, latest가 없으면 `404`다.
- `limit`은 1~10,000이고 기본값은 1,000이다.

다른 5개 가상 Device도 각 Profile의 resource 이름으로 같은 계약을 확인한다. 임시 Pod는 검증 뒤 반드시 삭제한다.

## 8. dashboard API

```bash
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/devices'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/dashboard'
```

정상 기준:

- 위 가상 Device 6개가 서로 다른 inventory 행으로 나타난다.
- 각 행의 `device_service_name=device-serial-jetson`, profile과 resource가 계약과 일치한다.
- `admin_state=UNLOCKED`, `operating_state=UP`, `connection_state=connected`다.
- `overall_status=available`, `telemetry_freshness=fresh`이고 latest Reading은 하나다.

Kubernetes node/workload 상태는 별도 진단이며 위 Device availability를 덮어쓰지 않는다.

## 9. 저장과 캐시 경계

- Device Service 메모리: Device/resource별 최근 10분·최대 10,000 sample, Core Command와 Local Data API용
- 중앙 Core Data/PostgreSQL: 최근·과거 Event/Reading의 영구 저장과 조회
- 로컬 recent window cache: 있음; Pod 재시작 시 초기화, 중앙 history fallback 없음
- SQLite outbox/offline replay: 없음
- 별도 InfluxDB: 없음

따라서 같은 Jetson의 Workflow Pod는 `edge-ai.io/local-data-client=true` label과 Service FQDN으로 최근 구간을 직접 소비할 수 있다. 이 기능은 bounded read cache일 뿐 중앙 단절 중 미전송 Event 보존·재전송이나 장기 history를 제공하지 않는다.

## 10. 남은 장애 검증

parser의 malformed line 복구, 공유 reader, state fan-out, 마지막 route 제거 시 close, reader backoff와 동일 Metadata update의 no-op 동작은 단위 테스트한다. 실제 케이블 분리 → 여섯 Device DOWN/degraded → 재연결 → 새 Event 발행은 현장 시연 gate로 남긴다. 현재 Device Service에는 durable outbox가 없으므로 중앙 단절 중 데이터 보존을 완료 기능으로 설명하지 않는다.
