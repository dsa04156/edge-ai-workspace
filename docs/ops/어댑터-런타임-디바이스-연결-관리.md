# 어댑터 런타임과 디바이스 연결 관리

## 목적

운영자가 Kubernetes manifest를 직접 작성하지 않고 대시보드 `디바이스 관리`에서 다음
순서로 물리 장비 연결을 관리하는 절차다.

```text
KubeEdge 노드 선택
  -> Discovery Plan 기반 후보 / 수동 endpoint 후보 검색
  -> 검토 대기 / 승인 / 거절
  -> exact Git binding·검증 package 일치 확인
  -> 기존 Runtime 재사용 또는 검증된 template 배포 plan
  -> EdgeX Profile / Device 등록
  -> Metadata readback
  -> first Event / Reading 확인
  -> 등록 연결 / 실제 장비 관측 / 통신 / 데이터 상태 확인

기존 사전 등록 장비의 수동 관리
  -> 선택 노드의 Runtime / EdgeX Device 확인
  -> protocol / Device Service / hardware binding 선택
  -> 기존 connection validation / apply
```

EdgeX Core Metadata와 Core Data가 물리 Device와 telemetry의 권위다.
`AdapterRuntime`은 Device inventory가 아니라 Device Service workload의 desired state다.

## 대시보드 노드별 관리

`디바이스 관리` 상단의 노드 카드는 다음 네 출처를 한 운영 범위로 합성한다.

- `GET /state/nodes`의 KubeEdge/Kubernetes 노드 관측 상태
- Adapter Runtime의 `targetNode`
- EdgeX Device 응답의 `node_name` 또는 Metadata `tags.nodeName`
- Git Adapter Catalog의 등록 `hardwareBindings[].nodeName`

노드를 선택하면 물리 연결 증거, Runtime inventory, protocol package, 기존 EdgeX Device 목록과 연결
마법사의 target node가 함께 바뀐다. 등록 1단계는 protocol/Device Service를 먼저 선택한다.
선택 노드에서 재사용하거나 설치할 수 있는 검증 package는 활성화되고, 다른 노드의 installed
Adapter와 미검증 protocol은 상태와 이유를 확인할 수 있지만 비활성화된다. target node와 raw
device path는 직접 입력할 수 없다.
관리 카드에는 `node_type=edge_*`인 노드와 Runtime·Device·등록 binding이 실제로 참조하는
노드만 표시한다. 관계없는 중앙 `cloud_server` 노드는 디바이스 연결 대상에 섞지 않는다.

이 노드 범위는 workload placement와 운영 탐색을 위한 것이다. Node가 미관측이거나
NotReady여도 그 사실만으로 EdgeX Device의 `available` 상태를 강등하지 않는다. Device
inventory와 `adminState`/`operatingState`는 Core Metadata, telemetry freshness와 첫 Event는
Core Data가 계속 권위다.

### 연결 등록과 실제 장비 관측

`등록됨`은 Git 카탈로그에 노드와 exact 장치 경로가 허용됐다는 뜻이며 장비가 지금 꽂혀
있다는 뜻이 아니다. 대시보드는 한 카드에서 다음 네 증거를 별도로 표시한다.

| 표시 | 근거 | 의미 |
|---|---|---|
| 연결 등록 | Adapter Catalog `hardwareBindings[]` | 운영자가 선택할 수 있는 노드·경로·protocol tuple |
| 장비 관측 | EdgeX Device `operatingState`와 Device Service readback | `UP`이면 관측, 모든 연결 Device가 `DOWN`/`LOCKED`면 미관측, 근거가 없으면 미확인 |
| 통신 상태 | EdgeX `adminState`/`operatingState` | connected, disconnected, unknown |
| 데이터 상태 | Core Data latest Event `origin` | fresh, stale, missing, unknown |

신규 등록 시 서버는 EdgeX Device tag에 `hardwareBindingId`, `physicalDeviceId`, `nodeName`을
저장한다. 따라서 같은 Device Service가 여러 USB/I2C endpoint를 소유해도 정확한 물리 연결로
묶을 수 있다. 기존 Device에 `hardwareBindingId`가 없으면 현재 전환 기간에는
`physicalDeviceId`와 service/protocol을 사용하며, 둘 다 없을 때는 단일 binding인 경우에만
안전하게 묶는다.

고정된 `edge-device-discovery` Agent만 read-only `/dev`, `/sys`에서 중앙 Discovery
Plan이 허용한 stable Serial identity와 I2C identity rule을 확인한다. I2C 버스 존재만으로
센서 후보를 만들지 않으며 네트워크 대역 scan은 수행하지 않는다. MQTT는 자기등록 schema
parser까지만 있고 subscriber가 없으며 Modbus, OPC-UA, ONVIF scanner는 미구현이다.

이 결과는 `발견 후보`이지 위 표의 `장비 관측`이 아니다. exact Device Catalog match 뒤
운영자가 승인하면 Controller가 외부 인증, 검증 Runtime 재사용/배포, 실제 image digest,
Profile/Device 등록과 readback, first Event를 하나의 영속 Saga로 진행한다.
`EVENT_CONFIRMED` 이전은 등록 완료가 아니다.

### 화면 사용 순서

노드를 선택한 뒤에는 한 화면에서 모든 입력을 동시에 다루지 않고 다음 네 작업 탭을 사용한다.

1. `장비 발견`: Agent 상태와 후보의 presence·상태·인증·package를 검색/필터한다.
   `PENDING_APPROVAL`의 `등록 가능` 후보를 승인하면 영속 Registration Saga가 시작된다.
   미지원 후보는 거절하고, 인증/backend 실패는 원인을 확인한 뒤 허용된 상태에서 재시도한다.
2. `노드 현황`: `등록 연결과 실제 장비 상태`에서 네 증거를 비교하고 Runtime, protocol package와 기존 EdgeX Device를 확인한다. 미검증 protocol은 `설치 전 확인이 필요한 프로토콜`을 펼쳤을 때 표시된다.
3. `새 디바이스 등록`: `연결 선택 → 디바이스 정보 → 프로필 → 검증 및 연결` 순서로 진행한다. 연결 선택 안에서는 protocol/Device Service → 등록된 물리 연결 → Device Service 준비 방식 순서로 선택한다. 한 번에 한 단계만 표시되며 실행 계획과 결과는 마지막 단계에 있다.
4. `기존 디바이스 수정`: 선택 노드의 Device를 목록에서 먼저 고른 뒤 설명, label, `adminState` 등 허용된 항목만 수정한다. protocol properties JSON은 고급 설정에 있다.

노드 현황의 Device 카드에 있는 `수정`을 누르면 같은 Device가 선택된 수정 탭으로 이동한다.
노드를 바꾸면 이전 수정 대상은 해제되고 새 노드의 Runtime·Adapter·Device 목록이 함께
갱신된다. 탭과 단계 분리는 입력 밀도를 줄이기 위한 UI 흐름이며 validation,
idempotency와 EdgeX authority 규칙은 그대로 적용된다.

등록 현황의 `프로필 만들기`는 Profile만 별도로 준비할 때 사용한다.

1. 이름, 제조사, 모델과 설명을 입력한다.
2. 각 읽기 resource의 고유 이름, EdgeX value type, 단위와 설명을 입력한다.
3. `Profile 검증`으로 같은 이름의 충돌과 resource 계약을 확인한다.
4. 검증 이후 입력을 바꾸지 않은 상태에서만 `Profile 생성`을 실행한다.
5. 기존 동일 계약이면 새 Profile을 만들지 않고 재사용한다.

후보 화면에서 연 Profile은 model과 capability 이름만 초안으로 채운다. value type과
units는 장비 문서·Manifest·parser 계약을 확인해 운영자가 입력한다. Profile을 생성해도
검증된 parser, immutable Device Service image와 exact hardware binding은 자동으로
추가되지 않으므로 후보 승인 가능 상태가 바로 바뀌지 않는 것이 정상이다.

### 프로토콜 패키지 상태

| 화면 상태 | 선택 가능 | 조건 |
|---|---|---|
| 재사용 가능 | 예 | 선택 노드의 등록 binding과 `UNLOCKED` Device Service가 있음 |
| 설치 가능 | 예 | 등록 binding, 검증 완료 template, `deploymentEnabled=true`이고 Device Service는 아직 없음 |
| 연결 등록 필요 | 아니오 | package는 있으나 선택 노드의 등록 binding이 없음 |
| 검증 필요 | 아니오 | image/profile/protocol/실장비 검증이 완료되지 않음 |

현재 live catalog에서 Serial과 Sense HAT I2C는 Argo CD 소유 Runtime을 `재사용 가능`으로
표시한다. Modbus/OPC-UA/MQTT/RTSP는 `검증 필요`이며 설치 버튼이 없다. 향후 `설치 가능`으로
승격하려면 검증된 immutable image, profile, exact binding, 최소 권한 manifest와 실장비
first Event 증거를 같은 Git 변경으로 반영해야 한다.

## 배포와 소유권

| 대상 | namespace | 소유자 | 대시보드 동작 |
|---|---|---|---|
| `device-serial-jetson` | `edgex-edge` | Argo CD | 조회·재사용만 |
| `device-sensehat-raspi` | `edgex-edge` | Argo CD | 조회·재사용만 |
| `edge-device-discovery` | `edgex-edge` | Argo CD | 지정 node에서 Plan 제한 후보 report 전송 |
| `edgex-adapter-controller` | `edgex-edge` | Argo CD | 내부 API, 상태 머신, Registration Saga와 reconciliation |
| `edgex-adapter-controller-state` PVC | `edgex-edge` | Argo CD/Controller | candidate, Plan, Saga, audit SQLite 영속 저장 |
| `edgex-device-discovery-registry` ConfigMap | `edgex-edge` | Adapter Controller | 기존 후보의 최초 1회 migration 입력 |
| Controller가 만든 `AdapterRuntime`과 workload | `edgex-edge` | Adapter Controller | 조회·재시작·조건부 퇴역 |
| `state-aggregator` 관리 BFF와 dashboard | `default` | Argo CD | 운영자 단일 사용자 진입점 |

브라우저와 `state-aggregator` ServiceAccount에는 Kubernetes 쓰기 권한이 없다. Controller
Role만 `edgex-edge`의 `AdapterRuntime`, Deployment, Service, ConfigMap과 NetworkPolicy를
관리한다. Cluster 범위 권한은 target node `get/list`뿐이다.
Discovery Agent의 ServiceAccount는 Kubernetes API token을 마운트하지 않으며 Controller
Service DNS와 HMAC report API에만 접근한다.

## Secret 준비

평문 HMAC key를 Git에 넣지 않는다. 최초 배포 전에 다음 스크립트를 한 번 실행한다.

```bash
edgex/k8s/scripts/provision-adapter-management-secrets.sh
edgex/k8s/scripts/preflight-adapter-management-secrets.sh
```

스크립트는 같은 `internal-hmac-key`를 다음 두 Secret에 넣는다.

- `default/edgex-adapter-management-auth`: `management-hmac-key`, `internal-hmac-key`
- `edgex-edge/edgex-adapter-management-auth`: `internal-hmac-key`

기존 Secret이 있으면 기본 실행은 회전을 거부한다. 의도적 회전만 `--replace`로 수행하고
두 Deployment를 함께 재시작한다. Secret 값은 명령 출력이나 문서에 기록하지 않는다.

## 배포 확인

운영 배포 진입점은 계속 `edgex/k8s`와 Argo CD Application `edgex-telemetry`다.

```bash
kubectl get application edgex-telemetry -n argocd
kubectl get application edge-orch-state-aggregator -n argocd
kubectl get crd adapterruntimes.edgeai.etri.re.kr
kubectl get deployment,service -n edgex-edge \
  edgex-adapter-controller device-serial-jetson device-sensehat-raspi
kubectl get daemonset edge-device-discovery -n edgex-edge
kubectl get adapterruntimes.edgeai.etri.re.kr -n edgex-edge
kubectl get pvc edgex-adapter-controller-state -n edgex-edge
```

정상 기준:

- 두 Application이 `Synced/Healthy`다.
- Controller, 기존 두 Device Service와 세 node의 Discovery DaemonSet이 `Ready`다.
- 기존 Serial/I2C는 `AdapterRuntime` CR이 없어도 정상이다. Catalog의 external runtime으로
  발견한다.
- Controller, Discovery Agent와 Device Service image는 immutable digest다.
- Service는 DNS discovery용 ClusterIP 객체를 사용하지만 manifest/API에 고정 ClusterIP,
  PodIP 또는 node IP가 없다.
- EdgeMesh resource는 이 배포에서 변경되지 않는다.

## 장비 발견 후보 조회와 검토

Discovery Agent는 30초 주기로 HMAC 서명 report를 보낸다. clean reconciliation에서
사라진 자동 후보는 즉시 `STALE`이고 같은 stable identity가 재연결되면 같은 candidate ID와
이전 상태를 복구한다. Agent/Plan 오류가 있는 빈 report는 장비 분리 증거로 사용하지 않는다.
후보, 상태 이력과 등록 Saga는 PVC SQLite에 남는다.

```bash
curl --fail --silent --show-error \
  'http://127.0.0.1:18000/management/discovery?includeIgnored=true&limit=2000'

curl --fail --silent --show-error \
  'http://127.0.0.1:18000/management/discovery?node=etri-dev0001-jetorn&protocol=serial&presence=present'
```

후보 상태:

| 필드 | 값 | 의미 |
|---|---|---|
| `source` | `node-scan` | stable USB Serial 또는 검증된 I2C identity를 Agent가 관측 |
| `source` | `manual` | 운영자가 endpoint 후보를 선언 |
| `presence` | `present` | 최근 node report에서 다시 관측 |
| `presence` | `stale` | 마지막 관측이 freshness 기준을 넘김 |
| `presence` | `declared` | 수동 선언이며 도달성·통신 검증 전 |
| `decision` | `pending` / `accepted` / `ignored` | 기존 Dashboard BFF 하위 호환 값. `accepted`는 승인 또는 FAILED retry, `ignored`는 거절 요청 |
| `state` | `DETECTED` … `EVENT_CONFIRMED` | 명시적 발견·승인·등록 상태 머신 |
| `authState` | `not_checked` / `approved` / `denied` / `unavailable` / `error` | 외부 인증 상태 |
| `packageState` | `registration-ready` | exact Git binding과 검증 package가 일치 |
| `packageState` | `binding-required` | 새 hardware binding과 장치 mount 검토 필요 |
| `packageState` | `verification-required` | Device Service/profile/실장비 검증 필요 |
| `packageState` | `unsupported` | 현재 catalog로 처리할 수 없음 |

수동 후보 생성·삭제와 후보 승인·거절·재시도는 browser 관리자 token 없이 요청마다
고유한 `Idempotency-Key`를 요구한다. state-aggregator가 Adapter Controller로 보내는
내부 요청에는 HMAC을 유지한다. 아래 예시는 endpoint 후보만 만들며 MQTT broker나
Device Service를 설치하지 않는다.

```bash
curl --fail --silent --show-error \
  -H 'Idempotency-Key: discovery-manual-mqtt-001' \
  -H 'Content-Type: application/json' \
  -d '{
    "nodeName":"etri-dev0001-jetorn",
    "protocol":"mqtt",
    "transport":"mqtt",
    "displayName":"라인 1 온도 MQTT 후보",
    "properties":{
      "Broker":"mqtts://broker.example:8883",
      "Topic":"factory/line-1/temperature"
    },
    "note":"자격 증명과 실장비 검증 전"
  }' \
  http://127.0.0.1:18000/management/discovery/manual
```

비밀번호·token·secret 성격의 property와 `user:password@host` URL은 거부한다. 승인된
후보는 별도 decommission Saga 없이 삭제할 수 없다. 같은 idempotency 요청을 재전송해도
Runtime/Profile/Device가 중복되지 않는다. 이 SQLite를 telemetry DB나 EdgeX/KubeEdge
Device inventory로 사용하지 않는다. 상세 승인·retry·rollback은
`ops/디바이스-발견-등록-운영.md`를 따른다.

## 조회와 plan

로컬 점검은 Kubernetes API Service proxy 또는 port-forward를 사용한다.

```bash
kubectl -n default port-forward service/state-aggregator 18000:8000

curl --fail --silent --show-error \
  http://127.0.0.1:18000/management/adapters

curl --fail --silent --show-error \
  http://127.0.0.1:18000/management/adapter-runtimes

curl --fail --silent --show-error \
  http://127.0.0.1:18000/management/profiles

curl --fail --silent --show-error \
  -H 'Content-Type: application/json' \
  -d '{
    "adapterId":"serial-jetson",
    "targetNode":"etri-dev0001-jetorn",
    "hardwareBindingId":"jetson-arduino-serial-001",
    "mode":"auto"
  }' \
  http://127.0.0.1:18000/management/adapter-runtimes/plan
```

현재 Serial plan의 정상 결과는 기존 `device-serial-jetson`을 선택한 `REUSE`다. Sense HAT도
같은 방식으로 `sensehat-raspi`, `etri-dev0003-raspi5`,
`raspi5-sensehat-i2c-001` 조합을 사용한다.

Profile 생성 API는 검증과 생성을 분리한다. 아래 payload는 예시이므로 실제 센서의
resource/value type/units 계약으로 바꾼다.

```bash
PROFILE_PAYLOAD='{
  "name":"factory-temperature-v1",
  "description":"읽기 전용 온도 센서 계약",
  "manufacturer":"Example",
  "model":"temperature-v1",
  "labels":["serial","temperature"],
  "resources":[{
    "name":"temperature",
    "valueType":"Float64",
    "units":"Cel",
    "description":"온도"
  }]
}'

curl --fail --silent --show-error \
  -H 'Content-Type: application/json' \
  -d "${PROFILE_PAYLOAD}" \
  http://127.0.0.1:18000/management/profiles/validate

curl --fail --silent --show-error \
  -H "Idempotency-Key: profile-create-$(openssl rand -hex 12)" \
  -H 'Content-Type: application/json' \
  -d "${PROFILE_PAYLOAD}" \
  http://127.0.0.1:18000/management/profiles

unset PROFILE_PAYLOAD
```

생성 API는 `edge-ai-web-managed` label을 추가하고 Core Metadata readback을 확인한다.
command, parser, image, hostPath, Device와 Catalog binding은 이 API로 만들 수 없다.

External runtime은 기본 호환용 `hardwareBindingId`와 실제 소유 목록
`hardwareBindingIds`를 함께 보고한다. Planner는 요청한 binding이 이 목록에 있으면 같은
protocol runtime을 재사용한다. 현재 두 runtime은 각각 등록 binding 한 개만 소유한다.

다음 조건은 `BLOCKED`다.

- catalog에 없는 adapter/node/hardware binding 조합
- target KubeEdge node가 `Ready`가 아님
- 기존 runtime이 `SERVICE_READY`가 아님
- 이미 점유된 binding에 명시적 `deploy`
- `unverified` protocol template
- image나 hardware binding 검토가 끝나지 않아 `deploymentEnabled=false`

## Connection validation

Connection validation은 Runtime과 EdgeX 변경을 함께 계산하지만 mutation은 수행하지 않는다.

```bash
curl --fail --silent --show-error \
  -H 'Content-Type: application/json' \
  -d '{
    "adapterId":"serial-jetson",
    "runtime":{
      "mode":"auto",
      "targetNode":"etri-dev0001-jetorn",
      "hardwareBindingId":"jetson-arduino-serial-001"
    },
    "device":{
      "name":"onboarding-check-serial-001",
      "description":"validation only",
      "labels":["serial","validation"],
      "tags":{"physicalDeviceId":"arduino-001","nodeName":"etri-dev0001-jetorn"},
      "protocolProperties":{
        "Port":"/dev/arduino-001",
        "BaudRate":115200,
        "DeviceID":"arduino-001",
        "ResourceName":"temperature_raw"
      },
      "adminState":"UNLOCKED"
    },
    "profile":{"mode":"existing","name":"etri-arduino-temperature"}
  }' \
  http://127.0.0.1:18000/management/connections/validate
```

현재 예시는 `runtimePlan.action=REUSE`지만 이미 `virtual-temperature-001`이 같은 route를
소유하므로 전체 `valid=false`, `protocol_binding_exists`가 정상이다. 새 센서를 연결하려면
기존 Device와 충돌하지 않는 물리 endpoint/resource 계약과 등록 hardware binding을 먼저
Git catalog에 추가해야 한다. 검증을 피하려고 임의 경로나 Pod를 입력하지 않는다.

Validation은 선택한 binding의 protocol tuple도 다시 대조한다. Serial은
`Port`/`BaudRate`/`DeviceID`, Sense HAT은 `Bus`/`DeviceID`가 catalog 값과 다르면
`hardware_binding_mismatch`로 차단한다. UI의 read-only 속성만 신뢰하지 않는다.

## 연결 실행

유효한 격리 endpoint가 준비된 경우에만 실행한다. 요청마다 새 idempotency key를 사용한다.

```bash
IDEMPOTENCY_KEY=$(openssl rand -hex 24)

curl --fail --silent --show-error \
  -H "Idempotency-Key: ${IDEMPOTENCY_KEY}" \
  -H 'Content-Type: application/json' \
  --data-binary @approved-connection.json \
  http://127.0.0.1:18000/management/connections

unset IDEMPOTENCY_KEY
```

현재 BFF에는 운영자 인증·인가가 없다. `Idempotency-Key`와 내부 HMAC은 각각 중복 요청
방지와 서비스 간 요청 무결성용이며 사용자 인증이 아니다. 따라서 이 명령은 접근이 제한된
개발 테스트베드에서만 사용한다. 운영 환경에서는 신뢰 가능한 TLS와 별도 사용자
인증·인가를 Ingress 앞에 둔다.

응답의 `requestId`로 다음 endpoint를 polling한다.

```bash
curl --fail --silent --show-error \
  "http://127.0.0.1:18000/management/connections/operations/${REQUEST_ID}"
```

상태 의미:

| 상태 | 의미 |
|---|---|
| `RUNTIME_REQUESTED` | 검증된 runtime 배포와 Device Service 등록 대기 |
| `RUNTIME_READY` | workload와 EdgeX Device Service readback 완료 |
| `DEVICE_APPLIED` | Profile/Device binding readback 완료 |
| `WAITING_EVENT` | Metadata 성공, first Event 대기 |
| `ACTIVE` | Runtime·Metadata·first Event 확인 완료 |
| `COMPENSATED` | 신규 runtime 뒤 Metadata 실패로 안전한 퇴역 완료 |
| `FAILED` | 단계 실패 또는 보상 실패 |

같은 idempotency key와 같은 payload는 같은 operation을 반환한다. 같은 key를 다른 payload에
사용하면 `409`다.

현재 복구 경계:

- EdgeX Device tag를 사용한 Metadata 적용 이후 operation 복구와 동일 payload 재요청의
  중복 방지는 지원한다.
- 신규 Controller runtime이 아직 준비 중인 connection operation은 state-aggregator 메모리에
  있다. 현재 승인 template은 모두 `deploymentEnabled=false`라 live 운영 경로에서는 external
  runtime 재사용만 가능하다.
- managed template을 처음 승격할 때는 CR에 connection payload reference를 남기거나 영속
  operation store를 추가하고, state-aggregator 재시작 뒤 GET-only 복구를 별도 canary로
  통과시켜야 한다.

## 재시작과 퇴역

- 외부/Argo runtime은 대시보드 버튼이 비활성화된다.
- Controller runtime 재시작은 CR의 `restartNonce`만 변경한다.
- 퇴역은 Controller runtime, EdgeX consumer 0, idempotency key와 exact runtime
  이름 확인을 모두 요구한다.
- EdgeX Core Metadata를 조회할 수 없으면 consumer를 0으로 가정하지 않고 퇴역을 차단한다.
- Controller label과 `AdapterRuntime` owner reference가 다른 리소스는 수정·삭제하지 않는다.

## 새 protocol과 장비 승격 순서

1. 물리 endpoint와 protocol security/재연결 요구를 확정한다.
2. EdgeX Device Profile, resource, value type, read/write와 command 계약을 만든다.
3. protocol별 Device Service를 구현하고 실장비 Event/Reading을 검증한다.
4. immutable image digest와 runtime별 Device Service/MessageBus identity를 검증한다.
5. target node와 raw device path를 `hardwareBindingId`로 Git allowlist에 등록한다.
6. template 검토 뒤 `verificationState`와 `deploymentEnabled`를 승격한다.
7. 대시보드 validation과 격리 canary로 첫 Event까지 확인한다.

Modbus, OPC-UA, MQTT와 RTSP는 이 절차를 통과하기 전까지 `unverified`다. MQTT를 공통
중간 protocol로 강제하거나 protocol마다 센서 한 개당 Pod를 만드는 방식은 사용하지 않는다.

## 두 번째 USB Serial 추가

`device-serial-jetson` driver는 `(Port, BaudRate, DeviceID)`별 reader를 만든다. 같은 tuple의
여러 `ResourceName`은 reader 하나를 공유하고, 다른 tuple은 같은 Device Service process에서
별도 reader를 사용한다. 따라서 두 번째 USB 장비를 위해 Device Service Pod를 하나 더 만들
필요는 없다. 다만 Pod가 두 장치를 실제로 볼 수 있도록 다음 절차를 모두 수행한다.

1. Jetson에서 두 번째 장비의 stable `/dev/serial/by-id/...`를 확인한다.
2. 충돌하지 않는 container path와 binding ID를 정한다. 예시는 설명용이며 실기기 확인 전
   `/dev/arduino-002`를 운영 manifest에 넣지 않는다.
3. `edgex/k8s/base/device-serial-jetson/workload.yaml`에 그 exact CharDevice만 추가
   마운트한다. broad `/dev`, privileged host access나 wildcard path로 우회하지 않는다.
4. `edgex/adapter-controller/config/runtime_templates.json`의 Serial
   `hardwareBindings`에 host/container path를 추가하고 기존 external runtime의
   `hardwareBindingIds`에 같은 ID를 추가한다.
5. `edge-orch/state-aggregator/app/config/adapter_catalog.json`에 같은 `bindingId`,
   `devicePath`와 `protocolProperties`(`Port`, `BaudRate`, `DeviceID`)를 추가한다.
   `BaudRate`는 Serial Device Service와 catalog가 함께 허용한 표준 allowlist 중에서 고른다.
6. 새 EdgeX Device/Profile을 등록한다. 같은 resource 이름을 써도 physical connection tuple이
   다르면 별도 reader route가 된다.
7. manifest·catalog·planner·dashboard 테스트와 실기기 first Event를 확인한 뒤 배포한다.

현재 승인 Serial binding은 `jetson-arduino-serial-001`뿐이다. 실제 두 번째 장비 identity가
확정되기 전에는 dashboard에서 새 포트를 등록할 수 없는 상태가 정상이다.
기존 Device의 `Port`/`BaudRate`/`DeviceID`를 PATCH해 새 binding으로 옮기는 작업도 차단한다.
새 물리 연결은 connection validation과 신규 Device 등록 흐름을 사용한다.
두 번째 장비가 현재 Arduino JSON frame과 지원 resource 계약을 따르지 않으면 이 절차만으로
연결하지 않는다. 새 parser/Adapter와 Device Profile을 실장비로 검증한 뒤 별도
`adapterId`로 catalog에 승격한다.

## 검증과 장애 점검

```bash
kubectl logs -n edgex-edge deployment/edgex-adapter-controller
kubectl logs -n edgex-edge daemonset/edge-device-discovery --tail=100
kubectl get events -n edgex-edge --sort-by=.lastTimestamp
kubectl auth can-i --as=system:serviceaccount:default:state-aggregator \
  create deployments -n edgex-edge
kubectl auth can-i --as=system:serviceaccount:edgex-edge:edgex-adapter-controller \
  create deployments -n edgex-edge
```

첫 `auth can-i` 명령의 기대값은 `no`, 두 번째 기대값은 `yes`다. Controller API는
`state-aggregator` Pod와 같은 namespace의 Discovery Agent report만 NetworkPolicy ingress로
허용한다. 현재 CNI가 정책을 집행하는지는 별도 확인하며 내부 HMAC을 네트워크 정책의
대체물로 생략하지 않는다.

문제가 생겨도 EdgeMesh, 고정 Service IP 또는 KubeEdge Device CRD로 우회하지 않는다.
