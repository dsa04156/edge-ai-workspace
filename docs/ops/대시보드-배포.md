# 대시보드 배포

## 목적과 배포 소유권

이 문서는 `state-aggregator` API와 Edge AI 운영 대시보드를 Git push로 배포하고,
Traefik 주소와 Argo CD 상태를 같은 revision에서 검증하는 운영 절차다.

배포 소유권은 다음처럼 고정한다.

| 대상 | Git 기준 | 운영 소유자 |
|---|---|---|
| Deployment·Service·RBAC·ServiceMonitor | `edge-orch/state-aggregator/k8s/` | Argo CD `edge-orch-state-aggregator` |
| 대시보드 외부 주소 | `edge-orch/state-aggregator/k8s/ingressroute.yaml` | 같은 Argo CD Application과 Traefik |
| 컨테이너 이미지 | `edge-orch/state-aggregator/k8s/deployment.yaml`의 immutable digest | Git 또는 `main` 이미지 배포 CI |
| 서비스 목록·DAG 정의 | `edge-orch/state-aggregator/app/config/service_catalog.json` | state-aggregator image |

공식 외부 주소는 다음 Traefik host route다.

```text
http://aggregator.192.168.0.56.sslip.io
http://aggregator.10.254.192.217.sslip.io
```

ClusterIP, Pod IP, `port-forward`와 `http://<LoadBalancer IP>/aggregator`는 운영 acceptance
주소로 사용하지 않는다. IngressRoute를 `kubectl apply`로 따로 관리하거나 Deployment에
`kubectl set image`를 실행하지 않는다. Argo CD self-heal과 충돌하기 때문이다.

## 배포 전 검증

저장소 루트에서 사용자 작업이 섞이지 않았는지 먼저 확인한 뒤, 변경한 파일만 커밋한다.

```bash
git status --short

cd edge-orch/state-aggregator
.venv/bin/python -m pytest -q
node --test tests/*.js
kubectl kustomize k8s >/dev/null
cd ../..

git diff --check
```

현재 Application이 추적하는 ref와 image override도 확인한다.

```bash
kubectl -n argocd get applications.argoproj.io edge-orch-state-aggregator \
  -o jsonpath='{.spec.source.targetRevision}{"\n"}{.spec.source.kustomize.images}{"\n"}'
```

2026-08-13 현재 즉시 반영 ref는 `agent/edgex-central-docs` 브랜치이며 image override는
없다. 이 상태에서는 해당 브랜치의 Kustomize manifest push를 Argo CD automated sync가
반영한다. 조회 결과가 다른 브랜치나 exact Git SHA라면 그 ref의 배포 정책을 먼저 확인하고
임의로 다른 브랜치를 push하지 않는다.

## Manifest와 문서만 변경한 경우

변경한 파일만 stage하고 Application이 추적하는 브랜치로 push한다.

```bash
git add <변경한-파일>
git commit -m "docs: document dashboard deployment"
git push origin agent/edgex-central-docs

kubectl -n argocd annotate applications.argoproj.io edge-orch-state-aggregator \
  argocd.argoproj.io/refresh=hard --overwrite
```

`refresh=hard`는 새 Git revision 확인을 앞당길 뿐 리소스를 직접 변경하지 않는다. automated
sync와 self-heal이 Deployment와 IngressRoute를 Git 상태로 맞춘다.

## 애플리케이션 코드를 변경한 경우

브랜치 push만으로는 새 Python·HTML·CSS·JavaScript가 실행 중인 컨테이너에 들어가지 않는다.
새 이미지를 build/push하고 immutable digest를 배포해야 한다.

### 정식 `main` 배포

`.github/workflows/docker-build-push.yml`은 `main`의
`edge-orch/state-aggregator/**` 변경을 감지하면 다음을 수행한다.

1. linux/amd64·linux/arm64 이미지를 빌드한다.
2. `192.168.0.56:5000/state-aggregator:latest`로 push하고 registry digest를 읽는다.
3. Argo CD Application을 해당 Git SHA와 immutable image digest로 고정한다.
4. 실제 Deployment image가 목표 digest가 될 때까지 기다린 뒤 rollout을 확인한다.

따라서 `main` CI가 실행된 뒤에는 Application의 `targetRevision`이 브랜치가 아니라 exact
SHA로 보이는 것이 정상이다. CI 성공 여부와 배포 digest를 확인하지 않고 코드 배포 완료로
판정하지 않는다.

### 현재 작업 브랜치에서 긴급 검증하는 경우

`main` 병합 전 검증이 승인된 경우에만 저장소의 비권한 amd64 OCI 빌드 스크립트를 사용한다.
state-aggregator가 배치된 서버가 amd64인지 먼저 확인한다.

```bash
kubectl -n default get deployment state-aggregator \
  -o jsonpath='{.spec.template.spec.nodeSelector.kubernetes\.io/hostname}{"\n"}'

TAG="git-$(git rev-parse --short=12 HEAD)"
IMAGE="192.168.0.56:5000/state-aggregator:${TAG}"
edge-orch/state-aggregator/scripts/build-amd64-oci.sh "${IMAGE}"
```

스크립트가 반환한 digest를
`edge-orch/state-aggregator/k8s/deployment.yaml`의 `image`에
`192.168.0.56:5000/state-aggregator@sha256:...` 형식으로 기록한다. 테스트 후 manifest와
코드 변경을 같은 커밋으로 push한다. tag나 `latest`만 manifest에 기록하지 않는다.

## 배포 완료 확인

Argo CD, Pod, IngressRoute, HTTP와 브라우저를 순서대로 확인한다.

```bash
kubectl -n argocd get applications.argoproj.io edge-orch-state-aggregator \
  -o jsonpath='target={.spec.source.targetRevision}{" sync="}{.status.sync.status}{" health="}{.status.health.status}{" revision="}{.status.sync.revision}{"\n"}'

kubectl -n default rollout status deployment/state-aggregator --timeout=180s
kubectl -n default get deployment state-aggregator \
  -o jsonpath='{.status.readyReplicas}/{.status.replicas}{" ready, image="}{.spec.template.spec.containers[0].image}{"\n"}'

kubectl -n default get ingressroute state-aggregator \
  -o jsonpath='{.metadata.annotations.argocd\.argoproj\.io/tracking-id}{"\n"}{.spec.routes[0].match}{"\n"}'

curl -fsS -o /dev/null -w 'dashboard_http=%{http_code}\n' \
  http://aggregator.192.168.0.56.sslip.io/
curl -fsS http://aggregator.192.168.0.56.sslip.io/state/services
```

완료 기준은 다음과 같다.

- Argo CD revision이 push한 commit과 같고 `Synced`, `Healthy`다.
- Deployment가 `1/1 Ready`이고 의도한 immutable image digest를 실행한다.
- IngressRoute tracking ID가 `edge-orch-state-aggregator` 소유권을 표시한다.
- 공식 Traefik 주소와 `/state/services`가 HTTP 200을 반환한다.
- `/#services` 브라우저 화면에서 서비스 목록과 DAG가 보이고 console 오류가 없다.

세부 화면·API acceptance는 [대시보드 검증](대시보드-검증.md)을 따른다.

## 롤백

Git에 반영된 잘못된 변경은 이력을 지우지 않고 revert한다.

```bash
git revert <문제가-발생한-커밋>
git push origin <Application이-추적하는-브랜치>
```

Argo CD revision, image digest, rollout과 Traefik HTTP를 다시 확인한다. 장애 중에도
Deployment image나 IngressRoute를 수동 patch해 Git과 다른 정상 상태를 만들지 않는다.

## 자주 발생하는 문제

| 증상 | 우선 확인 |
|---|---|
| push했지만 revision이 바뀌지 않음 | Application이 다른 브랜치 또는 exact SHA를 추적하는지 확인 |
| revision은 바뀌었지만 화면 코드가 그대로임 | 새 image가 빌드됐는지, Deployment digest가 바뀌었는지 확인 |
| host 주소가 404 또는 연결 실패 | Traefik Service 외부 IP, IngressRoute host rule과 backend `state-aggregator:8000` 확인 |
| Argo CD `OutOfSync` | 수동 변경 여부와 Kustomize render 오류 확인 |
| API는 200인데 화면이 비어 있음 | `/state/services`, 서비스 관측 API와 브라우저 console을 순서대로 확인 |
