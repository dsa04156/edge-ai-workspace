# 대시보드 검증 점검표

## 목적과 범위

이 문서는 `state-aggregator`가 EdgeX Core Metadata와 Core Data를 읽어 만든 dashboard API/UI를 **read-only**로 확인하는 절차다. 물리 디바이스 inventory, 관리 상태, telemetry의 authority는 EdgeX이며 KubeEdge는 Kubernetes node와 workload 관찰에만 사용한다.

현재 검증 대상은 MQTT canary 하나다.

```text
arduino-001
```

2026-07-14 Jetson MQTT에서 EdgeX Core Data까지의 ingestion과 dashboard live cutover를 모두 PASS했다. 배포 image의 runtime `imageID`는 `sha256:e13c8de7e8571ddd52821dc585fc7497eef3cfc880f9dc0654863dd26280d43a`이며, 이 image의 `/state/devices`가 `source=edgex`, `overall_status=available`, `telemetry_freshness=fresh`와 `acceleration`, `magnetic`, `temperature`, `light` typed readings를 반환했다. `http://192.168.0.56/aggregator#inventory`의 Assets/Explain Panel에서도 같은 네 source를 확인했으며 화면 증거는 `output/edgex-dashboard-live-20260714.png`다.

Serial, Modbus, OPC-UA, RTSP는 이 문서의 PASS 범위가 아니다. workflow builder와 자원증강 화면도 read-only/dry-run 경계를 넘지 않는다.

## 1. Authority와 관찰 경계

| 관찰 대상 | authority / API 근거 | dashboard 해석 |
|---|---|---|
| 물리 inventory와 관리 상태 | EdgeX Core Metadata -> `/state/devices` | `source=edgex`, profile, Device Service, admin/operating state |
| 물리 telemetry와 freshness | EdgeX Core Data Event/Reading -> `/state/devices`, device telemetry API | 최신 Event timestamp/origin과 typed Reading |
| 물리 availability | state-aggregator의 `overall_status`, `reason` | EdgeX 관리 상태와 Core Data freshness 결과 |
| node/workload | Kubernetes/KubeEdge와 Prometheus -> `/state/nodes` | 별도 진단 정보; physical availability gate가 아님 |

`node_name`은 Device metadata의 선택적 placement 진단값이다. node가 없거나 NotReady여도 물리 디바이스의 inventory, `overall_status`, telemetry freshness를 바꾸지 않는다. 반대로 EdgeX device가 unavailable/degraded여도 node/workload card와 같은 원인으로 합치지 않는다.

현재 MQTT canary의 physical data path는 다음과 같다.

```text
Jetson southbound MQTT (127.0.0.1:1883)
  -> mqtt-edge-bridge
  -> edgex-device-mqtt
  -> edgex-messagebus
  -> edgex-core-data
  -> state-aggregator
  -> dashboard
```

`edgex-messagebus`는 EdgeX 내부 ClusterIP message bus다. southbound MQTT endpoint가 아니다.

## 2. Kubernetes Service proxy로 API 확인

state-aggregator는 namespace `default`, EdgeX runtime은 namespace `telemetry`에 있다. API 확인은 Kubernetes API Service proxy를 사용한다.

```bash
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/devices'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/devices/vib-arduino-acceleration-01/telemetry'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/dashboard'
kubectl get --raw \
  '/api/v1/namespaces/default/services/http:state-aggregator:8000/proxy/state/nodes'
```

`/state/devices`가 EdgeX backend 오류를 빈 inventory로 바꾸어 반환해서는 안 된다. Core Metadata/Core Data를 읽을 수 없으면 API/UI cutover 증거가 아니다.

`/state/devices/{device_id}/telemetry`는 최근 Core Data Event를 Reading 단위로 반환한다. window/limit을 지정할 때도 Event `origin`과 typed value를 보존하는지 확인한다.

## 3. Device API / table / Explain Panel contract

Device row와 Explain Panel은 다음 `DeviceState` contract를 표시하거나 바로 확인할 수 있어야 한다.

| 필드 | 확인 의미 |
|---|---|
| `source` | 항상 `edgex`; physical source authority 식별값 |
| `name` | EdgeX Core Metadata Device 이름 |
| `profile_name` | EdgeX Device Profile |
| `device_service_name` | protocol endpoint를 소유한 EdgeX Device Service |
| `protocol_names` | 등록된 protocol 이름 목록 |
| `admin_state` | Core Metadata admin state |
| `operating_state` | Core Metadata operating state |
| `connection_state` | aggregator가 EdgeX 관리 상태에서 계산한 `connected` / `disconnected` / `unknown` 진단 |
| `device_service_available` | `operating_state=UP`에 따른 Device Service availability 표시 |
| `latest_event_timestamp` | 최신 Core Data Reading/Event 시각 |
| `latest_readings` | 최신 Event의 typed readings; `device_name`, `source_name`, `resource_name`, `value_type`, `value`, `timestamp`, `origin`, `event_id`, `units`를 보존 |
| `latest_readings[].origin` | nanoseconds Event/Reading origin. 별도 가공 timestamp로 freshness를 대체하지 않음 |
| `telemetry_freshness` | `fresh`, `stale`, `no_events` |
| `overall_status` / `reason` | aggregator가 계산한 물리 availability와 구체적인 EdgeX/Core Data 근거 |
| `node_name` | 선택적 Kubernetes placement 진단. physical availability 판정에는 사용하지 않음 |

`latest_event_timestamp`는 `/state/devices`의 최신 Event 표시값이며 Event의 원본 시각은 `latest_readings[].origin`과 telemetry API의 각 Reading `origin`으로 확인한다. 직접 읽은 data-store timestamp, API 조회 시각, node heartbeat는 freshness 근거가 아니다.

Explain Panel은 선택 device의 `overall_status`, `reason`, Device Service/profile/protocol ownership, admin/operating/connection state, 최신 Core Data Event timestamp/origin, typed readings, `telemetry_freshness`, 그리고 선택적 `node_name`을 구분해 보여야 한다.

## 4. Physical availability 판정

state-aggregator의 `overall_status`와 `reason`은 다음 순서를 따른다.

| 조건 | `overall_status` | `reason` 근거 |
|---|---|---|
| `admin_state=LOCKED` | `unavailable` | `EdgeX adminState is LOCKED` |
| `operating_state=DOWN` | `unavailable` | `EdgeX operatingState is DOWN` |
| `operating_state`가 `UP`이 아님 | `degraded` | EdgeX operating state가 unknown 또는 기타 값 |
| `operating_state=UP` + `telemetry_freshness=fresh` | `available` | 최신 Core Data Event가 fresh |
| `operating_state=UP` + `telemetry_freshness=stale` | `degraded` | 최신 Core Data Event가 stale |
| `operating_state=UP` + `telemetry_freshness=no_events` | `degraded` | Core Data Event가 없음 |

`connection_state`와 `device_service_available`은 이 EdgeX 관리 상태를 설명하는 API 출력이다. UI는 `overall_status`/`reason`을 우선 표시하고, node/workload signal을 physical reason에 추가하거나 그 결과를 승격·강등하지 않는다.

## 5. Overview KPI

physical-device KPI의 분모는 EdgeX Core Metadata inventory다. 다음은 현재 API가 제공하는 EdgeX physical KPI 이름이다.

| KPI 필드 | 의미 |
|---|---|
| `registered_device_count` | Core Metadata Device 수 |
| `available_device_count` | EdgeX state와 fresh Core Data Event 기준 `available` 수 |
| `degraded_device_count` | EdgeX state unknown, stale Event, 또는 Event 없음으로 `degraded`인 수 |
| `unavailable_device_count` | `LOCKED` 또는 `DOWN`으로 `unavailable`인 수 |
| `edgex_connected_device_count` | `connection_state=connected` 수 |
| `edgex_connection_ratio` | connected device / registered device |
| `edgex_operating_up_count` | `operating_state=UP` 수 |
| `edgex_operating_down_count` | `operating_state=DOWN` 수 |
| `edgex_operating_unknown_count` | `UP`/`DOWN` 이외 operating state 수 |
| `edgex_admin_unlocked_count` | `admin_state=UNLOCKED` 수 |
| `edgex_admin_locked_count` | `admin_state=LOCKED` 수 |
| `device_service_available_count` | `device_service_available=true` 수 |
| `device_service_availability_ratio` | Device Service available / registered device |
| `core_data_event_device_count` | Core Data Event가 하나 이상 있는 device 수 |
| `fresh_core_data_event_device_count` | 최신 Core Data Event가 fresh인 device 수 |
| `stale_core_data_event_device_count` | 최신 Core Data Event가 stale인 device 수 |
| `core_data_freshness_ratio` | fresh latest Core Data Event / registered device |
| `operator_focus_count` | `degraded` + `unavailable` physical device 수 |

`operator_focus_count`에는 node/workload health, workflow risk, placement risk를 더하지 않는다. `active_node_count`와 `node_online_ratio`는 node/workload 관찰 KPI로 별도 표시한다. ratio의 inventory 분모가 0이면 API 값은 `0.0`이다.

Service resource profile KPI는 Running Pod의 declared/observed resource 관찰용이다. `service_resource_profile_count`, `service_resource_profile_pod_count`, `service_resource_profile_container_count`, request/current CPU·memory, usage coverage, GPU limit 관련 값은 physical-device KPI나 device availability 근거가 아니다.

## 6. Issue / Focus List

Issue/focus list는 다음 physical condition을 우선 표시한다.

- `overall_status=degraded` 또는 `unavailable`
- `admin_state=LOCKED`
- `operating_state=DOWN` 또는 unknown
- `connection_state=disconnected` 또는 `unknown`
- `device_service_available=false`
- `telemetry_freshness=stale` 또는 `no_events`
- 최신 Event timestamp/origin 또는 typed Reading이 없는 경우

각 항목은 `reason`과 함께 해당 점검 위치를 가리켜야 한다.

| 관찰 결과 | 다음 확인 위치 |
|---|---|
| `LOCKED` | Core Metadata adminState 정책 |
| `DOWN`, disconnected, Device Service unavailable | Core Metadata operatingState와 `edgex-device-mqtt` |
| Event stale/no events | Core Data latest Event와 southbound-to-Core-Data path |
| `node_name` 누락 또는 node/workload 문제 | Kubernetes node/workload 진단 card; physical availability와 별개 |

## 7. Failure isolation

MQTT canary는 다음 순서로만 격리한다. 각 단계는 앞 단계의 physical authority를 대체하지 않는다.

1. **Jetson southbound MQTT**: `factory/devices/vib-arduino-acceleration-01/telemetry`가 Jetson local Mosquitto `127.0.0.1:1883`에 도달하는지 확인한다.
2. **bridge**: `mqtt-edge-bridge`가 canary 입력을 EdgeX input으로 정규화하는지 확인한다.
3. **device-mqtt**: `edgex-device-mqtt`가 Device Profile/Device Service ownership으로 payload를 typed Event/Readings로 처리하는지 확인한다.
4. **messagebus**: `edgex-messagebus` 내부 전달과 `edgex-core-data` consumer 연결을 확인한다.
5. **Core Data**: 최신 Event의 `deviceName`, `sourceName=telemetry`, nanosecond `origin`, typed readings를 확인한다.
6. **aggregator**: namespace `default`의 `/state/devices`와 device telemetry endpoint가 같은 EdgeX state/Event를 `source=edgex`, `latest_event_timestamp`, `latest_readings`, `telemetry_freshness`, `overall_status`, `reason`으로 반환하는지 확인한다.
7. **dashboard**: API payload와 UI card/table/Explain Panel의 값이 일치하는지 확인한다.

KubeEdge node readiness와 `telemetry` namespace workload placement/Pod readiness는 병렬 진단이다. 이를 1--7의 physical availability 판정에 넣지 않는다.

### Post-cutover absence check

dashboard/API의 current physical inventory, state, telemetry, KPI, Explain Panel에 KubeEdge `DeviceStatus`, legacy mapper, 또는 direct Influx 값이 나타나거나 physical authority로 사용되어서는 안 된다. 이 항목은 legacy path를 운영 절차로 되살리기 위한 것이 아니라 EdgeX cutover 후 부재를 확인하는 check다.

## 8. Workflow builder와 자원증강 경계

Workflow builder는 EdgeX Device/Service와 Core Data 최신 Event를 read-only로 표시하고 browser state에서 stage 구성, binding/release dry-run, validation, execution-plan preview만 제공한다. Kubernetes apply/delete/restart, EdgeX metadata/state mutation, command publish, actuator command, runtime migration/offloading을 실행해서는 안 된다.

자원증강 탭은 AI HAT/GPU/cache 같은 실행 자원과 Running Pod resource observation을 표시한다. Resource Profile 또는 augmentation candidate/decision이 보여도 physical sensor inventory, EdgeX availability, telemetry authority와 섞지 않는다. `observation_error`가 있어도 dashboard physical device 결과를 500으로 만들거나 변경하지 않는다.

## 9. 화면 정상 판정과 live cutover gate

다음은 API/UI contract가 배포된 경우의 정상 판정 기준이다.

1. Device table과 Explain Panel이 EdgeX `DeviceState` 필드를 표시하고 `source=edgex`를 유지한다.
2. physical availability는 `admin_state`, `operating_state`, 최신 Core Data Event freshness만으로 `overall_status`/`reason`을 설명한다.
3. latest Event의 timestamp와 Reading `origin`, `source_name`, typed values를 확인할 수 있다.
4. Overview가 이 문서의 current EdgeX KPI 이름과 의미를 사용한다.
5. node/workload 관찰과 physical availability reason이 별도로 표시된다.
6. workflow builder와 자원증강은 read-only/dry-run이며 control path를 제공하지 않는다.

2026-07-14에는 기존 Jetson-local MQTT canary와 당시 state-aggregator image의 API/UI를 확인했다. 이 결과는 장비·profile·dashboard contract의 과거 증거이며 중앙 server2 MessageBus/Core/PostgreSQL topology의 live cutover 완료를 의미하지 않는다.

현재 중앙 EdgeX runtime 점검은 [현재 서비스 데모 운영 절차](현재-데모-운영-절차.md)를 사용한다. 이전 Jetson-local canary의 상세 기록은 [2026-07-14 젯슨 MQTT 종단간 검증 기록](../archive/integration/2026-07-14-젯슨-mqtt-종단간-검증-기록.md)에 보관한다.
