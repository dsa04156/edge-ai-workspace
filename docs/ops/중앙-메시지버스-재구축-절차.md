# 중앙 메시지버스 배치 재구축 절차

## 목적

이 문서는 `telemetry` namespace의 EdgeX 라벨 자원을 엣지 Device Service → 중앙 EdgeX MessageBus → Core Data·PostgreSQL topology로 재구축할 때 사용하는 파괴적 운영 절차다.
일상 점검은 `현재-데모-운영-절차.md`를 사용하고, 이 문서는 승인된 전체 재구축에서만 사용한다.

## 파괴적 작업 경고

아래 절차는 `app.kubernetes.io/part-of=edgex-telemetry` 라벨이 붙은 Deployment, StatefulSet, Job, Service, ConfigMap, Secret, PVC만 삭제한다.
`telemetry` namespace 자체와 InfluxDB, Redis 등 다른 서비스는 삭제하지 않는다.
기존 telemetry 데이터의 backup·migration·무중단 전환은 현재 범위에 없다.
명시적인 재구축 승인 없이 삭제 명령을 실행하지 않는다.

## 사전 조건

- 대상 cluster와 kube context를 운영자가 확인했다.
- `edgex/k8s/kustomization.yaml`이 현재 승인된 root 진입점이다.
- render와 server-side dry-run이 성공했다.
- 삭제 대상이 `telemetry` 안의 EdgeX 라벨 자원인지 확인했다.
- 중앙 노드 `etri-ser0002-cgnmsb`, Jetson `etri-dev0001-jetorn`, Raspberry Pi `etri-dev0003-raspi5`가 존재한다.
- 세 노드의 EdgeMesh agent에서 Kubernetes DNS 질의가 성공한다.

## 읽기 전용 확인

```bash
edgex/k8s/scripts/rebuild-central-messagebus.sh
```

render 결과에서 다음 배치를 확인한다.

- Core Keeper, Core Metadata, Core Data, Core Command, MessageBus, PostgreSQL: `etri-ser0002-cgnmsb`
- `edgex-device-mqtt`: `etri-dev0001-jetorn`
- `edgex-device-mqtt-sensehat`: `etri-dev0003-raspi5`
- Edge node에는 Core, MessageBus, PostgreSQL workload가 없음

## 승인 후 재구축

```bash
edgex/k8s/scripts/rebuild-central-messagebus.sh --execute
```

스크립트는 render, server-side dry-run, node 존재 여부, EdgeMesh DNS를 먼저 검사한다. 그 뒤 EdgeX 라벨 자원만 교체하고 PostgreSQL, MessageBus, Keeper, 공통설정 bootstrap Job, Core 서비스, Device Service 순서로 Ready를 확인한다.

## 재구축 후 검증

1. 중앙 workload가 모두 server2에서 Ready인지 확인한다.
2. 두 Device MQTT workload가 지정된 엣지 노드에서 Ready인지 확인한다.
3. Core Metadata에서 Device, Profile, Device Service 등록을 확인한다.
4. UNO와 Sense HAT MQTT payload를 발행한다.
5. Core Data에서 typed Event/Reading과 `origin`을 확인한다.
6. PostgreSQL 저장을 확인한다.
7. `/state/devices`에서 중앙 inventory와 fresh Event가 표시되는지 확인한다.
8. 중앙 MessageBus 중단 시 데이터 유실 가능성을 확인하고, 복구 뒤 새 Event 수집이 재개되는지 확인한다.

## 현재 장애 계약

- SQLite offline replay가 없다.
- 중앙 MessageBus 또는 네트워크 장애 시 telemetry가 유실될 수 있다.
- 복구 성공 기준은 연결 회복 뒤 새 Event 수집 재개다.
- 과거 누락분 자동 재전송을 기대하지 않는다.
- SQLite replay와 PostgreSQL persisted acknowledgement는 별도 승인된 설계가 필요하다.
