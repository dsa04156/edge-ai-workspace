# Llama 3.2 1B 요청 단위 오프로딩 검증 보고서

## 결론

대체 노드와 CPU 추론이라는 제한 안에서 요청 단위 동적 라우팅을 구현하고 실제 KubeEdge 클러스터에서 검증했다. Nano 역할 부하가 지속될 때 AGX 역할로, AGX 역할 부하가 지속될 때 Spark 역할로 새 요청만 승격되었다. 부하 제거 뒤에는 cooldown과 recovery dwell을 거쳐 Spark→AGX→Nano 순서로 복귀했다.

이 결론은 제어 경로 자격시험에 한정한다. 요청된 Jetson Nano/AGX/DGX Spark 실장비의 GPU 성능이나 운영용 동적 오프로딩 완료를 뜻하지 않는다.

## 정책 전환 증거

본 dynamic 시험에는 두 번의 상향 전환이 기록되었다.

1. `offload:nano->agx:predicted_improvement=0.609`
2. `offload:agx->spark:predicted_improvement=0.935`

각 전환은 queue/TTFT 기반 부하가 2초 이상 지속되고 다음 역할의 예측 E2E가 최소 15% 개선된 뒤 발생했다. 총 62건 중 Nano 2건, AGX 53건, Spark 7건이었다. 프록시는 요청마다 선택 결과를 고정한 뒤 선택된 `/generate` endpoint를 한 번 호출하므로 실행 중 요청 이동은 없다.

최종 배포에서 동시성 8·16, 총 48건으로 Spark 역할까지 다시 승격한 뒤 다음 probe로 하향 복귀를 확인했다.

| probe | 선택 | 사유 |
|---|---|---|
| `final-recovery-probe-1` | Spark | `hold:spark:hysteresis_or_improvement_gate` |
| `final-recovery-probe-2` | AGX | `recovery:spark->agx:sustained` |
| `final-recovery-probe-3` | Nano | `recovery:agx->nano:sustained` |

마지막 프록시 route는 `nano`였다. 하위 역할이 비활성일 때 오래된 TTFT/TPS EWMA 때문에 복귀가 영구 차단되지 않도록, 건강 상태와 연속 유휴를 recovery latch로 사용하고 단계별 cooldown을 유지했다.

## 남은 제한과 다음 단계

- Jetson Nano/AGX/DGX Spark 실장비에서 CUDA/JetPack과 GPU inference를 다시 측정한다.
- 실제 GPU 실행에서는 per-request 전력, thermal throttling, GPU memory pressure와 모델 cold-start를 포함한다.
- 네트워크 지연·패킷 손실, 워커 장애, timeout을 주입해 fail-closed 동작을 검증한다. 현재 구현은 실행 중 요청을 다른 노드로 재시도하지 않는다.
- 장시간 ramp/soak로 hysteresis와 cooldown 값을 조정하고 oscillation 횟수를 관찰한다.
- 운영 기능 승격 전 `docs/프로젝트-범위.md`, `docs/저장소-구조.md`, `docs/단계별-추진계획.md`에 검증 기준, 배포 소유권과 운영 책임을 먼저 반영한다.
