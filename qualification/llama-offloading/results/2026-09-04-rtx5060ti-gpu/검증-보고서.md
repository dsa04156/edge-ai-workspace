# Llama 3.2 1B RTX 5060 Ti GPU 대체 서버 검증 보고서

> 측정일: 2026-09-04  
> 실제 장비: `etri-ser0001-cg0msb`, x86, NVIDIA GeForce RTX 5060 Ti 8GiB  
> 논리 역할: AGX 대체  
> 주의: 이 서버는 실제 Jetson AGX Orin이 아니므로 아래 값은 AGX 성능값이 아니다.

## ELI5 요약

작은 계산대인 Orin Nano 옆에 더 빠른 계산기를 하나 준비했다. 이 계산기는 글자를 만드는
순간 속도는 빠르지만, 이번처럼 답을 8토큰만 만드는 짧은 일에서는 손님 한 명을 끝내는
전체 시간은 Nano와 거의 같았다. 대신 두 계산대를 동시에 켜면 전체 처리량은 약 2배가 된다.

다만 큰 계산대를 켜는 데 시간이 든다. 모델 파일을 매번 다시 받으면 평균 19.07초,
파일을 SSD에 남겨두면 평균 2.33초였다. 따라서 짧은 줄에는 원격 계산대를 켜지 않고,
Cached 상태에서 Nano 앞에 약 12건 이상 대기할 때부터 새 요청을 보내는 편이 이득이다.

## 시험 조건과 경계

- 모델: `llama3.2:1b`
- digest: `baf6a787fdffd633537aa2eb51cfd54cb93ff08e28040095462bb63daf552878`
- backend: Ollama CUDA, `ollama ps`의 `100% GPU` 확인
- prompt와 최대 출력: Nano 포화시험과 동일, 최대 8토큰
- worker concurrency: 1
- client concurrency: 1, 2, 4, 8, 16, 32
- 반복: 조건별 12초, 무작위 순서 3블록
- 측정 요청: warm-up 제외 1,314건, 오류 0건
- RTT: 30회 median 1.549ms, p95 2.257ms

Kubernetes Pod 경로는 Ollama image pull 뒤 노드의 `DiskPressure`로 축출됐다. 운영 파일을
임의 삭제하지 않고 같은 호스트의 기존 Ollama 0.32.5 CUDA runtime과 격리 worker API를
사용했다. 따라서 GPU·모델 성능은 유효한 호스트 실측이지만 Kubernetes Pod 시작시간으로
해석하지 않는다.

## Activation 비교

첫 CUDA 사용 직후의 최초 CACHED→ACTIVE는 71.835초였다. 그 뒤 동일 runtime에서 아래
반복시험을 수행했다. 최초값은 driver/runtime first-touch 비용이 섞인 별도 worst case이며
반복 평균에서 숨기거나 합치지 않는다.

| 방식 | 반복 | activation 평균 | 개별값 | download 평균 | GPU load 평균 |
|---|---:|---:|---|---:|---:|
| Cold On-Demand | 3 | 19.074초 | 18.835 / 19.115 / 19.273초 | 17.147초 | 1.925초 |
| Cached On-Demand | 3 | 2.329초 | 2.306 / 2.313 / 2.369초 | 0초 | 2.327초 |

Cached 방식은 Cold보다 평균 16.745초, 87.8% 빠르다. CACHED 전환 시 모델 파일 1.3GB는
로컬에 남고 GPU runner만 내려가며, 최종 상태에서 `ollama ps`는 비어 있고 GPU memory는
228MiB로 복귀했다.

## Nano와 비교 및 break-even

| 항목 | Orin Nano GPU | RTX 5060 Ti x86 대체 | 차이 |
|---|---:|---:|---:|
| 단독 p95 전체 지연 | 208.0ms | 220.5ms | 대체 서버가 6.0% 느림 |
| 단독 중앙 전체 지연 | 198.4ms | 190.4ms | 대체 서버가 4.0% 빠름 |
| 최대 처리량 | 5.070 req/s | 5.306 req/s | 대체 서버가 4.7% 높음 |
| 단독 중앙 tokens/s | 49.352 | 281.452 | 대체 서버가 5.70배 |
| TTFT SLO capacity | 동시 요청 8 | 동시 요청 4 | Nano가 더 큼 |

짧은 8-token workload에서는 높은 token 생성속도가 요청 전체 처리량 증가로 이어지지
않았다. 고정 비용과 worker concurrency 1의 직렬 대기가 지배적이기 때문이다. 따라서 이
대체 서버로 바꿔 타는 것만으로 p95 latency가 의미 있게 줄었다고 결론 내릴 수 없다.

Nano 중앙 서비스시간 198.4045ms, 대체 서버 190.374ms, RTT 1.549ms와 반복 activation
평균을 사용한 첫 offload 요청의 근사 break-even은 다음과 같다.

| 방식 | 원격 첫 완료 예상 | Gain > 0인 Nano 선행 대기 | 15% 이득에 필요한 선행 대기 |
|---|---:|---:|---:|
| Always-On | 191.9ms | 0건 | 1건 |
| Cached On-Demand | 2,521.4ms | 12건 | 14건 |
| Cold On-Demand | 19,266.2ms | 97건 | 114건 |

두 worker가 이미 ACTIVE이고 backlog가 충분하면 합산 관측 상한은 약 10.376 req/s로,
Nano-only 5.070 req/s보다 약 104.7% 높다. 이는 두 독립 worker의 단순 합산 근사이며 실제
동적 라우팅 burst 시험 결과가 아니다.

## 결론

1. RTX 5060 Ti 대체 서버는 실제 GPU로 실행됐지만, 이번 짧은 요청의 단일 처리 지연은
   Nano와 거의 같고 p95는 오히려 6.0% 느렸다.
2. 원격 worker를 함께 ACTIVE로 쓰면 처리량을 약 2배로 늘릴 잠재력은 있다.
3. Cached activation은 반복 기준 2.33초로 Cold 19.07초보다 87.8% 빠르다.
4. Cached 방식도 Nano 앞에 약 12건 이상 대기하지 않으면 첫 요청 기준 이득이 없다.
5. 71.8초 first-touch가 재부팅·새 runtime에서 재현될 수 있으므로 첫 실행 warm-up을 별도
   운영 조건으로 두어야 한다.
6. 실제 AGX Orin과 DGX Spark 결론은 아직 없고, RTX 5080 대체 서버도 기존 센서 서비스가
   GPU를 사용 중이라 이번 시험에서는 중단하지 않았다.
