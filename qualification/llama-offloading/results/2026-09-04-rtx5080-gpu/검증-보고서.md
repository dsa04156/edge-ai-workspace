# Llama 3.2 1B RTX 5080 GPU 대체 서버 검증 보고서

> 측정일: 2026-09-04  
> 실제 장비: `etri-ser0002-cgnmsb`, x86, NVIDIA GeForce RTX 5080 16GiB  
> 논리 역할: Spark 대체  
> 주의: 이 서버는 실제 NVIDIA DGX Spark가 아니므로 아래 값은 DGX Spark 성능값이 아니다.

## ELI5 요약

Orin Nano 계산대에 줄이 길어질 때 쓸 아주 빠른 보조 계산대를 시험했다. 보조 계산대가 이미
켜져 있으면 짧은 요청도 약 22ms 만에 끝났지만, 모델 파일만 남겨 둔 상태에서는 처음 켜는 데
평균 1.85초가 들었다. 그래서 Nano 앞에 약 9건 이상 밀렸을 때부터 첫 요청도 이득이고,
15% 이상 빨라지려면 약 11건이 밀려 있어야 한다.

모델 파일까지 매번 지우는 Cold 방식은 평균 26.98초가 걸렸다. 짧은 burst마다 Cold worker를
켜는 것은 손해다. 모델 파일을 로컬에 남기는 Cached 방식이 Cold보다 평균 25.13초, 93.2%
빨랐다.

## 시험 조건과 경계

- 모델: `llama3.2:1b`
- digest: `baf6a787fdffd633537aa2eb51cfd54cb93ff08e28040095462bb63daf552878`
- backend: Ollama CUDA, `ollama ps`의 `100% GPU` 확인
- prompt와 최대 출력: Nano·RTX 5060 Ti 시험과 동일, 최대 8토큰
- worker concurrency: 1
- client concurrency: 1, 2, 4, 8, 16, 32
- 반복: 조건별 12초, 무작위 순서 3블록
- 측정 요청: warm-up 제외 10,766건, 오류 3건
- node RTT: ICMP 30회 평균 0.286ms, 손실 0%

RTX 5080을 쓰던 `sensor-anomaly-inference-server1`은 사용자 승인 아래 시험 동안만 0개로
내렸다. 시험 후 Llama worker를 0개로 내리고 센서 서비스를 원래 1/1 Ready, CUDA RTX 5080,
GPU 예약 1/1 상태로 복구했다. 이 임시 변경은 Llama가 센서 서비스와 GPU를 공유한 시험이
아니라 RTX 5080을 단독 사용한 자격시험이다.

- SLO capacity: 동시 요청 16
- first overload: 동시 요청 32. p95 TTFT는 1,500ms 아래지만 3건 오류가 발생했다.
- 관측 최대 처리량: 50.006 req/s
- 단독 중앙 생성속도: 540.358 tokens/s
- 생성속도 저하 보조선: 432.286 tokens/s
- 초기 대체 서버 압력 신호: `queue_length >= 16` 또는 TTFT 1,500ms 초과가 2초 지속

concurrency 32의 오류는 첫 블록 3건에만 발생했고 뒤의 두 블록은 오류 0이었다. 따라서
“항상 실패”라고 단정하지 않지만, 오류 0을 요구하는 admission 기준에서는 16까지만 안전
범위로 둔다.

## GPU 자원 표본

별도 18초 동안 동시 요청 16을 유지하며 `nvidia-smi` 40개 표본을 0.5초 간격으로 수집했다.

| 항목 | 값 |
|---|---:|
| GPU utilization 평균 / 최대 | 69.8% / 80.0% |
| ACTIVE GPU memory | 1,673MiB |
| CACHED GPU memory | 16MiB |
| runner 반환 GPU memory | 1,657MiB |
| 전력 평균 / 최대 | 185.1W / 204.6W |
| 최대 온도 | 57°C |

평균 GPU utilization과 전력에는 부하 시작 전과 종료 뒤 0% 표본도 포함한다. CACHED 값은
모델 runner를 내린 직후의 장치 기준값이며, Pod까지 0개로 내리면 Kubernetes GPU 예약도
0으로 반환됐다.

## Activation 비교

| 방식 | 반복 | activation 평균 | 개별값 | download 평균 | GPU load 평균 |
|---|---:|---:|---|---:|---:|
| Cold On-Demand | 3 | 26.980초 | 35.085 / 19.816 / 26.040초 | 19.890초 | 7.086초 |
| Cached On-Demand | 3 | 1.847초 | 1.873 / 1.959 / 1.711초 | 0초 | 1.844초 |

첫 Cold activation의 GPU load는 17.493초로 이후 약 1.9초보다 컸다. 첫 CUDA/model
first-touch 비용이 포함된 실제 최초 요청 위험이므로 평균에서 제외하지 않았다. Cached는
Cold보다 평균 25.133초, 93.2% 빠르다.

현재 Kubernetes manifest의 모델 cache는 Pod writable layer에 있다. runner만 내리는 동안에는
CACHED가 유지되지만 Deployment를 0개로 내리면 cache도 사라진다. 실제 Method C를 구현하려면
노드 local SSD 또는 PVC에 checkpoint를 영속해야 한다.

## Nano와 비교 및 break-even

| 항목 | Orin Nano GPU | RTX 5080 x86 대체 | 차이 |
|---|---:|---:|---:|
| 단독 p95 전체 지연 | 208.0ms | 23.8ms | 대체 서버가 88.6% 짧음 |
| 단독 중앙 전체 지연 | 198.4ms | 21.9ms | 대체 서버가 89.0% 짧음 |
| 최대 처리량 | 5.070 req/s | 50.006 req/s | 대체 서버가 9.86배 |
| 단독 중앙 tokens/s | 49.352 | 540.358 | 대체 서버가 10.95배 |
| TTFT SLO capacity | 동시 요청 8 | 동시 요청 16 | 대체 서버가 2배 |

Nano 중앙 서비스시간 198.4045ms, 대체 서버 21.904ms, ICMP RTT 평균 0.286ms와 반복
activation 평균을 사용한 첫 offload 요청의 근사 break-even은 다음과 같다.

| 방식 | 원격 첫 완료 예상 | Gain > 0인 Nano 선행 대기 | 15% 이득에 필요한 선행 대기 |
|---|---:|---:|---:|
| Always-On | 22.2ms | 0건 | 0건 |
| Cached On-Demand | 1,869.5ms | 9건 | 11건 |
| Cold On-Demand | 27,002.5ms | 136건 | 160건 |

요청 하나당 Nano 대비 중앙 서비스시간 절감은 약 176.5ms다. 이 절감만으로 activation 비용을
상쇄하려면 Cached는 약 11건, Cold는 약 153건의 지속 workload가 필요하다. 실제 controller는
prompt 길이, 최신 queue wait, RTT와 대상 queue를 매 요청 다시 반영해야 한다.

두 worker가 이미 ACTIVE이고 backlog가 충분하면 Nano+RTX 5080 단순 합산 상한은 약
55.075 req/s로 Nano-only보다 약 986.4% 높다. Nano+RTX 5060 Ti+RTX 5080의 세 worker 단순
합산은 약 60.382 req/s, Nano-only 대비 약 1,091% 높다. 이는 독립 측정값의 합산 근사이며
세 노드를 동시에 쓴 동적 burst 실측 결과가 아니다.

## 대체 서버끼리 비교

| 항목 | RTX 5060 Ti, AGX 대체 | RTX 5080, Spark 대체 |
|---|---:|---:|
| 최대 처리량 | 5.306 req/s | 50.006 req/s |
| p95 단독 지연 | 220.5ms | 23.8ms |
| Cached activation | 2.329초 | 1.847초 |
| Cold activation | 19.074초 | 26.980초 |

RTX 5080 대체 서버는 Cached activation이 20.7% 짧고 최대 처리량은 9.42배였다. 반면
Cold activation은 다운로드 변동과 첫-touch 비용 때문에 더 길었다. RTX 5060 시험은 호스트
Ollama 0.32.5, RTX 5080 시험은 Kubernetes 컨테이너 Ollama였으므로 이 차이를 순수 GPU 세대
차이로 해석하지 않는다.

## 결론

1. Nano 자체 부하 검토 기준은 그대로 `queue_length >= 8`, TTFT 1,500ms,
   tokens/s 39.5 이하가 2초 지속이다.
2. RTX 5080 대체 worker는 오류 0 기준 concurrency 16까지 허용하고 32는 보내지 않는다.
3. 이미 ACTIVE라면 새 요청 하나부터 Nano보다 빠르지만 Always-On은 idle VRAM 약 1,657MiB를
   더 점유한다.
4. Cached는 Nano 선행 대기 9건에서 gain이 양수가 되고 11건에서 15% 이득 gate를 넘는다.
5. Cold는 선행 대기 136~160건 또는 약 153건 이상 지속 workload가 아니면 켜지 않는다.
6. 짧은 burst에는 remote activation을 하지 않으며, 예상 burst가 11건 미만이면 Cached도
   Nano-only가 낫다.
7. 현재 대체 장비 중에는 RTX 5080 Spark 역할이 activation 대비 성능 향상이 가장 크다.
8. 실제 Jetson AGX Orin·NVIDIA DGX Spark에서는 같은 runtime과 local SSD cache로 다시
   측정해야 최종 장비 선택 기준이 된다.
