# Orin Nano·AGX Orin·DGX Spark 다중 모델 성능측정

## Material Passport

- Material ID: multimodel-three-devices-20260910
- Type: code experiment / fixed-work GPU serving benchmark
- Source: 사용자 요청, 기존 Llama 1B 실험기와 동일 토큰 생성 규칙
- Processing: 실제 장비 GPU 실행 → 요청별 원시 기록 → 조건별 기술통계
- Verification: 계획은 측정 성공의 근거가 아니다. 최종 `verification.json`을 확인한다.

## 질문과 경계

같은 크기의 추론 요청을 처리할 때 모델과 실제 장비에 따라 응답시간·대기시간·처리량이
얼마나 달라지는지 측정한다. 대상은 **Orin Nano, AGX Orin, DGX Spark GB10** 세 대다.
RTX 대체 장비에서는 실행하지 않는다.

기존 [Llama 장비별 GPU 성능측정](../../docs/Llama-장비별-GPU-성능측정.md)의
고정 작업량 실험을 확장한다. 정답 데이터가 있는 문제집·생산품질 모델 정확도 평가가 아니다.
모델 간 정답률·추론 능력 순위, 자동 오프로딩 정책, 네트워크 경로 성능,
실행 중 추론/KV-cache 이전은 이 실험의 결론이 아니다.

## 모델과 비교 조건

모든 모델은 Instruct 계열 **Q8_0 GGUF**다. 정확한 파일 SHA256·크기·registry manifest를
`models.json`에 동결하며 세 장비에서 파일 해시를 검증한다.

| 계열 | 크기 | 공식 배포 태그 |
|---|---|---|
| Llama 3.2 | 1B | `llama3.2:1b-instruct-q8_0` |
| Llama 3.2 | 3B | `llama3.2:3b-instruct-q8_0` |
| Qwen 2.5 | 0.5B | `qwen2.5:0.5b-instruct-q8_0` |
| Qwen 2.5 | 1.5B | `qwen2.5:1.5b-instruct-q8_0` |
| Qwen 2.5 | 3B | `qwen2.5:3b-instruct-q8_0` |
| Gemma 2 | 2B | `gemma2:2b-instruct-q8_0` |

출처는 각 manifest의 `source` URL이다. 모델 파일 크기와 명목 파라미터 수는 다른 값이다.
원본 학습 체크포인트 revision과 GGUF 변환 이력은 이 실험에서 검증하지 않는다.

- 런타임: 기존 `llama-server d222767c7`, context 4096, slot 1, thread 4,
  batch/ubatch 512/128, f16 KV, flash attention off.
- 각 장비의 기존 CUDA backend와 OS/드라이버를 유지한다. 전력 모드를 변경하지 않는다.
- 장비 내 API 컨테이너에서 같은 Pod/host network의 loopback HTTP로 요청한다.
  관리용 Kubernetes exec 왕복은 개별 추론 지연 측정에 포함하지 않는다.
- 입력 512·출력 128토큰, 동시 요청 **1·2·4·8**.
- 길이 변화: 입력128/출력64, 입력2048/출력128, 입력512/출력256 각 동시1.
- 한 모델·장비·회차당 준비 운동 1건, 측정 **18건**.
- 세 회차: 첫 회차는 파일 크기 순으로 호환성을 확인하고 이후 두 회차는 seed 20260910으로
  모델 순서를 섞는다. 각 회차의 조건 순서도 seed로 섞는다.
- 계획 합계: **6모델 × 3장비 × 3회차 = 54개 실행**, 측정 **972건**, 준비 운동 54건.
- 입력은 기존 factory sensor 텍스트 생성기(seed 20260908)를 각 모델 tokenizer로 자른다.
  **모델 간 토큰 ID나 의미상 동일한 문장 길이를 보장하지 않는다.** 동일 모델의 세 장비 입력
  fixture는 완전히 일치해야 한다. 모델 간 비교는 토큰 수를 맞춘 시스템 성능 비교다.
- `temperature=0`, 고정 seed, EOS 무시로 실제 출력 길이를 고정한다.
  `cache_prompt=false`, `cache_n=0`과 실제 입력·출력 토큰 수를 모든 요청에서 검증한다.

## 실행과 복구

각 장비의 모델 다운로드·파일 검증이 모두 끝나야 그 장비의 GPU 측정을 시작한다.
한 장비에서 다운로드와 측정을 겹치지 않는다. 다른 장비의 다운로드는 병행할 수 있으며,
추론의 측정 경로는 장비 내부다.

기존 `platform-runtime/llama-inference` RuntimeService의 `suspended`만 한시적으로 켠다.
UID와 이전 값을 검증한 JSON Patch를 사용한다. 기존 요청을 drain하고 모델이 해제된 것을
확인한 다음 별도 native 서버를 실행한다. 공통 operator 전체, 센서/EdgeX, GPU 예약,
Pod 정의, host 설정은 변경하지 않는다. 각 셀 종료 후 소유 모델·포트의 PID를 확인해 종료한다.
끝에는 `suspended=false`와 `Serving`을 확인하고 Pod UID·재시작 상태를 전후 비교한다.

Native 서버별 900초 제한과 실행기 소멸 후 복구 watchdog을 둔다. 요청 제한은 180초이며,
관측 온도 80°C 이상 또는 관측 가용 RAM 700MiB 미만이면 중단한다. 간헐적인 관측이므로
샘플 사이의 온도·메모리 최고/최저치를 보장하지 않는다. 실패 시 해당 장비의 이후 실행을
중단하고 원시 기록을 보존한다. CPU fallback이나 성공 값으로 대체하지 않는다.

## 지표와 해석

- 단일 요청: 세 회차 원시 값, 중앙값과 범위. n=3의 p95를 운영 p95로 쓰지 않는다.
- 동시8: 대기를 포함한 n=24 표본 p95, 첫 토큰 지연.
- 처리량: 조건별 실제 wave 시간 합으로 나눈 성공 요청/출력 토큰 수.
  모델 교체·다른 조건 측정·다운로드 대기 시간은 처리량 분모에 섞지 않는다.
- 실패·미실행·준비 운동은 각각 구분한다. 실패 요청을 예정 건수에서 지우지 않는다.
- 메모리: 런타임 로그의 GPU model buffer와 프로세스 RSS를 구분한다.
  통합 메모리 장비에서 GPU 전용 메모리/장치 전체 메모리와 같다고 해석하지 않는다.
- 기동: 관리 실행 시작→GPU health 관측의 복합 시간으로 기록한다. Kubernetes exec 관측
  비용과 polling 해상도를 포함하므로 순수 모델 파일 로딩 시간으로 부르지 않는다.
- 세 회차는 같은 날 같은 세션의 반복이다. 독립 날짜 반복·긴 지속 부하·holdout이 없으므로
  통계적 유의성, 최대 지속 처리량, 운영 전환 임계값을 확정하지 않는다.

## 재현 코드와 결과

- `multimodel_prepare.py`: 공식 registry 모델 파일·manifest 확보 및 SHA256 검증.
- `multimodel_cluster.py`: 고정 세 장비 파일 준비, 기존 서비스 일시정지/복구와 실험 수명주기.
- `multimodel_client.py`: 기존 `bench.dataset/stream`을 사용하는 장비 내 요청 발생기.
- `multimodel_report.py`: 원시 기록에서 비교표·CSV·검증 결과 재계산.
- `multimodel_figures.py`: 세 회차의 실제 값과 표본 p95 시각화.

준비 단계 a/b의 전송/접속 실패는 모델 성능 실패와 구분한다. 최초 측정 a는 Spark Qwen 0.5B
18건을 완료했지만 다음 셀의 포트 재사용 검사에서 중단됐다. `SO_REUSEADDR`를 적용한
새 실행 b는 전체 계획을 다시 수행한다. a를 삭제하거나 b와 유리하게 혼합하지 않는다.
최종 성공 여부는 `results/multimodel-three-devices-20260910-b/verification.json` 및
서비스 복구 증거가 생성된 후에만 보고한다.

### 실행 중 확인된 변경과 추적

b의 Spark Llama 3B 첫 회차는 호스트 thermal zone 81.1°C를 관측해 중단했다.
완료되지 않은 13개 실행을 `multimodel_spark_cooled.py`의 c 경로로 이어서 수행하며,
준비 운동과 각 조건 전에 관측 온도가 모두 60°C 이하가 될 때까지 기다린다.
냉각 대기는 별도 기록하며 요청 지연과 wave 처리량에 포함하지 않는다.

b의 Nano Qwen 3B 첫 회차는 관리 exec 연결이 끊겼다. 9개 성공 요청, 진행 중 terminal
기록이 유실된 1개, 미시작 8개를 구분해 보존했다. GPU 실행 프로세스가 남은 사실을
확인했으며 이 사건을 모델 OOM으로 분류하지 않는다. 미완료 14개 실행은
`multimodel_detached.py`의 d 경로에서 장비 내부 timeout·프로세스·tmpfs 로그를 사용한다.
Nano에도 조건 전 60°C 냉각 기준을 적용한다. 관리 조회만 재확인하며 추론은 재시도하지 않는다.
d의 첫 실행은 관리 연결이 다시 끊겼지만 장비 내 18개 요청이 완료되어 결과와 종료 증거를
회수했다. 해당 실행의 연속 자원 시계열 공백은 결과의 한계로 남긴다.

최종 집계는 b에서 완료된 실행과 c/d의 미완료 회차 후속 실행을 결합한다. 같은 셀에
완료된 기록이 둘 이상 있으면 집계기가 오류를 내므로 속도가 유리한 결과를 선택하지 않는다.
실패·미전송·기록 유실은 `aborted-attempt-requests.json`과 검증 JSON에 별도로 남긴다.
기존 b 실행기 종료 후에도 d가 남아 있으면 마지막 d 실행 종료 시 원래 서비스를 복구한다.
`multimodel_final_state.py`로 모든 측정 종료 후 서비스 spec·Serving·Pod/컨테이너 동일성·
실험용 포트/프로세스 부재를 다시 확인한다. 복구 파일 존재만으로 복구 성공을 판정하지 않는다.

완료된 원시 기록을 다시 집계하는 명령은 다음과 같다. 모델·서비스 실행은 하지 않는다.
