# AGX Orin time-slicing 실시스템 검증

2026-09-08 사용자 승인 후 `etri-dev0005-jetagx`에 적용했다.
AGX Orin 64GB에서 독립 Pod들이 GPU를 공유할 수 있는 기반을 검증했다.
현재 옥동 AI 서비스 두 종류의 모델·성능·실공장 실증을 완료했다는 의미는 아니다.

| JetPack / L4T | `7.2.1-b49` / `39.2.1-20260806224157` |
| Kernel / containerd | `6.8.12-1021-tegra` / `2.3.4` |
| NVIDIA Container Toolkit | `1.19.1-1` |
| KubeEdge | `v1.23.0`, node `v1.32.10-kubeedge-v1.23.0` |
| GPU UUID | `375b321a186258ce8355062de84a605f` |
| NVIDIA plugin | `v0.19.0`, arm64 digest `d2569d771ea77b94371b58e430fbf4a36ac7d2a79874cd0c5617ebd9cb1da220` |
| plugin 설정 | `tegra`, `envvar`, device ID `index`, time-slicing replicas `2` |

| 적용 경로 | `edge-orch/nvidia-device-plugin/jetson/`, 별도 수동 apply |

서버용 NVIDIA 플러그인은 2/2 Ready를 유지했고 서버 GPU 자원은 각각
`nvidia.com/gpu: 1`이다. 과거 HAMi 운영 메모와 달리 이번 관측 시점에는
HAMi DaemonSet과 Argo CD Application이 없었다. 서버 GPU 구성은 변경하지 않았다.
Nano의 센서/추론 서비스도 이 작업의 변경 대상이 아니다.

## 런타임 연결 문제와 처리

처음에는 AGX 전용 `RuntimeClass/nvidia-jetson`을 생성했다. Kubernetes API에는
객체가 있었지만 EdgeCore에서 `runtimeclass.node.k8s.io "nvidia-jetson" not found`가
반복돼 PodSandbox를 생성하지 못했다. GPU 드라이버 오류가 아닌 RuntimeClass 조회
경계의 실패다. 최종 설정에서는 RuntimeClass를 제거했다.

공식 `nvidia-ctk runtime configure --runtime=containerd --set-as-default`를 사용해
AGX 호스트의 기본 runtime을 NVIDIA로 설정하고 containerd를 재시작했다.
기존 containerd 설정을 `/var/backups/jetson-timeslicing-20260908/`에 백업했다.
Toolkit이 생성한 version 2 설정은 containerd 2.3.4에서 migration 경고와
미사용 `runtime_engine`/`runtime_root` 경고를 출력하지만, 실제 NVIDIA handler·CRI·
EdgeCore와 CUDA Pod 실행이 정상 동작했다. 경고 제거를 위한 전체 런타임 설정
정리는 이번 범위에 포함하지 않았다.

## 실제 CUDA 시험

두 Pod가 각각 독립 CUDA context에서 PTX kernel을 실행했다. 256개 정수 배열에
각각 1을 더하고 매번 전체 배열과 checksum `32896`을 확인했다. 약 0.2초 간격,
60초의 작은 작업이며 GPU 포화 성능 시험이 아니다.

| 시험 | 결과 |
|---|---|
| `cuda-share-a` | 299회 계산·검증, `passed`, exit 0, restart 0 |
| `cuda-share-b` | 299회 계산·검증, `passed`, exit 0, restart 0 |
| 같은 물리 GPU | 두 Pod의 CUDA UUID 동일 |
| 동시 실행 구간 | CUDA context와 반복 계산 구간이 **59.563초** 겹침 |
| 세 번째 `cuda-share-c` | `Insufficient nvidia.com/gpu.shared`로 Pending, 슬롯 반환 후 25회 계산·검증, exit 0 |
| GPU 미요청 `cuda-no-request` | `driver_not_injected`, GPU 접근 없음, exit 0 |

두 context가 활성화된 기간의 겹침은 증명하지만, 두 kernel이 정확히 같은 순간에
실행됐다는 하드웨어 동시성·50:50 분배·일정 지연 보장으로 해석하지 않는다.
Probe 이미지는 Python 3.12 slim trixie의 arm64 immutable digest이며 실제 Pod
`imageID`와 일치했다. 시험 Pod에 privileged, hostPath, 수동 GPU device mount 또는
`NVIDIA_VISIBLE_DEVICES=all`을 추가하지 않았다.
