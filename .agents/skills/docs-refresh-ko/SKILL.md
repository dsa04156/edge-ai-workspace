# 문서 최신화 및 한국어 정리

## 목표

문서 수를 무조건 줄이는 것이 아니라 다음 결과를 만든다.

1. 처음 보는 사람이 최신 기준 문서를 바로 찾는다.
2. 현재 동작, 후속 설계, 과거 기록이 섞이지 않는다.
3. 문서가 실제 코드·배포 manifest·테스트와 일치한다.
4. 한국어 파일명과 제목을 사용하되 기술 식별자는 정확히 보존한다.
5. 로컬 HTML 생성과 실제 웹 배포를 구분해 검증한다.

## 프로젝트 기준 문서

작업 시작 시 다음 문서를 우선 읽는다. 경로가 바뀌었으면 `find`와 `search`로 한국어 제목의 후속 파일을 찾는다.

- `AGENTS.md`
- `docs/문서-안내.md`
- `docs/프로젝트-범위.md`
- `docs/저장소-구조.md`
- `docs/문서-정리-계획.md`
- 변경 주제에 직접 연결된 운영 절차와 정책 문서

현재 이 프로젝트의 물리 디바이스 권위는 EdgeX, 노드·워크로드 권위는 KubeEdge다. 레거시 MapperFramework, KubeEdge Device plane, 워크플로·오프로딩 실험을 현재 기능으로 승격하지 않는다.

## 최신성 판단 우선순위

문서 수정 시 단순한 파일 수정 시각을 최신성 근거로 사용하지 않는다. 다음 순서로 사실을 확인한다.

1. 현재 사용자 지시와 승인된 범위
2. 실제 실행되는 코드, root 배포 진입점, manifest render, 테스트 계약
3. live read-only evidence가 있으면 실제 배포 상태
4. `프로젝트-범위.md`, `저장소-구조.md` 등 현재 정책 문서
5. 구현과 일치하는 승인된 설계 명세
6. 계획 문서, 일일 기록, 과거 보고서

코드·manifest와 정책 문서가 충돌하면 조용히 한쪽을 선택하지 않는다. 실제 구현과 문서가 어긋난 사실을 확인하고, 사용자의 최신화 요청이 구현 기준 정렬을 포함할 때만 현재 문서를 갱신한다. 구현되지 않은 계획은 설계 이력으로 남긴다.

## 문서 분류

| 분류 | 의미 | 처리 |
|---|---|---|
| 최신 기준 | 현재 범위, 아키텍처, 정책의 원본 | 문서 홈에서 최우선 노출 |
| 운영 | 실행, 검증, 장애 대응 절차 | 현재 배포와 명령을 검증 |
| 위키 | 질문별 탐색용 합성 문서 | 최신 기준 문서로 링크 |
| 설계 이력 | 미구현 또는 과거 구현 계획·명세 | 현재 완료 근거로 사용 금지 |
| 보관 | 과거 통합, 실험, 논문, 폐기된 운영 기록 | 기본 검색과 문서 홈에서 뒤로 배치 |
| 생성물 | HTML, 검색 색인, 보고서 | 생성기로 재생성하며 직접 편집 금지 |

## 안전 경계

- 먼저 `git status --short`를 확인하고 기존 수정·삭제·미추적 파일을 사용자 작업으로 취급한다.
- 코드 동작은 변경하지 않는다. 문서 경로를 직접 참조하는 생성 스크립트와 테스트는 필요한 범위에서만 함께 수정한다.
- 과거 문서의 역사적 내용은 현재 구조처럼 고쳐 쓰지 않는다. 보관 상태 안내를 추가하고 최신 문서로 연결한다.
- 원본 문서를 영구 삭제하지 않는다. 최신 문서에 내용이 흡수됐고 참조·재현 가치가 없다는 근거와 사용자 승인이 있을 때만 삭제한다.
- 오래된 원본의 기본 처리는 날짜와 상태를 붙여 `docs/archive/`로 이동하는 것이다.
- deterministic generator가 있는 생성물은 이전 출력을 제거한 뒤 즉시 재생성할 수 있다.
- commit, push, image build/push, Kubernetes rollout은 사용자가 그 실행까지 요청한 경우에만 수행한다.

## 한국어 이름 규칙

- Markdown 파일명과 최상위 `# 제목`은 한국어 중심으로 작성한다.
- EdgeX, KubeEdge, MQTT, API, GPU, CI/CD, HAMi 같은 고유 기술명과 코드 식별자는 유지한다.
- 날짜 기반 기록은 `YYYY-MM-DD-한국어-주제.md` 형식을 사용한다.
- 공백 대신 `-`를 사용한다.
- `index.html`, `SKILL.md`, API schema처럼 도구가 요구하는 관례적 파일명은 유지하고 사용자에게 보이는 제목을 한국어로 쓴다.
- 이름을 바꾸기 전에 기존 참조를 모두 검색한다.
- 이름을 바꾼 뒤 Markdown 링크, inline path, 생성기 순서 목록, display-title map, 테스트 fixture, 운영 안내를 모두 갱신한다.

## 실행 절차

### 1. 범위 고정

사용자 요청에서 다음을 추출한다.

- 문서만 수정할지, 문서 참조 스크립트·테스트도 포함할지
- 한국어화 대상이 제목만인지 파일명까지인지
- 오래된 문서를 보관할지 영구 삭제할지
- 로컬 HTML 생성까지만 할지 실제 문서 웹 배포까지 할지

명시가 없으면 보수적으로 다음을 적용한다.

- 문서와 직접 영향받는 생성기·테스트만 수정
- Markdown 파일명과 최상위 제목을 한국어화
- 오래된 원본은 보관하고 삭제하지 않음
- 로컬 HTML 생성과 검증까지만 수행

### 2. 인벤토리 작성

`find`로 문서 원본, 운영 문서, 위키, 설계 이력, 보관 자료, 생성물을 찾는다. `search`로 다음을 확인한다.

- 현재 아키텍처를 설명하는 중복 문서
- 과거 경로를 현재형으로 주장하는 문장
- 영어 문서 파일명과 제목
- 이동 대상 문서의 inbound link
- 생성기와 테스트에 하드코딩된 문서 경로

파일 수, 큰 파일, 중복 후보, 생성물 크기는 필요할 때 Python 또는 프로젝트 도구로 집계한다.

### 3. 실제 최신 상태 확인

문서 주장에 연결된 코드와 배포 경로를 직접 확인한다.

- root Kustomize/Helm/Argo CD 진입점
- node selector와 service endpoint
- 실제 API consumer와 데이터 authority
- 집중 테스트가 고정한 계약
- live 상태를 주장해야 할 때만 read-only cluster/web evidence

설계 문서가 최신 날짜여도 구현과 테스트가 없으면 현재 완료 상태로 쓰지 않는다.

### 4. 정리 계획 수립

수정 전에 내부적으로 다음 표를 만든다.

| 기존 경로 | 새 경로 | 분류 | 조치 | 근거 |
|---|---|---|---|---|
| 기존 최신 문서 | 한국어 경로 | 최신 기준 | 갱신·이름 변경 | 실제 구현 |
| 구형 운영 문서 | 날짜가 붙은 보관 경로 | 보관 | 이동·상태 안내 | topology 변경 |
| 계획·명세 | 설계 이력 경로 | 설계 이력 | 보존 | 미구현 |
| 생성 HTML | 동일 구조의 HTML | 생성물 | 삭제 후 재생성 | deterministic build |

동일한 새 경로가 이미 있거나 이름 충돌이 있으면 중단하고 내용을 비교한다.

### 5. 최신 문서 통합

최소한 다음을 일관되게 갱신한다.

- 문서 홈과 먼저 읽을 순서
- 프로젝트 범위와 저장소 구조
- 현재 데이터 흐름과 책임 경계
- 운영 절차와 완료 evidence gate
- 위키 지식 지도와 주제별 합성 문서
- 문서 정리·보관 정책

같은 현재 아키텍처를 여러 문서에 장황하게 복제하지 않는다. 정책 원본은 상세하게, 위키와 홈은 짧은 요약과 링크로 유지한다.

### 6. 오래된 문서 처리

- 현재 운영 절차로 오해될 수 있는 문서는 날짜가 붙은 보관 경로로 이동한다.
- 첫 제목 아래에 `> 상태: ... 현재 운영 기준이 아니다.` 안내를 추가한다.
- 현재 문서에서 보관 문서로 향하는 링크는 “과거 증거”임을 명시한다.
- 정확히 같은 중복은 canonical 문서를 정하고 다른 위치에는 안내만 남긴다.
- 삭제는 사용자 승인 없이는 수행하지 않는다.

### 7. 생성물 갱신

프로젝트의 문서 생성기를 확인하고 기존 생성 디렉터리를 정리한 뒤 재생성한다. 이 프로젝트의 기본 명령은 다음과 같다.

```bash
python3 scripts/build-docs-html.py
```

생성기가 분류 필터를 지원하면 최소한 `위키`, `최신 기준`, `운영`, `설계 이력`, `보관`을 분리한다. 보관 대형 로그는 기본 검색에서 제외한다.

### 8. 검증

다음 검증을 모두 수행한다.

1. 모든 Markdown 파일명과 최상위 제목에 한국어가 있는지 확인
2. fenced code block을 제외한 상대 Markdown 링크가 실제 파일을 가리키는지 확인
3. 이전 파일명과 구형 현재형 표현이 남았는지 검색
4. 생성 HTML 수와 source Markdown 수가 일치하는지 확인
5. 검색 색인의 모든 path가 실제 source를 가리키는지 확인
6. 문서 생성기 테스트 실행
7. 변경한 현재 아키텍처에 대응하는 manifest/contract 집중 테스트 실행
8. `git diff --check` 실행

이 프로젝트에서 사용 가능한 기본 검증 예시는 다음과 같다.

```bash
python3 scripts/build-docs-html.py
python3 -m unittest tests.test_docs_html_search
```

프로젝트 Python에 pytest가 없으면 이미 존재하는 검증용 가상환경의 pytest를 사용하되 새 dependency를 임의 설치하지 않는다.

### 9. 실제 웹 확인

로컬 `docs/html` 재생성은 실제 웹 반영이 아니다.

- 문서 웹 URL을 read-only로 요청한다.
- HTTP status, `<title>`, 새 한국어 path 존재, 이전 path 잔존 여부를 확인한다.
- image build/push와 Kubernetes rollout을 실행하지 않았다면 “로컬 생성 완료, 라이브 웹 미반영”으로 보고한다.
- 실제 배포를 요청받았으면 이미지 digest와 running Pod `imageID`까지 확인한다.

## 중단 조건

다음 상황에서는 파괴적 정리를 진행하지 않는다.

- 현재 문서와 실제 구현 중 무엇을 권위로 둘지 판단할 근거가 없음
- 이동 대상에 해석되지 않은 사용자 변경이 있음
- 새 경로 충돌 또는 링크 소비자를 찾지 못함
- 생성기 없이 생성물만 대량 삭제해야 함
- live 웹 배포에 필요한 registry/cluster 대상이 불명확함

비파괴적인 인벤토리, 분류, 링크 수정, 최신 문서 통합은 계속 수행한다.

## 결과 보고 형식

간결하게 다음을 보고한다.

- 최신 기준으로 정렬한 아키텍처와 근거
- 한국어화한 source 문서 수
- 보관으로 이동한 문서와 삭제 여부
- 새로 만든 또는 갱신한 문서 진입점
- 생성 HTML과 검색 색인 수
- 테스트, 링크 검사, 공백 검사 결과
- 실제 웹 반영 여부와 확인한 URL
- 남은 불확실성 또는 별도 승인이 필요한 영구 삭제 후보
